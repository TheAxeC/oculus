## 2. The worker's disagreement: lines and connected as ToolButton, not Chip

The reading is right, on both legs.

A line chip would fail the audit. `looseChips()` at `tests/views/chips.test.ts:241-253` reports every `<Chip .../>` whose text contains none of `CHIP_TONES = ['statusTone(', 'typeTone(', 'item.tone']` (`:126`), and `:257` asserts the list is empty over all of `src/lib`. The negative case at `:309` asserts that `<Chip label={one} />`, with no tone at all, is loose. A research line has neither a status tone nor a type tone, so a line chip is loose whether it is given a bespoke tone or none, and the only ways to pass are to widen `CHIP_TONES` or to add a second file to the `helperFiles` allow-list, which `:261` pins to `['views/Gallery.svelte']`. Either is loosening a check, which the spec forbids.

A pressed `Chip` for the type filters is consistent with the same audit. `Controls.svelte:66` is `tone={typeTone(item.type)}`, which is in `CHIP_TONES`, so `looseChips` passes it, and `DESIGN.md:288` ("the chip capsule stays on the status words and the project type alone") names the project type as exactly what the capsule is for. The card-level assertions (`chips.test.ts:330-357`, including "worn twice on the whole card and no more") are over `ProjectCard` and are untouched.

One thing the audit does not cover, and neither does the design line: both are about which *mark* wears the capsule, not about a capsule that is a control. Making the capsule pressable is a new use of the primitive, and the visible cost is that one row now holds two control shapes. That is a shape for you to accept or reverse, not a rule break.

## 3. `filterGraph` correctness, purity and the layout key

Correct on every case asked. Read at `graph.ts:235-254`, with `idsOf`/`joining` at `:220-227` and `measure` at `:198-217`.

- A project with two lines, one filtered out: the line node goes (`:240`), `joining` drops the membership edge whose target is gone (`:243`), and `measure` recomputes the project's degree one lower. Asserted at `tests/state/graph.test.ts:173`.
- A collaborator shared by a kept and a dropped project: kept, with its degree recomputed to the edges that remain. Not covered by any test (`person` sits on `alpha` alone, `graph.test.ts:51-54`), so I verified it with a throwaway probe: `filterGraph` over a graph with `c1: keep->person` and `c2: drop->person` returns nodes `[collaborator::person, line::one, project::keep]`, edges `[c1, m1]`, and `person.degree === 1`.
- `related` edges between a kept and a dropped project: dropped by `joining`, since both ends must be in the kept set. Also untested; confirmed in the same probe (`r1` gone).
- The empty-list rule: `types.size === 0` and `lines.size === 0` keep everything (`:239-240`), and the final prune at `:251-252` removes only a `line` or `collaborator` with no remaining edge, which an unfiltered graph never has (a line id is only minted from a visible project's membership, `graph.ts:110-124`, `:168-178`). Asserted at `graph.test.ts:206` by `toEqual` against the built graph.
- `connected` with no line drawn at all: every project goes and the graph is empty. Confirmed by probe (`{lines:['nosuch'], connected:true}` returns `{nodes: [], edges: []}`). The controls cannot reach it by pressing, because emptying the list means "all" (`Map.svelte:131-134`); a saved state naming a line the registry no longer holds can.

Purity holds. `graph.nodes.filter` keeps references but `measure` returns `{...node}` copies (`:207-214`), and no code anywhere writes a node or an edge field (`grep -rn "node\.degree = \|node\.radius = \|edge\.[a-z]* = " src/lib` prints nothing; `placeInit` at `:325` spreads). My probe deep-compared the input graph before and after and it was unchanged. Note the returned `edges` array is new but its elements are the caller's objects (`measure` passes `edges` straight through); harmless today because nothing mutates an edge.

The layout key. A filtered graph gets its own: `Map.svelte:172` keys the `{#key}` block on `layoutKey(graph.nodes)` of the filtered graph, and `retune()` at `:136-139` removes that same key. The unfiltered graph keeps the layout saved before this package: `layoutKey` is unchanged, it sorts the ids before hashing (`graph.ts:280-283`), and an empty filter leaves the node set identical, so the key string is byte-identical to what main writes today. Asserted at `graph.test.ts:214`.

## 4. `Chip.svelte`'s pressed form

Every existing call site still renders the span. `Controls.svelte:69` is the only `<Chip>` in the tree given an `onclick` (the other hit in `grep -rn "<Chip" -A 8 src/lib` is a `ToolButton`'s `onclick` at `views/collection/EntryCard.svelte:179`), and `Chip.svelte:46` branches on `onclick === undefined`, so every other site takes the unchanged span at `:47-52`. `tests/ui/primitives.test.ts:155-215` renders eight Chip forms with no `onclick` and all still pass (tone custom properties, muted, filled, glyph, no glyph, empty glyph name, the label-cut rule, bracketed in ascii mode). `tests/views/type-scale.test.ts:171` still reads `'src/lib/ui/Chip.svelte': '.chip=fs-sm'` unchanged, because the new rules set no font size.

A11y of the button form is sound: a native `<button type="button">` (`:54-55`), so Enter and Space activate it and it is in the tab order with no `tabindex` trick; `aria-pressed={pressed}` at `:60`, omitted when `pressed` is not passed; `:focus-visible` outline at `:110-113`. Its accessible name is its label text ("active (2)"). Two small points: unlike `ToolButton` it is not wrapped in `Tooltip`, so a type chip has no description beyond its words, and inside `role="toolbar"` (`Toolbar.svelte:16`) there is no roving-tabindex arrow navigation, which is how every other toolbar in the tree already behaves.

Tone rule respected: the button carries the same `toned`/`filled`/`bracketed` classes and the same `--tone` / `--tone-txt` / `--on-tone` custom properties as the span (`:56-62`), so it paints only the pairs `tests/contrast.test.ts` already measures. No new colour and no new token. `.chip.pressable` sets only `font-family: inherit`, `cursor`, hover border and focus outline (`:99-113`); it does not reset `font-weight` or `line-height`, so a pressed chip can sit a hair off its neighbours in a theme whose body weight is not 400.
