## Findings for you

1. **Landing risk, a path another in-flight brief owns.** Q25 removed one line from `config/text/views/project.yml` (`project.helper.edit_source`), and D5's brief names that same file twice, `briefs/D5.md:22` and `:33`. The spec's 2026-09-14 amendment says a brief that lists a path another in-flight brief lists is not dispatched. The removal was forced: `tests/keys.test.ts` fails on a key nothing reads, and the key's only reader was the deleted strip. So the fix is at landing, not in the worktree: whichever of Q25 and D5 lands second must be checked to still have that key absent, or `tests/keys.test.ts` goes red on main.
2. **The plan's Q25 sentence is wider than what was built, and the two docs are written as if it were not.** Venues, Data, Pillars and Domains are each drawn from one hub YAML that `config/sources.yml` names in the same `collections:` list, but `REGISTRY_KEYS` in `data/normalise.ts:49` keeps those four off the generic collection view (they have their own components, `views/Venues.svelte`, `Data.svelte`, `Programs.svelte`, `Domains.svelte`), so they carry no control. The brief scoped the package to the three feeds, LinkedIn, the generic collection views and the Config cards, and the worker did exactly that. The wording is the part to decide: `DESIGN.md:309` and HELP.md's new paragraph both say "every collection view", and HELP.md's table carries `venues` and `data` rows a reader will count as collection views. Either a follow-up package gives those four the control, or the two sentences say which views are meant.
3. **The control draws over a feed whose read failed.** The guards test `data.missing` only, so a feed with `data.error` set (`server/feeds.ts:103-109`) still draws the control. For malformed YAML that is what you want, since opening the file is how it gets fixed. For a feed path that leaves the hub, `readFeedFile` throws (`server/feeds.ts:63`) and the control appears over a path the file route then refuses (`server/files.ts:127`, `inside()` at `:62`), which is a dead control in a misconfigured hub. Nothing is read outside the root either way. The DESIGN line's clause "drawn only where the view holds the file" does not describe the error case.
4. **`viewSourceFile` does no path validation**, by design (`view-source.ts:1-8`): a `..` path or an absolute path in the config is answered as written and lands in the tooltip. The server is the guard, and it holds: `resolveRootPath` resolves both ends through realpath and refuses anything not inside the root. One disagreement worth knowing about: `feedFile` (`server/feeds.ts:50-54`) resolves a configured feed path with `join`, so an absolute value is taken as hub-relative, while `resolveRootPath` uses `resolve`, where an absolute value wins; an absolute `inbox_file` would therefore be read from under the hub and refused as outside when the control opened it. Pre-existing, not introduced here.
