## 1. Acceptance items and decisions not met

**Item 1, the default `~/workspace` root carries a removal control that always refuses.** `src/lib/server/fs.ts:112` synthesises `{key:'workspace', dir:~/workspace}` when nothing names a root. That root is not in `into.fixed()` (`src/routes/api/fs/+server.ts:16`, which is `roots()`), so `shownRoots` (`src/lib/server/fs.ts:120`) marks it `fixed:false`, `src/lib/views/Files.svelte:71` leaves it out of `fixed`, and `src/lib/views/files/Tree.svelte:47` draws the remove control on it. Pressing it reaches `removeRoot` (`src/lib/server/fs.ts:283`), which finds no such key in the saved workspace and answers 400 `no-such-root`, printed as "This workspace has no such root." (`config/text/views/files.yml:15`). The case is exactly the one item 1's default covers: a machine whose `config/sources.yml` names no root.

**Item 2, the tree leaves out more than the brief's list.** `src/lib/server/fs.ts:178` keeps only `entry.isFile() || entry.isDirectory()`, and a `Dirent` for a symbolic link answers false to both, so every symlink under a root is dropped from every listing, in-root ones included. Item 2 names dotfiles, `node_modules`, `__pycache__` and `.git`; the module comment at `src/lib/server/fs.ts:5` names only those. `resolveRootFile` still serves an in-root symlink through `api/file`, so what the tree offers and what the route serves differ. No test, no report line.

**Item 3, the 2 MB cut is characters, not bytes, and happens after the whole file is transferred.** `src/lib/state/fs.svelte.ts:196` awaits `response.text()` for the entire body and then slices at `TEXT_LIMIT` (`src/lib/state/fs.ts:37`), which counts UTF-16 code units. The note the reader sees says "its first 2 MB are shown" (`config/text/views/file.yml:16`), which is wrong for any non-ASCII file, and the window's stated reason at `src/lib/views/File.svelte:22` ("a browser asked to lay out forty megabytes of text stops being a browser") does not hold for the transfer and the decode, only for the layout.

**Decision 4, the pure workspace fold landed on the server, not in the client module.** The brief put `workspaceRoots(config, saved)` in the pure client module. `src/lib/state/fs.ts` has no fold over the workspaces; the equivalents are `savedRoots` (`src/lib/server/fs.ts:112`, which reads the file and is not pure) and `shownRoots` (`src/lib/server/fs.ts:120`). The report's decision-4 row says "taken, under different module names" and does not say the part moved from the client to the server.

Items 1 (rest), 2 (rest), 3 (rest), 4 and decisions 1, 2, 3 are met as the report describes; checked `workspaces` in `LOCAL_KEYS` at `src/lib/data/sources/config.ts:52`, the eleven registrations in `src/lib/views/file/languages.ts:36`, and the `[root, path]` instance identity at `src/lib/state/instance.ts:73`.

## 4. Defects in the new code

**A saved workspace can redirect the hub root.** `src/lib/server/files.ts:252` filters `added` against the configured keys only, and `withHub` (`src/lib/server/files.ts:246`) returns the list untouched when it already holds a `hub` key. A `workspaces.json` carrying a root keyed `hub` therefore replaces the hub root for `api/file` and for the listing, and `readSaved` (`src/lib/server/fs.ts:63`) validates only that key and dir are non-empty strings. The endpoint cannot mint such a key (`addRoot` takes `taken` from `into.all()` at `src/lib/server/fs.ts:276`), so it needs a hand-edited or corrupt file. The comment at `src/lib/server/files.ts:247` says the configured key wins, which is not true of the hub key, the one key no config names.

**Read-modify-write race on the workspaces file.** `handleFsWrite` reads at `src/lib/server/fs.ts:335` and every action writes the whole object back through `writeSaved` (`src/lib/server/fs.ts:97`). Two POSTs in flight lose one of the two changes; the atomic replace prevents a half-written file, not a lost update. `src/lib/server/sessions/overrides.ts:70` has the same shape, so it matches the tree. Neither a test nor the report names it.

**The file route does its disk work before the origin check.** `src/routes/api/file/[root]/[...path]/+server.ts:13` resolves the workspaces file and the roots, and only then `serveFile` runs `sameOrigin` (`src/lib/server/files.ts:194`), so a cross-origin request costs two `loadConfig`, one `loadLocal` and one read of `workspaces.json` before its 403.

**The config is read more than the report says.** Counted from the code, not measured: the file route calls `configuredRoots()` and `roots()`, and `roots()` calls `configuredRoots()` again (`src/lib/server/files.ts:254`), so two `loadConfig` per asset request where there was one. `GET /api/fs` with no root calls `into.fixed()` and `into.all()` (`src/lib/server/fs.ts:206`, `:217`), which is three `loadConfig`, two `loadLocal` and two reads of `workspaces.json` (`src/lib/server/fs.ts:205` and `:113`). `loadConfig` parses all 42 files under `config/` (`find config -name '*.yml' | wc -l`). `ServerContext` already carries `config` and `local` (`src/lib/server/context.ts:41`), which is where the brief's dispatch re-read said the roots should come from.

**A read failure is drawn as "no roots" or as an empty folder.** `Listing.error` and `WorkspacesState.error` (`src/lib/state/fs.svelte.ts:22`, `:32`) have no reader anywhere: `src/lib/views/Files.svelte:187` branches on `saved.loading` and `rows.length === 0` alone, so a 403 or a 500 on `GET /api/fs` prints "No roots yet. Add a folder to this workspace." and a folder that cannot be read draws as an open folder holding nothing. `FsStore.listing` (`src/lib/state/fs.svelte.ts:59`) is exported and nothing calls it.

**An in-flight listing can resurrect itself after an invalidate, and file text is never invalidated.** `invalidate()` (`src/lib/state/fs.svelte.ts:213`) clears `listings`, but a request already queued at `src/lib/state/fs.svelte.ts:98` writes its answer in when it lands with no generation check, so a listing fetched before a remove-root reappears after it. `texts` is not cleared at all, so a file's tab holds the bytes it first read for the life of the page, and `api/file` answers `cache-control: private, max-age=60` (`src/lib/server/files.ts:171`), so even a freshly opened tab can be a minute stale.

**Every toolbar write blanks the tree.** `act()` calls `invalidate()` on success (`src/lib/state/fs.svelte.ts:224`), which sets `held.workspaces = null`, so `src/lib/views/Files.svelte:187` replaces the whole tree with "Reading..." and re-fetches every open folder after each add, remove, save and select.

**The store's SSR premise is wrong.** `src/lib/state/fs.svelte.ts:93` says "a server rendering has none and asks for nothing"; Node carries a global `fetch`, so the microtask does run on the server, the relative URL throws, and the throw is written into the reader-facing `error` state. The worker observed exactly this under test and recorded it as a limitation without correcting the comment. `src/lib/state/docs.svelte.ts:101` carries the same wrong premise, so the premise is the tree's rather than this package's.

**The PDF frame is unverified in a browser.** `src/lib/views/File.svelte:87` renders `sandbox=""`. Chrome draws a PDF through an internal plugin, and a fully restrictive sandbox can leave the frame blank. The only check is that the attribute is empty (`tests/views/file.test.ts:56`), and the browser case opens a markdown file only (`tests/browser/files.spec.ts:12`), so item 3's PDF is not shown to render anywhere. Not verifiable either way without a browser.

**`addRoot` compares raw directory strings.** `src/lib/server/fs.ts:271` refuses `root-held` by `one.dir === dir` after `expandHome`, with no `realpathSync` and no separator normalisation, so a trailing slash or a symlinked path to the same folder is accepted a second time under a second key.

**A workspace root whose key collides with a configured key vanishes in silence**, dropped at `src/lib/server/files.ts:256` and again by `shownRoots` (`src/lib/server/fs.ts:122`), with no refusal and nothing in the answer to say so.

The report's own limitations, judged: the two highlighters, `api/open` not widened, no watcher on an open folder, no arrow-key walk of the tree, the view tests running against the real global `fetch`, and the browser case's coverage are all consequences of the brief and are stated plainly. The `~/workspace` constant is fine as reasoned, but see finding 1a. The config read twice is a defect inside the brief and is understated (see above). The highlight.js registry is fine: it is written once at import, `src/lib/views/file/languages.ts` is outside the prefixes `tests/boundaries.test.ts:128` checks, and `tests/state/fs.test.ts:63` cross-checks the registry against the extension map. The report does not name the invalidate race, the tree blanking on every write, the unread error states, or the concurrent-write race.
