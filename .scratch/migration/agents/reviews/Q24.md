## Does the map move for a reader who never tuned

The mount-time placement is reproduced exactly. `mapLayout` (`src/lib/state/graph.ts:634`) builds one `seededRandom(layoutSeed(graph.nodes))`, and `layoutSeed` (`:613`) is character-sum over `layoutKey(nodes)`, which is what the component's own `numericSeed(key)` was. `DEFAULT_BOUNDS` is `{ width: 1000, height: 680, pad: 48 }` (`src/lib/state/graph.ts:76`), byte-identical to the component's removed `BOUNDS`. The untuned path runs `optimize(graph, rng, 12, DEFAULT_BOUNDS)` and the tuned path `bestLayout(graph, rng, 8, 150, tuned, DEFAULT_BOUNDS)` with the generator still unconsumed, which is what `onMount` ran in each branch. So the settled positions are unchanged in both branches.

The pre-mount `bestLayout(graph, rng, 8, 120, DEFAULT_PHYSICS, BOUNDS)` is gone. It only ever painted the frame `onMount` replaced in the same task, before paint, so no settled position moves by its removal. The report's judgment call 1 is accurate.

Four ways the picture or the cost does change, none of them in the report:

1. **Closing a Map tab now drops the tuning.** `src/lib/state/layout.svelte.ts:529`, `:588` and `:797` call `ui.clearInstanceState(id)` when a pane closes or is replaced, so the tuning goes with the tab. The old per-node-set localStorage item survived a tab close. Reopening a Map tab therefore re-tunes and draws the `optimize` placement where it used to draw the `bestLayout` one, and those two differ (the browser case asserts exactly that at `tests/browser/map.spec.ts:179`).
2. **One tuning slot per pane, so a filter switch overwrites it.** Narrowing by a filter changes `layoutKey`, re-tunes and replaces the whole-graph tuning; filtering back re-tunes again. `optimize` is deterministic on the seed, so the parameters that come back are the same ones and the re-tuned picture is stable; what the reader loses is the reload picture for the set they return to, and the tuning cost is paid at every switch. This follows from the `tuned?: { key, params }` shape the brief itself named (`src/lib/state/graph.ts:662`), so it is the brief's decision rather than a deviation, but it is the sense in which "a filter change re-tunes once" understates it.
3. **Every mount that tunes rewrites the whole ui record.** `keepTuned` goes through `setInstanceState` (`src/lib/state/ui.svelte.ts:283`), whose `save` stringifies the entire ui state including every instance's record into one localStorage item (`:232`). The old code wrote one small item. Not measured.
4. **A reader carrying an old `oculus-map-v1-*` item re-tunes once on the next mount**, which is decision 2 of the brief and is in the report.

## The synchronous tune, measured

Every mount of every Map pane with no saved tuning runs `optimize` inside the render pass: `const chosen = $derived(mapLayout(graph, tuned))` at `src/lib/views/map/Graph.svelte:44`, read by `positions` at `:46` while `placed` is still null. Measured on this machine with node v24.21.0 over a synthetic graph built to the node and edge counts, calling the tree's own `mapLayout`, `optimize` and `bestLayout`:

- 15 nodes, 14 edges (the demo hub's 11 projects plus its lines): `optimize(12)` 30 ms, `bestLayout(8, 150)` 2 ms, the removed pre-mount `bestLayout(8, 120)` 2 ms.
- 53 nodes, 59 edges (a hub the size of Axel's): 72 ms, 13 ms, 11 ms.
- 100 nodes, 122 edges (collaborators on): 233 ms, 42 ms, 35 ms.

So the blocking cost went down, not up: the same `optimize` ran in `onMount` before, which is also before paint, and the 2 to 35 ms pre-mount placement is no longer paid. `src/routes/+layout.ts:2` sets `ssr = false`, so no request pays it.

`chosen` is not recomputed after mount. `onMount` (`src/lib/views/map/Graph.svelte:226`) sets `placed` before calling `ontuned`, so when the write flows back and changes the `tuned` prop, `positions` recomputes from a dirty `placed` and short-circuits on `placed ?? chosen.nodes`, dropping `chosen` from its dependencies; `chosen` has no other reader (`:46`, `:227` to `:229`). This is a laziness argument from the code, not a measurement.

`tests/views/map.test.ts` now pays `optimize` on every server render of `Graph`; the file reports 265 ms of test time, so the suite cost is not material.

## Two things for the orchestrator to take or leave

- `DESIGN.md:304` says "a map narrowed by a filter keeps a placement of its own". There is one slot per pane, so the narrowed map gets a tuning of its own only until the filter changes again; a reader can take the sentence as saying each filter retains its own placement, which the code does not do. Worth tightening at landing.
- `isPhysics` (`src/lib/state/graph.ts:604`) and the `MapLayout` type (`:621`) are exported with no reader outside `graph.ts`, and `layoutSeed` (`:613`) only from `tests/state/graph.test.ts`. No rule in the spec forbids it and the brief asked `isPhysics` to have one home, which it has.
