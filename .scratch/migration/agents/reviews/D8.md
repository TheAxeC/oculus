## Security

Credentials never leave the file: the payload is built at `poll.ts:92-107` from provider, label, status, hint, lastOk, calendars and events; `poll.test.ts:327-333` asserts the serialised payload holds neither the fake access token nor the refresh token nor the client fields. The only log is the status word, matching the HPC poller. The routes answer `{ok}`, `{status}` or a short `{error}`. The callback page is one catalog sentence through `escaped()`; `oauth.test.ts:349-351` asserts it holds none of the code, state, secret or tokens. What reaches the channel by design: the credential file's path as the not-connected hint (shape 2) and a provider's refusal line made of the status and the provider's code alone (`providers.test.ts:163-165`, `:277-281` assert the body's message is not in it).

The callback guard: `routes.ts:139-143` takes the `state` first; `ConnectStates.take` prunes, compares with `timingSafeEqual` and deletes the entry as it reads it; minted per press as 32 random bytes with a ten-minute expiry; the exchange carries `code_verifier`. An unknown, expired or empty state or code answers the 400 page and the fetcher is never called. One overstatement: the comment says the whole-map comparison hides which states exist, but the loop skips on a length mismatch and walks insertion order; not a practical leak with 256-bit states and a handful of entries.

Scopes: `calendar.readonly` and `Calendars.Read offline_access` alone; the consent URL carries only the seven OAuth parameters plus `access_type=offline` and `prompt=consent` for Google or `response_mode=query` for Microsoft (`oauth.test.ts:16-45`, `:51-65`).

`{ action: 'open', event: '<crafted id>' }`: the route never takes an address from the body; `linkFor` is an exact-id lookup in the last published state, links were filtered to `https:` in both readers and are filtered again at the call, so a crafted id, a URL-shaped id or a held `javascript:`, `file:`, `-n` or non-address link answers 400 and opens nothing (`routes.test.ts:52-85`). The most a crafted id reaches is an `https` address from the reader's own calendar.

`macOpen` is not itself the gate: it refuses only a target beginning with `-`; the folder rule stays in `allowed()` and the https rule in the calendar route, so the function's contract is wider than its two callers and a third caller would inherit only the dash check.

Gates on `POST /api/calendar`: origin and token in one expression, 403 before the body is read (`oauth.test.ts:70-90`). The credential file: folder 0700, file written 0600 and chmod after (`oauth.test.ts:238` asserts the mode); the path `join(dir, <key>.json)` with the label limited to `^[a-z0-9][a-z0-9-]*$` by the one producer of `LocalConfig.calendars`, which also runs on a page-side save of `local.yml`; `defaultCalendarDir` has one reader, `context.ts:212`.

A non-2xx behaves correctly. No test covers the path. Nothing in the package reads the credential files of the runners or the Keychain.
