## Acceptance items not met

**Item 4 (reply and archive at Microsoft).** The two Graph writes are addressed without the `/me` resource root the brief names. `src/lib/server/mail/microsoft.ts:174` posts to `${BASE}/messages/${encodeURIComponent(id)}/reply` and `:190` to `${BASE}/messages/${id}/move`, with `BASE = 'https://graph.microsoft.com/v1.0'` (`:26`). Graph has no top-level `/messages` collection; the documented forms are `POST /me/messages/{id}/reply` and `/me/messages/{id}/move`. The same file gets this right for every read (`:95` `${BASE}/me/mailFolders/inbox/messages`, `:113` `${BASE}/me/messages`), so the reads would work and both writes would fail. The test does not catch it because the fake fetcher matches on substrings: `tests/server/mail/write.test.ts:147` routes on `url.includes('/messages/g1/reply')` and `:164` on `'/messages/g1/move'`, which match the wrong URL as happily as the right one. The brief's own wording ("Microsoft `/me/messages/{id}/reply` with `comment`") is what the code should say.

**Item 3 (republish on an outside write).** The acceptance item is "republished on a change from outside (the skill's write)". No test exercises the watcher: `tests/server/mail/poll.test.ts:289` runs with `watchNotes: false` and calls `watcher.republish()` by hand, which is the same function the triage route calls. The fs watch itself (`src/lib/server/mail/poll.ts:283` `startNotesWatch`) is never entered by any test. It also returns without watching when the folder does not exist (`poll.ts:284`, `if (options.watchNotes === false || !existsSync(options.dir)) return;`) and is never retried, so on a machine where `mail_dir` has not been created yet a skill write does not reach the page until the next restart. The worker lists this as a limitation; under the spec's "a risk you name is a task you own" it is a repair, not a footnote.

**Item 2 / the plate rule (Microsoft unlabeled leg).** `microsoft.ts:94-108` sets `$top` to `per_signal` and then filters the answered rows by `categories(row).length === 0`, so the leg yields at most `per_signal` rows *before* the filter and can yield far fewer, or none, when the newest 25 inbox messages all carry a category. Gmail's `has:nouserlabels` (`google.ts:34`) yields 25 *unlabeled* threads. The comment at `microsoft.ts:103-105` states the cost as "one pass over at most `per_signal` rows that have already been read", which is not true of the code: the cap and the filter compose the other way round. Either the leg pages until it holds `per_signal` uncategorised rows, or the comment says plainly that this signal is capped before the filter.
