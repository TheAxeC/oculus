## 3. The note after the change

- `typed` (`Note.svelte:195-208`): computes `first` before touching anything, captures `tab = instance.id` and `named` from the instance label on the first keystroke into this note, sets `touched`, then either writes at once or pokes the wait. Correct order; `first` is read before `touched = true`, so the second keystroke cannot be mistaken for the first.
- `save(made)` (`:216-225`): guards on `draft.id === '' || tab === ''`, writes, sets `failed`/`savedAt`, and restates the tab. It reads no `instance` at all, which is the point of the fix.
- `leave` (`:182-188`): cancels when the note id is empty, when nothing was typed (`tab === ''`) or when the note vanished, otherwise flushes. The `tab === ''` test sits before `vanished(which)`, which matters: `vanished` calls `note(which)` and that schedules a server read (`src/lib/state/fs.svelte.ts:475-481`), so an untyped fresh tab asks the server for nothing when it is left.
- `reset` (`:122-130`) clears `tab` and `named` with the rest. The effect at `:135-139` takes `which = id`, resets, and returns `() => leave(which)`, so the teardown runs with the previous note's `tab` still in place and `reset()` follows it.
- The `fresh` flag is cleared by `restateInstance(tab, { id: draft.id, label: written })` at `:224`, and `restateInstance` replaces the state object (`src/lib/state/layout.svelte.ts:255-259`), so `fresh` is dropped. The saved layout round-trips `state` whole (`src/lib/state/layout/saved.ts:194`), so a fresh tab that was never typed into keeps its flag across a reload.
- `BLANK` (`:61-68`) is used at `:73` as `held = fresh ? BLANK : note(id)`, so `note(id)` is never called for a fresh tab and no read is scheduled.

The defect the worker found and fixed is real and its cause is where the report says. On the base, `save()` read the live prop after the await: `read(instance.state, 'label')` at base `src/lib/views/Note.svelte:200` and `restateInstance(instance.id, ...)` at base `:201`, both after `await saveNote(...)` at base `:196`. A save flushed by `leave()` after the pane had switched therefore restated whichever tab the pane had moved to. The fix closes it: `save` now uses the locals `tab` and `named` only (`:217-224`), captured in `typed` at `:197-200`, and `tests/views/note.test.ts:200` asserts `save` contains no `instance.`. A further benefit of the same change: `restateInstance` is a no-op for an id that is gone (`layout.svelte.ts:256-257`), so a save landing after the tab closed now changes nothing instead of hitting a live tab.

A first keystroke whose write fails: `save` returns at `:220` before `savedAt` and before the restate, so `fresh` stays set and `failed` shows the endpoint's word. The next keystroke has `touched === true`, so `writesNow(true, true)` is false (`src/lib/state/notes.ts:72`) and the retry goes through the 800 ms wait. That much matches the report; see section 6 for what the retry does not do.

A note can no longer be deleted by leaving: `grep -n deleteNote src/lib/views/Note.svelte` prints nothing (exit 1), and `deleteNote` plus `closeRecord` survive only in `Files.svelte:232-236`, the list's confirm path.

A reload of a fresh tab with nothing typed draws empty, not the error line: `held` is `BLANK` with `error: ''`, so the markup takes the field branch at `Note.svelte:249-264` rather than the `held.error` branch at `:246`. `tests/views/note.test.ts:88` holds it, counting fetches: zero for the fresh tab, more than zero for the same tab without the flag, so it fails if `held` goes back to `note(id)`.

`writesNow` for a tab that lost `fresh` but whose file was never written: that state is unreachable in the direction asked, because `fresh` is cleared only at `:224`, after `answer.ok`. The reverse is reachable, and is the defect in section 6.

## 6. Tests missing, and a defect neither the report nor the items name

Defect, `src/lib/views/Note.svelte:222`. The line `if (!made && named === written) return;` uses one condition for two jobs: whether the tab's label needs rewriting, and whether the `fresh` flag needs clearing. After a failed first write (`fresh` still set, `named` still the empty label a fresh tab carries), the retry runs as `save(false)`, and if the note's derived title is still empty at that point (`written` is `''` when the title is blank and `titleOf(body)` finds no non-blank line, `src/lib/state/notes.ts:32-39`), the write succeeds and the function returns at `:222` without restating. The file is then on disk while the tab still carries `fresh`, so a reload draws `BLANK` over a note that exists, and the next keystroke counts as the first (`writesNow(true, false)`) and overwrites the file. It self-heals as soon as the reader types a non-blank first line. Reachable only through a failed first write plus a still-empty title, so the severity is low, but the coupling is wrong; the shape that fixes it is to restate whenever the write succeeded and the instance still carries the flag, for instance `if (!made && !fresh && named === written) return;`.

Pre-existing and not a Q22 regression, but worth knowing since this package moved the code: `savedAt` and `failed` are assigned after the await (`:219-221`) on a component that may by then be drawing another note, so a save flushed by `leave()` can paint the next note's toolbar with "Saved <time>". The base had the same shape at base `:198-199`.

- The timing of the first write. The browser case polls with a 10 second timeout, so a write at the end of the 800 ms wait would also pass; the immediacy rests on `writesNow` plus the source read. The worker says this plainly, and a timing assertion there would be flake.
- The failed-first-write path (flag kept, retry through the wait), which is also where the defect above lives. Nothing covers it at any layer.
- That `fresh` is actually cleared in the layout after a successful write. `tests/views/note.test.ts:192` asserts the restate line exists in the source; no case reads the instance state back after a save.
- The two audit blind spots (a surfaceless partial that itself paints, a partial rendered twice) are by nature invisible to the audit, so they need a fixture case in `tinted.test.ts` if they are ever to be guarded; today nothing in the tree can trip them.

One small duplication, not a defect: `backgroundAlpha` in `tests/browser/files.spec.ts:48-50` repeats `boxAlpha` in `tests/browser/tinted.spec.ts:12-15`, and both wrap `alphaOf` from `tests/browser/style.ts`. The brief asked for the case in `files.spec.ts`, so the placement follows the brief; the helper could live in `style.ts`.
