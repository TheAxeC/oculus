# R17 review

I have read the spec, the brief, the report, and worked the whole diff against the worktree. I did not run any npm command (read-only remit), so the report's checks 1-5 and 9 are unverified by me; checks 6, 7 and 8 I re-ran and they hold.

---

## 1. Behaviour changes in src

**None that change what a reader sees.** Every store body is byte-equivalent after de-indentation and prefixing; I diffed all 22 modules with the store prefixes normalised away and the only non-mechanical edits are these, all inert:

- `state/entities.svelte.ts:52-72` — the seven channel readers went from `held === undefined ? null : (held.payload as X)` to `(payload(ch) as X | undefined) ?? null`. Differs only for a message whose `payload` is `undefined`, which `socket.handle()` rejects at `socket.svelte.ts:228` (`if (!isMap(message.payload)) return;`).
- `state/drag.svelte.ts:6-8` — the `Drop` union's `centre` and `edge` members swapped places. Type-only.

On the specific things you asked me to check:

**Wiring order in `createClientState`** (`state/context.ts:69-91`) is correct: every store is built after the ones it is handed. `socket(entities L70, writes L71)` at L72; `layout(ui L73)` at L74; `drag(layout)` at L75; `terminals(entities, socket, writes)` at L78; `selectors(entities, layout, selection L77)` at L87; `railBadges(entities, feeds L84, hpc L85, selectors L87)` at L88; `registry(layout)` at L90. No cycle: `layout` reads `ui`, `registry` reads `layout`, nothing reads back.

**Nothing new runs at construction.** I scanned every factory body for a top-level call statement; there is none (the only hit was `setContext` inside `provideTipIds`, not the factory). `createClientState()` is pure construction.

**The socket connect, `loadUi`, `loadLayout`** were already in `onMount` and still are (`+page.svelte:139-144`). Unchanged.

**The registry fill** moved from module evaluation of `routes/views.ts` to `+page.svelte:42-46` (`untrack`). `+page.svelte:17` is the only importer of `views.ts` under `src`, so in the built app and the dev server the page fills it, in its script body, before `Workbench` renders. Same frame as before. Under SSR it now builds a per-request registry instead of one shared across requests in the server process, which is the point of the package.

**The write token** is the one place where the path got longer and where I would put the risk. `+page.ts:28` now returns `{ collections, token }` and `+page.svelte:42-52` installs it in an `untrack` block plus an `$effect`. Startup is fine: the `untrack` call sets it before `onMount`, so the socket's first subscription and the first write carry it. The refresh path is the exposure: `writes.svelte.ts:317-319` does

```ts
const { invalidateAll } = await import('$app/navigation');
await invalidateAll();
response = await post(request, path);   // post() reads `token`
```

Previously `+page.ts`'s `load` called `setToken` synchronously, so the fresh token was in place the instant `invalidateAll()` resolved. Now it arrives only when the page's `$effect` flushes. Reading `@sveltejs/kit/src/runtime/client/client.js:473` (`root.$set(navigation_result.props)`) followed by `await Promise.all(promises)` on an empty array, the Svelte flush microtask is queued before `_invalidate`'s continuation, so it should land first. **That is reasoning from the scheduler, not a measurement, and no test exercises it**: `tests/routes/open.test.ts:122` mocks `invalidateAll` and calls `setToken(TOKEN)` inside the mock, so it proves the retry, not the new hop. See item 9.

**Judgment call 2's reason is true.** `state/text.ts:9-10` imports `configGeneration` and `glyphMode`; four `ui/` primitives (`Sash`, `Tabs`, `Glyph`, `Chip`) import `state/text`, and `text.ts:93` reads `glyphMode()` inside `asciiOf()`. `configInstalled()` is called from `+page.ts:27`, where there is no client at all. A per-client generation over a module-level catalog would say a push had landed for one client and not the other. Correct call, and the consequence is worth stating plainly: **two pages in one process share the text catalog, the tone vocabulary, the appearance list and the glyph mode**, so one page's `setGlyphMode` (`shell/Workbench.svelte:169`) would move the other. That is what the brief asked for by keeping the catalogs module-level.

**The tooltip counter as a second context (`TIP_KEY`) rather than a store on the client** is right on the boundary rule: `ui/`'s row is `['ui/**', 'themes/**', 'state/text']`, and putting `state/use` in it would let any primitive read any store. `state/context.ts:91` still builds the instance and the root provides both (`+page.svelte:25-26`). One consequence: `ui/Tooltip.svelte:57` calls `useTipIds().nextTipId()` unguarded, so a `ui/` primitive rendered with no provider now throws where before it used a module counter. Nothing in the tree does that. A side effect in the right direction: SSR and hydration now start the counter at 1 on both sides instead of the server's module counter running on across requests.

## 2. The factories

**Every public export of all 20 state modules plus `views/registry.ts` is present**, either as a member of the exported `*Store` type or as a top-level export. I checked this mechanically: for each module, the set of `export function|const|type` names at `69e1bf54` minus the union of the new `*Store` type members and the new top-level exports is empty for all 20. No old export shape (`export {`, `export let`, `export default`) existed to miss.

**No leak.** Every function the worker left module-level takes no instance state. I read each of judgment call 3's list:

- `drag`: `AT_END`, `THRESHOLD` are constants; `withoutOwn`, `markAt`, `edgeAt` are pure over their arguments (`drag.svelte.ts:26-47`).
- `selection`: `pinnedSession`, `pinnedTerminal` are pure over a passed-in `unknown` (`selection.svelte.ts:22-32`).
- `source`: `sourceAccess`, `sourceTabState`, `sourceFileUrl` pure; `loadSource` is a bare `fetch` with no token and no collection. The split against `saveSource` is exactly right: `saveSource` stayed a method because it goes through `writes.send`, which touches the pending counter, the error and the token.
- `terminals`: `ptyChannel`, `isTerminalId`, `encodeBytes`, `decodeBytes`, `resumeRefusal`, `titleStripper` all pure.
- `selectors`: `folderOf` pure. `registry`: `registrationLabel`, `registrationGlyph` read the module catalog through `lookup()`.

**Nothing pure was promoted to a method.** The functions that are new closures inside a factory (`ui.boundedTextScale/defaultUi/known/save/stringList`, `docs.keyOf/readFrontmatter`, `files.readRows`, `selectors.grouped/sessionsOf`, `rail-badges.projectTypeOrder`, `drag.listen/onKeyDown/onPointerMove/onPointerUp`, `socket.handle/open/strings/subscription`, the nine layout helpers, `writes.post`, `source.updateDraft`, `transcript.load/merge/request`) were all already module-level private functions at `69e1bf54`; I verified each with `grep -cE '^(export )?(async )?function <name>\(' `on the base blob. None of them is exported as a method. The only cost is that a handful of genuinely pure ones (`ui.boundedTextScale`, `ui.known`, `docs.keyOf`, `rail-badges.projectTypeOrder`) are now re-created per client. That is a nit, not a defect.

## 4. The boundaries audit

**The exemption is exactly the three catalogs plus the two runes.** `FROZEN` (`tests/boundaries.test.ts:190-210`) holds the two pre-existing server entries, `text.ts:{catalog,glyphs,ascii}`, seven `tones.ts` maps, five `appearance.ts` bindings, and `generation.svelte.ts:held` / `glyphmode.svelte.ts:held`. Nothing else.

**The regex** (`:168-170`) is the server clause verbatim: `^(?:export )?const (\w+)(?::[^=]+)? = (?:new (?:Map|Set)\b|\{\}|\[\]|\$state)` or `^(?:export )?let (\w+)\b`, applied where `holdsModuleState()` (`:129-138`) is true: `lib/server/`, `routes/`, `lib/state/`, `lib/shell/`, `lib/ui/`, `lib/views/registry.ts`. That is the brief's four client scopes plus the two that were already covered.

**Red on main's tree, green now, both measured.** I re-implemented `findGlobalState` in Python and ran it over `git show 69e1bf54:...` for every source file: **40 violations** on main (`entities:messages`, `layout:{backing,lastActive,store}`, `socket:{socket,live,wanted,channels,listeners,backoff,retry}`, `ui:{store,backing,updateTray,cardMove}`, the five cache stores, `usage-refresh:refusals`, `writes:{state,token}`, `ui/tooltip-target.ts:counter`, `views/registry.ts:registry`, and the rest). The same function over the worktree returns `[]`. The brief's inventory grep also prints only the five FROZEN files.

The audit's known blind spots, none of them a brief item: it does not match `const files = createFiles(createEntities())` (a factory call is not in the pattern), and it reads a component's `<script module>` only, never its instance script — both stated in the comment at `:140-149` and in the report.

**The three table changes** are exactly what the report claims; I diffed the `ALLOWED` block against the base and the only deltas are `'state/context'` and `'state/use'` added to the `shell` row and `'views/registry'`, `'ui/tip-ids'` added to the `state` row. Only `state/context.ts:15-16` imports those two, so the widening is minimal.

**`findShellStores` is sound for the tree as it is, with two escapes.** It matches `const { ... } = client` / `= useState()` (one level of nesting) and `\bclient\.(\w+)`, checking each name against `SHELL_STORES` (`:213-221`: layout, drag, ui, selection, terminals, paletteSource, registry — the shell's row by store name). Every shell file today either names the binding `client` (`ActivityRail:24`, `Palette:22`, `PaneView:29`, `Workbench:39`) or destructures straight off `useState()` (`DropLayer`, `PageStrip`, `UpdateTray`), so it catches everything. It would miss:

- a differently-named binding: `const c = useState(); c.entities.portfolio()`;
- an inline read: `useState().files.files(id)`.

Neither occurs. The third hole, the whole object handed to `badgeOf` at `ActivityRail:95,151` and `PaneView:82`, is deliberate and documented at `:227-230`.

**The synthetic case does prove it red** (`:263-275`): a fixture file destructuring `entities` and touching `client.files` yields both violations in sorted order.

## 6. Judgment calls 1 to 12

1. **`context.ts` rename.** Right. `contextText` is now `state/project-context.ts`, one importer (`views/shared/ProjectCard.svelte:13`), test renamed with it, no `tests/state/context.test.ts` left behind.
2. **`generation` and `glyphmode` stay module-level.** Right, and the reason is verified above. This is the one place the brief's factory list could not be built as written, and the worker said so.
3. **Pure functions stay module-level.** Right; all 19 verified pure.
4. **The tooltip counter as `ui/tip-ids.ts` with its own context.** Right, and it is the only shape that does not put `state/use` in the `ui/` row. The `tip-<n>` form is preserved and both selectors (`tests/ui/primitives.test.ts:509`, `tests/browser/views.spec.ts:65`) still resolve.
5. **Three table changes plus `findShellStores`.** Right. Without the second rule, adding `state/context` to the shell's row would have silently given the shell every store; the new audit is the payment, and it is red on the synthetic violation.
6. **`+page.ts` hands the token on; the `$effect` follows `invalidateAll`.** The shape is right (a `load` has no component and cannot reach a client), but the test that "asserts both wirings" (`page.test.ts:109-115`) is a source-text assertion, not a behavioural one, and the one behavioural test of the refresh path (`open.test.ts:122`) mocks `invalidateAll` so it bypasses the new hop entirely. Correct design, unproven behaviour. See item 9.
7. **`routes/views.ts` no longer registers on import.** Right, and necessary: a module-level side effect filling a per-client registry is the thing the package removes. Six test files now call `registerAll` explicitly.
8. **Badge hooks take the client; the shell passes the whole object to `badgeOf`.** Right. It is the only way a view's badge reads the view's own stores from a shell forbidden those stores, and the shell forwards rather than reads. The cost is that `findShellStores` cannot follow the object past that call, which the test comment states at `:227-230`.
9. **The binding is named `client`.** Right outcome regardless of the stated Svelte-parsing reason, and it is also what makes the shell audit's `\bclient\.` half work at all.
10. **Function properties, not method shorthand.** Verified: every `*Store` type uses `name: (args) => ret`, every factory returns closures over `function` declarations with no `this`, so destructuring a method off a store is safe. No `eslint-disable` was added for it.
11. **Support modules split by layer.** The principle is stated more cleanly than it is applied: `card.ts` and `edit-bar.ts` take the whole `ClientState` while needing two stores and one; `focus/rows.ts`, `linkedin/post-card.ts` and `shared/entry-form.ts` take individual stores. Both work and both are inside the views row; it is uneven, not wrong.
12. **`tests/client.ts` provides both keys.** Right, and it is why no view test had to learn about tooltips.

## 8. What the browser suite must be watched for at landing

The report says `npm run test:browser` gave `50 passed (55.3s)`; I could not re-run it. What it is the only gate for:

1. **The root providing the context.** Every one of the 64 files does `const { ... } = useState()` at script top level. If the provider is missing or a component initialises above it, the destructure throws and the page is blank. Nothing in the node suite catches a missing `provideState`.
2. **`registerAll(client.registry)` in `+page.svelte:43`.** No node test asserts it: `page.test.ts:104-107` checks only the `registerCollections` line in the untracked block, and the six test files that use `views.ts` call `registerAll` themselves. Watch that the rail draws every view and that the collection tabs are there on the first frame, not one frame late.
3. **A view rendered outside the context.** There is none today (`+layout.svelte` renders children only, there is no error page), so this is a watch on anything new.
4. **Tooltip ids.** `aria-describedby` must resolve, and SSR and hydration should now agree on `tip-1` where the old module counter could drift across requests in a long-lived server.
5. **The stale-token retry.** Restart the dev server under an open page and press a write control: this is the single path where the new indirection (`load` -> `data.token` -> `$effect` -> `setToken`) could lose a beat, and no automated check covers it.

## 9. Before ticking R17

Three items. None of them is a rework; all three are small.

**Caused by the brief** (it named `tests/boundaries.test.ts` and not the design):

1. **`tools/oculus/DESIGN.md:178-185` still carries the old boundary table.** The package widened the enforced table in two rows and left the document that the spec calls the source of those boundaries unchanged: the `shell/` row (line 181) does not mention `state/context` or `state/use`, the `state/` row (line 184) does not mention `views/registry` or `ui/tip-ids`, and DESIGN.md describes no client-context mechanism anywhere. Fix at landing: the two rows plus a line saying the client's stores are one object built at the root and read through Svelte context. (The rest of that table's drift, `state/**` and `data/dates` missing from the `state/` row, predates R17 and is not this package's.)

**Caused by a rule nobody wrote** (the brief said "no behaviour change", not "prove the one path whose timing changed"):

2. **The write-token refresh has no check that would fail if the risk is real.** `writes.svelte.ts:317-319` now depends on `+page.svelte:50-52`'s `$effect` having flushed by the time `invalidateAll()` resolves. `tests/routes/open.test.ts:122` mocks `invalidateAll` with a synchronous `setToken`, so it would stay green if the real path lost the token. Either add a case that drives the two hops (set `data.token`, let the effect flush, assert `writeToken()`), or book it as a browser-suite watch item with the manual reproduction in 8.5 and say in the landing note that it is unverified.

**Caused by the worker** (report prose, not code):

3. **The reach count.** "65 files under `src` call `useState()` (57 views, 7 shell, 1 route)" is 64 (57 views, 7 shell); `+page.svelte` builds the client and never calls `useState()`. Correct the ledger row if it quotes the number.

Two further things belong in the landing note as scope rather than as misses, because the brief chose them: **the catalogs, the tone vocabulary, the appearance list and the glyph mode remain shared across clients in one process** (the direct consequence of decision 2 and judgment call 2), and **`ui/Tooltip.svelte` now throws without a `TIP_KEY` provider**, which the root supplies and `tests/client.ts` supplies, and nothing else does.

Everything else in the brief's four items is built, and the audit it asked for is red on main's tree and green on the package, measured both ways.
