## Acceptance items not met

**Edge 11, the entry-write addressing change is a regression, not a substitute fix.** The worker replaced `writeEntry(collection, entry.id, ...)` with `writeEntry(collection, identityValue(entry, schema), ...)` at `src/lib/views/collection/EntryCard.svelte:101` (pin), `:106` (setStatus), `src/lib/views/shared/EntryForm.svelte:211` (save) and `:220` (delete). The server does the id-to-identity resolution itself: `src/lib/server/writes/entries.ts:164` calls `identityOf(held, id)`, and `identityOf` (`:144-146`) matches on `entryId(item)`, which is the raw `id`, then `key`, then `title` (`:79-84`) - the same order `src/lib/data/normalise.ts:395-399` gives `Entry.id`. So the old call matched exactly and the new one does not. Concretely, `funding/funding.yml` opens its schema with `title` (`funding.yml:10`) and three entries carry `key:` (`FAIR`, `ZonMw-AI-HCC`, `FWO-PhD`, lines 69, 106, 119): the client now sends the title, `identityOf` finds no item whose `entryId` is that title, and the write returns `{found:false}`. Pin, status, edit-save and delete on those three entries are broken by this diff. No test covers it: `tests/server/writes.test.ts:300-508` only passes ids that equal the identity value (`tasks` keyed on title, `venues` on `id`). Fix: revert those four call sites to `entry.id`; the real edge 11 (`Entry.id` field order) stays where the worker put it, NOT DONE in `src/lib/data/normalise.ts:385-406`, for R12c.

**Edge 17, a hub value now reaches `{@html}` unsanitised.** The brief's fix is "the intro takes the catalog line through `t()` without `sanitise` ... and sanitises a hub value". `src/lib/views/Radar.svelte:91-96` passes `trusted` on a template string whose `t('radar.intro_tail', live.length, String(lastRun || ...))` interpolates `lastRun = data?.meta.last_run` (`Radar.svelte:60`), a value read from the radar feed file, into `{1}` of `config/text/views/radar.yml:13`. `t()` does no escaping (`src/lib/state/text.ts:67-73`). So a `last_run` carrying markup is drawn raw where it was sanitised before. The audit does not catch it because the two new `ALLOWED` entries in `tests/html-sites.test.ts:27-30` exempt `drawn(html)` and `drawn(line)` wholesale; the file's own `t(...)` rule (`isCatalogLine`, `:117-128`) would have rejected this site, since the expression is a template string and its argument is neither a literal nor a sanitised call. Fix: either drop `trusted` from `Radar.svelte` and keep the catalog markup by passing `sanitise`-safe pieces, or make `Intro` sanitise interpolated values (e.g. `trusted` accepts only a key, not a built string). As written, edge 17 makes the tree less safe than before the package.

**Edge 13, the nested `retrieval:` block still cannot be edited.** `retrieval` is named in the collection's schema (`registries/data.yml:55`, `type: raw`), so `formFields` already drew a raw control for it and the new `extraRawFields` (`src/lib/state/collection.ts:530-547`) adds nothing for it, because it only offers map fields the schema does NOT name. The brief asked for "a textarea of its YAML with the write layer parsing it back"; the raw control is JSON (`rawFieldText`, `:583-586`). The test cited (`tests/state/collection.test.ts` "offers a map field the schema does not name as a raw block") uses a fixture whose schema omits `retrieval`, so it passes without touching the named case. Not met.

**Edge 9, the blocked tally is not over every tier for every blocked project.** `src/lib/state/focus.ts:242-259`: the `live()` guard was moved into the `waitingOn` branch and the `submitted` branch, so a project on any tier that carries `waiting_on:` entries or a `submitted` chip still `continue`s before the blocked check.
