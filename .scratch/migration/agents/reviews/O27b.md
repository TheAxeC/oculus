Drawn in the rail's Docs section after the configured ones: MET. `src/lib/shell/ActivityRail.svelte:75` is `const marks = $derived([...bookmarks, ...saved])` and `:212` draws them under the single `ui.docs` heading. `tests/shell/rail.test.ts` "draws the reader's own after the configured ones, under the one heading" reads the `data-bookmark` attributes out of the rendered body in order and asserts one `>Docs<`, so it exercises the ordering the item names.

A star on the open file, set and unset: MET for the file view. `src/lib/views/File.svelte:64` derives `marked` by matching root and path, and the toolbar button at the `tools` snippet flips label and `pressed`. `tests/views/file.test.ts` "the star on the open file" renders the real component against a store answered with one bookmark and asserts the two labels and `aria-pressed="true"`, plus a third case proving the root is part of the match. Note the scope: an `.html` file opens in the `document` view, which has no star, so only non-HTML files can be starred from a tab. That is what the brief's re-read specifies (`src/lib/views/File.svelte`'s toolbar), so it is met as written.

"+ bookmark" and edit through the shared entry form over the schema: NOT MET. The control exists (`src/lib/views/Files.svelte:277` and `:312`) and the form is wired (`:313` to `:322`), but on a machine with no bookmarks file `GET /api/fs?bookmarks=1` answers `{ entries: [], schema: [] }` (`src/lib/server/fs.ts:316` calls `readBookmarks`, which returns the empty pair for a missing file at `src/lib/server/fs/bookmarks.ts:85`), the file being created only by a write (`src/lib/server/writes/entries.ts:62`). `markSchema` (`src/lib/views/Files.svelte:112`) maps over that empty list, `formFields` in `src/lib/state/collection.ts` maps an empty schema to no fields, and `EntryForm`'s `save()` then computes `identityField([])` as `title` and refuses with `collection.form_needs title`. A bookmark opens `document` for HTML and `file` otherwise: MET. `src/routes/+page.svelte:98` computes `view` from `typeOfFile`, `ActivityRail.svelte:82` `openMark` splits on it. `tests/browser/files.spec.ts:131` clicks the rail bookmark for `README.md` and asserts `[data-fs-code="README.md"]` appears, which is the file branch. The document branch for a reader's own HTML bookmark is not exercised anywhere.

## 4. Defects in the new code

Two bookmarks on one path break the rail, and the crash is reachable from the shipped form. `src/lib/shell/ActivityRail.svelte:212` keys the Docs each block on `` `${mark.root}/${mark.path}` `` over `marks`, the configured list concatenated with the reader's own. The bookmarks file's identity is `label`, not the path, so the server accepts two entries naming the same file: I ran the shipped `createEntry` twice with `{label: 'a', root: 'hub', path: 'x.md'}` and `{label: 'b', root: 'hub', path: 'x.md'}` under the system temp directory and both were written (`{"found":true,"changed":["entries"],"refused":[]}` each time). Svelte then throws on the duplicate key, in production as well as in development: `node_modules/svelte/src/internal/client/dom/blocks/each.js:355` calls `e.each_key_duplicate` in both branches and `errors.js:146` throws in the non-DEV one. The same happens if the reader bookmarks a file the configuration already names, for instance `cathedra/docs/user/manual.html` of `config/layout.yml:111`. The file already knows this hazard: the comment at `ActivityRail.svelte:146` keys the sections block by position because "a duplicate key would be an error rather than a repeated heading". The new block a few lines below does the opposite.

"+ bookmark" cannot make the first bookmark. Detailed under acceptance 1: `readBookmarks` on a missing file answers `schema: []` (`src/lib/server/fs/bookmarks.ts:85`), the read path deliberately does not create the file (`src/lib/server/fs.ts:316`, and `tests/routes/fs.test.ts` "answers the bookmarks file, which is empty until something writes it" asserts `existsSync` is false afterwards), so the form draws no controls and refuses on the identity field. On a machine whose file browser shows only HTML files there is then no way to make a bookmark at all, since the `document` view has no star.

A pending autosave brings a deleted note back. `saveNote` (`src/lib/server/fs/notes.ts:94`) writes unconditionally; it does not ask whether the file is still there. I ran it: save, `deleteNote` (true, file gone), then a second `saveNote` with the same id, and `listNotes` shows the note again. From the browser this needs the note view alive while the delete happens, which a split layout gives directly (a note in one pane, the Files view in another): type, then confirm the delete within the wait, and the note is written back. The window is `notes.autosave_ms`, 800 ms. No test covers it, and the report does not mention it.

Deleting a note leaves its tab open. `src/lib/views/Files.svelte:225` `dropNote` calls `deleteNote` and sets the refusal line; it never closes the note's instance, although `closeInstance` is on the layout store (`src/lib/state/layout.svelte.ts:35`). The tab stays, the store's next round gets a 404, and the view draws "The note could not be read: no-such-note" with no way out but closing the tab by hand. Not in the report.

Every autosave invalidates the whole file-browser store. `src/lib/state/fs.svelte.ts:490` `act` calls `invalidate()` on every ok answer and `invalidate` bumps the one round counter, so each note save makes every currently rendered fs read ask again: the open tree listings and any open file's text, which is capped at 2 MB. Typing in a note beside an open file view therefore re-downloads that file roughly once a second. Correct but costly, and not in the report.

Notes are read whole to be listed. `listNotes` (`src/lib/server/fs/notes.ts:85`) calls `readNote` for every file just to take the first line, so listing reads every note's full text. Small at the sizes intended; worth knowing.

A symlink inside the notes folder is followed on read. `noteFile` (`src/lib/server/fs/notes.ts:41`) checks the id's shape and the resolved prefix but never `realpath`, unlike `resolveRootPath` in `src/lib/server/files.ts`, which does. I put a symlink at `<notes>/link.md` pointing at a file in another temp directory and `readNote(dir, 'link')` returned that file's content. The write is contained (`writeTextAtomic` renames over the link rather than through it, which I confirmed: the outside file was unchanged). It needs an attacker who can already write in `~/.oculus/notes`, so it is minor, but it is a difference from the rule the rest of the tree uses.

One comment is wrong. `src/lib/server/fs/notes.ts:93` says "An id this folder has no file for is null"; the function answers null only for an id of the wrong shape and otherwise creates the file.

Two tabs for one HTML bookmark. `src/lib/views/Files.svelte` opens a bookmark with `{root, path, label}` and no id, so its identity is `JSON.stringify([root, path])` (`src/lib/state/instance.ts:74`), while the rail opens the same HTML bookmark through `documentState`, whose identity is the string `root/path` (`src/lib/shell/rail.ts:40`). Opening the same HTML bookmark from the two places gives two tabs. Decision 2 only promised the file case, which does hold.

What I checked and found clean: path traversal out of the notes folder (every shape I tried, `''`, `.`, `..`, `../away`, `a/b`, `/etc/passwd`, `a.md`, a 65-character id, a leading `-` or `_`, is refused by `noteFile`); a write outside `~/.oculus` (both paths come from the server's own config, nothing a request names reaches them); a bookmark path escaping its root (the serving endpoint still runs `resolveRootPath`, which realpaths and checks containment); a read the route should refuse (both the bookmarks and the notes reads are same-origin gated, the writes token gated as well); and a lost keystroke on tab switch (the flush is correct for Svelte 5.57, see section 3). `ls -la ~/.oculus/` shows no `bookmarks.yml` and no `notes/`, so nothing in this work or in my checks touched the real home.

## 5. The thirteen decisions and the two brief corrections

1. The rail is handed the bookmarks rather than reading the `fs` store: kept, and the reason is right. `tests/boundaries.test.ts:214` and `DESIGN.md:187` both exclude `fs` from the shell's stores. The brief's re-read was wrong here and the worker said so.
2. A bookmark says which view opens it (`view?: 'document' | 'file'` at `src/lib/shell/rail.ts:20`): kept. The one-tab claim holds for the file case, verified at `src/lib/state/instance.ts:68`; it does not hold for HTML (section 4).
3. The root select carries no options of its own: questionable. The reasoning is sound (a root added later must still be nameable, and `src/lib/server/writes/entries.ts:105` checks an optionless select as text), but combined with the file being written only on the first write it is what makes "+ bookmark" empty on a fresh machine. The fix is to answer the scaffold's schema on the read, or to create the file on the first read.
4. A Bookmarks section in the Files view: kept and needed. User-visible shape; book it.
5. `GET /api/fs?note=<id>`: kept and needed. User-visible wire shape; book it.
6. The Files pane is no longer `tinted`: forced, but it is a visible change Axel should rule on. `tests/views/tinted.test.ts:112` fails a view that paints a surface and still asks for the tint, and importing `EntryForm` (whose `:global(body.wall) .form` rule is at `src/lib/views/shared/EntryForm.svelte:343`) makes `Files` count as painting one. The comparison with `Collection.svelte` is not exact: that view renders `Card` (`src/lib/views/Collection.svelte:288`) so its surfaces really are there all the time, whereas the Files tree, with the form closed, now draws its text straight onto a wallpaper. Book it.
7. Two glyph names, `star` and `note`: kept, added in matching positions in `config/glyphs.yml` and `config/icons.yml`, with ASCII fallbacks.
8. `EntryForm` gained `initial?`: kept, internal, and backwards compatible (`entry === null ? opening[field] : ...` with a default of `{}` is identical to the old `undefined` for every existing caller).
9. A note's file is title newline body: kept. The newline collapse is at `src/lib/server/fs/notes.ts:56` and tested.
10. The note id and the accepted file-name shape: kept, and I verified the shape rule by running it.
11. "+ note" writes an empty note before opening its tab: kept, but it has a consequence the report does not name: pressing "+ note" and closing the tab without typing leaves an empty note in the list forever, drawn as "Untitled note".
12. A pending autosave is flushed on teardown: kept and correct for this Svelte version. Untested through the component.
13. The first root of the workspace is preselected: kept, and a fair reading of a brief line that did not fit the view. Untested, and moot while the form has no fields.

Brief correction A, `startEntries` for a file with no list yet: correct and necessary. YAML really has no empty block list, and the new function verifies the result the way an append does (`src/lib/server/entry-edit/entries.ts:95` to `:121`). I confirmed the produced file parses and takes an ordinary append for the second entry.

Brief correction B, the `entryId` fallback to the collection's identity field (`src/lib/server/writes/entries.ts:157`): correct, and the claim that nothing else in the tree changes holds. I checked every collection `config/sources.yml:37` names by parsing its file: `venues`, `programs`, `domains`, `statements`, `funding`, `events`, `education`, `applications`, `collaborations`, `tasks`, `code` and `data` (whose list is `datasets:`, since `listOf` skips `schema:`), and every entry of all twelve carries an `id`, a `key` or a `title`, so the fallback never fires on a hub file.

Shapes the orchestrator has to book for Axel: `config/behavior.yml`'s `notes.autosave_ms`; the two optional `local.yml` keys `bookmarks` and `notes`; the two new files on a reader's machine, `~/.oculus/bookmarks.yml` and `~/.oculus/notes/<id>.md`; the three new query parameters and the two new POST actions on `/api/fs`; the Bookmarks section added to the Files view (decision 4); the Files pane losing its tint over a wallpaper (decision 6); and the new glyph names `star` and `note`.

## 6. The `boot()` change

It is what the report says, and it is not a loosening. `tests/browser/rail.ts:29` adds `await expect(page.locator('nav [data-group]').first()).toBeVisible();` after the two waits that were already there; nothing was removed or weakened. The reason given also checks out: `data-group` appears only at `src/lib/shell/ActivityRail.svelte:155`, inside `{#if label !== null && section.items.length > GROUP_MAX}`, and the group labels come from `nav_groups` of the merged config, which the page derives at `src/routes/+page.svelte:73` from the socket's push, so before that push there are no groups and every view is a bare `data-view` button. Waiting for a group is therefore waiting for the rail the reader ends up with, which is a stronger precondition than waiting for any button.

Two caveats. The new wait hangs if no configured group ever exceeds `GROUP_MAX`, which is 4 (`src/lib/shell/rail.ts:60`); that is fine for the shipped `config/layout.yml` but it couples the browser helper to a configuration fact nothing states. And I did not run the browser suite, so the report's "75 passed" over three runs and the claim that the timing-bound `collection.spec.ts` and `sanitise.spec.ts` failures are gone are unverified by me.


## Orchestrator's verdict

A repair round with those, the untyped note left behind, the tab label, the symlink in the notes folder, the HTML bookmark opening two tabs and the missing tests. The orchestrator's own read (runs/O27b/read-notes.md) found the autosave cost, the untyped note, the tab label and the deleted note's flush before the review named them.
