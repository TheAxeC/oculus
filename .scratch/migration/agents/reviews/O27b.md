## 4. Defects in the new code

Two bookmarks on one path break the rail, and the crash is reachable from the shipped form. `src/lib/shell/ActivityRail.svelte:212` keys the Docs each block on `` `${mark.root}/${mark.path}` `` over `marks`, the configured list concatenated with the reader's own. The bookmarks file's identity is `label`, not the path, so the server accepts two entries naming the same file: I ran the shipped `createEntry` twice with `{label: 'a', root: 'hub', path: 'x.md'}` and `{label: 'b', root: 'hub', path: 'x.md'}` under the system temp directory and both were written (`{"found":true,"changed":["entries"],"refused":[]}` each time). Svelte then throws on the duplicate key, in production as well as in development: `node_modules/svelte/src/internal/client/dom/blocks/each.js:355` calls `e.each_key_duplicate` in both branches and `errors.js:146` throws in the non-DEV one. The same happens if the reader bookmarks a file the configuration already names, for instance `cathedra/docs/user/manual.html` of `config/layout.yml:111`. The file already knows this hazard: the comment at `ActivityRail.svelte:146` keys the sections block by position because "a duplicate key would be an error rather than a repeated heading". The new block a few lines below does the opposite.

"+ bookmark" cannot make the first bookmark. Detailed under acceptance 1: `readBookmarks` on a missing file answers `schema: []` (`src/lib/server/fs/bookmarks.ts:85`), the read path deliberately does not create the file (`src/lib/server/fs.ts:316`, and `tests/routes/fs.test.ts` "answers the bookmarks file, which is empty until something writes it" asserts `existsSync` is false afterwards), so the form draws no controls and refuses on the identity field. On a machine whose file browser shows only HTML files there is then no way to make a bookmark at all, since the `document` view has no star.

A pending autosave brings a deleted note back. `saveNote` (`src/lib/server/fs/notes.ts:94`) writes unconditionally; it does not ask whether the file is still there. I ran it: save, `deleteNote` (true, file gone), then a second `saveNote` with the same id, and `listNotes` shows the note again. From the browser this needs the note view alive while the delete happens, which a split layout gives directly (a note in one pane, the Files view in another): type, then confirm the delete within the wait, and the note is written back. The window is `notes.autosave_ms`, 800 ms. No test covers it, and the report does not mention it.

Deleting a note leaves its tab open. `src/lib/views/Files.svelte:225` `dropNote` calls `deleteNote` and sets the refusal line; it never closes the note's instance, although `closeInstance` is on the layout store (`src/lib/state/layout.svelte.ts:35`). The tab stays, the store's next round gets a 404, and the view draws "The note could not be read: no-such-note" with no way out but closing the tab by hand. Not in the report.

Every autosave invalidates the whole file-browser store. `src/lib/state/fs.svelte.ts:490` `act` calls `invalidate()` on every ok answer and `invalidate` bumps the one round counter, so each note save makes every currently rendered fs read ask again: the open tree listings and any open file's text, which is capped at 2 MB. Typing in a note beside an open file view therefore re-downloads that file roughly once a second. Correct but costly, and not in the report.

Notes are read whole to be listed. `listNotes` (`src/lib/server/fs/notes.ts:85`) calls `readNote` for every file just to take the first line, so listing reads every note's full text. Small at the sizes intended; worth knowing.

A symlink inside the notes folder is followed on read. `noteFile` (`src/lib/server/fs/notes.ts:41`) checks the id's shape and the resolved prefix but never `realpath`, unlike `resolveRootPath` in `src/lib/server/files.ts`, which does. I put a symlink at `<notes>/link.md` pointing at a file in another temp directory and `readNote(dir, 'link')` returned that file's content. The write is contained (`writeTextAtomic` renames over the link rather than through it, which I confirmed: the outside file was unchanged). It needs an attacker who can already write in `~/.oculus/notes`, so it is minor, but it is a difference from the rule the rest of the tree uses.

One comment is wrong. `src/lib/server/fs/notes.ts:93` says "An id this folder has no file for is null"; the function answers null only for an id of the wrong shape and otherwise creates the file.

Two tabs for one HTML bookmark. `src/lib/views/Files.svelte` opens a bookmark with `{root, path, label}` and no id, so its identity is `JSON.stringify([root, path])` (`src/lib/state/instance.ts:74`), while the rail opens the same HTML bookmark through `documentState`, whose identity is the string `root/path` (`src/lib/shell/rail.ts:40`). Opening the same HTML bookmark from the two places gives two tabs. Decision 2 only promised the file case, which does hold.

What I checked and found clean: path traversal out of the notes folder (every shape I tried, `''`, `.`, `..`, `../away`, `a/b`, `/etc/passwd`, `a.md`, a 65-character id, a leading `-` or `_`, is refused by `noteFile`); a write outside `~/.oculus` (both paths come from the server's own config, nothing a request names reaches them); a bookmark path escaping its root (the serving endpoint still runs `resolveRootPath`, which realpaths and checks containment); a read the route should refuse (both the bookmarks and the notes reads are same-origin gated, the writes token gated as well); and a lost keystroke on tab switch (the flush is correct for Svelte 5.57, see section 3). `ls -la ~/.oculus/` shows no `bookmarks.yml` and no `notes/`, so nothing in this work or in my checks touched the real home.

## 2. The two defects the repair found

**The emptied `entries:` key.** `startEntries` (`src/lib/server/entry-edit/entries.ts:106` to `:146`) treats a key as writable only when its value is null or a scalar holding null (`:112` to `:114`). I ran the shipped function under `$TMPDIR` over thirteen sources. It writes for: no key at all, a dangling key, a dangling key that is not the last one in the file, a dangling key followed by a comment, and a file carrying an anchor. It refuses for: `entries: hello` (a scalar holding a string), `entries: []` (an empty flow list), `entries: [{label: a}]`, and `entries: {}`, each with "the file already has a entries key". So it cannot write under a key holding a scalar or a flow list. A key in a *nested* map is not found by `pairOf`, which reads only the top-level items (`src/lib/server/entry-edit/lines.ts:98` to `:101`), so `outer:\n  entries:\n` gets a new top-level `entries:` appended and the nested key is left alone; the result parses and the post-write verification (`entries.ts:129` to `:144`) passes because it compares every other key. A top-level list, a bare scalar and an empty file all refuse with "the file does not parse" rather than throwing. The `(before[listKey] ?? null) !== null` guard at `:140` is a second line of defence for the flow-list case. End to end the emptied file recovers: `tests/server/fs.test.ts:431` creates, removes and creates again through `createEntry`/`removeEntry`.

**The teardown and `fresh`/`seeded`.** `id` is the instance's own note id (`src/lib/views/Note.svelte:55`), `seeded` records which note the draft was read from (`:67`, set at `:103`, `:107`, `:112`), and "+ note" opens with `fresh: true` (`src/lib/views/Files.svelte:227`), which seeds an empty draft with no round trip (`Note.svelte:106` to `:110`). Order of events on unmount (`:143` to `:155`):

- a fresh untyped note: `vanished()` false, `empty()` true, so cancel, then `deleteNote(id)` (not awaited), then `closeRecord('note', id)`. No flush. The file goes.
- a fresh typed note: `touched` true so `empty()` false, so `autosave.flush()`, which runs the pending save synchronously with the last keystrokes (`src/lib/state/notes.ts:133` to `:138`). No delete, no close.
- an old note untyped: `seeded === id` and the draft holds the file, so `empty()` is false unless the file itself is empty; `flush()` with no armed wait returns without running. Nothing happens. If the file *is* empty, it is deleted and the tab closed, as in the fresh case.
- an old note typed: `flush()`, the save runs. No delete, no close.
- a note deleted elsewhere in this page: `dropNote` adds the id to `gone` before it closes the tab (`src/lib/state/fs.svelte.ts:546`, then `Files.svelte:240`), so `vanished()` is true and only `autosave.cancel()` runs. Nothing is written back.

One hole in that last state: `vanished()` is `noteDeleted(id) || held.error !== ''` (`Note.svelte:126`), so any failed read, a transient network error included (`fs.svelte.ts:483` sets `error` from the thrown reason), makes the teardown cancel instead of flush, and the reader's pending keystrokes are dropped. Round one flushed unconditionally. `NOTE_GONE` is exported for exactly this word (`fs.svelte.ts:36`) and is not used here; narrowing the check to `held.error === NOTE_GONE` would keep the fix and drop nothing. Also, `NOTE_GONE` is used only by the store and by `tests/state/fs.test.ts:526`: the views map the literal `'no-such-note'` themselves (`src/lib/views/Files.svelte:150`), so the report's judgment call 5 ("so the view's refusal line and the Files view's refusal() map say the same thing") overstates what the constant does.

## 3. The notes round

`invalidate()` still moves the notes: it bumps both counters (`src/lib/state/fs.svelte.ts:507` to `:510`), and `tests/state/fs.test.ts:531` relies on that.

A stale answer cannot be written over a newer one. Every notes read checks `fresh(at, 'notes')` before it writes (`:434`, `:445`, `:471`, `:499`), and `schedule` keys its in-flight ticket by round and key (`:238` to `:245`), so the same key is never in flight twice in one round; an older round's answer that lands late is dropped without touching `rounds`, and the newer round schedules its own.

A re-fetch is skipped in one place on purpose: `note(id)` never asks again for an id in `gone` (`:456`), which is the item 3 fix. It is also skipped when nothing moves the notes round, which is the item 4 fix.

What the round does not fix, and what neither review named: while a re-fetch is in flight, `note(id)` returns the previously held answer with `loading: false` (`:454`, `:459`), and the Note view seeds its draft as soon as `held.loading` is false (`src/lib/views/Note.svelte:111` to `:115`). The store's cached note therefore trails the disk by one save, and the view has no way to tell a fresh answer from a stale one. See the data-loss path in section 6.

Cost, stated for the record: one successful save moves the notes round, so an open Files view re-asks `?notes=1` and the note's own tab re-asks `?note=<id>` for text it just wrote. Two reads per save instead of the whole store, which is what item 4 asked for.

## 6. Still failing the brief or the spec, named by neither review

**Switching between two note tabs in one pane runs no teardown, and a pending save can write the wrong note's text.** `PaneView` mounts only the active instance (`src/lib/shell/PaneView.svelte:268` to `:270`) through Svelte's component block, which keeps the existing branch when the component is the same (`node_modules/svelte/src/internal/client/dom/blocks/branches.js:186` to `:207`, Svelte 5.57.0). So moving from note A to note B reuses one `Note` component: no flush, no delete, no close, and the `autosave` scheduler survives with A's wait still armed. The seeding effect then re-seeds the draft to B (`src/lib/views/Note.svelte:100` to `:116`), and when A's wait fires, `save()` reads `draft.id` and `draft.body` at fire time (`:169` to `:171`), which are B's. A's last keystrokes never reach the disk and nothing says so. The local note read is far faster than the 800 ms wait, so the re-seed normally wins the race. Same mechanism, second consequence: a fresh untyped note A is not deleted when the reader switches to note B, only when they switch to another view. This is reasoned from the source and the Svelte runtime, not measured in a browser.

**A tab switch away from a note and back can seed the draft from a stale cache.** `note()` returns the held answer with `loading: false` while its re-fetch is in flight (`src/lib/state/fs.svelte.ts:454`, `:459`), and the view seeds as soon as `held.loading` is false (`src/lib/views/Note.svelte:111`). Switching to the Files view within the autosave wait flushes the save, but the remount immediately after reads the cache from before that save, seeds the older text, and never re-seeds (the guard at `:101` is `seeded === id`). The next keystroke then saves the older text plus that keystroke. Seeding on `held.modified` being newer than the last save, or clearing the held note when a save is sent, would close it.

**A delete in a second browser page can still be revived by this page.** `gone` is per client (`src/lib/state/fs.svelte.ts:203`), which is what the repair item asked for, and `vanished()` also catches a landed 404. Between the other page's delete and this page's next note read there is a window in which the teardown flush writes the note back through `saveNote` (`src/lib/server/fs/notes.ts:116`), which still writes unconditionally. Narrow, and worth knowing because the brief's words were "stays deleted".

**A malformed saved bookmark is still drawn.** `src/routes/+page.svelte:98` to `:104` maps a bookmark entry whose `root` or `path` is not a string to the empty string rather than dropping it, so a hand-edited `bookmarks.yml` entry missing a path becomes a rail button on `data-bookmark="/"` that opens a file view on root `''`. Cosmetic, no server risk (the serving endpoint still runs `resolveRootPath`).

**`local.yml`'s two new path keys are not home-expanded.** `bookmarks` and `notes` are taken as written (`src/lib/data/sources/config.ts:206` to `:216`) and used as given (`src/routes/api/fs/+server.ts:17` to `:18`), so `~/elsewhere/notes` would be a relative directory named `~`. This matches how the existing `workspaces` key behaves, so it is the tree's practice rather than a regression, but both new keys are user-visible configuration.
