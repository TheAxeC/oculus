There is no version-3 page with a bottom panel. The four variants live on version 2 instead (`:63`, `:69`, `:57`, `:75`).
- **Item 3, "absent on a root pane", is implemented but not verified.** `src/lib/shell/PaneView.svelte:122` gates the item on `path.length > 0`. The only check of its absence is `tests/browser/layout.spec.ts:22`, which asserts `toHaveCount(0)` for `ui.pane_fold` **before** the pane menu is opened at `:23`. `src/lib/ui/Menu.svelte:168` renders the item list under `{#if open}`, so the assertion is 0 whether or not the gate exists, and it is never re-checked after the menu opens. Nothing in the suite would fail if the gate were deleted.
- **Item 7, the test count.** The brief requires "The test count does not fall except for cases whose subject is gone". The report states it did not record the pre-change total and quotes no before/after, so this item is unevidenced (the removal list is given).
- **Check 9** is red; see section 6, which is the one place the brief itself is wrong rather than the code.

## 4. Defects, and report claims that do not match the code

- **`foldPane` un-maximises on a path it then ignores.** `src/lib/state/layout.svelte.ts:491-497`: `inside` is computed as `path.every((step, at) => focus.path[at] === step)`, which is vacuously true for `path = []`. With a pane maximised, `foldPane([])` therefore calls `restore(current)` and applies it, while `fold(shown.root, [])` returns the tree unchanged (`src/lib/state/layout/tree.ts:305-306`). The call gives the workbench back and folds nothing. Not reachable from the pane menu (gated at `PaneView.svelte:122`), reachable from the store's public method, and untested.
- **The shell does not use the store method the brief named.** `src/lib/shell/Workbench.svelte:203-204` expands with `change((tree) => expand(tree, path, index))`, duplicating `expandChild` at `src/lib/state/layout.svelte.ts:500-502` exactly. `expandChild` has no caller in `src/`. Brief item 3 names `expandChild(path, index)` as the store's expand; the shell bypasses it, so one operation has two entry points and the store's one is exercised only by a test. The report does not list this among its judgment calls.
- **The brief's premise about `openPinnedView` is wrong and the report does not say so.** The removed function (diff.patch:1418-1431) ended `return openView(view, 'main', { session, label })` and its own comment said "in the main area". The brief (line 10 and item 2) records it as opening in the panel. The consequence on the tree: `src/lib/views/sessions/SessionDetail.svelte:139` now calls `openBeside(area, ...)`, so pinning an area from a session detail moves from "a tab in the active pane" to "a new pane split to the right". That is a user-visible change of a control the brief did not intend to change, and it has been written into the design record at `DESIGN.md:271` ("a pinned session view"). The spec requires a premise found wrong to be reported; the report states the opposite in judgment call 3.
- **Judgment call 3 misnames the callers.** It says `openPinnedView`'s "two callers (`SessionDetail`'s pin control, `CardSessions`' pick)". `CardSessions` never called it: its old line was `openView('session-detail', 'panel')` (diff.patch:2936). `openPinnedView` had one view caller.
- **The report's browser-selector claim is wrong.** It states `grep -rn 'data-' tests/browser` shows "`data-pane`, `data-pane-path`, `data-pane-view`, `data-pane-active` only". The actual set is `data-card, data-cursor, data-domain, data-edit-source, data-entry, data-fold, data-fold-label, data-group, data-lead, data-pane, data-pane-active, data-pane-view, data-reveal, data-scroll, data-search, data-source-editor, data-view`; `data-pane-path` is not among them. The substantive point (no browser spec selected on `data-pane-target`) holds.
- **The relaxed `panelSize` refusal is absent from the report's ledger.** Its migration section lists "refusals kept: ... a dock that is not one of the three" and its removed-case list does not name the deleted panel-share refusals, while `tests/state/layout-saved.test.ts:153` now asserts acceptance. Judgment call 8 covers only the unreadable (non-numeric) case.
- **An unasked edit to the design record.** `DESIGN.md:272` (the 2026-09-11 pages decision) was rewritten: "each one a whole workbench (its two trees, dock and panel share)" became "each a whole workbench", and "A strip of page names runs across the top of the main area and the panel together, since a page governs both" became "across the top of the area the tree fills". Brief item 6 asked only that the new line be added beside the earlier decisions, "which stay as the record they are". The docking decisions at `DESIGN.md:258` and `:265` are untouched, as asked.
- **A sharp edge of decision 2 the report does not name.** Because `openBeside` splits whenever the wanted instance is not open (`src/lib/state/layout.svelte.ts:551-556`), and `stateId` distinguishes instances by `id`/`session`, opening the manifest editor from five different project cards (`src/lib/views/shared/ProjectCard.svelte:135`) now produces five side-by-side panes where the panel previously stacked them as tabs. `splitPane` nests once `MAX_CHILDREN` is reached (`tree.ts:253-257`, `:280-286`), so nothing is lost, but the arrangement degrades with use. This is a consequence of the brief's decision 2, not a deviation from it; it belongs in the report's limitations.
- **A leftover name in a rewritten test.** `tests/shell/workbench.test.ts:114-116` still calls the rendered default workbench `docked`, a name from the retired category, in a file this package rewrote.

## 6. The check 9 contradiction

The migration reader's use of the old field names is unavoidable given brief item 4, and none of the ten lines is anything but the reader or its fixtures. Verified by running the grep myself: the four source hits are `src/lib/state/layout/saved.ts:297` (`value.panel`), `:308` (`value.panelSize`), `:324` and `:327` (the `{ target: 'main' | 'panel' }` shape of a version-2/3 saved focus), all inside `readDockedWorkbench` / `readDockedFocus`, the two functions that exist only to read the older envelopes. The six test hits are `tests/state/layout-fixture.ts:46,48` (the `docked()` builder, which returns a `Record<string, unknown>`, not a `Workbench`) and `tests/state/layout-saved.test.ts:65,71,93,156` (four migration fixtures). Nothing else in `src` or `tests` matches: `dockedAt`, `Dock`, `DOCKS`, `Target`, `clampPanel`, `PANEL_MIN/MAX/DEFAULT`, `holderOf`, `treeOf`, `withTree` and `openPinnedView` return nothing at all.

The keys `main`, `panel`, `dock`, `panelSize` and the focus `target` are what the version-2 and version-3 JSON literally contains, so reading them means writing them; the only way to satisfy the grep would be to hold the key names in constants or index them dynamically, which hides the wire shape from the reader for no gain. The brief's check 9 is the item that is wrong, not the code: it should have excluded `saved.ts`'s migration reader and its fixtures, or been written as `grep -rn ... src tests --exclude-dir` over everything but those three files. The remaining lowercase `dock` occurrences (`saved.ts:218,224,239,269,292,298-316`, `model.ts:68`) are the same reader and its doc comments, plus the stale comment at `tree.ts:2` noted in section 2.
