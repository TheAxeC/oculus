## 3. Defects in the new code

**D1, openBeside stacks into the wrong pane once the tab moves.** `besidePath` (`layout.svelte.ts:579-583`) resolves the remembered instance's *current* pane, not the pane `openBeside` created. Drag that tab back into the pane being read and the split collapses (`tree.ts:113-120`); the next `openBeside` then finds `stack = []` and takes the `openInstance(shown, stack, instance)` branch (`:572-573`), so the view opens as a tab in the pane being read instead of beside it. No test.

**D2, `lastBeside` is never cleared.** `loadLayout` clears `lastActive` (`layout.svelte.ts:216`) and `closePage` deletes its entry (`:310`); neither touches `lastBeside` (`:146`). The comment at `:142-145` says it behaves like `lastActive` because "a reload opens the next one in a pane of its own", which is not what the code does: a saved layout restores the same instance ids, so a second `loadLayout` on one store still finds the remembered instance. One caller (`src/routes/+page.svelte:142`) keeps it harmless in the app; the asymmetry and the dead per-page entries after `closePage` stand.

**D3, the two constructors of `folded` disagree on duplicates.** `splitOf` dedupes (`tree.ts:91`), `readFolded` does not: it pushes every entry and only rejects when `new Set(folded).size >= count` (`saved.ts:116-128`), and `saved.ts:100` assigns that array straight to the node. A saved `folded: [1, 1]` on a three-child split therefore parses, `isFolded` draws one strip, `foldedCount` (`tree.ts:48-50`) returns 2, and `SplitView.svelte:46-47` takes `FOLD_PX` out twice, mis-scaling every sash drag in that split. Reachable only from a hand-edited or corrupted saved value.

**D4, a folded child in the middle freezes the split.** `separated` (`SplitView.svelte:70-72`) is false on both sides of a folded child, so children `[A, folded, B]` draw no handle at all and A and B cannot be resized until the middle child is expanded. The brief asked for no sash beside a folded child; this consequence is named nowhere and nothing tests it.

**D5, `openSum`'s fallback is the wrong value.** `SplitView.svelte:56` returns 1 when every open child's size is 0, which gives each of them `flex: 0 1 0` and renders the split blank. `checkLayout`'s `MIN_SIZE` rule (`saved.ts:92-96`) keeps a parsed tree out of that state, so it is a guard returning the wrong number rather than a live bug.

**D6, the fold menu item is offered on panes that cannot fold.** `PaneView.svelte:122` adds it whenever `path.length > 0`; `tree.ts:314` refuses a fold that would leave no open child, and `layout.svelte.ts:501-502` then returns silently. In a two-child split with one child already folded, the other pane's menu still shows "Fold pane" and picking it does nothing. No test.

**D7, migration can put the maximised pane inside the folded child.** For a version 2 or 3 page with `dock: 'hidden'`, a panel that still holds tabs and a focus whose target is `panel`, `saved.ts:316` sets `folded = [1]` and `:319-320` sets `focus.path = [1, ...]`; `settleFocus` keeps it because the pane exists (`workbench.ts:17-21`) and `checkWorkbench` has no rule against it (`saved.ts:174-182`). `Workbench.svelte:156-160` then draws that pane alone, so the panel the old build was hiding comes back full-screen on the first load after the upgrade. The store refuses to create this state (`foldPane` restores first, `layout.svelte.ts:494-505`). Untested: every focus case in `layout-saved.test.ts` uses `dock: 'right'`.

**D8, the dropped panel-target focus is untested.** `saved.ts:303-306` drops a focus whose target is `panel` when the panel holds nothing; the only case there covers target `main`.

**D9, the workbench-keys test's stand-ins.** `tests/shell/workbench-keys.test.ts:51-58` and `:92-93` assign `globalThis.document` and `globalThis.HTMLElement`. The spec's judged principle is "No globals. No `globalThis` ... a dependency is passed in"; `tests/boundaries.test.ts:152-156` only walks `src`, so nothing enforces it here.
