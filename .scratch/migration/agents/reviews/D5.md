## The defect to fix before landing

A build whose answer is in flight when the terminal leaves the list leaves the row stale for the life of the tab. `src/lib/state/latex.svelte.ts:122-128`: a second request for an id is dropped while one is in flight. `:130-132`: `load` records `asked[id] = at` for the signature it was asked at. `:171-177`: `settle` decides the build is over from `live(terminal)` at the moment the answer lands, not from the signature the answer was fetched at, deletes `waiting[id]` and sets `asked[id] = ''`. So: a push at version N starts a request while the build still runs; the build ends and the push at version N+1 arrives while that request is in flight and is dropped by the inflight guard; the in-flight answer (pre-build state, old PDF mtime) lands, `redraw` at `:165-170` sees no mtime move and bumps nothing, and `settle` then clears the wait, after which `signature(id)` and `asked[id]` are both the empty string and nothing ever asks again. The row keeps the old PDF time and the old error count, and the open PDF tab keeps the old address. Nothing else re-reads: `invalidate` at `:114` has no caller anywhere in `src/` or `tests/`. The smallest fix is in `settle`: pass `at` in and, when `at !== signature(id)`, set `asked[id] = ''` and return without clearing `waiting`, so the next read asks again. This is read from the source, not executed; the existing state cases await each step and cannot hit the window.

"A literal string ... anywhere a reader sees it is a defect." `src/lib/server/pty/routes.ts:248` builds the terminal name as the literal `latex ${step} ${id}/${main}`, which the reader sees in the terminals list. Judgment call 1 defends it by saying the catalog would have meant reading the merged config inside the endpoint. So the mechanism is in the same endpoint, one action over, and a `server.latex.name` key would have been the shape. The mitigation the report does state is true: `recover <key>` (`routes.ts:149`) and `task <kind>` (`routes.ts:190`) are literals of the same kind already, so this adds a third rather than starting the habit. I judge this a rule break that the orchestrator can either fix in one line at landing or book for all three together, as the report proposes; it is not a reason to reject the package.

3. DRY, minor. The rule "this folder is inside the hub" now exists twice: `src/lib/server/latex.ts:83-87` (`inside`, used for the GET at `:303-304`) and `src/lib/server/pty/chat.ts:75-83` (`projectDirectory`, used for the POST at `routes.ts:237`). Judgment call 8 claims the export made the check exist once; that is true of the POST only.
