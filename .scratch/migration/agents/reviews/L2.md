The report names it and proposes the fix (the store remembering the page last acted in); the brief's stated outcome ("a view opened while reading inside a shown page lands in that page") is not reached for that path.

## 3. Defects in the new code

**1. The touched-page memory keeps naming a page that is no longer drawn.** `lastTouched` is cleared in exactly one place, `switchPage` (`layout.svelte.ts:350`), and `touched()` (`:177-179`) accepts any page the list still holds. Removing the leaf (`unembedPage`, `:619-626`), folding it, or maximising a pane of the host (`:629-631`) unmounts the nested page's panes (`SplitView.svelte:148-151` renders the leaf snippet only for a `page` node) and leaves `lastTouched` naming that page. The rail then opens a view into a page nobody is looking at and the reader sees nothing happen. The key handler does not have the bug, because its own memory checks `lastPagePane?.isConnected` (`workbench-keys.svelte.ts:139`); the two memories of one fact, a DOM element in the key handler and a page id in the store, disagree exactly here. No test.

**2. The screen rule is not enforced through a nested page's own leaves, and the arrangement it produces cannot be read back.** `showable` (`nested.ts:70-71`) asks whether the screen draws the *nested* page; it never asks whether the nested page draws something the screen already draws. Three menu picks reach it: show C in B while the strip is on B, switch to A, show C in A, then show B in A. Verified with `node` over `nested.ts` and `saved.ts`:

```
1 showable(B,B,C)= true
2 showable(A,A,C)= true
3 showable(A,A,B)= true
A tree = {"kind":"split",...,"children":[{"kind":"pane",...},{"kind":"page","page":"B"},{"kind":"page","page":"C"}]}
reload -> parseLayout = null
```

So page C is drawn twice on screen A, its instances mount twice, and `refusedLeaves` (`nested.ts:83-114`) does not flag it either. Worse, `refusedLeaves` and `settlePageLeaves` disagree about the *same* arrangement: `settlePageLeaves` keeps the second leaf, `checkPages` then reports `page "A" root node at [2]: shows "C", which this page already shows`, and `parseLayout` returns null. The next reload therefore throws away **every page** and starts from one default page (`layout.svelte.ts:291`). The two functions decide by different rules: `refusedLeaves` adds everything a kept leaf draws to `drawn` (`:96-99`), `settlePageLeaves`'s `draws` walks only the leaves kept so far, page by page down the strip (`:205-213`), so its answer also depends on the order of the strip.

**3. The refusal has a word only over a pane body or a leaf header.** `hover` (`drag.svelte.ts:203-205`) drops a non-edge drop for a page drag and sets `refused` false, so dragging a page over a pane's tab strip (`PaneView.svelte:163`) draws the ordinary `ui.drag_hint` ghost while the pointer is over a place the page can never land. The word appears only where `bodyHover`/`headHover` call `hover(null, null, true)`.

**4. The leaf header is the only drop target, and its bottom edge is unreachable.** `headHover` measures `edgeAt` against the leaf's whole box (`PageLeaf.svelte:60-62`) while the pointer is confined to the header at the top of that box, so `top` depth is near zero and `bottom` (depth near one) can never be the nearest side (`drag.svelte.ts:99-109`). A tab or a page can be landed above, left of and right of a leaf, never below it. The area under the header belongs to the nested page's panes, which is the report's judgment call 6.

**5. `here()` is right.** `PaneView.svelte:143-149` compares `drop.page ?? currentPage().id` with the pane's own page before the path; a drop always carries its page now (`:163,180`).

**6. The stale-id paths are right.** `at()` returns null and `apply` (`:405-408`), `closePane` (`:540`), `unembedPage` (`:620`), `embedPage` (`:610`), `transferInstance` (`:568-570`), `splitInstance` (`:586-588`), `activateInstance` (`:439`), `closeInstance` (`:530`) all return without writing; `maximisePane`/`restorePanes`/`foldPane`/`expandChild` reach `apply`, which returns early. A reader is answered with the shared `GONE` workbench (`:81,216`), which nothing mutates.

**7. `clearPage` is right.** `withoutPage` removes leaves one at a time and re-reads the paths after each removal (`nested.ts:181-189`), so a tree holding two leaves of the closed page is handled, and a root leaf becomes an empty pane through `removeNode`'s root case (`tree.ts:152-156`).

**8. `pageName` is right**, with one edge: `pageNameOf` answers `''` for an id the list does not hold (`page-strip.ts:22`), and `FoldedPane.svelte:41` prints that raw, so a folded leaf naming a page the list lost draws a nameless strip. `clearPage` and `settlePageLeaves` make that unreachable through the store.

**9. DESIGN.md states a rule the code does not enforce.** `DESIGN.md:206` ("A page is drawn at most once on a screen, directly or through a page the screen already draws, so nothing is drawn twice and no view is mounted twice") and `:275` ("a drop or a menu item that would break either rule is not offered") are both false under defect 2.
