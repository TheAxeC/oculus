## Feasibility

F1. The address the app is served from decides whether the frame can load its own files, and the brief does not say so. Under /api/, a subresource request from an opaque-origin document carries `Sec-Fetch-Site: cross-site` and either no Origin (a classic script, CSS or image) or `Origin: null` (a module script or fetch). `refused()` rejects both with 403 (hooks.server.ts:41-48, auth.ts:49-61), so the app's own scripts and stylesheets fail. Outside /api/, the guard does not run, so the route is unguarded by design. A cross-site page can then GET an app's files, which is acceptable only if the files are not secret. Change: require the section to put the address outside /api/ (or add it to UNGUARDED with a reason), and say it does so on purpose.

F2. Module scripts and fetches from an opaque origin are CORS requests. The app's own `<script type="module">` and its `fetch('./data.json')` need an `Access-Control-Allow-Origin` of `*` or `null` on the response (standard CORS for an opaque origin; not run in a browser). Change: the section's served headers name ACAO or forbid module scripts. The choice between `*` and `null` goes in the report (either value also opens the files to any site or to any sandboxed frame).

F3. The CSP keyword 'self' in a sandboxed document. Whether 'self' matches the URL's origin in an opaque-origin document is browser-dependent, and I did not verify it. Change: have the section name sources by the served address or scheme, not 'self', or name the browser check the build step runs.

F4. penpal with an opaque child. penpal.mjs `#isAllowedOrigin` accepts only an exact string, a RegExp or "*". `#getOriginForSendingMessage` returns "*" only when the concrete remote origin is "null" and allowedOrigins includes "*"; otherwise it posts to targetOrigin "null", which `postMessage` rejects as an invalid target (HTML spec; not run in a browser). The parent's allowedOrigins must therefore include "*". The restriction then rests on `if (source !== this.#remoteWindow) return;` in `#handleMessageFromRemoteWindow`. The child's default allowedOrigins is its own origin ("null"), so the child must be given the page's origin. The brief also does not say how penpal's child code reaches the app: shipped in the app folder, or served by oculus at an address the CSP allows. Change: state these three facts from scratch/E1-brief-check/package/dist/penpal.mjs:520-610, and require the section to name the parent's `allowedOrigins: ['*']` with the source-window check as the guard, the child's allowedOrigins, and where the child script comes from.

F5. What `sameOrigin` and `allowedOrigin` do. `allowedOrigin` is used only on the socket's upgrade (DESIGN.md:146; auth.ts:13-15). An opaque frame's WebSocket to the page's host sends `Origin: null`, and `allowedOrigin('null')` returns false, so the upgrade is refused. The brief's "never reaches the socket" holds, but the reason to cite is auth.ts:29-38. This is sound reasoning and was not run.

F6. Read ranges. spec.md:8 limits the builder to the listed ranges, but the brief's own cases need DESIGN.md:249, :283, :299 and :305, plus hooks.server.ts, +page.server.ts, +page.svelte, Collection.svelte, diagrams.ts, writes.ts:239-494 and `grep -rhoE publish` for the channels. None of these is in Read. Change: add them.

## Cases

Cases the text implies but does not state, each with the answer the brief should fix or require the section to state:

C1. An app's file address opened directly in a browser tab, or a popup if `allow-popups` is granted. Without the frame's sandbox attribute the document is same-origin, can read `/__data.json` (P7) and gets the token and every GET under /api/ (`Sec-Fetch-Site: same-origin` is admitted at auth.ts:51). Expected: the server sends `Content-Security-Policy: sandbox allow-scripts` (the `sandbox` directive) with every app response, so the document is opaque wherever it opens, and the sandbox leaves out `allow-popups-to-escape-sandbox`. This is the most important missing case.
C2. An app that asks the server for its own files before approval, or after its files changed. Expected: the server refuses to serve an unapproved or stale app, so approval is not enforced by the page alone.
C3. A symbolic link inside an app folder pointing out of it (for example to `~/.ssh`). Expected: refused by the realpath check, as in diagrams.ts:41-50.
C4. An app name that equals a built-in view id or a collection key (`focus`, `funding`). Collection ids are the bare key (Collection.svelte:19-24), and `ViewId = string` (layout/model.ts:11). Expected: app views use a namespaced id such as `app:<name>`, and a name that is empty, repeated or reserved is a finding. spec.md:58 requires the empty, duplicate and colliding cases.
C5. A saved layout naming an app's view on a machine that has the app, drawn before the app list arrives. Expected: the list rides with the page data for the first frame, as the collection keys do (+page.server.ts:20-22), so the tab is not drawn as unknown for a frame and is not closed.
C6. A manifest asking for `undo` (which takes back any change by time, writes.ts:494), `rail` (rewrites config/layout.yml) or `session`. Expected: the section names which kinds are open to apps. I recommend closing undo and rail to apps, and listing that as a choice.
C7. A manifest naming `pty:<id>`, `inbox`, `calendar`, `sessions` or `usage`. Expected: refused at approval, or shown with a warning. The section says which (P4).
C8. The manifest's title, description and words are untrusted (spec.md:58). Expected: drawn as text in the catalogue, the tab and the approval dialog, never as HTML.
C9. A wallpaper theme is on (the body carries `wall`). Expected: the section says what the frame's box paints (DESIGN.md Theming, 214-216) and whether the bridge also sends `wall` and the panel opacities.
C10. A keyboard chord or right-click while the frame has focus. The page's chord handler and Z55's page-wide context-menu handler do not see events inside the frame. Expected: the section states it, or says the bridge forwards a set of keys.
C11. An app tab in a floating pane or a popped-out window (S3). Expected: the bridge is rebuilt per frame instance on remount.
