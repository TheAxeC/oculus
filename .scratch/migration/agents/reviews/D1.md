3. THE UNDO

`undoChange` (`src/lib/server/writes/undo.ts:164`): `nothing` when `change.undo === 'none'` (`:165`), `gone` when the address is no longer there (`:167`), `moved` when the value now differs from the record's `after` (`:168`), and `nothing` again when no writer exists for the kind (`:170`). `valueNow` (`:96`) and `apply` (`:175`) read the same dispatch table, so the address checked is the address written.

- The value-now check against `after`: correct for every kind I exercised. `same()` (`src/lib/server/changes.ts:104`) compares maps by key rather than by key order, which is needed because one side comes from a JSON line and the other from a fresh parse.
- A later change to the same key: refused. Verified by `tests/routes/undo.test.ts:75` and by my own probe (409, `{"error":"moved"}`, file unchanged).
- A record whose file no longer exists: refused with `gone`. I verified this by removing the project folder between the write and the undo: `404 {"error":"gone"}`. There is no test for it.
- An undo of an undo: works. `tests/routes/undo.test.ts:49` undoes the undo and asserts the manifest comes back to the later value.
- An undo of a session unhide: the orchestrator's read is CONFIRMED. I ran hide, then unhide, then undo through `handleWrite`: the unhide records `{"field":"hidden","before":true,"after":false,"undo":"field"}` and the undo answers `409 {"error":"moved"}` with the overrides file left at `{"sessions":{}}`. The cause is exactly as described: `overrides.ts:85` deletes the key while `:100` records `after: false`, and `undo.ts:105` reads `entry[change.field] ?? null`, so the check compares `null` with `false` and refuses. Bringing a dismissed session back can never be undone. The fix is one word, `after: plain(hidden ? true : undefined)` or the equivalent at `overrides.ts:100`, and it forces a change to `tests/server/overrides.test.ts:41`, which asserts `record(path, 'hidden', true, false)` in the same case that asserts the file holds `{ sessions: {} }`. That test is what keeps the suite green over the defect.

A second defect of the undo, named by neither the report nor the items: an undo whose writer refuses or writes nothing answers `200 { ok: true, changed: [], refused: [...] }`, because `undoChange` returns the writer's `WriteOutcome` unchanged and `answer` (`src/lib/server/writes.ts:419`) does not look at it. The view checks only `answer.ok` (`History.svelte:101`) and therefore says `history.undone`, "X is back as it was", over a file that was not written; `reload()` then draws a list with no new row. I reproduced it: deleting the only lead of `feeds/position-leads.yml` and undoing it answers `200 {"ok":true,"changed":[],"refused":[{"field":"entries","reason":"entries is not a block list"}]}` and the lead does not come back. With two leads in the file the same undo works, so the case is a feed whose last entry was deleted; the identical shape occurs for an undo that normalises back to no change (the empty-metalist case the report lists as a limitation). The narrow fix is in the view (treat a 200 with `refused` non-empty, or with `changed` empty, as a refusal); the broad one is in `undoChange`.

Restoring a deleted lead is also not a faithful restore: the record's `before` is `{title: 'Lead'}` but `addLead` (`feeds.ts:331`) re-derives `status` and today's `date` and appends the entry at the end, so the undone file reads `- title: "Second"` then `- title: Lead / status: open / date: 2026-09-15`. Not a correctness bug in the log, but the row said "Lead is back as it was" and it is not.

2. `restoreFeedEntry` AND THE `refused` OUTCOME

`restoreFeedEntry` (`src/lib/server/feeds.ts:393`) writes the recorded fields and nothing else: `:416-425` walks `Object.entries(fields)` alone, with no default for `status` or `date` and no `localDate` call in the function. Order is `renderEntry(fieldNames(parsed.schema), ident, values)` (`:426`), which puts the identity first, then the schema's order, then any field the schema does not name in the record's own key order (`src/lib/server/entry-edit/render.ts:30-31`); a feed with no schema (`radar`, `inbox`) gets `fieldNames(undefined) === []` (`src/lib/data/validate.ts:101`) and therefore identity-first plus the record's order, which is the file's order because the record came from the file.

The four shapes of `entries:`:
- absent: `parse(source).entries` is undefined, so `startEntries` (`src/lib/server/entry-edit/entries.ts:106`) takes the `pair === undefined` branch at `:119` and appends `entries:` with the block at the end of the file.
- present with nothing under it: the `dangling` branch at `:112` splices the block after the key line.
- `entries: []`: `Array.isArray([])` is true, so `appendEntry` is chosen, and `appendEntry` refuses at `src/lib/server/entry-edit/entries.ts:157-159` with `entries is not a block list`. The undo then answers 400 `refused` and the view says the file would not take the value back. Honest, and not covered by a test.
- a flow list with entries: the same refusal, same path.

It cannot duplicate an entry: `src/lib/server/feeds.ts:410` refuses when an entry with that identity is already in the file, and `undo.ts:173` refuses with `moved` beforehand if the entry is back. It keeps every other byte in the two block-list paths; the one exception is the key-absent path, where `startEntries` writes `source.replace(/\n*$/, '\n')` (`entries.ts:120`) and so collapses trailing blank lines.

Two fidelity gaps, neither tested and neither in the report's "Still true" list. `renderEntry` silently drops a field whose value is `null`, `''`, an empty list or an empty map (`render.ts:35-38`) and a scalar that renders across lines (`:49`), so an entry that held one of those comes back without it while the row says it is back as it was. And `restoreFeedEntry` returns `{ ...out, refused: [...refused, ...out.refused] }` (`feeds.ts:439`) without looking at `refused`, so an undo that wrote the entry with some fields rejected answers 200 with `changed: ['entries']` and a non-empty `refused`; `undoSaid` ignores `answer.refused` entirely (`rows.ts:77-83`), so the reader is told the value is back and never sees the reasons.

`undoChange`'s `refused`: I found no undo that writes bytes and answers `changed: []`. Every writer an undo can reach guards its write on the change list: `saved` at `src/lib/server/writes/entries.ts:46` (`edit.changed.length > 0 && edit.text !== source`), `writeManifest` at `src/lib/server/writes/manifest.ts:198`, `writeDeck` at `src/lib/server/writes/deck.ts:92` (returns `changed: []` when the text is identical, before the write at `:97`), `setHidden` at `src/lib/server/sessions/overrides.ts:90` and `setOverride` at `:168`, both after the change list is non-empty. The reverse, writing nothing and answering a field, is structurally possible only through `saved` when an edit reports a change with identical text; `setEntryFields` returns early on an empty change list (`src/lib/server/entry-edit/entries.ts:88`) and I found no edit function that reaches it.

3. THE FOLD AND THE VIEW

`undoSaid` (`src/lib/views/history/rows.ts:77`) and `sentenceFor` (`:86`) are a pure fold over `{ ok, changed, error }` and are tested without a DOM (`tests/views/history.test.ts:92`, `:99`, `:112`).

The wire word is never drawn for any outcome the undo branch produces. `sentenceFor` maps `moved`, `gone`, `unknown`, `nothing` and `refused` to their own sentences (`rows.ts:87-91`), and those five are the only errors `src/lib/server/writes.ts:392-398` can answer for a body that parsed as an undo. What can still reach `t('history.refused', word)` at `rows.ts:92` is everything upstream of the undo branch or of the server: the origin refusal `the request did not come from this page` (`writes.ts:365`), the token refusal `the write token is missing or stale` (`writes.ts:368`), `HTTP <status>` when a non-ok answer carries no string `error` (`src/lib/state/writes.svelte.ts:350`), and a thrown fetch's message with `network: true` (`:371`). Those are English sentences and a browser error string, not oculus vocabulary, so the "never the wire word" rule holds; but the branch has no test, and a reader can be shown `The undo was refused: Failed to fetch`.

The kind gate: verified by running, see item 4 above. `tests/kinds.ts:15` matches `/body\.kind !== '([a-z-]+)'/g` over `src/lib/server/writes/bodies.ts`. Every parser in that file uses exactly that form: `:112`, `:125`, `:145`, `:154`, `:175`, `:184`, `:192`, `:204`, `:213`, `:221`, `:244`, `:252`, `:258`, `:266`, `:282`, `:294` (undo, filtered out at `tests/kinds.ts:18`) and `:301`, seventeen in all, sixteen after the filter, which is the sixteen words in `config/text/views/history.yml`. It is a grep, so its weakness is that it derives the expected list from the same construct it checks: a kind added through a `switch`, a double-quoted literal or a name with a digit or underscore would be missed by the list and by the gate together, and would then throw at render time in the browser instead (`src/lib/state/text.ts:56`). Nothing in the round makes that worse; it is worth knowing before a kind is added.
