A save's own push does not lose anything: when the order changed the signature changes and the view redraws from the file, which is exactly what was just written; when only ticks changed the signature is unchanged and the work is kept. # 4. Item 9's instance-state move

Where the work lives: `Slides.svelte:67` reads `parseSlidesState(instanceState(instance.id))`, `:98-100` writes it, `:178-182` writes it after a save. `ui.setInstanceState` (`src/lib/state/ui.svelte.ts:312-314`) goes through `save()`, which persists to localStorage (`:193`), so a page switch and a reload both keep the pane's unsaved work, and closing the tab clears it (`:316-322`). A second Slides pane is only possible on a second page: `openBeside` (`src/lib/state/layout.svelte.ts:700`, `openInto` `:709-727`) activates an existing `slides` view in the page rather than making another. Two such panes on two pages each hold their own work with no warning to either; last Save wins.

**The signature rule does misfire, on a refused save after a reorder.** `save()` writes `at: catalogSignature(picks.order)` for every answer, success or refusal (`Slides.svelte:178-182`). When the write is refused (`invalid_order` from a race, `unwritable`, or a network failure) the file is unchanged, so the derived `signature` (`:65`) is still the file's catalog order while `held.at` is the reader's reordered one. `dropped` (`:73`) goes true, so `said` (`:93`) draws `slides.dropped` instead of the failure sentence `saveMessage` just computed, and `picks` (`:76-84`) falls back to `fileState`, discarding the reorder. The reader is told the deck changed on disk when it did not, loses their work, and never sees which refusal it was, which is the opposite of what item 6 was for. `tests/views/slides.test.ts:231` renders exactly this state and asserts that outcome, so the behaviour is shipped and test-locked; no test frames it as a failed save. The fix is to keep `at: signature` on a refusal and write `catalogSignature(picks.order)` only when `answer.ok`.

Two smaller misfires of the same rule: a successful save whose push also carries a catalog change (a PRESENT.md written in the same second) shows `slides.dropped` instead of `slides.saved`, and a push arriving while `busy` makes the post-save write store a signature and picks that are not what was sent. Both are narrow; the refusal case is not.
