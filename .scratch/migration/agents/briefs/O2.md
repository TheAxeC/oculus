# Brief: O2, data sources part one, manifests and registries

Read `../spec.md` first; it governs this package unchanged. Then `tools/oculus/DESIGN.md`, the sections "Layer 1, data" and "Boundaries". This package is layer 1 only: it reads files and returns raw records with provenance. It validates nothing and resolves nothing; that is O4.

## What to build

Under `tools/oculus/src/lib/data/`:

- `model.ts`: the types, no logic. `RawManifest` (every key the YAML held, untouched, plus the provenance fields below), `RawRegistryEntry` (the YAML entry untouched, plus `source`), and the typed entities `Project`, `Venue`, `Dataset`, `Program`, `Domain`, `Funding` with their id-carrying relation fields (`venueId`, `fundingIds`, `datasetIds`, `programIds`, `domainIds`), which O4 fills. `Id` is `string`. A `Finding` type: `{ file: string; key: string; message: string }`.
- `sources/manifests.ts`: `readManifests(hub: string, scan: ScanRule[]): { manifests: RawManifest[]; findings: Finding[] }`. A `ScanRule` is `{ dir: string; type?: string; nested?: boolean }`, the shape of the five entries under `scan:` in `tools/cockpit/data/config/layout.yml` (read it for the exact list; do not copy the file, O5 copies config). A flat rule reads `hub/<dir>/<name>/project.yml` and gives the manifest `type` from the rule; a nested rule reads `hub/<dir>/<category>/<name>/project.yml` and takes `type` from the manifest itself, with the category folder recorded. Provenance on every record: `file` (absolute path), `folder` (relative to the hub, `projects/coauthor/active/clinical-hccnet`), `id` (the folder's basename; the manifest's own `id` is kept as it was read, and a mismatch is a finding, not a repair), `tier` (the rule's `dir` basename: `ideas`, `active`, `manuscripts`, `coauthor`, `archive`), `category` (nested rules only). A folder without `project.yml` is skipped silently; a `project.yml` that does not parse, or parses to something other than a map, is a finding and the record is omitted. Nothing under a project's `code/` or `attic/` is looked at.
- `sources/registries.ts`: `readRegistries(hub: string, files: RegistryFiles): { venues, datasets, programs, domains, funding: RawRegistryEntry[]; findings: Finding[] }` where `RegistryFiles` names the five relative paths (`registries/venues.yml`, `registries/data.yml`, `registries/programs.yml`, `registries/domains.yml`, `funding/funding.yml`). Each file is a map with an entry list under `entries`, except `registries/data.yml` whose list is under `datasets`; the other top-level keys (`schema`, `intro`, `title`, `theme_labels`) are returned as `meta` per registry, untouched. A missing file gives an empty list and one finding; a file that does not parse gives an empty list and one finding; an entry without a string `key` (the id field in every registry) is a finding and is kept with `key: ""`.
- Both sources use the `yaml` package and `node:fs`, synchronous reads, and throw on nothing: every failure is a finding.

Under `tools/oculus/tests/data/`:

- `manifests.test.ts`: builds a hub in a temporary directory with the five tiers, at least one flat and one nested manifest, a folder without `project.yml`, a manifest whose `id` differs from its folder, a manifest that is not valid YAML, and a `code/project.yml` decoy that must be ignored. Asserts the records, their provenance fields, the findings, and that the order of records is deterministic (sorted by `folder`).
- `registries.test.ts`: builds the five files in a temporary directory, one with `datasets` as its list key, one missing, one unparseable, one entry without `key`. Asserts the lists, `meta`, and the findings.

## Facts checked on the tree, 2026-09-10

- `find projects -name project.yml | wc -l` prints 91: 50 in the flat tiers (ideas 31, active 4, manuscripts 15), 16 under `projects/coauthor/<category>/`, 25 under `projects/archive/<category>/`. None sits under a `code/` or `attic/` folder.
- Nested categories seen: `coauthor/{abandoned,active,published,phd}`, `archive/{disproved,dropped,nogo,...}`. A nested manifest's `type` is its own field (`in-prep`, `abandoned`, `disproved`, `dropped`), not the category folder.
- In every manifest sampled, `id` equals the folder's basename.
- Registry shapes: `venues.yml` `{schema, entries[70]}`, `data.yml` `{intro, theme_labels, schema, datasets[49]}`, `programs.yml` `{schema, entries[9]}`, `domains.yml` `{schema, entries[12]}`, `funding/funding.yml` `{title, intro, schema, entries[11]}`.
- The manifest schema (`tools/cockpit/data/config/manifest-schema.yml`) names 45 fields; dotted names (`status.chips`, `followup.do`, `code_availability.url`) are nested maps in the YAML. O2 does not use the schema; O4 does.

## Conventions

Every file under 1000 lines. ASCII. No dependency beyond what O1 installed (`yaml` is already there). No reads outside the `hub` argument; tests never point `hub` at the real research hub, only at the temporary directory. `tests/boundaries.test.ts` must still pass: `data/` imports nothing client-side.
