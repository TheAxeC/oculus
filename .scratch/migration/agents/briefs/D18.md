## What to build

1. **The setting.** `config/behavior.yml` gains, with a comment in the file's style:
   ```yaml
   # The Processes view lists the local processes whose program is one of these names, beside oculus's own terminals.
   processes:
     patterns: [python3, codex, claude, node, latexmk]
   ```
   `options.yml`'s `behavior.yml:` block gains its entry `processes.patterns` with a description ("The program names the Processes view lists beside oculus's own terminals. A name matches a process whose program, or whose first argument, has that file name. A list that is not names is refused."). The entry carries `default: [python3, codex, claude, node, latexmk]` and `control: list`, as `options-catalog.test.ts` requires. A reader `processesSettings(config)` in `data/sources/config/settings.ts` (its head comment's list of readers gains it) gives `{ patterns: string[] }`: a list of names, each non-empty, without `/` or a space, duplicates read once; `[]` is accepted and lists oculus's own processes only; a missing `processes:` gives the default list; anything else (a non-list, a non-string entry, an empty name, a name with `/` or a space) is refused the way the other behaviour readers refuse, and `live-settings.ts` hands a changed list to the watcher at the next config push, as it does for the other groups (`LiveStart` and `LiveTargets` gain `processes`).
2. **The rows.** A new folder `src/lib/server/machine/processes/`. `read.ts` builds one read: the process table from `systeminformation`'s `processes()`; oculus's own processes (Z245), which are the pane process of every pane of every terminal session (a session `oculus-<id>` whose id is a terminal id; one `tmux list-panes -a -F '#{session_name} #{pane_pid}'` read added beside `listTerminals` in `server/machine/pty/sessions.ts`, through the same `run` and its timeout) and every descendant of it by parent pid, the walk keeping a visited set so a self-parent ends it; the usage sessions and foreign `oculus-` sessions are not own; the matched processes, by Decision 2; and the folder of each listed process and each agent (item 3) from one `lsof -a -d cwd -Fn -p <pids>` call over those pids only, each pid an integer, run as an argument list with a 5 s timeout that kills the child; `lsof` exits 1 when one pid has gone and still prints the others, so its output is read whatever its exit, a pid it prints nothing for has an empty folder, and a timeout or a failure to run gives every folder empty. `processes()` gets a 10 s timeout: a read that passes it fails as a thrown read does (case 12); an empty table is a failed read. A row is `{ pid, ppid, user, started, cpu, memory, command, folder, terminal? }`: `started` an ISO time in UTC, empty when the library's value does not parse; `cpu` a finite percentage of at least 0; `memory` bytes resident, converted from the library's unit; `command` the command line (the program path and its arguments) cut at 1,000 characters with `...` (Z247); `terminal` the id of the oculus terminal whose tree holds the process. Each value is read from the library's own type declarations in `node_modules/systeminformation/lib/index.d.ts` and its source, and the report quotes the field names, units and the `started` format it relied on; a non-finite or negative number reads as 0. A project for the head line is the deepest project of the hub whose folder holds the row's folder, matched by whole path segments over real paths (`realPath(path, true)` of `server/core/paths.ts` on both sides, so a linked or differently cased hub still matches). A process that is oculus's own and also matches is one row, oculus's own. `processes()` and `lsof` are reached through injected functions, so a test passes fixed tables and never reads or signals the machine's processes.
3. **The watcher.** `src/lib/server/machine/processes/watch.ts` publishes the payload `{ status: 'ok' | 'failed', updated, rows, agents, projects, error? }` on a new channel `processes`: `agents` the count of processes in the whole table whose program is `claude` or `codex` by Decision 2's rule, a process whose parent is the same program not counted again (Z246), the usage sessions' trees left out; `projects` the count of distinct projects over oculus's own rows and the agents. It reads every ten seconds while the hub has at least one subscriber on `processes`, and reads nothing while none (Z244): every page subscribes to `processes` with its other channels in `routes/+page.svelte`, so the reads run while a page is open; the first subscriber after none starts a read at once, and the hub's replay of the last payload on subscribe stands, since a later page gets the newest read of a watcher that is running. A failed read publishes `status: 'failed'` with the last good rows and the error's sentence. One read at a time: a tick while a read is in flight does nothing. Patterns changed while a read is in flight: that read's result is dropped and a fresh read runs. After `close()` nothing is published and no timer or child process outlives it. The hub (`server/core/channels.ts`) gains the two calls the watcher needs: whether a channel has a subscriber, and a callback when a channel goes from no subscriber to one (called once at that change, not for every later subscribe message of the same sink), each with its cases in `tests/server/core/channels.test.ts`. `server/root/context.ts` builds the watcher beside `watchHpc` and closes it where `hpc.close()` is called; the file stays under 900 lines (move the watcher wiring of the machine pollers into a module under `server/root/` when the additions would pass it).
4. **The payload type.** `src/lib/data/model/model-processes.ts` declares `ProcessRow` and `ProcessesPayload`, exported through `data/model/index.ts`, and `state/client/payloads.ts` gains the channel's schema, so the socket checks the payload as it checks every channel's; `state/shared/stores/shapes.ts` gains `processes` in `Payloads` and the store accessor, `state/client/entities.svelte.ts` its `processes: () => payload('processes')`, and `routes/+page.svelte`'s channel list `processes`. Each row inside the list is read where the state layer reads it; a row of the wrong shape is dropped there.
5. **The page.** A store `createProcesses(entities)` that reads the payload, and the view `Processes.svelte` registered as `{ id: 'processes', label: 'views.processes', glyph: 'views.processes_glyph', group: 'info', order: 6 }`. The view draws: the head line "<n> projects in flight, <m> agents running" (`processes.head`, with the singular forms); a table with the columns PID, Parent, User, Started, CPU, Memory, Command, Folder; oculus's own rows first, grouped under their terminal's name with the terminal's pane process as the group's row, then the matched rows sorted by CPU, highest first; the time of the last read, the failure sentence while `status` is `failed`, and a reading sentence before the first payload. A press on a column head sorts by it, as Activity Monitor does: within each terminal's group and within the matched rows, the groups keeping their place first. The Command cell shows the command line, cut with an ellipsis in the cell and whole (as the payload carries it) in its title. The view is added to the System page's arrangement in `config/layout.yml:93` after `gallery`; the chords become y1 to y7 in `HELP.md:70` and `config/text/app.yml:12`, with `catalogue.test.ts` and `registry.test.ts` updated. Its glyph is a new `processes: "(p)"` in `config/catalogs/glyphs.yml` and `processes: cpu` in `icons.yml`.
6. **Stop.** The group row of an oculus terminal carries a Stop control; no other row has one. A press asks first in `views/shared/AskConfirm.svelte`'s form, naming the terminal and its pane process as `DESIGN.md:150` requires: `processes.stop_question` "End the terminal '<name>' (<command>, pid <pid>)? Every process under it ends with it, including any started there by hand.", with the terminal's name as the terminals store draws it (its title, else its name) and the confirm's own buttons; on Confirm the store calls the terminals store's `endTerminals([id])` (`state/sessions/terminals.svelte.ts:791`), the end the UI's `endTerminals` (`state/workbench/ui.svelte.ts:343`) reaches for a closed tab's terminals. The report states, from the Terminal view's code, what a Terminal tab showing that terminal draws after the end. The view never signals a pid itself. A group whose pane process is not in the table (it has just exited) is drawn from the terminal record with empty figures and keeps Stop.
7. **The folders.** The three full folders are split before the new files go in: `views/system/hpc/` and `views/system/usage/` move to `views/system/machine/hpc/` and `views/system/machine/usage/`, beside the new `views/system/machine/processes/`; `tests/views/system/hpc.test.ts` and `usage.test.ts` move to `tests/views/system/machine/` beside the new `processes.test.ts`, mirroring the view folder; `state/system/hpc.svelte.ts`, `hpc.ts`, `usage.ts`, `usage-refresh.svelte.ts` move to `state/system/machine/` beside the new `processes.svelte.ts`; `config/text/views/system/hpc.yml` and `usage.yml` move to `config/text/views/system/machine/` beside the new `processes.yml`; `tests/state/system/hpc.test.ts`, `usage.test.ts`, `usage-refresh.test.ts` move to `tests/state/system/machine/` beside the store's test. Every importer and every list that names a moved path is updated (the 21 files the grep above lists; `allow-audits.txt:61` re-keyed with the moved view test); a moved file's text changes only in its import paths and comments that name paths.
8. **Words and docs.** Every word is a key of `config/text/views/system/machine/processes.yml` (`views.processes`, `views.processes_glyph`, the head line, the column heads, the Stop control, the question, the read time, the failure sentence, the empty sentence "No process matches the patterns."). `DESIGN.md:114`'s list of channels is written whole, as `+page.svelte:171-182` subscribes them, with `processes`; `DESIGN.md:162` says a group's folder may hold a subfolder of views when it is full, as `views/system/workbench/` and `views/system/machine/` do; a paragraph "**Processes view.**" after the Live HPC paragraph at `DESIGN.md:132` says what is listed, the ten-second read while a page is open, the matching rule, the agent count, and that only oculus's terminals have Stop. `HELP.md` gains a `processes` row after the `history` row at `:145`, saying what the view lists, that it reads every ten seconds while a page is open, how `processes.patterns` matches, that the folder column is the process's working folder, that the CPU and memory figures come from `ps` and differ from Activity Monitor's own measure while PID, user and command match it, and that Stop ends an oculus terminal and everything in it after a question. `README.md:13` names `systeminformation` (MIT) with what it does. `config/catalogs/options.yml` as item 1.

## Decisions taken in this brief (each reversible, none silent)

1. oculus's own processes are the process trees under every pane of its terminal sessions (Z245); the usage sessions and foreign `oculus-` sessions are not own. Processes oculus runs outside tmux (ripgrep, git, ssh, latexmk builds) are outside the ruling's "in tmux" and are listed only when a pattern matches them.
2. The matching rule: a pattern matches a process when it equals the file name (the part after the last `/`) of the command line's first word, or of its second word. Five real cases from this machine under the rule: `claude --resume 6266a558-...` with `claude`: a row; `node .../node_modules/.bin/vitest run ...` with `node`: a row; `bash .../pyenv-exec python3 - ...` with `python3`: no row (a wrapper; the `python3` it starts is its own process and matches); `/bin/zsh -c source /Users/axelfaes/.claude/shell-snapshots/...` with `claude`: no row; `.../.codex/plugins/.../ChatGPT for Chrome chrome-extension://...` with `codex`: no row. A substring match would list the last two wrongly; the second word covers a script run by its interpreter (`node /usr/local/bin/codex`). A path with a space in its first word (the ChatGPT case) is split at the space, and neither part's file name is `codex`, so it stays out.
3. Agents are the processes of the whole table whose program is `claude` or `codex` by that rule, whatever `processes.patterns` holds, one per tree of the same program (Z246); a project is in flight when an oculus terminal or an agent works in its folder.
4. Stop ends the terminal (tmux's `kill-session`, the end a terminal tab's close makes), never a single pid: the terminal is what oculus started, and everything in it ends with it, a process the reader started there by hand included, which the question says; the question always asks, and names the terminal and its pane process as `DESIGN.md:150` requires.
5. The read cadence is fixed at ten seconds while a page is open (Z244), said in `HELP.md` and `DESIGN.md`, with no config key, as the plan line books it.
7. A command line is cut at 1,000 characters in the payload (Z247); every matching row is listed.
6. The HPC and Usage modules move into a `machine` subfolder of each full folder, the one split that makes room for the Processes view beside the other two views of this machine's and the cluster's processes.
