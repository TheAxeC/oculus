# Brief: Q111, an undo gives a removed manifest field's lines back where they stood

Read `.scratch/migration/agents/spec.md` first; its rules govern this step unchanged. The configuration lists no further standards pages. No ADR touches the step: the repository has no `docs/adr` folder (`ls docs/adr` finds none).

A design ruling decides what is built. It never exempts the code: every line is written to the standards, so that people can read, use and maintain it.

## The plan line

Q111 Undo gives a cleared field's lines back: a manifest write that removes a field records the removed lines and where they stood (an optional `removed: { offset, text, next }` in `~/.oculus/changes.jsonl`), and its undo puts those lines back, a group clear included, so the text is as it was; a record without the key undoes as today; `edit/writes/`; after Q110 (ruling Z105) (ruling Z110)

## The rulings it carries (plan.md, Rulings)

- Z105: a manifest write that removes a field keeps the removed lines and where they stood, and its undo puts them back, a group clear included.
- Z110 (c): the record's key is `removed: { offset, text, next }`. `offset` is the index (the name `at` is kept for the record's time), `next` is the text from the end of the removed span to the end of its line in the file the write left (the whole following line for a whole-line removal, empty at the end of the file). The undo puts the text back just before the occurrence of `next` nearest to `offset`, at a line start for whole lines; only when `next` is not found does it fall to the nearest line start that passes the parse check, and then to today's value write.

## What to build

1. **The removal a field's edit made.** `setFields` answers a new type `SetFieldsResult`, which is `EditResult` with one more key (`EditResult` itself is unchanged, since twelve functions outside this step answer it), holding the removal of each changed field whose edit took text out and put none in: `removed: Record<string, { offset: number; text: string; next: string }>`. `text` is the characters that field's own edit removed, taken where the splice is made (`removePair`, `removeFlowChild`, the parent pair of a map's only child), never from the whole write's diff. `offset` is a UTF-16 code-unit index (a JavaScript string index) into the file's text read as UTF-8: the point where the removed text stood, carried through every later edit of the same write, so it is the index in the text the write left (an edit after it in the file leaves it; an edit before it moves it by that edit's change in length; an edit whose span holds the point moves it to that span's start). `next` is the text of the file the write left from `offset` to the end of that line, the line break not included (a `\r` before a `\n` belongs to the line); for a whole-line removal this is the whole following line, and it is empty at the end of the file or before an empty line. A field whose edit replaced or added text has no entry. When the final check fails and nothing is written, `removed` is empty.
2. **The record.** `ChangeRecord` gains an optional `removed?: { offset: number; text: string; next: string }` with a doc comment saying what each key is, that `offset` is an index into the file (the record's time is `at`), and that only a manifest write that removed a field carries it. `writeManifest` puts `removed` on the record of each field that has an entry in the edit's `removed`, and on no other record. `changes.ts`'s log shape is unchanged (a loose object already keeps the key).
3. **The undo.** The undo runs every check `writeManifest` makes today before anything is inserted: the manifest found and inside the hub, the field named by the schema or a group name, `unwritable` for its type, and `READ_ONLY`; a record that fails one is refused exactly as today, whatever its `removed` says, and the file is unchanged. A group name is accepted with a value only on this path. `removed` is well-formed when it is a plain object whose `offset` is a non-negative integer, whose `text` is a non-empty string and whose `next` is a string; anything else (`null`, an array, a string, `offset` `-1`, `3.5` or `"10"`, `text` empty or not a string, `next` missing or not a string) is ignored and the undo writes the value as today. `text` is whole lines when it ends with `\n`; a line start is index 0 or an index that follows a `\n` (so CRLF files work). When a manifest change carries a well-formed `removed` and its `before` is not `null`, the undo, after the existing check that the file holds `after` (`undoChange`, `undo.ts:180-191`), puts `text` back instead of writing the value, at the first place in this order where the new text passes the same check `setFields` makes (it parses to the current parsed document with the field set to `before`):
   - The places where `next` stands: an index `p` such that the file's text from `p` to the end of its line, line break not included, equals `next` (an empty `next` so matches the end of the file and the start of an empty line); for whole-line text `p` must also be a line start. They are tried in order of their distance from `offset`, nearer first, the earlier of two at equal distance.
   - When no place of `next` passes, and only for whole-line text, every line start of the file, the end of the file included when it follows a `\n`, in the same order.
   - When none passes, the undo writes the value as it does today; a group name (`followup`) with no place that passes, or with no well-formed `removed`, is refused as today.
   An index between the two halves of a surrogate pair is never tried. An `offset` past the end of the file only sets the distances. The write goes through the manifest writer's own path (`insideHub`, `writeTextAtomic`), and it is recorded like every write: `before` `null`, `after` the restored value, `undoes` the change it took back, and no `removed`. Put the insertion in `yaml-edit.ts` beside `setFields`, as one exported function that answers `EditResult`, and have `writeManifest` take the record's `removed` as an optional argument used only with the `record` reading; `apply` in `undo.ts` passes `change.removed`.
4. **An undo of that undo.** It removes the field again through `setFields`, so its record carries a new `removed`, and undoing it puts the lines back again.
5. **Docs.** `DESIGN.md:140` and `DESIGN.md:376` and `HELP.md:254` each gain one sentence in their own voice: a write that removes a field keeps the removed text, where it stood and the text that followed it, so its undo puts the text back before that following text, as it was, whatever else changed in the file; when the following text is gone, the text goes back at the nearest line start that gives the right values, and only when none does does the value come back as a new line, as for a change that carries no such text. Every other sentence of those paragraphs that the change makes false is corrected. Head comments of `manifest.ts`, `undo.ts` and `yaml-edit.ts` are corrected where the change makes them false (grep them).

## Decisions taken in this brief (each reversible, none silent)

1. `offset` is an index into the file's text, not a line number: a flow map's child is removed from inside a line (case 5), which a line number cannot place.
2. `text` holds the exact characters removed, comments and the parent line included, so the undo gives the bytes back.
3. `next` stops before the line break, so a line with a changed ending (a comment added after the value) no longer matches and the undo falls to the line starts, as Z110 (c) says for a following line that changed.
4. An edit of the same write whose span holds a removal's point moves the point to that span's start (item 1), which is where the removed text stood in the text the write left.
5. The undo's own record carries no `removed`, since it removed nothing.
