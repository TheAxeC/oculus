## What is on the tree (read 2026-09-14 at 01:00 on main at 0c4a67d2; R5 runs before this and moves the keyboard code out of `Workbench.svelte`, so the line numbers are re-read at dispatch)

- The keyboard cursor over the cards of a board (Q14): `src/lib/shell/keys.ts` is pure and returns actions (`{ kind: 'cursor', direction }`, `{ kind: 'clear-cursor' }`, an Enter on the cursor at line 150) from a `context.cursorActive` flag; `src/lib/shell/Workbench.svelte` (lines 114 to 330 today: `cursorIndex`, `cursorPane`, `cards(pane)`, `selectCard(pane, index)`, `moveCursor`, `clearCursor`, `paneFocused`, `panePressed`) performs them by querying the focused pane's DOM for `[data-card]` elements and setting or removing a `data-cursor` attribute on one of them; `src/lib/shell/key-dom.ts` line 15 finds the cursor card with `pane?.querySelector('[data-card][data-cursor]')` to act on Enter; `src/lib/ui/Card.svelte` line 98 styles `:global(.card[data-cursor])`.
- The browser spec `tests/browser/keyboard.spec.ts` (lines 33 to 47) asserts exactly one `[data-card][data-cursor]` in the focused pane after a cursor key and that it moves; that selector is load-bearing and stays.
- The layout's instance state (`src/lib/state/layout.svelte.ts` lines 126 and 134, `instanceLayoutState(id)` and `restateInstance(id, state)`, over `restate` in `state/layout.ts` line 309; `state/instance.ts` since Q9) is where a view's own state lives and is saved.

The defect: the cursor is a DOM attribute the shell writes onto elements a view rendered. A view that re-renders (a new snapshot, a facet change) drops it; nothing but the DOM knows which card is current; the shell reaches into a view's markup, which the layer rule forbids in every other case.

## What to build (code and view; no data or wire change)

1. **The cursor is state.** The focused pane's instance state gains `cursor: string | null` (the card's `data-card` id, or null); `shell/keys.ts`'s actions stay; the performer (in `shell/workbench-keys.svelte.ts` after R5) computes the next card id from the pane's ordered card ids and writes the instance state, never an attribute.
2. **The views render it.** `Card.svelte` gains an `id` prop written as the value of its `data-card` attribute (line 51 today writes the attribute with no value) and a `cursor` prop that sets `data-cursor`; every caller passes its item's id (the project's id, the entry's key, the lead's id) and `cursor={instanceState.cursor === id}`; `key-dom.ts` finds the cursor card by the id in the state (its `[data-card="<id>"]`), not by scanning for the attribute. The ordered list of card ids a pane shows is what the view exposes (a `cards` snapshot in the instance state, or a query of `[data-card]` ids in DOM order, the brief's choice: the query of ids is allowed, since ids are data; setting an attribute is not).
3. **Survives a re-render and a snapshot.** A cursor set on a card stays on that card after the view re-renders; a card that disappears (filtered out, deleted) clears the cursor; Escape clears it; a pointer press in the pane clears it, as today.
4. **The spec passes unchanged:** `tests/browser/keyboard.spec.ts` with its `[data-card][data-cursor]` selector; `tests/shell/workbench.test.ts` and the keys tests follow the state; a new unit test proves the cursor survives a re-render and clears when its card is gone.

## Decisions taken in this brief (each reversible, none silent)

1. The cursor lives in the pane's instance state (per view instance, saved with the layout), not in a module-level store.
2. The card's id (`data-card`) is the cursor's value; an index is not, since an index moves when the list changes.
