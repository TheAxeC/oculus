# Brief: O4, validate, normalise, and the portfolio entry point

Read `../spec.md` first; it governs this package unchanged. Then `tools/oculus/DESIGN.md`, "Layer 1, data" (Validate and Normalise), "The wire model" under Decisions, and "Boundaries". O2 and O3 read files into raw records; this package turns them into the validated, normalised snapshot the socket will carry.

## What to build

Under `tools/oculus/src/lib/data/`:

- `validate.ts`: `validate(raw: RawPortfolio, rules: ValidationRules): Finding[]`. Pure: no reads, no throws, one finding per problem, sorted by `file` then `key`. The checks, each its own small function:
  - every top-level key of a manifest is one the manifest schema names (the schema is the `manifest_schema` list from the config; dotted names such as `status.chips` mean a nested map, so `status` is the top-level key to check and `chips` a key inside it); a key outside the schema is a finding naming the key. The provenance keys O2 adds (`file`, `folder`, `id`, `tier`, `category`, `type`, `manifestId`) are exempt.
  - `type` is one of the type vocabulary (`type_color` keys in the config's vocab); every type on the tree today is (`manuscript`, `idea`, `active`, `published`, `nogo`, `dropped`, `disproved`, `abandoned`, `phd`, `tech-report`, `in-prep`, `software`).
  - `venue_id`, when a string, names a venue (by the registry's `id`); each id in `funding`, `datasets`, `program` names an entry of that registry (by `key`); `domain`, a single string, names a domain; each id in `related` names another manifest by folder basename. A dangling id is a finding naming the field and the id.
  - the field shapes as the tree has them: `venue_id` string or null; `domain` string; `program`, `datasets`, `related`, `collaborators`, `funding` lists (funding may be null). A wrong shape is a finding.
  - `status.chips`, when present, is a list of strings. Read `tools/cockpit/data/config/vocab.yml` (as a fact source only; O5 copies it) and report whether a key there holds the chip vocabulary (`status_legend` is the candidate); if it does, validate chips against it; if it does not, chips are free strings and you say so in the report. Today's chips include `exploring`, `lead`, `coauthor`, `submit-ready`, `journal`, `conference`, `abstract`, `thesis`, `submitted`, `revision`, `poster`.
  - a collection entry's `status`, when present, is a `status_palette` key.
  - the O2 and O3 findings (parse failures, missing files, id mismatches) are passed through, not re-derived.
- `normalise.ts`: `normalise(raw: RawPortfolio, findings: Finding[]): Snapshot`. Builds the wire model of `DESIGN.md`: `{ version, entities: { projects, venues, datasets, programs, domains, funding, collections }, relations: { projectVenue, projectFunding, projectDataset, projectProgram, projectDomain, projectRelated, fundingProgram }, findings }`. Entities are keyed by id in plain objects; relations are `[Id, Id][]` in a deterministic order; every value is JSON-safe (a test round-trips the snapshot through `JSON.stringify` and `JSON.parse` and asserts deep equality). `Project` and the other entity types are the ones `model.ts` already declares; fill each field from the raw record's key of the same meaning (`status.line` to `statusLine`, `status.chips` to `chips`, `venue_id` to `venueId`, and so on), and extend `model.ts` only where a field the tree carries has no home. The manifest's other keys are not carried; the snapshot is the typed model, not the YAML. `version` is a monotonic integer the caller passes in (the watcher increments it), defaulting to 0.
- `index.ts`: `buildPortfolio(hub: string, config: PortfolioConfig, version = 0): Snapshot`. Composition only, about forty lines: read manifests, registries and collections with the O2 and O3 sources; validate; normalise. `PortfolioConfig` is `{ scan: ScanRule[]; registries: RegistryFiles; collections: CollectionFile[]; schema: unknown; vocab: { types: string[]; statuses: string[]; chips?: string[] } }`, and `portfolioConfigFrom(merged: Record<string, unknown>): PortfolioConfig` derives it from the merged config O3's `loadConfig` returns (the `scan`, `collections`, `manifest_schema`, `type_color`, `status_palette` keys, plus the four `*_file` keys and `funding` from `collections`). Until O5 copies the config files in, `config/` holds only `text.yml`; so `index.ts` also exports `HUB_CONFIG_TODAY`, the same values typed by hand as the probe has them, used by the integrity test and the probe and deleted by O5.
- `model.ts`, extended: `RawPortfolio`, `Snapshot`, `PortfolioConfig`, `ValidationRules`, and any field the normaliser needs.

Under `tools/oculus/tests/`:

- `integrity.test.ts`: the one test that reads the real hub, read only: `buildPortfolio(hub, HUB_CONFIG_TODAY)` on the path `loadLocal` resolves, asserting zero findings, 91 projects, 70 venues, 49 datasets, 9 programs, 12 domains, 11 funding schemes, and the JSON round trip. It writes nothing, and it skips with a printed reason when the hub path does not exist, never silently. This is the exception `spec.md` grants.
- `data/validate.test.ts` and `data/normalise.test.ts`: hand-built raw records covering every check above (an unknown key, a bad type, each dangling relation, each wrong shape, a bad chip when a vocabulary exists, a bad collection status) and the normaliser's field mapping, relation tables, determinism across two runs, and the round trip.
- `data/real-hub.probe.ts`, extended: prints the snapshot's entity counts, relation counts and findings.

## Facts checked on the tree, 2026-09-10

- Relation field shapes across the 91 manifests: `venue_id` string 51, null 21, absent 19; `datasets` list 25; `program` list 91; `domain` string 91; `related` list 47; `collaborators` list 36; `funding` list 22, null 3.
- Distinct ids referenced: 33 venues, 3 funding keys (`FAIR`, `FWO-PhD`, `ZonMw-AI-HCC`), 40 datasets, 9 programs, 10 domains. The cockpit's selftest reports zero dangling references today, so a dangling-id finding on the real hub means the check is wrong, not the hub.
- `funding/funding.yml` reaches the raw portfolio twice: O2's `readRegistries` reads it as the `funding` registry (keyed by `key`, 11 entries) and O3's `readCollections` reads it again as the `funding` collection (the layout config lists it under `collections:`). The snapshot carries it once: `entities.funding` comes from the registry, and the normaliser leaves the `funding` collection out of `entities.collections` (7 collections on the wire, not 8). The integrity test asserts 11 funding schemes and 7 collections.
- `type_color` has 14 keys and covers every `type` on the tree. `status_palette` has 42 keys and is the vocabulary for collection entry statuses, not for manifest chips.

## Conventions

Four-space indentation (`npm run format`); every file under 1000 lines; ASCII; no new dependency; `tests/boundaries.test.ts` must still pass (`data/` imports nothing client-side; `validate.ts` and `normalise.ts` import only `model.ts`).

## Verify before you report

From `tools/oculus` in the worktree, each must hold and its output is quoted:

1. `npm test` passes, with `tests/integrity.test.ts`, `tests/data/validate.test.ts` and `tests/data/normalise.test.ts` listed and every earlier test still passing. If the integrity test finds anything on the real hub, that is reported verbatim and never repaired by you; the test is allowed to fail in your report if the finding is real.
2. `npm run check` reports 0 errors and 0 warnings.
3. `npm run build` completes.
4. `npm run format:check` passes.
5. `node tests/data/real-hub.probe.ts` prints the entity counts (91/70/49/9/12/11), the relation counts, and every finding.
6. `LC_ALL=C grep -rn '[^ -~]' src tests` prints nothing.
7. `find src tests -type f | xargs wc -l | sort -rn | head -3`: every file under 1000 lines.
