# Brief: O17, the terminal server

Read `../spec.md` first; it governs this package unchanged. Then `tools/oculus/DESIGN.md`, "PTY" under Layer 2 ("Sessions run inside tmux, so they outlive the server. oculus attaches a pty to the tmux session and bridges it over the `pty:<id>` channel"), "The socket", "Auth", step 6 of the migration order, and the decisions on tmux (2026-09-09) and on the three things a terminal runs (2026-09-10: `claude`, `codex`, a plain shell). This package is the server half: starting, listing, attaching, feeding and stopping tmux sessions, and the `pty:<id>` channel. O18 draws it with xterm.js; O19 resumes an existing agent session into tmux.

## How the bytes move

No native PTY module: tmux is the terminal, and its control mode is the bridge. Measured on this machine on 2026-09-10 (tmux 3.7c): a `tmux -C attach-session -t <session>` child with piped stdin and stdout prints `%begin`/`%end` around each command's reply, `%session-changed`, and one `%output %<pane-id> <bytes>` line per chunk of pane output, the bytes escaped as octal (`\015\012` for CR LF, `\\` for a backslash), and it accepts tmux commands on stdin (`send-keys -t <session> -l <text>` typed a line into a pane running `cat`, which came back as `%output`). One control client per tmux server sees every session's output, so the server holds one, not one per terminal.

## What to build

Under `tools/oculus/src/lib/server/pty/`:

- `tmux.ts`: the one process boundary, list arguments only, never a shell. `run(args, timeout = 5000)` calls `tmux` through `execFile`; `control()` spawns `tmux -C attach-session -t <session>` (against the user's default tmux server, so a session oculus started is attachable from any terminal with `tmux attach -t <name>`) and returns an object that parses the stream: `%output` lines decoded from the octal escapes into a `Buffer` per pane id and emitted to a listener; `%begin`/`%end` pairs matched to the command that was sent, resolving its promise with the reply text or rejecting on `%error`; `%session-changed`, `%window-add`, `%exit` and the rest forwarded as events. Commands are written to its stdin one per line with arguments quoted for tmux (double quotes with `\"` and `\\` escaped, the same convention the spike used). The control client is opened lazily on the first attach and closed when nothing is attached for a minute; it is restarted with a one-second backoff when it exits while something is attached.
- `sessions.ts`: the terminals as records: `listTerminals()` from `tmux list-sessions -F '#{session_name}\t#{session_created}\t#{session_attached}\t#{pane_current_command}\t#{pane_pid}\t#{pane_current_path}'` filtered to the `oculus-` prefix, giving `Terminal = { id, name, kind: 'claude' | 'codex' | 'shell', cwd, command, pid, created, attached }` (the kind from a name suffix or from the pane's command); `startTerminal({ kind, cwd, cols, rows, name? })` runs `tmux new-session -d -s oculus-<id> -c <cwd> -x <cols> -y <rows> <command>` where the command is `claude`, `codex`, or the user's shell (`$SHELL`, else `/bin/zsh`) and the id is a short random hex; `resizeTerminal(id, cols, rows)` runs `resize-window -t <session> -x <cols> -y <rows>`; `stopTerminal(id)` runs `kill-session -t <session>`; `scrollback(id, lines = 2000)` runs `capture-pane -p -e -S -<lines> -t <session>` so an attaching page gets what the pane already shows. A cwd must be an absolute existing directory; the command never carries text from the page except through `send-keys -l`.
- `channel.ts`: the `pty:<id>` channels on O6's hub. On `subscribe` to `pty:<id>` the server publishes the scrollback as the first message, then every `%output` chunk for that session's pane as a message `{ channel, version, payload: { bytes: <base64> } }`; the channel's version counts chunks. The socket of O6 learns one more inbound message from the page, `{ type: 'input', channel: 'pty:<id>', bytes: <base64> }`, which the server turns into `send-keys -t <session> -l <text>` (and `send-keys -t <session> Enter` and the other named keys for the control characters xterm sends: CR, the arrows, Home, End, PageUp, PageDown, Tab, Escape, Backspace, and Ctrl-letters, each mapped to tmux's key name); and `{ type: 'resize', channel: 'pty:<id>', cols, rows }`. Every inbound message on a `pty:` channel is accepted only on a socket whose page carried the write token in its subscribe message (O11's token, sent as `{ type: 'subscribe', channels, token }`; a socket without it may read every channel as before and write to none), which is DESIGN.md's "The socket accepts nothing from the page except subscriptions and, later, terminal input" made concrete. The unsubscribe on socket close stops the delivery; the tmux session lives on.
- `src/routes/api/terminal/+server.ts` and `server/pty/routes.ts`: `POST /api/terminal` with `{ action: 'start', kind, cwd, cols, rows }`, `{ action: 'stop', id }`, `{ action: 'resize', id, cols, rows }`, token-guarded and same-origin as `/api/write`; `GET /api/terminal` lists the terminals. The `sessions` channel of O13 gains the list of terminals in its payload (`terminals: Terminal[]`) so the page sees a terminal appear the moment it exists; `watch/sessions.ts` republishes on `tmux` changes, which it learns from the control client's `%session-*` events and, without a control client open, from a `list-sessions` every 5 s.

Under `tools/oculus/src/lib/data/model.ts`: `Terminal`, `TerminalKind`, the `pty` payload and the two inbound message shapes.

Under `tools/oculus/tests/`:

- `server/pty/tmux.test.ts`: the control-stream parser on recorded text (the `%begin`/`%end` pairing, an `%error`, the octal decoding including `\\` and a multi-byte UTF-8 sequence split across two chunks, `%output` for two panes interleaved), the argument quoting, the key map (every control character xterm.js emits to its tmux name). No tmux is run here.
- `server/pty/sessions.test.ts`: against a real tmux on a private socket (`-S` under `mkdtemp`, so the user's own tmux server is never touched; `tmux.ts` takes the socket as an option for exactly this): start a shell terminal running `cat`, list it, send a line and read it back through a control client, resize, capture the scrollback, stop it, list it gone; every session and the socket's server killed at the end even when an assertion fails. Skipped with a printed reason when `tmux` is not on the PATH.
- `server/pty/channel.test.ts`: the hub with a recording sink: the scrollback as the first message on subscribe, chunks as versions, input from a sink with the token reaching `send-keys`, input from a sink without it refused, resize forwarded, unsubscribe stopping delivery.

## Facts checked on the tree, 2026-09-10

- `tmux 3.7c` at `/opt/homebrew/bin/tmux`. The spike above ran on a private socket (`-S /tmp/...`): `new-session -d -s spike -x 80 -y 24 cat`, a `-C attach-session` client with piped stdio, `send-keys -t spike "typed via control" Enter` written to its stdin, and the reply `%output %0 typed via control\015\012typed via control\015\012`; `capture-pane -p -t spike` returned the two lines; `pipe-pane -O` also works but is not needed.
- `claude` is at `/Users/axelfaes/.local/bin/claude`, `codex` at `/opt/homebrew/bin/codex`; the user's shell is `zsh`. A session started by oculus and one started in a terminal are told apart by the `oculus-` prefix only.
- The page's write token exists since O11 (`hooks.server.ts` mints it, `+page.server.ts` ships it, `state/writes.svelte.ts` holds it); the subscribe message today is `{ type: 'subscribe', channels }` with no token, and O6's socket refuses nothing a page sends beyond ignoring it.
- The socket server (`attachSocket`, called from `src/server.ts` and from `vite.config.ts`'s plugin) cannot import the token: `hooks.server.ts` lives in the app's own module graph (the built `build/` bundle, or Vite's SSR graph in dev), which is separate from the plain imports of `src/server.ts` even though both run in one process. O16 met the same wall for the Hub and crossed it with `globalThis.__oculusHookBridge` (`sessions/hooks.ts`). This package does the same for the token: `hooks.server.ts` puts the token it minted on the process-wide bridge through one function in `server/auth.ts` (`publishToken(token)` / `processToken()`), and `socket.ts` checks a subscribe message's `token` against `processToken()`; a process where nothing published one accepts no terminal input. This is a decision the brief takes; the report says so.
- The catalog is two files: `config/text.yml` and `config/text-oculus.yml`; this package is server-side and should need no text key, and a new one would go in `text-oculus.yml`.
