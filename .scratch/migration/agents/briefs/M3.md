Read `tools/oculus/.scratch/migration/agents/spec.md` first; its rules govern this step unchanged. The plan names no further standards. "M3 the resources registry" (`plan.md:402`, ruling The queue, ruling M3). ## What to build

1. **The registry file.** `registries/resources.yml`, in the shape of `organisations.yml`: a head comment saying what it holds and who names its keys (a manifest's `compute:` and `slurm.resource` of `behavior.yml`), a `schema:` list `{ field: key, type: text, required: true, label: "Resource key" }`, `{ field: name, type: text, required: true }`, `{ field: kind, type: select, options: [cluster, machine, storage], required: true }`, `{ field: host, type: text, help: "the ssh alias, for a cluster or a remote machine" }`, `{ field: access, type: textarea, help: "how it is reached: the network, the VPN, the login rules" }`, `{ field: links, type: tags }`, and the entries of Decision 1. `tools/oculus/demo/registries/resources.yml` holds the same schema and two invented entries, a cluster keyed `utwente` named "Demo cluster" with host `utwente` (so the shared `slurm.resource: utwente` resolves on the demo hub as `slurm.host: utwente` did) and a machine `laptop` named "Laptop". Both registry files are written as the text Decision 1 and this item give, through one `cat > <path> <<'EOF'` command each ("Conventions").

3. **The model.** `model-entities.ts` gains `'resources'` in `RegistryName`, `resources: string` in `RegistryFiles`, and a `Resource` type `{ id: Id; name: string; kind: 'cluster' | 'machine' | 'storage'; host?: string; access?: string; links: string[] }` with a comment in the style of `Organisation`'s; the project's `compute?: string` becomes `resourceIds: Id[]`, the keys of `compute:` that the registry holds, in the manifest's order. `model/index.ts`'s entities gain `resources: Record<Id, Resource>`. `normalise.ts` maps the entries with a `resource` function and keeps an entry only when its `kind` is one of the three words, its key is not reserved (`__none__`, the board's NONE; `__proto__`; `constructor`) and no earlier entry has its key (the first of two entries with one key is kept); `name`, `host` and `access` are read with `str` (a non-string `host` reads as none), `links` with `strings`. It adds `resources` to `known` and to the entities, and reads `resourceIds` as the string entries of `compute:` that `known.resources` holds, in the manifest's order, each key once: a plain filter, with no join table and no `Relations` entry, so nothing sorts them. ## Cases

1. `registries/resources.yml` with the three entries of Decision 1: the snapshot's `entities.resources` holds `utwente`, `this-mac`, `data` with their kinds; no finding.
2. An entry `{ key: x, name: X, kind: gpu }`: finding `kind_not_resource` at `entries[i].kind`; `x` is not in the entities; a manifest `compute: [x]` gets `no_resource` and `resourceIds` `[]`.
3. An entry without `key`: the registry's missing-id finding, as for organisations; the entry is left out. An entry without `kind`: `kind_not_resource`, left out.
4. No `registries/resources.yml`: the registry is empty with the missing-file finding the other registries give; every manifest's `compute:` key gives `no_resource`; the server starts. A file that does not parse: the parse finding, the same result.
5. A manifest `compute: [utwente]`: `resourceIds` is `['utwente']`; the card shows one tag "UTwente HPC" with the HPC glyph; the facet offers "UTwente HPC".
6. A manifest `compute: [utwente, data]`: `resourceIds` is `['utwente', 'data']`; two tags in that order, the glyph on the first only; the project counts under both facet values. `compute: [data, utwente]`: the tags in that order, the glyph on the second.
7. A manifest `compute: [nowhere]`: finding `no_resource` naming `nowhere`; `resourceIds` is `[]`; the facet counts it under `NONE`.
