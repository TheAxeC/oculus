## Decisions taken in this brief (each reversible, none silent)

1. The reader lives in `server/core/fetch-period.ts`, which both `server/root/watch` and `server/edit` may import; the timer in `server/root/watch/` and its test in `tests/server/git/`, since `server/git` and `tests/server/root/watch` are at ten items.
2. `TICK` is a fixed 60000 ms with no key: the period is read from the `config` channel at every look, so a change in the Settings view takes effect within a minute with no restart. One `setTimeout` on the injected `Clock`, armed at the start of each look.
3. The first look is one tick after the start, so the `git` channel has had its first read; then a round runs at once when the key is above 0.
4. Repositories are fetched one at a time and once each per round, grouped by the first worktree path the `git` payload gives; a round never overlaps another.
5. A repository has a remote when `git remote` lists one; `GitState.remotes` is not used. `gitRoots` is not reused, since it answers keys without states.
6. A failed fetch is said on stderr only, as VS Code's auto fetch is silent; the next period tries again. Two servers on one machine (the dev server and the built one) both fetch; a ref-lock failure of one is logged and is no defect.
7. A wrong value stops the server at start, as `changes.keep` does, and the Settings write refuses it; a wrong value that reaches a running server by a hand edit stops the fetching and is said once on stderr.
8. Fetch runs `fetchIn` on the roots the `git` payload names, which is the rule `git-write.ts:50-53` gives; `fetchAll`'s default roots would refuse every repository.
9. The timer's fetch is unattended: `GIT_TERMINAL_PROMPT=0` and, unless set, `GIT_SSH_COMMAND=ssh -o BatchMode=yes`; a repository whose remote needs a password then fails and is logged rather than waiting a minute on a prompt. The pressed Fetch keeps today's environment.
