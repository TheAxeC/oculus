## For the orchestrator: user-visible choices

Each item is a shape the plan line does not name. None is taken here. Each gives the options, their pros and cons, one recommendation and the lazy option.

1. **Where the API keys live, and their names.** The plan line says "the per-machine secret file", which is `config/local.yml`; `LOCAL_KEYS` (`src/lib/data/sources/config/local.ts:108-127`) holds no literature key today, and an unknown key is refused (`local.ts:267`).
   - (a) One map `literature:` in `local.yml` with seven optional text keys: `wos_key`, `scopus_key`, `scopus_insttoken`, `openalex_key`, `semantic_scholar_key`, `ncbi_key` and `mailto` (the contact address OpenAlex, Crossref and NCBI ask callers to send). Pros: the file the plan line names; one key per service that has one; the probes below show that OpenAlex without a key allows about 100 searches a day and that Semantic Scholar's search answered 429 to four keyless requests of four, so the two optional keys are what makes those sources usable; the Settings view lists `local.yml` keys without their values (`HELP.md:261`). Cons: a secret in a plain text file beside tracked files (gitignored), shown in full when the reader opens `local.yml` in a source tab.
   - (b) Two flat keys, `wos_api_key` and `scopus_api_key`. Pros: the plan line's minimum. Cons: Semantic Scholar stays at 429 and OpenAlex at its keyless daily allowance, so two of the six keyless sources fail in ordinary use.
   - (c) A file `~/.oculus/literature.json`, mode 0600, written from the Account setup view, as the OAuth client halves are (`DESIGN.md:412`). Pros: the secret handling oculus already uses for provider credentials. Cons: departs from the plan line's "per-machine secret file"; adds a setup form.
   - Recommendation: (a). The lazy option is (b).
2. **The wire format.**
   - (a) One request per source, `GET /api/literature?source=<id>&q=...`, the page sending one per toggled source at once and merging the answers as each arrives. Pros: fast sources draw at once while a slow one (arXiv answered its 429s after 10.6 s) is still out; each source's state is its own answer; the merge is a pure client function. Cons: up to eight requests per search.
   - (b) One request for every source, merged on the server. Pros: one request. Cons: every hit waits for the slowest source.
   - Recommendation: (a). The lazy option is (b), which leaves the wait on the slowest source in place.
3. **The source state vocabulary**, the words of each source's answer and the line the view draws for it: `ok` (count, and the total the source reports), `limited` (429, with the wait when the source names one), `timeout` (no answer within `timeout_s`), `refused` (401 or 403: a key refused or not entitled), `failed` (any other status, or an answer that does not read), `no-key` (a keyed source with no key), `skipped` (a filter the source cannot hold, such as arXiv under a type other than preprint). Options: (a) these seven; (b) `ok` and `failed` alone. Recommendation: (a), since the reader acts differently on each (wait, set a key, widen a filter). The lazy option is (b).
4. **The document type vocabulary.** Options: (a) one shared list, `any`, `article`, `review`, `preprint`, `conference`, `book`, `chapter`, mapped to each source's own types by the table under "What to build" item 4; (b) no shared list, each source's own types shown untranslated. Recommendation: (a). The lazy option is (b).
5. **What sort means.** Options: (a) every source asked in its own relevance order, the merged list sorted on the page by relevance (fused rank), date or citations; (b) each source asked in the chosen order. Evidence for (a): Crossref's `sort=published&order=desc` for "tensor decomposition EEG" answered three unrelated works dated 2103, 2103 and 2028 (probe 8 below), Europe PMC's `sort=P_PDATE_D desc` answered dates out of order (2026-08-24, 2026-09-18, 2026-05-22), and Semantic Scholar's search has no sort. Pros of (a): every list is relevant to the query; changing the sort asks nothing. Cons of (a): "newest" means newest among the relevant hits asked for, which item 6 widens. Recommendation: (a); it is also the cheaper one, and it is recommended on the probe evidence, not on its cost.
6. **Paging.** Options: (a) a `More` control after the list that asks every source still holding more for its next page and merges it in; (b) the first page alone, `per_source` hits from each. Recommendation: (a). The lazy option is (b).
7. **The merge identity.** Options: (a) two hits are one when they share a DOI, else a PubMed id, else an arXiv id, all compared exactly after normalising; a preprint and its published version are one hit when any source names both identifiers (Semantic Scholar's `externalIds` with `DOI` and `ArXiv`, OpenAlex's `locations` holding an arXiv landing page beside the DOI, arXiv's `arxiv:doi` element), the published fields preferred and the preprint's PDF kept; (b) DOI alone, so a preprint and its published version are two hits, and a hit without a DOI is never merged; (c) (a) plus a match on normalised title and year. Pros of (a): one row per paper for the identifiers the sources give; no guess. Cons of (a): a source that names a wrong pairing merges two works. (c) merges papers that share a title (errata, a conference and journal version with different content). Recommendation: (a). The lazy option is (b).
8. **The Add to Lit Watch record.** The radar's 561 entries carry `title`, `authors`, `venue`, `year`, `url`, `bucket` and `found` each, and 376 carry `project`, `relevance` and `why` (`grep -oE '^ +[a-z_]+:' feeds/literature-radar.yml | sort | uniq -c` for the other keys, `grep -c '^  - title:'` for `title`). Options: (a) Add opens a small form on the card: bucket (the `radar_buckets` of `config/catalogs/vocab.yml:289-293`, `adjacent` preselected), project (optional, the portfolio's projects), relevance (`high`, `med`, `low`, `med` preselected), why (optional text); Enter writes `title`, `authors`, `venue`, `year`, `url`, `bucket`, `project`, `relevance`, `why`, `found` in that order, the empty ones left out; (b) one press writes `title`, `authors`, `venue`, `year`, `url`, `bucket: adjacent`, `found`. Pros of (a): a record Lit Watch can sort and explain like the scout's; one Enter when the defaults fit. Cons: one more step than a press. Recommendation: (a). The lazy option is (b).
9. **The text written into the hub file.** The radar file holds no character outside printable ASCII today (`LC_ALL=C grep -c '[^ -~]' feeds/literature-radar.yml` prints `0`); the hub's writing rules keep accented letters in names and ban curly quotes, en and em dashes, the ellipsis character and the non-breaking space. Options: (a) the text as the source gives it; (b) markup stripped and entities decoded, then curly quotes to straight, an en or em dash to `-`, the ellipsis character to `...`, a non-breaking space to a space, and every other character kept (accented letters, Greek letters); (c) everything folded to ASCII. Recommendation: (b), which keeps names right and keeps the characters the hub bans out. The lazy option is (a).
10. **The behaviour settings.** Options: (a) a `literature:` block in `config/behavior.yml` after `search:`, `timeout_s: 20` (seconds one source is given), `per_source: 25` (hits asked of each source per page, 1 to 100), `cache_min: 30` (minutes an answer is kept for the same request), each with its `options.yml` entry and read by a `literatureSettings` reader beside `searchSettings`; (b) constants in code. Recommendation: (a), as the Search view's `search:` block does (`config/behavior.yml:175-179`). The lazy option is (b).
11. **The view's place.** Options: (a) id `literature`, words "Literature search", the `incoming` group at order 5 after the Calendar, so the chords of Inbox, Lit Watch, Position Leads, LinkedIn and Calendar stay as they are, a tab after `linkedin` in the first pane of the Incoming arrangement (`config/layout.yml:72`), glyph `book` (`config/catalogs/glyphs.yml:124`, `icons.yml:123`, no new glyph); (b) the same group at order 2 after Lit Watch, which moves the digit of Position Leads, LinkedIn and the Calendar by one; (c) the `references` group after Statements, away from Lit Watch, which Add writes to. Recommendation: (a). No option is cheaper than another here.
12. **Where the toggles and the search are kept.** Options: (a) the tab's instance state, saved with the layout: the query, the filters, the sort and the toggles, every keyless source on and a keyed source on when its key is set; a keyed source with no key drawn as a disabled toggle whose tooltip names its `local.yml` key; (b) a list of sources in `behavior.yml`, the keyed toggles hidden without a key. Recommendation: (a). The lazy option is (b).
13. **A query that is a DOI.** Options: (a) a query matching `^(https?://(dx\.)?doi\.org/|doi:)?10\.\d{4,9}/\S+$` is looked up by DOI in each source (the requests are under item 2 of "What to build"); (b) it is sent as text, which OpenAlex's title and abstract search cannot match. Recommendation: (a). The lazy option is (b).
14. **A guarded entry for the merge** (Z392: a new entry needs Axel's yes, so this is his to rule and goes to him as an open item). Options: (a) a new entry, "Hits that share an identifier are one hit, and hits that share none are never one", tested by one table over the merge function (rows: one DOI in two cases, a DOI with and without `https://doi.org/`, two DOIs, a PubMed id only, a preprint named with its DOI by one source, no identifier); (b) no test, the cases checked by quoted runs and the look. Pros of (a): a wrong merge hides a paper, which neither the reader nor the look can see once it happened. Cons: one more entry. Recommendation: (a). The lazy option is (b). Until he rules, the builder writes no merge test (spec.md:57).

## What to build

1. **The route.** `GET /api/literature` in `src/routes/api/(docs)/literature/+server.ts`, a thin join to a handler in `src/lib/server/content/literature/`, as `routes/api/(files)/search/+server.ts` joins `handleSearch`. It refuses a request without the token with 403 `{ error: 'token' }` before anything else, as `handleSearch` does, and answers with `cache-control: no-store`. Three forms, under item 2 of the choices (the per-source form is assumed until ruled):
   - `?sources` answers `{ ok: true, sources: [{ id, keyed, available, key }] }` for the eight sources in the order `openalex`, `semantic_scholar`, `crossref`, `pubmed`, `europe_pmc`, `arxiv`, `wos`, `scopus`; `keyed` is true for `wos` and `scopus`; `available` says whether the source can be asked (a keyed source only when its key is set); `key` is the name of the `local.yml` key a keyed source needs, never a value.
   - `?source=<id>&q=<text>&from=<year>&to=<year>&type=<word>&oa=1&venue=<text>&author=<text>&min_cites=<n>&page=<cursor>` answers `{ ok: true, source, state, total, more, cursor, cached, hits }` for `state: 'ok'`, and `{ ok: true, source, state, status?, wait_s? }` for every other state of choice 3. `total` is the count the source reports, null when it reports none; `more` and `cursor` page the source (choice 6); `cached` is true when the answer came from the cache of item 3.
   - `?bibtex&doi=<doi>`, `?bibtex&s2=<paper id>` or `?bibtex&arxiv=<id>` answers `{ ok: true, bibtex, from }` (`from` one of `doi`, `semantic_scholar`, `arxiv`) or `{ ok: true, bibtex: null }` when the source has none.
   - Refusals, each with 400 and one word: `query_empty` (nothing after trimming), `query_long` (over 1000 characters, decision 2), `source` (an id outside the eight), `year` (a year that is not a whole number from 1000 to the current year plus one, or `from` after `to`), `cites` (not a whole number from 0), `type` (outside choice 4's list), `doi` (a `bibtex` DOI that does not match `^10\.\d{4,9}/\S+$`), `id` (an `s2` that is not 40 hex digits, an `arxiv` that is not an arXiv identifier). No value of the request reaches a URL except through `URLSearchParams` or `encodeURIComponent`.
   - A key is never in an answer, a refusal line, a log line or a thrown message. `wos` and `scopus` carry their key in a header (`X-ApiKey`, `X-ELS-APIKey`, and `X-ELS-Insttoken` when set); `semantic_scholar` in `x-api-key`; OpenAlex and NCBI take theirs as the `api_key` query parameter (from their documentation), so no request address is ever logged or put in a line. A failure line names the source, the status and the source's own code when it gives one, as `refusalLine` (`connect/api.ts:41-44`) does, and never the body.
2. **One adapter per source**, in `server/content/literature/sources/`, each a function from the parsed request to the source's answer read into the per-source hit shape, its answer read through a zod schema beside it (`DESIGN.md:151`). Every source is asked in its relevance order (choice 5), `per_source` hits a page. The request each sends (`<q>` the query, `<n>` `per_source`):
   - `openalex`: `https://api.openalex.org/works?filter=title_and_abstract.search:<q with commas replaced by spaces>[,publication_year:<from>-<to>][,type:<t>][,is_oa:true][,cited_by_count:><min-1>][,raw_author_name.search:<author>]&per-page=<n>&page=<p>&select=id,doi,display_name,publication_year,publication_date,type,cited_by_count,open_access,best_oa_location,primary_location,authorships,ids,abstract_inverted_index[&mailto=<mailto>][&api_key=<key>]`. The abstract is rebuilt from `abstract_inverted_index` (each word put at each of its positions). A DOI query uses `filter=doi:<doi>`. The `raw_author_name.search` filter is from the documentation; when OpenAlex refuses it the builder drops it and the after-fetch filter of item 4 holds.
   - `semantic_scholar`: `https://api.semanticscholar.org/graph/v1/paper/search?query=<q>&offset=<o>&limit=<n>&fields=title,abstract,year,venue,authors,externalIds,citationCount,isOpenAccess,openAccessPdf,publicationTypes,publicationDate,journal,url,citationStyles[&year=<from>-<to>][&publicationTypes=<t>][&openAccessPdf][&minCitationCount=<min>]`, header `x-api-key` when set. A DOI query is `GET /graph/v1/paper/DOI:<doi>?fields=...`.
   - `crossref`: `https://api.crossref.org/works?query.bibliographic=<q>&rows=<n>&offset=<o>&select=DOI,title,author,published,type,is-referenced-by-count,container-title,abstract,link,license&filter=<from-pub-date:<from>,until-pub-date:<to>,type:<t>>[&query.author=<author>][&query.container-title=<venue>][&mailto=<mailto>]`. A DOI query is `GET https://api.crossref.org/works/<doi>`. Crossref names no open access, so its hits are open only through a merged source or a PDF link (item 4). Its `link[]` entries are text-mining links and are never the open PDF.
   - `pubmed`: `esearch.fcgi?db=pubmed&term=<q>[ AND <from>:<to>[dp]][ AND <pt>[pt]][ AND free full text[sb]][ AND "<venue>"[ta]][ AND "<author>"[au]]&retmode=json&retmax=<n>&retstart=<o>&sort=relevance&tool=oculus[&email=<mailto>][&api_key=<key>]`, then `efetch.fcgi?db=pubmed&id=<ids>&retmode=xml` for the titles, authors, journal, dates, DOI, publication types and abstracts. PubMed gives no citation count. A DOI query is `term=<doi>[doi]`.
   - `europe_pmc`: `https://www.ebi.ac.uk/europepmc/webservices/rest/search?query=TITLE_ABS:(<q>)[ AND PUB_YEAR:[<from> TO <to>]][ AND <type clause>][ AND OPEN_ACCESS:y][ AND JOURNAL:"<venue>"][ AND AUTH:"<author>"]&format=json&resultType=core&pageSize=<n>&cursorMark=<cursor or *>`. The open PDF is the `fullTextUrl` with `documentStyle: pdf` and `availabilityCode: OA`. A DOI query is `query=DOI:"<doi>"`.
   - `arxiv`: `https://export.arxiv.org/api/query?search_query=<terms>[ AND submittedDate:[<from>01010000 TO <to>12312359]]&start=<o>&max_results=<n>&sortBy=relevance&sortOrder=descending`, `<terms>` each word or quoted phrase of the query as `all:<term>` joined by ` AND `, an author filter adding ` AND au:<author>`. Its hits are preprints, open, with the PDF link of the entry; the abstract page and PDF addresses are built as `https://arxiv.org/abs/<id>` and `https://arxiv.org/pdf/<id>` from the entry's identifier, since the entry's `<id>` is `http`. Under a type filter other than `any` and `preprint`, under a venue filter or under a citation minimum above 0 it is not asked and answers `skipped`. A DOI query of an arXiv DOI (`10.48550/arXiv.<id>`) is `id_list=<id>`; any other DOI query skips it. The source's pacing is one request per 3 s (item 3).
   - `wos`: `https://api.clarivate.com/apis/wos-starter/v1/documents?q=TS=(<q>)[ AND PY=<from>-<to>][ AND DT=(<dt>)][ AND SO=(<venue>)][ AND AU=(<author>)]&db=WOS&limit=<n up to 50>&page=<p>&sortField=RS+D`, header `X-ApiKey`. No abstract, no open access flag. A DOI query is `q=DO=(<doi>)`.
   - `scopus`: `https://api.elsevier.com/content/search/scopus?query=TITLE-ABS-KEY(<q>)[ AND PUBYEAR > <from-1> AND PUBYEAR < <to+1>][ AND DOCTYPE(<dt>)][ AND OPENACCESS(1)][ AND SRCTITLE(<venue>)][ AND AUTH(<author>)]&count=<n>&start=<o>&sort=relevancy`, headers `X-ELS-APIKey`, `X-ELS-Insttoken` when set, `Accept: application/json`. A hit's fields: `search-results.entry[]` with `dc:title`, `dc:creator` (first author only), `prism:publicationName`, `prism:coverDate`, `prism:doi`, `citedby-count` (text), `subtype`, `openaccessFlag`, `pubmed-id`, `eid`, `link[]`; an empty answer is one entry with `error: "Result set was empty"`, read as no hits. A DOI query is `query=DOI(<doi>)`.
   - The per-source hit: `{ source, id, doi?, pmid?, arxiv?, title, authors: string[], venue?, year?, date?, type, abstract?, cites?, oa?, pdf?, url?, rank, bibtex? }`, typed in `data/model/model-search.ts` and exported through `data/model/index.ts`. `doi` is normalised: lowercased, `https://doi.org/`, `http://dx.doi.org/` and `doi:` taken off, percent escapes decoded, trimmed, a trailing period dropped. `rank` is the hit's place in its source's answer, from 1 over the pages. `date` is `YYYY-MM-DD`, `YYYY-MM` or `YYYY`; a date more than a year after today (Crossref's 2103) is read as absent, and so is a year outside 1000 to the current year plus one. Every text field has its markup removed and its entities decoded (`entities` is a dependency already) and is drawn as text, never as HTML. `pdf` and `url` pass `httpsLink`. A record with no title and no identifier is dropped.
3. **Pacing, timeouts and the cache**, one object on the server context (`ServerContext`, `server/root/context.ts:105`, made once beside `mailConnects` at `:461`), handed to the handler through `locals`, never module state (spec.md's no-globals rule).
