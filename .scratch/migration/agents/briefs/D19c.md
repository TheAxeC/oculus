## How it lives in oculus (the three layers, the data live)

**Data.** Nothing new on disk: the figures land in each account's file (`cachedUsageUtilization`, D19b's reader) and the account-file watch D19b added publishes them within a second.

**Code.** `server/usage/refresh.ts`: for every Claude account of `local.accounts`, one hidden tmux session named `oculus-usage-<account>` (`<account>` the basename of the config folder, as the status-line files use), started detached in the hub root with the environment `CLAUDE_CONFIG_DIR=<dir>` and the command `<claudeBin> --model haiku` (the bin from `local.claudeBin`, the model from a new `behavior.yml` key `usage_refresh_model: haiku`), through the same tmux calls `server/pty/sessions.ts` and `tmux.ts` make (reuse `startArgs`'s shape or the runner; do not duplicate the tmux plumbing). Every `usage_refresh_min` minutes (a new `behavior.yml` key, 10) and on the Refresh control, it sends `/usage`, Enter, waits for the sheet (poll `capture-pane` for the words "Current week" up to 15 s), then Escape. Recovery, Axel's requirement: before each refresh the session is checked with `tmux has-session`; a missing or dead one is started again; a session whose pane shows a login prompt, a usage-limit message, an offline message or anything other than the prompt after `/usage` is killed and restarted on the next tick, with the reason published (see below); a restart that fails is retried on every tick, never more often. Nothing is typed into these sessions except `/usage`, Enter and Escape; nothing they print is kept beyond the check. `src/server.ts` and the dev plugin start the refresher beside `watchUsage` and stop it on close; the sessions themselves are left running at oculus's exit, as every oculus tmux session is, and found again at the next start by name.

**Hidden.** `server/pty/sessions.ts`'s `parseTerminal` (line 207) leaves a session named `oculus-usage-*` out of the terminal list, so it never appears in the sessions views, the terminal rail or the Terminal view's picker; a test proves it. Added 2026-09-13 21:40 (Axel saw the orchestrator's test session in the card's live list): the session is started with `--name oculus-usage-<account>`, which the status line reports as `session_name`, and D19b's `liveClaude` drops a status file whose `session_name` starts with `oculus-usage-`, so the refresher is never a live row on the card either; a test proves it. D18's Processes view, when built, lists it as oculus's own.

**View.** `views/Usage.svelte`: a Refresh control (`ui/ToolButton`, `usage.refresh` "Refresh now", glyph `refresh`) on each Claude card that asks the server to refresh that account now (`POST /api/usage/refresh` with the account label, behind the write token as the HPC refresh is: read `server/hpc/routes.ts` for the pattern); under the card's windows one line `usage.refresher` ("refresher: {0}") with the refresher's state from the payload: `running`, `restarting`, or the reason it is down (`usage.refresher_down` "down since {0}: {1}"). The `usage` payload gains per Claude account `refresher: { state: 'running' | 'restarting' | 'down', since: string, reason: string, lastRefresh: string }`.

## Decisions taken in this brief (each reversible, none silent)

1. Session name `oculus-usage-<account>`; the hub root as its folder; Haiku as its model, a config key.
2. The refresh waits for the sheet's words rather than a fixed delay, capped at 15 s.
3. A session that shows anything but the prompt after `/usage` is restarted, and the reason is on the card.
