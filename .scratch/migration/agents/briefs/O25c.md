Read `../spec.md` first; it governs this package unchanged. The cockpit's Position Leads tab is `tools/cockpit/src/cockpit/render/surfaces.py` `leads_cards_html`, lines 232 to 287, over `feeds/position-leads.yml` (43 entries; `meta.log` holds the scout's run lines, newest first; `title` is the identity, `status` is open, applied, declined or closed), with the lead actions of `render/actions.py` lines 37 to 45 and the add form's schema shipped by `page.py` lines 745 to 754; the server writes are `set_lead`, `delete_lead` and `add_lead` of `setstatus/feeds.py` lines 237 to 259. ## Decisions taken in this brief (each reversible, none silent)

1. **One new write.** `kind: 'lead-add'` `{ fields }` appends an entry to the leads file with `date` defaulting to today and `status` to `open` when absent, refused without a title, through `appendEntry` of `server/entry-edit.ts` with the fields in the schema's order; `state/writes.svelte.ts` gains `addLead(fields)`.
2. **The lead schema lives in config.** The eight fields the cockpit shipped from `page.py` (title required, inst, country, typ, focus, fit, deadline as a date, url) become `lead_schema:` in `config/sources.yml` beside `leads_file`, read by `loadConfig` and handed to the shared form; the feed file itself carries no schema and is not given one.
3. **The pure parts.** `state/leads.ts`: `isClosed(status)`, `deadlineOf(text)`, `isExpired(lead, today)`, `fitKey(fit)`, `fitTone`, `splitLeads(entries, today)` (live sorted, expired sorted), `leadsSearch`; a `LeadsState` from the instance state (search words, the two collapsibles).
