## What to move, and what stays

The rule is the plan's ruling "O181 keys": a config key exists only for a fact of the user's setup or data, or a choice a person makes. Axel's words on its scope: "Just so we're clear, it's really the project config that a user might reasonably want to change. Folder or file names, Any other important settings, that sort of stuff, not random constants".

So a hardcoded value moves to config when it is a fact of the user's setup or data or a choice a person makes. Examples: a folder or file name of the user's projects, hubs or tools; a word that names a hub's own content (a task, a registry, a feed); a host, an address or an account name of the user's; a setting a person would reasonably choose (which agent a start opens with).

The program's internal timeouts, waits, polling intervals, buffer and output sizes, retry counts, truncation lengths and cache sizes stay in code as they are, and get no config key. This step does not otherwise touch them: the one it changes is `hpc/poll.ts:330` (item 5). Config keys that exist today are left as they are, whatever they hold.

A fallback that repeats a value a config key already has (`?? 'strip'` beside `editor_actions`) is removed whatever its kind, since the config's default in `config/defaults/` is the one place that value lives.
