## What to build

### Part A, the Literature view (open item 76, Z868)

1. The collection. The engine's `config/sources.yml` lists `{ key: literature, file: "registries/literature.yml" }`. The hub's file `registries/literature.yml` (with `title: Literature`, an `intro:`, a `schema:` and `entries: []`) and its line in the hub's `collections:` are given under "Doc text" and applied by the orchestrator at landing (spec.md:37: the builder writes nothing under `registries/`). Its schema, in this order: `key` (text, required; the citation key, the identity field), `title` (text, required), `authors` (tags), `venue` (text), `year` (text, a whole number), `doi` (text), `url` (text), `abstract` (textarea), `keywords` (tags), `projects` (tags, `from: projects`), `source` (select, options `search`, `lit-watch`, `hand`), `added` (date), `note` (textarea); `venue`, `keywords`, `year`, `projects`, `source` and `authors` carry `filter: true`. Each field has its `help:` sentence, one line per field in the hub's style. The demo hub gets the same file (Part E).
2. The Literature search view's id becomes `literature-search`: its registration, its words (`views.literature_search: Literature search`, `views.literature_search_glyph: search`) and every reader of the id, quoted or not (`config/layout.yml:101`, `HELP.md:201`, `DESIGN.md:675`, and what `rg -n "\bliterature\b" src config tests` finds used as a view id). The collection's view is placed in the group `incoming` at order 6, so no chord of an earlier view moves; its words are `views.literature: Literature`, `views.literature_glyph: book`. The Incoming page's arrangement pins `literature-search` where `literature` was and the new `literature` view after it (Z883).
3. The citation key: surname, year and the first word of the title, each kept to lowercase ASCII letters and digits (accents stripped, every other character dropped), with `b`, then `c` and on, appended when the file holds the key already; no author gives `anon`, no year `nd`, no title word nothing. The surname of an author name: the part before a comma when the name holds one ("Faes, Axel"); the words before the initials when the name ends in one to three capital letters standing alone, as Europe PMC writes a name ("Faes A" gives `faes`, "Van Hulle MM" gives `vanhulle`); otherwise the last word, with the lowercase or capitalised particles before it joined to it (`van`, `von`, `de`, `der`, `den`, `da`, `di`, `du`, `del`, `dos`, `das`, `la`, `le`, `ter`, `ten`), so "Marc M. Van Hulle" gives `vanhulle` and "Khanh Dao Duc" `duc`. One function makes the key, on the server, where the file is read under its lock.
4. Save to Literature. The Literature search card and the Lit Watch card each gain Save to Literature, which writes the paper to the `literature` collection file of the primary hub (else the first) through one new write kind, with `source` `search` or `lit-watch`, `added` today, and every field the paper carries (from a search hit: title, authors, venue, year, doi, url, abstract as plain text; from a Lit Watch entry: title, authors as the names of its line, venue, year, url). The server refuses a paper the file holds already: the same DOI as `normalDoi` spells it, or, when either has no DOI, the same title by the one title rule: `sameTitle` becomes "equal after lower casing and dropping every character that is not a letter or a digit", the rule Lit Watch's own duplicate checks (`radar.ts:23`, `feeds.ts:510`) then use too. The card reads In Literature, not pressable, once the file holds the paper, by the same rules on the page. The write is logged and undoable (G9), changes only the file it names (G8), and is refused over a source tab's unsaved text of the file (G28, through `write-files.ts`). A hub whose `collections:` names no literature file and whose engine path holds none refuses Save with a sentence that says so.
5. Add on the Literature view asks one value, a DOI or an address. A DOI (as `queryDoi` reads it, a doi.org address included), an arXiv address (`arxivId`) or a PubMed address (`pubmedId`) is looked up through the sources the Literature search asks, the hits merged as the search merges them, and the merged paper is saved with `source: hand` and its page opened in its editor. A lookup whose sources all fail (a network error, a rate limit, a timeout) saves nothing and says which sources failed, so the reader can try again. A lookup that finds nothing, and any other address, saves an entry with `source: hand`, the `url` (for a DOI, `https://doi.org/<doi>`, and the `doi` field set), and a key from the address by item 3's character rule: the last path word with a file extension dropped (`https://example.org/papers/tensor-notes` gives `tensornotes`, `.../paper.pdf` gives `paper`, a DOI's last part `j.neucom.2024.127654` gives `jneucom2024127654`), the host's first label when the path has no word (`https://example.org/` gives `example`), suffixed as item 3 suffixes; its page opens. An empty answer opens an empty entry's page with the key asked, as every collection's Add does. A refusal (a duplicate) is said in the Add box.
6. Filters. A schema field may carry `filter: true`: `SchemaField` gains `filter?: boolean`, read by `fieldOf` as the other flags are, and the generic collection view draws, in the bar beside the search, one filter per such field of every collection: a `select` or `tags` field as chips of its values with their counts; a `text` field whose present values are all whole numbers as a range (from and to); any other `text` field as chips of its values. `filter: true` on any other type is a finding naming the field, the type and the file, and draws nothing. The filters are the tab's instance state, saved with it as the search and the facets are. The schema checker accepts the key, and the apps' `collections` payload carries it in the schema.
7. A venue linked to its record. A literature entry whose `venue` equals the `name` of a venue record, ignoring case, draws the venue as a link that opens that venue's page, on the card and on the page.
8. Copy BibTeX. A literature entry's card and page have Copy BibTeX, which puts one BibTeX entry on the clipboard: fetched by its DOI as the search's Copy BibTeX fetches it, else formatted by citation-js from the entry's fields; the entry key is always the literature entry's own key. The Literature view's toolbar has Copy BibTeX of the entries shown (those the search and the filters leave, in the view's order). Each copy says how many entries it copied, and which it could not.
