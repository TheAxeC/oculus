## What to build

1. **The rule is Q85a1's, as Q85a2, Q85a4 and Q85b apply it.** A schema goes where a map or a list that came from outside the code (a hub file, a config file, `local.yml` through `checkLocal` or `loadLocal`, the merged configuration, the raw portfolio's entries, the deck file, an agents cache) is read for its named fields or its items. The schema is a `const` beside the function that reads, in that function's file, named in lower camel case ending in `Shape`, built once at module level; a schema whose answer has a declared type is held to it with `satisfies z.ZodType<...>`. The function answers, for every input, what it answers on main, except the changed answers item 9 names: the same value, the same null, the same fallback, the same keys, absent keys absent, the same finding with the same text, file and key, the same thrown sentence, and findings in the same order. zod's own error text is never shown, logged or put into a finding or a thrown sentence, and no `.issues`, `.error` of a parse, `prettifyError` or `treeifyError` is read. A reader that hands on an object or a list it was given answers the input value itself (`unchanged`), so its identity, key order and keys the schema does not name all stay. A hand check moved into `z.custom(...)` or `.refine(...)` where a shared helper or a zod type expresses the test is a hand check still, and fails the step; each converted reader's answer is built from `safeParse(...).data` or `readAs(...)`. The five answer-keeping rules of Q85a4's brief hold here unchanged: a whole number is tested as the hand code tests it (`Number.isInteger`, `Number.isSafeInteger`, never `z.int()`); a `typeof === 'number'` test keeps `NaN` and the infinities accepted (`anyNumberShape`), and a `Number.isFinite` test refuses them as today; an optional field is `.optional()` where the hand code refuses `null`, and a field read with a fallback for any other value is `.catch(<fallback>)`; a raw `a ?? b` and a helper fallback keep their own forms; keys read from a map come from the input's own keys in their order, never from `z.record`'s `data`.
2. **A parsed file's top.** Each reader of the first kind tests the parsed value through `mapShape` (or a schema of its named fields) and keeps its own answer for a top that is not a map: the same finding with the same text, the same thrown sentence, the same fallback. The casts listed under What is on the tree go: the parsed value is used as the schema's `data`.
3. **The files' lists and rows.** Each list and row reader of the second kind reads through a schema of its items: a row that fails is skipped, or raises its finding or its thrown sentence, as today, chosen by which part fails first in the hand code's order (each part checked with its own schema, as Q85a4's item 6 does for findings). `local.ts`'s thrown sentences (`accounts must be a list`, the row and field sentences of `:141-155,184-190,242-295`) stay word for word and keep their order. `rail.ts:33`'s and `agents.ts:262`'s local map tests become `isMap` or a schema.
4. **The configuration.** Each reader of the third kind reads its key through a schema of what it reads (a map of numbers, a host text, a boolean, a positive whole number, a map of strings, a list of rows), with today's fallback for a refused value and today's sentence where it throws. `settings.ts`'s six inline map tests and their casts go. `flattenText` walks any value and stays a walk, its map test `isMap`; `portfolioConfigFrom`'s lists (`index.ts:41-91`) read through item schemas; `searchCap`, `programApps` and `paintLimit` read through a schema each.
5. **The snapshot.** `normalise.ts`'s readers of an entry's named fields read through schemas with today's fallback (a field absent where it is absent today; `num` keeps `Number.isFinite`), the casts `:66,107` go, and the map readers `:155,167` become schemas or `isMap`. In `validate.ts` the shape tests become schemas: `fieldNames` and `schemaKeys` read the schema through a schema of its two forms (a list of names or `{ field }` rows, or a map with `fields`), the `SHAPES` table's `list` and `text` kinds test through `stringItemsShape`-style schemas or zod's array and string types, the list readers `:341,388,412` and the chips `:443-459` through item schemas, and the host rows `:776-781` through a row schema (the cast `:780` goes).
