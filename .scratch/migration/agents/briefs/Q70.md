## What is on the tree (read on main at ae9dcb6a)

Each fact with the command that checked it, run from `tools/oculus`.

1. The mail poller watches its folder with `fs.watch`: `notesWatch = watch(options.dir, ...)` at `src/lib/server/accounts/mail/poll.ts:304` (`grep -n "watch(options.dir"`). A darwin folder watch is an FSEvents stream that registers asynchronously, and a write landing while it registers is never delivered; the git watcher had the same defect for the workspaces file and now polls it (`src/lib/server/watch/git.ts`, `pollWorkspaces`). The case "makes the mail folder when it is not there, so the first write from outside is seen" (`tests/server/accounts/mail/poll.test.ts:317`) failed in 1 of 10 loaded node runs of the previous step's builder and 2 of 3 of its round reviewer's, and passes alone.
2. Three git watcher cases, "re-reads only the root that changed, once for a burst inside the window" (`tests/server/watch/git.test.ts:208`), "publishes one files message naming the root a write landed under, and reads that root alone" (`:245`) and "drops a root the sessions payload no longer names" (`:326`), failed in 4 of 5 runs for one reviewer while fseventsd ran at 100% CPU, with failure values that read as a surplus event (`expected 8 to be +0`, `expected 1 to be +0`), and in none of 58 runs since. Their cause is not found; they run the recursive root watch, which the poll change did not touch.
3. A bookmark added to `~/.oculus/bookmarks.yml` by hand did not reach an open page: an entry written at 19:09:33 on 2026-09-24 was not in the open page's Bookmarks menu at 19:09:56, and was there after a reload (seen on the dev server on 8790). The server polls the file with `watchFile` at `src/lib/server/watch/bookmarks.ts:80-82` (interval `Math.max(20, Math.floor(debounce / 4))`) and publishes on the `files` channel; the page reads the bookmarks again when a `files` message with `bookmarks: true` is newer than the version it holds (`src/lib/state/sources/fs.svelte.ts:360-369`); the server context starts the watcher at `src/lib/server/core/context.ts:60,153,170` (`grep -n bookmarks`). Where the chain breaks is not known: the dev server's context, the watcher, the publish, or the page's read.
4. A page boot times out under load: every browser case boots through `settled()` in `tests/browser/helpers/rail.ts:61-67`, which waits the default assertion time for the status bar's server item to read `statusbar.server_open`. `tests/browser/workbench/unsaved-forms.spec.ts:425` failed there on 2026-09-25 with the load average at 15 and passed 3 of 3 alone; `:406` failed there once before at a load average near 38.

## What to build

1. The mail poller reads the notes file by a poll on an injected clock, as the git watcher reads the workspaces file, so a write made while a watch would be arming is never lost; its folder is still made when missing. A case that writes the file the moment the poller starts and fires the clock, red under its revert, and the case at `poll.test.ts:317` passing in ten whole node runs under file-event load.
2. The three git watcher cases: find their cause. Run them under a load that saturates fseventsd (for instance many processes writing and renaming files across a large tree, as in the previous step's reproduction), paired against the base, and quote the counts. If a surplus or late event reaches the recursive root watch after a case's setup, fix it where it lives (the watcher's handling of events that predate its arming, or the case's own setup ordering against the watcher's arming), never with a longer wait. If no run fails them, say so with the counts and the load, and name what was tried.
3. The hand-added bookmark: reproduce it on a served build (the browser suite's layer) and on the dev server's context, find the link that breaks, and fix it, with a browser case that writes the bookmarks file from outside while the page is open and sees the entry in the rail's Bookmarks menu without a reload, red under its revert.
4. The page boot under load: find what makes the socket take more than the assertion time to open under load (measure the time from the page's load to the socket's open and to the first pushed config, loaded and unloaded), and fix the cause in the server or the page. A boot helper that waits longer is not a fix. If the cause is the machine's load alone and no work of the server's is in the way, say so with the measurements; the orchestrator rules on it.
