# Brief: D3, software as a project type

Read `../spec.md` first, its section "The principles every package is judged on" above all. The plan's D3 line (Axel, 2026-09-12 23:45): software as a project type: a scan tier `projects/software/` of manifests with `type: software` and `related:` to the paper that introduced the algorithm, the Code view listing them beside the paper deposits, the card linking both ways. ## What is on the tree (written 2026-09-15 at 20:05 against 1aa56bac; re-read at dispatch)

- The boards: `src/lib/state/board/presets.ts` (line 149, the three boards and the tiers each shows, `TIERS[id]` at line 301) and `items.ts` line 118 (a project of another tier is on no board). The Focus view, the map and the deck read every project of the snapshot.

- The demo hub `tools/oculus/demo/` is what the browser suite serves (`tests/browser/serve.ts` copies it under the system temporary directory); it has no `projects/software/`.

## The acceptance list

1. **The tier.** `config/sources.yml` gains a flat rule `{ dir: projects/software, type: software, tier: software, optional: true }`; `ScanRule` gains `optional?: boolean`, and `readManifests` reports no finding for an optional rule whose directory is not there (the hub has no such folder until Axel makes one), scanning it like any flat rule when it is. `Tier` gains `'software'`; every place that names the tiers (`presets.ts`, the manifest schema's two help lines, `tests/data/manifests.test.ts` and the twelve other test files that pin them, `HELP.md`'s Projects rows if they name tiers) is updated so the type checker and the suites hold the sixth tier; a software project is on none of the three boards, is in the Focus view, the map and the deck only where a rule of theirs already includes every tier, and `validate` accepts `type: software` on that tier and refuses another type there (the flat-rule finding, as for active).
2. **The Code view lists them.** `views/collection/Software.svelte`, a partial beside `Coverage.svelte`, drawn in the Code view under the coverage groups and above the cards: one row per software project, with its title (opening the project's tab as a coverage row does), its `type` tag, its `code_availability` status word, and its related papers as cross-links (each opening that project's tab); the section says so in the catalog's words when the tier holds nothing. The rows come from a pure `softwareRows(projects)` in `state/collection.ts`, sorted by title.
3. **The card links both ways.** A software project's card draws its `related:` papers where a card draws related projects today (no change if that already holds); a paper's card gains a cross-link kind `software` in `CardLinks.svelte` listing the software projects whose `related:` names it, computed once in the board's join (`state/board/items.ts`, a `software: BoardTag[]` on `BoardItem` from the snapshot's `projectRelated` pairs), each tag opening the software project's tab.
4. **The demo hub** gains `projects/software/demo-toolkit/project.yml` (type `software`, `related:` naming a demo paper, a `code_availability`) and a `README.md`, so the browser suite and the fixtures hold one; `tests/browser/serve.ts` needs no change if it copies the folder whole.
5. **Words** in `config/text/views/collection.yml` (the section's heading, its empty sentence, the row's labels) and `config/text/views/project.yml` (the new kind's label and glyph); the manifest schema's two help lines; `HELP.md`'s `code` row names the software list; DESIGN.md's tier table if it has one, and one dated decision line.
6. **Tests**: `tests/data/manifests.test.ts` (the optional rule silent when absent, scanned when present, the type finding on a software folder saying another type), `tests/state/collection.test.ts` (`softwareRows`), `tests/state/board.test.ts` (the `software` kind on a paper's item, and none on a software item's own card for itself), `tests/views/collection.test.ts` (the section drawn with one row and its links, the empty sentence), `tests/views/card.test.ts` or `project.test.ts` (the kind drawn), `tests/config.test.ts` (the sixth rule's shape), and a browser case: open the Code view, see the software row, open the paper it names, see the software link on the paper's card.

## Decisions taken in this brief (each reversible, none silent; the shapes go to Axel through the orchestrator)

1. The tier folder is `projects/software/` (Axel's own words in the plan line; the name is his to rule) and the rule is `optional`, so a hub without the folder reports nothing; `optional` is a new key of the scan rule shape.
2. A software project is listed in the Code view and on no board.
3. The reverse link is a cross-link kind `software` on the paper's card, computed in the board join from the existing related pairs, not a new manifest field.
