## What to build

1. **The rule is Q85c's item 1, unchanged, in these areas.** A schema goes where a value that came from outside the code (a tab's instance state, an HTTP answer's body, the merged configuration, an entry's fields) is read for its named fields or its items. The schema is a `const` at module level beside the function that reads, in that function's file, named in lower camel case ending in `Shape`; in a `.svelte` file it goes in the component's `<script module>` block, so it is built once and not per instance (53 components already have one, `grep -rln '<script module' src/lib | wc -l`). A schema whose answer has a declared type is held to it with `satisfies z.ZodType<...>`. Every reader answers, for every input, what it answers on main: the same value, the same fallback, the same text drawn, the same thrown error caught where it is caught today. zod's error text is never shown or logged, and no `.issues`, `.error`, `prettifyError` or `treeifyError` is read. A reader that hands on an object or a list it was given answers the input itself (`unchanged`). A hand check moved into `z.custom(...)` or `.refine(...)` where a shared helper or a zod type expresses the test is a hand check still, and fails the step. Q85a4's answer-keeping rules hold: a `typeof === 'number'` test keeps `NaN` and the infinities accepted (`anyNumberShape`); a `Number.isFinite` test refuses them; a field read with a fallback for any other value is `.catch(<fallback>)`. The answers that change are the ones item 11 names (Z179, closed by the orchestrator in automode); any other changed answer is a finding.
