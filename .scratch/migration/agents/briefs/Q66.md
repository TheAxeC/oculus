## What to build

1. **The scope in the query helper** (`src/lib/state/client/queries.svelte.ts`, and the `Queries` type in `src/lib/state/shared/stores/shapes.ts`). `createQueries` gains `scoped<T>(shown: () => boolean, run: () => T): T`: it sets the current scope, held in a variable inside `createQueries` (never a module-level `let`), to `shown` for the synchronous run of `run`, and restores the scope that was current before in a `finally`, so scopes nest. With no scope current, every function behaves as today.
   - `read`: where it would schedule today (`options.enabled && wants(state)`), and a scope is current whose `shown()` is false, it schedules nothing and answers what is held. `shown()` is called only at that point, never on a read that would not schedule, so a shown tab's derived values gain no dependency and a hidden tab's re-run on show is limited to the keys that need an answer. Reading `shown()` there is what makes the derived run again when the tab is shown, and that run schedules the one catch-up request.
   - `refetch` in a hidden scope: with a request out or scheduled and `whileFetching` `drop`, it returns, as today; with one out and any other mode, it sets `waiting` to `wait` unless `waiting` already holds `again` (a live caller's `again` is never lowered); with none out, it calls `invalidate(key, true)` when the cache holds the key, and nothing when it does not. It never cancels, never schedules and never sets `fetchers` for the key (a later `again` lands with the live reader's fetcher). Readers are woken, so a shown tab reading the same key asks on its next read, and the hidden tab asks once when shown.
   - `peek`, `fetch`, `hold`, `mark`, `forget` and `entries` are unchanged in a hidden scope. `fetch` is an awaited call made by a handler or by the one-shot effects above, which ask because their caller waits for the answer.
   - `settled` is unchanged: a socket mark of `again` while a request is out (`docs.svelte.ts:214`) asks once more when it lands, as today, since a socket listener runs in no scope; a document only hidden tabs read can so take one request while hidden, which the look does not count as a failure.
   - A read scheduled while shown whose tab is hidden before the microtask runs still goes: `schedule` (`:164-173`) does not ask the scope again.
2. **The tab's copy of the stores** (`src/lib/state/client/context.ts`). `createClientState` records each store it hands `queries` to, at the hand-over, under the store's `ClientState` name (one small local helper used at each of the ten hand-overs, so the list lives where the hand-over is and a store added later with `queries` is recorded by the same call). `ClientState` gains one member, `tabScope: TabScopeStore`, an object with one function `wrap(state: ClientState, shown: () => boolean): ClientState`: it answers a copy of `state` in which each recorded store is replaced by an object holding the same members, each function member calling the original inside `queries.scoped(shown, ...)` with the same arguments and answering its answer, each other member copied as it is. Every other store of the copy is the original instance. `TabScopeStore` is exported from `context.ts`, beside `ClientState` (the folder is full, so no new file). The recorded list is a local of `createClientState`, never module-level. The head comment `:5-6` says that a tab provides the copy for its subtree.

## Decisions taken in this brief (each reversible, none silent)

1. The scope is dynamic and synchronous (`scoped` sets it for the call's stack). Every read a hidden tab makes on its own runs synchronously inside a derived or an effect, and a handler's call to a store function after its own await goes through the tab's copy again, so both are gated; only a read inside a store function after that function's own await runs in no scope, which case 24 lists.
2. The ten stores are reached through a copy provided by each `TabView`, so no view and no store module changes for them; the copy is built by a `tabScope` member of the client, which keeps `queries` off the client object (a view cannot reach the query client) and passes the shell's store check, since only `use.ts` touches it.
3. A hidden `refetch` marks with readers woken: a shown tab of the same key must not be left stale because a hidden tab consumed the stamp.
4. `shown()` is read only where a read would schedule, so a tab switch re-runs no derived of a key that needs nothing.
5. The five views gate through one `shownGate` each, remembering what they last loaded for by identity, so showing a tab with nothing changed asks nothing and a reset clears the memory.
6. One-shot reads on a change of subject (`File.svelte`'s `readFileKind`, `ShowPath.svelte`, `Merge`, `CommitFiles`, `Diagram`, `loadSourceDraft`) stay live: they run on a change the reader made, and their caller awaits the answer.
7. A socket `again` mark while a request is out still asks once more when it lands, for hidden readers too (`settled` unchanged): the request is already in flight, and gating `settled` would need the scope of a request that has none.
