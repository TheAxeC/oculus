## What to build

When the step is done, a repository named by a `roots:` entry of the first hub's `.oculus/config/sources.yml` with `tier: projects`, `coauthor` or `archive` is a research project of the first hub: on its board, its project page, the editor, Cmd-K and the Map as a hub project is, its references resolved against the first hub's registries, and every write to it lands in `<root>/.oculus/project.yml` and no other file. With `tier: personal` or no `tier`, it is a side project exactly as it is today, LaTeX included.

1. **The `tier` key of a roots entry.** `readRoots` reads an optional `tier` on an entry. The values are `projects`, `coauthor`, `archive` and `personal`. A `tier` with any other value, or one that is not text, is a finding on the entry (key: the root's key) naming the four values, and the root is read as if it had no `tier`. A `tier` on an entry marked `hub: true` is a finding on the entry, and the root is a hub as it is today. A research `tier` is refused with a finding on the entry, and the root read as if it had no `tier`, when: the key holds a colon, a slash or whitespace, or is one of `RESERVED_HUB_KEYS`; the dir is the first hub's, lies inside it or holds it; or an earlier entry with a research `tier` has the same real directory (the first is read, the second is the finding). A root added from the saved workspaces has no `tier`. `Root` gains `tier?` for the three research values only (`personal` and absent read the same, so the type holds no second spelling of "a side project"). Every finding's words are a line of `config/text/` under `findings.roots`, as the other roots findings are. The roots write keeps an entry's `tier` through every write it makes (add, remove, order): `RootItem` and `itemShape` carry it, `itemText` writes it, and `kept` compares it, so a write that would lose it is refused rather than made. The Settings view's `roots` fields gain `tier` (Z785): a choice of the four words with none allowed, its help naming what each does, in `config/catalogs/options.yml`.
2. **Which tier and type a repository takes (Z779).** `ScanRule` reads the scan rule's `tier:` word, as both layers write it. A repository with `tier: coauthor` or `archive` takes the scan rule of that `tier` word, which is nested: its `Tier` is the basename of that rule's `dir` (`coauthor`, `archive`), its `type` (the outcome) is its manifest's own, and it has no `category`. A repository with `tier: projects` takes the flat scan rule of that `tier` word whose `type` equals its manifest's `type` (`idea`, `active`, `manuscript` on this hub), and its `Tier` is the basename of that rule's `dir`. Each of these is a finding naming the reason, and the repository is then read as a side project, so it stays on the Personal board with the finding on the Findings view: a manifest whose `type` is missing, not text, or named by no such rule (on the manifest's `type`); a `tier` word no scan rule of the first hub carries (on the entry); a key equal to the id of a project the hub's scan reads (on the entry). A manifest whose own `id:` differs from the root key gets the `id` finding a scan project gets, with `manifestId` kept, and stays a research project. A repository with a research `tier` whose `.oculus/project.yml` is not there is a finding on the entry and no project, and a root whose dir is not on this machine gives `readRoots`'s one finding and no second. `model-entities.ts` is at 880 lines, so the change to `ScanRule` comes with a split of that file by concern, into files named for what they hold.
3. **The record.** The repository's research project is a `RawManifest` read from `<root>/.oculus/project.yml`, under the same size bound and file checks as a side project's manifest (`readPersonalFile`), with the id the root's key (Z778), the `tier` and `type` of item 2, no `root` (it is the first hub's, read as `hub`), `file` the manifest's absolute path, `folder` the repository's absolute path, its documents and its deck read from the repository's folder as a side project's are (`folderHolds`, so `deck` is relative to the repository's Files root), and its provenance `repository: { root: <key>, dir }`, carried into `Project.repository`. It joins the hub's manifests before validation and normalisation, so the manifest schema, the vocabulary, the registries and the relations of the first hub apply to it exactly as to a project of a scan folder, and its references (venue, pillar, domain, datasets, people, `related`, `waiting-on`) resolve against the first hub's registries, while another manifest's `related` or `waiting-on` naming its id resolves with no finding. `checkFolderNames` takes a repository's name as its id, so its key is what clashes with a hub folder's name. `personalRoots` leaves out every root read as a research project, and a workspace-added root whose real path is a research root's, so no repository is both. One function reads the first hub's research manifests, the repositories included, and every server reader that today calls `readManifests` for the first hub calls it: the build (`data/index.ts`), the manifest write (`homeOf`), the undo's routing (`holding`), the chat's portfolio context, the task seed and a project's files; the deposit is the one exception (item 7). The function takes the roots it reads from the configuration it is given, so a reader that holds only the merged config reads the same projects the build reads. A second hub's `roots:` stays unread, as `docs/DATA-MAP.md`'s "A second hub" says. Its place: in `manifests.ts` while that file stays at or under 880 lines; a new file goes only into a folder with room, and `src/lib/data/sources` and `src/lib/data/snapshot` are full, so a new file there comes with a split of that folder by concern.
4. **The watcher.** The watcher hears `<root>/.oculus/` of every research root as it does a side root's (`roleDirectories`, `namedByConfig`, `watchRootParents`, `openRootFolder`), so an edit, a creation or a removal of `<root>/.oculus/project.yml` rebuilds the snapshot, and a change of a root's `tier` in the hub's layer is a config change and rebuilds it (item 9).
5. **Every reader of a project's folder.** Each reader the premises list as pairing the hub with the folder reads it through `placeOf` (`as-project.ts`) or `Project.repository`, so a repository's research project is read in its repository: its documents, its decks (both deck readers), the Present view's project decks (the ref's root is `placeOf(project).root`, so the deck opens under the repository's root), the audit's project checks (the scope of a finding is the project's `folder` as the record holds it), the LaTeX endpoint and build (item 8), the session index (a session started in the repository is matched to the project), the cluster submit, a project's files, the chat's portfolio context (headed by the project's folder as the record holds it), the client's `projectFolder` and so a session's manifest file (`<root>`, `.oculus/project.yml` for a repository; `{ root: hub, path: project.folder }` and `project.yml` for a scan project, as now), and the terminal's hub folder (`hubRoot` skips a project with `repository`, so the terminal starts in the hub). `context.ts` is at 885 lines, so the change to it comes with a split by concern into files named for what they hold, which brings it under 880. The comments of `Project.repository`, `RawManifest`'s `id` and `folder`, `Project.folder`, `checkFolderNames`, `holding` and `hubRoot` say which records are made with `repository`, that a repository's `folder` is its absolute path, and that its id is its root's key.
6. **The editor.** The manifest editor opens a repository's research project with the fields of `manifest_schema`, as a hub project's, and the YAML schema the editor checks `<root>/.oculus/project.yml` against is the manifest schema for a research repository and the side project schema for a side repository (`schema/static.ts`, `schema/run.ts`). Cmd-K and the Map find it as a project of the first hub, with no `RootChip` mark.
7. **Writes.** Every write to a repository's research project from the page (the editor, Pin, a subtask added, ticked or edited, a follow-up, a snooze, the undo of each) finds its file through the reader of item 3 and writes `<root>/.oculus/project.yml` and no other file, with the fields of `manifest_schema`; `insideHub`'s refusal is kept for a scan project, and a repository's file must be `<dir>/.oculus/project.yml` of a root in force with a research `tier`, as `isOwnFile` checks a side project's. The undo's routing (`holding`, `hubs.ts`) accepts that file, so the undo of each write puts it back. A write from an app's frame naming a repository's research project answers not found, as for a repository side project (Z783, `sidesFor` and the reader of item 3 in `writes.ts`). A write to the id after the entry's `tier` is removed finds no research project (it is then `root:<key>`, a side project). The scaffold of a new idea stays in the hub. The deposit (Z780): a repository's research project has no Deposit; its card is drawn with `deposit` off, as a side project's is, and the deposit route answers not found for its id (the deposit keeps reading the hub's scan with `readManifests`), since the deposit mirrors a hub folder's `code/` and a repository is its own git repository. `ProjectCard.svelte` is at 520 lines: the `deposit` flag is set by the board files that pass it, and a change that would take the card past 520 comes with a split.
8. **LaTeX in a research repository (Z780).** The LaTeX endpoint and build read a research project's `manuscript/` from the project's folder as `placeOf` gives it, a repository's included, under the same refusals of a folder that leaves its root. `src/routes/api/(sessions)/latex/+server.ts` and `Project.svelte` stop refusing a research repository, so one whose `manuscript/` holds a main file has the LaTeX panel, and one without draws what a hub project without one draws. A repository side project keeps the refusal and draws no panel, as now. The head comment of `Project.svelte` says so.
9. **Moving and archiving (Z784).** A repository's research project moves to the archive or the coauthor board, or back, by a change of its `tier:` in `.oculus/config/sources.yml`, and between ideas, active and manuscripts by its manifest's `type:` line, edited in the manifest's source; the next rebuild after the file is written reads it there. A write keeps refusing `type`, and no action of the board moves it.
10. **The text.** `docs/DATA-MAP.md`: the `roots` row (302) names `tier` with its four values and what each does; line 72 and the rows at 181-182 and 597 say that a repository is a side project only with `tier: personal` or no `tier`; 570 says a repository's `type` line picks its column; the "A second hub" section's rows agree that a second hub's `roots:` is unread. `tools/oculus/HELP.md:169` and the paragraph at `:451` say how a repository becomes a research project, that a move between boards is a change of its `tier` or of its manifest's `type` line, that it has LaTeX and no Deposit, and that an app cannot write it. `tools/oculus/DESIGN.md:558` says which records read a repository, that a repository's research project is in `entities.projects` with `repository`, and that an app's write to it answers not found; `:593` says a first-hub record's `folder` is hub-relative except a repository's, which is its absolute path opened under its own root. `tools/oculus/docs/apps.md:125` names `repository?` (`{ root, dir }`) on a project and says its `folder` is the repository's absolute path. The comment of `roots:` in `tools/oculus/config/sources.yml:76` and in the hub's `.oculus/config/sources.yml:80` names `tier` and its four values; the hub's line is hub text, given before and after in the report. `config/text/views/boards/personal.yml:8` says a repository gets a side project card when its entry is not `hub: true` and has `tier: personal` or none. `options.yml`'s `roots` help (item 1).
