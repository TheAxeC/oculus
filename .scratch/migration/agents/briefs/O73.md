## What to build

1. **One rule for what a `from` names.** One exported function `namesList(source, merged)` in `src/lib/data/snapshot/schema/static.ts` says whether a source names a list: it does when it is `projects`, one of `REGISTRIES`, or `vocab.<name>` where `<name>` is a key of `vocabLists(merged, VOCAB_FILE_KEYS)` (so `vocab.<key>` for a key of `vocab.yml` set in the merged config, and `vocab.<key>.<field>` for a field a row of that key carries as `true`). An empty source names no list. `schemaFileProblems` builds its `lists` from it; on the tree it reports what it reports today (none). The function's doc comment says what it holds a list. Grep for `namesList` before writing it; a name already taken is replaced by a free one and the report says so.
2. **The check of a hub's row.** The check runs in `mergeHub` after the hub's values are set into `config` (after the loop at `hub-layer.ts:518-531` and `dropRemovedWords`), against that `config`, so a list the hub itself adds counts. `readManifestFields` keeps each taken row's index in the hub's list, so the finding names the row's key as the hub wrote it. A taken row whose `from` holds a source `namesList` does not hold a list is a finding on the hub's file at the key `manifest_fields.<i>.from`, naming the first such source, and the row is taken out of `config.manifest_fields`, as every other kind of row the form cannot take is left out. A `from` that is a list is checked source by source. A row whose `from` is an empty list, or whose first bad source is the empty text, gets the second sentence of item 3, which names no source. A row with no `from` is not affected. The doc comments of `readManifestFields` and `mergeHub`, and the file's head comment at lines 10-13, name the new kind among the others.
3. **The sentence**, in `config/text/findings.yml` under `findings.config`, after `manifest_field_shape` (line 140), word for word:
   - `manifest_field_from: '{0} names {1}, which is no registry, projects or vocab list; the row is left out'`

4. **The four sentences that list the kinds of row left out** name the new kind, a `from` that names no registry, `projects` or vocab list, in the words each line already uses: `config/options/schemas/manifest-schema.yml:4`, `config/schemas/manifest-schema.yml:86` (which today names three of the six kinds the code reports; it is written to name all seven: no field, a field the form has, a field an earlier row names, a section the form lacks, a widget the form does not draw, a row the shape refuses, a `from` that names no list), `docs/HELP.md:524` and the comment of `manifest_fields` in `docs/templates.md:305-310` (kept a commented block of lines of at most 100 columns, as the lines around it are).

## Decisions taken in this brief (each reversible, none silent)

1. A row whose `from` names no list is left out, as each of the six kinds of row the form cannot take is left out today (G128, `config/options/schemas/manifest-schema.yml:4`). Kept, the field would offer no choices and its manifests would be held to a list that does not exist.
2. The rule of a list is one function for oculus's own schema files and a hub's rows alike, and it checks the field part of `vocab.<key>.<field>` against the field lists the build reads (`vocabLists`), since a source with a field no row carries names no list (`lists.ts:4-5`). The hub's rows are checked after the hub's own values are laid in, so a list or a flag the hub adds counts.
3. One finding per row, naming the first source that names no list, at the key `manifest_fields.<i>.from`, as each other kind gives one finding per row.
4. The sentence's key is `manifest_field_from`, an internal key of the text catalog; its words follow the five `manifest_field_*` sentences beside it and the `bad_from` sentence of oculus's own schema files.
5. A `from` that names nothing (an empty list or an empty text) is a finding with its own sentence, `manifest_field_from_none`, since the first sentence would print an empty name.
