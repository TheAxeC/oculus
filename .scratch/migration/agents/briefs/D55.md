## What to build

1. **A root marked as a hub (Z762 (a)).** A `roots:` entry of the first hub's layer may carry `hub: true`. `rootEntryShape` takes `hub`; a `hub` value that is not a boolean, a hub root whose real directory is the first hub's, lies inside it or holds it, and a hub root keyed `side`, `root`, `hub` or `engine` or whose key holds `:`, two hub roots whose real directories are one, and a hub root whose real directory lies inside or holds another hub root's, are each a finding naming the root (words in `config/text/findings.yml`), and that root (the later of two) is then read as a plain root. A hub root whose directory is not on this machine keeps today's finding and builds nothing. The roots writer keeps `hub: true` on every entry it rewrites (Add Folder, Remove Folder, the reorder), so no write of `roots:` drops it. A root with `hub: false` or no `hub` is a plain root as today. Every root stays a served root of the Files view.
2. **Each hub built with its own settings (Z762 (d)).** The first hub is `local.yml`'s `hub`; the others are the `hub: true` roots in the order of `roots:`. Each is built by `buildPortfolioWithSchemas` with its own merged settings, the engine's general defaults under that hub's own `.oculus/config/` (`loadConfig(engine, { hub: <its dir> })`). The page's settings (the rail, the arrangements, the words, the themes, the colours) and the `roots:` list are the first hub's; a second hub's own `roots:` is not read, and a key of its layer that only the first hub's layer is read for gives no finding. The watcher watches each hub's folders and its `.oculus/config/` and rebuilds on a change to any, as it does for the first; the merged snapshot holds the latest build of every hub, and a build of one hub that finishes after a newer build of the same hub, or after its root left `roots:` or lost `hub: true`, is dropped. A second hub's own `domains`, `venue_themes` and `data_themes` check its own records; the page draws a word the first hub's vocabulary has no colour for with the neutral colour it gives any such word today (Z765 (d)). The YAML server's schemas and reference index are built per hub, a file of a hub given its own hub's schemas and keys and no key of another hub.
3. **One merged portfolio with ids that never collide (Z762 (b)).** Every record of a hub other than the first has the id `<root key>:<id>`: projects, venues, datasets, pillars, domains, funding, people, organisations, resources, collections and their entries, side projects (so `<key>:side:<slug>`), and feed items. Every id inside its records (a project's `venue_id`, `pillars`, `collaborators`, ...) and every relation pair names the same hub's records, prefixed alike. A reference never crosses hubs: a value its own hub cannot resolve is the finding it is today, never resolved against another hub. A first-hub id that begins with `<a hub root key>:` is a finding naming its file, so no merged id is ambiguous. The merged snapshot holds every hub's entities and relations; its findings are every hub's, each naming its own hub (item 4).
4. **Every record knows its hub (Z762 (c)).** Every entity carries `root`: `hub` for the first hub's records, the root key for another's. Its `folder`, `deck`, `path` and every other hub-relative path stay relative to its own hub (an absolute `file` stays absolute), and the page and the server open each under `root`: the Files view, the doc view, a project's documents and decks, Show in Files, an entry page's folder, the sessions working in a folder, a card's file finder (`project-files.ts`), a chat started on a project (`pty/start/chat.ts`), an HPC submit (`hpc/submit.ts`), a deposit (`git/deposit.ts`) and the deck and image reads (`content/deck/read.ts`, `content/images.ts`). An audit finding of a hub other than the first carries the same `root`, and the Audit view opens its file under that root (Z765 (a)). A snapshot finding keeps its absolute `file`. A record with no `root` read from an older snapshot is read as `hub`.
5. **The career, the website, the feeds and the audit (Z762 (e)).** The career file, the website keys (`publications_file`, the website's data) and `portfolio_deck` (the Present view's default deck) are read from the first hub alone; a second hub's project decks open from their cards under item 4's `root`. The feeds (Position Leads, Lit Watch, LinkedIn) and the audit are built per hub and merged, their items under item 3's ids and item 4's `root`. The audit's publications section runs over the first hub only. A second hub's audit finding names its place with the root key in front, so its mute signature differs from a first-hub finding of the same place, and every first-hub signature, and so every existing mute, is unchanged; the mute list is the first hub's.
6. **A write goes to its record's hub (Z762 (f)).** A write that names a record (a manifest field, an entry field, a subtask, a subtask added, a reorder, a deletion, a feed field, a feed deletion, a LinkedIn posted, a deck write, a session override that names a project, the deposit's `code_availability` write) goes to that record's hub, with that hub's merged settings, the prefix taken off before the writer looks the record up. The `linkedin-posted` write, which names a file, carries the post's `root` beside its file, absent read as `hub` (Z765 (b)). An app's write that names a record of a hub other than the first is refused as an unknown record, as an app's write outside the hub's side-projects tier is today (Z765 (c)). The page names a write's file and an undo's file under the record's `root` (`state/sessions/source/write-files.ts`), so the refusal of a write over a tab holding unsaved text of that file holds for a second hub as for the first. A new project, entry, lead, Lit Watch entry or idea goes to the first hub. Settings writes the first hub's layer, as today. The change log records a file of the first hub relative to it, as today, and a file of another hub by its absolute path, as it records the engine's files, and the undo from History puts that file back. A write that names a prefix no hub carries is refused as an unknown record, with the sentence the route gives today. A write whose base the second hub's file no longer holds is refused with G8's sentence. When a hub root leaves `roots:` or loses `hub: true`, its records leave the snapshot, an open tab of one shows the not-found state it shows for a deleted record today, and an undo from History of its file is refused as a path outside every root (G2).
7. **The mark on a card (Z762 (g)).** A card, a row and an entry page of a record whose `root` is not `hub` shows a chip with the root key, through `ui/controls/Chip.svelte` and words of `config/text/`, on every hub view that draws records (the boards, the collection views, the registries' views, Focus's rows, the entry and person pages, the side projects).
8. **Every hub's `secrets` folder is private (Z762 (h)).** `privateFolders` answers `~/.oculus` and the `secrets` folder of every hub, and each of its six callers is given every hub, so a hub root's `secrets` is withheld from the language servers, the writing rules, search, paste and the library rules as the first hub's is. The page learns which served roots are hubs from a `hub: true` on each such root of the workspaces answer (`workspacesAnswer`, `server/files/fs.ts`), the same key the `roots:` entry carries (Z765 (e)), and `isPrivateFile` withholds every hub's `secrets`.
9. **A hub root's own manifest (Z762 (i)).** A hub root's own `.oculus/project.yml` is not read as a side project (`personalRoots` drops it), and the hub root stays a served root of the Files view. Saved state that names its former `root:<key>` side project (a Focus pin, an override, a kept workbench, an open tab) shows what it shows today for a side project whose manifest is gone.
10. **The undo of a deleted entry with subtasks (ruling Subtasks on undo).** A write of a collection entry carries a field whose value is a list of maps whose values are scalars (strings, numbers, booleans, null), such as a task's `subtasks`: `fieldValueShape` takes that shape, the YAML writer and `renderEntry` render it as a block list of one-line flow maps in the file's indent, the form the hub's files hold subtasks in, and the undo from History of a deleted entry that held `subtasks` (through `createEntry`, `writes/undo.ts:505-507`) puts the entry back with its subtasks, each map's keys and values as the record holds them, re-read after the write. The shape is accepted by every writer that shares it (a manifest field, an entry field, a feed field), each written in the file's form and re-read. A value of another shape (a map holding a list or a map) is still refused with `NOT_A_FIELD_VALUE`, its words updated to name the new shape, and `tools/oculus/docs/apps.md:524`, which quotes them, follows.
11. **The sessions and the projects.** A session whose folder lies in a project folder of a hub other than the first is filed under that project as a session in a first-hub project is; a session whose folder is a hub root itself is filed under no project, as a session at the first hub's root is.
12. **The text.** The words the page shows (the root chip's tooltip, the new findings) are keys of `config/text/`. `HELP.md` gets bullets appended at the end of its section "Configuration and the data", saying what `hub: true` does, which settings a second hub's layer sets, where a new record goes, what the chip says and that its `secrets` is private. `DESIGN.md` gets a decision bullet appended at the end of its decisions list stating items 1 to 9 in its own words. The hub's `docs/DATA-MAP.md` gets a section "A second hub" appended before its section "Outside the hub". The sentences "What is on the tree" lists as made false are rewritten in place (`DESIGN.md:557`, `HELP.md:107`, `DATA-MAP.md:182`, `:312`, `:519`, `docs/apps.md:524`, `search-routes.ts:19`), and every other head comment or document sentence the change makes false, found by grepping each changed name across `src`, `tests`, `config`, `docs`, `HELP.md`, `DESIGN.md`, `README.md` and the hub's `docs/DATA-MAP.md`.
13. **The tests.** `tests/` gets, under the rules file's test rule, a test for each behaviour whose failure loses or misplaces work or leaks a secret: item 1's findings (a G13 row, G13's Code line widened to `server/files/files.ts`); item 3's ids and relations over two hubs that hold the same ids, every record of both present (a G32 row: what each hub shows is what its files say, built from two copies of `demo/` under `$TMPDIR`); item 6's writes to a second hub's record, one row per write kind of item 6, and their undo (G8 and G9 rows); item 8's withheld folder through every caller, the page's included (a G3 row); item 10's undo with subtasks (a G9 row). Each test is the test of the entry named here, and no test is written under no entry. Each is run on the unchanged tree first, where it fails for the reason it names, and passes after. The G entries of `agents/guarded.md` are named in the report with the rows the step adds; the orchestrator writes `guarded.md`.
