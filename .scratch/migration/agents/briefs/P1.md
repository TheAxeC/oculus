# Brief: P1, the writes foundation

Read `../spec.md` first; it governs this package unchanged. Then `tools/oculus/DESIGN.md` lines 158 to 163 ("Git" and "Auth": every write behind the token and the origin check) and the header of `src/lib/server/yaml-edit.ts` (lines 1 to 60: a field's bytes and no others, verified before disk, which is O11's rule for every write). Then `../../parity.md`, the audit of 2026-09-11: every cockpit tab carries write-back buttons the oculus views lack (snooze, done, del, status, pin, add, edit, host status, new idea), and every one of them needs a writer that does not exist. This package is that writer; P2, P3 and P4 draw the buttons over it.

The cockpit's `tools/cockpit/src/cockpit/setstatus/` (`entries.py`, `subtasks.py`, `feeds.py`, `manifests.py`, `yamlio.py`) is the cautionary reference for what each write has to do to the file: which line an entry is, how a subtask line is re-emitted, how a host line is patched, what a new idea scaffold holds. Its line-regex approach is not the model; oculus's `server/yaml-edit.ts` (O11) is, with its rule that the result must parse to exactly the source with the change applied or nothing is written.

## What to build

Under `tools/oculus/src/lib/server/`:

- `entry-edit.ts`, new, beside `yaml-edit.ts` and sharing its helpers (`renderScalar` line 128, `deepEqual` line 98, `sameValue` line 113, `asFieldValue` line 119, the parse-and-verify rule of `setFields` lines 476 to 542): `entryRange(source, ident, value)` (the line range of the entry whose `- <ident>: <value>` line opens it, to the next entry at the same indent or the next top-level key, the cockpit's `_entry_range` rule at `entries.py` lines 113 to 128); `setEntryFields(source, ident, value, fields)` (each field written in the bytes of its own value inside that range, a field the entry lacks appended at the entry's indent, `null` removing the line, the whole verified as `setFields` verifies); `appendEntry(source, listKey, block)` (the rendered block inserted at the end of the list, before the next top-level key); `subtaskLines(source, range)` (the `subtasks:` block of a manifest or an entry: the lines and their keys, a map's own keys or a list's positions, matching what `normalise.ts` lines 155 to 176 read); `setSubtask(source, range, key, fields)` (one line re-emitted with `done`, `deadline` or `snooze` set or cleared; `done: false` and an empty value drop the field, as `subtasks.py` lines 100 to 126 do); `deleteSubtask(source, range, key)` (the line, and the empty `subtasks:` key after it); `addSubtask(source, range, fields)` (a flow-map line appended to the block, the block made when absent); `setHostStatus(source, name, status)` (the one-line flow map under `hosts:` whose `name` matches, its `status` replaced, `feeds.py` lines 262 to 276). Every function answers `{ text, changed, refused }` like `setFields` and never throws.
- `writes.ts`, extended (lines 124 to 308): `WriteTarget` is unchanged; `entryWrite(body)` for `{ kind: 'entry', collection, id, fields }` (the collection key of `sources.yml`, the entry's id as `normalise.ts` line 323 makes it, which is the schema's first field's value or the title; the identity field is the file's schema's first field, `title` when it has none, the cockpit's `_identity_field` at `entries.py` lines 103 to 108; a test asserts over the real hub that every entry's id is that field's value); `subtaskWrite(body)` for `{ kind: 'subtask', target: { id } | { collection, id }, key, action: 'done' | 'reopen' | 'snooze' | 'delete', value? }`; `subtaskAdd` for `{ kind: 'subtask-add', target, fields: { do, deadline? } }`; `hostWrite(body)` for `{ kind: 'host', name, status }` (the status must be a key of `career_host_status`, `vocab.yml` lines 206 to 212, else refused; the file is `career_file` of `sources.yml`, `CAREER.yml`); `newEntry(body)` for `{ kind: 'new-entry', collection, fields }` (rendered from the file's own schema in schema order, the identity field first, refused when an entry with that identity exists); `newIdea(body)` for `{ kind: 'new-idea', fields: { id, title, short?, domain?, eli5? } }` (the scaffold of `manifests.py` lines 136 to 163: `projects/ideas/<id>/project.yml` with `type: idea`, `focus: holding`, `status.chips: [exploring]` and the status line, `eli5`, `next`, and a `README.md` with the title, the eli5 and a Next section; a bad id or an existing folder refused). `handleWrite` (lines 260 to 308) dispatches on `kind` in that order after the session and manifest writes it has, every write answering `{ ok, changed, refused }` or the 400 and 404 the existing kinds answer; the manifest's `snooze`, `priority`, `focus`, `followup.do`, `followup.after` and `deadline` already write through `writeManifest` and are what P2's snooze, flame and quick-add buttons use.

## Facts checked on the tree, 2026-09-11

- `yaml-edit.ts` writes a manifest's top-level and one-deep dotted fields (`pathOf` at line 84 allows two parts) and nothing inside a list; no module writes a collection entry, a subtask line, a host line or a new file.
- An oculus entry's id is its `key` when it has one, else its `title` (`normalise.ts` line 323). The hub's collection files carry schemas whose first field is `key` on the collections that have keys and `title` on the others; the real-hub test in this brief is what proves the two rules agree.
- The hub's `subtasks:` blocks are lists of one-line flow maps on entries and either a list or a map on manifests (`manifest-schema.yml` line 74 calls the manifest's a keymap); `normalise.ts` addresses a list line by its position and a map line by its key.
- `CAREER.yml`'s hosts are one-line flow maps with `name` and `status` (lines 26 to 41); `career_host_status` has five keys.
- `writeManifest` verifies before disk and the O11 check showed 91 of 91 real manifests byte-identical on a no-op write.
