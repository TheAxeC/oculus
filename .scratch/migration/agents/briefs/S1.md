# Brief: S1, the generic plan-orchestration skill

Read `../spec.md` first; it governs this package unchanged, with one difference: the deliverable is a skill (Markdown and one symlink), so there is no `npm` toolchain and the verification commands are the ones listed below.

## What to build

A hub skill at `.agents/skills/plan-orchestration/` that runs a multi-package plan with agents, the way `tools/oculus/.scratch/migration/` is run, with every project-specific fact read from the plan's ledger folder rather than written into the skill. Files:

- `.agents/skills/plan-orchestration/SKILL.md`, under 200 lines.
- `.agents/skills/plan-orchestration/templates/plan.md`, `orchestrator-state.md`, `spec.md`, `brief.md`, each under 60 lines, with `<placeholders>` in angle brackets.

Create it with `ln -s`; it is the one shell write this package makes, and it lands on main through git like the rest.

## What the skill must say

**The ledger folder contract.** A plan lives under `.scratch/<feature>/` inside the tool or project it belongs to, tracked in git: `plan.md` (packages in execution order, each one dispatch, ticked with the green checkmark only after verification ran and the orchestrator read the whole diff; a "Could run in parallel" list; a "Rulings" list of the user's decisions, dated; a "Blocked, and by what" list), `orchestrator-state.md` (read first after any compaction; rewritten at every package), `agents/spec.md` (the standing rules every package runs under), `agents/briefs/<package>.md` (one per package), `agents/reviews/` (a second agent's read of a diff, when used).

**The configuration block** at the top of `orchestrator-state.md`, the only place project specifics live. The skill reads it and nothing else:

```yaml
verify:            # commands run in the worktree and again on main, in order; all must pass
  - <command>
worktree_paths: [] # sparse-checkout paths for a package's worktree; empty means the whole tree
standards: []      # files every brief tells the agent to read in full
executor: agent    # agent | academic-paper | inline
model: opus        # for executor agent: opus or lower, never fable
```

**Executors.** `agent`: a general-purpose agent on the configured model, in a worktree, landed by cherry-pick; for code tools, research projects, any package whose deliverable is source or data. `academic-paper`: the package's brief is a dispatch of the `academic-paper` skill in the mode the brief names; for manuscripts, responses to reviewers, grant text, anything under the hub's rule that manuscript content is never written by a raw agent and a `.tex` is never hand-edited; verification is the PDF build and whatever the brief names; landing is the same cherry-pick. `inline`: bookkeeping the orchestrator does itself with Write and Edit, no agent. A package may name its own executor in the brief; the block gives the default.

**The workflow, in order, one package at a time.** Read the state file, then the ledger, then the tail of the transcript. Pick the next unblocked package. Write its brief from `spec.md` and the ledger; every count, path, name or claim in the brief is checked on the tree with a grep or a probe before dispatch, and a premise found wrong is corrected in the brief, never left for the agent. Create the worktree at main's head, by the orchestrator, never by the Agent tool's own isolation (`git worktree add -b <package> .claude/worktrees/<package> HEAD`, then `git -C .claude/worktrees/<package> sparse-checkout set <worktree_paths>` when the block names any). Dispatch one agent with the worktree path, the spec and the brief; the agent never runs git and never edits the ledger folder. While it runs, the orchestrator does ledger work only: the next brief, bookings, the usage table. On the report: read the whole diff; the report is a lead, not a fact. Run the `verify` commands in the worktree. Land: in the worktree `git add -A && git commit -q -m wip`; on main `git cherry-pick -n <package>`; a conflict is resolved on main by the orchestrator with Edit, never by an agent on main. Run `verify` again on main. Book the package in `plan.md`. Commit by explicit path from `git diff --cached --name-only`, in the user's message shape (capitalised imperative subject, blank line, `- Verb ...` bullets, the last bullet the plan booking), with no attribution of any kind, never push. `git status --short` is empty after it. Remove the worktree and the branch. Rewrite the state file.

**Rewind.** The orchestrator's own edits go through Write and Edit only, so `/rewind` covers them; the shell never writes, moves or deletes a file. An agent's edits and a commit are outside `/rewind`; the worktree and the cherry-pick are the substitute, and one package is one commit so undoing a package is `git revert` of one commit.

**Stops.** The turn ends only when nothing unblocked is left. The only stops put to the user: a user-visible shape the ledger does not name, a premise found wrong that the plan cannot absorb, a red check no fix within the plan covers, a contradiction between two established rules or decisions; each in one message with one recommendation.

**Reports**, from the orchestrator to the user after a package and from an agent to the orchestrator: anything NOT DONE first, then a DONE / NOT DONE ledger naming the command that proves each row; no narration of wrong turns; no measurement stated that was not taken.

**Usage.** Per package, the agent's tokens, tool uses and duration go into a table in the state file.

**Sharing.** The skill carries no project name. A repository adopts it by creating a ledger folder from the templates; installing the skill at `~/.claude/skills/plan-orchestration` makes it available in every repository. Say this in one paragraph at the end of `SKILL.md`.

## What the templates must contain

`plan.md`: the header paragraph naming the checkmark rule and the state-file-first rule, an empty "Packages, in execution order" list with one example line, the three trailing sections. `orchestrator-state.md`: the configuration block above, then the four sections of the worked example ("The standing demands", "Verification, every package", "Where things are", "Current position") with placeholders. `spec.md`: the worked example's structure (read first, where you work, what every package obeys, verify before you report, report) with the project-specific lines turned into placeholders. `brief.md`: package name, read-first list, deliverable, verification with expected output, report shape.

## Conventions

ASCII only in every file, including the templates (the checkmark appears in `SKILL.md` and `templates/plan.md` only as the words "green checkmark", never the glyph). One continuous line per paragraph or bullet; no hard wrapping. Plain prose; no quips. No project name anywhere in the skill or the templates: not cathedra, not oculus, not the cockpit, not curia; the worked example is referenced by its path in this brief, not in the skill.
