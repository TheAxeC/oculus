## The rule the step ends

Since O82, a Live HPC poll in which ssh connects and any one of `squeue`, `sacct` and `sinfo` exits with a code other than 0 is published as `slurm_down` over the last good rows. When `squeue` answers and only `sacct` (the Recent table) or `sinfo` (the Capacity table) fails, as when Slurm's accounting database is down while the controller answers, the whole view freezes: the queue, Recent and Capacity stay as the last good poll left them, Recover stops reading the cluster (a download's bytes, rate and end freeze), the log prewarm stops, and a server started during such an outage shows no queue. Ruling 430 keeps the queue and Recover's reading live from that poll and keeps only the failed table, marked as stale with its own time; the status stays `slurm_down` with the failing command's message. Ruling 432 fixes the payload's `stale`, the view and the words, and keeps the mark on a table through later failed polls while the table is older than the queue. Ruling 433 (`choices.md` Z1028) has the payload say its queue is this poll's by `lastOk` equal to `updated`. All three are in `plan.md` Rulings.

## What to build

1. **The poll tells a partial answer apart (`poll.ts`).** A poll's answer is partial when ssh connected (the marker), ssh did not exit 255, `squeue`'s code is 0, and `sacct`'s or `sinfo`'s code is not 0. On a partial answer, after the checks that drop an answer for a closed watcher or a superseded host or window (`stopped() || began !== asking`), as on a good poll:
   - `jobs`, `running`, `pending` and `total` are this poll's, read from its `squeue` section, and `options.recover?.take(parts.recover, jobs)` is called;
   - a table whose command answered (code 0) is this poll's; a table whose command failed keeps the rows of the last poll in which that command answered (decision 1);
   - `lastOk` is this poll's time, and the payload's `updated` is that same time (ruling 433);
   - the published status is `slurm_down`, its hint the failing commands' message as `slurmHint` gives it over `sacct` and `sinfo` (the time-limit sentence when `timeout` stopped the first failing one, else the first stderr line that is not empty, else the time-limit sentence when `timeout` stopped any);
   - the payload carries `stale` (item 2);
   - the next poll is at `RETRY_MIN`, as after any failure;
   - the prewarm runs when this poll's `sacct` answered, against this poll's Recent rows, as after a good poll; with `sacct` failed it does not run.
   The watcher keeps the time of each table's rows beside the rows. A good poll sets every table and its time, and `lastOk`. A failure that is not partial (ssh not connecting, `squeue` failing, ssh breaking, a runner rejection) publishes as O82 does, over the rows as they stand, with its own `updated`, later than `lastOk`, and with `stale` as item 2 gives it. A change of the host, of the sentence for having none or of `unconfigured` drops the tables' times with the rows. A window change (`days`) keeps the rows and their times (decision 3). The doc comments premise 2 names are rewritten to say what the code now does.
2. **The payload's `stale` (`model-sessions.ts`, `payloads.ts`, `docs/apps.md`), as ruling 432 fixes it.** `HpcPayload` gains `stale?: { recent?: string | null; sinfo?: string | null }`, with a doc comment saying: present on a failed poll whose Recent or Capacity table is older than its queue, which is a poll whose `squeue` answered and whose `sacct` or `sinfo` did not, and every later failed poll while a table kept so is still older than the queue; it names each such table with the time (ISO) of the poll its rows came from, or `null` when no poll has answered for that table since the server started (its rows then empty). A payload of a good poll, of `starting`, of `unconfigured`, and of a failed poll whose tables are as old as its queue carries no `stale`. The doc of `lastOk` (`:668`) says it is the time the cluster last answered for the queue, and that a payload whose `lastOk` equals `updated` has this poll's queue (ruling 433). `hpcShape` reads `stale` as an optional object of those two optional keys, each a string or null, so a payload with a well-formed `stale` passes unchanged, one without it passes as before, and one with a malformed `stale` (`stale: 'x'`, `stale: { recent: 5 }`) is refused as `hpcShape` refuses a malformed key. The `hpc` row of `docs/apps.md:421` names `stale?` after `lastOk?`, and its parenthesis says, in place of "each with the last good rows": each failed poll carries the last rows; a `slurm_down` poll whose `lastOk` equals `updated` has this poll's queue; `stale` names each table older than the queue with the time its rows came from.

## Decisions taken in this brief (each reversible, none silent)

1. A table whose command failed keeps the rows, and the time, of the last poll in which that command answered, which can be a partial poll (cases 6 and 7); ruling 430's "the last good poll" is read for each table.
2. A runner rejection stays as O82 reads it: the runner's 40 s is past the three commands' 25 s, so a rejection after `squeue` answered means ssh or the remote shell hung, not one Slurm table, and the whole poll is `slurm_down` or `error` as now (case 13).
3. A window change keeps the Recent rows and their time, as a failed poll keeps them on the base; the mark then says how old they are (case 12).
4. While a failed payload's queue is this poll's, the head bar's refresh control stays hidden, as for every failure, since the error box under it holds the retry.
5. Login gets no reason while a failed payload's queue is this poll's, since the login node answered.
6. A table `stale` names is drawn with no rows, its heading at a count of 0 ("Recent (finished) - 0", "Cluster capacity (0 partitions)"), so its mark shows.
7. The only test is G115's row (item 7); the rules file's test rule calls for no other, since no entry of `agents/guarded.md` covers the poll's status or the view.
