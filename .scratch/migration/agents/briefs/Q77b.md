## Library check

The capability is a flag of a test tool and a comparison of case texts between two folders. Parsing the case's extent is covered by `typescript`, already a dependency (premise 4); the flag is read by the loop `readArgs()` already has. No new dependency; none is named.

## What to build

1. **`--base <dir>`.** revert-check takes a second optional flag, `--base <dir>`: a folder holding the tree the change starts from (a worktree or a checkout of the base commit), which revert-check reads and never runs, copies or writes. `--base` with no folder after it, or naming a path that is not a folder, prints the usage (which now shows `[--base <dir>]`) and exits 2. Paths in the file list and in directives are read in the base folder at the same relative path as under the root.
2. **A directive unchanged from the base is not proven again.** With `--base`, a directive is left out of the run when all of these hold, and proven exactly as today otherwise:
   - the base folder holds the test file and the directive's target file;
   - the target file's text is the same string in both;
   - the test file holds exactly one case of the directive's case name in each folder, and that case's text is the same string in both. A case's text is the whole call statement that opens with `it(` or `test(` (with its modifiers, such as `it.each(...)` or `test.skip`), found by parsing the file with `typescript` (`ts.createSourceFile`, the script kind from the extension), with its leading comments included (`getFullText()` of the statement), so a directive written above the case and every directive inside it are part of the case's text;
   - the test file's text with the text of every case removed is the same string in both, so a change to an import, a helper, a hook or a `describe` around the cases proves every directive of the file again.
   A test file that fails to parse, and a case the parser does not find, are proven as today. The comparison lives in a new module `bin/revert-check/base.mjs` with a Layer 4 head comment in the tree's form saying what it is and why; `directives.mjs` and the two proving paths are unchanged in what they do.
3. **The output.** A directive left out prints `unchanged <file> :: <case> (revert <target>:<first>)`, the same `whereOf()` text the other lines carry, in the place it has in the order of directives. With `--base`, a case with no directive is listed as `unchecked` only when it is not unchanged from the base by the case-text and outside-the-cases rules of item 2 (its test file present in the base, one case of its name in each folder with the same text, the rest of the file the same); the summary line is `<n> reverts, <n> unproven, <n> unchecked, <n> unchanged`, where `<n> reverts` counts every directive found, `<n> unproven` and `<n> unchecked` only what this run proved or listed, and `<n> unchanged` the directives left out. Without `--base`, every line, the summary and the exit status are word for word today's. The exit status stays 0 only when unproven and unchecked are both 0.
4. **The head comment** of `bin/revert-check/revert-check.mjs` states the flag, what is left out and why (a directive whose case, whose file around its cases and whose target are unchanged was proven on the base), and what the rule does not see: a change to a module the case imports other than the target leaves the directive out all the same. The usage lines there and in `main()` show `[--base <dir>]`. No history.
5. **Tests** in a new `tests/checks/bin/revert-base.test.ts`, over the fixture project of `revert-fixture.ts` (helpers added there as needed), each case making a root fixture and a base fixture, running the check with `--base`, and asserting the line and the summary; `sweepFixtures()` after each case. Each case carries its revert directive in the tree's form, red under its revert:
   - a directive whose case, file and target are the same in both, and whose revert leaves its case green: the line is `unchanged`, the summary `1 reverts, 0 unproven, 0 unchecked, 1 unchanged`, exit 0 (the same fixture without `--base` prints `GREEN` and exits 1, which proves the directive was not run);
   - the target changed in the root: the directive is proven (`red`);
   - the case's body changed: proven;
   - a line outside every case (an import or a helper) changed: every directive of the file proven;
   - a directive added to an unchanged case: proven, since the case's text differs;
   - the test file or the target missing from the base: proven;
   - two cases of one name: proven;
   - an unchanged case with no directive is not listed and a new case with no directive is `unchecked`;
   - `--base` alone, and `--base` naming a file: the usage and exit 2;
   - a test file the parser cannot read: proven as today.

## Decisions taken in this brief (each reversible, none silent)

1. The rule compares text, not results: a directive is left out when what decides its run (its case, the file around its cases, its target) is the same string in the base, since a directive on main was proven at its landing. Nothing is cached or written.
2. The word for a directive left out is `unchanged`, printed so the reader sees every directive of the file named, and the summary gains `, <n> unchanged` only under `--base`, so output without the flag is unchanged for every caller.
3. The case's extent comes from the TypeScript parser already in the tree rather than from brace counting, since a case holds strings, templates and regular expressions a brace count misreads.
4. The comparison is its own module, `bin/revert-check/base.mjs`, and its tests their own file, since `revert-check.test.ts` is near the size limit.
