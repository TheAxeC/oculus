## What to build

Ruling 440 (a), widened by ruling 444 (a): a Settings row of a key of the hub list that each hub's own `config.yml` is read for names the hub it writes, the primary first and chosen, as Add does; it shows that hub's value; and its write, its list or family write, its Reset and their Undo land in that hub's `.oculus/config.yml`. The 37 such keys are the per-hub list above. The 12 keys read from the primary alone keep writing the primary's file with no hub choice.

1. **The per-hub keys, named once.** The set of the 37 keys read from each hub's own file is defined once, in a new file under `src/lib/data/shapes/`, and the page and the server both read it. The 12 others are the rest of `HUB_LIST`. `hub-names.ts` stays unchanged (O79 and O81 share it and it is near its size limit).
2. **The write names its hub.** The bodies of the config key write, the value write (the list or family write included) and the reset take an optional hub name, `root`, as `new-entry` does. The server places the write in that hub's `.oculus/config.yml`, the hub folder taken from the open workspace's hubs.
   - A body with no `root` writes the primary, as now. A `root` naming the primary is the same write as a body with no `root`, recorded and undone alike.
   - A `root` that is empty, holds path characters, or names no hub of the open workspace is refused with `server.workspace.no_hub_named`, and no file or folder is created. The primary's file and folder are created as now; a second hub is a hub only while its `.oculus/config.yml` exists, so a write never creates one.
   - A `root` other than the primary's on one of the 12 keys is refused with a new sentence of the text catalog that says the key is read from the primary hub alone, and no file is touched.
   - With a `root` naming a hub, a workspace with no primary writes that hub.
   - The values of `folder` and `file` controls are checked under the named hub's folder, and with a `root` and no primary they are not refused with `no_primary` (`sourcesOf` and `config-fit.ts`).
   - B's file that does not parse refuses the write with the sentence the primary's gets now (`not_parsed`). The `local.yml` refusals hold for every hub's file. The "changed since it was read" refusal holds for every hub's file.
   - Every write is logged and undoable in History as the primary's are: `recordLayers` in `undo.ts` finds the layers of the hub whose file the record names, among the open workspace's hubs. Undo of a record whose file changed since is refused as for the primary; of a record whose hub left the workspace, refused as gone. Its doc comment says so.
3. **The page sends it.** `writeConfigKey`, `writeConfigValue` and `resetConfig` of the client writes store, their types in `shapes.ts` and `WriteConfigValue` in `editors/writer.ts` take the hub and put it in the body. The unsaved-text guard (`write-files.ts:120`) names the chosen hub's `.oculus/config.yml`, so a write to B while a source tab holds unsaved text of B's file is refused before sending. `writes.svelte.ts` is 867 lines and `src/lib/state/client` holds 10 items: a change that takes the file past 880 lines moves the three config writes (lines 560-630) into `src/lib/state/system/config/editors/config-writes.ts`, beside the editors that call them, and leaves the lines around 435 in place, where O79 changes a comment.
4. **The row offers the hub.** In a workspace of more than one hub, each row of one of the 37 keys draws a hub choice inside `Item.svelte`, listing the workspace's hubs, the primary first (`hubList`), with the hub chosen first by `chosenHub`: the primary when there is one, none when there is no primary. While no hub is chosen the row's control writes nothing and says a hub must be picked. In a workspace of one hub the row draws no choice and writes that hub, primary or not. A row of one of the 12 keys draws no choice. The chosen hub is kept per row while the view is open and is not saved; when the chosen hub leaves the workspace or is renamed, the choice falls back to `chosenHub` of the new `hubList`. The row's write state (`write.ts`) is keyed by the row and the hub, so an answer or a refusal for A is not shown with B chosen, and a list or family draft made with one hub chosen is neither ended by a push of the other hub's value nor applied to it.
5. **The row shows the chosen hub's value.** With a hub other than the primary chosen, the row's value in force, its oculus value for the Modified bar, and its option's default are B's as B's merge gives them (the pruning of a word B removes, and of one the primary removes but B keeps, included). The page gets them from a read the Settings view alone makes: a GET route `src/routes/api/(docs)/hub-settings/+server.ts`, its handler in `src/lib/server/files/source/hub-settings.ts`, answering for a hub name of the open workspace the slice of `locals.server.configCache.hub(dir)` the rows of the 37 keys read (their merged values, their catalog entries with their defaults as B's merge left them, and `from` for them) and refusing any other name with `no_hub_named`. The row's `own` and the line of its key are read from B's `.oculus/config.yml`, read as `hub-file.ts` reads the primary's, in B's root, and its link to the key's line opens B's file. After a write to B, the config push makes Settings read B again (the route and B's file), so the row's `own` and line move. A file of B that is being read or does not parse makes the row say so, as the primary's does, and write nothing. The pickers of `folder` and `file` controls and the collection keys `chat_context` offers list B's (`editors/sources.ts`). The group's line for the hub's settings file stays the primary's. No field is added to the `config` channel or to any other channel apps read; the route is not reachable from an app (`CLOSED_WRITES` already closes the three write kinds to apps, `src/lib/server/edit/writes/apps/gate.ts:113-116`).
6. **Words.** Every new sentence the page or the server shows is a key of the text catalog under `config/text/`, in the file of its view (`config/text/views/system/workbench.yml`) or of the server (`config/text/server.yml`, under `server.workspace.*` beside `no_primary`).
7. **Tests.** The cases below that the rules file's test rule calls a test for are tests in the existing files of G8, G9, G28 and G96 named above, or in one new file `tests/state/system/settings/chosen-hub.test.ts`. The builder does not edit `agents/guarded.md`: the report names each new test by file and title and the entry it belongs to, and the orchestrator writes the titles into those entries at landing.
8. **Comments and the schema description.** The doc comment of `recordLayers`, the head comments of `writes.ts:29` and `write-files.ts:17-19`, the schema description at `workspace-file.ts:55`, and every comment of a file the step changes that says a key of the hub list is written to the primary's file (on main: `config-place.ts:4`, `config-reset.ts:5`, `rows.ts:6,65,357`, `writes.svelte.ts:612`, `Settings.svelte:25,31,167`, found by check 8 of "Verify before you report") say where a key of the hub list is written: the hub the write names, the primary when it names none, for a key read from each hub's own file.
9. **Doc text.** `docs/HELP.md` and `docs/data-map.md` are kept out of the step's paths because O79 changes them: the report's "Doc text" section gives each current line as `grep -n` prints it and its replacement, applied at landing.
   - `docs/HELP.md:325`: its sentence "A key of the hub's list is written to the primary hub's `.oculus/config.yml`" becomes one that says a key each hub's own file is read for is written to the `.oculus/config.yml` of the hub the row names, and any other key of the hub's list to the primary's.
   - `docs/HELP.md:527`: its sentence on where Settings writes a hub's words becomes one that says a row of a key each hub's own file is read for names the hub it writes, the primary first and chosen, in a workspace of more than one hub, and writes that hub's `.oculus/config.yml`; the keys read from the primary alone write the primary's.
