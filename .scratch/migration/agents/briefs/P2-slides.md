## What is on the tree (written 2026-09-15 at 17:00 against 07322c5c; re-read at dispatch)

- The deck: `state/present.ts` `deckFrom` reads `deck.selection` and `deck.slide_order` (lines 305 and 306) and `deckSlides` applies them (lines 388 to 437): a saved selection is the shown list, a saved order the positions, a key the deck no longer holds places nothing; `slideKey` (line 112) is the key vocabulary: a project slide's own id (`hccnet-revision`, `hccnet-revision/data`), a deck slide's kind or `kind:ref` (`title`, `framing:engine`, `summary:summary1`). - The Present view holds its position in the instance state as `{ slide, overview }` (`parsePresentState`, `state/present.ts` line 106; `views/Present.svelte`), so `openView('present', { slide: '<key>' })` opens the deck at that slide. The store answers `slides()`, `current(key)`, `position(key)`, `slideOf`, `projectOf`.
- The writes: `POST /api/write` (`routes/api/write/+server.ts`) hands the body to `server/writes.ts` `handleWrite(request, token, target())`, which dispatches on the body's kind (manifest, session, entry, subtask, host, feed, ...); the client side is `state/writes.svelte.ts` (`send(fields, path)` behind the token, one method per kind). - The project view (`views/Project.svelte`) draws the project's markdown documents in a `Segment` (`names` at line 60 from `item.project.docs`, `docFor(id, chosen)` through `api/docs`), one chosen at a time, the choice in the instance state.
- The cockpit: the Slides dialog lists every slide of the catalog in order (drag handle, position number, checkbox, title, up and down buttons), Save posts `{ selected, revision, order }` to `/__slides`, a stale revision (the file changed since it was read) is refused, an empty selection is refused, the file is rewritten with `selection_text` (the two lists replaced in place, everything else byte-identical), then `build.py` regenerates `present.html`; the words are `slides.title`, `slides.intro`, `slides.save`, `slides.drag`, `slides.up`, `slides.down`, `slides.moved`, `slides.saving`, `slides.saved`, `slides.stale`, `slides.failed`, `slides.empty`, `slides.loading` in `tools/cockpit/data/config/text.yml`, and the opener is the `presentation.button` "Slides" beside the cockpit's Present link. ## The acceptance list

1. **The Slides view** (`views/Slides.svelte`, registered `slides`, `listed: false`, one instance): every slide of the deck as the reader would see it, in the order `deckSlides` would place them with no selection applied (the catalog: `deckSlides` over a deck whose `selection` is null and whose `slideOrder` is the saved one), one row per slide with its position number, a checkbox (checked when the saved selection holds the key, or when there is no saved selection and the slide is placed), its plain title and its kind, a drag handle for reordering and an up and a down control (the cockpit has all three); a Save control writing the selection and the order; a status line saying moved, saving, saved, refused. An empty selection is refused in the view before any write. Escape does nothing special (it is a tab, not a dialog). The view is opened from the Present view's toolbar by a "Slides" control (`openBeside('slides')`), the cockpit's opener beside its Present link.
2. **The write.** `POST /api/write` gains the kind `deck`: `{ kind: 'deck', selection: string[], order: string[] }`; the server checks every key against the catalog it computes itself (the snapshot's slide ids plus the deck's own keys), refuses an empty selection, a key it does not know, a repeated key, or an order that is not a permutation of the catalog (answers 400 with `{ error: 'invalid' | 'invalid_order' }`), then rewrites `config/present.yml` in place: the two lists `selection:` and `slide_order:` under `deck:` replaced or appended as `deck_config.py`'s `selection_text` does, every other byte of the file kept (a text edit, not a YAML dump; `server/deck-edit.ts`, pure, tested on a file with comments before, between and after the two keys, and on a file holding neither). The answer is `{ ok: true, changed: ['deck'], refused: [] }` in the shape every write answers. No build step: the deck is live (Axel's ruling of 2026-09-12 21:45).
3. **The Present control on the card.** `views/shared/ProjectCard.svelte` gains a control in its list, drawn only for a project that carries a slide (`item.project.present` non-empty), opening the deck at the project's own slide: `openBeside('present', { slide: <the project's first slide id> })`; the words `project.card.present` and its tip in `config/text/views/project.yml`, the glyph `project.card.present_glyph`.
4. **The PRESENT.md body in the project view.** `views/Project.svelte`'s document segment offers `PRESENT.md` when the project folder holds one (the presence is already read by `data/sources/docs.ts` `projectDocs`; ruling (f) dropped it from the card's row, and Axel's line for P2 puts its body in the project view), drawing the body through `api/docs` with the front matter stripped (`splitFrontmatter` of `data/sources/docs.ts`), as the cockpit's helper did at line 71.
5. **Words**: `config/text/views/slides.yml` (a new owner file) for the view; DESIGN.md's views list and one dated decision line; the key sheet unchanged.
6. **Tests**: `tests/server/deck-edit.test.ts` (the text edit: replace, append, comments kept, byte-identical elsewhere, the flow-style list case), `tests/routes/write.test.ts` or the writes suite (the `deck` kind: the four refusals and the write landing in a temp engine dir), `tests/state/slides.test.ts` if a pure catalog helper is added, `tests/views/slides.test.ts` (the rows, the checked state with and without a saved selection, the status line), `tests/views/project.test.ts` (PRESENT.md offered, its body drawn without the front matter), the card test (the control drawn only with a slide), `tests/views/registry.test.ts`, `tests/browser/present.spec.ts` (open Slides from the deck's toolbar, uncheck one slide, move one, save, the deck's slide list reflects both after the push).

## Decisions taken in this brief (each reversible, none silent)

1. The Slides view is a tab, not a dialog: oculus has no modal for content, and a tab beside the deck is what `openBeside` is for.
2. No revision check: the cockpit refused a save when the file changed since it was read; oculus pushes every change of the file to the view within a second, so the view always holds the file's current state and the write is atomic; a write racing an edit by hand is the last writer's. Reported as a difference.
3. The `deck` write edits the engine file as text, never through a YAML dump, so the deck's comments and layout stay as written.
4. The two saved lists live under `deck:` in `config/present.yml`, where P1 reads them (the cockpit's are top-level in its own file).
