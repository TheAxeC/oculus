## What to build

Ruling 441 (a): the tray offers each update task of every hub that holds its file under `.oculus/tasks/`, named by its hub when two hubs hold that task, the primary first; a schedule or a request runs the task of the hub it names.

1. **The tasks the hubs hold.** The schedule payload's `tasks` becomes the offered pairs `{ task, hub }`, `hub` the hub's name: ordered by task in the order of `UPDATE_TASKS`, and within one task by hub, the primary first, then the others in the folders' order. It is null only while the workspace holds no hub; with hubs and no file, it is empty. With no primary every hub's pairs are offered in the folders' order (ruling 460). The watcher watches the tasks folder, and the folder above it while that does not exist, of every hub of the open workspace, as it watches the primary's now, so a task file added or removed in any hub changes the payload without a reload; a change of the workspace's hubs rebuilds those watches. The watcher's options take the open workspace's hubs, read at each call, and the workspace subscription of `context.ts` (lines 800-813) tells the watcher when the hubs change, whether or not the primary moved: a hub added brings its pairs and its watches, a hub taken out takes them away, and every row is checked again against the hubs as they then stand. `watch.ts` is 849 lines: what the step adds there that takes it past 880 moves into a new file of `src/lib/server/machine/runs/schedules/` (6 items).
2. **A press runs the task of its hub.** The request body takes an optional `root`, the hub's name, as `new-entry` and the config writes do. No `root` is the primary, refused `no-primary` with no primary as now. A `root` naming a hub of the open workspace starts the task in that hub's folder; a `root` naming the primary is the same start as no `root`. A `root` that is not text is `bad-terminal`; a `root` that is empty or names no hub of the open workspace is refused with a new terminal refusal `hub-unknown`, naming the value, and nothing starts. A hub that lacks the file is `task-file-missing`, whose names now hold the file and the hub's name, and its sentence names the hub. `terminalSentence` (`terminal-words.ts`) gains the case `hub-unknown` and passes the hub's name to `task-file-missing`'s sentence. `startUpdateTask` takes the hub's folder and name; `startTask` of the page takes the hub's name and sends it as `root`.
3. **A schedule runs the task of its hub (ruling 458).** `runs` of a task takes `hub:` beside `task:` (`RUNS_KEYS.task` gains `hub`). Absent, the task is the primary's. A value that is not text, or text that is empty or only white space, is the problem `hub-wrong`, naming the value as written; a hand-written `hub: 2026` reads as a number and is `hub-wrong` naming 2026. A name is compared with the hubs' names exactly as written, with no trimming and no change of case. A name that no hub of the open workspace holds is the problem `hub-unknown`, found by the disk checks (`file.ts`), whose `Disk` gains the open workspace's hub names. Like every row with a problem, such a row says it, has no job and no next time, and Run now refuses it before writing the record (`watch.ts:670`, `784-786`); once the hub is back, the problem clears and the job and next time return. The save route checks the same way: `checkSave` gets the hub names through its options (`+server.ts` passes them, as the fixture `routeOptions` does), so a save of an entry naming no hub is refused `hub-unknown` and writes nothing, as any disk problem is now. `runEntry` given an entry whose hub is not among the hubs at the call, a hub taken out after the row was checked, refuses `hub-unknown` and starts nothing. `hub:` beside `command:` or `prompt:` is `key-unknown` as any other key. `runEntry` starts the task in the hub its entry names: its options take the open workspace's hubs read at the call, and `context.ts` passes them. A schedule names its hub by name, so a hub moved on the disk keeps its schedules. A schedule still lives in the primary's `schedules.yml`: with no primary, no schedule exists and a save is refused as now.
4. **The tray's rows.** One row per offered pair. A row's label is the task's label, written `{0} ({1})` with the hub's name by a new catalog key `app.tasks.in_hub` when two or more hubs hold that task, and the task's label alone otherwise. The rows are keyed by task and hub, and the pressed row alone turns its glyph while its start runs. Its press sends the pair's hub. Its "Schedule" opens the dialog with the pair chosen and the row's label as the name. Its next-run cell names the next run of the schedules that run this task in this hub (no `hub:` is the primary's). The line in place of the rows says that no hub holds a task file when the payload's list is empty, and that the workspace holds no hub when it is null; `app.tasks.no_files` and `app.tasks.no_primary` are reworded for that, the second renamed `app.tasks.no_hub`.
5. **The dialog.** The Task box offers the offered pairs, each labelled as its tray row; a new draft (from "New", from a command switched to Task, or from a tray row) takes the pair it was opened with, else the first offered pair, and with none offered the Task box is empty and its line says no hub holds a task file, so no task can be saved. A save of a pair whose hub is the primary writes `runs: { task: <task> }`, and of any other hub `runs: { task: <task>, hub: <name> }`, the name written so that the file reads back the same text (quoted where YAML would read it as another type), which the write's reparse check holds. An entry opened whose pair is not offered keeps that pair chosen, labelled with its hub, so a save never moves it silently: one whose hub holds no file saves as it is, and one whose hub names no hub of the workspace is refused `hub-unknown` by the save route until another pair is chosen. An entry whose `hub:` is `hub-wrong` opens with its hub unchosen (`UnchosenKey` gains `hub`, and `unchosenKeys` names it), and a save writes the pair chosen. A schedule row's "what" (`whatOf`) is the pair's label, named by its hub whenever the entry names a hub other than the primary.
6. **Each hub's last run (ruling 459).** The feeds summary the wire carries, `Feeds`, gains the required field `byHub`, and a hub's own feeds as read, `RawFeeds`, become the four keys without it, so `sources/documents/feeds.ts`, `data/index.ts` and `normalise.ts`'s `feeds` read and give `RawFeeds`, and `NO_FEEDS` and any other fixture of the summary carry `byHub`. `byHub` is one row `{ hub, radar, scout, linkedin }` per hub of the merge, in the merge's order, each with the shape the merged summary has (`{ lastRun }`, `{ lastPost }` or null), built in `feedsOf` from each part's own feeds; the merged `radar`, `scout` and `linkedin` stay as they are for their present readers. A folder of a workspace with no primary is a part with no hub (`folderParts`, `build.ts:106-117`); its part gives no row. The tray's last-run cell of a pair reads the pair's hub's row; the Inbox row of every hub reads `notesRun`, the one triage date of the machine. `docs/apps.md:411` names `byHub` with its row shape.
7. **The Focus board's refresh lines.** `refresh` takes the offered pairs and gives one line per offered pair whose own hub's feed is stale by the rules it has now (the radar nudges with no run date; `refresh_stale_days` from the page's configuration as now), the inbox once, as its date is the machine's. A line names its task as the tray row names it, for Lit Watch and Scout alike: `refresh_litwatch_plain` and `refresh_scout_plain` take the label as a placeholder in place of their fixed task names. `CommandCenter.svelte` passes the pairs and draws the label.
8. **The "updated" notice.** A notice is posted for each pair whose hub's run date is one the channel has not shown before, keyed by task, hub and date, said with the pair's label as the tray names it, and opening the task's view as now. A hub with no file of the task posts no notice for it. The pairs are read from the `schedule` channel the notices already hear. The inbox keeps its one key.
9. **Words.** Every new or changed sentence is a key of the text catalog: `app.tasks.in_hub`, `app.tasks.no_files`, `app.tasks.no_hub` and the two schedule problems in `config/text/app.yml`; `refresh_litwatch_plain` and `refresh_scout_plain` in `config/text/views/boards/focus.yml`; `refused_hub_unknown` and the reworded `refused_task_file_missing` in `config/text/views/sessions/terminal.yml`. A sentence the page shows for a refusal names the hub by its name.
10. **Tests.** The cases below that the rules file's test rule calls a test for are rows of the existing tests of G35 (`tests/routes/sessions/terminal-actions.test.ts`, the task describe for a start, the refusal table 'POST /api/terminal, a refusal' for a refusal) and G46 (`tests/server/machine/runs/schedules/run.test.ts`, describe 'runEntry'). The builder does not edit `agents/guarded.md`: the report names each new test by file and title and the entry it belongs to, and the orchestrator writes the titles into those entries at landing. Every other case is a run the report quotes, and a case only a page shows is checked by reading and by the unit-level runs that reach it, its row in the report naming the look on landing (`spec.md`, "What every package obeys"). The fixtures `worldOf` and `world()` gain a second hub for the cases that need one. Existing tests that build the payload's `tasks`, the feeds summary or the task request are updated to the new shapes, each changed line listed in the report's table.
11. **Comments.** The head comments of `task.ts`, `watch.ts` (line 6 and the task-file watch at 742), `run.ts` (`RunEntryOptions.hub`), `schedules.ts` (the `runs` keys), `UpdateTray.svelte`, `feeds.ts` (`refresh`'s doc comment), `notice-sources.ts`, the `tasks` doc of `SchedulePayload`, the doc of `offered` in the store type (`schedule.svelte.ts:144`) and the `Feeds` doc say what the code now does: a task is a file of any hub, and the run is in the hub it names.

   - `docs/HELP.md:105`: a task is a file of a hub; the tray offers the task of every hub that holds the file, named by its hub when two hubs hold it, the primary first, and a workspace with no primary offers them too.
