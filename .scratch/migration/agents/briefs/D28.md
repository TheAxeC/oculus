## What to build

When the step is done: a source tab learns of every change of its file on disk within a second; a tab with no unsaved text takes the new text with its caret and scroll kept; a tab with unsaved text keeps it, says the file changed, and its Save is refused by the server with Compare, Overwrite and Revert; `editor.autosave` saves after a delay or on a focus change, `off` by default; two keys per language trim trailing whitespace and end the file with one newline, off by default; and the server refuses to replace a file that is not UTF-8 throughout, keeping a BOM the file starts with.

### 1. A file changed on disk under an open tab (part 1)

1.1 The draft knows what it read. `SourceDraft` gains `base: string` (the hex SHA-256 of the bytes the tab last read or wrote, the empty string for an untitled text or a tab at HEAD or in the index) and `disk: 'same' | 'changed' | 'gone'`, both in `draftShape` with `catch` defaults (`''`, `'same'`). `loadSource` reads the bytes with `readCappedBytes` (`fs-transport.ts:380`), computes `base` over exactly those bytes with the digest `readHash` uses, taken out of `readHash` into one helper both call, and decodes them as today. A truncated read keeps the base of its bytes and still saves nothing.

1.2 The server says when an open file changes (C1 (a), Z528 and Z713 (1)). A channel per open file, `source:<root>/<path>`, its payload `{ hash: string | null }`: the hex SHA-256 of the file's bytes, or null when nothing readable is there (deleted, a folder, unreadable).
- A new server module `src/lib/server/files/fs/open-files.ts` (Layer 2 server; `server/files/fs/` holds 9 items, so this is its tenth) is the socket's sink for `source:` channels, as the terminals are for `pty:` channels: `socket.ts`'s options gain `openFiles` beside `terminals` (:75-76), its subscribe branch (:177-188) also calls `options.openFiles?.subscribed(sink, subscription.channels)`, and its close calls `options.openFiles?.remove(sink)`; `source:` channels stay among the hub's plain channels, so `hub.publish` delivers to each sink and a new subscriber gets the latest message. `ServerContext` (`server/root/process/server-context.ts`) gains `openFiles`, `attachAtWs` (`serve.ts:21-27`) passes it, and `server/root/context.ts` makes it beside the git watcher (`const git` :386) and closes it in `close()` (:496-521), and in the rebuild path (`starters` :525-550) when that path rebuilds what it reads.
- A subscribed name is resolved with `resolveRootPath` over the browser roots (the source route's roots); a name that does not resolve inside a root is never polled and never published. A resolved file is polled with `pollFile` (`POLL`, the server's clock); on each move the name is resolved again before any read (Z714 (2)), and a name that no longer resolves inside a root (a link now pointing out, a root key renamed or dropped from `sources.yml`) publishes null and reads nothing; otherwise it reads the file, hashes it with `node:crypto` and publishes the hash. A file over `TEXT_LIMIT` (2 MB, `data/file-ops.ts:32`) is not read: its message is the hash of its stat signature (inode, size, mtime, ctime), prefixed `stat:` (Z714 (4)). The first publish is at the first tick.
- The poll ends when no socket holds the channel (Z714 (3)): the page's `unsubscribe` (`socket.svelte.ts:238`) sends `{ type: 'unsubscribe', channels }` for the `source:` names it drops, the server's socket hands it to `openFiles` and to the hub, and a closed socket drops all its channels as today; when a channel's last sink goes, its poll closes and the hub forgets the channel's latest message (a `forget(channel)` on the hub, `channels.ts`), so a later subscriber is never handed a stale hash. The comment at `socket.svelte.ts:234-237` and `DESIGN.md:121` say so. The other channels keep today's behaviour.
- The number of polls is bounded: at most 200 `source:` channels per socket and 1,000 across the server, a subscribe past either bound being dropped for that name (Z714 (4)); a `source:` channel is a read channel, open to a socket without the token as every read channel is (`socket.ts:191-193`).
- `DESIGN.md:121` (the channel list) gains `source:<root>/<path>`, and `DESIGN.md:125` ("Watchers") the open-file poll and why it polls.
- The source store subscribes a tab's channel through the socket store's `subscribe` once its draft has loaded, listens with `listen`, and drops the listener and the name with `unsubscribe` when no open tab holds that file. Several tabs over one file share one channel. `createSource` gains the socket, which is made at `context.ts:286`.
- On a message for a file: a tab whose `base` equals the hash is `disk: 'same'` and nothing else moves; a null hash makes every tab over it `disk: 'gone'` with its text kept; another hash reads a tab with no unsaved text again (its text, `saved` and `base` from the new read, `disk: 'same'`) and makes a tab with unsaved text `disk: 'changed'` with its text kept. The read again keeps an edit typed while it was out, as `reloadSource` does now (:472-487), and hands the editor its edits (3.4).
- `reloadClean` keeps reading clean tabs at once after a Replace; the channel's message that follows finds the same hash and moves nothing.

1.3 The save carries the base and the server compares it.
- `SourceBody` gains `base?: string` (64 hex characters; any other value is a 400 with `root, path and content are required` widened to name `base`) and `create?: boolean`.
- `handleSource` reads the file's bytes once with the `stat` taken before the read. With a `base` that differs from the bytes' SHA-256, or a `base` and no file, it answers 409 `{ ok: false, error: 'changed', refused: [{ field: 'base', reason: 'changed' }] }` and writes nothing. Then it stats the file again and refuses `changed` when inode, size, mtime or ctime moved since the first stat, writing nothing and keeping no copy (DESIGN.md:515, a refused save leaves no copy). Then the history copy is made from the bytes read, through a new `keepBytes` beside `keepCopy` in `fs/history.ts` (`keepCopy` reads the file itself, `history.ts:132-160`, `readFileSync` :144, and its other callers `edit/writes/file-undo.ts`, `fs/replace.ts` and `fs/file-changes.ts` keep it), so the copy is the text the compare saw. Then the write. The `ok` answer carries `hash`, the SHA-256 of the bytes written.
- The hash and the BOM's keeping on write are `lsp-edit.ts`'s (`hashOf` :62-64, `BOM` :46, :73-80), taken out into one new server module under `server/core/` (8 items; `server/files/` holds 10) that `lsp-edit.ts` and `source.ts` both use. The whole-file UTF-8 rule lives in `text-kind.ts` (Part 4), used by both layers. `lsp-edit.ts` then refuses a file with a NUL byte anywhere, where today it refuses one only in the first 8 KB (Z714 (6)); nothing else of its behaviour changes.
- A body without `base` writes as today (Overwrite, the Timeline's Restore). A body with `create: true` and no file writes a new file when its folder exists inside the root (`resolveRootPath` of the parent is a directory), refuses `outside` as today for a path out of the root, and answers 404 `the file is not there` when the folder is gone; `create` over an existing file is the ordinary save with its base rule.
- The base of a draft restored from storage after a reload (Z714 (5)): an edited draft keeps the base it stored; an edited draft stored with no base (before this step) is marked `disk: 'changed'` when its file's hash is heard, so its Save shows the conflict; a clean draft takes the new read's base.
- A tab's saves run one at a time, each sending the hash the previous one answered, so the tab's own write never makes its next save a conflict; a channel message that arrives while the tab's save is in flight is held until the answer lands and is then compared with the answer's hash, so the tab's own write never draws `source.disk_changed`. After the socket reconnects, the first message of each channel is compared as any other: a clean tab takes the disk text within a second, a dirty one is marked changed only when the disk differs from its base.
- The tab's `saveSourceDraft` sends `base: draft.base` (or `create: true` and no base for a `disk: 'gone'` tab), sets `base` to the answer's `hash` and `disk` to `'same'` on `ok`, and on `changed` sets `disk: 'changed'` (or `'gone'` when the next channel message says so) and the line below.

1.4 What the tab draws (the lines in `save/`, the strip through the registration below).
- A tab with unsaved text and `disk: 'changed'`: the line under the editor `source.disk_changed`.
- A save refused `changed`: the line `source.save_conflict` with the file's name (VS Code's 16205), and three `ToolButton`s: Compare (`source.compare`), Overwrite (`source.overwrite`), Revert (`source.revert`).
