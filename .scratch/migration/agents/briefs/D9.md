## The shapes this brief sets (booked for Axel's ruling; built as written)

1. **Accounts and credentials.** `config/local.yml` gains `mail:` rows of the same shape as `calendars:` (`{ provider: google | microsoft, label }`, the label rule the same) and `mail_dir` (default `~/.oculus/mail`), one credential file per account, `<provider>-<label>.json`, the client half the reader writes and the `refresh_token` the connector writes. A mail account is its own consent with its own scopes and file; a calendar token never gains mail rights. The connector modules that both share move from `server/calendar/` to `server/connect/` (`oauth.ts`, `store.ts`, `api.ts`, `ConnectStates`) parameterised by a kind (`calendar | mail`) that selects the scopes and the folder; the calendar keeps its behaviour and its tests, with the imports moved. Scopes: Google `https://www.googleapis.com/auth/gmail.modify` and `https://www.googleapis.com/auth/gmail.send`; Microsoft `Mail.ReadWrite Mail.Send offline_access`; nothing wider.
2. **The poll.** `server/mail/poll.ts` with `watchCalendar`'s shape reads each account's plate by the skill's three signals ported exactly: Google `users.threads.list` with `q` `in:inbox is:unread`, `in:inbox label:todo`, `in:inbox has:nouserlabels`, each capped at 25, the union deduplicated by thread id, the unlabeled leg dropping a thread of more than one message or whose subject starts with `Re:`, `RE:`, `Fwd:`, `FW:`, and every leg dropping a thread whose newest message is `SENT` or in `TRASH`; each kept thread read with `format=metadata` for `From`, `Subject`, `Date`, the message count and the newest message's snippet; Microsoft the same three signals over `/me/mailFolders/inbox/messages` (`isRead eq false`; `categories/any(c: c eq 'todo')`; no categories, single-message conversations, the same subject rule), read with `$select` of sender, subject, receivedDateTime, bodyPreview, conversationId. `mail: { poll_min: 10, per_signal: 25 }` in `config/behavior.yml`, read by `mailSettings`. One complete state on the `inbox` channel: `InboxPayload { status, accounts, threads: InboxThread[], updated, pollMin, retryMin }`, `InboxThread { id: '<account key>-<thread id>', account, provider, sender, subject, received (ISO), age (the payload carries the time; the page draws the age), snippet, messages, url (the provider's own page for the thread), triage: { kind?, what?, draft?, triaged } }`. No body of a message is published beyond the snippet the provider gives.
3. **The triage notes.** The triage model (`kind`, `what`, `draft`, `triaged`) stays, held per thread in one machine-local file, `<mail_dir>/triage.json`, keyed by the thread's id, written by the page through `POST /api/mail { action: 'triage', thread, fields: { kind?, what?, draft?, triaged? } }` and by the `/research-cockpit inbox` skill, whose SKILL.md steps 3 and 4 are rewritten by you to write that file (the same three signals, the same words, one JSON object per thread id, `triaged` never set by the skill) instead of `feeds/inbox.yml`; the server watches the file and republishes on a change, and a note whose thread is no longer on the plate is dropped from the payload and kept in the file for thirty days. The file's path is `mail_dir`'s, so the served test run writes its own.
4. **Reply and archive.** `POST /api/mail { action: 'reply', thread, body }` sends a reply on the thread through the provider (Google `users.messages.send` with a raw RFC 2822 message carrying `In-Reply-To` and `References` of the newest message and the `threadId`; Microsoft `/me/messages/{id}/reply` with `comment`), never creating a draft at the provider; `{ action: 'archive', thread }` takes the thread off the inbox (Google `threads.modify` removing `INBOX`; Microsoft moving the messages to the `archive` folder); both refresh the poll after. The page sends a reply only from the card's draft editor through a confirmation naming the recipient and the account (`inbox.send_confirm`), and archive through a confirmation too; no other write to a mailbox exists. A send or archive that the provider refuses answers 400 with the status and the provider's code, drawn on the card.
5. **The view.** `views/Inbox.svelte` keeps its shape and words (the three sections by `kind`, unclassified threads in a fourth section "Unsorted" first, the triaged disclosure, the search, the draft disclosure now an editor over the note's draft with Send and Archive controls, the provider link) drawn from the `inbox` channel instead of the feed; the account rows with their state word and Connect control as the Calendar view draws them; the head with the as-of time, the cadence and a Refresh control; the rail badge counting the plate's untriaged `reply` and `action` threads (a thread with no kind counts too); the ticker's inbox line from the channel.
6. **The file retired.** `feeds/inbox.yml` is deleted from the hub and the demo, `inbox_file` leaves `config/sources.yml`, the feed reader's inbox branch, the watcher's, the entries writer's inbox rule, `FeedKind`'s `inbox`, the Q25 source control on the view and the `no_file` word go; the cockpit's `docs:` entry for the inbox leaves `tools/cockpit/data/config/layout.yml` (its Inbox tab is gone, the cockpit's own words for it left in place), and its selftest, dummy build and tests stay green.

## Decisions taken in this brief (each reversible, none silent)

1. A mail account is a separate consent from a calendar account even for the same mailbox, so the read-only calendar token never carries send rights.
2. The triage notes live beside the credential files under `mail_dir`, machine-local, since they are private and the hub file is retired.
3. The skill keeps reading Gmail through the runner's connector and writes the notes; the server never asks a language model anything.
4. A send needs a confirmation naming the recipient; nothing sends on a keystroke.
