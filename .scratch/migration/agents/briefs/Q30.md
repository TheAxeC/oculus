## What to build

1. **The sentence file.** `config/text/findings.yml` holding every finding sentence of `data/validate.ts` and `data/sources/*.ts` under `text: findings:`, one key per sentence, grouped by the file that raises it (`findings.validate.*`, `findings.config.*` and so on), the variable parts as `{0}`, `{1}` placeholders. The sentences keep their current words exactly, so every finding reads as it does today.
2. **One formatter for the data layer.** A pure function in `src/lib/data/` (for example `data/finding-text.ts`) taking the catalog, a key and the arguments and answering the sentence, with the placeholder rule of `state/text.ts`'s `t()` (share the replacement, do not copy it). The data layer never imports from `state/`.
3. **Threaded through.** `ValidationRules` gains the catalog (`text: Record<string, string>`), `data/index.ts` passes `textCatalog(config)`; each reader that raises findings takes the catalog the same way from its caller. No literal sentence is left in those files (`grep -n "message: ['\`]" src/lib/data/validate.ts src/lib/data/sources/*.ts` prints nothing).
4. **The catalog's own findings.** `loadConfig` formats its findings once the merge is done, with the catalog it merged. When that catalog lacks a finding key (the sentence file itself did not parse), the finding's message is the key followed by its arguments, so a broken `findings.yml` still reports which file broke instead of throwing; a test covers that case.
5. **A missing key elsewhere.** Every key the code names exists in `config/text/findings.yml`: a node test reads every `findings.` key the data layer names (by a list exported beside the formatter, or by a grep of the source in the test) and asserts each is in the real catalog, and asserts no key of the file is unused.
