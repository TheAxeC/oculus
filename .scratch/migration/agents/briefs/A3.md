### 5. The schedule (`src/lib/server/machine/tasks/schedule.ts`)

`watchSchedules(hub, options)` answers `{ set(schedules), setText(text), close() }`, built in `startPollers` beside the Processes watcher, handed every config push by `liveSettings` (a changed pattern only), closed in `context.ts`'s `close()`.

- One croner job per task with a pattern: `new Cron(pattern, { mode: '5-part' }, fire)`, in the local time zone (no `timezone` option). A task with `''` has no job. `set` stops the job of a changed or emptied pattern and starts the new one at once; `close()` stops every job, and nothing starts after it, a start already awaited included.
- At each due time `fire` takes the due time the job was waiting for (croner's `currentRun()` at the trigger, or the time `nextRun()` answered before it; the builder reports which) and runs the claim of item 6, then `startUpdateTask(kind, { trigger: 'schedule', due }, ...)` when the claim says start.
- Catch-up, once, at start and at a pattern first read: for each task, `previous = job.previousRuns(1, now)[0]`; when `previous` is later than both the task's last handled due time and the time its pattern was first read (`since`, item 6), one run starts with `{ trigger: 'catch-up', due: previous }`. Earlier missed due times start nothing; a machine that slept through several due times starts one run when croner's next check finds the awaited time passed.
- One run at a time (Decision 4). A due time finds the task's earlier run going when the terminal recorded for the task's newest run (hand, scheduled or catch-up) is in the `terminals` of `hub.latest('sessions')` and the Claude session in that terminal is not `idle` in that payload's records; the session is found by its registry `pid`, equal to the terminal's `pid` or a child of it, as case 1 finds. A listed terminal with no record matched, or a record `busy` or of any status other than `idle`, is going. A run that is going makes the due time start nothing and records it `skipped` with the earlier terminal's id.
- `tasks.skip_permissions: true` starts a scheduled or catch-up run with the flag and without a question (Decision 5); `false` starts it with its prompts, which wait in its terminal, and the run counts as going while they wait.
- A scheduled start does not show its terminal on any page: it is listed with the other terminals, and the tray's record row opens it (item 7).
- After every change of a job, a record or the record file's state, the watcher publishes one complete payload on the channel `schedule` (Decision 7).

### 6. The run record (`src/lib/server/machine/tasks/record.ts`, Decision 6)

The record is `~/.oculus/schedule.json` (no `local.yml` key, as `commands.json`; the path is handed in by the context so a test and a probe point it at a scratch folder):

```json
{
    "litwatch": {
        "pattern": "0 7 * * *",
        "since": "2026-10-05T09:12:00.000Z",
        "handled": "2026-10-06T05:00:00.000Z",
        "runs": [
            { "trigger": "schedule", "due": "2026-10-06T05:00:00.000Z", "at": "2026-10-06T05:00:00.412Z", "outcome": "started", "terminal": "k3f9a2" }
        ]
    }
}
```

- `trigger` one of `schedule`, `catch-up`, `hand`; `outcome` one of `started`, `skipped`, `failed`; `terminal` the started terminal's id, the earlier going terminal's id for `skipped`, null for `failed`; `runs` newest first, at most 20 per task.
- `pattern` and `since`: when the pattern read differs from the one recorded (or none is recorded), `since` becomes now and `handled` null, so writing or changing a pattern never catches up a due time from before it was written.
- The claim: before a scheduled or catch-up start, the record is read again and written with `handled` set to the due time and the run `started`, under an exclusive lock (`schedule.json.lock` opened with `wx`, removed after the write); a due time already handled starts nothing. The start follows the write; a start that fails rewrites that run's `outcome` to `failed`. So a crash between the write and the start never starts a due time twice, and two oculus servers sharing one home start one run per due time.
- The file is read through `readJsonChecked` and written through `writeTextAtomic` of `src/lib/server/core/json.ts` (:49, :72), as `commands/saved.ts:14` does (G31's pattern): a missing file is created on the first write; a file that does not read (not JSON, or not this shape) is never written over, no scheduled or catch-up run starts while it does not read, a hand press still starts its task without recording it, the payload carries the catalog's sentence saying the record does not read, and stderr says it once.
- A hand press records `{ trigger: 'hand', due: null }` with its outcome, through the same file and lock.
