# Brief: A3, the four update tasks re-run on a cron-style `schedule:` read through croner, with catch-up, one run at a time and a run record

Read `tools/oculus/.scratch/migration/agents/spec.md` first; its rules govern this step unchanged. Then, in full, the files and ranges under "Read, with sections or line ranges". The configuration names no standards pages (`.agents/plan.yaml`: `standards: []`), and no ADR touches this step: `ls tools/oculus/docs` prints only `diagrams`.

A design ruling decides what is built. It never exempts the code: every line is written to the standards pages, so that people can read, use and maintain it.

The machine's own file `config/local.yml` is never opened, printed, grepped or hashed by this step, its builder, its reviewer or its tests, in any checkout. Every grep over a `config/` folder carries `--exclude=local.yml` before the pattern, in the form `grep -rn --exclude=local.yml -e <pattern> config`.

No test or probe of this step runs a real update task: none starts the real `claude`, `/research-cockpit` or tmux on the oculus socket. Every run of the scheduler in a test or a probe is handed a recording tmux runner (or a scratch tmux server under its own `TMUX_TMPDIR`), a stub `claude`, a scratch record path and a clock. The one real task is started by hand at the look (look case 10, from the Q2 ruling).

### 5. The schedule (`src/lib/server/machine/tasks/schedule.ts`)

`watchSchedules(hub, options)` answers `{ set(schedules), setText(text), close() }`. `ContextDependencies` (`context.ts:198-216`, and the `dependencies` object :218-236, corrected after X3f, D38 and D20) gains `watchSchedules`; `startPollers` builds it beside the Processes watcher with `taskSchedules(config)`, the record path and the text catalog; `liveSettings` hands it every config push through an `attempt('schedules', ...)` beside the Processes one (`live-settings.ts:180-185`), a changed pattern only, and a push whose merge dropped `behavior.yml` keeps every job (`live-settings.ts:15-16`); `context.ts`'s `close()` (:477-495) closes it.

- At each due time `fire` takes the due time the job was waiting for (croner's `currentRun()` at the trigger, or the time `nextRun()` answered before it; the builder reports which) and runs the claim of item 6, then the one-run rule below, then `startUpdateTask(kind, { trigger: 'schedule', due }, ...)` when both say start.
