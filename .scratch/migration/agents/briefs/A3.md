### 1. The file `~/.oculus/schedules.yml` (Decision 1)

A YAML list, one map per schedule:

```yaml
- name: Weekly radar
  runs: { task: litwatch }
  when: "0 7 * * 1"
- name: Nightly results sync
  runs: { command: rsync-results, folder: ~/workspace/research-hub }
  when: "@daily"
  paused: true
- name: Monday portfolio summary
  runs: { prompt: "Summarise what is blocked", folder: hub }
  when: "0 8 * * 1"
  unattended: true
```

- `name`: required text, trimmed, 1 to 80 characters, no control character; two names equal after trimming and ignoring case are a clash. The name is the record's key and the terminal name of a prompt run.
- `runs`: a map holding exactly one of `task` (one of `litwatch`, `scout`, `linkedin`, `inbox`), `command` (a saved command's name, with `folder`, the repository it is saved under) or `prompt` (the first message of a new Claude session, with `folder`, where the session starts). `folder` is `hub` (the configured hub folder, `local.hub`), an absolute path, or a path starting `~/`; a `task` entry takes no `folder`.
- `when`: a cron pattern of five fields or a croner nickname, in the server machine's local time; absent means Off, and the schedule runs only by Run now.
- `paused`: optional boolean, false by default.
- `unattended`: optional boolean, false by default; it applies to a `task` or a `prompt` run, which then starts with `--dangerously-skip-permissions`.
- Any other key of an entry, or of `runs`, is a problem of that entry.

Reading (`src/lib/server/machine/schedules/file.ts`): a missing file, an empty file, a comments-only file and `null` are no schedules. A file that does not parse, or whose top level is no list, is unread: no schedule runs, every job stops, the tray shows the unread line under the Schedules heading (with the line number when the parser gives one), and no write of oculus touches the file. An entry that does not read gets its problem (item 2) and does not run; the others run. Both entries of a name clash get the problem `name-twice` and neither runs.

Writing (the same module): every write goes through `parseDocument` so the reader's comments and layout stay. A new entry is appended as a block map with `runs` in flow style and `when` double-quoted; an edit changes only the keys whose value changed (a removed `when`, `paused: false` or `unattended: false` deletes the key); a pause sets `paused: true` and a resume deletes it; a delete removes the item. An empty, comments-only or `[]` file becomes a block list on its first write. A write names its entry by its position `at` and the `name` the page read there, and is refused with `entry-changed` when the entry at `at` no longer has that name. Before writing, the result is parsed again and compared with the list as asked (the old list with the one change); a mismatch is refused and nothing is written. The write is `writeTextAtomic(path, text, 0o600)` and read back, behind the server's write chain (`chained(server.writes, ...)`), and a write over a file that is unread is refused with `schedules-unread`, the file left as it is. The path comes in from the context (`~/.oculus/schedules.yml` resolved at the call), so a test and a probe point it at a scratch folder. Every write that changed something is one record of the change log, kind `schedules`, `file` the path, `key` the schedule's name, `field` `entries`, `before` and `after` the entry (null for a new or deleted one), `undo: 'none'`, as `commands/routes.ts:119-140` records a saved command.

### 2. One rule for an entry and one for a pattern, shared by the page and the server (Decisions 2 and 3)

- `src/lib/data/helpers/run/cron.ts` (new, layer 1, imports croner): `cronRuns(pattern, count, from)` answers `{ ok: true, runs: Date[] }` with the next `count` runs from `from`, or `{ ok: false, why: 'unreadable' | 'never' }`. ## Decisions taken in this brief (each reversible, none silent)

1. The file format of item 1, with the field names `name`, `runs` (`task`, `command` with `folder`, `prompt` with `folder`), `when`, `paused`, `unattended`, following the shape the rulings' example gives. `folder` is added to a command entry because saved commands are kept per repository (`commands.json` is a map from a repository's real path to its commands), so a name alone can name two commands. Five cases under it: (a) `{ name: Weekly radar, runs: { task: litwatch }, when: "0 7 * * 1" }` runs Lit Watch Mondays 07:00; (b) `{ name: Nightly results sync, runs: { command: rsync-results, folder: ~/workspace/research-hub }, when: "@daily", paused: true }` is listed Paused and starts nothing; (c) `{ name: Monday portfolio summary, runs: { prompt: "Summarise what is blocked", folder: hub }, when: "0 8 * * 1" }` starts a Claude session in the hub folder Mondays 08:00 with its prompts answered in the terminal; (d) the same with `unattended: true` starts it with `--dangerously-skip-permissions`; (e) `{ name: Scout by hand, runs: { task: scout } }` is Off and runs only from Run now.
2. A pattern is croner's five-field form or one of its nicknames, in the server machine's local time; the dialog writes only `0 * * * *`, `M H * * *` and `M H * * d,d`, and opens anything else as Custom.
3. One rule for an entry and one for a pattern, in layer 1 (`data/helpers/run/schedules.ts`, `cron.ts`), read by the dialog before it sends and by the server when it reads and writes; the disk checks (folder, saved command, repository) are the server's.
4. The record stays `~/.oculus/schedule.json`, keyed by the schedule's name; a rename moves its entry, a delete or a new schedule under a reused name drops it; `pattern` is the effective pattern, so a pause, a resume and a changed `when` reset `since`.
5. An entry with a problem does not run and its row says why; both entries of a name clash are held, since the record is keyed by name. The problem sentences are: `name_missing` "The schedule has no name."; `name_wrong` "The name {0} is longer than 80 characters or holds a control character."; `name_twice` "Two schedules are named {0}; neither runs until one is renamed."; `runs_wrong` "What it runs must be exactly one of a task, a command and a prompt."; `update_task_unknown` "{0} is not an update task; the tasks are litwatch, scout, linkedin and inbox."; `command_missing` "No saved command {0} in {1}."; `commands_unread` "The saved commands file does not read."; `folder_empty` "The folder is empty."; `folder_wrong` "The folder {0} must be hub, an absolute path or a path under ~/."; `folder_missing` "The folder {0} does not exist."; `prompt_empty` "The prompt is empty."; `prompt_too_long` "The prompt is longer than {0} characters."; `prompt_control` "The prompt holds a control character other than a tab or a new line."; `when_unreadable` "The pattern {0} does not read: a cron pattern has five fields, such as 0 7 * * 1, or is a nickname such as @daily."; `when_never` "The pattern {0} never comes due."; `key_unknown` "{0} is not a key of a schedule."; `flag_wrong` "{0} must be true or false."; `unattended_command` "Run unattended applies to an update task or a prompt."; `needs_approval` "The command {0} runs lines that need your approval; run it once from its repository's command bar."; `record_unread` "The run record does not read, so nothing starts."; `schedules_unread` "The schedules file does not read, so oculus writes nothing to it."; `entry_changed` "The schedules file changed since the tray read it; try again."
6. `tasks.skip_permissions` is removed, not kept for the tray's press. Its current users (the fact above) are the press's confirmation, the press's argv and the docs; after Z572 the press is its only user. A press is made by a reader sitting at the terminal, so it has nobody to spare from the prompts, and keeping the key would leave two places that decide whether a run is unattended, one of them a config key that applies to every task at once. Run unattended on a schedule is the one place. The shipped value is `false`, so no shipped behaviour changes. Both retired keys get a finding pointing at Run unattended. Keeping the key is the cheaper option (no change to the tray, the store, the route, the docs or the findings test) and leaves the old mechanism beside the new one.
7. Run now records a `hand` run, follows the one-run rule, runs a paused or Off entry, is refused for an entry with a problem or while the record or the file does not read, and when it starts a terminal, shows it and closes the tray, as a task press does. A tray task press belongs to no schedule and records nothing.
8. The terminal of a scheduled task run is `task <kind>` (the press's name), of a command run the command's name (the command route's name), of a prompt run the schedule's name. A scheduled start shows no terminal (Z510).
9. The dialog is drawn in the tray's `over` snippet, and Schedule... on a saved command opens the tray through `requestUpdateTray()` with the dialog over it, so the dialog always stands over the tray (`Modal`'s `dialog` level is under `tray`) and the new row is seen once it is saved.
10. The prompt's folder is checked as the composer checks a start's folder: an absolute existing directory once `hub` and `~/` are resolved, with no restriction to the served roots; a command's folder is checked by `repositoryOf`, as a command run is.
11. The payload carries words and line numbers, never the server's English, so the watcher needs no text catalog and `live-settings.ts` is not touched.
Three of these are user-visible choices the rulings do not settle, written here as recommended and open until Axel rules (the orchestrator's open items OI-4 to OI-6): Run now of a paused or Off schedule runs (Decision 7); Run now that starts a terminal shows it and closes the tray (Decision 7); both entries of a name clash are held (Decision 5). A different ruling changes only those sentences and cases S10, S15 and S16.

12. Internal choices the builder makes and lists: the split of the tray into `ScheduleList.svelte` and `ScheduleDialog.svelte`, the store's function names beyond those named, the stub of the look, the probe forms.
