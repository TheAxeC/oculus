# Brief: R14, the sanitiser at the HTML sites

Read `../spec.md` first, its section "The principles every package is judged on" above all. Axel ruled on 2026-09-14 at 08:30 (ruling (a) of the sharp-edge audit) that the HTML oculus renders from hub files, feeds and transcripts goes through a sanitiser dependency. This package adds it and puts it at every site. This package runs beside W2 (the rail and the flyouts) under the two-worker rule: it writes only under `src/lib/views/`, `src/lib/ui/Card.svelte`, `src/lib/state/`, `src/lib/ui/html.ts` (new), `tests/views/`, `tests/state/`, `tests/ui/html.test.ts` (new), `tests/integrity.test.ts` or a new audit test under `tests/`, `package.json` and `package-lock.json`; it never touches `src/lib/shell/`, `src/lib/ui/ToolButton.svelte`, `Glyph.svelte`, `Tooltip.svelte`, `Menu.svelte`, `tests/browser/` or `DESIGN.md`'s wallpaper paragraph.

## What to build (code, state and tests; no wire or config change)

1. **One sanitiser, one function.** `src/lib/ui/html.ts` exports `sanitise(html: string): string` over `dompurify` with a fixed profile: the elements and attributes inline Markdown and `marked` produce (paragraphs, headings, lists, code, pre, emphasis, links with `href`, images with `src` only where a document uses them, tables) and nothing else; `target` and `rel` on a link set by the profile, not by the input; no inline event handler, no `javascript:` URL, no `style`, no `<script>`, `<iframe>`, `<object>`, `<form>`. The profile is data in the file, read by the test.
2. **Every site whose input is not oculus's own text goes through it once.** Groups (1), (2) and (3) above pass through `sanitise` at the site, or `inlineMarkdown` calls it on its result so its 17 sites are covered in one place (the DRY choice; the report says which sites are covered where). Group (4), the `t(...)` strings from `config/text/`, stays as it is, and `t('radar.threatens', inlineMarkdown(threat))` is covered by the inline value's sanitising. `Editor.svelte`'s `painted` is read: if the highlighter escapes the text it paints, it stays and the report says so with the line; if it does not, it goes through `sanitise`. The two comments that gave the old reason are rewritten to the new one.
3. **A new site cannot skip it.** An audit test in the shape of `tests/views/type-scale.test.ts` walks every `{@html ...}` expression under `src/lib` and requires it to be one of: `sanitise(...)`, `inlineMarkdown(...)`, `t(...)`, or a name the test's own exact allow-list carries with its reason (the sanitised-upstream cases such as `shown.html` if sanitised where it is assigned, or `painted` if it escapes); a site outside those fails.
4. **Tests.** (a) `tests/ui/html.test.ts`: `sanitise` drops a `<script>`, an `onerror` attribute, a `javascript:` href and a `<style>`, keeps a paragraph with emphasis, a link and a code block, and the profile's lists are what the test reads. (b) The test Axel named: a feed title carrying `<script>alert(1)</script>` renders as text in the card, through `ui/Card.svelte`'s title path and through `inlineMarkdown` (a component test with the existing view-test harness under `tests/views/`). (c) A document body from `marked` with an inline handler renders without it (`views/Project.svelte`'s path, at the unit level of the function that assigns `shown.html`, or of `sanitise` if that is where it is called). (d) The audit of item 3. Every existing test passes unchanged.

## Decisions taken in this brief (each reversible, none silent)

1. `dompurify`, exact version, browser-only, since SSR is off.
2. One `sanitise` in `src/lib/ui/html.ts` with a data profile; `inlineMarkdown` calls it on its result.
3. `config/text/` strings are trusted as oculus's own and are not sanitised.
4. The audit test's allow-list is exact and carries a reason per entry.
