## What to build

### Part 1: one deck per research project

Every one of the 95 research projects has a deck under its `present/` folder when the step is done: the 70 without one get one, and the 25 with one are written again the same way, so no slide keeps text it had before unless that text is still current and right.

- The work goes one project at a time: the builder reads that project's files, writes its deck and adds its row to the report's table of decks before it opens the next project's files. The sources run to about 2.3 MB in all, more than one context holds, so no project's deck is written from a memory of files read for another.
- Each deck is written from the project's own files: its `project.yml`, its `README.md`, its manuscript (`manuscript/main.tex` and the files it inputs) and its `CLAUDE.md`, each read in full where it exists. A project with only a manifest gets a deck from its manifest's fields (`title`, `eli5`, `outcome`, and `results` where it has one) and states nothing those fields do not hold.
- Every deck is complete: it states the project's question, its method, its main result with its numbers and its state (for an idea, what it would test, how, and where it stands), as far as the project's files hold each. A part the files do not hold is left out, never invented.
- Every number on a slide is the project's current number, and every framing the project's current one. Where the files disagree, the deck follows Decision 2, and the report lists each disagreement with the project, the two values and the file of each.
- Every deck is internal. Nothing is hidden, thinned or left out for any reason: confidentiality, a data agreement, a failed or withdrawn result, a dead end. A failed or stopped project is written like every other: what it set out to do, what was built, what came out, with its numbers.
- Each deck is one slide, or two where two read better. Never more than two.
- Every slide has a title by the title rule of "What is on the tree". A project slide carries its own `title:` or a level-1 heading wherever the project's short name alone would not name what the slide shows, and an idea slide of a project's deck is titled by its project (a `title:` on it is not read, so none is written).
- Every slide fits the 1280 by 720 frame with the facts strip at its foot: at the least factor 0.75 its content ends above the strip in the reading column (at most 1040 px wide and about 530 px tall above a strip of two lines, body text 18 px and title 42 px at that factor). The builder cannot draw a slide, so it fits each one by its content: the amount of text, the number of list items and the size of any figure, read against those measures.
- Each deck's `present.yml` and slide files follow `docs/decks.md` exactly, so the deck reader raises no finding on them: only the keys and kinds it names, each slide of a kind it lists, every `{{project.<field>}}` naming a field the project's manifest holds, every figure path naming a file that exists. The report lists, per deck, the kinds and keys it uses and each figure path with the file it names.
- A figure a deck draws is a file in the deck's folder or in the project's own folders, named by its path from the deck (Decision 6). A file in a `present/` folder that no slide of the reworked deck names is removed.
- A deck carries no word of oculus's own interface (no "click", no "toggle", no view name) and no note addressed to the reader of the deck about the deck itself.
- Nothing of an earlier deck run is read or used. The builder does not read `.scratch/migration/agents/reviews/O150-O151-undone.patch`, does not run `git show` or `git log -p` on an earlier commit of O151 (`d6bb91263` and its parents), and does not read any deck file outside the 95 `present/` folders and `docs/decks.md`'s examples.
- The research hub is written on disk and not committed: the hub's commit waits on Axel's word. The builder writes only inside the 95 `present/` folders of the hub, under the authority named in "What is on the tree".

## Decisions taken in this brief (each reversible, none silent)

1. The strip's sizes under a rice theme are 11 px and 9 px: 12 and 10 times 12/13, rounded to whole pixels, the rule `slide.css:59-63` gives the other five sizes. Cases: 56 gives 52, 36 gives 33, 28 gives 26, 24 gives 22, 18 gives 17, so 12 gives 11 and 10 gives 9.
2. Where a project's files disagree, the deck takes the README's and the manifest's number and framing over the manuscript's, since the hub keeps those two current with every new result, and the manuscript of a paper under review may hold the submitted figure. Between the README and the manifest, the manifest wins for the stage, the status and the venue, since the hub keeps the manifest as the source of those, and the README wins for a number and a framing, since it carries the results in full. The report lists every disagreement.
3. A project's second slide is used only where one slide would not hold the project's question, method, result and state at a readable size; the report names each deck with two slides and why.
4. The step's "no finding left" is checked at the look: the orchestrator draws every deck in the Present view on a scratch server over a copy of the hub with the new decks, and a deck with a finding goes back in the repair round. The builder starts no server.
5. The ruling "Facts strip smaller" names a value size of 12 px and a label size of 10 px through "a slide size of its own"; the brief sets two design sizes, one per size, so neither is written as a fraction of the other (10/12 would need a factor of 0.8333 that rounds differently under rice).
