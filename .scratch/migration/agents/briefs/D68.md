# Brief: D68, workspaces as files

Size: a full step

Read `tools/oculus/.scratch/migration/agents/spec.md` first; its rules govern this step unchanged. It is also the one standards page the configuration lists. No ADR folder exists (`ls docs/adr tools/oculus/docs/adr` answers no such file for both), so no ADR touches this step.

You work in the worktree `.agents/worktrees/D68` (from the repository root) and nowhere else; the base copy is `.agents/worktrees/D68-base/tools/oculus/`.

A design ruling decides what is built. It never exempts the code: every line is written to the standards pages, so that people can read, use and maintain it.

Today the folders oculus shows come from two files in two formats: the `roots:` key of a hub's `.oculus/config/sources.yml` for the unnamed workspace, and `<hub>/.oculus/workspaces.json` for the named ones and the folders added to the unnamed one. On top of those, two folders are always served and never listed anywhere: the hub itself under the key `hub` and oculus's own `config/` folder under the key `engine`. The machine's own file `local.yml` sits in oculus's `config/` and names the hub. Axel ruled that this becomes VS Code's model: a workspace is one YAML file listing its folders, nothing is served that the file does not list, any listed folder that holds `.oculus/config/` is a hub, and each hub keeps its own `local.yml`.

## What to build

1. **A workspace is one file.** A workspace is the YAML file `.oculus/workspaces/<name>.yml` in a hub, its name the file name without `.yml`. Its shape is VS Code's `folders` list (Z820), and Save Workspace As writes exactly this flow style:

   ```yaml
   folders:
     - { name: research-hub, path: ~/workspace/research-hub }
     - { name: claude, path: ~/.claude }
   primary: research-hub
   ```

   - Each folder has a `name` (letters, digits, `.`, `_` and `-`, unique in the file) and a `path` (`~/...` or absolute); both are required. An entry missing either, a name repeated, a name with any other character, a path that is neither, two entries over one real path (a symlink included), and a `primary` that names no folder of the file or a folder that is no hub are findings that name the file and the entry; the entry is left out (for two over one real path, the later one), and a bad `primary` leaves the workspace with no primary. The other entries stand.
   - A file that does not parse is a finding naming the file; no folder of it is served, and Add, Remove and reorder are refused with the reason and leave the file byte for byte (G31's rule).
   - `primary` is optional. Without it there is no primary.
   - A key oculus does not read is a finding and is ignored.
   - Every write to the file (items 4 and 5) keeps every other line and comment, through the byte-preserving list edit `roots.ts` uses today (`server/edit/list-edit.ts`), with its undo record.
2. **Nothing hidden.** The keys `hub` and `engine` go as served roots, with `HUB_ROOT`, `ENGINE_ROOT`, `ENGINE_IN_HUB`, `engineRoot`, `byPrefix`, `DEFAULT_ROOT` (`~/workspace`) and `configuredRootsOf` with its caller's use. The Files view, the file route and every reader (the fs listing, search, the language servers, git, app hosts) serve exactly the folders the open workspace lists, under their names.
   - The primary's files are served under the primary's name, and the merged portfolio gives the primary's records bare ids and every other hub's records `<name>:`; with no primary, every hub's records carry `<name>:` (Z821). `rootOf`, `hubId`, `inHubOf`, `splitHubId`, `bareId`, `ofHub`, `collectionsOf` and `fileUnder` take the primary's name (or none) as an argument; nothing assumes a fixed key. The record writes (`server/edit/writes/hubs.ts`) route an id to its hub by its name: with no primary a bare id answers not found, and a new project with no hub of the workspace is refused with a catalog sentence.
   - A folder listed inside another listed folder (Axel's `oculus` inside `research-hub`) is served under both names, and `sameDiskFile` treats the two paths as one file by real path.
   - oculus's own `config/` is still read for the defaults, from oculus's folder, as today, and is not served as a root. The Settings view reads the text of oculus's own config files and the listings of its `catalogs/`, `schemas/` and `text/` through a read-only route over that folder alone, as the docs route serves oculus's documents (Z827); it writes oculus's own config files for the keys outside the hub list, through the config writers, by the file's path. Its "open in the editor" and the Files view reach those files only through a workspace folder that holds them (Axel's ruling: `ENGINE_ROOT` replaced by listing the folder); with none, the Settings view offers no open for them and says why in a catalog line.
   - oculus's own documents (Help, the manual, the apps guide, `engine: true` doc tabs and the shipped doc id `engine:docs/apps.md`, which is a document id and stays) stay served by the docs route. Hub documents are keyed by the hub's name: `?hub=<name>`, a missing `hub` meaning the primary, and with no primary a link that names no hub opens nothing. G74's engine-in-hub links resolve when oculus's folder lies inside a listed hub folder, against that hub.
   - The reference scan resolves a reference into oculus's own config to the workspace folder that holds the file, and with none the reference has no openable definition.
   - Every place that closed the `engine` root to apps (`reach/fs.ts`, `reach/open.ts`, `frame/methods.ts`, `read/scan.ts`, `read/manifest.ts`, `host/manager.ts`) closes oculus's own `config/` folder by its real path instead (today's scope, DESIGN.md:410), under whatever name a workspace lists it, and every hub's `.oculus/local.yml` (item 7). An app's `files:` names workspace folders by name, `<name>` or `<name>/<path>`; a name that is no folder of the open workspace is a finding, and `files_engine` goes with the `engine` key.
3. **What a folder is.** A listed folder that holds `.oculus/config/` is a hub: its portfolio is built and merged as a `hub: true` root's is today. `hub: true` goes from the root shape; its findings and `hubRefusal`'s first-hub cases follow, and `project_in_hub`, `project_same_dir`, `missing_dir` and `hubs.id_prefix` carry over with their words updated. A listed folder that is no hub and holds `.oculus/project.yml` is a project of the workspace, with the folder's name as its id and the primary's prefix rule; such a folder inside a listed hub stays `project_in_hub` and no project, as today; a folder project whose id equals another project's id is a finding naming both, and the folder's project is left out. Any other folder is served and is nothing else. A folder that gains or loses `.oculus/config/` while oculus runs becomes or stops being a hub at the next build.
4. **The open workspace and the recent list are machine state.** The path of the open workspace file, the recent list and the folders of an unsaved workspace live in `~/.oculus/workspace.json` (Z822, keys in Z831), written by oculus alone, never read by a person. The server context takes the state folder as a dependency (today's `scratchReadLocal` pattern in `tests/server/root/inert-context.ts`), so a test never sets `HOME`.
   - With no such state, a state that does not parse, or a state naming a file that is gone or lies in no hub's `.oculus/workspaces/`, oculus opens an unsaved workspace with no folders, and a state that does not parse is not overwritten until a deliberate write (G31's rule): the server starts on the default port, every view is empty, and the Files view says to add a folder (VS Code's empty Explorer). Nothing errors, and a start with no workspace or no hub is no lack (G73 is rewritten at landing to drop the hub folder from the required lacks, Axel's ruling that oculus works with no hub).
   - Switch Workspace lists the recent list and every `.oculus/workspaces/*.yml` of the open workspace's hubs, a name two hubs share shown with its hub and taken by the palette as `<hub>/<name>` (Z830); choosing one opens it and puts it first in the recent list, which keeps the last 10; a recent file that is gone is drawn as missing, and choosing it says so and takes it off the list. The server follows a switch and a hand edit of the open file: the roots, the portfolio, the git watch and its start, the language-server relay, the open-files poll, the app hosts and the local.yml watcher each follow `~/.oculus/workspace.json` and the open file, whose path changes on a switch. The port and the state paths are read at start only (Z829): a switch to a workspace whose primary sets another value keeps the running one, with a finding naming the key and that a restart takes it.
   - A source tab of a folder a switch removed keeps its unsaved text and shows the missing root (G28, G69).
   - Save Workspace As asks a name (the folder-name rule of item 1; an empty name, `..`, or a `/` is refused) and writes `.oculus/workspaces/<name>.yml` in the primary, else in the first hub of the workspace, with the open folders and the primary; it is refused with a catalog sentence when the workspace holds no hub, or when the file exists (Z822). The unsaved workspace's name in the header is the catalog's "Untitled (Workspace)", VS Code's (Z830).
5. **Add and Remove Folder edit the open workspace's file.** Add Folder to Workspace appends `{ name, path }` (the name from the folder's base name as `rootKey` makes it today, with `folder` as the stem where the base name gives none, the path written `~/...` under the home folder); Remove Folder from Workspace takes the entry out. In an unsaved workspace both change the state of item 4. No folder is fixed: the primary can be removed too, and `primary` is then taken out with it. Reordering keeps working on the file.

   - The project's own hub, by its record's name, where the use is per project: deposit (`git/deposit.ts:285`), LaTeX (`content/latex/endpoint.ts:201,222`, `pty/latex/latex.ts:196`), HPC (`hpc/submit.ts:152`, the hpc route), sessions (`sessions/index.ts:60`), decks (`content/deck/read.ts:90-91`, the deck route), `project-files.ts`, a project chat. A project of a hub not listed does nothing.
   - Every workspace folder where the use spans them: search, git, the roots.
   - The start line in `src/server.ts:144` names the open workspace file, or says it is unsaved.
   - A bookmark whose folder is not in the workspace is drawn as today's missing bookmark. The roots an app reaches are the open workspace's folders, under the closures of item 2. The machine apps are the primary's `.oculus/apps`; another hub's `.oculus/apps` is not read; a root app of a folder a switch removed stops.
7. **`local.yml` in each hub's `.oculus/`.** The machine's own file is `<hub>/.oculus/local.yml` for every hub of the workspace, out of git (the hub's `.gitignore` gains the line at landing, item 10). oculus's `config/local.yml` is no longer read; `.gitignore`, `.prettierignore` and `utils/folder-check.sh`'s comment stop naming it, and G3 still closes that path of the running oculus, so a leftover file there is never served.
