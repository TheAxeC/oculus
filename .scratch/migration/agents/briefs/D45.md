## What to build

The step is large: about 45 behaviours across the server, the store, the editor, the viewer, the windows, a view and the shell. Every one is inside D45 by the plan line, its sub-lines, Z671, Z683 and the two inventories; none is split out.

### A. Root and build

1. **Root detection** (`server/content/latex/root.ts`, the shared reader). For a source file (`.tex`, and the literate kinds of item 9): (1) a `% !TEX root = <path>` in the leading comment block, resolved from the file's folder inside the same served root and followed while the named file is not a main, a cycle answering none; (2) the file itself when it declares a class; (3) walking up from the file's folder to the served root, at each folder the mains of that folder (`mainsIn` order) whose include closure holds the file, the first such folder and the first such main winning; the closure follows `\input`, `\include`, `\subfile`, `\import`, `\subimport`, `\includefrom` and `\inputfrom` through the shared reader, each file read once, and, when the main has a `<main>.fls` beside it or in the output folder, its `INPUT` lines under the root; (4) the only main of the file's own folder (today's rule); (5) none. A `% !TEX root` naming a file outside the root, missing, or not a `.tex` file falls through to (2). A `.bib`, `.sty` or `.cls` file (`config/sources.yml:110` maps them to `latex`) takes rules (3) to (5): a `.bib` named by a main's `\bibliography` or `\addbibresource` is in its closure (closes brief check, Implied inputs 10). `GET ?root=&file=` answers `{ root, path, main, how }`, `how` one of `magic`, `self`, `included`, `folder`, and `{ main: null }` otherwise. The walk stops at the served root and takes at most 200 ms per call on each case of "Cases" and each look file (closes brief check, The question 1: case 5 now has a bound).
2. **Recipes and tools** (`server/content/latex/recipes.ts`, new; `pty/routes.ts`). LaTeX Workshop's nine default recipes and their tools (Z503), in `config/behavior.yml` under `latex:` as `recipes` (name and tool names) and `tools` (name, command, arguments), read through zod. The placeholders resolve as LaTeX Workshop's (`out/src/utils/utils.js:333-347`): `%DOC%` the main's absolute path without its extension, `%DOC_EXT%` with it, `%DOCFILE%` and `%DOCFILE_EXT%` its file name without and with the extension, `%DIR%` the main's absolute folder, `%OUTDIR%` the resolved `latex.out_dir`, `%AUXDIR%` the resolved `latex.aux_dir` (closes brief check, Implied inputs 3 and The question 2). The default `latexmk` tool is LaTeX Workshop's whole: `-synctex=1 -interaction=nonstopmode -file-line-error -pdf -outdir=%OUTDIR% -auxdir=%AUXDIR% %DOC%`. A build runs one recipe as one task terminal in the main's folder whose line is the tools joined by `&&`, the command and every argument of each tool one `shellWord` (`pty/shell-word.ts:11`, which always single-quotes), since tools come from the configuration. The recipe is the one asked for (Build with Recipe, or a node of the TeX view's Build), else a `% !LW recipe = <name>` comment, else `latex.recipe_default` (`first` or `last_used`), and with `first` a `% !TEX program = xelatex | lualatex` picks LTW's `latexmk (xelatex)` or `latexmk (lualatex)` recipe, so today's program comment keeps working. Before the terminal starts, every program of the recipe is looked up on PATH; a missing one refuses the build with a catalog sentence naming the program and how TeX Live or Homebrew installs it, and no terminal starts. Two recipes or two tools with one name keep the first, with a finding naming the key, through the setting readers (item 31).
3. **Output and auxiliary folders.** `latex.out_dir`, default `%DIR%` (beside the main, as today and as LTW), and `latex.aux_dir`, default `%OUTDIR%` (LTW's `latex.auxDir`, a key of Z503's "LaTeX Workshop's `latex:` settings"). Any other value is resolved from the main's folder inside the served root; a value leaving the root is refused with its sentence. The PDF, `.log`, `.synctex.gz`, `.fls` and `.aux` are looked for there.
4. **A build that can be stopped.** A `latex` step `stop` sends Ctrl+C to the foreground of the main's kept build terminal and to no other terminal (G35); it answers 404 when the main has no build running. The page's store keeps each root's last outcome (item 8); a build asked for after a stop or a failure carries `force: true` on the `latex` action, and the server passes `-g` to latexmk when `force` is set or the main's `.synctex.gz` is missing in the output folder, since latexmk otherwise answers "Nothing to do" after an interrupted or failed run and never writes the SyncTeX file to a folder built before (cases 9 and 14) (closes brief check, Implied inputs 12). Clean while a build of that main runs is refused with a notice naming Kill Build. The new step, `force` and the recipe name travel from the page through `state/sessions/terminals.svelte.ts`'s `latex` (:110-111, :127-133, :485-497) (closes brief check, Names 3).
5. **Clean and retry, auto clean.** With `latex.clean_and_retry` true (LTW's default), a build that ends non-zero, was not stopped and is not itself a retry is cleaned (`latexmk -c` with the output and auxiliary folders) and run once more. `latex.auto_clean` `never` (default), `on_failed`, `on_succeeded`, `on_built` runs Clean after the build, as LTW's `latex.autoClean.run`.
6. **Auto build.** `latex.auto_build`: `on_file_change` (the default, Z503), `on_save` and `never`, the catalog entry's `values` and default and the reader `latexAutoBuild` in `settings.ts` changed with it (Z509); `buildsOnSave` (`latex.svelte.ts:654-660`) becomes the rule of the three values. `on_file_change` builds a root when a file of its dependency set changes on disk, from any writer (the editor's save, an agent, git), for roots the page watches: the root of every open LaTeX source tab and of every PDF tab of a build. The dependency set is the root's include closure and its `.fls` `INPUT` files under the root, minus what the build writes (the output and auxiliary folders' `.aux`, `.log`, `.pdf`, `.synctex.gz`, `.fls`, `.fdb_latexmk` and the rest latexmk names). Since a `files` message names only its root, at most once per two seconds (premise above), the mechanism is: on each `files` message for a served root, the store asks `GET /api/latex?root=&file=<main>&deps=1` for each watched root under it, which answers the dependency set with each file's modification time; the first answer is the baseline and builds nothing, and a later answer with any time later than the one held builds once (closes brief check, Premises 7 and Implied inputs 4). A build's own writes change no dependency's time, so they build nothing. Builds of one root start at most once per `latex.auto_build_interval_ms` (1000, LTW's `autoBuild.interval`) and coalesce into the one-more-build rule. A change while the root is building gives one build after it.
7. **Saving before a build.** A build the reader asks for saves every unsaved source tab first, as LTW's `saveAll` (Z503). An auto build never saves. Save without Building (LTW's `saveWithoutBuilding`, an editor action) saves the tab with no build under any `auto_build` value.
8. **Build state for the page.** The store keeps per root: idle, building (with the recipe and the step), succeeded, failed or stopped, and the time; the TeX view, the status item, the breadcrumb bar and the viewer read it. A build started anywhere (breadcrumb bar, key, palette, TeX view, project panel, save, file change) is the same state. A build the server refuses before a terminal starts (case 7, a missing program, an output folder outside the root) sets the root to failed with the refusal's sentence as its reason (closes brief check, Implied inputs 11).
9. **Literate sources.** `.rnw`, `.Rnw`, `.jnw` and `.pnw` join the `latex` list of `config/sources.yml:110`, are roots by the self rule when they declare a class, and default to the Rnw, Jnw or Pnw recipe; a missing `Rscript`, `julia` or `pweave` is refused as in item 2.

### B. The PDF beside the source, and SyncTeX
