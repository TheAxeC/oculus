- The cause, read on the tree: `undoChange` (`src/lib/server/edit/writes/undo.ts:180`) writes a manifest change back through `apply`, which calls `writeManifest(hub, config, change.key, { [change.field]: change.before })` (`undo.ts:197`). `writeManifest` (`src/lib/server/edit/writes/manifest.ts:141`) passes every value through `coerce` (`manifest.ts:69`, called at `:184`), the form's reading of a value: an empty list becomes `null` (`manifest.ts:90`, `strings.length === 0 ? null : strings`), an empty or blank text becomes `null` (`:97`), and a checkbox that is not true becomes `null` (`:73`). `null` removes the field (`setFields`, `src/lib/server/edit/yaml-edit.ts:654`). ## What to build

1. `src/lib/server/edit/writes/manifest.ts`: `writeManifest` takes an optional last parameter that says how its values are read: as a form (the default, `coerce` as it is, so the route's form write and the deposit are unchanged) or as a record's values (each value handed to `setFields` as it is). Under the record reading the schema still decides what may be written: a field the schema does not name is refused as for a form, and a field whose type is `readonly` or `keymap` is refused with `coerce`'s reasons. The head comment's sentence on what `writes.ts` re-exports is made true.
2. `src/lib/server/edit/writes/undo.ts`: the manifest row of `apply` calls `writeManifest` with the record reading and `change.before`. The head comment stays true: the undo goes through the writer the change came from.
3. `tests/routes/edit/undo.test.ts`: the cases below that are not already there.
4. `DESIGN.md` line 313: the two citations `writes/undo.ts:181` and `writes/manifest.ts:314` carry the line numbers the change leaves.

## Cases

1. A manifest holding `related: []`: a write of `related: ['x']` (as the Map's link sends it), then the undo of that change: the file's text is byte for byte what it was before the write, and the undo's record holds `before: ['x'], after: []`. Fails on main (the line is removed).
2. A manifest without `related`: the same write and undo: the undo answers 200, the field is removed and the file's text is what it was. Fails on main (400 `refused`, 'the value is not a list').
3. A manifest holding `title: ""`: a write of a title, then the undo: the file's text is what it was. Fails on main.
4. A manifest holding `pin: false`: a write of `pin: true`, then the undo: the file's text is what it was (the whole text compared, not a search for `pin: false`). Fails on main.
5. The existing case "writes a manifest field back, logs the undo, and undoes the undo" still passes: a text value goes back as it was. An audit.
6. A form write through the route still reads an empty control as clearing: `title: ''` removes the `title` line, and `related: []` over `related: [x]` removes the `related` line. Passes on main and after (an audit); `coerce`'s own cases in `tests/server/edit/writes.test.ts` lines 160-182 stay green.
7. An undo of a hand-made record naming `nosuch`, whose `after` the file holds (the field absent and `after: null`, so the `moved` check at `undo.ts:184` passes): answers `refused` with 'the manifest schema does not name the field', the file unchanged. An audit.
8. An undo of a hand-made record naming a `readonly` field (`tier`) or a `keymap` field, with the `moved` check passing: answers `refused` with `coerce`'s reason for that type, the file unchanged. Passes on main (the form reading refuses it) and must still pass after (an audit of a preserved refusal).
9. The undo of case 1's undo: `related: [x]` is back, the text as it was after the first write, the record `before: [], after: ['x']`. Fails on main (the first undo already removed the line, so the second is `moved`).
10. A change whose `after` the file no longer holds: a record `after: []` while the file now holds `related: [y]`, and a record `after: null` while the file now holds `related: []`: each answers 409 `moved` and the file is unchanged. An audit.
11. A record whose `before` is a number (`year: 2024`, a write of `'2025'`, then the undo): the text as it was. An audit.

## Decisions taken in this brief (each reversible, none silent)

1. The fix covers every value `coerce` reads differently from the record (`[]`, `''`, `false`, and `null` for a list), not only the empty list: all are the same cause, an undo read as a form, and each leaves a tracked manifest changed or an undo refused.
2. The record reading is a mode of `writeManifest`, not a second function, so an undo still goes through the writer the change came from, as `DESIGN.md:140`, `:376`, `HELP.md:254` and `undo.ts` lines 7-8 say.
3. The undo of a write that removed a field is left as it is (Z105): restoring its text needs the record to carry the removed lines, a change to the change log's record shape that is Axel's to rule on.

## What it must do

An undo of a manifest write that replaced a value gives the file back byte for byte: a value the file held (an empty list, an empty text, `false`, a list, a number) is written back as that value, and a field the file did not hold is removed, lists included. A form write keeps its meaning: an empty control clears the field. What the schema refuses a form, it refuses an undo.
