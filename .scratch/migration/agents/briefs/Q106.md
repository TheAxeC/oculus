## What was seen

On TEST: a pane holding History and Slides, its pane menu, Close pane, Confirm on "Close this pane and the 2 tabs in it?": the pane closed and came back, in the page and in the saved layout. On a pane of one tab, which asks nothing, Close pane closes it at once. The palette has the same defect: Cmd+K, then a tab of another pane (Deposit), and the choice is undone.

## The cause (found, `agents/reviews/Q106-diagnosis.md`, sections "Cause" and "Probes")

`Modal.svelte:68-71` gives the focus back to the control that held it before the dialog from inside an effect's cleanup:

```svelte
    // No dependency, so the body runs once and the cleanup runs when the ground goes.
    $effect(() => () => {
        if (came instanceof HTMLElement && came.isConnected) focusQuietly(came);
    });
```

A browser runs a control's focus handlers at once inside `focus()`, so PaneView's `entered` (`src/lib/shell/panes/PaneView.svelte:139-142`, `touchPane(page)` then, when `active !== '' && !activePane`, `activateInstance(active, page)`) runs inside that teardown. Svelte 5.57.1 runs a teardown with `is_destroying_effect` set, and a read of `$state` there answers with the value from before the first write of the same flush (`node_modules/svelte/src/internal/client/runtime.js:659-660`, `reactivity/sources.js:191-197`). So `change` in `layout.svelte.ts` reads the tree from before `closePane` and `savePages` writes it back. The probe that shows it: the red command is red with the handler run inside the teardown and green with the same handler queued after it; run from an effect body in the same flush it is green.

## Decisions taken in this brief (each reversible)

1. The give-back is deferred for every dialog, not only Confirm, since every Modal gives the focus back from the same cleanup and the palette shows the same defect.

3. The menu's give-back from a teardown (a menu destroyed while open) is left as it is: not reproduced, and its trigger goes with the destroyed branch.
