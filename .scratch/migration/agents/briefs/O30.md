### 1. The app and its server

`npm run app` (the script is `electron .`) starts the app from the checkout; `package.json` gains `"main": "src/desktop/main.ts"`. The main process is TypeScript under `src/desktop/`, run unbuilt by Electron's Node as the probe ran it. It takes the single-instance lock of item 2 first; only once it holds the lock and runs from the checkout (`app.isPackaged` false) does it run `vite build` as a child process (its output printed on the app's own output with a prefix naming the build), so a second `npm run app` never rebuilds `build/` under a running app. A failed build shows a dialog quoting the build's last stderr line, with Quit. The packaged app (item 14) runs no build and serves what `build/` holds.

The server runs in a utility process (`utilityProcess.fork` of `src/server.ts`, `stdio: 'pipe'`, `serviceName` the app's name), never in the main process, so a long config read never stops the window's menus or its move. The main hands it the environment of item 1.1 and `--engine`. Its output is printed on the app's own output with a prefix naming the server.

`src/server.ts` reports to its parent when it has one (`process.parentPort`, read once in the entry and passed down; nothing else reads it): `{ kind: 'listening', port }` on every `listening` event of the http server (the first listen and every port move), and `{ kind: 'failed', reason, port }` when the first listen fails. The first listen gets an `error` listener in every run: `EADDRINUSE` prints the catalog line `server.start.port_in_use` (`oculus: port {0} is in use`) on stderr and exits 1, under the app and under `node src/server.ts` alike, in place of the stack it throws now. The message shapes live in one module under `src/lib/server/root/process/` that both ends import.

The main waits for `listening`, then opens the window on `http://127.0.0.1:<port>/`. It keeps the port the server last reported, so a port move (D35) is followed by the window, whose page goes to the new address itself (`socket.svelte.ts:254-277`), and the navigation guard of item 5 admits the new origin by the rule of item 1.2.

`build/handler.js` missing (the packaged app, or a build that wrote none): a dialog says the server is not built and names `npm run build`, and the app quits. A server process that exits while the app runs (a crash, a kill) shows a dialog with its exit code and its last stderr line, offering Restart (the process forked again, the windows left open; their pages reconnect as on any restart) and Quit.

Quit (Cmd+Q, the menu, the Dock) stops the server process (`kill()`, which is SIGTERM, so `onShutdown` closes the socket, the context and the tmux control clients) and waits for its `exit`, at most 5 s, then the app exits. tmux sessions are left running, as a page that detaches leaves them (G28); the next start's Terminal tabs attach to them again.

1.1. The environment. Started from the Dock (`app.isPackaged`), the main resolves the login shell's environment with `shell-env` before forking the server and merges it over the inherited one, so PATH, LANG and the rest are the login shell's; a 10 s limit, after which, or on any failure, the server starts with the inherited environment and a dialog says once that programs on the login PATH (tmux, git, claude) may not be found. Started from a terminal (`npm run app`, unpackaged), the inherited environment is used as it is. DESIGN.md:395 ("The server reads no environment variable of its own") stays true: the server reads none of its own; the app hands it the shell's.

1.2. A port in use, and how an oculus is told from another program (D10 (a), Z516). An oculus answers `GET /api/health`, a new route (`src/routes/api/health/+server.ts`) that answers 200 with `{ "app": "oculus" }`, the body a constant of the parent-message module both ends import; it joins `HEADERLESS` in `src/hooks.server.ts` with its reason (the app's main asks it with Node's `fetch`, which sends neither header), and `auth.ts:13-14` and DESIGN.md:151 name five paths. Any other answer, no answer within 2 s, another status or another body, is another program. When the server's first listen fails with `failed`, the main asks `GET /api/health` on that port: another program gives a dialog naming the port and saying another program holds it, with Quit; an oculus gives a dialog saying an oculus answers on the port, with Open a Window and Quit. Open a Window opens a main window on that oculus's page and keeps the app running with no server of its own; Quit leaves that server running. Every word of both dialogs comes from the catalog's `desktop` group (item 13).

A window onto an oculus follows that server's port move by its socket, the app's own server and one the app did not start alike: the page carries its arrangement and calls `location.assign` as it does now, and `will-navigate` meets a top-level navigation of an app window to `http://127.0.0.1:<p>/` (path `/`, a `float` query at most) whose port is not the one the window's origin has. That navigation is stopped, and the main admits it when `<p>` is the port its own server last reported, or when `listening` with `<p>` arrives or `GET /api/health` on `<p>` answers as an oculus within 5 s, whichever comes first; it then loads the address in the same window (`webContents.loadURL`) and keeps `<p>` as that window's server. Otherwise the address goes to item 5's decision. So a navigation that reaches the main before `listening` is admitted and never sent to the browser. The page's `window.name`, which carries the arrangement, must survive that load; the builder's first run checks it on the unchanged design's probe and stops, as "Cases" says, if it does not. A window onto an oculus the app did not start uses that server's folder picker as it is: the server has no parent, so `handlePick` runs the JavaScript for Automation panel (item 9).

1.3. The switches a start admits. `--engine <dir>`, with `parseEngineArgs`'s rules, handed to the server; any other argument is refused with `parseEngineArgs`'s sentence in a dialog, except Chromium's own switches, which Electron consumes. The remote debugging port is on only when the start names Chromium's `--remote-debugging-port=<n>`, which Chromium binds to 127.0.0.1; nothing in the app, in `npm run app`'s script or in the packaged stub sets it, so a start without it has no debugging port. The look passes it (Z557). `--crash-window-after=<s>` is a test-only switch the app admits: the main calls `webContents.forcefullyCrashRenderer()` on the first main window's page once, that many seconds after its first load; nothing sets it but case 25.

### 2. One instance

`app.requestSingleInstanceLock()`, taken before anything else the main does: a second start prints the catalog line `server.start.already_running` (`oculus is already running; its window is brought to the front`) on its output, quits with status 0 and starts no build and no server; the first takes `second-instance` and shows its main window, opening one when none is open. The second start's arguments are not taken.

### 3. The windows' lifetimes

The main window is a `BrowserWindow` on the server's page. Closing the last main window leaves the app and the server running, as a macOS app does; a Dock click (`activate`) or File > New Window opens the main window again, with its popped-out windows (item 8). A window whose page crashes (`render-process-gone`) is reloaded, the reason printed on the app's output.

Every window: `contextIsolation: true`, `sandbox: true`, `nodeIntegration: false`, `nodeIntegrationInSubFrames: false`, `webSecurity: true`, the preload of item 12, `spellcheck: true`. These options are made by one pure function that imports nothing from `electron`, so G47's test reads them. The page's headers and `sameOrigin` are unchanged: Chromium sends `Sec-Fetch-Site` and `Origin` as Chrome does, so the guard admits the window's requests with no change to `sameOrigin`.

Permissions: `setPermissionRequestHandler` and `setPermissionCheckHandler` grant `clipboard-read`, `clipboard-sanitized-write` and `fullscreen` to the server's origin and deny every permission to every other origin and every other permission; the decision is one pure function, read by G47's test.

### 4. Window state

The main window's bounds, maximised and full screen state, and zoom factor are written to `~/.oculus/window.json` when the window moves, resizes, changes state or closes (debounced 500 ms, through a temporary file and a rename), and read before the window is made. A file that is missing or does not read opens the window at 1280 by 800 centred on the primary display; a saved place on no attached display opens on the primary display, its size kept and clamped to the display's work area. The popped-out windows keep their places in the arrangement (item 8), not in this file, and are clamped by the same function.

### 5. Links and navigation

One pure function, which imports nothing from `electron`, decides where an address goes: the server's own page (same origin, path `/`) opens in an app window, a main window when it carries no `float` query and the popped-out window of item 8 when it does; any other `http:`, `https:` or `mailto:` address, same origin included (a file's own address from `pages.ts:506` and `row-menu.ts:524`), opens in the default browser through `shell.openExternal`; any other scheme is refused and printed. It is applied by `setWindowOpenHandler` (every `window.open` and `target="_blank"`) and by `will-navigate` and `will-frame-navigate` (a top-level navigation to another origin is stopped and handed to the same decision, a port move of item 1.2 first; a subframe keeps navigating as the page's own policy allows). The page's code is unchanged for links: Open Worktree in New Window (`Worktrees.svelte:121`) opens a second main window, an Inbox thread (`InboxCard.svelte:141`) and a terminal's link (`TerminalGrid.svelte:301`) open in the browser.

A download (`will-download`) keeps Electron's Save dialog.

### 8. A floating pane in a window of its own (Z3)

A popped-out window is a page of its own: the server's page loaded with `?float=<id>`, with its own client, socket and stores, drawing the float with that id and nothing else (no rail, no status bar), filling the window. Both pages hold the whole arrangement and follow each other's writes through the `storage` event they already follow (`takeSaved`), so a move made in one window shows in the other. The main window's FloatLayer leaves out every float placed in a window, as it leaves out every place that is not free before it styles one (`FloatLayer.svelte:54-58`), so `floatStyle` never receives a window place; its doc comment (`float-geometry.ts:37-39`) says so. Every library draws in its own document, so nothing of Monaco, xterm, bits-ui or interactjs is made window-aware.

The arrangement: `FloatPlace` gains `{ kind: 'window'; x; y; w; h }`, the window's content bounds in screen points (`model.ts:111-113`, `saved.ts:124-138`, `placeFits`, which holds a window place to finite numbers with `w` and `h` at least 200). The envelope's version stays 6: a page of this code reads its own writes, and a window place met by a page with no bridge (Chrome) is read as the default free place (`floats.ts:65`) with its tabs kept, and written back only when that page changes the float. `DropLayer.svelte:39`, `navigation/arrangement.ts:91,99,120` and `layout/index.ts:27` stay true unchanged: they count free floats, build config places and re-export the type.

One writer at a time: in the app, every save of the arrangement goes through the main process, one window at a time. A page's save sends the new envelope together with the envelope it was made from (`ipcRenderer.sendSync` in the preload, which a sandboxed preload has); the main keeps the last envelope it admitted and admits a save only when the envelope it was made from is that one (any save while it holds none), and the page then writes `localStorage` and the write record as it does now. A refused save is answered with the admitted envelope: the page takes it as `takeSaved` takes another page's write and runs the same store operation on it again, by the name and arguments `named()` already wraps (`layout.svelte.ts:786-804`). Two windows changing the arrangement at once therefore lose neither change, which the write record under `oculus.layout.writes.v1` shows. In Chrome nothing changes.

One page keeps the tabs: the upkeep a client runs over the whole arrangement because a payload changed (a Terminal tab closed when a `sessions` message stops naming its terminal, in `state/sessions/terminals.svelte.ts`, and every other follower that closes, moves or rewrites a tab from a payload, found with `grep -rn "afterReceive\|closeInstance" src/lib/state` and named in the report) runs only in a main window's page. A popped-out page's client is built with that upkeep off, through the same optional argument of `createClientState` that carries the bridge (item 12), and acts only on what its own reader does; the main window's page acts once for every tab, the popped-out float's included.

What opens one (the words in item 13): a float's strip menu and pane menu, Move into New Window (the float placed in a window at its place on screen, 600 by 400 when it was docked); a pane's strip menu and pane menu, Move into New Window (`floatPane`, then the same); a tab's right-click menu, Move into New Window (`floatTab`, then the same) and Copy into New Window (a new instance of the same view with a copy of the tab's state, in a new float placed in a window; not offered on a Terminal tab, since a terminal belongs to one tab, HELP.md:138); a tab dragged and released outside every oculus window, a new window at the release point (VS Code's `workbench.editor.dragToOpenWindow`); a tab dragged from one oculus window and released over another, the tab moved into the pane under the pointer there (the source page hands the release to the main process, which finds the window holding the point, the one focused last when several do, and hands the point to that page, which runs its own drop hit test and performs the move). None of these is offered in a page with no bridge.

What the popped-out window's menus offer: its strip and pane menus hold Restore into Main Window (the float free in the main window, at the default place), Return to Page (`returnFloat`), Dock Left, Dock Right and Dock Bottom (docked in the main window), Lock Group and Unlock Group, Switch to Main Window, and no split, fold, maximise or Float; its tab menu holds Move into New Window and Copy into New Window.

How a window follows its float: the main process keeps one window per float id; a page that finds a float placed in a window and no window open for it asks the main to open one, and the main opens none twice. A window place on no attached display opens on the primary display, its size kept and clamped to the display's work area, by item 4's function. The main tells the page of a popped-out window its new bounds after `moved` and `resized` (debounced 500 ms), and that page writes the place. A popped-out page whose float no longer exists (returned, closed elsewhere) asks the main to close its window.

What closing does: closing a popped-out window by its close button or Cmd+Shift+W puts its tabs back in the main window as a free float at the default place, terminals running and unsaved text kept, with no question; Cmd+W or Close on the last tab of a popped-out window closes the float, as closing a float's last tab does now, and its window with it, asking nothing beyond G28's question over unsaved text or a running terminal; closing the last main window closes its popped-out windows and keeps their places, so they open again with the next main window; Quit keeps them likewise, and the next start opens them where they were.

Move Terminal into New Window is a Terminal tab moved by Move into New Window: the terminal detaches from the page it leaves and attaches in the new window's page, and keeps running (G28's "ends no terminal when it moves").

The store's split: `layout.svelte.ts` is 886 lines and gains the window operations, so the step splits it by concern before it adds them (spec.md:45). The load and follow of the saved arrangement (`unfollow`, `takeSaved`, `loadLayout` and `stopFollowing`'s entry, :394-462 and :828-831) and the save turn above move to a new module `state/workbench/layout/saved/load.ts`, built beside the factory and handed the access object as the modules under `layout/open/` are (`layout.svelte.ts:15-20`), with what it needs of the factory's `fresh` and `pendingFloats` handed through that object; `layout/index.ts` re-exports it as it re-exports the others. The factory keeps the rune, the write path and the operations. The head comments of both files say what each holds. If the factory still passes 880 lines with the window operations, the float operations (:746-776 and their entries) move the same way to a module the report names, and the report quotes `wc -l` of each file.

## Cases

Each case runs the app from the worktree under the recipe of "The look", on a scratch hub, a scratch HOME and the scratch tmux socket, never on port 8787 or 8790. A case that needs a press, a drag or a look at the screen is checked by the look at landing (the report names the state to put it in and what should be seen); every other case is checked by a command whose output the report quotes. A server is counted by the utility process's identity, never by `pgrep -f "src/server.ts"`: the utility processes whose parent is the app's main process and whose arguments carry `--type=utility`, read with `ps -ax -o pid,ppid,args`, the exact arguments settled by the builder's first run, which quotes `ps -o pid,args` of the running app.
