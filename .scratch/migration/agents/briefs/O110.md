## What is on the tree (read on main at 35db337bb; `src`, `tests`, `docs` and `config` unchanged since f63c790f5)

- `src/lib/server/machine/pty/tmux.ts:279`: `createParser`'s `feed` holds the control stream as a latin1 string, one character per byte, since `%output` lines carry bytes. Read with `grep -n "toString('latin1')" src/lib/server/machine/pty/tmux.ts`.
- `createParser`'s `line` pushes a line inside a `%begin` block onto `block.lines` as it stands, so a reply line is that latin1 string (`tmux.ts`, the `block.lines.push(text)` line).
- `control()` resolves a command with `reply.lines.join('\n')` at `tmux.ts:378`, with no decoding back.
- `channel.ts:788` then runs `Buffer.from(screen, 'utf8')` on the screen read through `this.#driver.read` (`channel.ts:774`), so every byte above 127 is encoded twice.
- Seen on a scratch server on the v1.0.0 build: a pane that printed the record glyph U+23FA drew `<a-circumflex><masculine ordinal>`, a row of U+2500 box characters drew about three characters each and wrapped over two rows. `#attach` calls `driver.attached` (`channel.ts:752`) before the read (`:774`), and `open` sets the client at once (`:253`), so every replay reads through the control client, a page's first attach included; `run` is used only when that client failed. In a probe on a private socket the same capture gave line lengths `[9,49]` by `run` and `[15,135]` through the control client. Leaving a rail leaves the sink attached (`channel.ts:668-682` drop it only when the socket closes), so a return reads through the same client.
- A `%error` reply's text goes through `new Error(text)` at `tmux.ts:379`, is caught at `capture.ts:268`, `:272` and `:305`, and reaches the server log, with the same fault.
- tmux writes a reply and an `%error` line as raw UTF-8 bytes, read with `tmux -u -C attach-session | od -c` on a private socket: `342 217 272` for U+23FA, `342 224 200` for U+2500, `360 237 230 200` for an emoji. tmux replaces a raw 0xFF typed into a pane before it reaches a reply, so an invalid sequence does not reach this code.
- `createParser` also passes the `rest` of an event through as latin1, and the one reader of events, `channel.ts:236`, tests `event.name` alone, so no character of `rest` reaches anyone.
- `tests/server/machine/pty/tmux.test.ts` feeds the parser recorded bytes with no tmux running, through `feed`, which encodes its text as latin1; the one case there holds `%output` and no reply. `channel.test.ts` uses a fake driver and `pane-screen.test.ts` reads through `run`, so neither reaches this code.
- `tmux.ts:12-15`, the head comment, says the stream is decoded to a Buffer once a whole line is in, which holds for `%output` alone after this step.
- Every reply through a control client comes from `capture.ts`: `captureArgs` (:25), `historyArgs` (:35), `savedScreenArgs` (:44), `alternateScreenArgs` (:49), `alternateOnArgs` (:54) and `cursorArgs` (:88). `grep -n "Buffer\|latin1\|toString\|decode\|encode" src/lib/server/machine/pty/capture.ts` prints nothing, so none of them decodes or re-encodes.
- `docs/adr` does not exist; no ADR touches the step.

## What to build

A reply read through the control client gives the text the pane holds: every character above ASCII comes through as itself, a reply's lines are UTF-8 text from `createParser`, and `%output` stays bytes.

- `src/lib/server/machine/pty/tmux.ts`: `createParser` turns a reply line from its held latin1 form back into the bytes tmux wrote and decodes them as UTF-8 where the line joins the block. `ControlReply`'s doc comment says a reply's lines are text, and the head comment at lines 12-15 says the latin1 holding serves both forms: `%output` becomes a Buffer and a reply line becomes UTF-8 text. The `%output` path and the line splitting in `feed` keep working per byte, so a character cut across two chunks still arrives whole.
- `tests/server/machine/pty/tmux.test.ts`: one test, a table, titled 'decodes a reply to the text the pane holds', with one row per row of the first case below. Its bytes are the recorded ones above, given through a helper that feeds a Buffer, since `feed` encodes as latin1.

Every screen read through the control client follows from this one change: selecting a terminal, a page's first attach, coming back from another rail and a resize, on the normal and the alternate screen. A line of box characters no longer wraps, which is what broke the input box Claude draws at the bottom of its screen. The report goes through the six argument builders of `capture.ts` and states for each that its answer is right after the change, the two `display-message` ones holding numbers and flags only.

## Cases

  - a `%error` block with a non-ASCII line: the line is the text and `error` is true;

  - an `%output` line with octal escapes and raw non-ASCII bytes between two ASCII replies: the output bytes as before, the replies as they stand.

## Decisions taken in this brief (each reversible, none silent)

1. The decoding sits in `createParser`, at the reply line, and not in `control()` after the join: the parser is what holds the stream as latin1, so it hands out text, and the parser tests need no tmux.
2. An event's `rest` stays as it is, since nothing reads its characters.
3. G90 is widened and no new entry made, by open item 615 in `plan.md`'s Rulings: the guarantee is the screen as tmux holds it.
