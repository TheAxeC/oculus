## What to build

1. **Mark posted writes the date and `publish: True`.** `markLinkedinPosted` sets, in the front matter of the idea it promotes, `date:` to the day the button is pressed (`localDate(Date.now())`, the function Add Idea dates with) and `publish:` to `True`, and renames as now. The front matter is the lines from the file's first line, which is `---`, to the next line that is `---`.
   - The idea's name is accepted by the rule the view offers the button by: a base name that starts with `xx-` and ends with `.md`, holding no path separator. The numbered name is the next `NN-` followed by the rest of the name after `xx-`, and the sidecars are the files whose name is the idea's name without `.md` followed by a dot, as now. The refusal sentence `server.feeds.post_needs_idea` reads "A LinkedIn post must name an xx-*.md idea." as now.
   - A line of the front matter whose key, at column 0, is exactly `date` or exactly `publish` is replaced whole by `date: <day>` or `publish: True`, each such line when there are two; a quoted date or a date with a time becomes the unquoted day the stub writes. A key such as `published:` or an indented `date:` is not one of them.
   - A key the front matter lacks is added as a line before its closing `---`, `publish` before `date`.
   - Every other byte of the file stays as it was: the other front matter lines, the body (a `date:` line in the body included) and the line ends.
   - A file whose first line is not `---` (a byte order mark before it included), or whose front matter has no closing `---`, is refused with a new sentence `server.feeds.post_no_front_matter` in `config/text/server.yml` beside `post_needs_idea`: "The LinkedIn idea has no front matter between two --- lines."
   - The new text is checked before any file moves: its front matter is parsed with the `yaml` library the module imports, and a result whose `date` is not the day or whose `publish` is not `true` is refused with a new sentence `server.feeds.post_not_dated`: "The LinkedIn idea's front matter did not read back with the new date and publish: True." Every refusal leaves the files as they were.
   - The order: the idea is renamed to its numbered name with `renameSync`, its new text written in place with `writeTextAtomic`, then the sidecars renamed. A failure after the rename leaves a numbered post with its old text, which the refusal's sentence or the thrown error names.
   - The record stays one record of the renamed names with `undo: 'none'`, and its comment says the write also dates the post.
   - The comments of the page's call (`writes.svelte.ts:519-520`, `shapes.ts:375`) say the write renames the idea and sets its date and `publish:`.

## Decisions taken in this brief (each reversible, none silent)

1. The front matter is edited line by line, not re-rendered through a YAML library, so every byte the write does not name stays as written (G8).
2. A missing `publish:` or `date:` is added before the closing `---`, `publish` first, the order of the stub; the hub's ten ideas all hold both, so this reaches only files written by hand.
3. A file with no front matter is refused rather than given one, since the LinkedIn view reads a post's date from its front matter and a written front matter would be oculus's guess at the title and category; nothing moves.
4. The record keeps `undo: 'none'` and names the renames only; the dated text has no inverse writer, as the rename has none.
5. The day is the local calendar day of the server, the one Add Idea writes.
6. The tip's and `ontrack`'s words drop the spaced hyphen (the prose rule bans it); the tip starts in lower case as its siblings do.
7. The idea name rule is the view's (`xx-` and `.md`), so every file the view offers the button on is accepted.
8. The idea is renamed first and written in place, so the post keeps the idea's file mode and a failure never leaves the idea and the post both listed.
9. A file with carriage returns is not handled apart: no post or idea holds one, and its first line `---<CR>` is then refused as no front matter.
