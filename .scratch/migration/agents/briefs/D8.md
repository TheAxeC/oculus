## The shapes this brief sets (recommended by the orchestrator, booked for Axel's ruling, built as written)

1. An account is a row of `config/local.yml` `calendars:`: `{ provider: google | microsoft, label: <word> }`, the label unique per provider, read by `loadLocal` into `LocalConfig.calendars` (an empty list when absent, a thrown error naming the key on a bad row, as `hpc_host` and `accounts` are handled); `local.yml` also gains `calendar_dir`, the folder of the credential files, `~/.oculus/calendar` by default, read as `changes` and `bookmarks` are, so a served test run points it at a folder of its own and never at the reader's. The polling settings are `config/behavior.yml` `calendar: { poll_min: 15, days_back: 1, days_ahead: 14 }`, read by a `calendarSettings` beside `slurmSettings` with the same throw on a missing or mistyped key.
2. An account's credentials live in one file, `<calendar_dir>/<provider>-<label>.json`, mode 0600, written by Axel for the client half and by the connector for the token half: Google `{ client_id, client_secret, refresh_token? }` (a Google Cloud OAuth client of the Desktop kind, whose secret is not a secret and whose loopback redirect allows any port), Microsoft `{ client_id, tenant, refresh_token? }` (an Entra app registration of the public-client kind, `tenant` defaulting to `common`). The server reads the file at each poll and never logs, publishes or answers any of its fields; the Keychain is never read; a file that is absent or holds no `refresh_token` puts the account in the state `not connected` with the path the reader must create, in the view and nowhere else.
3. The connect flow is OAuth authorization code with PKCE, the redirect the server's own loopback: the view's Connect control on an account calls `POST /api/calendar { action: 'connect', account }` (origin and token gated), the server builds the provider's consent URL with the read-only scope (`https://www.googleapis.com/auth/calendar.readonly`; `Calendars.Read offline_access` for Microsoft), a fresh `state` and a PKCE verifier held in memory for ten minutes, opens it through an `Opener` (the operating system's `open <url>`, injectable so no test opens anything), and answers `{ ok: true }`; the provider sends the reader's browser to `GET /api/calendar/callback?code&state` on `127.0.0.1:<local.port>`, which is the one route without the token gate (the browser arrives there from the provider, not from the page), checks `state`, exchanges the code at the provider's token endpoint with the verifier, writes `refresh_token` into the account's file, drops the verifier, and answers a plain page saying the account is connected and the tab can be closed; a wrong or expired `state` answers 400 and writes nothing. The refresh token is exchanged for an access token at each poll and the access token is held in memory only.
4. The poller: `server/calendar/poll.ts` `watchCalendar(hub, options)` with the shape of `watchHpc`: one poll over every account every `poll_min` minutes, `RETRY_MIN` 2 after a failure per account, the last good events of an account kept under its state word when a poll fails, one poll at a time, `refresh()` and `close()`, an injectable `fetcher` (the `fetch` the providers are called with) so tests reach every branch without the network. One complete state per poll on the `calendar` channel: `CalendarPayload = { status: 'ok' | 'error' | 'unconfigured', accounts: CalendarAccount[], events: CalendarEvent[], updated, pollMin, retryMin, daysBack, daysAhead }`, `CalendarAccount = { provider, label, status: 'connected' | 'not-connected' | 'error', hint?, lastOk?, calendars: { id, name }[] }`, `CalendarEvent = { id, account, calendar, title, start, end, allDay, location?, link?, status?: 'confirmed' | 'tentative' | 'cancelled' }`, events sorted by start over the window from `days_back` days before now to `days_ahead` days after, `start` and `end` ISO strings with the offset the provider gave. Google reads `calendarList` (the calendars with `selected` true) and each one's `events` with `singleEvents=true`, `timeMin`, `timeMax`, `orderBy=startTime`, following `nextPageToken`; Microsoft reads `/me/calendars` and each one's `calendarView?startDateTime&endDateTime` with `Prefer: outlook.timezone` left to the account's default, following `@odata.nextLink`. A provider's error answer (401 after a refresh, 403, 429, 5xx) puts that account in `error` with a one-line hint made of the status and the provider's error code, never its body.
5. The Calendar view: `views/Calendar.svelte`, `id: 'calendar'`, listed, `group: 'personal'`, `order: 1` (after Memories), label "Calendar", glyph `calendar` added to `config/glyphs.yml` and `config/icons.yml`. What the reader sees: a head as the HPC view's (the "as of" time, stale after the period plus two minutes, a Refresh control, the polling word), one row per account with its state word, its label and its Connect control (shown when `not-connected`, disabled while a connect is pending), then an agenda: the events of the window grouped by day with a heading per day (today marked), each event one line with its time or "all day", its title, its calendar name and the account label as a chip, its location, a link control opening the provider's page through the open route when the event carries one; a cancelled event struck through, a tentative one marked. The Command center, the ticker and the Focus board are not touched; the rail badge is the count of today's remaining events, empty when none, through `badge`, `badgeTitle` and `badgeCells` as the HPC registration does.
6. The routes: `POST /api/calendar` with `action: 'refresh' | 'connect'` (and `account` for connect) through `server/calendar/routes.ts` with the gates of `handleHpc`; `GET /api/calendar/callback` as in shape 3. No route answers a token, a secret or an event body.

## Decisions taken in this brief (each reversible, none silent)

1. The credentials file is per account and hand-created for its client half, so no client id or secret is ever in the tracked tree or in `local.yml`; the server writes only the token half.
2. The callback route is the one unauthenticated route, since the provider's redirect carries no oculus token; it is guarded by the `state` it minted and writes only the field it was asked for.
3. Read-only scopes only, in both providers; no write, no invitation response, no free-busy publishing.
4. The window is by days, not by month grid; an agenda over two weeks is what the reader uses the view for, and a grid is a later shape if he asks.
