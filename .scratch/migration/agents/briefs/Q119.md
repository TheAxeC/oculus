## What to build

When the step is done, a wrong value of a setting in `config/behavior.yml` or of a key in `config/local.yml` never stops the server and never resets more than that one setting: the reader answers that setting's default, every other setting is read as written, and the Findings view lists one finding naming the file and the key. This holds at start and on every change while the server runs.

### 1. One rule for a setting of behavior.yml

The readers are the ten of `settings.ts` and the three start checks (Decision 1): `editor.paint_limit_kb`, `git.autofetch_minutes`, and `usage_refresh_min` with `usage_refresh_model`.

1. A leaf key (a scalar, or a list read as one option such as `processes.patterns`):
   - absent from its block, or its block absent or null: the catalog's `default` for the key, and no finding (Decision 3);
   - present and failing the reader's shape (null included): the catalog's `default`, and one finding naming the dotted key (`slurm.poll_min`, `usage_refresh_min`);
   - the catalog has no entry for the key, or its `default` fails the same shape, and the value is wrong: the reader throws one sentence naming the key and saying `config/catalogs/options.yml` holds no default that reads (Decision 2). A value that reads never needs the catalog.
2. A block that is present and is not a map (`slurm: 5`, `slurm: [1]`): every key of the block takes its default, and one finding names the block (`slurm`).
3. A family (`usage_tiers`, `open.program_ext`), which has no catalog default (Decision 4):
   - a member whose key or value fails the reader's shape is not read, and one finding names it (`usage_tiers.b`, `open.program_ext..x`); every other member is read;
   - the family present and not a map: the empty map, and one finding names the family;
   - absent: the empty map, no finding.
   - `programApps` (`data/helpers/files/opens-in-program.ts:58-68`), the one rule the page and the server share, drops a member it cannot read instead of answering null for the whole map, so the cards and the open endpoint offer the same extensions. It still answers null for a missing or non-map `program_ext`, which the page reads as `{}`.
4. The default is read through the same shape as the value, so a default that does not read is never handed to a poller.
5. The readers keep their exported names and value types, so the callers that need only values (the routes, `writes.ts:258`, `host.ts:95`, `open-fixture.ts`) do not change: each answers the value with defaults in place and throws only in the case of 1.3. The three start checks become readers of the same kind beside the others in `settings.ts` (so G13's Code line and test cover them), answering the minutes, the paint limit in kilobytes and the refresh settings with defaults in place; `requireAutofetch`, `requirePaintLimit` and `requireRefreshSettings` are deleted, `server/core/fetch-period.ts` with them when nothing is left in it. `paintLimit` (the page's read, `editor.ts:32-35`) answers the bytes of the value, else of the catalog default, else null (a configuration without the catalog, which is the page before the config channel's first message), from the same rule as the server's reader, not a copy of it.
6. One function of `settings.ts` answers the problems of every setting above for a merged configuration: the dotted key and the words of what it must be (Decision 5). `behaviorFindings` (`catalogs.ts`) words each as a finding against `join(configDir(engine), 'behavior.yml')`, in place of its own `paint_limit` finding, so the start's `reportFindings`, the config payload of `portfolio.ts` and `FINDERS` carry them with no new line in those lists.
7. The sentences are new keys of `findings.config` in `config/text/findings.yml`, each read by a string literal (G24), and every "must be" words of the readers (`CADENCE_WORDS` and the rest, `settings.ts:35-42`, the words passed to `settingOf`) become catalog lines the sentences are filled with, since they now reach the Findings view. The `paint_limit` key goes, its finding becoming the general one.

### 2. Where the behavior.yml readers are called

1. `context.ts`: the start reads every group through the readers and starts every poller with what they answer; the lines "Read for their check alone" (:277-285) and the start's `requireRefreshSettings` (:371-374) go, and its comment says the new rule. `processesSettings` drops its `findings` parameter (the dropped-file rule moves to live-settings, 2.2).
2. `live-settings.ts`: each push reads each group, so a wrong value hands the poller the default and a corrected value hands it the value, each only when it differs from what is held (as now). A push whose merge dropped `behavior.yml` (its finding with key `''` on that file, the test `behaviorDropped` makes now) keeps every group's settings in force and hands nothing on, since a file that does not parse is no wrong value of a setting; the next push that reads the file takes its settings (Decision 7). `attempt` stays around each setter and the 1.3 throw, so a setter that throws is still logged once.
3. `refresh.ts`: the refresher takes typed settings and trusts them; its own checks at :170 and :360 go.

### 3. One rule for a key of local.yml

1. A text-level reader in `local.ts` answers, for a text, the values with defaults in place, the problems (the key, as the sentences name it now: `port`, `accounts[1].tool`, `calendars[1].label`), and whether the text read at all. `applyLocal`'s checks become problems:
   - a scalar key with a wrong value (`hub`, `port`, `hpc_host`, `claude_bin`, `open_bin`, the ten path keys): that key takes its default (`localDefaults`, or absent for an optional key) and the others are read;
   - a list key that is not a list (`accounts`, `calendars`, `mail`): that list takes its default;
   - a row of such a list that fails a check (not a map, a wrong tool or provider, an empty dir or label, a label that repeats): that row is not read, and the rows before and after it are (Decision 4);
   - a text that does not parse, or is not a map: every default, one problem with key `''`, and the text marked unread.
   - An unknown key stays as now: warned on stderr and ignored, no finding.
2. `loadLocal(engine)` reads the file through it and never throws: a missing file is every default, and a file that cannot be read (an `EACCES`, a folder at the path) is the unread case with its reason. `loadLocalOrDefaults` and `reportedLocal` go (Decision 8); its seven callers call `loadLocal`.
3. A finder of `local.ts` words each problem as a finding against `localFile(engine)` with the key, and the message `<key> must be <words>; the default is used` (a row: `...; the row is not read`; the unread file: the parse error's first line, or that it is not a map). `context.ts`'s start prints them with the other findings, and `portfolio.ts`'s config payload carries them, so a write of `local.yml` shows its findings within one config push.
4. `checkLocal(text, file)` keeps its signature and answers the first problem's sentence in today's form, `${file}: ${key} must be ${words}` (every row of `local.test.ts:13-51` keeps its sentence, and D11's `local.yml: rite_dap_bin must be a non-empty string` holds), or null. The source tab's save and the account rows' writes are refused exactly as today.
5. `reloadLocal` (`context.ts:653-669`) reads through the same reader: an unread file keeps every value in force and says why once (as now); a file that reads hands on the values it read, a wrong key's default included, so a wrong key costs that key alone (Decision 10 for `port`).

## Decisions taken in this brief (each reversible, none silent)

1. **The three start checks are in the step.** (a) Only the ten readers of `settings.ts`: a wrong `usage_refresh_min`, `usage_refresh_model`, `git.autofetch_minutes` or `editor.paint_limit_kb` still stops the server at start, against the ruling's reason that a typo costs one setting and the server still starts; less code. Chosen (b). The lazy option is (a).
2. **The default is the options catalog's `default`, and a wrong value with no usable default throws.** The tree has one `behavior.yml`, and the catalog's `default` is "the value the tracked file holds"; `processesSettings` already reads it, and `agents/spec.md` puts a default in the config file, never beside a read. For the case where the catalog also fails (a hand edit that breaks `options.yml` while a value is wrong): (a) throw naming the key and the catalog, so the start stops with both causes named and a running server keeps the group in force through `attempt`; (b) a literal fallback in code, which `agents/spec.md` forbids; (c) the poller or route that needs the setting stays off with a finding, which needs an "off" state in every consumer for a case two broken shipped files make. Chosen (a); the case 9 test proves every shipped default reads. The lazy option is (b).
3. **A missing key or block is its default with no finding.** (a) Silent, as `readEditorOptions` (`editor.ts:180-183`), `processesSettings` and VS Code's settings treat a missing key, and as a merge that dropped the file needs to avoid a finding per key; (b) a finding per missing key, which catches a misspelt key name but floods the Findings view whenever `behavior.yml` does not parse, unless every finder is handed `loadConfig`'s findings. Chosen (a). Neither is the cheaper one by much; (b) is the one with the false findings.
