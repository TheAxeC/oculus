## What to build

When the step is done, saving a file a linter takes, or showing a source tab of such a file with no unsaved text, runs that linter on the file on disk in the background; its findings are Monaco markers in every editor of the file on the page and rows of the Problems view under the file, with VS Code's severities, sources and codes; a quick fix, a disable comment and the rule's documentation are offered where the linter gives them; a linter that is missing, failing, not approved or switched off says so on the status bar and never throws.

1. **The program runner, once.** `run` and its types move from `src/lib/server/content/latex/tools.ts` to a new `src/lib/server/core/program.ts` (core 9 to 10 items), with `onPath` from `content/latex/recipes.ts:241-246`; `tools.ts`, `recipes.ts`, `endpoint.ts`, `synctex.ts` and `texdoc.ts` import them from there and behave as today. `run` gains two options: `findings`, the exit codes whose stdout is the answer (`done` with the code), and `signal`, an `AbortSignal` that kills the child and answers `stopped`. The head comments of both files are rewritten.

2. **The linters' table and readers** (Z729 O1, O8). A new folder `src/lib/server/machine/runs/lint/` (runs 3 to 4):
   - `linters.ts`: one entry per linter id `chktex`, `ruff`, `eslint`, `shellcheck`: the extensions it takes (O8), the program (the configured path or the name on PATH, O3), its arguments as a list, the exit codes that carry findings, and its reader. ChkTeX: `-q -I0 -f<format>` with the newline character, the configured arguments (O3) and `-l <.chktexrc>` when one is in the file's folder or the repository's root folder, as LaTeX Workshop does; exit codes 0, 2, 3. ruff: `check --output-format json --no-cache --force-exclude <file>`, cwd the file's folder; exit codes 0, 1. ShellCheck: `--format=json1 <file>`, cwd the file's folder; exit codes 0, 1. Every path is one argument.
   - `readers.ts`: the four readers of each linter's output into rows `{ line, column, endLine, endColumn, severity, message, code?, href?, fixes }`, each JSON read through a zod schema beside it (`DESIGN.md`, "Untyped input"), an output that does not read being a `failed` answer, never a throw. Severity as VS Code's: ChkTeX `Error` error, `Warning` warning, `Message` info, columns converted from bytes and tabs (TabSize from the `.chktexrc` used, else 8) to characters as LaTeX Workshop's `convertColumn`, the end at column plus length, the message as ChkTeX prints it and the code its number; ruff `F821`, `E902` and a row with no code (a syntax error) error, every other rule warning, `href` its `url`; ESLint severity 2 error, 1 warning, a `fatal` message error, `href` the rule's docs URL; ShellCheck `error` error, `warning` warning, `info` and `style` info, the code `SC<n>`, `href` `https://www.shellcheck.net/wiki/SC<n>`. `fixes` (Z729 O5): ruff's `fix.edits` with its `fix.message`, ESLint's `fix` and each `suggestions` entry, ShellCheck's `fix.replacements` (one or two, as VS Code takes them); ChkTeX gives none.
   - `eslint.ts` (Z729 O1, O2): the held ESLint. One child process per repository and ESLint package, started by the first lint of a file under an approved configuration: the node that runs oculus (`process.execPath`, as `servers.ts` runs pyright) with a program of oculus's own that imports the ESLint package Node resolves from the folder of the nearest `eslint.config.*` (from the file's folder up to its repository's root), makes one `ESLint` with that folder as `cwd`, and answers each request on its standard input (a file path) with the file's messages and the rules' metadata as one JSON line; a file `isPathIgnored` answers no rows. The program is shipped so that it runs from the built server and from the desktop app as from `vite dev`. A request superseded or stopped is dropped by its id; a child that exits, hangs past the time limit or writes what does not read is ended and the next lint starts a new one. A child ends after 15 minutes with no request, at once when its repository's root stops being served or its approval changes, and with the oculus server; nothing it started outlives oculus. A file under no `eslint.config.*`, or in a repository whose `node_modules` holds no `eslint`, is not linted by ESLint.
   - `routes.ts`: `handleLint(request, token, roots, ...)`: a POST with the write token (G1) whose body names `{ root, path, linter }`, the path resolved inside its root through `resolveRootPath` (G2), refused as outside, a folder or a file that is gone; it runs that linter on the file and answers `{ ok: true, rows }`, or `{ ok: false, state: 'not_found' | 'failed' | 'timeout' | 'not_approved' | 'no_config' | 'off', reason? }`, `reason` the first line the program wrote to stderr. The time limit is 30 s per run. The request's own abort signal stops the run. A ChkTeX run that exits 0 with `Unable to open` on stderr is `failed`.
   - `src/routes/api/(machine)/lint/+server.ts` (5 to 6 items) joins Kit's request to `handleLint` over `browserRoots`, as `src/routes/api/(files)/source/+server.ts` does.

## Decisions taken in this brief (each reversible, none silent)

1. The server half sits in `server/machine/runs/lint/` (runs 3 to 4), since `server/machine` is full and a lint is a program oculus runs; the route in `routes/api/(machine)/lint/`; the page's store in `state/system/machine/lint/`, since `state/system` is full.
2. `run` and `onPath` move to `server/core/program.ts` so the LaTeX endpoint and the linters share one runner, widened by `findings` and `signal`, since every linter exits non-zero when it finds something and `run` drops stdout then (`tools.ts:49-59`).
3. A lint reads the file on disk, after a save or on a clean tab's open, never the tab's text, so the linter finds its configuration by the file's own path and the rows match the text that was saved. A tab with unsaved text keeps its last rows until saved.
4. A file's lint rows live while an editor of it is mounted on the page, as VS Code's ESLint, Ruff and ShellCheck clear a closed document's diagnostics; they leave with a served root through the source's `served()` filter, as `commandProblems` maps by `served()`.
5. One run per file and linter at a time: a new run aborts the one in flight, the route's abort signal ends the process, and a counter drops a late answer (the pattern of `builds.ts:605-620` and LaTeX Workshop's `linterProcess?.kill()`).
6. 30 s per run, since the measured ESLint cold run took 17.08 s on this machine; the held ESLint idles out after 15 minutes. Neither is a key.
7. ruff runs with `--no-cache` and ESLint without `--cache`, so no linter writes into a repository (ruff 0.06 s on the scratch file, so the cache saves nothing worth a write).
8. The owners are `lint-<id>`, defined once in `problem-sources.ts`; the sources shown are the names VS Code shows (`ChkTeX`, `Ruff`, `eslint`, `shellcheck`).

## Conventions

- ASCII only in every file under `tools/oculus`; comments say what and why, never history, at most 100 columns, a comment edited rewrapped as a paragraph.
- A source file at most 880 lines and a component at most 520; at most ten tracked items in a folder.
- Every user-facing string, the status item's words and the quick fixes' titles included, from a catalog through `t()`; a linter's own message is the linter's text, shown as it came; an error of a program or a library is mapped to a catalog line before it is shown.
- No module-level mutable state: the held ESLint children are held by an object the server context creates and passes in, never by a module variable; the lint store is created in the client context.
- The layer boundaries: `views/` imports no shell and no other view; `shell/` imports no view by name and reads the linters' state through `EditorStatus`; `ui/` imports no state; nothing client-side imports `lib/server/`.
- Every program is started with an argument array and no shell; a path from a request is one argument.

## Rulings on the choices

Each item below was raised by the brief's writer. O1 to O5 and O7 to O9 are closed with the recommendation each names (Z729, the orchestrator in automode, booked in `choices.md`). O6 is open item 12, for Axel; the builder is dispatched once it is ruled, with this section rewritten to the ruling.

**O1. How a linter runs.** Evidence: the plan line says "run as a process on save"; VS Code runs Ruff and ESLint as long-lived language servers that lint as the text changes, and ShellCheck and ChkTeX as a process per lint ("What VS Code's linting extensions do"). Measured: ruff 0.06 s and ChkTeX 0.16 s per file; ESLint's CLI 17.08 s cold and 6.98 s warm on one oculus file, whose config is type-aware. oculus's relay runs one server per language and root (`DESIGN.md:166`, G36) and `relay.ts` is 864 of 880 lines.
- (a) A process per lint for all four, the CLI with JSON, from a stateless route. Pros: what the step line says; one runner; no process to keep. Cons: every save of an oculus `.ts` or `.svelte` file shows its marks 7 to 17 s later.
- (b) The linters as language servers through D23's client: `ruff server`, `vscode-eslint-language-server`, `bash-language-server`, ChkTeX through texlab. Pros: VS Code's own architecture, on type. Cons: the relay must host two servers for one language (pyright and ruff, the TypeScript server and ESLint) in a file at 864 of 880 lines; `vscode-langservers-extracted` was last released 2024-05-08; ChkTeX through texlab contradicts Z703 (U8) and D43 is in flight; a much larger step.
- (c) (a) for ChkTeX, ruff and ShellCheck, and a held ESLint per repository: a child node process that loads the repository's ESLint once and lints each file on request, ended when idle, when its root leaves or its approval changes, and with the server. Pros: ESLint answers in the time of one file after the first, as VS Code's does; the three fast linters stay one process per lint. Cons: one held process with its lifetime to keep (O6 widens G36), and a program of oculus's own to ship to the built server and the app.
- (d) (c) through eslint_d 15.0.3. Pros: no held process written by hand. Cons: it writes `.eslint_d` into a repository's `node_modules/eslint`, keeps its own 15 minute lifetime unless given a parent pid, and falls back to its bundled ESLint.
- The lazy option is (a): it leaves ESLint at 7 to 17 s per save. Recommendation: (c). Ruled: (c).

**O2. ESLint runs the repository's code.** Evidence: an `eslint.config.*` is a JavaScript module importing plugins from the repository's `node_modules` (`tools/oculus/eslint.config.js`); `DESIGN.md:166` says what a repository's configuration would run is a process of the repository's text and takes the approval; `svelte-config:` is the precedent; the hub and officium hold ESLint configurations.
- (a) The repository's own ESLint runs only after the reader approves the text of its `eslint.config.*` files on this machine, an entry `eslint-config:<sha256 hex>` in the approvals file, made and taken back in a palette list `:eslint-config`; until then no ESLint rows and the status item reads `ESLint: not approved`. A repository with no `eslint` package of its own is not linted by ESLint.
- (b) Share the `svelte-config:` approval. Cons: approving a Svelte configuration would approve an unrelated ESLint configuration, and a TypeScript-only repository has none to approve.
- (c) Run without an approval, with oculus's own ESLint. Cons: still imports the repository's config and plugins, against `DESIGN.md:166`; plugins resolved against another ESLint can fail.
- The lazy option is (c). Recommendation and ruling: (a). The kind name, the list name and the status words are user-visible shapes.

**O3. The settings.** Evidence: `latex.<tool>_path` keys (`behavior.yml:147-154`) with Settings entries (`options.yml:660-680`); VS Code offers enable, path and arguments per linter; ChkTeX is off by default in LaTeX Workshop; D33 took no `problems.*` keys (Z702 (3)).

- (b) A `lint:` block in `behavior.yml`: `lint.chktex`, `lint.ruff`, `lint.eslint`, `lint.shellcheck` (`on` or `off`, all `on`), `lint.chktex_path`, `lint.ruff_path`, `lint.shellcheck_path` (empty finds it on PATH), `lint.chktex_args` (LaTeX Workshop's `[-wall, -n22, -n30, -e16, -q]`), in a Settings section "Linting".
