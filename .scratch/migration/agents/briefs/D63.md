# Brief: D63, apps in the shell

Size: a full step

Read `tools/oculus/.scratch/migration/agents/spec.md` first; its rules govern this step unchanged. It is also the one standards page the configuration lists. No ADR folder exists (`ls tools/oculus/docs/adr` answers no such file), so no ADR touches this step.

You work in the worktree `.agents/worktrees/D63` (from the repository root) and nowhere else; the base copy is `.agents/worktrees/D63-base/tools/oculus/`.

A design ruling decides what is built. It never exempts the code: every line is written to the standards pages, so that people can read, use and maintain it.

This step is the second of three (D62, D63, D64) that give an oculus app everything a VS Code extension can do. D62 built the host process, its JSON-RPC protocol, the frame's new methods and the management of apps. This step adds an app's contributions to the shell: commands, keybindings, menus, status bar items, views in the side bar and the panel, tree views, panels, custom editors, settings, quick pick, input box, messages and progress, and colour and icon themes. Rulings Z790 to Z805 shape each part, and they are restated below as requirements. The protocol table D62 wrote into DESIGN.md is kept: this step builds the rows it marks "later step" that the shell needs, and adds rows; it changes none (ruling 43). D64 adds the tools' contributions (language servers, debug adapters, tasks and terminals, source control, file decorations, and the `scm/*`, `debug/*` and `terminal/*` menus); nothing of this step is left for D64 beyond what D64's own line names.

## What to build

Every item holds for a machine app and a root app alike unless it says otherwise. An app adds nothing to the shell while it is unapproved, disabled, removed or changed since its approval: its contributions are drawn from its approval on, before its host runs, and withdrawn the moment one of those states begins (G77). Every id an app adds (a command, a container, a view, a custom editor's `viewType`, a setting key, a context key) starts with the app's `name` and a dot, so two apps never take one id; an id that does not is a finding that refuses the app. Two apps may share a `name` (a machine app and a root app, or root apps of two roots): an id an app earlier in the Views catalogue's order already declares refuses the later app with a finding naming both apps (Z807). When an app becomes unapproved, disabled, removed or changed, or its host stops, every open request of its host is withdrawn on every page, the host's promise settling `undefined`, its registered handlers, status items, tree views and panels go, and the context keys it set go (Z809). Every refusal word is one of `docs/apps.md` "Refusal words".

1. **The manifest key `contributes`** (Z790). `appShape` gains `contributes`, a map of VS Code's contribution points by their own names and shapes, written in YAML: `commands`, `keybindings`, `menus`, `viewsContainers`, `views`, `customEditors`, `configuration`, `themes` and `iconThemes`, each read in its own module under `read/` (the reader of `contributes` lives in a new module or subfolder, so `manifest.ts` stays under 880 lines). A fault in a point refuses the app with a finding keyed `apps[<id>]` and worded under `findings.apps` of `config/text/findings.yml`, except a menu id outside item 6's list or a container kind other than `activitybar` and `panel`, which drops that entry with a finding and leaves the app offered. A `when` clause anywhere in `contributes` that does not parse refuses the app with a finding naming the clause (item 4). `AppRow` gains `contributes`, the checked map, with a comment saying what it holds; the editor's JSON Schema of `app.yml` follows from `appShape` as today. The approval panel lists what the app adds, by kind and count, in plain words from `config/text/views/apps/apps.yml` ("adds 3 commands, 2 keys, 1 view, 1 setting, 1 colour theme"; the reader's word for a keybinding is "key", as on the key sheet and in HELP.md, while the manifest point keeps VS Code's name `keybindings`, Z813). `onCommand:<id>` and `onView:<id>` activation events name a declared command or view; one that names neither is a finding that refuses the app.

2. **The `app-shell` channel and the page's way back** (Z805). A new channel `app-shell`, added to `CLOSED_CHANNELS` (`data/helpers/files/apps.ts`), so a manifest that lists it is refused with the reason `findings.apps.carries.app_shell`; its payload type joins `Payloads` (`state/shared/stores/shapes.ts`) and its store `ClientState` (`state/client/shapes/client-state.ts`). Its payload holds, for each app with a running host, what the host registered (command handlers, status items, tree views with a change count per element handle, panels, context keys set by `setContext`) and the open requests of `oculus/ui` (quick pick, input box, message, progress), each with an id. The page asks and answers through `POST /api/app-host` with new actions under the write token: `run` (a command id with its JSON arguments), `provide` (a tree's children or tree item for a handle, a `validateInput` for a request id), `answer` (a request's result or its cancel) and `settings` (the page's notice that settings changed is the server's own, so `settings` reads one app's resolved values for a frame). A request shows on every page the server serves, a page that connects while it is open included; the first answer settles it and every other page withdraws it, and a later answer is answered `missing` and settles nothing. Three kinds of request are taken by one page, not answered on all (Z808, Z809): a host's run of an `oculus.<name>` command, a host's run of a command only a frame registered, and a host's panel; such a request is taken by the page that has the focus (`document.hasFocus()`), else by the first page that gains it, and waits while no page is open. Static contributions ride `AppRow.contributes` on the `apps` channel. The channel's payload type is beside `AppsPayload`, its shape in `src/lib/state/client/shapes/payloads.ts` and its reader in `src/lib/state/client/entities.svelte.ts`. The protocol rows this step builds (`oculus/register`, `oculus/unregister`, `oculus/provide`, `oculus/event`, `oculus/subscribe`, `oculus/unsubscribe` for the kinds `settings`, `visibility`, `selection`, `expand`, `collapse` and `dispose` (the tree view's expand and collapse events and a panel's `onDidDispose`), `oculus/ui`, `oculus/changed`, `oculus/settings/get`, `oculus/commands/execute`) lose their "later step" mark in DESIGN.md; the four `oculus/stream/*` rows stay marked for D64. A second `register` of the same id is refused `refused:registered`.

3. **Commands** (Z791). A declared command `{ command, title, category, icon, enablement }` (`icon` as `$(name)` naming a glyph of `glyphs.yml` or a path of a file of the app; `enablement` a when clause) is listed in Cmd-K as `<category>: <title>` (the title alone without a category) with the app's title as its hint, and its keybinding (item 5) as its key hint, while the app is approved and enabled and its `commandPalette` menu entry's `when` (item 6), if any, holds; an `enablement` that does not hold draws the row disabled. Choosing it fires `onCommand:<id>` through the manager's `activate`, which starts the host of an app that declares the command whatever its `activation` lists, as VS Code activates an extension for a contributed command, then runs the handler the host registered with `oculus.commands.registerCommand(id, handler)` (`oculus/register` kind `command`, run through `oculus/provide` kind `command` with the arguments), else the handler of an open tab of the app that registered it with the frame's `oculus.register('command', id)` (the frame's handler `onCommand(id, args)`), else a notice naming the command and the app. The host's connection object gains VS Code's namespaces `oculus.commands`, `oculus.window` and `oculus.workspace` beside its members (`registerCommand` answers a disposable whose `dispose()` unregisters). `oculus.commands.executeCommand(id, ...args)` (`oculus/commands/execute`) runs a command of any approved and enabled app (a command only a frame registered runs on the page item 2 names, through that app's open tab, and answers `missing` when no page holds one), `setContext` (item 4), and those of oculus's palette colon commands that change only what a page shows, as `oculus.<name>` with one text argument: `oculus.theme`, `oculus.file-icons`, `oculus.crt`, `oculus.tab` and `oculus.goto`, run on the page item 2 names (Z808). The other colon commands (`language`, `interpreter`, `compile-database` and `eslint-config`, which write configuration; `update`, which starts agents; `workspace` and `workspace-save`, which write the workspaces file; `folder`, which opens the system's folder panel; `accent` and `help`) answer `closed`, since no approval names what they do, and any other id answers `missing`. A frame gets `oculus.commands.execute(id, ...args)` with the same reach, an `oculus.<name>` command running on the frame's own page. A command an app runs counts under `apps.opens_per_min` per frame or host, and the sentence of that key in `config/behavior.yml` (line 306) says so.

4. **When clauses and context keys** (Z793, Z804). A `when` (and an `enablement`) is read with `ContextKeyExpr.deserialize` of `monaco-editor/platform/contextkey/common/contextkey`: `undefined` is the refusal of item 1, and `evaluate` reads a context of oculus's keys: `editorTextFocus`, `editorFocus`, `editorLangId`, `resourceExtname`, `resourceFilename`, `resourceLangId`, `resourcePath` (`<root>/<path>`), `explorerResourceIsFolder`, `view`, `viewItem`, `focusedView`, `activeCustomEditorId`, `activeWebviewPanelId`, `isMac`, `isLinux`, `isWindows`, and each key an app sets with `executeCommand('setContext', key, value)`, whose key must start with that app's name and a dot (else `refused:context_key`). A key nothing set is undefined, as in VS Code. The context is one module of the page, read where a menu, key or command is resolved; the keys an app set are kept per app in the `app-shell` payload and go when its host stops, so after a restart a key is undefined until the app sets it again. The import runs in Node and in the page; the brief's case 9 shows it.

5. **Keybindings** (Z792). `contributes.keybindings` entries `{ command, key, mac, linux, win, when, args }` in VS Code's key syntax (`ctrl+shift+p`, `cmd+k`, a two-part chord `ctrl+k ctrl+c`), `mac` taking the place of `key` on macOS, `linux` and `win` likewise; the key names are read by hand with `KeyCodeUtils` of the same monaco-editor package. On macOS `mac` takes the place of `key` when present, on Linux `linux`, on Windows `win`; `cmd` and `meta` name the Command key on macOS, `meta` and `win` the Super or Windows key elsewhere. oculus's own keys and the editor's come first: a binding is not bound, with a finding naming both, the app still offered, when it, or the first part of its chord, is a key oculus takes: a key `resolveKey` resolves or a chord prefix it reads (the letters of `nav_groups`, `g`), a key `workbench-keys.svelte.ts` resolves before it (Cmd+K and Ctrl+K, Cmd+P, Cmd+Shift+P, `:` and `?`), an editor key the key sheet lists, or a key of the desktop app's menu (the accelerators of `src/desktop/windows/menu.ts` and the keys of its roles, Cmd+Q, Cmd+H and Cmd+M). Two apps binding one key under one `when` give it to the app first in the Views catalogue's order, with a finding on the other. A binding is resolved after oculus's keys and before the browser, while no text field, overlay or editor holds the keyboard unless its `when` asks for `editorTextFocus` (then it is resolved in the editor too, after the editor's own keys). The key sheet (`?`) lists app bindings under a heading Apps, each with its command's title and app title; Cmd-K shows a command's key as its hint.

6. **Menus** (Z794). The menu ids built: `commandPalette` (a `when` hides a command from Cmd-K), `editor/context` (the source editor's right-click, through `addAction` with `contextMenuGroupId`), `editor/title` (a source tab's or custom editor's strip actions: group `navigation` as buttons with the command's icon, the rest in its More Actions menu), `editor/title/context` (a tab's right-click, `tab-menu.ts`), `explorer/context` (a Files row's right-click, `row-menu.ts`), `view/title` (an app view's title actions) and `view/item/context` (an app tree row's right-click, group `inline` as row buttons). An entry is `{ command, when, group, alt }`; groups are ordered as VS Code orders them (`navigation` first, then by name, `@<n>` ordering inside a group), an app's groups after oculus's own in each menu, a separator between groups. Each command is called with VS Code's arguments: the resource `{ root, path }` for `explorer/context`, `editor/context` and `editor/title`, the element's handle for `view/item/context`. Any other menu id, and an entry that is a `submenu`, drops the entry with a finding naming it (D64 builds `scm/*`, `debug/*` and `terminal/*`; `contributes.submenus` is refused `key_unknown` as any point outside item 1's list).

7. **Status bar items** (Z795). `oculus.window.createStatusBarItem(id, alignment, priority)` in the host, and `oculus.register('statusItem', id, options)` with `oculus.changed('statusItem', id, options)` in a frame; each item is VS Code's `{ text, tooltip, command, name, backgroundColor, accessibilityInformation }` (`backgroundColor` the warning or error tone alone) with `show()`, `hide()` and `dispose()`. `$(name)` in the text draws a glyph of `glyphs.yml` and an unknown name as its text. Left items are drawn after `latex` and right items before `sessions`, each side by priority, higher first, then by app view id. ## Decisions taken in this brief (each reversible, none silent)

1. The reader of `contributes` is its own module (or subfolder) of `read/`, so `manifest.ts` keeps one concern and its size.
2. `subscribe` and `unsubscribe` are built for the event kinds this step needs (`settings`, `visibility`, `selection`); D64 adds its kinds as rows.
3. A setting whose stored value is outside its type or bounds reads as its default with a finding, as Z800 says; the Settings view's control refuses such a value before it is written.
4. The git extension's registered colours become a table in the moved mapping module, so converting an app theme needs no VS Code install; the script's `--check` keeps comparing it with the installed extension.
5. The `settings` action of `/api/app-host` answers one app's resolved values for a frame; the server tells hosts of a change itself, so the page sends no change notice.
6. An app's keybinding that a field or overlay would receive is not resolved unless its `when` names `editorTextFocus`, as Z792 says; inside Monaco it is resolved after the editor's own keys.
7. Choosing a command an app declares starts its host whatever its `activation` lists, as VS Code does for a contributed command.
8. A frame's requests (`ui.*`) show on the frame's own page and count per frame; a host's show on every page and count per host.
9. A hidden app status item is kept in the ui store's hidden list under `<view id>/<item id>`.
10. The `app-setting` write kind is closed to apps, so an app changes its settings only through the reader.
