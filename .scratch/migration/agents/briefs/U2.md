## Who does the audit

The builder of this step, an agent, does the whole audit: it reads VS Code's stylesheet and layout constants, looks at every view on TEST in Axel's Chrome, measures, and writes the audit. The orchestrator does not take the looks for it. The notes the orchestrator took (`agents/reviews/U2-audit-notes.md`) are a lead to check, never a finding to copy: every line of the audit comes from the builder's own look and measure.

## What to build

1. `agents/reviews/U2-vscode.css`: every rule of VS Code's stylesheet the audit compares against, one rule per line, grouped by the element it styles (list and tree rows, pane and view headers, title-bar actions, buttons, inputs, badges, hover and focus, empty states, tables, the welcome view, the settings editor's rows, the editor and its tabs' content area), each group headed by a comment naming the selector family. A last group, `/* layout constants from workbench.desktop.main.js */`, holds each js constant the audit uses as a comment line: the grep that finds it and the text it matched (the row height, the pane header height, the tree indent, any other). VS Code's default look only.
2. `agents/reviews/U2-audit.md`: for each of the 56 views, one `## <view-id>` section, the 45 of the table in HELP.md's order and then the 11 in the order above:
   - the state it was looked at in (pane width, what it held, the theme and text size in use) and the screenshot's name, or why it has none;
   - each view is looked at in a narrow pane of about VS Code's side-bar width (300 px) and in a wide pane, both widths named;
   - the fixed set, measured wherever the view has the element and written "none" where it has not: row height, indent, header height and type, toolbar action size, text button, input, badge, empty state, error state, hover actions (revealed by hovering a row), focus ring (reached by keyboard);
   - every difference from VS Code's visual language under these headings, each with oculus's measured value (computed style, with the element) and VS Code's value (its line in `U2-vscode.css`): rows, indents, headers, toolbars and actions, spacing, type sizes, icons (size, placement and colour role), hover actions, focus, empty state, error state, anything else;
   - what the view does that VS Code does not, or does better, which the build keeps (spec.md line 76);
   - for a view VS Code has no counterpart for, which VS Code element its parts are measured against and why;
   - `settings` is headed `## settings`, its first line saying its findings go to S3; `changes` names the parts that are X3d's; `project` names Q91.
3. In the same file, after the views, exactly two closing sections: `## Common differences` (the differences common to many views, each with the views it holds for; the icon set, if the audit judges it a difference, goes here once as a question for Axel) and `## Proposed grouping` (one grouping of the differences into build steps, each group with the views and differences it takes and why they belong together). The grouping is a proposal: Axel rules on it, and no build step exists before his ruling. Two differences seen at X3d's landing are among the common ones, each measured on every view that has it: a pane's header actions wrap onto a second line when the title is long and the pane narrow (`ui/frame/Pane.svelte`'s `.tools` has `min-width: 0` and `ui/frame/Toolbar.svelte` wraps; seen on a file's own diff at about 480 px, its `...` on a second row), where VS Code keeps the actions on one line and cuts the title; and an open code or diff editor keeps the colours of the theme it was drawn in when the theme is switched in Settings, until the page is reloaded, where VS Code repaints it at once.
4. `agents/reviews/U2-shots/`: one PNG per view state looked at, named `<view-id>-<state>.png`, taken with the browser tool's `zoom` on the view's pane region with `save_to_disk: true`, then copied from the path the tool returns into this folder. A shot is of one pane only. No shot is taken of the views that show personal or secret content: config, inbox, calendar, memories, transcript, terminal, session-detail, linkedin, person and gallery; these are measured by computed styles only (Decision 7).

## Cases

1. Every one of the 56 views has a section, and each section gives the fixed set of What to build 2, each value measured or written "none", or says why the view could not be put in a state that shows it.
2. A view whose empty state and error state can both be reached on this machine (for example Findings with no finding, Live HPC with the cluster unreachable) has both measured; a state written as unreachable names the attempt made to reach it.
3. Every value the audit attributes to VS Code names its line in `U2-vscode.css`, a stylesheet rule or a js-constant comment line; a value found in neither is not written as VS Code's.
4. The 31 views of the notes are looked at again, deposit and the hub document included; where the builder's measure differs from a note, the audit gives the measure and the note's line.
5. The Config view is measured by computed styles only: no screenshot of it, its `local.yml` card never opened, its file text never read or quoted.
6. Before any screenshot and any whole-page read, no pane of TEST shows the Config view with `local.yml` disclosed or a source tab of `local.yml`; if one does, the builder stops and hands it back without reading it.
7. `tmux list-sessions` at the end prints the same sessions as before the first look: a terminal the audit starts is ended, and `oculus-a5f844-shell` and any terminal the audit did not start are left alone.
8. A view that needs data this machine does not have (a session detail with no live session, Agents with no subagent, HPC off the VPN) is looked at in the state that exists, and the audit names the state it could not reach and the attempt made.
9. `files` and `repositories` have no section; `settings` has one headed `## settings`.
10. History, read at the end, lists no write made during the audit: no control that writes was pressed.
11. `## Common differences` holds the header-wrap and the live theme switch differences named in What to build 3, each with the views it holds for, measured; the theme switch is made and undone through Settings' Theme control, which keeps its choice in the browser.

The builder's first task, before any other work, is the first read of every case above against the unchanged tree (the notes, HELP.md, VS Code's files, the TEST page reachable, `tmux list-sessions` recorded), with each result noted. When the first read finds a case the brief's own rules get wrong, the builder stops there and hands back that case, with the rule and the result it gives.

## Decisions taken in this brief (each reversible, none silent)

1. The builder, an agent, does the audit (Axel's ruling 6 (a) left who to the brief). A reader who did not take the notes gives a read not anchored on them; the orchestrator's part is to check the audit against TEST at landing.
2. `settings` is audited and its findings go to S3, which rebuilds it; `files`, `repositories`, the tab strip and the X3d parts of `changes` are left to X3a, X3d and X3c.
3. The step's report has four parts, the paths above, all in the worktree's copy of the ledger where every builder writes its report (the exception to spec.md line 33 every report takes); the orchestrator copies them into main's ledger when the report comes, and the landing commits them.
4. The builder takes its looks in the one tab that shows TEST in Axel's Chrome (the tab `tabs_context_mcp` lists on `localhost:8790` showing TEST), in front. While the builder runs, the orchestrator takes no look in any oculus tab. The builder's first action on the page is to read which page the tab shows and, if it is not TEST, go to TEST through the Pages view; making TEST with New page when it is missing is the only change allowed to the Pages list, and no other page is opened or changed.
5. VS Code's reference is its declared default: `workbench.experimental.modernUI` off, whatever an experiment may set on an installed copy.
6. The icon set (Lucide) is a decision of `DESIGN.md` "Theming"; the audit measures icon size, placement and colour role per view, and raises the set itself at most once, under Common differences, as a question for Axel.
7. The views that show personal or secret content get no screenshot, since the shots are committed to git: config, inbox, calendar, memories, transcript, terminal, session-detail, linkedin, person, gallery.
8. The step changes no code, so the minimum verify list of spec.md line 63 (npm test and the others) is not run by the builder: no file it runs over changes. The landing runs the list on main as for every step.

## How the looks are taken

- Only in Axel's Chrome, through the browser tools, on `http://localhost:8790/`, on the workbench page named TEST, in the tab Decision 4 names. Open no other page of oculus, never a page Axel works on, never another tab of oculus, and never close that tab.

- A terminal started for a look is ended before the report; `oculus-a5f844-shell` is never touched.
- No alert, confirm or prompt dialog is triggered; a control that asks first is not pressed.
- If the browser tools are not available to you, TEST cannot be reached, a screenshot comes back blank, or a saved shot cannot be copied into `U2-shots/`, stop at once and hand back what you saw; do not audit from source code instead.
