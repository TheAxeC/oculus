## What to build

1. **The stores come from the accounts.** Each of the three stores reads one folder per account of its tool: `<dir>/sessions` for the registry and `<dir>/projects` for the transcripts of every `tool: claude` account, and `<dir>/sessions` for the rollouts of every `tool: codex` account. Folders that resolve to one real path are read once (`realpath` before scanning), so a symlinked account lists no transcript twice. No fixed home path is left in the three stores. The options stay injectable as a list of folders per store, so no test reads the real home. The watcher watches each of those folders, and the head comments of `watch/sessions.ts`, `stores/transcripts.ts` and `registry.ts` name the account folders. The stale first comment at `usage/accounts.ts:63` goes.
2. **The launch note, as Axel ruled on 2026-09-23.** One file, `~/.oculus/dispatches.json`, resolved at the call like the other machine-local files, holding one record per launch: `id`, `launcher` (what launched it, such as `plan-orchestration`), `label` (what the launcher calls the work, such as a step name), `harness` (`claude` or `codex`), `model`, `parent` (the launching session's id), `cwd` (where the child works, a worktree for a plan step), `transcript` (the child's transcript or rollout path, empty until known), `startedAt`, `endedAt` (empty while it runs). Any skill that starts an agent process may write it, so the note is not tied to the plan skills.
3. **The writer: `bin/dispatch-note.mjs`.** `start` takes the fields above as flags and prints the new record's id; `transcript <id> <path>` sets the path once it is known; `end <id>` stamps `endedAt`. Several launchers may write at the same moment, so every write takes a lock beside the file (created exclusively, retried, and cleared if its holder is gone) and replaces the file by writing a temporary copy and renaming it; a missing or unreadable file starts a new list rather than failing the launch. No dependency beyond Node's own modules.
4. **The reader.** The sessions layer reads the note, tolerating a missing, empty or garbled file, and every record whose `parent` is a session's id joins that session's `agents` as a dispatched builder: its label, harness and model, running or ended, and for a Codex rollout its token usage from the rollout's last usage event. The Agents view draws these beside the subagents the transcript names, marked as launched processes, and a row whose transcript is known opens it as the view opens a subagent's. A change to the note reaches an open page on the `sessions` channel.
