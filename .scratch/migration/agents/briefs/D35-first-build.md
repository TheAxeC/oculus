## What to build

1. **`src/lib/server/root/live-settings.ts`** (new; the folder goes to 10 items). `liveSettings(hub, start, targets)`: `start` holds the settings the pollers were built with (the baseline), `targets` the setters below. It subscribes one sink to the `config` channel with `replay` false and, on each config message, parses the JSON text, narrows `payload.config` through a schema (never a cast), and reads each group again through its reader: Live HPC (`slurmSettings`), the calendar (`calendarSettings`), the mail (`mailSettings`), the usage refresh (`requireRefreshSettings` over `usage_refresh_min` and `usage_refresh_model`), the usage tiers (`usageTiers`), and the three sentences `calendar.ics_no_link`, `calendar.ics_failed` and `accounts.timed_out` (through `textCatalog`; a sentence that is missing or not a string is refused like a group). Each group is read on its own, so one refused group keeps its settings while the others take theirs. A refused group keeps the settings in force and logs one stderr line, `config: <the reader's message>; the settings in force are kept`, once: the same message on a later push logs nothing; a different message logs its own line once; a push that reads the group without a throw clears its logged state, even when its values equal the ones in force, so a later refusal logs again. A message whose `config` is not a map refuses every group with one line, `config: the pushed configuration is not a map; the settings in force are kept`. A group whose values equal the ones in force hands nothing on. It returns `{ close }`, which removes the sink.
2. **`context.ts`**: the start read stays (a value the readers refuse at start still stops the server with the key named). After the pollers are made, `createServerContext` starts `liveSettings` with the start values and the targets, and `close()` closes it first. The comment at :215-217 says the start read builds the pollers and that every config push hands them the re-read settings through `live-settings.ts`. The HPC host stays `local.hpcHost ?? slurm.host`: a pushed `slurm.host` reaches the poller only when `hpc_host` is not set. The hook target built at start keeps `store`, `hub`, `limiter` and `logged` only: `config` and `stopMessage` leave it, the hook route being their one reader, and `HookTarget` in `hooks.ts` is split so the context's part has no such fields.
3. **The cadence rule**, for every cadence below: a new period `m` minutes moves the next run to `min(next, now + m)`, then runs every `m`; a retry time is treated as the next run, so it moves earlier only when `now + m` is earlier. A raise leaves the next run where it is.
4. **`watchHpc`** gains `set({ host, days, pollMin, quotaMin, prewarm })`. A changed `host` clears the rows, `lastOk`, the quota, `asked` and the resolved log paths, publishes that, and starts a poll now; a changed `days` starts a poll now; both go through the existing gate, so a poll never runs beside one in flight, one push changing both starts one poll, and rows of a poll begun under the old host or window are dropped, the follow-up poll answering. A changed `pollMin` follows item 3 and publishes again (the head's lateness reads it). A changed `quotaMin` follows item 3 for the quota timer. A changed `prewarm` takes effect at the next good poll.
5. **`accountLoop`** gains `setPollMin(minutes)`, following item 3 for each account's due time, and re-arms its timer. One function in `loop.ts`, `liveLoopSettings` or a shape the builder judges cleaner, holds what the calendar and the mail setters share. **`watchCalendar`** gains `setSettings({ pollMin, daysBack, daysAhead })` and `setWords(words)`: a changed window reads every account now (`loop.run(true)`), a round in flight being corrected by that follow-up; a changed `pollMin` publishes again; new words are used from the next sentence written. **`watchMail`** gains `setSettings({ pollMin, perSignal })` and `setWords(words)` the same way, a changed `perSignal` reading every account now.
6. **`watchUsageRefresh`** gains `set({ refreshMin, model })`: a changed `refreshMin` follows item 3; a changed `model` is used from the next start, a start already running finishing with the model it began with; with no Claude account the interval is still replaced and nothing starts. **`watchUsage`** gains `setTiers(tiers)`, which publishes again when the tiers changed.
7. **Every setter after its watcher's `close()`** does nothing: no timer, no poll, no publish. No setter reads the disk.
8. **Z174, the readers** (`settings.ts`, on Q85c's shapes): `slurm.poll_min`, `slurm.quota_min`, `calendar.poll_min` and `mail.poll_min` are numbers from 1 to 35791; `slurm.days`, `calendar.days_back` and `calendar.days_ahead` whole numbers from 0 to 3650; `mail.per_signal` a whole number from 1 to 500. The Settings write refuses the same values through `config-key.ts`'s readers with no change to `READERS`.

## Cases

All timers run under vitest fake timers.

1. A push with `slurm.poll_min: 5` while the poller waits on a 20-minute timer with 15 minutes left: the next poll runs 5 minutes after the push, and the payload's `pollMin` is 5 from a publish at the push.
2. Raise: `slurm.poll_min` from 5 to 60 with the next poll due in 3 minutes: it runs in 3 minutes, then every 60.
3. A push with `slurm.host: other` and no `hpc_host`: the rows, `lastOk` and quota are cleared and published, and a poll runs against `other` at once; with `hpc_host` set, the host stays `hpc_host` and no poll is started.
4. A push changing `slurm.host` while a poll is in flight: that poll's rows are dropped, one follow-up poll runs against the new host.
5. One push changing `slurm.host` and `slurm.days`: one poll.
6. `slurm.days: 14`: a poll runs at once with `sacct -S` 14 days back.
7. `slurm.quota_min: 30`: the quota read runs by item 3, then every 30 minutes.
8. `slurm.prewarm: false`: the next good poll does not prewarm.
9. The HPC poller in its retry wait (2 minutes) when `slurm.poll_min` becomes 1: the next poll runs 1 minute after the push; becomes 5: the retry time stands.
10. `calendar.days_back: 7`: every calendar account is read at once with a window opening 7 days before now, the payload carrying `daysBack: 7`; `calendar.days_ahead: 30` the same, `daysAhead: 30`.
11. `calendar.poll_min: 5` with an account due in 15 minutes: read 5 minutes after the push; an account in retry due in 2 minutes keeps 2; `calendar.poll_min: 1` with that account: read 1 minute after the push; a raise to 60 with an account due in 3: read in 3.
12. `mail.per_signal: 10`: every mail account is read at once asking each provider for 10 threads; `mail.poll_min` as case 11.
13. `usage_refresh_min: 3`: the refresh runs by item 3, then every 3 minutes; `usage_refresh_model: sonnet`: the next start passes `--model sonnet`, a start already running keeps its model; with no Claude account, the interval is replaced and nothing starts.
14. A new `usage_tiers` label: the `usage` channel publishes again with it.
15. A pushed `calendar.ics_no_link`, `calendar.ics_failed` (calendar) and `accounts.timed_out` (calendar and mail): the next row of that kind carries the new sentence. A push missing `calendar.ics_failed`: the sentence in force stays, one line logged.
16. `slurm.poll_min: 0` by hand: the poller keeps its minutes; stderr has `config: config/behavior.yml: slurm.poll_min must be a number from 1 to 35791; the settings in force are kept` once; the same push again logs nothing; `slurm.poll_min: 15` then takes 15; a later refusal logs again. A push back to the value in force after a refusal clears the logged state.
17. A refusal per group, each logged once with its reader's message: `calendar.poll_min: 0`, `mail.per_signal: 0`, `usage_refresh_min: 0`, `usage_tiers: { a: 5 }`. A push refusing `slurm` while `calendar.poll_min` changes: the calendar takes its change, Live HPC keeps its settings.
18. A push whose values equal the ones in force: no poll, no re-arm, no publish (an audit, since nothing re-reads on the unchanged tree; said so in the report).
19. A push whose `config` is not a map: every group keeps its settings, one line `config: the pushed configuration is not a map; the settings in force are kept`.
20. `behavior.yml` saved unparseable: the push follows with its keys missing; slurm, calendar, mail, the usage refresh and the tiers each log their own line once and keep their settings; the parse error is a finding on the config channel (existing).
21. Two pushes in quick succession: the settings of the last one hold.
22. The bounds at start and in Settings: the server started with `slurm.poll_min: 0` refuses to start with the key named; the Settings write of each of `slurm.poll_min: 0`, `slurm.poll_min: 35792`, `slurm.quota_min: 0.5`, `calendar.poll_min: 40000`, `mail.poll_min: 0`, `slurm.days: -1`, `slurm.days: 2.5`, `calendar.days_back: 3651`, `calendar.days_ahead: -1`, `mail.per_signal: 0`, `mail.per_signal: 501`, `mail.per_signal: 2.5`, `usage_refresh_min: 0` is refused with the reader's message; `calendar.days_back: 0`, `slurm.poll_min: 1`, `slurm.poll_min: 35791`, `mail.per_signal: 500` are accepted; `-0` into `days_back` still reads 0.
23. Each setter after its watcher's `close()`: no timer, no poll, no publish.
24. `close()` of the context: the sink count of the hub returns to its value before `liveSettings` started, and a later `config` publish changes nothing and logs nothing.
25. The hook route: a hook event with `notify.enabled: false` in the request's config pushes no notification (existing behaviour, kept; the context's hook target holds no `config`).
26. A write through `target()`, a wallpaper request, a project-files request, an agents request and a terminal start after `local.yml`'s `hub` is edited on disk: each uses the start `hub`.

The builder's first task, before any change, is the first run of every case above on the unchanged tree, with each case's result noted. A case of a code step becomes a test of the step, run on the unchanged tree first; no prototype script stands in for the test.

When the first run finds a case the brief's own rules get wrong, the builder stops there, before changing any code, and hands back the first run and that case, with the rule and the result it gives. The orchestrator rules on the case and resumes the builder with the ruling, and the final report carries it.
