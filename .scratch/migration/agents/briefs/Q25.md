# Brief: Q25, every view drawn from one file carries the control that opens it

Read `../spec.md` first, its section "The principles every package is judged on" and its amendment of 2026-09-16 (the port rule) above all. The plan's Q25 line (Axel, 2026-09-16 00:35, a fix of Q9): every view drawn from one file of the hub carries the control that opens that file in the source tab: the three feeds (Inbox, Position Leads, Lit Watch), LinkedIn, a collection over its YAML, and the Config cards as they already do. The reader edits the file the view draws where the view's own controls stop, without hunting for it in the file browser.

## What is on the tree (written 2026-09-16 at 04:02 against main with D4, D21 and Q23 landed)

- The one way a view opens a file in the source tab: `layout.openView('source', sourceTabState(root, path))` (`state/source.svelte.ts` `sourceTabState(root, path)` builds `{ root, path, label }`). `views/Config.svelte` line 82 does it for a config card under `ENGINE_ROOT`; `views/shared/edit-bar.ts` `openSourceFile` and `views/shared/EditBar.svelte` do it for a project's own files (the bar's word is `project.helper.edit_source`, "edit source: {0}"); `views/linkedin/post-card.ts` line 13 does it for one post under `HUB_ROOT`; `views/File.svelte` and `views/Files.svelte` for a file of the browser.
- The files the four feed views draw: `config/sources.yml` `inbox_file: feeds/inbox.yml`, `leads_file: feeds/position-leads.yml`, `radar_file: feeds/literature-radar.yml`, `linkedin_dir: theaxec.github.io/_linkedin`, read into `PortfolioConfig.feeds` at `data/index.ts` lines 132 to 135 (`inbox`, `leads`, `radar`, `linkedin`); the views are `views/Inbox.svelte`, `views/Leads.svelte`, `views/Radar.svelte` (Lit Watch), `views/Linkedin.svelte`. The client reaches the portfolio config through the snapshot and the config channel (`configMap()` in the state layer; `views/Map.svelte` lines 63 and 79 read `configMap().arch_color` and `map_label_mode`, which is the pattern; `PortfolioConfig.feeds` is `FeedFiles` at `data/model.ts` line 100).
- A collection view (`views/Collection.svelte`, "one collection file as its own tab") is drawn from the file `config/sources.yml` `collections:` names for its key (`file:`), carried on the snapshot's `collections` record (`data/model.ts` line 38, `RawCollection`).
- The hub root on the client is `HUB_ROOT` of `state/fs.ts`; every feed and collection path above is relative to the hub, so the tab state is `sourceTabState(HUB_ROOT, path)` (`HUB_ROOT` lives in `state/collection.ts`, as `post-card.ts` imports it).
- `ui/Toolbar.svelte` and `ui/ToolButton.svelte` are the toolbar primitives every view's bar is built from; `views/Config.svelte`'s card control is a `ToolButton` with the glyph the catalog names.

## How it lives in oculus (the three layers, the data live)

1. **Data.** Nothing new: the paths are the portfolio config's and the collection record's, already on the client.
2. **State.** One pure helper, `viewSourceFile(kind, config, collection?)` in `state/` (or beside `edit-bar.ts` in `views/shared/`, whichever the boundary table allows for a reader in five views), answering `{ root: HUB_ROOT, path }` for a feed kind or a collection key, and null when the config names no file, so the five views share one rule and one test.
3. **View.** Each of the five views draws one control in its toolbar, after its own controls: the source glyph the Config cards use, the label `views.open_source` ("Open the file", a new catalog word under `views` or the existing `project.helper.edit_source` reworded so it reads in every view; pick one word for all six places and say which), the tooltip naming the path; pressing it opens the file in the source tab the way the Config card does. LinkedIn is drawn from a folder, not one file: its control opens the folder's index or, when the folder has no single file, the control is omitted and the per-post control (`post-card.ts`) stays the way in; say which in the report. The Config cards are unchanged.

## Decisions taken in this brief (each reversible, none silent)

1. One word for the control in all six places; the Config cards' existing word is the candidate, and the report says which key won and why.
2. The control sits last in each view's toolbar, after the view's own controls, since opening the file is the reader's way out of the view rather than one of its own actions.
