## What to build

The rulings, in Axel's words (`plan.md`, Rulings):

- Open item 71: "(1) yes, every collection entry has a page; (2) (a), the schema-driven editor of the project page on it, built from the collection file's `schema:`, which reverses the 2026-10-03 removal of the collection forms (Z343) for this editor; (3) (a), Add asks the key, writes `new-entry` and opens the page in its editor, Delete on the card and the page asks first and writes `delete-entry`."
- Open item 72: "(a), pillars, domains, venues, data and statements each get a page (the record, its editor, and the projects that refer to it), the editor, Add and Delete; the identity field (`name` for venues, `key` for the others) is read-only in the editor; a Delete of a record projects refer to asks first naming each of them, and the references left show on the Findings view."
- Open item 73: "(a), people, organisations and resources become collections, each a card list in the rail group of Venues and Data with D72's page, editor, Add and Delete; the Person page becomes the person's page with the editor; an organisation's page lists the people and funding schemes that refer to it, a resource's page the projects that run on it; career gets the editor over its sections from an Edit control on the Career strategy panel, with no Add or Delete."
- Open item 74: "(a), the leads and radar feeds get D72's page, editor, Add and Delete beside the actions they have; the radar's Dismiss stays the way to hide an entry the scout would find again."
- Open item 75: "`:task-add <title>` writes a task with that title, `status: todo` and a key made from the title (lowercase ASCII words joined by `-`, `-2`, `-3` on a clash), undoable, with a notice carrying Open, Shift+Enter also opening the task's page in its editor, an empty title adding nothing; the palette page `tools/oculus/docs/palette.md` is generated by `npm run docs:palette` from the palette's registry (views, colon commands with argument and catalog description, language-server choice commands, editor and Present commands, prefixes, keys), the landing check comparing the committed page with a fresh generation, HELP.md's palette section linking to it."

What must hold when the step is done:

1. **A page for every entry.** Every entry of every collection (the eleven, organisations and resources) and of both feeds has a page, the `entry` view, opened from its card's title in every view that draws the card (the generic collection view, Venues, Data, Pillars, Domains, Leads, Lit Watch, and the new card lists) and from a palette result for the entry. A person's page is the `person` view, kept under its id so that every opener of it and every saved tab of it stays as it is (decision 9). The page shows the record, its editor (item 2), and the blocks that apply to it: the documents, files and sessions of the folder its `link` names only when `link` names a folder (as now), and the referrers of item 5. An entry whose collection or key no longer exists (its own Delete included) says so in a plain sentence, as the page does today for no entry, and shows the entry again when an Undo brings it back.
2. **The editor.** The page holds the project page's schema-driven editor, built from the collection file's own `schema:`: one widget per field under its label (the schema's `label`, else the field name) and its `help`, in the schema's order; a schema with no sections is one section. The editor form moves out of the `editor` view into a shared component under `src/lib/views/shared/forms/entry/`, which the `editor` view, the entry page, the person page and the Career panel all draw (a view imports no other view). Every type the files use is drawn and written: text, textarea, select (its `options`, or the keys of its `from:` source), tags (free words, or the keys of its `from:` source as chips), date, checkbox, metalist (label and value rows, add and remove a row), and records in each of its three shapes: a list (one card per record with a widget per sub-field, add and remove a record), one record (one card, no add or remove, saved as a map) and an `open: true` map of labels (label and value rows, add, rename and remove a row, saved as a map). A key of a record that no sub-field names is drawn as an editable label and value row and kept on Save (career's `hosts` score columns, `situation`'s labels). Save posts only the fields that changed, through the `entry` write; a field the editor did not change is never sent, so a change another writer made to it stays. A sub-field the edit did not touch keeps its text as the file wrote it (a folded `notes: >` keeps its style). A refused field keeps its edit and shows the refusal under the field, as every write's refusal is shown today (`tell`, `writes.svelte.ts:160-170`). Unsaved edits are kept in the instance state across a tab switch, a reload and a change of the file on disk, and closing the tab over them asks first, as the project editor does; a write over a file a source tab of the page holds unsaved text of is refused before it is sent and the edit kept (G28; `src/lib/state/sessions/source/write-files.ts` lists the new `career` kind). The identity field is read-only in every editor, and a venue's `id` too (decisions 1 and 2). The project editor keeps working as it does.
3. **Add.** Each card list's Add asks the new entry's identity value in a box (a venue: its name and its id; a Lit Watch paper: its title, its address and its bucket, which `radar-add` requires; decision 2), refuses an empty value, a value the file already holds and a key that reads as another hub's id (it begins with a hub's key and a colon) with the refusal's sentence, writes the entry and opens its page with its editor. A collection's Add writes `new-entry`, a lead's `lead-add`, a paper's `radar-add`; each writes the primary hub (else the first), as those writes do today. The new entry holds what the box gave; a field its schema marks `required` stays empty and shows its `required` finding until the editor, opened right after, fills it. The source-tab Add (the new entry placed in the file's unsaved text) is replaced by this Add on every view that has it (`Collection.svelte`, `Leads.svelte`, `registry-file.svelte.ts`), and the part of `draft-entry.ts` only that Add used goes with it; Edit in File stays.
4. **Delete.** Delete is on each card's menu and on the page's toolbar. It asks first; for a record other files refer to (item 5), the question names each referrer; the yes writes `delete-entry` (a feed entry: `feed-delete` in the hub that holds it), undoable from History. The references left are the existing `no_key` findings on the Findings view; nothing rewrites them. The radar's Dismiss stays; a radar entry also gets Delete (decision 4).
5. **Referrers.** A record's page lists what refers to it, each a link that opens it: for a pillar, domain, venue or dataset the projects whose manifest field names it (`pillar`, `domain`, `venue_id`, `datasets`); for a resource the projects whose `compute` names it and, when the hub's `behavior.yml` `slurm.resource` names it, that setting; for a funding scheme the projects whose `funding` names it; for an organisation the people whose `affiliations` and the funding schemes whose `funder` name it; for a person what the Person page lists today (its joins of `state/boards/person.ts`) and the projects whose `waiting-on` names the person. A statement has no referrer field, so its page has no such block. Delete's question names the same referrers.
6. **People, organisations and resources as collections.** The three become collections: entries for `people`, `organisations` and `resources` (files `registries/people.yml`, `registries/organisations.yml`, `registries/resources.yml`) in `config/sources.yml`'s `collections:` after `statements`, written in the list's own form (quoted path, aligned columns), the `*_file` keys kept, as venues and data keep both (decision 3). Each is a card list in the References page group after Statements, in that order (`Collection.svelte`'s placements; `config/layout.yml`'s `references` arrangement gains the three). The Person page gains the editor, Delete and the referrers, and keeps its joins and folder block; a person's card and a collaborator tag open it. The orchestrator adds the three lines to the hub's `.oculus/config/sources.yml` at landing, from the report's "Doc text".
7. **Career.** The Career strategy panel gets an Edit control that opens the editor over `registries/career.yml`'s sections, built from its `schema:` (the two text fields, the records sections in their shapes: `situation` an open map of labels, `order`, `hosts`, `not_hosts` and `dropped` lists, `eligibility` one record, and the `host_criteria` tags), with Save writing only the changed sections and undoable from History, through a new write `career` (decision 5). No Add and no Delete. History names it with a catalog word beside `kind_host`.
8. **Feeds.** Leads and Lit Watch keep every action they have (a lead's status, a paper's Dismiss, Lit Watch's `radar-add` from the literature search) and gain the page, the editor, the Add of item 3 and Delete. The editor's Save of a feed entry sends one `feed-field` per changed field, in the schema's order, each a row of History, a refused field keeping its edit; `FEED_RULES` lists every schema field but the identity as writable for leads and radar, `feed-field` checks the value against the field's schema type as `writeEntry` does, and a feed entry of another hub is written in that hub through `root` (decision 4). A feed file with two entries of one title refuses the editor's writes and Delete with the sentence collections give (`sharedIdentity`).
9. **`:task-add <title>`.** A colon command of the palette that writes a task to the tasks collection of the primary hub (else the first) through `new-entry`: `title` the words given, `status: todo`, `key` the title made into lowercase ASCII words joined by `-` (accents taken off, at most 80 characters, decision 6), `-2`, `-3` and on when the key is taken. It is undoable from History (the `new-entry` record). On success a notice says the task was added and carries Open, which opens the task's page; Shift+Enter on the command adds the task and opens its page with its editor. An empty title (nothing but spaces after the command) adds nothing and the palette says a title is needed; a title that gives no key (no ASCII letter or digit after the accents are taken off) adds nothing and says so; a hub with no tasks collection adds nothing and says so. Its argument hint and description are catalog strings like the other commands'.
10. **The palette page.** `npm run docs:palette` writes `tools/oculus/docs/palette.md` from the palette's own registry, never from a hand list: the views (as the palette lists them), the colon commands with their argument hint and catalog description, the language-server choice commands, the editor's Cmd-K commands and the Present commands, the prefixes (`:`, `#`, a line number, Cmd+P's file mode) and the palette's keys. The page's text is made by a function in `src/lib/shell/keys/` that takes the registry and the catalog as arguments; `utils/diagrams/palette.mjs` (decision 7) loads it through Vite's server module loading (`createServer` with the project's Vite configuration and its module loader), since the registry's modules use `$lib` aliases and runes. A test in `tests/checks/diagrams/` fails when the committed page differs from a fresh generation, as `diagrams.test.ts` does for the diagrams, and the function is tested over a small registry given to it, never by changing the real registry. HELP.md's "The palette" section links to the page.
11. **Leftovers and words.** `Collection.svelte`'s `code` placement and its head comment's Code go (open item 69's ruling). The three `slug` rules become one shared helper with a length argument, which `presets.ts`, `feeds.ts`, `radar.ts` and `:task-add` import (spec.md: a rule exists once). Every sentence the change makes false is rewritten: DESIGN.md, HELP.md, `docs/apps.md`, `docs/DATA-MAP.md` (the collections, the registries, people, organisations, resources, career and the feeds), `config/text/`, the head comments of the files changed. The hub data files whose head comment says Add opens the file (`funding/funding.yml:1`, `network/events.yml:1`, the hub's `.oculus/config/sources.yml:58`) are rewritten by the orchestrator at landing from the report's "Doc text". The words of new controls, questions and notices are catalog strings.

## Cases

- A funding entry with no `link`: its card's title opens its page, with the record, the editor and the projects whose `funding` names it, and no documents, files or sessions block.
- A funding entry whose `link` names a folder: the page has the editor and the three folder blocks as today.
- The editor of an events entry: the `meta` metalist drawn as label and value rows; adding a row and saving writes `meta` with the new row and nothing else.
- The editor of a dataset: its `retrieval` (one map) drawn as one card with no add or remove; editing `method` and saving writes `retrieval.method` as a map, and every other sub-field (a folded `notes: >` included), field and comment of the file keeps its text.
- The editor of a venue: `name` and `id` read-only; editing `short` and saving writes `short` alone.
- An edit typed and not saved, then a reload: the edit is still in the editor; closing the tab asks first.
- A select field given a value not among its options through the editor is refused by the server, and the field keeps the edit with the reason under it.
- Add on Tasks with key `review-x`: `new-entry` written with `key: review-x` alone, the page of `review-x` opened with its editor, the `required` findings of `title` and `status` shown until they are filled; Add with a key the file holds: refused with the refusal's sentence, nothing written.
- Add on a collection whose file's `entries:` holds only comments (the hub's `tasks/tasks.yml` as it stands now, copied to a scratch hub): the entry written under `entries:`, the comments kept.
- Add with a key that begins with a workspace hub's key and a colon: refused, nothing written.
- Add on a card list that shows a second hub's collection beside the primary's: written to the primary hub's file.
- Add on Venues with a name and an id: written; with an empty id: refused with the refusal for an empty id.
- Add on Lit Watch with a title, an address and a bucket: `radar-add` written, the page opened; with a bucket not among the radar buckets: refused.
- Add on Leads with a title: `lead-add` written, the page opened; with a title the file holds: refused.
- Delete of a pillar two projects name: the question names both projects; yes removes the entry, History lists it and Undo puts it back; the two projects' `pillar` values show as `no_key` findings until changed.
- Delete of a statement no file names: the question names no referrer; yes removes it.
- An organisation's page lists the people whose `affiliations` and the funding schemes whose `funder` name it.
- A resource's page lists the projects whose `compute` names it.
- The person page of a collaborator: the joins it has today, plus the editor; a collaborator tag on a project opens it.
- People, Organisations and Resources appear in the References group of the view catalogue after Statements, each a card list.
- The Career strategy panel's Edit opens the editor over the sections; changing `milestone` and saving writes only `milestone`, undoable from History.
