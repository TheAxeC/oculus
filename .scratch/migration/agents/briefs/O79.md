## The rule the step ends

An entry's identity and the target of a reference are given by words and positions in code: an entry is addressed by "the schema's first field", `title` without one (`TITLE_FIELD`), except the venues, addressed by `id` because a table in code says so (`KEYED_FIELDS`); a schema field names where its choices come from with `from:`, whose sources are a fixed list of registry words in `schema.ts`, each with the fields its choice shows written beside it. The rulings of this step put both in the schemas: a field flagged `primary_key: true` is an entry's identity, a field's `foreign_key:` names any collection, stores the target's primary key and shows the target's fields ranked by `display:`. The rulings are in `plan.md` Rulings: open items 392, 397, 398, 404, 415, 416, 425, 426 and 427 (Axel's). Ruling 404 renames `from:` only where it is a schema field's key.

## What to build

1. **`primary_key: true` (rulings 392 (a), 397 (a)).** A schema field may carry `primary_key: true`; an entry of a file is addressed by its value in every read and write (the collection views, the entry page, the edit, Add and remove writes, the identity findings, the reference index, the registries' id). One function gives a file's primary key field, read from the flag (or the `collections:` entry, below), and every reader of premises 1 and 2 calls it: `TITLE_FIELD`, the three `identityField` copies, `identityFieldOf`, `KEYED_FIELDS`, the `idField` column of `REGISTRY_SHAPES`, the first-field rule of `normalise.ts:512,539`, `page-file.ts:48`, `collection-text.ts:279-280` (`stubFields`) and `identityValue` all go, and `entryIdOf` and `entryTitleOf` (`model-collections.ts`) take the primary key and the display (item 2) instead of the written field names `id`, `key`, `title` and `name`. `page-file.ts:43` reads the feed by the page's collection, not by the words `leads` and `radar`. `FEED_IDENTITY` keeps `linkedin: 'file'` (a folder of files, no collection); leads and radar are collections and take their primary key from their file. `NOT_WRITTEN` (`schema.ts:79`) becomes the manifest schema's primary key field. Bookmarks take theirs from their schema: `BOOKMARK_IDENTITY` goes and the `SCAFFOLD` (`bookmarks.ts:41-60`) flags `label` with `primary_key: true`. The rule covers files of `collections:` whose entries are a list (the entries kind) and the bookmarks file; the career file (a sections file), `deck-schema.yml`, `cpp-schema.yml`, the manifest schema's nested `records` fields and the options catalog get no primary-key rule and no finding. A file with no schema names its primary key on its `collections:` entry as `primary_key: <field>`, described in `config/options/sources.yml`. An entry's `primary_key:` beside a schema flag, the same field or another, is a finding naming both, and the file's writes are refused. `primary_key: true` on a list, tags or records field, on a nested field, or a value that is not `true` (`"yes"`) is a finding naming the field. A schema with no field flagged, or two, and a file with neither a schema nor the entry's key, is a finding naming the file (and the fields, when two), worded in `config/text/findings.yml`; such a file is read and drawn, and every write that addresses an entry of it (edit, remove, Add) is refused with a sentence naming the missing primary key, worded in `config/text/`. A primary key is required: an entry without a value there is the finding `identityFindings` gives today for an empty identity, once per entry (a registry file whose primary key is its id gives one finding, not one from `checkEntryIdentity` and one `entry_no_id` from `registries.ts:97-102`). The entry page shows the primary key and never writes it, as `fixedFields` shows a venue's `id` today. The Add form (`askFields`, `new-entry.ts:31-38`, called by `entry-add.ts:112`) asks the primary key and every field the schema marks `required`, in the schema's order; for a venue that is `id` and `name`, the same two it asks today. A card's heading and an entry page's title are the entry's display (item 2), else its primary key.
2. **`foreign_key:` and `display:` (rulings 398 (a), 404 (a), 415 (b), 416 (b)).** `from:` on a schema field is renamed `foreign_key:` once in every file that writes it as a schema field's key (premise 4), oculus's and the demo hub's, and the code reads only `foreign_key:`; the options catalog's own `from:` (premise 5) and an entry's data field `from` (premise 6) are no schema field and stay. A `foreign_key:` names a collection by its key in the record's own hub (`collections:`), `projects` for the manifests, or a vocabulary list as `vocab.<key>` or `vocab.<key>.<field>`; it may be a list of these, or the map that picks a source by another field of the record, as `from:` is today. A value stored is the target's primary key. A schema field may carry `display: <n>`, a whole number from 1; a reference shows the target's first filled field by rank (`display: 1` first), and the target's primary key when none is filled. `sourceChoices` reads the target's entries and its schema's ranks, so `schema.ts` names no registry and no field; `Literature.svelte:97` and `FieldControl.svelte:148` take the display the same way. Where code asks whether a field picks people (`picksPeople`, `schema.ts:411-413`; `PEOPLE_SOURCE`, workbench `FieldControl.svelte:83,128-133`; `PEOPLE_OPTIONS` and `kindOf`, `collection/index.ts:175,197-200`), it asks whether the target collection carries the registry `people` (O78's `registry:` words, which code may name), never whether its key is `people`. `addPerson` (`new-entry.ts:233`) writes the new person's name into the people schema's `display: 1` field in place of `NAME_FIELD`. A resource choice keeps its glyph when the target collection carries the registry `resources`. Each hub's foreign key resolves against that hub's own `collections:`; where choices merge hubs (`recordChoices`, `schema.ts:223-249`), another hub's entries are offered when its collection carries the same registry as the named collection. The reference index names a target by the registry of the collection it resolves to (else the collection key), so a `foreign_key: people` value and the options catalog's `from: people` (`sources.yml:192`) stay one definition and a rename (G67) edits both. A `foreign_key:` that is empty or `[]`, or names a collection whose file has no primary key, is a finding naming the file and the field, and the field offers nothing. A hub collection keyed `projects` or with a key starting `vocab.` collides with the reserved targets: a finding naming the hub's file and the key, and the reserved meaning wins. The apps payload's schema line carries `foreign_key` in place of `from`, and `docs/apps.md:410` says so (ruling 427). A vocabulary list's primary key is the word's key and its display the word's label. A `foreign_key:` naming no collection of the record's hub, no vocabulary list and not `projects` is a finding naming the file and the field; a target schema with no field carrying `display:`, two fields of one rank, or a rank that is no whole number from 1, is a finding naming the target's file and the field. A `from:` left on a schema field is a key no schema shape names, the finding G56 gives such a key, so no code reads it. The `manifest_fields` row of a hub takes `foreign_key:` in place of `from` (`hub-layer.ts:385-505`, `config/options/schemas/manifest-schema.yml:4,22`), with its finding worded for a source that names no collection. `server/edit/writes/manifest.ts:98-125` (`sourced`) reads `foreign_key`.
