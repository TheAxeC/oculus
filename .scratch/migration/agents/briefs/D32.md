## What to build

### A. Replace in the Search view

The VS Code Search view's replace, item by item, each built:

1. **The replace row.** A Toggle Replace control (VS Code's chevron, at the start of the query row) shows or hides a second row under the query: the replace box, the Preserve Case toggle (VS Code's `AB` toggle, a chip here like the three others) and Replace All. Whether the row is shown, the replace text and Preserve Case are the tab's own state beside the query, kept with a saved page (`SearchState`). Enter in the replace box runs the search, as Enter in the query box does; Cmd+Alt+Enter in either box is Replace All. Up and Down in the query box and in the replace box walk that box's history (the last 20 texts the tab ran, newest first, kept in `SearchState`), as VS Code's two boxes do. Cmd+Shift+F opens the Search view and focuses its query box; Cmd+Shift+H opens it with the replace row shown and focuses the replace box, as VS Code's Find in Files and Replace in Files do: two `KeyAction`s in `shell/keys/keys.ts`, performed in `workbench-keys.svelte.ts`, and two rows of the key sheet (`config/text/app.yml:12`).
2. **The preview in the results.** While the row is shown, each hit row draws the matched text struck through followed by its replacement, and the count line says how many hits would be replaced in how many files. The replacement is computed on the page by the function of item 6 from the groups the run reported (item 3), so it follows the replace text and Preserve Case as they are typed, as VS Code's preview does, without a new run. A hit whose groups the run did not report (a run made before regex mode was on) shows the struck match without a replacement until the next run.
3. **One hit per match.** A line holding two matches is two hits, two rows, each its own replace and dismiss, as VS Code lists them, keyed by `line` and `at` (never by `column`, which two cut windows of one long line can share). `SearchHit` gains `at`, the match's start in the whole line counted in UTF-16 units from 0, and in regex mode `groups`, the text of every group of the pattern by number (group 0 the match) and by name, from ripgrep's replacement of a template of item 6. `column` and `length` keep their meaning in the cut `text`. The cap (`search.max_hits`) counts hits; the fold's truncation test compares ripgrep's `matched_lines` with the lines held, not with the hits. A saved answer whose hits lack `at` reads as no answer, so the tab runs again rather than drawing hits that cannot be replaced.
4. **Replace, Dismiss, per hit and per file.** While the row is shown, a hit row offers Replace under the pointer and on focus, and a file heading offers Replace All in that file; Cmd+Shift+1 runs the one the focused row offers. Every hit row and file heading offers Dismiss, with Delete, and Cmd+Backspace on macOS, on the focused row. Dismiss takes the hit or the file out of the tab's answer without writing; Replace All then leaves it out. After a Replace or a Dismiss the focus moves to the next row, as VS Code's does, and after a Replace with a Replace Preview pane open, the next hit opens in its preview. The keys are new key handling in the Search view, built as the Files view's (`views/sources/files/tree/control/keyed.ts`).
5. **Replace All.** Asks first, in the view's own question (the `AskConfirm` of `views/shared/writes/`), with VS Code's sentence: "Replace {n} occurrences across {m} files with '{text}'?", and "Replace {n} occurrences across {m} files?" for an empty replace text; the singular forms for one occurrence and one file. After it lands the count line says "Replaced {n} occurrences across {m} files with '{text}'." (or without the text), and the replaced hits leave the answer. An answer the cap cut says in the question that only the hits listed are replaced. One replace request runs at a time: Replace and Replace All are disabled while one is in flight.
6. **The replace text read as VS Code reads it (Z264).** Two functions of one module of `data/` that the page and the server both call:
   - `replaceTemplate(pattern, mode)` gives the ripgrep `-r` text the search run carries in regex mode: for each group of the search pattern, number 0 to the count and each name, `${N}` or `${name}` wrapped in the private-use markers U+E002 and U+E003 with the group's key between, so each match's `replacement` holds every group's text, and the server splits it back into `groups`. The count and the names come from reading the pattern under ripgrep's syntax: an unescaped `(` outside a character class opens a group, counted when it is not followed by `?`, or followed by `?P<` or `?<` (a named group); `[...]` classes are skipped with their nesting and escapes.
   - `replacementOf(pattern, groups, { regex, preserveCase, crlf })` returns VS Code's `getReplaceString` over the match's text, ported from the source named under "What is on the tree": `parseReplaceString`, the parameters test, `buildReplaceStringWithCasePreserved`, `replaceWithCaseOperations`, and JavaScript's substitution rules for `$$`, `$&`, `` $` `` and `$'` (both the empty text), `$N` and `$NN` (a number past the group count reads as one digit and the rest literal, and a group number the pattern lacks stays as typed), and `$<name>` (only when the pattern has named groups). In literal mode it is the text as typed, with Preserve Case. In a file with CRLF line ends, a newline the text writes is written `\r\n`, as VS Code's model writes its own line end.
   - The server never trusts the page's replacement: the write recomputes each from the current file.
   - Every behaviour of VS Code's two functions is a test (the cases below); the port is written in this module's own words and carries VS Code's MIT notice in its head comment as the source it follows.
7. **The write.** `POST /api/ops` gains `{ op: 'replace', query: { q, word, case, regex, under }, replace, preserveCase, items: [{ root, path, hits: [{ line, at, match }] }] }`, run by a new `src/lib/server/files/fs/replace.ts` that `ops.ts`'s `run` dispatches to, calling `runRipgrep` of `server/files/search.ts` so that module stays the one subprocess call site. The request is refused whole before anything is read when `refusalOf` refuses its query (`bad-query`, new), when `items` or a file's `hits` is empty, or names a file or a hit twice (`not-an-action`), or when the replace text holds a marker (`marker`). For each file in order: resolve it in its root (`outside`, `missing`), refuse a protected file (`protected`), a file its mode locks (`denied`), a file whose bytes are not text (`binary`, new), a file over `SAVE_MAX_BYTES` (`too_large`), a file holding a marker character U+E000 to U+E003 (`marker`, new); run ripgrep with the query's arguments and the template over that one file, with the search timeout (`searchSettings(config).timeoutS`, read by the route); a run that fails or times out refuses the file `search-failed` (new); every hit the request names must be a submatch of that run at the same line and character start with the same matched text, or the file is refused `changed` (new); then keep a copy of the file (`keepCopy(history, path, 'replace')`, a third `HistoryKind`, with the `save` size limit and pruned per file as `save` copies are), splice the named submatches' replacements in from the end of the file back at their byte offsets, every other byte (a `\r\n` included) as it was, write it through `writeTextAtomic` inside the process's write chain (`chained`), and note it. The request stops at the first refused file, as a list operation does: the answer names the files done and the one it stopped at. The whole request is one `files` record of the change log with the field `replace` (a new `FILE_FIELDS` word, which `file-undo.ts`'s `fieldShape` then reads from `FILE_FIELDS` instead of its own copy), `before` the stamps of the files as they were, each with its `kept` copy id, and `after` their stamps as written.
8. **The undo and the redo.** `file-undo.ts` takes back a `replace` record by writing each file back from its kept copy, only while every file still holds what the replace left (`holds`, else `moved`); a copy the history pruned refuses as the other kept-copy undos do. The undo keeps a `replace` copy of each file as the replace left it and records itself as a `replace` record whose `before` names those copies, so Shift+Cmd+Z writes the replaced text back by the same path. The History view words the record ("Replaced in {n} files", with the file names as the other file records list them). The Timeline (`timeline.ts`, `timeline-reads.ts`) lists a `replace` copy with its own word.
9. **Open tabs.** Before a replace is sent, a file whose source tab holds unsaved text is left out of the request and named in the outcome ("has unsaved changes in an open tab"), as the Files view's `unsaved` does for its operations; a Replace on one hit of such a file writes nothing and says so. After the answer of a replace or of its undo or redo, a clean source tab on a written file reads the file again (a new `reloadSource(id)` in `source.svelte.ts` beside `loadSourceDraft`), so it shows the text on disk; a tab with unsaved text keeps it.
10. **Replace Preview.** With the row shown, pressing a hit opens VS Code's Replace Preview: a diff pane, the file on the left and the file with this tab's replacements on the right, titled "{name} <-> {name} (Replace Preview)", at the hit's line. The left is the file on disk; the right comes from `GET /api/ops` with the query, the replace text, Preserve Case and the hits not dismissed (a `preview` branch of `handleCompare`'s route), so a dismissed hit stays unreplaced in it. `DiffSubject` gains one optional field for it and `sideOf` one line (`replace`), so one preview pane per file; the query is carried in the subject's own field and not in the id, and a second preview of the same file with another query or replace text updates that pane's field and reads again.
