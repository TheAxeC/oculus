## Shapes for Axel (booked in the state file's open items when this brief was written; the recommended reading is what the package builds)

1. **Where a new worktree goes.** Recommended: `<root>/.agents/worktrees/<name>`, the hub's own convention, for every root; the view says the path before the worktree is made, and a root whose `.gitignore` does not carry `/.agents/worktrees/` gets a warning line in the view rather than an edit to its `.gitignore`.
2. **What the merge-back does.** Recommended: `git merge <branch>` on the root's checked-out branch, git's own default (a fast-forward when it can be one, a merge commit otherwise), refused when the root has staged or unstaged changes or the branch is the one checked out, behind the page's confirm and the write token like `commit` and `push`; a conflict aborts the merge (`git merge --abort`) and the answer says which paths conflicted, so a press on the page never leaves a repository half-merged and the reader takes the merge to a terminal knowingly. Removing the worktree after the merge is a second control, never part of the merge. (Axel, 2026-09-15 23:32: the three shapes agreed; the mid-merge alternative was the lazy one and is not what is built.)
3. **Which roots the channel carries.** Recommended: every root the file browser knows (the hub, the configured roots of `sources.yml`, the saved workspaces' roots) plus the sessions' workspaces as today, the engine config folder left out since it is not a repository of its own.

## The acceptance list

1. **The channel carries more.** `GitState` gains `log` (the newest twenty commits as `{ hash, short, subject, when }` from `git log -20 --format=...`), `branches` (the `Branch` rows `git-write.ts` `parseBranches` already reads), and `worktrees` (`git worktree list --porcelain` parsed into `{ path, branch, head, main: boolean }`), each read in `server/git.ts` beside the status with the same timeout and never throwing; the watcher reads the roots of shape 3, taken from the fs reader (`server/files.ts`) at start and again when the `files` channel or the workspaces file changes, so a root added in the page is watched. The diff is not on the channel: `GET /api/git?diff=<root>&path=<file>&staged=<0|1>` answers one file's diff (`git diff` or `git diff --cached` over one path, same-origin only, the root checked like every other git request, the path inside the root), capped at `MAX_OUTPUT`; and `GET /api/git?worktree=<path>` answers a worktree's diff against the root's checked-out branch (`git diff <root branch>...HEAD` in the worktree, plus its own status through `statusFor`).
2. **The Repositories view** (`views/Repositories.svelte`, id `repositories`, Sources group order 5 after Files, listed; the words in `config/text/views/repositories.yml`): one section per root of the channel, in the order the fs reader lists them, each with the branch line (branch, ahead, behind, upstream, detached), the three change groups as `ChangesRepo.svelte` draws them (reuse the partial or lift its groups into a shared partial under `views/shared/`, not a copy), a control per row that opens the file's diff in a pane of its own (`views/repositories/Diff.svelte`, an unlisted view instance keyed by root and path, drawing the diff as a code block through the file view's highlighter with `diff` registered), the log as a list of twenty rows, the branch list with the create and switch controls the Changes panel has, and the worktrees of the root each with its path, branch, a diff control (the same Diff pane over the worktree endpoint), a "terminal here" control (a `shell` terminal started with the worktree as `cwd`, the terminal pane opened) and the merge-back control (shape 2). A "new worktree" control per root takes a name, makes `<root>/.agents/worktrees/<name>` on a new branch of that name from the root's HEAD (`POST /api/git` action `createWorktree`, confirmed), and starts a `shell` terminal in it. A root whose state carries `error` draws the error and nothing else.
3. **The writes.** `ACTIONS` gains `createWorktree` `{ root, name }`, `removeWorktree` `{ root, path }` (refused when the worktree has uncommitted changes; `git worktree remove` and `git branch -d` of its branch) and `merge` `{ root, branch }` (shape 2, aborted and reported on a conflict), all three in `CONFIRMED`; each in `git-write.ts` with the allowed-root check and the same timeout; a worktree path is checked to be under the root's `.agents/worktrees/` before anything runs. The page's `writeGit` carries them.
4. **The Changes panel** keeps working as it does, over the same channel, its tests unchanged.
5. **Words and docs**: `config/text/views/repositories.yml`; `HELP.md`'s row and one paragraph on worktrees and the merge-back; DESIGN.md's decision line; `views/registry` and rail tests updated for the sixth Sources view.
6. **Tests**: `tests/server/git.test.ts` (log, branches, worktrees parsed over a repository made under `mkdtemp` with `git init`, a worktree added, a commit; never over the checkout), `tests/watch/git.test.ts` (the roots of shape 3 watched; a workspace root added at runtime picked up), `tests/routes/git.test.ts` (the diff GET and the worktree GET; the three actions with their refusals: outside path, dirty worktree, dirty root on merge, unconfirmed), `tests/state` for the writes store, `tests/views/repositories.test.ts` (a section per root, the error case, the log rows, the worktree rows with their controls, the Diff pane), and a browser case: open Repositories over the served hub copy (which is a git repository the run makes, or one the spec makes under the temporary hub), see its branch line and log, open one file's diff, make a worktree, see it listed, remove it.

## Decisions taken in this brief (each reversible, none silent)

1. The diff is fetched on open rather than published, since a diff of every changed file of every root on every event is what the channel's two-second throttle is there to avoid.
2. The log is twenty rows, the number in one constant, since the view is a glance and a terminal is where a longer history is read.
3. The new worktree's terminal is a shell, not an agent, since which agent to run there is the reader's own next command.
