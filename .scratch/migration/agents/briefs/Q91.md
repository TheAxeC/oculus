## What to build

1. **The editor shows every modelled field** (`state/forms/schema.ts`):
   - `NOT_IN_MODEL` keeps only the fields the model does not carry (`code_availability.description`, `.homepage`, `.topics`, `.visibility`, `paths`) and its head comment says five.
   - `fieldValues` maps `priority` to `project.priority`, `waiting-on` to `project.waitingOn`, `snooze` to `project.snooze`, and `subtasks` to one line of text, the open lines' `do` joined by `; ` with a done line left out (the box is a one-line read-only input, as the schema's help says the form does not change them).
   - `followup.do` and `followup.after` map to the one note's `do` and `after` when the project has exactly one note, writable. Two or more notes: both fields read-only, with the sentence that the manifest holds several follow-up notes and they are edited on the Focus board or in the file (a key of `config/text/views/boards/editor.yml`); a rule in `schema.ts` (`followupWritable(project)`) decides it, and the payload function leaves both fields out whenever it says no, a draft kept from before the second note included.
   - The write (`server/edit/yaml-edit.ts`) treats a `followup:` list of exactly one note as that note: setting a child rewrites the one-item list as the map, as `SHORTHAND` does for a bare note. A list of two or more is refused as today.
   - Emptying `followup.do` clears the whole `followup` group (the form posts the parent `followup` cleared, as `manifest.ts:254-262` allows), so no orphan `after` is left and a bare note is removed rather than left in place with a "saved" line.
2. **The card draws the follow-ups** (`views/shared/card/CardDetails.svelte`): a Follow-up field after Next, one line per note: its `do` drawn with `CodeText`, and "not until <date>" when `after` is a date in the future, decided by the rule `dueFollowups` uses (`state/boards/ticker.ts:175`), exported and reused, with the card's `now` passed down from `ProjectCard`. A note whose `after` is not a date draws no "not until". The board's open card and the project view's card both draw it, since they are one card.
3. **The status line as a field**: drawn with the `field` snippet under the label "Status" (a text key), its value through `CodeText`, so backticked words are code; it takes the field value's size (`fs-md`, before `fs-sm`), and `tests/views/whole/type-scale.test.ts:227` drops `.statusline=fs-sm`. Every manifest prose field the section draws goes through `CodeText` by the same rule: `latest`, `next`, `outcome`, each result, each idea, and `reproduced.note`.
4. **The project's file list is the Files view's tree, on every card** (Z286, decision 1):
   - The explorer tree moves under `views/shared/explorer/`: `views/sources/files/tree/` (its 17 files), the two files outside it the tree imports (`Questions.svelte`, imported by `tree/Tree.svelte:47`, and `opening.ts`, imported by `tree/menu/row-menu.ts:36`; both import only `ui/`, `state/` and the tree), and the rooted-tree wiring moved out of `Files.svelte` into one component, `views/shared/explorer/RootedTree.svelte`, under 300 lines (the rows from `treeRows` with a `top`, the selection, the toggle, the open through `opening.ts`, the listing failures and the filter-matches-nothing line). `Files.svelte` draws `RootedTree` for its tree and the card draws it for the project; no copy of the wiring is left. Every importer follows (`git grep -ln "views/sources/files/tree\|files/tree/"`), and the head comments that name `Files.svelte` as their owner (`Tree.svelte:2`, `:83`, `control/view-access.ts:1-3`) say what they are now. The layer rule is met by the move, never by a widened allow list.
   - The folder reading for a fixed folder is a function exported from `tab-roots.ts` (the root holding the folder, and the folder as `top`), which `followView` then calls; a project folder that is itself a root has the path `''` and its head is named by the folder.
   - `CardDocs.svelte`'s Files section becomes: the finder box as today; while text is typed, the matching files listed as today (recursive over the project, most recent first, capped, with sizes, each opening by today's rules, a program file through its program); with the box empty, `RootedTree` rooted at the project's folder, its head open on first draw, with no `..` row and no workspace header, the hidden, ignored and nesting toggles at their defaults.
   - The tree's state is a record of its own: owner `<tab instance id>#files:<project id>`, so the project tab's `{ id, doc }` record and the board tab's own record are never touched, and each card on a board keeps its own tree. The forget the layout is handed (`state/client/context.ts:207-214`) also clears every record whose key starts with `<id>#files:` (a prefix clear in the ui store). A saved record of the wrong shape reads as an empty tree.
   - `followTabs` (`ops.svelte.ts:273-286`) restates these records too after a rename or a move, so their open folders and selection follow.
   - The Files tree's row menu gains Open in Program for a file `open.program_ext` names (through `opensInProgram`), so the tree opens such a file as the card's list did; this holds in the Files view too.
   - In a card the tree's Enter, menu, bookmark star, git decorations and drag are the Files view's own; the menu's bookmark item is offered as there.
   - A project folder no root holds: the tree's place says the folder is outside every root of the workspace (`files.outside`, `config/text/views/sources/files.yml:137`) with the Add Folder to Workspace action, as `Files.svelte` does.
   - `files(item.id)` is asked only while the finder holds text, so a card with an empty box makes no `api/project-files` request.
5. **Words and docs**: every new sentence a key of the text catalog; HELP.md (`:101`, `:152` the `project` and `editor` entries and "Open in its program ... on a project card's file list") and DESIGN.md (`:159`, `:366`, `:421`) rewritten where the change makes them false, found with `grep -n "project view\|Project view\|project tab\|status line\|follow-up\|file list\|its program" HELP.md DESIGN.md`.
