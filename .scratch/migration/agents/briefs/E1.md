## What to build

1. **One new section in DESIGN.md, `## Apps added while oculus runs`**, placed after `## Hot reload` and before `## Relationship to the cockpit`, opening with one sentence that it is a proposal for Axel's ruling and that nothing in it is built. It answers, each as rules in the document's own voice, with the concrete shapes a builder would need:
   - **Where an app lives** and what one is on disk: the folder (named by a `local.yml` key with its default, as `calendar_dir` and `mail_dir` are), its manifest file and every key of it (name, title, glyph, entry file, the channels it reads, the write kinds it may ask for, anything else), and what makes a folder not an app. An app's view id is namespaced (for example `app:<name>`) so it never meets a built-in view id or a collection key; an empty, repeated or reserved name is a finding with its sentence in `config/text/findings.yml`.
   - **How oculus finds it while running**: the watcher module (DESIGN.md:116's rule), what the page is told (a channel or a field of an existing one) and that the list also rides with the page data for the first frame, as the collection keys do; how an app becomes a view of the catalogue without a build, through the per-key registration `registerCollections` already does; how an app's own title and glyph reach the catalogue and the tab although a registration carries catalog keys (a registration field for literal words, or one catalog key taking the title as its argument, as `ui.unknown_view` takes `{0}`); the catalogue group it sits in; and what happens when an app is added, changed or removed while a tab of it is open, stating whether its tabs close (as `unregisterView` does today) or stay as unknown views, and why.
   - **How it is served and isolated**: the address the server serves an app's files from and its relation to the `/api/` guard (an opaque frame's requests for its own files under `/api/` would be refused by `refused()`, so the address sits outside `/api/`, or is added to `UNGUARDED` with its reason; say which and that a cross-site page can then read an app's files); the `Access-Control-Allow-Origin` its answers carry for the frame's module scripts and fetches; the inside-folder check by real path, symlinks included (as diagrams.ts:38-50); the iframe's `sandbox` value and why it leaves out `allow-same-origin`; the `Content-Security-Policy` sent with every app file, which carries the `sandbox allow-scripts` directive so the document is opaque wherever it is opened (a frame, a direct visit, a popup), never `allow-popups-to-escape-sandbox`, and names its sources by address rather than `'self'`; that the server serves an app's files only while its approval holds; and what an app can never reach (the write token, `/__data.json`, the socket, other apps, the page's DOM). The rules hold for an app tab in a floating pane, a popped-out window and the Electron window, or the section says what differs.
   - **What it may read**: the bridge (`penpal` 8.0.1), owned by one frame instance and made again when the frame remounts (never a module-level bridge, spec.md:73), with the parent's `allowedOrigins: ['*']` and the source-window check as its guard, the child's `allowedOrigins` the page's origin, and where the child's penpal script comes from; the methods the page exposes: the snapshots of the channels the manifest names and the pushes after them (each of audit, calendar, config, feeds, files, git, hpc, inbox, portfolio, sessions, usage and `pty:<id>` ruled open or closed to apps, with the reason for the ones that carry mail, calendar, account, transcript or terminal content), the theme's tokens with the wallpaper state and their changes, the tab's instance state (read and write) or that apps keep none; and what is refused and how the app is told.
   - **How it writes**: every write goes through the page, which sends it through `/api/write` with its token as any view's write does; the manifest names the write kinds of `/api/write` the app may ask for (the vocabulary under "What is on the tree"), each kind ruled open or closed to apps (undo and rail, which take back any change and rewrite `config/layout.yml`, stated), the page refuses any other; the other 13 write routes are closed to apps unless the section names one with its reason; a confirmation where DESIGN.md:249 asks one.
   - **Approval**: an app runs only after the reader approved it on this machine, by the same rule as DESIGN.md:148 (the approval kept under `~/.oculus/` and keyed by the app's content, so a changed app asks again), enforced by the server as well as the page; the approval file's name and shape stated once for every user of the rule, D17's commands included; what the reader sees before approving (the manifest's reads and writes, its title and words drawn as text, never as HTML).
   - **What an app does not get**: no process, no server code, no file outside its folder, no network beyond what the CSP allows (say what it allows); the page's keyboard chords and its right-click handler do not see events inside the frame (say so, or name the keys the bridge forwards).
   - **Words**: the words the reader sees (the approval question, a refused read or write, an app that failed to load) come from `config/text/`, and the finding sentences from `config/text/findings.yml`, named as keys the build step will add.
   - The section names no plan id, date or session (the history check fails on them).

## Cases (read, since this is a text step)

The builder's first task: read DESIGN.md's sections named above and the files under "Read" before writing, and hand back, before writing, any case below the brief's rules get wrong.

1. An app whose manifest names a channel oculus does not have: the section says what the page does (refuses the read and says so in the app's frame, or refuses the app at approval).
2. An app that tries `fetch('/api/write')` from its frame: the section says why it fails (opaque origin, `sameOrigin` refuses `Origin: null`, and no token).
3. An app whose files change after approval: it asks again.
4. An app folder with no manifest, or a manifest that does not parse: not an app, and the Findings view says so, or it is ignored; the section says which.
5. Two apps with the same name in the manifest: the section says which wins or that both are refused.
6. An app path like `../../.ssh/id_ed25519` in a request to the app's address: refused, and the section names the check.
7. An app asking for a write its manifest names, the write itself needing a confirmation elsewhere in DESIGN.md: the confirmation is asked.
8. The theme switched while an app's tab is open: the app gets the new tokens through the bridge.
9. An app removed while its tab is open: the tab says so, as an unknown view does (DESIGN.md's rule for a renamed view's saved tab).
10. A saved page layout naming an app's view on a machine without that app: drawn as an unknown view.
11. An app's file address opened directly in a browser tab: the `sandbox` CSP directive makes it opaque, so it cannot read `/__data.json` or any `/api/` route.
12. An app that asks the server for its files before approval, or after its files changed: the server refuses them.
13. A symbolic link inside an app folder pointing out of it: refused by the real-path check.
14. An app named like a built-in view or a collection key (`focus`, `funding`): its namespaced id does not meet them; an empty or repeated name is a finding.
15. A saved layout naming an app's view on a machine that has it, drawn before the app list arrives by the socket: the list rides with the page data, so the tab is never drawn unknown or closed for a frame.
16. A manifest asking for the `undo` or `rail` write kinds, or for the `pty:<id>`, `inbox`, `calendar`, `sessions` or `usage` channels: the section says which are refused at approval.
17. A manifest whose title holds HTML: drawn as text in the catalogue, the tab and the approval question.
18. The wallpaper theme on: what the frame's box paints, and whether the bridge sends the wallpaper state.
19. A page chord or a right-click with the focus inside the frame: the section says what happens.
20. An app tab moved into a floating pane or a popped-out window: the bridge is made again for the new frame.
