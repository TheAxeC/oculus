## What to build

The section stays a proposal: its second paragraph now says the section is ruled and unbuilt. It carries no date and no person's name, as the rest of DESIGN.md carries none.

1. **Two kinds of app.** A machine app lives in `<apps_dir>/<name>/` (`apps_dir` in `config/local.yml`, `~/.oculus/apps` when absent). A root app lives in `<root>/.oculus/apps/<name>/`, for each root shown in Files, whether or not the root is a git repository. The section says which rules differ for the two kinds, each in the paragraph it belongs to, and gives both kinds one name each that it then uses every time ("machine app", "root app").
2. **Identity.** A root app's view id and its address carry its root, so two roots can each hold an app of one name and a machine app can share a name with a root app. The form: the view id is `app:<name>` for a machine app and `app:<root key>/<name>` for a root app; the address is `/apps/<name>/<key>/<path>` and `/apps/@<root key>/<name>/<key>/<path>`. The section says why `@` and `/` cannot collide with a name (the name pattern `^[a-z][a-z0-9-]{0,39}$` has neither) and what happens to a root whose key holds a character the address cannot carry (it is percent-encoded in the address, and compared decoded). The key derivation (the HMAC input) names the root as well. The row of the `apps` channel gains `root` (empty for a machine app).
3. **Approval keyed by folder.** An approval entry is found by the app's real folder path, not by its name: the entry's `name` field becomes `folder`, approving an app removes the earlier entries of that folder only, and `revoke` names the folder. `POST /api/approve` carries the view id in place of the bare name. Approval stays per machine and keyed by content, so a root app that arrives or changes by `git pull` asks before it runs.
4. **The Document view rule.** A file whose real path lies inside any apps folder, the machine's or a root's `.oculus/apps/`, never opens in the Document view and opens as source text.
5. **The watcher.** `server/root/watch/apps.ts` watches the machine's folder and each shown root's `.oculus/apps/`, and follows the roots as they are added to and removed from Files (the workspaces file and a config push). A root with no `.oculus/apps/` is looked at again as the machine's missing folder is. The tabs of a root app whose root leaves Files stay and draw the unknown view, as a removed app's do.
6. **What a root app sees (N1 (a)).** On `git` and `files` a root app gets only the part of the payload that belongs to its own root; the page builds that copy. The hub channels it declares (`portfolio`, `feeds`, `hpc`, `audit`, `config`) are whole. A machine app gets every declared channel whole. The section says what "the part that belongs to its root" is for each of the two payloads, read from their types.
7. **The channels (C8 (e)).** `inbox`, `calendar`, `sessions` and `usage` are open to a machine app and refused for a root app (`findings.apps.channel_closed`, with the reason in the sentence). `apps` and every `pty:<id>` stay closed to all apps. The words `apps.read.<channel>` exist for the four newly open channels and say plainly what each carries (other people's mail subjects and senders, attendees, transcript titles and prompts, account labels and limits).
8. **The store (C11, N2 (c)).** The per-tab value stays. Each app also has one store: one JSON value, read with a bridge method `getStore()` and written with `setStore(value)`, which the page sends as a new write kind `app-store` through `POST /api/write`. A machine app's store is `~/.oculus/app-data/<name>.json`, a root app's `<root>/.oculus/app-data/<name>.json`. Every tab of the app shares it; a change by one tab reaches the others through a bridge call `onStore(value)`; a write is a change record, shown in History and undoable; the size limit is a new key `store_max_kb` of `apps:` in `config/behavior.yml` (256); an app needs no `writes:` entry for its own store. The section says that a root app's store is a file of the root, tracked by git unless the root ignores `.oculus/app-data/`, and that the store is outside the app's folder, so writing it never changes the app's content hash. The `app-store` kind is refused for any request that does not carry the app header, and an app can name no store but its own.
9. **Outside addresses (N3 (c)).** A manifest key `connects:` is an optional list of origins (`https://host` or `https://host:port`, no path, no wildcard, each once; `http:` only for `localhost` and `127.0.0.1` on a port other than oculus's own). The approval panel lists them in plain words. The policy's `connect-src` names them beside the app's own files. Both kinds of app may declare it. A malformed entry refuses the app (`findings.apps.connect_shape`). The paragraph "What an app does not get" and C29's sentence are corrected: what an approved app reads can reach the origins it declared, and the reader sees those at approval.
10. **Downloads (N4 (b)).** `allow-downloads` is added to the frame's `sandbox` attribute and to the policy's `sandbox` directive, and leaves the list of tokens that are never there. The section says what a download is for (an export the app builds from what it read).
11. **The `open` method (N5 (b)).** The bridge gains `open(target)`: `{ view: <view id> }` opens a registered view, `{ project: <key> }` a project's tab, `{ file: { root, path } }` a file as source text in the source tab. It never opens the Document view, and a root app may name only its own root in `file`. A target that is refused rejects `closed`. The method needs no manifest entry.
12. **Approval while an app is written (N6 (b)).** The approval panel of a machine app offers a second control, "Keep approved while I edit": until the server process ends, a change to that app's files keeps it approved and served. It is held in the server's memory, never in `approvals.json`, is ended by Revoke, and is never offered for a root app. The tab's strip shows the lock mark's counterpart (a word `apps.editing_mark`) while it holds.

The name of a root app's view id is the text after the last `/`, which the name pattern keeps free of `/`.
18. **The `open` method against the closed route.** The bridge method `open` never reaches `POST /api/open` (DESIGN.md:385), which starts a program and stays closed to apps; the sentence listing the closed write routes stays true, and the section says the two are different things in the paragraph of the method. `{ view }` admits the view ids the Views catalogue lists; `document`, `terminal`, `file`, `source`, `project` and any view that needs an argument are refused `closed`. `{ file }` naming a file that does not exist rejects `missing`; a binary file or a file that opens in a program opens as the source tab shows such a file today, and no program is started. `open` counts toward a limit `apps.opens_per_min` (30) and rejects `rate` past it.
19. **The store, completed.** `getStore()` answers `null` when the file is absent, does not parse or is over the limit. `onStore(value)` is called in every tab of the app, in every window, whenever the file changes, whoever changed it (another tab, History's undo, a pull, a hand edit): the server watches the store file and the page hears it on the `apps` channel. A store write counts toward `apps.writes_per_min`. `app-store` in a manifest's `writes:` is refused `write_closed`: the kind is granted to every app for its own store and cannot be asked for. The change record of a store write holds the file, the app's view id and the sizes before and after, and the value before is kept beside the log in `~/.oculus/app-data/.undo/` for the undo, so a 256 KB store does not put 512 KB in a line of `changes.jsonl`. A root that cannot be written rejects `setStore` with `refused` and the server's reason; `.oculus/app-data/` is created on the first write. The approval panel of every app says where its store is written, and for a root app that the file is in the root and tracked by git unless ignored.
20. **`connects:`, completed.** A trailing slash alone (`https://api.example.org/`) is accepted and stored without it. An origin given twice is `findings.apps.list_repeated`. An entry with a user name, a path, a query, a wildcard, a scheme other than `https:` (`wss:` included, since `connect-src https://host` does not admit it) or `http:` to anything but `localhost` and `127.0.0.1`, and `http://localhost:<oculus's own port>`, are each `findings.apps.connect_shape`.
21. **Downloads, what is not claimed.** The section claims nothing about whether a download link to an outside address sends a request from an app with no `connects:`; it says the build step measures it in Chrome and closes it if it does, as the section already says for WebRTC.
22. **What a root app gets on `git` and `files`, exactly.** `git` is `Record<string, GitState>` (`model-sessions.ts:544`): a root app gets the one entry of its root's folder and `onChannel('git')` is called only when that entry changed. `files` is one notice `{ root, bookmarks? }` (`model-sessions.ts:555`): a root app is called only for a notice naming its root, `read('files')` answers the newest such notice or null, and the bookmarks notice (`root: ''`) reaches machine apps only.
23. **Keep approved, and the manifest.** "Keep approved while I edit" covers every file of the app except `app.yml`: a change to the manifest ends it and asks again, since the manifest is what names the channels, the writes and the origins the reader approved. The control's words are catalog keys (`apps.keep_approved`, `apps.editing_mark`).
24. **A root's apps folder that is a link.** A root's `.oculus/apps` that is a link is followed once, as the machine's folder is, and must resolve inside the root; one resolving outside the root is `findings.apps.folder_outside` and none of its apps is offered. One real folder reached through two roots (a link, or two root keys naming one folder) belongs to the root that comes first in the order Files shows the roots, and the other gets `findings.apps.repeated`. A folder that is both `apps_dir` and a root's `.oculus/apps/` holds machine apps, and that root gets `findings.apps.repeated`.
25. **A root key that comes to name another folder.** Root keys are per workspace, so after a workspace switch a key can name another folder. A root app's tab keeps, in its saved state, the real folder it was opened for; when the key names another folder the tab draws the unknown view and does not draw the other app with the first app's per-tab value.
26. **Telling apps apart.** Where an app's title is drawn (the Views catalogue, a tab, the approval panel), a root app's title is followed by its root's key, and the approval panel gives the app's folder path.
