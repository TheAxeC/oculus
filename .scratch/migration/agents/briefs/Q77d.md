## What is on the tree (read on main at fa59cab3)

1. The whole unit suite on an idle machine: `npx vitest run --reporter=json` printed 5332 passed in 160.85 s of wall time. Its slowest case is `tests/checks/bin/dispatch-note.test.ts:188` "lands every record of many writers started at once against a lock a dead writer left", 125.9 s; the suite's files run side by side, so the suite cannot end before this case does.
2. That case runs 150 rounds; each round starts 24 writer processes of `bin/dispatch-note.mjs` at once against a lock a dead writer left, 3600 process starts in all. Its directive `// revert: bin/dispatch-note.mjs:166 => return true;` names `stale()`'s body at `bin/dispatch-note.mjs:166`, `return !alive(holderOf(state.content)) || state.age > waitMs;`: with the revert every lock is judged stale, live or not, and a writer clears a lock another live writer holds. Checked: `sed -n 160,170p bin/dispatch-note.mjs` and `sed -n 188,208p tests/checks/bin/dispatch-note.test.ts`.
3. `takeLock(lock, waitMs, once)` is exported from `bin/dispatch-note.mjs:224`. On a lock that is there, it calls `wait()` (`:253`), which clears the lock only when `stale()` says so and otherwise pauses and retries until `waitMs + 2000` ms have passed. `tests/checks/bin/dispatch-note.test.ts:430` already imports `takeLock` in-process.
4. `tests/checks/bin/dispatch-note-race.test.ts` proves, by one fixed interleaving, that a clearer leaves alone a lock a live writer took after the clearer judged it.

## What to build

1. **Replace the 150-round case by one deterministic case** in `tests/checks/bin/dispatch-note.test.ts`, named "waits for a lock a live writer holds, and takes it only once that writer lets it go". It:
   - starts one child process (`node -e`), which writes the lock file with its own pid as holder (the content form `takeLock` writes, `<pid> <hex>`), prints a line when the lock is written, waits 300 ms, then reads the lock: if the content is still its own it removes it and exits 0, otherwise it exits 1;
   - once the child has printed that line, calls `takeLock(lock, 10000)` in the test process;
   - expects `takeLock` to return, the child to exit 0, and the lock to hold the test process's own content afterwards.

   With the revert of item 2 applied, `stale()` judges the child's live lock stale, `takeLock` clears it at once, and the child exits 1, so the case is red on every run. The case carries `// revert: bin/dispatch-note.mjs:166 => return true;`.
2. **Remove the 150-round case and its comment**, whose revert the new case now proves deterministically.
3. The case needs no timeout option: it runs within vitest's 5 s default.

## Part 3, the watcher waits and the launch note's file timeout (read on main at fa59cab3)
