## What to build

1. **The hub's parent is private.** `labTarget` (`tests/routes/edit/write-fixture.ts`) makes its primary hub and its lab hub inside one private folder of their own, so `<hub>/..` is that private folder and never the shared temporary folder. It does so by building the primary through `targetOver` over a hub folder inside that private folder (the same files `target()` writes, through one function both use, never a copy of `target()`'s body), or by an optional parameter of `target()` naming the parent, default unchanged, so `target()`'s 38 importers and `configTarget`'s callers are untouched. Every other behaviour of `labTarget` stays: the same `LabTarget` shape, the lab's `.oculus/config.yml` and `pictures`, the primary's files as `target()` makes them, the `primary` false form. The 11 rows of describe 'a write that names a hub' then pass whatever the temporary folder holds, and their assertion at line 458 is not changed, loosened or removed. `/tmp/x` itself is never touched, read, moved or removed: it is the user's file.
2. **A load reuses the parse of an unchanged file, through a value its caller passes in.** `loadConfig` takes an optional `parses` in its options and returns the `parses` of its own load beside `config`, `findings` and `from`:
   - `parses` holds, for each file of oculus's config folder the load parsed without error, keyed by its name relative to `config/` (`defaults/behavior.yml`, `options/local.yml`), the file's text and its raw parse as `yaml`'s `parse` returned it, before `?? empty`.
   - On each call every file is read from disk as today. A file whose name is in the given `parses` with the same text takes a `structuredClone` of the kept parse and is not parsed again; any other file is parsed. The returned `parses` holds one entry per file parsed without error in this load (the kept entry or the new one), so it holds only the files of the folder now and grows no larger than the folder.
   - A file whose text comes from `instead` neither reads nor writes `parses`: it is parsed, and the returned `parses` keeps for that name the entry given in, so a candidate's text is never kept.
   - A file that does not parse is not kept, and its finding is made on every call as today. `?? empty` and the shape check run on every call, so an empty defaults file reads as `{}` and an empty options file as `null` (`not_a_map`) as today, and each finding names the file of this call.
   - No kept parse is reachable from a result: what the merge and the layers receive is a copy, so nothing a caller or a later layer changes in `config` reaches `parses` or another call's result. A `parses` passed in is only read, never changed, so a frozen one works.
   - For any input, `config`, `findings` and `from` are deep-equal to today's, with or without `parses`.
   - The product passes it: `contextConfig` (`config-parse.ts`) keeps the `parses` of its last load in its closure and passes them into the next, for `load` and `loadHub` alike, so the server parses again only the files whose text changed, and parses no unchanged engine file for another hub. `config-cache.ts` and its stamps are unchanged; G61's behaviour is unchanged.
   - No module-level state: the kept parses live only in values a caller holds and passes.
   - The type of `parses` is exported only where a production file imports it.
3. **The test fixtures stop loading per row what does not change per row.** One fixture module (a new file `tests/fixtures/engine-load.ts`) computes at import, once per test file, `loadConfig(engineDir())` and `loadConfig(engineDir(), { hub: DEMO_HUB })`, deep-frozen (each map and list frozen, by a small helper in that file), and exports functions that hand each caller a `structuredClone` of either, plus the frozen engine `parses` for a load over another hub. Then:
   - `write-fixture.ts` takes them in `targetOver` (the `config` and `career` of `:135,149`, and `engineConfig`) and in every other place of the file that loads either per call (`:121`, `:148-149`, `:317`, `:325-326`, `:504-505`, as `grep -n 'loadConfig(' tests/routes/edit/write-fixture.ts` lists them); a load over another hub there passes the engine `parses`.
   - `deposit-world.ts`'s `depositTarget` (`:69`, `:75`) takes the engine clone.
   - `zenodo-world.ts`'s `fixture()` (`:121`) and `withLab()` (`:153`) load over the row's hub with the engine `parses`; `:42` takes the engine clone.
   - No row's change reaches another row. `targetOver`'s signature, `keep` included, stays. `warmConfig` and its 17 callers stay unchanged.
4. **The rows run fast alone, with nothing to raise or tag.** After items 2 and 3, each of the 5 rows takes at most 300 ms alone under `npx vitest run <file> --reporter=verbose` (at the 5 to 10 times slowdown measured under the whole suite, that stays under 5000 ms). The report quotes, for every row of `app-store.test.ts` and `zenodo.test.ts`, its time before and after, marks each row that still takes 100 ms or more alone (the tree's definition of slow, `vite.config.ts:485-486`) with where its remaining time goes, read from the code and from a timing run, and quotes the two files' durations before and after. No timeout is raised, no row is tagged slow, and no `it.concurrent`, retry or sequence setting is added.
5. **The comments say what the code now does.** The head comments of `merge.ts:1-12` and `text.ts:1-8`, the doc comments of `loadConfig` (`merge.ts:124-146`) and `readConfigFile` (`text.ts:56-61`), `config-cache.ts:2-4,9,22,38` and the doc of `HubSettings` (`src/lib/data/index.ts:611-616`) are re-read and each listed as still true or rewritten. `config-cache.ts:2-4`'s "about 75 ms" is replaced by the cost a timing run in the worktree measures for a load with no `parses`, and the paragraph says that a parse again reparses only the files whose text changed. Nothing else in `config-cache.ts` changes.

## Decisions taken in this brief (each reversible, none silent)

1. The reuse is a value the caller holds and passes in (`parses`), keyed by a file's name relative to `config/` and its exact text, read on every call: it cannot return a stale value, it keeps no module-level state (`agents/spec.md:88`), it is bounded by the folder, a scratch engine's copy of `config/` reuses it, and the reads that `config-value.test.ts:47-56` records stay.
2. The product passes `parses` from `contextConfig`'s closure, so the option has a production caller (`agents/spec.md:89`) and the server stops reparsing unchanged files after a write and for each other hub. `portfolio.ts:642`, `config-place.ts:93,362`, `channel.ts:255`, `words.ts:18`, `start-colours.ts` and `vite.config.ts:480` keep their calls unchanged.
3. The fixtures compute the two fixed loads at import, deep-frozen, and clone them per row, since no test writes oculus's config folder or `DEMO_HUB`. A module constant computed once and never changed is no mutable state; the freeze makes a change throw.
4. `labTarget`'s two hubs share one private parent, so the shape a row sees (two hubs, each its own folder) is unchanged and both hubs are off the shared temporary folder.
5. The bound of item 4 is 300 ms alone, from the slowdown measured under load. A row left at 100 ms or more alone is reported, not tagged: tagging it would change its limit, which ruling 753 forbids. The orchestrator raises any such row.
