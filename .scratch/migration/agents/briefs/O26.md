# Brief: O26, the Live HPC view

Read `../spec.md` first; it governs this package unchanged. The cockpit's Live HPC tab (`tools/cockpit/src/cockpit/hpc.py`, 576 lines, and `tools/cockpit/assets/js/cockpit/07-slurm.js`, 228 lines) polls the UTwente cluster over ssh and draws the user's queue, the recent finished jobs, the partitions' capacity and the disk quota, with a cancel and a log tail per job, and a pill on the Focus command center saying how many jobs run. oculus has none of it: `config/layout.yml` already names `hpc` in the rail's System group (line 27) and `views/focus/CommandCenter.svelte` keeps the right of its heading row empty for the pill (its comment at lines 10 and 464), so the view registers into a place that is waiting for it. This package builds the view on oculus's design: a server poller publishing one socket channel, a route for the three actions, pure parsers with fixture tests, a client store, the view and its partials, the pill and a rail badge.

The cluster rule, absolute: the only commands that ever run on the cluster are the cockpit's own read-only queries (`squeue`, `sacct`, `sinfo`, `quota -s`, `df -h`, `scontrol show job`, and `ls`, `tail` and `test -f` inside the log path search) plus `scancel <id>` on the user's explicit, confirmed click. Nothing else is ever sent over ssh: no `srun`, no `sbatch`, no interpreter, no compute of any kind. The login node is for queries, and this package adds no way to run anything on it.

3. The disk meters: "disk" heading, one bar per quota item (name, used of limit, percent), from `quota -s` with `df -h $HOME` as the fallback.

5. "No jobs in the queue for you right now." when the queue is empty and the cluster answered.
6. The recent jobs, collapsible "Recent (finished) - N", over `sacct -u $USER -S <today minus days>`: Job, Name, State, Exit, Elapsed, Mem (peak used of requested, as a percent in an efficiency tone), CPU (efficiency percent), End, and the log control.

The path is found the cockpit's way: `scontrol show job` for a live job, else the candidate ladder over the job's work directory, each candidate re-checked with `test -f`, the whole search bounded by a remote timeout and a timeout reported as a timeout and never as "no log file found"; a cached path is reused only when it passes the cockpit's `_safe_log_path` shape (`hpc.py` line 477).
8. The footer line: what is polled, on which host, where the how-to is.
9. The pill on the Focus command center's heading row: "{n} HPC job(s) running | {m} pending", hidden when the cluster is unreachable or the queue is empty, opening the Live HPC view on click.
10. The rail badge on the Live HPC entry: the running count and the pending count, as the cockpit's tab button carries them (`3 5` in its header).
11. The cadences: a poll every `slurm.poll_min` minutes (20), the quota every `slurm.quota_min` (60), from `config/behavior.yml` lines 76 to 79; a forced refresh from the control; the first poll at server start. `slurm.prewarm` is read and reported but the prewarm thread is not built (decision 5 below).

## Decisions taken in this brief (each reversible, none silent)

1. **The host.** `config/behavior.yml`'s `slurm:` block gains `host: utwente` (the ssh alias, the cockpit's default) and `days: 3` (the sacct window); `local.yml` gains `hpc_host` in `LOCAL_KEYS` (`data/sources/config.ts` line 33) as the per-machine override, absent by default. Both are user-visible keys and are named here so the report does not have to.
2. **The wire.** One socket channel, `hpc`, whose payload is `{ status: 'starting' | 'ok' | 'unreachable' | 'error', hint?: string, jobs: Job[], running: number, pending: number, total: number, recent: Recent[], sinfo: Partition[], quota: QuotaItem[], updated: string (ISO), pollMin: number, host: string }`, published by the poller and on every forced refresh; `Job` carries the thirteen `squeue` fields as the cockpit parses them (`_parse_squeue`, lines 91 to 106), `Recent` the sacct fields with `memPct`, `memUsed`, `memReq`, `cpuPct` folded from the step rows (`_parse_sacct`, 133 to 180), `Partition` the five sinfo fields, `QuotaItem` `{ name, used, limit, pct }`. `POST /api/hpc` with the write token and the same-origin check, body `{ action: 'refresh' }`, `{ action: 'cancel', id }` or `{ action: 'log', id }`; cancel and log validate the id against `^\d+(_\d+)?(\.\w+)?$` (`slurm_cancel`, line 326) and answer 400 otherwise; log answers `{ status, log, path }`; cancel answers `{ status, hint? }` and triggers a poll. No GET.
3. **The ssh runner is injected.** `server/hpc/ssh.ts` exports `run(host, remote, timeoutMs)` over `child_process` with `-o ConnectTimeout=8 -o BatchMode=yes` (`SSH_OPTS`, line 17) and the poller, the route and every parser take it as a parameter, so `tests/server/hpc/*.test.ts` run the parsers over fixture outputs and the poller over a stub runner, and no test opens an ssh connection. The one ssh round trip for queue, recent and sinfo is the cockpit's (`slurm_fetch_all`, lines 248 to 279, with its section markers); quota is its own call on its own cadence.
4. **The badge mechanism.** `views/registry.ts`'s `Registration` gains `badge?: () => string` (a function the view registers, read by the rail on each render; the empty string draws nothing); `shell/ActivityRail.svelte` draws it beside the glyph. The shell keeps reading the registry only, so the boundary rows are unchanged. This is the mechanism O25's Inbox and Position Leads badges will use too.
5. **No prewarm thread.** The cockpit resolves finished jobs' log paths ahead of the first click (`slurm_prewarm_logs`, lines 422 to 475). Here a finished job's log is resolved on the click, cached per job id for the process's life, and the report says how long the first click took on the real cluster if the check reached it. Prewarm is a follow-up if that is slow.
6. **The pill and the badge read one store.** `state/hpc.svelte.ts` holds the latest `hpc` message and the derived counts; `views/focus/CommandCenter.svelte` imports it for the pill (a view importing `state/`, allowed); the pill opens the `hpc` view through `openView`.
