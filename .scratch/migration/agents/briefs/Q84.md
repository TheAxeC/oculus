## What to build

1. **The dependency.** `@tanstack/query-core` 5.104.0 in `dependencies` (`npm install @tanstack/query-core@5.104.0` from `tools/oculus`), and in `README.md`'s runtime dependency line with its licence.
2. **One query client per client state, and one helper.** A new module `src/lib/state/client/queries.svelte.ts` builds a `QueryClient` with `retry: false`, `gcTime: Infinity`, `staleTime: Infinity` and `networkMode: 'always'` as query defaults, and nothing module-wide (query-core's notify manager is left as it is). `createClientState` builds it first and hands it to each of the ten stores; it is not a key of `ClientState`, so `client-state.test.ts` stays as it is. The module exports the helper the ten stores use, for example `createQueries(): Queries` with `client` and:
   - `read<T>(key, fetcher, options)`: keys are arrays; the call reads a `$state` tick for the key's hash and answers `client.getQueryState(key)` (data, fetch status, invalidated), and never builds, fetches or writes anything on the caller's stack. When the query does not exist, or exists invalidated and idle, it schedules the fetch on a microtask, where the query is built and fetched with `client.query({ queryKey, queryFn })` (never the deprecated `fetchQuery`). It schedules nothing where the store's guard says there is no fetch (as each store guards today). One cache subscription per helper bumps the tick of the query each event names; the events are synchronous, and every call that causes one (the microtask's fetch, `setQueryData` from a `hold`, an invalidation from a socket listener, a cancel) runs outside any `$derived`.
   - A query function never throws: it answers the store's own held shape, error answers included (`{ ...PENDING, error, loading: false }` where the store replaces what is held today, the previous data with the error where the store keeps it), and never `undefined`. So an error never invalidates a query and a failed read is not asked again on every read; a store that asks again after an error today (`docs` over a drawn document on a network error) invalidates its own key as it marks today.
   - `mark(key, whileFetching)`: invalidates with `refetchType: 'none'`; when the query's fetch is in flight, `whileFetching: 'again'` records the mark in the helper and invalidates again when the fetch settles (a success clears the flag), and `whileFetching: 'drop'` leaves the fetch alone. Each store uses the value it follows today: `again` for `docs`, `files`, `latex` and `fs` marks; `drop` for `deposit.reload`, `memories.reload`, `lines.recount` and `changes` (a request in flight takes the reload's place, as today).
   - `replace(key, fetcher)`: cancels the fetch in flight for the key (`client.cancelQueries`, its late answer dropped) and fetches again, for the two stores that supersede a request today: `agents.refreshCustomizations` (two requests are sent, the superseded answer dropped, as `agents.test.ts:89-100` asserts) and `fs`' newer rounds (an older round's answer never lands after a newer one).
   - `forget(key)`: `client.removeQueries`, so the key reads as never asked (`PENDING`, `loading` true), for `files.invalidate`, `latex.invalidate` and `transcript.forget` and the transcript's release by its last viewer.
3. **The ten stores on it.** Each of the ten files holds its answers in the query client through the helper, with no record of answers, no in-flight set and no `queueMicrotask` of its own, and keeps its exported functions, its argument lists (the query client added to its constructor; `createAccounts` is not one of them), its return types and every behaviour rule listed in "What is on the tree". In particular: the channel rules become `entities.afterReceive` listeners calling `mark` on the affected keys (for `files` and `latex`, which read the channel version during a read today, on the same channel and version); `hold` becomes `setQueryData`; `docs` keeps its etag beside the held entry, sends it only when something is held, and a 304 answers the held data; `fs` keeps its failed-round rule, `readListing`'s join of the request in flight, `readFileKind`'s shared promise, `otherForm`, `relist`'s rule, `gone`, `saveNote`'s seed and `closeGoneForms`; the transcript's tail and the changes' older page are merged into the held data inside the query function, which reads the held data first, and `merge` works on copies of the held turns, so a tail that only patches `tool.ok` gives a new object that structural sharing does not fold back into the old one; `latex.redraw` reads the held answer the same way. `fs.svelte.ts` stays under 1000 lines. A clone the rewrite makes between stores goes into the helper; the allow list gains no row.

## Cases

Each existing test file named in "What is on the tree" is a case as it stands: it passes after the change with no assertion, stub or expected value changed. Two changes to existing tests are allowed, each named in the report: how a store is built (the query client passed to `createAgents`, `createLines`, `createChanges` or another constructor that gains it), and a wait helper such as `agents.test.ts`'s `settle()` waiting for the answers to be applied (for example a macrotask turn in place of five microtasks), since how many microtasks a store takes is not behaviour. A changed assertion is a finding, not a fix. Beyond those:

1. Two reads of one key in the same tick, before the answer: one request.
2. A read after the answer: no request; the answer is returned.
3. A `files` channel message while a project's files are held: the held rows keep showing, one request follows on the next read, and the new rows replace them.
4. A `files` message arriving while that key's `docs` request is in flight: a second request after the first settles, and the second answer is what is held.
5. A failed request (the fetch rejects, and a 500), then three more reads after it settles: exactly one request in all, and the store's error reads as today. 6. With `environmentManager.setIsServer(() => false)` (restored after), a key held across six minutes of fake time with no reader: still held, no request on the next read.
7. No fetch function (the server render): no request, and the store reads as today on the server.
8. `onlineManager.setOnline(false)` (restored after): the request still goes (`networkMode: 'always'`).
9. `hold` on deposit, memories, changes and transcripts: the value reads back at once and no request is sent. A `hold` while that key's fetch is in flight: the held value reads at once, and the fetch's answer then replaces it, as today.
10. `docs` with a held etag: the request carries `if-none-match`, a 304 keeps the held document, and the object read is the same object as before.
11. `agents`: a refresh while the first answer is in flight sends a second request; the first answer arriving last is dropped and the second is held.

## Decisions taken in this brief (each reversible, none silent)

1. The query defaults of item 2 (`retry: false`, `gcTime` and `staleTime` Infinity, `networkMode: 'always'`), since today's stores never retry, never drop a held answer and refetch only on their own rules; nothing module-wide of query-core is set.
2. A query function answers errors as data and never throws, so query-core's error state (which invalidates) is never reached and each store's own error rule decides.
3. A socket message marks with `refetchType: 'none'` and the next read refetches, since no query has a query-core observer and a store fetches when it is read.
4. A mark during a fetch asks again after it only where the store asks again today (`docs`, `files`, `latex`, `fs`); a reload, recount or older page during a fetch is dropped where it is dropped today.
5. `agents`' refresh and `fs`' newer rounds cancel the fetch in flight, so the superseded answer never lands.
6. `forget` and the transcript's release remove the query, so an answer arriving after it is dropped; today it is written back into the store's record, a record no reader asks for until the next read, which then asks again.
7. The query client is not a key of `ClientState`; the helper lives in `state/client/`, beside the client state that builds it.
