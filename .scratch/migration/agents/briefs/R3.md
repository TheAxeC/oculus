# Brief: R3, no globals

Read `../spec.md` first, its amendment of 2026-09-13 22:30 above all: no `globalThis`, no process-wide bridge, no module-level mutable state shared across module graphs. Axel decided it on 2026-09-13 at 22:30 ("I don't like globals at all"). This package removes every bridge the tree holds and leaves a shape a later package cannot get around.

## Why the bridges exist, and the replacement

The built server has two module graphs: `src/server.ts` (the http server, the WebSocket, the watchers, the terminals) and Kit's bundle (`build/handler.js`, the routes and `hooks.server.ts`), and a module imported by both is instantiated twice. Six modules cross that gap through `globalThis`: `server/auth.ts` line 72 (the write token), `server/hpc/poll.ts` line 135 (the HPC watcher for its refresh route), `server/pty/channel.ts` line 464 (the terminals for the terminal routes), `server/sessions/hooks.ts` line 199 (the hook store and hub for the hook endpoint), `server/watch/git.ts` line 238 (the git watcher for its routes), and D19c's `server/usage/refresh.ts` (the usage refresher for its refresh route). In dev the Vite plugin (`vite.config.ts` `configureServer`, line 28) builds the same objects inside Vite's graph.

The replacement, verified on the tree: adapter-node's handler passes the raw Node request to Kit as `event.platform.req` (`node_modules/@sveltejs/adapter-node/files/handler.js` line 112, `platform: { req }`). So:

1. `server/context.ts` (new): `type ServerContext = { hub, terminals, hooks, git, hpc, usage, usageRefresh, token, local, config }` and `createServerContext(engine)` that builds every one of them once, exactly as `src/server.ts` lines 40 to 100 and the Vite plugin do today (one composition, two callers: the duplication between `server.ts` and `vite.config.ts` goes with it); `close()` on it stops the watchers.
2. `src/server.ts` builds the context, attaches the WebSocket to it, and wraps the built handler so that every request carries it: `(req as OculusRequest).oculus = context` before `handler(req, res)`. The Vite plugin does the same in a `configureServer` middleware placed before Kit's.
3. `src/hooks.server.ts` reads `event.platform?.req.oculus` (a typed accessor in `server/context.ts`, throwing a clear error when absent) and sets `event.locals.server = context` and `event.locals.token = context.token`; `src/app.d.ts` declares `locals.server`. The token is minted in `createServerContext`, not in the hook module.
4. Every route that reached a bridge takes `locals.server` instead: `server/hpc/routes.ts` (the refresh), the terminal routes (`server/pty/routes.ts`), the hook endpoint, the git routes, `server/usage/routes.ts`; the `bind*`, `refresh*` and `bridge()` functions and their `declare global` blocks are deleted; `grep -rn globalThis src` prints nothing and a test in `tests/boundaries.test.ts` fails on any `globalThis` or `declare global` under `src/`.
5. The socket (`server/socket.ts`) takes the context's token and terminals as arguments, as it takes the hub.

Behaviour is unchanged; every existing route test passes with a context built by a test helper (`tests/server/context-fixture.ts`) instead of the bridges.

## Decisions taken in this brief (each reversible, none silent)

1. The carrier is the raw request through `event.platform`, since adapter-node supplies it; if Kit's dev server does not populate `platform` in dev, the plugin's middleware still attaches the context to the raw request and the accessor reads it there (say which path dev takes).
2. One composition module for both entry points.
