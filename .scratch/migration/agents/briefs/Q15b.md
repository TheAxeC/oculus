## What to build

1. **`prewarmLogs(host, ids, days, runner)` in `src/lib/server/hpc/prewarm.ts`**, the port of `slurm_prewarm_logs`: for the finished job ids given (validated by `validId`, array steps included), one `sacct -X -u "$USER" -S <date> -o JobID,WorkDir%600 -Pn` (30 s) to learn each job's WorkDir through `safePath`, then one batched script over the distinct WorkDirs, each rung of `PREWARM_RUNGS` (`hpc/logs/*`, `logs/*`, `slurm-*.out`, `*.out`, `*/logs/*`) listed inside `timeout 15 sh -c` with the glob inside the timed child, sections marked `@@oculus:wd=<dir>@@` and `@@oculus:rung@@` (the cockpit's markers with the oculus name, as `actions.ts` names its markers), parsed back into a map of job id to path by the cockpit's `_pick_from_listing` rule (the newest listing entry whose name contains the job id, rung by rung). A miss is omitted; a failed ssh gives an empty map. Pure functions for the parse and the pick, exported for the tests.
2. **The loop in the watcher.** When `options.prewarm` is true, `watchHpc` runs the prewarm on the queue cadence after each good poll: the finished ids of `rows.recent` not yet in the log-path map are resolved in the background through the same `refresh` gate's rule (never beside a queue poll: it runs after the poll settles and before the next is scheduled, or as its own step that the gate serialises), the found paths written into the map with `setdefault` semantics (an on-demand path already there is never replaced), and the map cleared when it holds more than 500 entries; a failure is swallowed until the next cycle. The watcher takes the map: `HpcOptions.logPaths?: LogPaths`, handed in by `context.ts` (the same map the route's `log` uses). Running and pending jobs are never prewarmed, as the cockpit's docstring says: `scontrol` answers those and its answer is exact.
3. **Tests.** `tests/server/hpc/prewarm.test.ts`: the parse of a two-WorkDir listing, the pick by rung and newest-first, an id with no listing omitted, a failed sacct giving nothing, the batched script naming every WorkDir once and each rung inside `timeout 15 sh -c`; `poll.test.ts`: after a good poll with two finished jobs the runner is asked the sacct and the listing commands, the map gains both paths, an existing entry is kept, a third poll asks nothing for ids already held, the map is cleared past 500, `prewarm: false` asks nothing, a prewarm failure leaves the map and the cadence alone, and the prewarm never runs beside a queue poll (the gated runner). The route: `log` of a prewarmed id uses the held path on the first press (`actions.test.ts` already checks the held-path branch; add the case that the map's entry is what the remote script gets).
4. **DESIGN.md.** One sentence in the Live HPC paragraph: the finished jobs' log paths are resolved in the background after each poll so the first press on a log is as fast as the second.

## Decisions taken in this brief (each reversible)

1. The prewarm runs inside the watcher's serialised step rather than on its own timer, so it never opens a connection beside a queue poll; the cockpit runs it on its own thread with the poll's period.
2. The map stays the route's `LogPaths` in the server context: one map, two writers, on-demand answers never replaced.
