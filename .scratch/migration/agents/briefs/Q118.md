## Open items this brief rests on

Two choices of this brief are not the brief's to take; each is written below as an open item, and the brief is written for its recommendation. The orchestrator closes them before dispatch; a ruling other than the recommendation strikes or rewrites the items named in each.

- **O1, what Enter does on an Audit row.** The step line says "Enter acts on that row as on a card". On a card, Enter presses the card's title button, the record the card names, or else the control marked as the card's open-and-close toggle (`key-dom.ts:33-40`). An Audit row has neither (`grep -c -e 'class="title"' -e dataCardToggle -e data-card-toggle src/lib/views/system/audit/Audit.svelte` prints `0`), and it has no place link either: the place is a plain `<span class="where">` (`Audit.svelte:124-126`), so the only control on a row is the mute control. VS Code's list gives a row's Enter to the row's open action, never to an inline action: in the Problems view, the list of findings nearest the Audit, Enter (and a click) opens the problem's file. A finding carries no file today: `AuditFinding` is `{ scope, where, kind, message, signature }` (`src/lib/data/model/index.ts:258-264`), and `where` is a display word (`project.yml`, `status.chips`, `venue_id`, `results[2]`, an entry's title).
  - (a) Each finding carries `file`, the hub-relative path of the file it is about, or the empty text when there is none (a missing file, a folder); the place is drawn as a link that opens that file in a source tab; Enter presses the link. Pros: Enter does what VS Code's Problems list does and what a reader wants from a finding (open the file that needs the fix); the server already knows each file, so nothing is guessed from a display word; the signature does not read `file`, so every mute is kept. Cons: a wire field the `audit` channel carries to the page and to every app that reads it (`DESIGN.md:320`); 32 finding sites in `server/content/audit/` each pass a file; `data/model/index.ts` is also in D42's write list (D42 adds an export line, this step changes lines 258-264, so the merge is simple); the file opens at its top, with no line, since no rule knows a line; a press on the row's free space does nothing, where VS Code's row opens on any press (Q35 left the row with no selection).
  - (b) Enter presses the mute control, marked as the row's Enter control. Pros: no wire change, a few lines. Cons: a key press writes `config/behavior.yml`; VS Code's list never gives Enter to a row's inline action; HELP calls Enter the card's open or expand key; the muted row leaves the open list, and with the muted section closed the cursor is dropped with it.
  - (c) Enter does nothing on an Audit row, as on a card whose title is plain and which has no toggle; HELP says so. Pros: no new shape. Cons: the step line's "Enter acts on that row" gives the reader nothing.
  - Recommendation: (a), for the reasons in its pros; it is the one that makes Enter useful and follows VS Code. The lazy option is (c), and (b) costs little and is wrong for the reasons in its cons. Under (b), items 4 and 5 below are replaced by "the mute ToolButton of a row carries `dataCardToggle`"; under (c), items 4 and 5 are struck and item 7 says Enter does nothing on an Audit row.
- **O2, Enter on a Focus lane card.** Ruling Z446 names the Focus lanes as the model the Audit follows, and a lane card answers Enter with nothing for the same reason: `LaneCard.svelte` draws its name as `<ToolButton plain cut {label} onclick={onopen} />` (`:107-109`), with no `.title` and no `dataCardToggle` (`grep -rn "dataCardToggle\|data-card-toggle" src/lib` prints `ToolButton.svelte:107`, `:152` and `:197`, `key-dom.ts:36` and `CardActions.svelte:160` only).
  - (a) Fold it in here: the lane card's name ToolButton carries `dataCardToggle`, so Enter opens the project as a press on its name does. Pros: one prop in a file no step in flight writes; the subject is this step's (Enter on a cursor row that is not the Card primitive). Cons: widens the step by one file.
  - (b) A step of its own. Pros: none beyond a narrow Q118. Cons: a one-line step, which the standing demand against tiny steps refuses (`orchestrator-state.md`, "No tiny steps").
  - (c) Leave it. Cons: Enter on a lane card stays dead. The lazy option.
  - Recommendation: (a). Under (b) or (c), item 6 is struck and LaneCard leaves the write list.

### The cursor (shell and state)

- The cursor lives in the layout tree's instance state, a different record from the view's own: `cardCursor(state)` reads `cursor` (`src/lib/state/workbench/layout/instance.ts:63-66`), `withCardCursor` sets or removes only that key and keeps the others (`:68-75`), `reconcileCardCursor` clears it when its id is not in a list (`:77-81`). The shell reads it with `cardCursor(options.layout.instanceLayoutState(id))` (`src/lib/shell/keys/workbench-keys.svelte.ts:330-333`) and writes it with `options.layout.restateInstance(id, withCardCursor(state, cursor))` (`:335-351`); `instanceLayoutState` answers `held(id)?.state`, the layout tree's instance (`src/lib/state/workbench/layout/instances.ts:106-109`), and a layout change is saved (`layout.svelte.ts:569-575`, `apply` then `savePages`).
- So the Audit's `setInstanceState` at `:90` and `:94` neither keeps nor drops a held `cursor`: it writes the ui store's record, which never holds one. What changes the cursor when the search is typed or Show muted is pressed is the list the view then draws: the shell observes the pane that holds a cursor (`observePane`, `workbench-keys.svelte.ts:370-389`, a `MutationObserver` over `childList`, `subtree` and the `data-card` attribute) and `reconcilePane` (`:358-367`) clears the cursor when its id is not among the visible `[data-card]` elements (`cards`, `:277-283`, which keeps only elements whose `offsetParent` is not null).
- The arrow keys: `j`/ArrowLeft and `k`/ArrowRight resolve to `cursor` left and right, `i`/ArrowUp and `o`/ArrowDown to up and down (`src/lib/shell/keys/keys.ts:196-207`); `moveCursor` (`workbench-keys.svelte.ts:293-309`) finds the current card by the held id with `findIndex`, takes the next one by `horizontalCursor` or `rowCursor` (`keys.ts:63-87`; from no cursor both answer the first card, and past either end the current one), and `selectCard` (`:285-291`) writes the cursor and scrolls the card to the centre. With two cards of one id, `findIndex` always answers the first, so Down from the second lands on the second again: the cursor cannot pass a pair of equal ids.
- Enter: only with a held cursor (`keys.ts:208-210`, `if (event.key === 'Enter' && context.cursorActive)`) does Enter resolve to `activate`, and `activateCursor` (`src/lib/shell/keys/key-dom.ts:32-40`) clicks `.title button, [data-card-toggle]` inside the card of the shown view, answering false (the key left to the browser) when there is none. - The cursor is cleared when the reader presses or focuses into another pane (`rememberPane`, `workbench-keys.svelte.ts:407-416`, which writes null to `lastFocusedPane ?? pane`: before any pane was focused in this page load, that is the pane being entered), on Escape (`keys.ts:163-165`), and when a tab of the pane is shown by key (`showTab`, `:241-245`). ## Decisions taken in this brief (each reversible, none silent)

1. The cursor is drawn as an outline, 1px of `--accent` inset by 1px, with the row's controls revealed, and no fill: the same mark as a card under the cursor (`Card.svelte:148-151`) and a tree row holding the keyboard's focus (`TreeItem.svelte:262-267`), and VS Code's mark for a list's focused row. A fill (`--accent-bg`) is a tree's and VS Code's selection, and the Audit has no selection (Q35's item 4).
2. The style rule lives in `Audit.svelte`, beside the row's other rules, since the Audit row is drawn by hand (Q35) and no list-row primitive exists to hold it.
3. The card id of a repeated signature is `<signature>:<n>` from the second occurrence, numbered within the drawn list (repeats of one signature share scope, place, kind and message, so a search keeps all or none of them and the numbers do not move under it; they share a kind, so they sit in one section).
4. Enter's target is marked with ToolButton's existing `dataCardToggle` prop, which renders the attribute `activateCursor` already looks for, so the shell and `key-dom.ts` stay as they are and no new attribute is added. `ToolButton.svelte` is not changed: it is 539 lines, so a change there obliges a split of the shared primitive (spec.md's size rule), a different concern from this step. Its doc line "Marks the project-card control the keyboard cursor activates when its title is plain." then has two more users than it names; the report names the line, and the orchestrator books it with the next step that splits `ToolButton.svelte`. Rewording the line here with the split is the option this decision does not take.
5. The place, not the scope, is the link: it names where the finding is, as a Problems row's location does, and the scope (the project folder or the collection) stays the row's main words.
6. The tooltip is a new catalog key, `audit.open_place_tip`, "Open {0}", the file filling `{0}`, in the `audit` group where the view's words live.
