## What to build

1. **The `config-value` write** (`server/edit/writes/config/config-value.ts`, new, under 400 lines). The body `{ kind: 'config-value', file: string, key: string, value: unknown, base: unknown }`, parsed by a zod shape beside `configKeyShape` in `bodies.ts`, dispatched in `config-write.ts` after `config-key`, sent by a new `writeConfigValue(file, key, value, base)` in `state/client/writes.svelte.ts`. It writes one list option or one family (the catalog entry has `fields`, or `control: list`) of a tracked file, and refuses, writing nothing, with a sentence from `config/text/server.yml` under `server.config_value.*`:
   - `local.yml`, before anything is read; a file or key the catalog does not describe; an entry that is a single value (those go through `config-key`); `rail` and `arrangements`, which keep their own writes;
   - a file that does not parse, or a key the file does not hold as a block or flow collection (an alias, an anchor, a tag, a scalar or null);
   - `base` not deep-equal to the value the file holds at the key now, with the sentence that the setting changed in the file since it was read;
   - a value whose shape is not the entry's: a list option takes a list of strings; a family takes the collection kind the file holds at the key (a list stays a list, a map stays a map), each record a map whose keys are the catalog's `fields` (the `key` field of a map-keyed family is the map's key, never a record field) or a field the file already holds in a record of that family (item 3 keeps such a field, so the write accepts it back); `tab_rollup` is a map whose every value is a list of such records; each key/value entry a string key; a key or a field named `__proto__`, `constructor` or `prototype` anywhere in the value is refused;
   - an edited text whose read-back is not the original with exactly this key changed (the `kept` check as it stands, at the full dotted path);
   - a new `loadConfig` finding, or a reader of `READERS` or `FINDERS` refusing, exactly as `refusedBy` does. `READERS`, `FINDERS` and `refusedBy` move out of `config-key.ts` into one module both writes import, so the two writes share one list.
   A list option or family the file does not hold, or holds as null, is refused as not in the file; Settings draws such a row as `missing` with no editor (`rows.ts:185-195`, `Item.svelte:54`), so it is never created from Settings. An emptied list or family is written as `[]` or `{}` unless a reader refuses it. A string the YAML would read as another type or that holds a character YAML reserves (`: `, ` #`, a leading `#`, `- `, `[`, `{`, `*`, `&`, `!`, `yes`, `no`, `null`, `~`, `20`) is written quoted, and a key likewise (a space, a colon, a dot as in `read_limits` `status.line`, `1`, the empty string). New lines take the file's line ending. A value deep-equal to the file's writes nothing and answers with nothing changed. A write records `{ file, key: file, field: key, before, after, undo: 'field' }` under the body kind `config-value`, so History lists it and Undo takes it back: `undo.ts` reads the value now with a `configValueNow(engine, file, key)` and writes `before` with `after` as the base.
2. **The block rewrite** (in `server/edit/list-edit.ts` or a new `server/edit/block-edit.ts`, under 400 lines): the value at a dotted key path of any depth, replaced in place. Every byte outside the lines of the key (from the start of the key's line to the end of its value) stays as it was. The mechanism is `yaml`'s concrete syntax tree, since rendering a node with `stringify` changes 13 of the 28 shipped values (column padding in flow maps, flow collections over several lines, `{ }` and `[a, b]` padding mixed in one value; the brief check's probe, `yaml` 2.9.0): parse with `new Parser()` and `new Composer({ keepSourceTokens: true })`; every item the edit keeps reuses its source bytes verbatim (spliced by its token's range, its comments, quotes, padding, line breaks and blank line before included); a scalar the edit changes is set with `CST.setScalarValue` on its source token; only an added item is rendered, with `stringify`, in the style of its siblings (a flow map on one line where the siblings are flow maps, a block map otherwise), at the file's own indentation (read from the key's first item, as `setItems` does) and with no line folding. The brief check's probe round-tripped `present.yml` byte for byte this way and changed only line 75 for one `deck.framing` card title (scratchpad `probe4.mjs`). The result is read back as item 1 says before anything is written. Rendering is tested apart from item 1's equal-value rule, so C1 changes one scalar per value and never passes through that rule.
3. **The editors** (new partials in a new folder `views/system/workbench/editors/`, each under 300 lines, with their state as pure functions in `state/system/config/` and their tests in `tests/state/system/settings/`):
   - A list editor for a `control: list` row: one text field per item, Add (a new empty item at the end, focused), Remove per item, Move up and Move down per item (the rail editor's controls, `RailEditor.svelte`), and Save and Discard while the draft differs from the file. Items are strings.
   - A key/value table for a family whose fields are exactly `key` and `value`: one row per entry, a key field and a value field, the same Add, Remove, Move and Save. A value is shown as one line of YAML flow text (`8`, `Max 20x`, `[.sh, .bash]`) and read back with `yaml`'s `parse` on Save, so a number stays a number and a list stays a list; a string that reads back as itself is shown without quotes. A text that is not empty and not `null` or `~` but parses to null (a bare colour `#123456`, which YAML reads as a comment) is kept as the string typed.
   - A form per record family: one card per record with a field per catalog field, in the catalog's order, a field's value shown and read as the key/value table's values are; for a map-keyed family the card's first field is `key`; for `tab_rollup` each key is a card holding its list of `{ label, keys, color }` records, each with the same Add, Remove and Move. A field left empty is left out of the record. A record field the file holds that the catalog does not name is kept as it is and drawn read-only.
   - What every editor shares: the draft is the tab's instance state under the file and key (as `typed.ts` keeps typed text), so it survives a tab switch and a reload; a draft that does not read back (a duplicate key, an empty key, a value whose YAML does not parse) is named under the editor and Save waits for it; the draft's instance-state key carries the editor's own prefix so it never meets `typed.ts`'s key for the same file and key; Save sends one `config-value` with the whole value and the row's value as `base`; a refusal is drawn under the row as the single-value rows draw theirs (`write.ts`'s `answered`); while the write is out the editor shows the draft and a second Save waits, the watcher's push of the file ends it when the pushed value equals the value sent, and a push carrying another value ends the draft with the sentence that the file changed; an answer arriving after the tab closed writes nothing to state. ## Decisions taken in this brief (each reversible, none silent)

1. Editors hold a draft and write it with Save, as the rail editor does, rather than writing on each keystroke: a list or a record is only valid whole (a key typed half-way would collide), and one `config-value` write per Save keeps History one entry per change.
2. A family's values and record fields are shown and read as one line of YAML flow text. It keeps a number a number and a list a list (`usage_tiers`, `languages`, `floats.view`, `tab_rollup.keys`) with one rule for every field, where a per-field type picker would need a type the catalog does not record. Five real values under this rule: `read_limits` `status.line: 220` shows `220`, reads back the number 220; `usage_tiers` `default_claude_max_20x: Max 20x` shows `Max 20x`, reads back the string; `languages` `bash: [.sh, .bash, .zsh, .slurm]` shows `[.sh, .bash, .zsh, .slurm]`, reads back the list; `deck.tag_tones` `measured: green` shows `green`; `floats[0].view: [hpc, usage]` shows `[hpc, usage]`. A string that would read back as another type (`"true"`, `"20"`) is shown quoted.
3. The merged rail item is labelled `System` with the chord `y`, keeping the arrangement key `views` so a saved page stays tied to it. Settings comes first (`y1`), then account setup, the two navigators (Catalogue and Pages share the upper right pane, Z171), and the five status views in the lower right pane in their old order. "System" names what the page now holds (oculus's own setup and state); the alternative, "Views and Settings", no longer covers Status to Gallery.
4. Reorder is by Move up and Move down buttons, as the rail editor's, with no drag.
5. A saved `info` page is folded into the `views` page rather than kept as a page of its own, since the rail no longer has its button; a `config` tab becomes a `settings` tab.
6. The merged group keeps the `settings` glyph and the rail button its `sliders` glyph, so neither icon a reader knows changes.
7. A flow text that parses to null without being empty, `null` or `~` is kept as typed, so a bare colour is never lost to YAML's comment rule.
8. A record field the catalog does not name is accepted by the write only when the file already holds it in that family, so an editor that keeps it can save, and nothing new outside the catalog gets in.
9. Departure from VS Code's list and object setting widgets (per-item Edit with OK and Cancel): one draft per row with Save, since a family is valid only whole (a key half typed collides) and one Save keeps History one entry per change; the per-item editing VS Code offers is kept (each item its own field, Add, Remove).
