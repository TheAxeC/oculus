## What to build

When the part is done, a reader with a `.slurm` job script open in the source tab presses Submit in the open file's editor title bar, reads one confirm that names where the code is copied from and to, how many files, and the exact command run on the cluster, with a warning first when the script never names `/local/$SLURM_JOB_ID`; on a yes, oculus copies the project's code to the cluster with rsync, runs `sbatch` there through ssh, says the job id under the editor, and the job is in the Live HPC view. Nothing else runs on the login node: the only remote processes are rsync's own receiving end and one `cd <folder> && sbatch --parsable <script>`.

### 1. The server: the plan, the check and the run

Three new modules in `src/lib/server/machine/hpc/` (the folder goes from 7 to 10 items), each opening with the layer head comment:

- `transfer.ts`: the rsync child (section 3).

**`planSubmit(input, deps)`**, from `{ root, path }` (a served root's key and a path under it, as every file route takes them), computes the plan or one refusal, in this order, and runs nothing remote:

1. The file: `resolveRootPath` over the roots `browserRoots` gives this request; a refusal there is the refusal (G2). Its extension, lowercased, must be `.slurm` (`not-slurm`). It must be a file.
2. The project: the deepest project of the latest portfolio snapshot (`locals.server.hub.latest('portfolio')`, `entities.projects`, ghosts left out) whose folder, `projectDirectory(hub, project.folder)` by real path, holds the file, by whole path segments (the `projectOf` rule, moved to a shared module, decision 13). None: `no-project`. No snapshot yet: `no-project` as well.
3. The code folder: `<project folder>/code`. A file not under it: `outside-code`.
4. The cluster folder: the project's `cluster` (section 4), else `~/projects/<id>`. A value outside the rule of section 4: `bad-cluster`.
5. The host: `hpcRouteHost` as the cancel and the log take it. An empty host: `no-host` with the resolver's sentence. A throw of `slurmSettings` (a `slurm.resource` that is not a non-empty string): `no-host` with the catalog's sentence that `behavior.yml` names no usable `slurm.resource`; the route never answers 500 for it.
6. The files: the new read `keptFiles(code)` in `server/core/git/files.ts`, `git -C <code> ls-files -z --cached --others --exclude-standard` through `run.ts`'s call site, its 5 s timeout and list arguments (a new exact vector, written into `run.ts`'s head comment list and `DESIGN.md:128`). From its answer drop every path with a `__pycache__` segment, every path ending `.npy`, every path whose first segment is `results` or `logs`, and every path `lstat` does not find (a tracked file deleted on disk, which would make rsync copy nothing). 8. The commands, as section 3 builds them.

The plan, the wire shape this step adds (decision 5):

```ts
/** What Submit will do, computed by the server and confirmed by the reader. */
export type SubmitPlan = {
    root: string; // as asked
    path: string; // as asked
    project: string; // the project's id
    host: string; // the ssh alias
    source: string; // the absolute local code folder, ending in '/'
    target: string; // '<host>:<cluster folder>/'
    files: number; // how many files the copy sends
    digest: string; // sha256 of the sorted paths joined by NUL, hex
    rsync: string[]; // the rsync argument vector as run, without the program name
    remote: string; // the one remote command, `cd <folder> && sbatch --parsable <script>`
    scratch: { named: boolean; unread: string[] }; // section 2
};
```

**`runSubmit(plan, deps)`**, for `{ action: 'submit', plan, confirm: true }`:

1. `confirm` must be the boolean `true` (as G6's git actions take it); else `unconfirmed`, and nothing runs.
2. The plan is computed again from `plan.root` and `plan.path`. A refusal is the refusal. A plan that is not deep-equal to the one the page sent (`isDeepStrictEqual` of `node:util`, or the `same` of `server/core/changes.ts` when it compares the same way; grep first): `changed`, and nothing runs.
3. The key `<host>:<cluster folder>` already in flight: `busy`, and nothing runs. Otherwise it is held until the run ends, whatever the end (a `finally`).
4. rsync runs (section 3). A non-zero exit or a spawn error: `copy-failed` with the last non-empty line rsync or ssh wrote to stderr; `sbatch` does not run.
5. `sbatch` runs through `ssh.ts`'s `run(host, plan.remote, SUBMIT_TIMEOUT_MS)`, 30 s (one command that either queues the job or does not, as scancel's 20 s). A non-zero exit or a timeout: `submit-failed` with the last stderr line, or the word for the timeout.
6. The job id: the first line of stdout up to a `;` (`--parsable` prints `<id>` or `<id>;<cluster>`), held to `validId`. None: `no-job-id` with the first stdout line.
7. `deps.refresh()` (the poller's `refresh`), so the queue on the `hpc` channel holds the job; then the answer `{ status: 'ok', job }`.
8. One line on the server's console for each run, as the poller logs its publishes: `hpc submit: <project> <path> job <id>` or `hpc submit: <project> <path> <refusal word>`.

### 2. The scratch rule (`scratch.ts`)

What is said: whether the script, or a file it sources that the rule can find, names `/local/$SLURM_JOB_ID` outside a comment.

- The text of each file is `await print(text, { minify: true })` of `sh-syntax` 0.7.0 (Z431, through its printer: premise 4). A file that does not print (a parse error) is listed in `unread` by its path relative to the code folder, and counts as naming nothing.
- A file names it when a line of the printed text holds `/local/` followed at once by `$SLURM_JOB_ID` not followed by a name character, or by `${SLURM_JOB_ID}`, or by `${SLURM_JOB_ID` with an operator and a word (`${SLURM_JOB_ID:-$$}`, `${SLURM_JOB_ID-x}`). One regular expression, written once:

  ```ts
  const SCRATCH = /\/local\/(\$SLURM_JOB_ID(?![A-Za-z0-9_])|\$\{SLURM_JOB_ID(\}|:?[-=+?][^}]*\}))/;
  ```

  A here-document body counts (decision 3); a comment never does, since the printer has dropped it.
- A source is a printed line whose first word is `source` or `.`; its argument, one word, with the double quotes around a whole word taken off, is resolved by these rules and no others: `${SLURM_SUBMIT_DIR}`, `${SLURM_SUBMIT_DIR:-<anything>}` and `$SLURM_SUBMIT_DIR` stand for the code folder (sbatch is run from the cluster folder that mirrors it); `$(dirname "$0")` and `$(dirname $0)` for the folder of the file being read; a leading `~/`, `$HOME/` or `${HOME}/` followed by the cluster folder's own path and `/` for the code folder; a relative path is taken from the code folder. A word left holding `$`, a backquote or a quote, a path outside the code folder, or no file there is not followed and is listed in `unread` as written (`/etc/profile.d/modules.sh`, `activate`, `"$PROJECT_DIR/radiologist_code/hpc/radiologist_env.sh"`).
- A file already read is not read again (a cycle ends); at most 20 files are read per plan, and a source past the twentieth is listed in `unread`.
- `named` is true when any file read names it. `unread` is said with the warning only.

### 3. The commands (`transfer.ts` and `submit.ts`)
