# Brief: O19, resuming a session into tmux

Read `../spec.md` first; it governs this package unchanged. Then `tools/oculus/DESIGN.md`, "PTY" under Layer 2 ("A session started elsewhere is observed (transcript only) until Axel explicitly resumes it into tmux with `claude --resume <id>`; nothing migrates on its own. The server sends no signal to any registry pid other than the liveness probe"), step 6 of the migration order, and the decisions on tmux and on the two agents. O17 starts terminals and O18 draws them; this package is the one explicit act that turns an observed session into a terminal oculus holds: a click on a session, a confirm, and `claude --resume <id>` or `codex resume <id>` in a new tmux session in the session's own cwd.

## What to build

Under `tools/oculus/src/lib/server/pty/`:

- `sessions.ts`, extended: `startTerminal` takes `{ kind, cwd, cols, rows, name?, resume?: { tool: 'claude' | 'codex'; id: string } }`; with `resume` the command is `claude --resume <id>` or `codex resume <id>` (the kind is the tool), the id checked against the UUID shape both tools use (anything else refused), the cwd the record's own `cwd` (it must exist; a session whose cwd is gone is refused with a reason the page shows). The tmux session name keeps O17's shape `oculus-<6 hex>-<kind>` (`isTerminalId` guards every stop, resize and channel on it, so the name may not carry more); which session the terminal continues is a tmux user option `@oculus_resumes` set right after `new-session`, the way `@oculus_name` is, and read as an eighth field of `LIST_FORMAT` into `Terminal.resumes: { tool, id } | null` (`resumes` is `null` on a terminal that continues nothing; `tests/sessions-fixture.ts` and every fixture that builds a `Terminal` gain the field). The `name` of a resumed terminal is the session's title when the record has one, else the id.
- `routes.ts`, extended: `{ action: 'resume', tool, id, cols, rows }` on `POST /api/terminal`, token-guarded and same-origin as every write. The record the resume needs (its `cwd`, its `title`, whether it is live) is read from the last published `sessions` payload through `bridgedRecord(id)` of `server/sessions/hooks.ts` (O16's bridge, the same wall this route sits behind); a session the payload does not hold is refused with `sessions.resume_unknown` (the page only offers sessions the payload holds, so this is a race, not a path). The server never signals the original process: DESIGN.md says so, and a live session (the record's `live` is true) is refused with `sessions.resume_live` until it has ended, since two processes on one transcript is what the rule exists to prevent; an ended session resumes.

Under `tools/oculus/src/lib/views/sessions/`:

- `SessionDetail.svelte`, extended: a "Resume in a terminal" control (`sessions.resume`) for an ended session of either tool, behind a confirm (`sessions.resume_confirm`, naming the cwd it starts in); on success the new terminal is selected and, if no terminal view is open, `terminal` opens in the main tree (`openView`). A live session shows why it cannot be resumed (`sessions.resume_live`) instead of the control.
- `SessionList.svelte`, extended: the row's context (the pane menu pattern of O10b, a `Menu` on the row) offers the same resume for an ended session.

Under `tools/oculus/tests/`:

- `server/pty/sessions.test.ts`, extended: the resume arguments for each tool as pure functions (`resumeArgs` or the like, the argv asserted: `claude --resume <id>`, `codex resume <id>`, `-c <cwd>`), a malformed id refused, the `@oculus_resumes` option parsed back from a list line; nothing here runs `claude` or `codex` (the private-socket tmux test runs `cat`, and stays so).
- `routes/terminal.test.ts`, new (there is none yet; `tests/routes/hook.test.ts` is the pattern, a handler called with a Request and a target the test owns): the `resume` action with a stub `run` recording the argv and a stub record source (`handleTerminal` gains an options bag carrying `run` and `recordFor`, defaulted to the real ones by the route): a malformed id 400, a live record 400 with the `sessions.resume_live` reason, a record the source does not hold 400, a missing cwd 400, a good one 200 with the terminal.
- `views/sessions.test.ts`, extended: the control on an ended session, the refusal line on a live one, the row menu offering the resume.

## Facts checked on the tree, 2026-09-10

- `claude --help`: `--resume <session-id>` continues that session; `-c, --continue` the most recent; `-p, --print` is the non-interactive mode; `--model <model>`. `codex resume --help`: `codex resume [OPTIONS] [SESSION_ID] [PROMPT]`, a UUID or a session name, `--last` for the most recent, `--all`, `--include-non-interactive`. A Codex session id is the rollout's UUID (`session_meta.id`), and `codex resume <that>` is how the CLI itself reopens it.
- A resumed Claude session writes to the same transcript file, so O13's watcher sees it continue; O12's registry then holds a new pid for it and the record turns live on the next rescan.
- Codex has no registry; a resumed Codex session is live by O12's process-plus-fresh-file rule as soon as it writes.
