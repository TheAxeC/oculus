## What to build

1. **The keys.** A side project's manifest accepts `deadline`, `subtasks`, `followup`, `snooze`, `priority`, `pin`, `short`, `latest`, `collaborators`, `waiting-on` and `related`, besides its five keys, each with the research manifest's name and shape.
   - `normalise-personal.ts` reads them with the functions `project()` uses: `str` and `strings` from `data/helpers/guards.ts`, `pin === true`, and `followups` and `subtasks`, which move out of `normalise.ts` into a new file `src/lib/data/snapshot/normalise-plans.ts` that both readers import (an import of `normalise.ts` from `normalise-personal.ts` would make a cycle).
   - `SideProject` gains `short`, `pin`, `priority`, `latest`, `deadline`, `waitingOn`, `followups`, `snooze`, `subtasks`, `relatedIds` and `collaborators`, named and typed as on `Project`, written as a `Pick` of `Project`'s fields rather than repeated, so `model-entities.ts` stays under 880 lines with D41's change beside it. A field the manifest does not hold is left out of the record, as `compact` leaves it out of a research project, so a side project with only its five keys reads to the record it reads to today.
   - A value of the wrong type for one of them costs that field alone, with one `field_type` finding, as the five keys do; a key outside the sixteen is still a `key` finding. The two finding sentences (`findings.yml:43,45`) are made true for every field: the type sentence names the type the field takes, and the key sentence says the key is not a field of the side-project schema rather than listing five.
   - `side_project_schema` gains a row per key with the type word, the `from:` and the help text of its `manifest_schema` row (the `followup` group as its two dotted rows, `followup.do` and `followup.after`). `schema/static.ts` builds the side kind's JSON Schema through the translation `manifestSchema()` uses (`WIDGET_TYPES`, dotted names nested), so the YAML editor completes, explains and checks the sixteen keys the same way in both manifest kinds, and a research-shaped value of each validates clean in both.
   - The write side reads the side kind's field types through the same function as the research kind's (`fieldTypes` made to read the list form too), so a side write refuses what a research write refuses (`subtasks` as a form field among it).
   - The new `from:` rows make a side manifest's `collaborators`, `waiting-on` and `related` values references of the index (G66): Find References on a person key lists a side manifest that names them, and a rename changes it.

2. **Focus.** A side project whose status is live (decision 2: the row of `side_project_status` carries no `live: false`; the `parked` row gains `live: false`) is read by the ticker beside the research projects, with the research rules unchanged for it:
   - its `deadline` gives a line in a new deadline group `side` (`CATEGORIES` between `task` and `conference`, `GLYPHS.side = 'spark'`, the Personal view's glyph), within `deadline_horizon_days` as a paper's is, overdue lines joining the overdue group as a paper's do; `categoryLabel` answers `dlcat_side` for it ("side projects"), never the conference heading;
   - its `followup` notes join the follow-ups and the tasks as a research project's do (a dated due note in the follow-ups, a note with no `after` in the tasks, a future one nowhere);
   - its open `subtasks` join the subtasks and the tasks under the heading `dlcat_side`, the catalog word, never a raw word (decision 7);
   - `snooze` keeps its lines in `snoozed` as a project's does;
   - a line's label is what `focusLabel` makes, which takes a side project as it takes a research project;
   - a press on a line's name opens the side project's manifest in a source tab, as the Personal card's title does, through `openLine` for a side target, never `onproject`;
   - its `waiting-on` values count in the Focus waiting tally beside the research projects'.
   A side project that is not live draws no line and counts nothing in the tally.

3. **The buttons on a side project's lines.** Snooze, wake, tick, reopen, delete and clear write the side project's manifest as they write a research project's: `writeManifest`, `manifestValue`, `writeSubtask`, `restoreSubtask` and `writeSubtaskAdd` take a side project's id (`side:<slug>`, `root:<key>`), and the server finds its file through the side projects of the portfolio it last published, a `sideProjects: () => SideProject[]` on `WriteTarget` beside `projects`, each carrying the absolute `file` `readPersonal` found; never through `readManifests`. It writes only that file (a `project.yml` under the hub's side-projects tier, or `.oculus/project.yml` at a served root), with the field names of `side_project_schema`. A field outside it is refused as a research write refuses one outside `manifest_schema`; an id the published portfolio does not hold (a side project removed, a root no longer served) is refused as not found and nothing is written. Each write is logged and its undo puts the file back as a research write's does (G9), `undo.ts` reaching the side file the same way; the change log keeps the absolute path for a root's file, so History shows it in full. Every caller of the changed signatures follows (`undo.ts`, `deposit.ts`, the routes that build a `WriteTarget`). The request and its answer keep their shape (decision 3). The side lookup lives in `writes/manifest.ts` (486 lines), since `server/edit`, `writes` and `writes/config` hold 10 items each.

4. **The Personal card.** A pinned card (`pin: true`) is drawn first within its status, with the pin glyph the project card's menu names (`project.card.pin_glyph`); `priority` draws the flames the Focus lane card draws for it (`views/boards/focus/lanes/LaneCard.svelte`, `flames`); `latest` is drawn under the explanation; `waiting-on` draws as the project card's waiting line (`ProjectCard.svelte:113`, `:358`, `waitingLine`); `collaborators` draws as the project card's collaborator links (`CardLinks.svelte`, the collaborator kind, a press opening the person); `related` draws as a line headed by the new catalog word `personal.related` ("related"), each id a project tag that opens its project tab, the tag `CardLinks.svelte:97` opens (decision 8), since the project card has no related line to reuse. The card reuses those components and helpers where their props take what a side project holds, and otherwise draws with the same classes and words. The card's words stay edited in its manifest, as today (`Personal.svelte:89`).

5. **The ticker rows.** In `Ticker.svelte` a row is at `--fs-xs`, the name at weight 400, on an 18 px row (`calc(18px * var(--text-scale, 1))`) and a 14 px line (`calc(14px * var(--text-scale, 1))`); `.plain` and `.tail.toned` drop to 400 with the name. A row's button keeps its words, its border and its 6 px sides and is exactly the row's height at every text scale from 0.7 to 1.6 (its height the row's `calc`, border-box, its words centred on their 14 px line), so a shown button never changes a row's height (decision 4). No heading of Focus, of a band or of a group changes (`focus.yml`'s group headings, the band titles and their CSS). The head comment of `.act` and of the row is made true.

6. **The text.** The heading `focus.command.dlcat_side` ("side projects") in `focus.yml`, and `personal.related` ("related") in `personal.yml`. Every sentence listed under "What is on the tree" as naming the five keys or a side project read by the Personal board alone is made true: `manifests.ts:25` and `:356-360`, `normalise-personal.ts`'s head comment, `hub-names.ts:82`, `config/sources.yml:15`, `docs/configuration.md:41`, `DESIGN.md:552`, `docs/views.md:23` and the Focus section (5-7), `HELP.md:105` (the Personal row), `docs/apps.md:248` (the `personal` map's fields, decision 9), `findings.yml:43,45`, and the head comment of `side-project-schema.yml`. The builder also runs `grep -rn -i "side project\|side-project\|SideProject" src config docs DESIGN.md HELP.md README.md --exclude=local.yml` after the change and makes each hit true.

7. **Sizes.** A source file at or under 880 lines, a component at or under 520; `ticker.ts` (638) takes the side lines in a new file in `state/boards/board/` (8 items); `normalise-plans.ts` makes `data/snapshot` 10. No folder passes 10 items.

## Decisions taken in this brief (each reversible, none silent)

1. 3. A side project's write goes through the existing `writeManifest` and `writeSubtask` requests, its id telling the server to look it up through `readPersonal` (Z746): the request and answer keep their shape, and the server's two readers stay apart, as `readPersonal`'s comment requires. A new write kind for side manifests is a second request with the same fields.
4. A row's button is the row's height at every text scale (Z746, Z748), so the row stays 18 px when its buttons show and the board does not move; a 22 px button on an 18 px row would make every row with a shown button 22 px, which the plan line's 18 px row rules out, and a fixed `padding: 1px 6px` would still be taller than the row below a text scale of 1.

7. A side project's subtasks and undated follow-ups sit under the heading "side projects" (`dlcat_side`) in the Tasks band (Z748), the same word as its deadline group, so a side task is never under a research kind's heading or a raw word.
