## What to build

Axel's ruling (2026-09-23, option (a)): an Add account control in the Calendar and Inbox views; pick Google or Microsoft and type a label, and oculus writes the `local.yml` row and the credential file itself and starts Connect at once; the provider app is set up once per provider, not per account, on a setup page that walks through the console step by step with a link to each console page, the exact redirect addresses to paste and one field for the client id (and the Google secret); that one app then serves every account of that provider and both the Calendar and the Inbox, each consent still separate. Each item below is an acceptance item.

1. **The provider's client half, once per provider.** One file per provider, `~/.oculus/connect/google.json` (`client_id`, `client_secret`) and `~/.oculus/connect/microsoft.json` (`client_id`, optional `tenant`), 0600 in a 0700 folder, written atomically behind the write chain. `readCredentials` reads the client half from the account's own file when it holds one (every file that works today keeps working, unchanged) and otherwise from the provider file; the account file then holds only the account's `refresh_token`. One provider app so serves every account of that provider in both connectors, each account still its own consent and its own token.
2. **The setup page.** A view (listed in the `personal` group, opened from the Add account flow when the provider has no client half yet, and from a Set up provider entry in both views' `...` menu) with one section per provider, each numbered step with the link to the exact console page and what to press there, the values to enter shown with a copy button, and at the end the field for the client id (and the Google secret, and the optional Microsoft tenant), saved with a Save press that checks the shape (a Google client id ends in `.apps.googleusercontent.com`; a Microsoft client id is a GUID) and says what is wrong in words. The steps, at least:
   - Google: open console.cloud.google.com, create or pick a project; enable the Google Calendar API and the Gmail API (a link to each API's library page); configure the OAuth consent screen (External, the app name, the reader's address; in Testing, each Google account that will connect added as a test user, said plainly); Credentials, Create credentials, OAuth client ID, application type Desktop app; copy the client id and the client secret into the fields. A Desktop client takes any loopback port, so no redirect address is registered, and the page says so.
   - Microsoft: open entra.microsoft.com, App registrations, New registration; supported account types "Accounts in any organizational directory and personal Microsoft accounts"; the redirect under the platform "Public client/native (mobile and desktop)" with both addresses, `http://127.0.0.1:<port>/api/calendar/callback` and `http://127.0.0.1:<port>/api/mail/callback`, the port read from the running server's `local.port`, never written as a literal; under Authentication, Allow public client flows set to Yes; under API permissions, the delegated Microsoft Graph permissions `Calendars.Read`, `Mail.ReadWrite`, `Mail.Send` and `offline_access`; copy the Application (client) ID into the field, and the Directory (tenant) ID only when the organisation requires its own tenant.
   - A sentence that a university tenant may require an administrator to approve the app, and that the consent screen then says so.
   The scopes and addresses on the page are read from `oauth.ts`'s constants, so the page and the code cannot disagree; a test holds that.
3. **Add account in both views.** The Calendar and Inbox views carry Add account in their head (and in the empty state that replaces `no_accounts`): pick Google or Microsoft, type a label (checked by the same label rule and uniqueness `local.ts` applies, the refusal in words before anything is written); on confirm, oculus adds the row to `local.yml`'s `calendars:` or `mail:` list through a comment-preserving YAML edit (`parseDocument`), atomically and behind the write chain, creating the list when absent, checked with `checkLocal` before the write; writes the account's credential file (holding nothing yet when the provider file carries the client half); and starts Connect at once, the consent page opening as today. When the provider has no client half yet, the setup page opens first and the account is added after its Save.
4. **Accounts read live.** A row added, or removed, reaches the routes and the pollers without a restart: the server re-reads `local.yml`'s `calendars`, `mail`, `calendar_dir` and `mail_dir` after its own write and when the file changes on disk (the config watcher), and the pollers start and stop accounts to match. HELP.md's "holds from the next start" for these keys becomes wrong and its replacement is in the Doc text.
5. **Remove account.** Each account row's menu carries Remove, behind a confirm naming the account, which drops the row from `local.yml` (comment-preserving) and deletes the account's credential file; the provider file stays.
6. **One account list component.** The two near-copy `Accounts.svelte` become one shared component under `src/lib/views/shared/`, parameterised by the connector, drawing each row, Connect, the new menu and the hint; the hint for a missing client half points to the setup page instead of a file path.
7. **The token file written safely.** `writeRefreshToken` writes atomically (`writeJsonAtomic` or the text writer with mode 0600); a `refresh_token` the provider returns on refresh is saved, so a rotated Microsoft token is kept.
