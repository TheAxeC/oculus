## What to build

1. **New Terminal starts a shell at once.** Every control labelled New Terminal (the Terminal view's bar button, the pane strip's menu item, the list's empty-area menu item) posts `start` with kind `shell` and the tab's folder, and the new terminal joins the tab and is shown; no composer. The tab's folder is the folder of the terminal the tab shows, else of its first terminal, else the hub root; a start while the hub root is not yet known waits for the portfolio rather than posting an empty folder. The pane strip's item starts it in a Terminal tab of the pane it was picked on (that pane's active Terminal tab, else a new Terminal tab opened in that pane), never another pane's: `StripDeps` gains a pane-scoped start (for example `newTerminalIn(page, path)`) wired in `src/lib/shell/Workbench.svelte` beside `composeIn`, and the terminals store opens the new Terminal tab in that pane through the layout (the layout has no open-in-pane function today, `context.ts:190`, so one is added to the layout store). The `n` key and the Sessions view's New are the agent-session start ("Start a new session (n)", the key sheet's "start a new agent session") and keep showing the composer in the page's Terminal tab, with its folder now the tab's folder by decision 1. Two quick presses start two terminals. A press while the hub root is `''` is held and posted once the root is known; several presses in that window post one start each, never an empty folder. A start the server refuses (a deleted folder, tmux down) shows a said refusal on the bar and leaves the tab as it was.
2. **The kinds dropdown beside New.** A dropdown button beside the bar's New lists Shell, Claude, Codex, a rule, and "With a Prompt..." (the composer). Shell, Claude and Codex start that kind at once in the tab's folder; "With a Prompt..." shows the composer as today, its kind the shown terminal's kind. The empty-area menu's New Terminal With Profile starts the chosen kind at once the same way.
3. **Split starts at once.** Split (the row's button, the row menu, Shift+Enter on a row, the grid menu, and a new Split button on the bar, the last acting on the shown terminal) posts `start` with the split terminal's kind and folder and puts the new terminal right of the split one in the tab's row; no composer. The kind and folder come from the store's record of the terminal, which keeps what each `start` answered until the payload lists it, so a terminal started a moment ago can be split; a terminal the store knows nothing of shows a said refusal on the bar, never a silent return.
4. **A row of any number.** A Split on a terminal that is not the shown one puts the new terminal right of the split one. `TerminalTabState` holds the terminals drawn side by side as an ordered list with a share per terminal (for example `row: string[]`, `shares: number[]`, `shown` the focused one), in place of `beside` and `share`; `readTab` reads the old `{ shown, beside, share }` shape and every older one it reads today. There is no count; each terminal keeps at least 80 px through the sashes' bounds, and a row wider than the pane scrolls sideways. The widths come from one pure function in `terminal-tabs.ts` given the shares and the pane width (every width at least 80, a row wider than the pane at 80 each), which the sashes and the tests both use. Killing the middle of four keeps the others' order and renormalises the shares to sum to 1; Unsplit on a row of one does nothing. Every function listed in "What is on the tree" that assumes two halves takes the row: Unsplit takes a terminal out of the row, Join adds one to it, Kill and an ending terminal close its place, and a row of one is an unsplit tab. The left grid is not torn down when a second joins the row (the `{#if}` branches of `Terminal.svelte:302-326` become one keyed `{#each}`).
5. **Rename.** A Rename item on the list row's menu and the grid's menu, and a double-click on the row's name, open an inline field on the row (or, with the list hidden, on the bar's title) holding the current title; Enter saves, Escape cancels, an empty value clears the title. The server's new `rename` action sets the tmux user option `@oculus_title` (checked by `label()`'s rules, at most `NAME_MAX`), then calls `refresh()`; `LIST_FORMAT` and `parseTerminal` read it as `title`, and the row, the tab label, the title and the Sessions list's row (`TerminalRows.svelte:57`) show it when set, and today's text otherwise. The value is trimmed; a value of only spaces clears the title; a tab or any other control character is refused (`LIST_FORMAT` is tab-separated); 80 characters are accepted and 81 refused; a trailing `;` is stored as typed (the argument vector passes it as one argument, shown by a route-double test). `rename`, `restyle` and `clear` on an id the server does not list, or on an ended terminal, answer a said refusal and run no tmux command.
6. **Change Icon and Change Color.** Items on the same two menus. Change Icon opens `GlyphList` over `glyphs.yml`, with "Default" first; Change Color offers VS Code's eight ANSI colours (black, red, green, yellow, blue, magenta, cyan, white) through `grid-look.ts`'s token map, with "Default" first. Each is a tmux user option (`@oculus_icon`, `@oculus_color`) set by one `restyle` action (the value checked against the vocabulary or the eight names, an empty value clearing it) and read into the `Terminal` record; the row and the tab draw the icon and the colour. "Default" sends the empty value and unsets the option; a stored glyph no longer in `glyphs.yml` draws as the default.
7. **Clear.** An item on the grid menu and the row menu: xterm's `clear()` on the grid, and a server action `clear` running `tmux clear-history -t oculus-<id>` so a reattach does not paint the history back.
8. **Copy as HTML.** An item on the grid menu while the grid holds a selection: `@xterm/addon-serialize` 0.14.0 loaded on the grid, `serializeAsHTML({ onlySelection: true })` written to the clipboard as `text/html` with the selection's plain text as `text/plain`, through a helper handed the serializer and the clipboard so a test can give it fakes. A clipboard that refuses (`ClipboardItem` missing or `write` rejected) shows a said failure on the bar.
9. **Closing ends what the tab owns.** Closing a Terminal tab, the pane holding it, or its page (and a page reset that removes it) ends the terminals the tab's state lists that are still running; moving a tab to another pane or page, splitting it, and reloading the page end none. The ui store (`src/lib/state/workbench/ui.svelte.ts`) gains one registration in the shape of `registerUnsaved` (182), and the terminals store registers with it: which running terminals a set of instances owns, a fresh busy read of them, and ending them. The user-facing removals (`closeInstance`, `closePane`, `closePage`, `resetPage`, `resetPages`) call the ending with the instances they removed. `closeInstanceAnywhere` does not: its callers are a view being unregistered (`registry.ts:189`) and `closeRecord` (`Sections.svelte:99`), neither of which a reader presses to end a terminal. A start answered after its tab closed is ended, since its tab is gone. A terminal that ends by itself during a close's busy read is not stopped twice (the stop skips a terminal the payload lists as ended, and a stop of an unknown id is ignored). `moveTerminal` writes the old tab's state without the moved terminal before closing that tab, so moving a tab's last terminal away ends nothing; `closeEnded` closes a tab whose terminals have already ended.
10. **Asking first.** A close that would end a terminal whose foreground program is not its shell asks first, through the same close question the unsaved tabs use, naming each such terminal and its program; an idle shell closes without asking. The server answers a fresh read (a new GET, `?busy=<ids>`, running `display-message -p -t oculus-<id> '#{pane_current_command}'` per terminal and comparing with the terminal's shell); a Claude or Codex terminal is busy while its agent runs; a read that fails asks. Cancel leaves the tab, pane or page as it was, terminals included. How the async read fits the synchronous `closeQuestion`: each close handler (`closeTab` and the pane's close in `PaneView.svelte`, `close` in `Pages.svelte`) becomes async, awaits the busy read for the instances it would remove, and then chooses among act, the unsaved question and the busy question; a pane or page with unsaved text and a busy terminal asks one question naming both (the unsaved text first). A second press of the same close while its read is in flight does nothing (one read, one question). `resetAfterAsking` asks the busy question once, naming each busy terminal of the touched pages, after its first question and before `act`; its three callers pass the registration's read through, so `ActivityRail.svelte`, `PagesReset.svelte` and `Pages.svelte` change their call. The comparison with the shell: `pane_current_command` is a basename (`zsh`) and `commandFor('shell')` answers `$SHELL` as a path (`sessions.ts:152-153`), so the server compares basenames and an idle shell is idle. A task, recover or LaTeX terminal is kind `shell` running its program, so it is busy while that runs. `?busy=` takes at most the ids of one page's terminals, each checked by `isTerminalId`; a malformed id or a list longer than 64 is refused before any tmux command (the GET carries no token). The busy question's words live in `config/text/ui.yml` beside the other close questions.
11. **Docs and words.** `DESIGN.md` and `HELP.md`'s Terminal text say what New, the dropdown, Split, Rename, Change Icon, Change Color, Clear, Copy as HTML and closing do now, and that a closed tab ends its terminals (the Z40 (d) text replaced wherever `grep -rn "stops nothing\|keep running\|keeps running\|leaves its terminals running" src DESIGN.md HELP.md` finds it, `HELP.md:127` among them, and `DESIGN.md:273` and `HELP.md:79` rewritten); the key sheet's `n` row (`config/text/app.yml:12`) says the composer opens in the tab's folder; new words in `config/text/views/sessions/terminal.yml` and, for the close question, `config/text/ui.yml`.
