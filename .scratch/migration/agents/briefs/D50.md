## What to build

Items 1 and 8 depend on open items 25 and 26; they are written for the recommended options and are changed before dispatch if Axel rules otherwise.

1. **The hub's folder and its five files.** `<hub>/.oculus/` is the hub's own folder. When `config/local.yml` does not set the key, `bookmarks.yml`, `notes/`, `schedules.yml` and `workspaces.json` are read and written at `<hub>/.oculus/<name>`, and the machine's apps folder is `<hub>/.oculus/apps` (decision 3, open item 25 ruled (a)). One function per file gives its default from the hub, taking the hub as its argument, and every caller listed under "What is on the tree" resolves the path through it, the five outside the defining files included (`routes/api/(files)/fs/+server.ts`, `routes/api/(machine)/schedules/+server.ts`, `server/edit/writes/config/roots.ts`, `server/root/watch/git-start.ts`, `server/files/roots.ts`). A key set in `local.yml` still wins. The scan reads `<hub>/.oculus/apps` once, as the machine folder, and never a second time as the hub root's `.oculus/apps` (no `repeated` finding for it). Every other path under `~/.oculus` stays. A change of `hub` in `local.yml` while the server runs moves the five defaults and the hub layer as a change of `hub` moves the other hub readers today; the report states what the code does.

2. **The carry-over.** At server start, for each of the five whose key `local.yml` does not set: when `<hub>/.oculus/<name>` does not exist and `~/.oculus/<name>` does, it is copied there (a folder with its files), the source left as it is, and the server's log says what was copied; when both exist, nothing is copied, the hub's copy is the one read, and the log says the home copy is not read. A failed copy is a finding naming the path and the reason, and leaves the hub's path absent. Nothing is ever deleted from `~/.oculus`. The copy runs once per start, before the files store, the schedules watcher and the apps watcher read their paths. A symbolic link under a copied folder, or a copied path that is itself a link, is copied as the file or folder it points to, so the hub holds no link out of itself. When `<hub>/.oculus` is `~/.oculus` (the hub is the home folder), nothing is copied. A key of `local.yml` that names a path keeps that path whatever it is, the old default included, and nothing is copied for it. An app copied to the hub has a new folder, so its approval (keyed by the folder, `apps/record.ts:78-80`) no longer matches and the app asks again; `approvals.json` is not written. A carried note's earlier save copies (keyed by the note's real path, `docs/files-and-search.md:51`) stay under the old path's key and are not shown for the carried note; the docs say so.

3. **Two layers of settings.** `loadConfig(engine, hub?)` merges the engine's `config/` (oculus's general defaults) and then, when a hub is passed, the hub's `<hub>/.oculus/config/`, the same file names in the same places (`sources.yml`, `layout.yml`, `behavior.yml`, `catalogs/vocab.yml`). Every server caller passes `local.hub`; a call with no hub reads the engine alone, so the tests over fixture engines and over the real engine read no hub's `.oculus`, and the four tests of `agents/spec.md:37` stay the only readers of the real hub. The hub layer may set only the keys of the hub list (decision 1), each a dotted key path, and a value it sets replaces the engine's value of that path whole. A key of the hub layer outside the list is a finding naming the key and the file, and is not applied; inside a map the rule is per dotted path, so `slurm: { resource: x, days: 5 }` applies `slurm.resource` and is a finding for `slurm.days`. A hub-layer file that does not parse is a finding and the engine's values stand. A `local.yml` under `<hub>/.oculus/config/` is a finding naming it and is never read. No hub-layer file is required: a hub without `.oculus/config/` reads the engine's values. `from` records the hub-layer file for each key the hub sets, and every finding about such a key (the roots findings of `files.ts`, the documents findings of `content/docs.ts`, the settings findings) names the file the value came from. The hub list:
   - `sources.yml`: `scan`, `portfolio_deck`, `venues_file`, `datasets_file`, `pillars_file`, `domains_file`, `people_file`, `organisations_file`, `resources_file`, `collections`, `leads_file`, `radar_file`, `publications_file`, `linkedin_dir`, `career_file`, `roots`;
   - `layout.yml`: `docs`;
   - `behavior.yml`: `slurm.resource`, `data_domains`;
   - `catalogs/vocab.yml`: `domains`, `venue_themes`, `data_themes`.
   The tiers, the types, the statuses, the Focus lanes, the lifecycle and the manifest schema stay in the engine, with no hub key.

4. **This hub's layer, and the engine's general values.** The step writes `<hub>/.oculus/config/` for this hub: each key of the hub list with the value it has on main today, the whole `docs:` list included (oculus's own guides with it), so this hub reads the same values as before. The engine's files keep a general value of each key: the folder layout keys (`scan` to `career_file` except the two website keys) keep their values, which are the layout every research hub follows and the demo hub uses; `publications_file` and `linkedin_dir` are removed from the engine; `roots` is `[]`; `docs` is `[]`; `slurm.resource` is `''`; `data_domains`, `venue_themes` and `data_themes` are `[]`; `domains` is `{}`. Each reader of a value that is now empty or absent treats it as a hub that has none, with no finding and no throw:
   - `linkedin_dir` absent is no LinkedIn feed: `data/index.ts`'s `FEED_FILES` drops the website folder, the portfolio watcher does not watch it, and the LinkedIn view says the hub names no LinkedIn folder (a text key); `publications_file` absent reads as no publications file, as `audit/rules.ts:112` does now.
   - `slurm.resource` `''` is no cluster: the option's default becomes `''`, `config.test.ts`'s row "slurm.resource must not be empty" is made true to the new rule (an empty resource is no cluster, with no finding), and the Live HPC view and the poller say no cluster is set in the hub's settings (a text key) and poll nothing.
   - The options' defaults of the hub list (`options.yml:187` `data_domains`, `:337` `slurm.resource`, `:1327` `publications_file`, `:1334` `linkedin_dir`, and any other hub-list option whose default is this hub's value) become the engine's general value, so the Settings view's Reset writes the general value into the hub layer.
   - A theme word of a registry that a hub's lists do not hold stays a finding, as it is today for a word missing from the list.
   The `help` arrangement of `layout.yml` names no hub document: its tabs are `help`, oculus's own guides and `memories`. A page saved before the step keeps the tabs it holds, Axel's Help page with its four hub-document tabs among them, until it is reset; the report says so.

5. **The demo hub's layer.** `tools/oculus/demo/.oculus/config/` holds the hub-list values that make a server over the demo show what it shows on main: `domains`, `venue_themes`, `data_themes` and `data_domains` as main's engine holds them, `slurm.resource: utwente` (the demo's `registries/resources.yml:14`), and no `roots`, website keys or `docs` (main's 13 `docs` entries name files the demo does not hold and draw nothing; the demo's catalogue lists none of them after the step, which the report states).

6. **Writes and reload.** A write of a hub-list key through the Settings view, Edit in File, Add Folder to Workspace and the other roots writes, the documents list, or the write endpoint goes to the hub layer's file; any other key goes to the engine's file as today; the change log and History record the file written. When the hub-layer file or the key in it does not exist, the write inserts the key (creating the file, and the folder, when absent), and its undo gives the hub layer back as it was: the key removed, and the file and folder removed when the write created them. The roots findings, the reader (`readRoots`) and the undo (`rootsNow`) read the hub layer. The config channel watches `<hub>/.oculus/config/` beside the engine's folder, and a change to either rebuilds the config and the portfolio as an engine change does today. The Settings view lists the hub layer's files in their groups, each with its name and a control that opens it, and each hub-list option names the hub layer's file as its file. `server/edit/writes/config` is full: new code goes where a folder has room.
