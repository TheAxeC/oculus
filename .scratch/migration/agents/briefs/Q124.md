## What to build

1. **Every tree check runs under `npm run test:checks`, with no per-case limit.** The nine limits are removed, each with the comment that justifies it. `test:checks` drops `--tagsFilter '!slow'`, so it runs every file under `tests/checks`, the slow-tagged `claude-usage.test.ts` included; `test:slow` gains `--exclude 'tests/checks/**'`, so no tree check runs under its 20 s. Every tree check then runs under the `--testTimeout 0` of `npm run test:checks`. No other limit takes the place of the nine: no `vi.setConfig`, no `describe`-level timeout, no hook timeout, no config entry. A case that is slow stays slow and passes, which is the rule. The `@module-tag slow` at `claude-usage.test.ts:3` stays, since it says what the file does (it starts sh and python3). Before the first change, the builder lists every slow-tagged file under `tests/checks` with the grep above and names in the report what each one runs, so the landing's `test:checks` lane takes them on knowingly; a file the grep prints beyond `claude-usage.test.ts` is named the same way.
2. **The deps cache race ends.** The vitest runs started at once never race on a shared folder under `node_modules/.vite`. The race is ended at its cause: each run that starts beside another has a deps cache of its own, or runs with no deps cache. The mechanism is read from the installed vitest and vite (the files named above, their docs and their types in `node_modules`), and the report names it with the vitest and vite source lines it was read from. The whole of `vite.config.ts` is open to the mechanism, so a per-process cache folder in the `test` block, a per-process or a no-cache setting outside it, or a no-cache setting for the `__vitest__` environment are all open. The mechanism holds under these constraints, and the report shows each:
   - Axel's running `vite dev` keeps its own `deps` folder untouched: the top-level `cacheDir` the dev server reads does not move.
   - The results cache (`results.json`) is covered by the same mechanism.
   - `npm run test:quick` started beside `npm test` is covered.
   - A cache left by a killed run (no `deps___vitest__`, or a `_temp_` folder) is covered.
   - Per-process folders, if used, do not pile up without bound; the report says how they are cleared.
   - The change holds wherever the runs start together, in `landing.mjs` and in a person's shell alike. A mechanism in `landing.mjs` alone (one vitest start before `Promise.all`) is not accepted, since nothing the builder runs would prove it.

   These are not a fix:
   - a retry around the start;
   - a sleep or stagger between the lanes;
   - running the lanes one after another;
   - an environment variable;
   - hiding the error.

   When the mechanism needs a cache folder of its own, it lies under `node_modules/` or another folder already gitignored.
3. **The comments and documents say what is true.** `landing.mjs`'s head comment and any comment on the tiers that describes the start of the vitest runs say how the runs share or do not share the cache, with no history. `vite.config.ts:31-37`, `README.md:17` and `HELP.md:371-373` say what `npm test`, `npm run test:checks` and `npm run test:slow` run after item 1. `quick.mjs:127` and `:252` are re-read and rewritten if item 1 makes them false.
