## What to build

Under `tools/oculus/src/routes/api/hook/+server.ts` and `src/lib/server/hooks.ts`:

- `POST /api/hook`, the one endpoint a hook reaches. It carries no token (a hook is `curl` from a Claude Code process, with no page to mint one for) and no `Origin`, so its rules are different from the write route's: the body is JSON of at most 64 KB; a request that carries an `Origin` header is refused with 403 unless `allowedOrigin` accepts it (a browser always sends one on a cross-origin POST, `curl` never does, so this is what keeps another page from forging a notification); at most 20 requests per second are accepted and the rest answered 429; anything else is 200 with `{ ok: true }` so the hook's `|| true` never hides an error worth seeing. The body's fields are taken loosely: `hook_event_name` (`Notification` or `Stop`), `session_id`, `cwd`, `transcript_path`, `message`, `title`, `notification_type` (Claude Code sends `permission_prompt`, `idle_prompt` and others), `stop_hook_active`; unknown fields are kept in a `raw` map for the report and the first payload of each event name is written to stderr once per process, so the real shape is on the record after the first hook fires.
- `handleHook(body, now)` (pure, tested) turns a body into a `HookEvent = { session: string; event: 'notification' | 'stop'; kind?: string; message?: string; title?: string; cwd?: string; at: string }`, and the server keeps the latest event per session in `server/sessions/hooks.ts` (an in-memory map with a 24 h expiry) and publishes it on the `sessions` channel: the watcher of O13 merges `hook` into each record when it rescans, and a hook arriving between rescans republishes the payload with just that record's `hook` changed (through the hub's `publish` with the same records, so the page never waits for a rescan to see a permission prompt). A `Stop` event also marks the record's transcript-tail state `idle` until the next rescan.
- The push: `notify(event, record)` runs `osascript -e 'display notification <message> with title <title> subtitle <subtitle>'` through `execFile` with list arguments (never a shell) and every string escaped for AppleScript (`"` and `\`), a two-second timeout, failures written to stderr and never thrown. The title is `oculus`; the subtitle is the session's title from the record when known, else the cwd's basename; the message is the hook's `message` for a `Notification` and the catalog's `notify.stop` for a `Stop`. Which events push is config: `behavior.yml` gains `notify: { enabled: true, events: [permission_prompt, idle_prompt, stop], quiet_seconds: 3 }`, the events being `notification_type` values plus `stop`; the same session's same event within `quiet_seconds` pushes once. `osascript` is `/usr/bin/osascript` on this machine; on a machine without it the push is skipped with one stderr line.

Under `tools/oculus/src/lib/views/sessions/`:

- `SessionList.svelte`, extended: a row whose record carries a `hook` shows it: a `permission_prompt` as a `warn`-toned chip with the message as the tooltip, an `idle_prompt` as a muted one, a `Stop` as the "stopped at HH:MM" line in the row's meta. The workbench's document title gains a count of sessions waiting on a permission (`app.title_waiting`, "oculus (2 waiting)"), set by `Workbench` from the payload, so a tab in the background says so.
- `SessionDetail.svelte`, extended: the latest hook event as one more key-value row.

Under `tools/oculus/tests/`:

- `server/hooks.test.ts`: `handleHook` on a Notification body, a Stop body, a body missing everything but the event name (accepted with nulls), a body over 64 KB (refused), the per-session latest map and its expiry, the quiet window, the escaping of `"` and `\` for AppleScript, the event filter from the config; `notify` with `execFile` injected as a recording stub, so no notification is fired by the suite.
- `routes/hook.test.ts`: the handler with a header-less request (200), with a foreign `Origin` (403), with a same-origin `Origin` (200), 21 requests in one second (the 21st 429), a non-JSON body (200, nothing recorded).
- `views/sessions.test.ts`, extended: the chip on a row with a `permission_prompt` hook, the stopped line, the detail row.

## Facts checked on the tree, 2026-09-10

- The hooks: `Notification` and `Stop`, each `curl -s -m 1 -X POST http://127.0.0.1:8790/api/hook -H 'Content-Type: application/json' -d @- >/dev/null 2>&1 || true`, timeout 5, at project scope in the hub's `.claude/settings.local.json`, so they fire only for sessions started in the research hub; moving them to `~/.claude/settings.json` is Axel's open call and would make them fire everywhere. The port in the command is 8790, the built server's; `npm run dev` on 5173 receives none unless the command is changed, which the report says.
- Claude Code's hook input is JSON on stdin with `session_id`, `transcript_path`, `cwd`, `hook_event_name` and, for `Notification`, `message` and `notification_type`; for `Stop`, `stop_hook_active`. No hook payload is recorded in any transcript on this machine, so the exact shape is taken loosely as described and logged once when the first real one arrives.
- `/usr/bin/osascript` exists; `terminal-notifier` does not. `display notification` needs no permission prompt on macOS for a script run from a terminal process, and the notification shows under "Script Editor" until the app has its own bundle (step 8's native window).
