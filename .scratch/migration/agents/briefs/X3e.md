H1.1 **One asynchronous runner.** `run` in `server/core/git/run.ts` runs git through `execFile` and answers `Promise<Outcome>`. H1.2 **One outcome reader.** A finished run is read into an `Outcome` by one function, and each end maps exactly as `spawnSync`'s does today (premise "The server's git reads"): exit 0 is ok with the bytes; a non-zero exit, and a signal other than the timeout (`code: null`, `killed: false`), are not ok, `answered: true`, `ran: true`, with git's stderr or the failed sentence; a timeout (`killed: true`, no output-limit code) is not ok, `answered: false`, `ran: false`, with the timed-out sentence; the output limit (`ERR_CHILD_PROCESS_STDIO_MAXBUFFER`) and a git that cannot start (`ENOENT`, and any other text code) are not ok, `answered: true`, `ran: false`, with `short(error)`. ## Decisions taken in this brief (each reversible, none silent)

1. **How the tree follows the disk (C1, C2).** Options: (a) the git watcher's existing recursive watch publishes the changed folders on the `files` channel and the fs store relists them; (b) the fs store polls each open folder; (c) Refresh only, as now (the lazy option). Pros of (a): no new watch, no poll, changes arrive within the watcher's two-second throttle, and the channel already reaches every page. Cons: a busy root relists more; the 64-folder cap bounds it. (b) reads the disk for folders nobody is looking at; (c) leaves X3a-1. Taken: (a).
