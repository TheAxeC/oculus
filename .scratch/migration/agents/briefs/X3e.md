### H. The server's git reads and the folder panel (Z441, Z525)

H1. **No git read holds the server's event loop (X3a-1's five-second Delete, the hub Graph's 10 s first read).**

The cause, one for both symptoms (`agents/reviews/X3e-diagnosis-delete.md` and `agents/reviews/X3e-diagnosis-graph.md`, each under "Cause"): the git watcher reads a root with about a dozen git commands, each run by `spawnSync` in `run` on the server's one event loop, on every write under a watched root, at most once per two seconds per root. The hub's `.agents/worktrees/*` checkouts are roots of their own on the `git` channel (the sessions' workspaces), so while builders write in them their reads come back to back and hold the loop for seconds. A Delete's Trash program finishes in 22 to 92 ms, but its exit is handled only when the loop is free, and the listing the page asks for after the answer waits the same way: the answer's mean was 6405 ms over fifteen Deletes on the delete record's original case and 3907 ms on its shrunk case. The Graph's first page, 60 to 120 ms of git, waited up to 13369 ms on the graph record's shrunk case. The probes that show it: the same reads run without holding the loop turn both red commands green (the delete record's P1, answer mean 55 ms shrunk and 273 ms original; the graph record's probe 1, a mean wait of 2 ms), and each red command is red without them. The on-demand reads of `GET /api/git` hold the loop for their own length the same way: with the watcher's reads already off the loop, one graph request ran 2885 ms, held the loop 2898 ms and kept another request waiting 1390 ms (the graph record's first controlled unshrunk run under "Fix and test"), which Z525 ends as well.

The two records each wrote a diff of `run.ts`, `state.ts` and `root/watch/git.ts`. They differ in the runner's outcome mapping, the queue (one chain for every root in the delete record, one chain per root in the graph record), `refresh` (returning at once in the delete record, awaited by the write route in the graph record) and `worktrees` (both keep a synchronous copy for `compare.ts`). This item is the one design; where it differs from either diff, this item holds, and decisions 34 to 39 give the reasons.

H1.1 **One asynchronous runner.** `run` in `server/core/git/run.ts` runs git through `execFile` and answers `Promise<Outcome>`. No `spawnSync` is left in `server/core/git` and no synchronous runner is kept beside it, since after H1.4 no reader would call one. `run` keeps its parameters (`root`, `args`, `timeout`, `input?`, `env?`), its argument list (`-C <root> --no-optional-locks`, then the command's own, never a shell), `maxBuffer: MAX_OUTPUT`, and the output read as bytes (`encoding: 'buffer'`) with `utf8` and `text` as now; it gives `input` on standard input and closes it, or closes it at once when there is none, as `git-write.ts`'s runner does, so no git waits on an open standard input. `show` and `readDiff` answer the same promise. `run` stays the module's one subprocess call site, so DESIGN.md:137 and the comments `server/files/search.ts:7` and `server/machine/pty/tmux.ts:3` stay true.

H1.2 **One outcome reader.** A finished run is read into an `Outcome` by one function, and each end maps exactly as `spawnSync`'s does today (premise "The server's git reads"): exit 0 is ok with the bytes; a non-zero exit, and a signal other than the timeout (`code: null`, `killed: false`), are not ok, `answered: true`, `ran: true`, with git's stderr or the failed sentence; a timeout (`killed: true`, no output-limit code) is not ok, `answered: false`, `ran: false`, with the timed-out sentence; the output limit (`ERR_CHILD_PROCESS_STDIO_MAXBUFFER`) and a git that cannot start (`ENOENT`, and any other text code) are not ok, `answered: true`, `ran: false`, with `short(error)`. D5's change of `run.ts:167` and `:171` (the empty text in place of 'git timed out' and 'git failed', worded by each reader through D20's codes and keys, Z552) lands in this one reader, once.

H1.3 **The state read.** `statusFor` and every function under it in `state.ts` (`state`, `checkedOut`, `upstream`, `log`, `refs`, `stashes`, `remotes`, `worktrees`) are `async` and await `run`, one command after another in today's order, so one state read runs at most one git process at a time, as now. `statusFor` reads its roots one after another and never rejects. `worktrees` stays one exported function, now asynchronous, which `state` and `compare.ts`'s `workspaceSides` both await; no synchronous copy is kept.

H1.4 **The on-demand reads (Z525).** Every exported read of `reads.ts`, `compare.ts` (X3f's `blameAt` among them) and `files.ts` answers a promise and awaits `run`, and each caller awaits it: `git-reads.ts` (`fileSides`, `worktreeSides`, `REAL`'s `blame` and every read in `handleGitGet`; the `CoreReads` types follow through `typeof`), `autofetch.ts:113` (`sshCommand`), `lines.ts:251` (`trackedFiles`), `keptFiles` and its callers (Z554: `server/machine/hpc/submit.ts`, the type :99-100 and the call :215; `src/routes/api/(machine)/hpc/+server.ts:9` and :38; `tests/server/machine/hpc/submit-world.ts:39` and `submit-files.test.ts:72`), and the Files listing in `fs.ts` (`cachedIgnored`, whose `ask` answers `Promise<Set<string>>`, `listShown`, and `handleFs`, which answers `Promise<Response>`; the route returns it unchanged). `cachedIgnored` keeps its reuse window, an answer held from the moment it came; two listings of one folder asked at once may each ask git. A read that loops over `show` calls (`sidesOf`) awaits each in turn.

H1.5 **One read per root at a time (`server/root/watch/git.ts`).** Each watched root has at most one read running and at most one waiting. A read asked for while none runs starts at once; one asked for while a read runs waits for that read to end, and every later ask before it begins joins it, so a burst of events or refreshes during a long read gives one more read and not one per event. Reads of different roots may run at the same time. An event during a read goes through the throttle as now (`touch`), and the read it asks for waits behind the running one. The first read of new roots in `follow` keeps the same rule, so a root is never read twice at once, its first read included; the new roots of one `follow` are read one after another, and the payload is published once they have answered, in the order `wanted()` gives then. A root appears on the `git` channel when its first read answers; a set of roots that only changed order is still published at once. The rescan's `follow` inside a root's read is started and not awaited by that read. A read that answers for a root dropped while it ran (`drop`), or after `close()`, keeps nothing, publishes nothing and moves no `readFrom` stamp, and `drop` and `close()` leave no waiting read that would start later. The `files` message of a window is published by the throttle's timer (C1), never by the read.

H1.6 **`refresh` keeps its callers' order.** `GitWatcher.refresh(root)` answers `Promise<void>`, which settles once a read of the root that began after the call has ended: published, found unchanged, or kept nothing because the root was dropped or the watcher closed. For a root that is not watched it settles at once. It never rejects and always settles, after `close()` and `drop` included, so no answer hangs on it. `handleGit` awaits it (`git-routes.ts:468`, after D20's `finally` at :461-463 has ended the run, so a Cancel never waits on the re-read; the option typed `(root: string) => Promise<void>` at `:199`), so a write is still answered after its state is on the `git` channel. The automatic fetch awaits it in `visit` (`autofetch.ts:206`, typed at `:55`), so a repository's re-read still ends before the next repository's fetch. `tests/server/root/context-fixture.ts:71` stands in `refresh: () => Promise.resolve()` in place of `noop`. `src/routes/api/(git)/git/+server.ts:23` and the automatic fetch's wiring (`context.ts:433`, moved with `startGit` under Z705 (I1)) need no change of behaviour, since each returns what `refresh` returns.

H1.7 **The callers of `statusFor` in tests.** `tests/server/git/refs/cherry-pick.test.ts:38` (G33's file) and `tests/data/real-hub.probe.ts:128` await it; each edit is listed in the report with its before and after.
