# Brief: O24a, the metalist editor, the shared entry form, the three registries as collections, and the Venues view

Read `../spec.md` first; it governs this package unchanged. O24 was one package (Venues, Programs, Domains, Map, the dedicated collection forms starting with the metalist editor) and is run as two: this one builds what the other three views need (the write vocabulary for a `metalist` field, the entry form as a shared partial, the three registry files carried as collections so their entries get the add and edit form) and the Venues view; O24b builds Programs, Domains and Map on it. The cockpit's Venues tab is `tools/cockpit/src/cockpit/render/collections.py` `venues_tab_html`, lines 337 to 457, wired at `page.py` lines 530 to 538; oculus has no view under `venues` today although `config/layout.yml` line 24 names it in the Sources group, and the entry form draws no control for a `metalist` field (P4 left it out: `views/collection/EntryForm.svelte` lines 11 to 13 and 40 say why).

## Decisions taken in this brief (each reversible, none silent)

1. **The three registries are collections too.** `config/sources.yml`'s `collections:` list gains `{ key: venues, title: "Venues", file: registries/venues.yml }`, `{ key: programs, title: "Pillars", file: registries/programs.yml }` and `{ key: domains, title: "Domains", file: registries/domains.yml }`, so `readCollections` (`data/index.ts` line 169, every entry of the list) carries their entries and schemas as `collections.venues`, `collections.programs`, `collections.domains` beside the entities the registry reader already makes of them, exactly as funding is carried twice since P4 (`data/normalise.ts` lines 43 to 51). `REGISTRY_KEYS` (line 52) keeps the three out of `registerCollections`, so no generic collection view appears for them; this package registers `venues` itself and O24b registers `programs` and `domains`. The write path needs nothing new: `collectionFile` (`server/writes/entries.ts` line 37) resolves a key through the same list.
2. **The write vocabulary widens for a metalist.** `FieldValue` (`server/yaml-edit.ts` line 20) gains `Record<string, string>[]`, a list of flat maps of strings; `asFieldValue` (line 119) accepts a list whose every item is a map whose every value is a string, and refuses anything else as before. A metalist is never one line: `renderOneLine` returns null for it, and the two places a value is written render it as a block list of one-line flow maps at the key's own indentation, `- { label: Scheme, value: "NWO Veni" }` per item, which is the shape every `meta:` on the tree is written in (`funding/funding.yml` lines 30 to 34): `replaceValue` over an existing key (the old block replaced whole, the bytes outside it untouched), `appendTop` for a key not there, `setEntryFields` and `appendEntry` through `renderEntry` (`server/entry-edit.ts` line 186, which today skips any value whose rendering holds a newline: a metalist is rendered as its block lines instead, the item lines indented two deeper than the field). An empty list clears the key as an empty string does. `createEntry` (`server/writes/entries.ts` line 169) passes a metalist through `asFieldValue` unchanged.
3. **The form draws a metalist as rows.** `EntryForm.svelte` draws a `metalist` field as rows of two `TextInput`s (label, value) with a remove control per row and an add-row control under them, saving the rows as the list of `{ label, value }` maps (a row with both empty is dropped); the words are `collection.meta_label`, `meta_value`, `meta_add`, `meta_remove` in `config/text-oculus.yml`'s `collection` group, where P4's form words are. The head comment's reason for drawing nothing (lines 11 to 13) goes with the limitation.
4. **The entry form is a shared partial.** `views/collection/EntryForm.svelte` moves to `views/shared/EntryForm.svelte` with `Collection.svelte` importing it from there, since the boundary row of Q1 lets any view import `views/shared/**` and nothing else may reach another view's partials (`tests/boundaries.test.ts` lines 19 to 22 and 58 to 61). The Venues view, and O24b's two, open it for "+ add" and for a card's edit control. Its props stay as they are.
5. **A select can take its options from the vocabulary.** `SchemaField` (`data/model.ts` line 399) gains `optionsFrom?: string`, read by `collectionSchema` (`data/normalise.ts` line 382) from the file's `options_from`; `formFields` (`state/collection.ts` line 416) takes a second argument, the merged config as `configMap()` gives it (`state/selectors.svelte.ts` line 53), and a `select` with `optionsFrom` and no `options` resolves them there: a plain list of strings is the options; a list of maps takes each map's `key`, leaving out one with `assignable: false`. The two venue selects are the first users: `venue_tiers` is in `config/vocab.yml` at line 268; `venue_categories` is not there (checked 2026-09-11: `grep -n '^venue_categories' config/vocab.yml` prints nothing), so this package adds `venue_categories: [journal, conference]` beside `venue_tiers`, the cockpit's own value (`tools/cockpit/data/config/vocab.yml` line 289).
6. **The venue entity carries four more fields.** `Venue` (`data/model.ts` line 288) gains `heldMonth`, `timing`, `call` and `email`, read in `data/normalise.ts` where `deadlineMonth` is, since the ribbon and the meta row draw them; the registry holds them on 18, 19, 5 and 1 entries.
7. **The pure parts are one module.** `state/venues.ts`: `realProjects(projects, dead)` (the rule of item 5), `venueUsers(venue, projects)` with the concentration flag, `themeFacets(venues)`, `applyThemeFacets(venues, off)`, `quartileTone(q)`, `freeTone(free)`, `monthIndex(word)`, `isBiennial(venue)`, `timeline(venues, todayMonth)` (the twelve columns and the next-deadlines list), `sparkline(counts, ramp)`, `venueSearch(venues, words)`; every function under test in `tests/state/venues.test.ts`. The view's own state (the search words, the facets that are off, the two sections' open state) is a `VenuesState` parsed from the instance state the way `parseCollectionState` does it.
