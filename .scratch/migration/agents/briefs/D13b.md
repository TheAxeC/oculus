## What to build

1. **The diff answer.** The four diff reads answer `{ ok: true, files }` in place of `output`, `files` one `DiffSides` per file in git's order: `{ oldPath, newPath, head, binary, original, modified }`. `head` is git's head lines for the file (from `diff --git` to the line before its first `@@`, or its `Binary files` line), which a patch cut from the file repeats; `binary` is git's own call; `original` and `modified` are the two whole texts, the empty string for a side that does not hold the file and for a binary file. The sides: a file's changes, `:path` (the index) against the worktree file; a staged file, `HEAD:path` against `:path`; a commit's file, `<hash>^:oldPath` (nothing for a root commit) against `<hash>:newPath`; a stash, `<ref>^1:oldPath` against `<ref>:newPath` for each file of `diff --name-status <ref>^1 <ref>`; a worktree, `<merge base>:oldPath` against `HEAD:newPath` in the worktree for each file of the three-dot diff. The head lines are cut on the server (`server/core/git-parse.ts`), from the same `git diff` or `show` the read runs today. The type is `DiffSides` in `data/model/model-sessions.ts`. The refusals and the roots checks stay as they are.
2. **The diff primitive.** A Monaco diff editor component in `ui/controls/editor/`, built on the same `loadEditor` kit, theme, chord removal and palette listing as `Editor.svelte` (both inner editors), read-only on both sides. It takes the two texts, the language, a model name unique to the tab instance, the layout (side by side or inline, `renderSideBySide`), and draws: the changed words of a line (Monaco's own), the line numbers of both sides, every unchanged run longer than six lines hidden with three lines kept each side (`hideUnchangedRegions` with `contextLineCount: 3`, `minimumLineCount: 1`), whitespace changes shown (`ignoreTrimWhitespace: false`). It answers its line changes (`getLineChanges()` after each diff update), its selections on both sides, and its view state (`saveViewState`), and restores a view state handed in. It holds view zones handed in by the parent above given lines of the modified side, for the hunk bars. It sizes itself to its content when asked (for a list of files) and fills its box otherwise. To make room, the page-level loading and theme files (`load.ts`, `workers.ts`, `grammars.ts`, `theme.ts`, `colours.ts`) move into `ui/controls/editor/kit/`, every import updated, so the folder holds at most ten items after the new files.
3. **The hunks and the chosen lines** (a pure module in `state/sources/repositories/`, in place of `diff-rows.ts`). From Monaco's line changes (`{ originalStartLineNumber, originalEndLineNumber, modifiedStartLineNumber, modifiedEndLineNumber }`, an end of 0 for an empty side): the hunks, each run of changes whose unchanged gaps are at most `2 * CONTEXT` lines (6), which is git's own grouping, so a hunk staged is the hunk `git add -p` offers; the chosen rows of a hunk from the selections: a line of the modified side's selection chooses the added line on it; a line of the original side's selection chooses the removed line on it; a change the modified selection touches that has removed lines is taken by VS Code's rule (`intersectDiffWithRange` in VS Code's git extension): a pure deletion whole (touched when the selection holds the modified line it sits after, or line 1 for one at the top), a change with as many removed as added lines line by line (the removed line paired with each chosen added line), any other change with all its removed lines; the step from change to change (Previous, Next, wrapping as `stepChange` does); the change nearest a line.
4. **The patch** (`diff-patch.ts`, rewritten over `DiffSides` and chosen rows). For a stage (applied forwards) the patch goes from `original` to the text `original` becomes with the chosen rows applied (a chosen removed line deleted, a chosen added line inserted at its place, the rest as `original` has it); for an unstage or a revert (applied in reverse) it goes from the text `modified` becomes with the chosen rows taken back to `modified`. Its head is the file's `head`; its hunks hold three lines of context from the text the patch is applied to, hunks whose context would overlap merged into one; a last line with no newline carries `\ No newline at end of file`; a choice that changes nothing answers the empty string. The server's `apply --recount` is unchanged.
5. **The diff pane** (`Diff.svelte`, `DiffFile.svelte` replaced by a file section on the primitive). One diff editor per file, each under its path when the diff holds more than one file; a file section's editor is created when the section first comes within one screen of the pane's view and until then holds its height from its line count; a binary file is the note it is today. The bar as today: Side by Side and Inline, Previous and Next Change, Open File at the change, the re-read. Alt+F5 and Shift+Alt+F5 move through the changes of every file while the pane holds the focus, as today. A file's own diff draws a bar above each hunk as a view zone of the modified side, with Stage Block and Revert Block, or Unstage Block in a staged diff, each reading "Stage N Lines" (the existing keys) while the selections choose rows in that hunk; a press applies the patch of item 4 through `applyPatch`, a revert after the same confirm. The pane opened at a line goes to the change nearest it. The pane keeps the diff editor's view state in its instance state in place of `opened` (the revealed runs and the scroll), kept across a re-read and a reopen; a stored `opened` from before is dropped. The text is re-read as today, and a re-read that changes nothing keeps the view state.
6. **The merge editor.** `regionsOf` takes its regions from node-diff3's `diff3MergeRegions(ours, base, theirs)`, the `Region` shape and every rule of today kept: a stable region, or an unstable one whose two sides are equal, or one where only one side changed, is settled; any other is a conflict with each side's lines and spans; three empty versions still answer one settled region. `diff-words.ts` goes whole. Incoming and Current are read-only Monaco editors with each conflict's lines decorated and its bar of choices as a view zone above it (a settled conflict saying how, as today); the Result is a writable Monaco editor whose typing goes through `typedPieces` as today, and a choice rewrites the Result as one edit over the whole model, so undo takes it back. The bar, the notes, Complete Merge, Accept Deletion and their confirms stay as they are.
7. **Removed.** `diff-rows.ts`, `diff-words.ts`, `DiffFile.svelte`, `MergeSide.svelte`'s line list, and every catalog key, glyph, style and test entry only they used (the `type-scale.test.ts` entries follow the files).
8. **Documents.** `HELP.md:82`, `:177`, `:179` and `:187`, and `DESIGN.md:294`'s sentences on the diff answer, the diff pane and the merge editor say what is built: the two versions answered, Monaco's diff editor per file, the folds as Monaco hides them, the chosen lines as the selection, the merge editors on Monaco and the regions from node-diff3.

## Cases

- The answer, a file's changes: a repository where `a.txt` has line 10 changed in the worktree answers one `DiffSides` with `oldPath` and `newPath` `a.txt`, `head` starting `diff --git a/a.txt b/a.txt` and ending with `+++ b/a.txt`, `binary` false, `original` the index's text and `modified` the worktree's.
- The answer, staged: a new file staged answers `original` `''`, `modified` its index text, and a head holding `new file mode`; a staged deletion answers `modified` `''`.
- The answer, a commit: a root commit's file answers `original` `''`; a commit that renamed `x` to `y` answers `oldPath` `x`, `newPath` `y`, each side its own version.
- The answer, a stash and a worktree: every file of each in git's order, each with both sides.
- The answer, binary: `binary` true, both texts `''`, the head holding git's `Binary files` line.
- The answer, refusals: a root not published, a path outside the repository, a malformed hash or stash ref answer the errors they answer today.
- Hunks: changes at modified lines 10 and 17 (gap 6) are one hunk; at 10 and 18 (gap 7) two; a single change is one hunk; no change, no hunk.
- Chosen rows: a modified selection on line 12 of a change 10 to 14 against original 10 to 14 chooses added 12 and removed 12; against original 10 to 11 chooses added 12 and removed 10 to 11; a selection on the line a pure deletion sits after chooses the deletion; an original selection on a removed line chooses it alone; a selection touching no change chooses nothing.
- The patch, stage of a whole hunk: the patch `git apply --cached --recount` takes, leaving the index equal to the worktree for that hunk and the other hunks unstaged (proved with git in `git-ops.test.ts`).
- The patch, stage of one added line of three, one removed line of two, unstage of one line, revert of one line: each applied by git, the resulting index or worktree text as the chosen rows say.
- The patch, the edges: a hunk at the first line, a hunk at the last line of a file with no final newline, a new file, a deleted file, two chosen changes four lines apart (one hunk), a choice that changes nothing (`''`).
- Steps: Next from before the first change goes to the first; Next from the last wraps to the first; Previous from the first wraps to the last; over two files the steps cross from the last change of one to the first of the next.
- The line a pane opens at: the change nearest line 15 of changes at 10 and 17 is the one at 17.
- The pane's view state: a stored `opened` is dropped; a stored view state is handed back to the primitive; a re-read with the same texts keeps it.
- Merge regions on node-diff3: every case of `merge.test.ts` passes unchanged (the stable run, the conflict, the one-sided change, the same change both sides, both sides deleting, the empty versions, the typing and the deletion cases).
- `grep -rn "diff-rows\|diff-words\|DiffFile\|pairedWords\|wordDiff" src tests` prints nothing.
- For the look, stated in the report's before and after and not tested here: a file's diff side by side and inline with the changed words marked; the hidden runs and their reveal kept across a re-read; the hunk bars aligned between the two sides; Stage Block, a line chosen by pressing its number, Stage 1 Line, Unstage, Revert with its confirm; Alt+F5 through a stash of several files; Open File at the change; the merge editor's conflicts, a choice, typing into the Result and undo; every theme's colours on the diff and merge editors.

## Decisions taken in this brief (each reversible, none silent)

1. The answer's shape: `files: DiffSides[]` with `oldPath`, `newPath`, `head`, `binary`, `original`, `modified`, in place of `output` for the four diff reads. LA9 3 (a) ruled that the answer carries both versions; the field names and dropping `output`, which no reader needs once the page stops parsing diffs, are this brief's.
2. Hunks are git's grouping (changes at most six unchanged lines apart), drawn over Monaco's line changes, so what a Stage Block stages is what it stages today.
3. The chosen lines are the selections: pressing a changed line's number in Monaco selects that line, as pressing it chose it in X3b's pane, Shift extends and Alt adds a selection; a change the modified selection touches takes its removed lines by VS Code's rule, and the original side's selection chooses removed lines directly, so one removed line can still be staged alone.
4. Both sides of every diff are read-only, as X3b's pane is; Monaco's own revert arrows (`renderMarginRevertIcon`) are off, since the hunk bars carry Revert.
5. Whitespace changes are shown (`ignoreTrimWhitespace: false`), since a hidden whitespace change could not be staged.
6. A diff of several files creates each file's editor when it first nears the view, since a stash can hold dozens of files and each diff editor is two editors.
7. The pane's memory of opened folds becomes the diff editor's view state; an old `opened` is dropped, which opens a remembered fold closed once.
8. The editor folder's page-level files move into `kit/` to keep the folder under the ten-item line.
