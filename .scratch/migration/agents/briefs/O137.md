## What to build

1. **`sort:` on a list entry.** `CollectionTraits` gains `sort?: string[]`, the fields in their order. `entryOf` reads it: a list of texts is read as it stands, an empty list is no `sort`, and any other value, a text among them, is left out with the problem `findings.collections.sort_unread` (wording under "Decisions" 6), worded as `skip_unread` is with the value and the entry's key. `traitsOf` carries it onto the read collection, so `Collection` carries it to the page. The doc comments of `CollectionTraits`, `entryOf` and `traitsOf`, and the head comment of `collections.ts` (:7-13), name it.
2. **A field the schema does not name.** For a collection file with a `schema:`, each word of its entry's `sort` that names no field of the schema is a finding `findings.schema.sort_unknown` (wording under "Decisions" 6) at the file's `schema` key, where `key_beside` is put, made in `run.ts` from `HubFile` carrying the entry's `sort`; the order (item 4) leaves that word out and reads the others. A file with no schema has its `sort` read as written. The head comment of `run.ts` (:7-13) names the finding.
3. **oculus's sorts.** `config/defaults/sources.yml` gives each card-list entry its `sort:`: statements `[status, title]`, people `[name]`, organisations `[name]`, resources `[kind, name]`, funding `[status, deadline]`, events `[status, date]`, education `[status, date]`, applications `[status, deadline]`, tasks `[status, deadline]`, literature `[title]`. The six entries of `REGISTRY_VIEWS` carry none (Decisions 1). The comment over the list (:28-33) gains `sort:` in its bullets, saying what item 4 does; `docs/templates.md`'s config template says the same in its comment (:62-75) and its commented list (:76-92) equals `sources.yml`'s list line for line; `docs/data-map.md:34` names `sort:`. `config/options/sources.yml` gains the field `sort` with `control: list` and a help line saying what it orders and what a list with none does.
4. **The order.** One pure function in `src/lib/state/boards/collection/index.ts` (in place of `pinnedFirst`, which goes, or beside it if another caller keeps it: grep), taking a part's entries, its collection's `sort` and its schema, gives the order the cards are drawn in:
   - the pinned entries (`isPinned`) first, then the others, and inside each group by the `sort` fields read left to right, then in the file's order (a stable sort over the file's order);
   - the field `status` (`STATUS_FIELD`, index.ts:81) by the order of its schema field's options (`optionKeys`), a value its options do not hold after the ones they hold, alphabetically among themselves; a file with no schema, or a status field with no options, compares it alphabetically;
   - a field whose schema `type` is `date` oldest first, by its text (`YYYY-MM-DD` sorts so);
   - any other field alphabetically, by one `Intl.Collator('en', { sensitivity: 'base', numeric: true })`, so the order is the same in every reader's locale, `<O diaeresis>` sorts beside `O`, case is ignored and `2` sorts before `10`; a number compares by its text (`2025` as `"2025"`), and a list value by its first item's text;
   - an entry that lacks the field, or holds an empty text, a map or an empty list there, goes after those that hold it;
   - with no `sort` (none written, an empty list, or every word left out by item 2), by `entryWords(entry)`, the words the card is headed by, alphabetically as above; for a file whose entries carry the title field this is that field, as the step line says.

   `Collection.svelte`'s `shown` and `entries` draw each part in that order, handing the function `part.collection.sort` and `part.schema`, the parts still in the hubs' order (:214-220). The views that draw entries outside a collection's cards (Focus's Tasks section, the awaiting box, the positions band, the Person page and the Entry page) keep the file's order and are not changed. Its head comment (:14, :19) says the order and no longer the keyboard move; `index.ts`'s head comment (:1-12) names the function. List mode keeps its column sort.
