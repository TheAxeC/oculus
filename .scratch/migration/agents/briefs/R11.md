# Brief: R11, a config push repaints the page

Read `../spec.md` first, its section "The principles every package is judged on" above all. Axel decided on 2026-09-14 at 00:30 that every open edge is fixed; this one is O10d's: a `config` push that changes a string, a glyph or a tone reaches the client's stores but the page keeps drawing what it drew, until a reload. The glyph mode is the model: it is one rune, read where a glyph renders, so a change redraws every glyph. This package runs beside R15 (the hooks snippet) under the two-worker rule: it writes only under `src/lib/state/`, `src/routes/views.ts`, `src/lib/views/registry.ts` if the registry needs a remove, `tests/state/`, `tests/views/registry.test.ts` and `tests/routes/` if one exists; it never touches `src/lib/server/`, `src/lib/views/Status.svelte`, `config/text/views/status.yml`, `README.md` or `tests/server/`.

## What to build (client state; no data, wire or config change)

1. **A push is a version the readers depend on.** One rune, in a `.svelte.ts` file beside `glyphmode.svelte.ts` (or in it, renamed to what it now is: the configuration's generation), holds a counter the config push bumps after the five setters ran; `t()`, `lookup()`, `glyph()`, `asciiOf()`, `resolveGlyphTokens()`, `toneOf()`, `paletteTone()` and every other exported reader of `text.ts`, `tones.ts` and `appearance.ts` read it, so a template or a `$derived` that called them re-runs when a push lands, exactly as the glyph mode makes them re-run today. The bump happens once per push, after every store took its part, so a component sees the new strings and the new tones together and never a half state. Plain code that reads these outside a reactive context (a test, a server-side helper) is unchanged: reading a rune outside an effect is allowed and costs nothing.
2. **The registry follows the keys.** `registerCollections(keys)` registers the collection views for the keys given and unregisters the ones no longer in the list, so a key removed from `config/sources.yml` disappears from the rail and the palette on the push; an instance of a removed collection view that is open on a page is closed by the shell's existing path for a view that no longer exists (find it; say which). `registerComponent` gains its inverse if the registry has none.
3. **Tests.** (a) `tests/state/` gains a test that, after `setCatalog` and the bump, a `$derived` over `t('some.key')` (or a `$effect` in a component test of the existing harness) yields the new string, and the same for a tone through `toneOf` and for an appearance value; (b) a test that the bump happens once per push and after every setter (order observed through a spy or the sequence of values); (c) `tests/views/registry.test.ts` gains the unregister case: keys `[a, b]` then `[a]` leaves `b` out of the registry and its rail entries; (d) `tests/boundaries.test.ts` passes: the rune lives in the state layer and `text.ts` stays plain.

## Decisions taken in this brief (each reversible, none silent)

1. One generation rune for the whole config push, not one per store: the readers are many, the push is one, and a single dependency is the smallest thing that redraws everything that read the config.
2. The rune lives in a `.svelte.ts` file in `src/lib/state/`, beside or merged with `glyphmode.svelte.ts`; the worker chooses and says which.
3. `registerCollections` is the one owner of the collection registrations, adding and removing.
