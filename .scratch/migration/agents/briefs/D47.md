## What to build

1. **One Session view.** The view `session-detail`, label Session, holds three sections in one tab: Details (what the Session detail view shows today: the key-value block, the pin, rename and resume controls, the context meter, the tokens and cache lines), Changes (what the Changes view shows today, the touched files and the repository in each of its shapes, its writes and their confirmation) and Agents (what the Agents view shows today, its rows and its running timer). One `SessionPicker` in the view's bar picks the session for all three. With no session the view shows `PickSession` as today and draws no section; a session dismissed while shown gives `PickSession`, the closed list and the order kept in the tab. Every behaviour of the three views is kept: no control, row, state or sentence of the three is lost, and the report lists each with where it now is.

2. **Built as the Files view's sections.** Each section has a head drawn by the same section head the Files view uses, with its name and, for Changes and Agents, a count (Changes: the files the session touched; Agents: the agents listed); Details has no count, so the moved `Section.svelte` takes `count` as optional. Each section is its own `TreeView`, one focus stop, as each Files section is; Tab moves between the heads and the arrows move within a section; content that is not a tree row (Details' controls, the Changes commit box) sits in the section's open body. A press on a head opens or closes it; every section starts open; a closed section's rows are unmounted, so the Agents timer stops and the Changes section asks `/api/git` for nothing while closed, and once on reopening. Which are closed is kept in the tab's own state under `closed` (as the Debug view keeps it) and the order under `sections` (as the Files view keeps it), so a reload, a tab switch and a move of the tab keep them. A pick, a pin or an unpin in the bar keeps them: `pinInstance` and `unpinInstance` (`instances.ts:139`, `:164`) change only `session` and `label` and keep the tab's other state. The heads are dragged among each other and moved with Alt+Up and Alt+Down as the Files view's heads are, and the order is kept in the tab's state. To share them, `Section.svelte` and `list-drag.svelte.ts` move from `views/sources/files/sections/` to `views/shared/explorer/sections/`, and every importer listed above imports them from there; the Files view's behaviour is unchanged.

3. **The retired views.** The registrations `changes` and `agents` go, with their components folded into the Session view's folder as its sections. The Session view's pane toolbar keeps its Transcript and Timeline buttons and loses Changes and Agents, which are its own sections now. `SESSION_VIEWS` (`card.ts:21-27`) loses `changes` and `agents`. A saved layout's `changes` or `agents` tab is carried to a `session-detail` tab keeping its id and its state (its pin) in `saved/migrate.ts`, the way a `config` tab is carried; such a tab in a pane that also holds a `session-detail` tab of the same pin (the same session, or both unpinned), a tab carried earlier in the same pane included, is dropped, and the pane's active tab moves to that `session-detail` tab when the dropped one was active. The two migration functions are renamed for what they now carry (`treeWithoutRetired`, `withoutRetiredTabs`), their two callers in `saved.ts` following, and the workbench held before pages (`load.ts:98`) is carried through the same migration, so a retired `config`, `changes` or `agents` tab there draws as its successor. The `transcript` and `timeline` registrations and the `[transcript, timeline]` pane at `config/layout.yml:64` stay as they are.

4. **The Sessions arrangement.** `config/layout.yml:65` becomes `view: [session-detail, { view: files, state: { follow: true } }]`. A page made from the arrangement opens the Session tab with its three sections.

5. **The text.** The labels, bar labels and glyph keys the step no longer reads are removed (G24), and the glyph `changes` leaves `config/catalogs/glyphs.yml` and `icons.yml`; the section name Details is a new key `sessions.section_details` in `session-detail.yml`, and Changes and Agents keep their view labels' words under section keys; the text files keep their names and their other keys, and each head comment names the section of the Session view that owns it. `HELP.md:43` and the key sheet's row in `config/text/app.yml:13` read `m1-m5`. `DESIGN.md:225` drops `'changes' | 'agents'` from `ViewId`, `DESIGN.md:456` names the Agents section's file at its new path, and `answers.ts:2` says "the Changes section". `HELP.md:134` describes the one Session view with its three sections, and the rows at `:138` and `:139` go. `docs/views.md`'s `## Session` section describes the view and its sections and takes in the content of `## Changes` and `## Agents`, which go; nothing either says is lost. `docs/source-control.md:23`, `DESIGN.md:472`, the "Changes panel" comments listed above and each head comment of a moved or merged file are made true or marked still true in the report. `tests/checks/tree/allow-duplication.txt:23` follows the moved paths.

## Decisions taken in this brief (each reversible, none silent)

1. The merged view keeps the id `session-detail` and the label Session it has today, so the opening calls (`SessionList.svelte:212`, `context.ts:750`, `CardSessions.svelte:46`) and the saved Session tabs need no change; `changes` and `agents` are the ids that retire. A new id would carry every saved Session tab through the migration as well, for no gain.
2. The sections are named Details, Changes and Agents. Changes and Agents keep the names their views had; Details names what the Session detail view showed, since a section named Session inside a view named Session says nothing.
3. Every section starts open, as the Debug view's do: the three views were open side by side as tabs, and a closed section is one press away.
4. The heads are reordered by drag and by Alt+Up and Alt+Down, as the Files view's are, since the plan line asks for the sections built as the Files view's are and reordering is part of how those are built. Open and close alone would be the lazy option: it leaves out the part of the Files sections that needs the shared drag.
5. `Section.svelte` and `list-drag.svelte.ts` move to `views/shared/explorer/sections/`: `views/shared` and `ui/tree` are full, `views/shared/explorer` has room for one more item, and the boundary check forbids importing them from the Files view.
6. A saved `changes` or `agents` tab is carried to a Session tab, and dropped beside a Session tab of the same pin, as the retired `config` view's tabs are carried and dropped (`migrate.ts`), so a saved Sessions page reads as one Session tab and no tab draws as an unknown view.
7. The text files keep their names and keys, owned by the sections, so `CATALOG_FILES` and the keys of the kept text stay as they are; only the keys nothing reads go.
8. With no session the view shows `PickSession` alone, as each of the three views does today; the section heads would have nothing to hold.
9. A pick, pin or unpin keeps the tab's other state (Z745): the closed sections and their order are the reader's own arrangement, and a pick that wiped them would undo it on every session change. Leaving `instances.ts` alone is the lazy option.
10. The migration functions are renamed and the workbench held before pages goes through them (Z745), so no retired view's tab draws as an unknown view from any saved source; leaving the old names on functions that carry three views, or the pre-pages workbench unmigrated, is the lazy option.
11. The state keys are `closed` (as the Debug view's) and `sections` (as the Files view's order); neither collides with `session`, `label` or `id`, which `stateId` reads.
