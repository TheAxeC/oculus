# Brief: O148, the Project facts strip

Size: a full step

Read `.scratch/migration/agents/spec.md` first; its rules govern this step unchanged. Then `.scratch/migration/agents/guarded.md` for the test rule and the guarded behaviours. No ADR touches this step (the repository has no `docs/adr` folder: `test -d docs/adr || echo "no docs/adr"` prints `no docs/adr`).

A design ruling decides what is built. It never exempts the code: every line is written to the standards pages, so that people can read, use and maintain it.

## The step's line and its rulings

The plan's line: "a strip at the foot of every slide that comes from a project's deck, with form, stage, status chips, domain, pillars, datasets, lead, supervisors, collaborators, year, venue, funding, compute, code, reproduced and tier, each field that holds a value, the stage shown as it is, `failed` and `stopped` included, wrapping to two lines at most; a toolbar toggle, saved with the pane, drawn only when the slide on screen comes from a project's deck; `{{project.<field>}}` in a slide's text is filled from that project's manifest; the strip shown on screen, in the presenter screen, in the audience window and in the PDF the same way".

The rulings it rests on, as Axel ruled them:

- 680 (a): the strip's fields are drawn as short labelled chips, the way the project card draws them; only fields that hold a value appear, wrapping to two lines at most; a toolbar toggle, "Project facts", turns it on and off, on by default and saved with the pane; slide text can write `{{project.venue}}`, `{{project.year}}` and so on, the same way `{{<group>.count}}` works.
- 682 (a): one Present view whose controls follow the deck: the Project facts toggle is drawn when the slide on screen comes from a project's deck, and not for a plain deck.
- 684: the strip shows the stage as it is, `failed` and `stopped` included, since a deck in the workbench is not a publication.

## What to build

1. **The facts on the deck answer.** The deck the deck route answers carries, for every slide built from a project's deck, which project that is, and the project's facts once per project, so the pane, the presenter screen, the audience window and the print page all draw the strip from the deck they already read and from nothing else (the two routes hold no client state, `show/+page.server.ts` and `print/+page.server.ts` say so).
   - The project of a slide is the project of the deck whose file holds the slide: the member deck's for a slide a group places, the shown deck's own for a slide of its own files and for a summary or grid it places. A slide of a deck that is no project's carries none.
   - The facts are the sixteen fields of the step's line, in this order: form, stage, status chips, domain, pillars, datasets, lead, supervisors, collaborators, year, venue, funding, compute, code, reproduced, tier. Each field holds the words the project card gives it, worked out on the server from the snapshot: a person by the people registry's `name`, else the person's key; a pillar by its `title`, else its key; a dataset and a funding scheme by their key; the venue by its `short`, else its `name`; a compute resource by its `name`; the year as the manifest writes it (`yearWritten`); the code status by its word (the card's `codeLabel` words); reproduced by its date, else the yes word the card draws; form, stage, chips and tier by their words of the hub's vocabulary (a word's `label`, else the word); the domain by its domains registry title, else its key. Form, stage, chips and domain also carry their word or id, so the strip draws them in the hue the card draws them in. A field with no value carries none, and an id the registry lacks is left out as the card leaves it out.
   - The words are read in the hub the deck is read under, its own vocabulary and registries, so a deck of a second hub draws that hub's words.
   - Both readers of decks give the reader the same facts, made by one function of the data layer from a project's ids and the hub's registries and vocabulary: the deck route's read (through `DeckSource`, which its two builders, `api/(docs)/deck/+server.ts` and `deck-files.ts`, fill, `WriteTarget.entities` and `hooks.ts`'s `entities()` widened to the kinds it needs) and the snapshot build's read (`data/index.ts` `deckProjects` and `decks()`), so the findings the Findings view lists from the snapshot build are the ones the deck route's read raises. The deck writes read the same source and are unchanged in what they write.
   - Each word rule exists once (`spec.md:89`): a person's name else key, the venue's short else name, the code status's words, a vocabulary word's label else the word, a domain's title else its key. A rule the card holds on the client side that the server now needs moves to the data layer, and the card reads it from there (`card.ts`, `items.ts`, `person.ts`, `tones.ts` as each rule needs); a rule the server side already has is reused. The code status's words come from the catalog the server holds (`config.text`), the same keys the card reads.
   - The project keys of the facts map are the keys of the projects of the hub the read is made under, which are unique in that hub (`DeckProject.id`).
   - The client's `deckShape`, the model types and the model facade (`model/index.ts`) carry the new fields. The names are: `project?: string` on a slide (the project's key), `projects: Record<string, ...>` on the deck (the facts by the project's key), `facts: boolean` in `PresentState`, and `facts: boolean` in the `keep` message. The builder reports the facts' TypeScript type.
2. **The strip.** `Slide.svelte` draws, at the foot of every slide that carries a project, below the slide's own content and the key hint, a strip of the project's facts: each field that holds a value, as a short labelled chip, the field's label then its words, a list's words joined in the one chip. The form and the chips wear the card's hues (a blocking chip red), the domain the domain's hue, the stage the stage's hue as the card's filled stage chip, the year, the code, reproduced and compute the card's glyphs; the rest are plain tags. The stage is drawn as it is, `failed` and `stopped` included. The strip wraps, and is two lines at most: a third line is not drawn, and a chip's words longer than its room end in an ellipsis. Its labels are catalog words, the existing ones reused where the catalog has the field's word, new ones added to the `present` group. The strip is the same component on every surface, in the slide's type scale (`themes/slide.css`), so it scales with the slide.
   - The strip is laid out whether the toggle of item 3 is on or off: with the toggle off its words are hidden and its room stays, so a slide is laid out and measured the same either way, in every pane and every window, and the store's one measure per deck and slide (`present.svelte.ts:400-404`) stays true. The Stage's measure counts the strip (the key hint alone stays out of it).
3. **The toggle.** A "Project facts" control in the toolbar (`Bar.svelte`), a pressed control as Overview is, drawn only while the slide the pane is on carries a project (with the Overview open, the slide it marks as current), and not for a plain deck or a deck whose slides carry none. It is on by default, and opening another deck in the pane keeps it (`leftDeck` carries it), since it is a setting of the pane. Its state is the pane's own, a field of `PresentState` read by `parsePresentState` as on when absent or of the wrong type, written with the pane's other state, so it is kept when the page comes back and two panes on one deck hold two toggles. The pane, the presenter screen (both slides) and the Overview's tiles draw the strip by the pane's toggle.
4. **`{{project.<field>}}`.** In a slide's text, front matter included, `{{project.<field>}}` is replaced by the reader, where `{{<group>.count}}` is replaced (`fileSlides`), by the words item 1 gives the field for the project of the deck whose file holds the slide, a list's words joined with ", ". The fields are the sixteen of item 1, named `form`, `stage`, `chips`, `domain`, `pillars`, `datasets`, `lead`, `supervisors`, `collaborators`, `year`, `venue`, `funding`, `compute`, `code`, `reproduced` and `tier`, and spaces inside the braces are allowed as they are for a count.
   - A field that holds no value for the project is replaced by nothing and raises a finding on the slide's file at the slide's line, naming the placeholder and the project.
   - A name that is not one of the sixteen, and any `{{project.<field>}}` in a deck that is no project's, stays as written and raises a finding the same way.
   - `{{project.count}}` is not a field: it stays the count of a group named `project`, as the count's fill gives it.
   - Field names are matched as written: `{{project.Venue}}` is an unknown name. A placeholder inside a code block is filled, as a count is.
   - A filled value is written so the slide draws its words as they are: a character Markdown or HTML would read (`*`, `_`, `<`, `&` and the like) is escaped.
   - The finding texts join the `findings.deck` group in `config/text/findings.yml`.
5. **The audience window and the PDF.** The audience window and the print page draw the strip by the toggle of the pane that presents or exports: the toggle travels with the kept list over the deck's channel, the `keep` message carrying it beside `keep`, the presenting pane saying it again whenever the toggle or the kept list changes (as `sendKeep` says the kept list again), and the exporting pane answering the print page with the toggle as it was at the press. `exportKeep` gives the print page both. While the kept list is not yet known (`sendKeep` sends nothing then), the toggle goes with it once it is. Each window draws the strip on every slide that carries a project, hidden as item 2 says when the toggle is off. A message of the old shape is not read in any special way: the shape is changed in one place for both halves.
6. **The help and the comments.** `docs/HELP.md`'s Present paragraph says what the strip shows and where, that the Project facts toggle in the toolbar turns it on and off for the pane and its presenter screen, audience window and PDF, and that `{{project.<field>}}` in a slide's text is filled from the project's manifest, with the sixteen field names. Every head comment and doc comment of the code the step changes says what it does after the step; among them, `present.ts`'s `messageShape` doc (`:672-688`), `answerPrint` (`export.ts:108-112`), `exportKeep` and `sendKeep` (`present.svelte.ts:262-266, 614-617`), `presentation.svelte.ts:1-7`, `model-deck.ts:139-140`, the `DeckProject` doc (`kinds.ts:24`), the server read's head and `deckProject` doc (`server/content/deck/read.ts:31-36, 45`), `deck-files.ts:90`, `data/index.ts:301`, `writes.ts:136-140` and `hooks.ts:137-141`.
7. **Splits.** `Present.svelte` is split by concern before a line is added to it, and a folder at ten items gets no eleventh: a new file goes into a folder named for what it holds, made by moving the files of one concern into it. Each moved file's importers and every comment naming its path are carried.
