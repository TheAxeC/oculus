## What to build

1. **Sizes read on the server.** A function beside `images` in `server/images.ts` reads a picture's width and height from its header bytes: PNG (the IHDR chunk), JPEG (the first start-of-frame marker, walking the segments, so a large EXIF block before it is read through), and WebP (VP8, VP8L and VP8X). It reads only as many bytes as the header needs, through a file handle, never the whole file. A JPEG whose EXIF orientation is 5, 6, 7 or 8 has its width and height swapped, since the browser draws it turned. A file whose header cannot be read gives no size. No new dependency.
2. **The listing carries them.** `GET /api/memories` answers `{ images: { name: string; width: number | null; height: number | null }[] }`, in the same order; `images(dir)` keeps returning names for the wallpaper.
3. **The client holds them.** `Wall.images` becomes that list of records; `hold` takes records.
4. **The tile takes the picture's shape.** A tile whose picture has a size sets its `aspect-ratio` to width over height from the answer, so its box has its final shape before the picture arrives and the picture fills it uncropped; a tile with no size keeps the 4:3 box with the picture fitted whole. A very tall or very wide picture is bounded (decide the bound, name it in the brief's report, keep the picture whole inside it). The loading placeholder, the failed tile's words, the enlarged overlay and the wallpaper and rice rules stay as they are.
5. **The comments** in `Memories.svelte`, `memories.svelte.ts`, `images.ts` and `memories.ts` that describe names without sizes follow the change.
