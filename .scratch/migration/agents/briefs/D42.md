## What to build

1. **Each commit row names its author, its date and its subject, and opens the change at the file's path in that commit.**
   - `fileLog` reads, for each commit, the hash, the short hash, the subject, the author's name and email, the author date and the committer date, and the file's path in that commit, in one `git log --follow -z --name-status --diff-merges=first-parent` form with `GIT_LITERAL_PATHSPECS=1` kept. The format's fields are unit separated (`%x1f`) and each commit's record opens with the record separator (`%x1e`), so the status lines that follow a format line stay in that commit's record; the newline git writes before the status lines is stripped before the block is handed to `parseNameStatus`.
   - Each commit carries `path`, the file's path in that commit (the new path of an `R` or `C` status line, the path of any other), and `from`, the path the commit started from (the old path of an `R` or `C` line, `path` otherwise). A commit with no status line (a merge whose first-parent diff does not name the file) takes as its `path` and its `from` the `from` of the newer commit above it in the list, or the path asked for when it is the first of the page.
   - The answer's type is a new `GitFileCommit` beside `GitCommit` in `model-sessions.ts` (exported through `data/model/index.ts`), `GitCommit` unchanged, since the `git` channel's `log` and `GitGraphCommit` carry it. Its parser is beside `parseLog` in `parse.ts`, reusing `parseNameStatus` for the status lines; paths are read from the NUL-ended output byte for byte, so a space, an accented letter or a tab in a name reads back as on disk.
   - The client's shape in `timeline-reads.ts` (`commitShape`) and `TimelineEntry`'s commit member (`timeline.ts`) carry the author, the email, both dates, `path` and `from`.
   - A commit row draws its subject as the label, the author as the row's muted detail, and how long ago at the row's right end (`TreeItem`'s `end` with `trailing`); a copy row draws its words and how long ago at the right end. The row's time and the order are the committer date (decision 3). The tooltip of a commit row is a new catalog line naming the author with the email, the date written out in full with how long ago, the subject and the short hash; a copy row keeps `files.timeline_row_title`, which is then used for copy rows only.
   - A press on a commit row opens `openDiff` with the path of that commit (`row.path`), so a commit made before a rename opens the file's change at its old path, and the rename commit opens the change from the old path to the new. The tab's label is `files.timeline_commit_diff` filled with the file's name in that commit (`nameOf(row.path)`) and the short hash.
2. **Fifty commits a page, and the rest on Load more (Z434).**
   - `GET /api/git?log=<repository>&path=<file>` answers the first page and `GET /api/git?log=<repository>&path=<path>&before=<hash>` the page after the commit `<hash>`, `<path>` being that commit's `from`; both answer `{ ok, commits, more }`. `fileLog` takes the cursor and runs `git log --follow ... -51 <hash>^ -- <path>` (`-51` with no cursor and no `<hash>^` for the first page), lists the first `FILE_LOG_ENTRIES` (50) and says `more: true` when the 51st came. A `before` that is absent reads the first page; a `before` that does not match `HASH` (`run.ts:88`) is refused with a 400 before git runs, so no value reaches git as an option. The `log` branch of `handleGitGet` answers `more` beside `commits`, and the route's head comment (`git-reads.ts:159-168`) names `before=`.
   - The Timeline draws a `Load more` row (a new catalog line) after the last row while `more` is true. A press on it, Enter on it, and the row coming into view at the end of the section's scroll each ask for the next page once, with the last commit read as the cursor; while that page is read the row says `files.timeline_reading` (`Reading...`), as VS Code's says `Loading...`, and asks nothing more. The pages are held in order and drawn as one list. A page answer that arrives after the followed file changed, after Refresh, or after the repository's `HEAD` moved is dropped, and only the current file's list is drawn. A page after the first that fails keeps the rows read and draws the commits failure line (item 7) in place of `Load more`; Refresh reads again from the first page.
   - Copies older than the oldest commit read are held back while more commits remain, so the list stays in time order; the last page draws them. With Git History unchecked (item 6) every copy is drawn, since no commit is read.
3. **The lists are read again when they change.**
   - The commits of a file are held under a key that names the repository's `HEAD`: the hash of `gitFor(repository).log[0]` with the branch (`GitState`, read through `selectors.gitFor`), so a commit, an amend, a checkout or a pull reads them again from the first page. The fileVersion part of the key goes.
   - The copies of a file are read again when a `files` message names the root the file is under (the message's `root` is the root's directory; `fs.roots()` maps it to the root key, `FsRoot = { key, dir, fixed }`), and every held copies read is marked on a version gap, as `src/lib/state/system/docs.svelte.ts:208-217` does; a message with `root: ''` marks none unless it is a version gap. The fileVersion part of that key goes too. The marking lives beside the reads (`fs-history.ts`), handed the entity store, so `fs.svelte.ts` stays under 880. `invalidate()` keeps marking both, under the `['fs']` prefix.
4. **The Timeline keeps the editor's file.** The file the Timeline shows is, in this order: the pinned file (item 6), the file selected in the tree, the file of the file tab activated last on the page while that tab is still open on the page. A tab that shows no file (the Files tab itself, a terminal) activated after it does not change it; that tab closed or moved to another page with no other file tab activated on this page since, the section says `files.timeline_no_file`. The followed file is state of the Timeline (the optional module of `state/sources/explorer/sections/`), not a DOM side effect.
5. **Open Timeline from the Files view and from the editor.**
   - A new layout call `showTimeline(path, root)` in `show-in-files.ts`, exposed by `layout.svelte.ts` beside `showInFiles`, does what `showInFiles` does and also asks the Files tab to open its Timeline section: the reveal ask carries `timeline: true` (`RevealAsk`, with its zod shape in `files-view.ts`). `revealSettled` adds `timeline` to `opened` for such an ask (a pure helper beside `sectionFlipped` in `section-state.ts`), with a row found and with none.
   - The scroll: `ShowPath.svelte`'s scroll effect (`:90-107`) runs once the ask is settled and the row is drawn. For an ask with `timeline: true` it selects and focuses the row as it does (`focus({ preventScroll: true })`) and, in place of the row's `scrollIntoView({ block: 'center' })`, scrolls the Timeline section's head of the same instance (`[data-instance="<owner>"] [data-fs-timeline]`) with `scrollIntoView({ block: 'start' })`, then writes `revealScrolled`.
