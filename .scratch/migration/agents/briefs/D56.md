# Brief: D56, the workbench: a page that belongs to one folder, and the VS Code themes as code themes

## The plan line and the rulings

The plan line (`plan.md`, D56): a page that belongs to one folder (`{root, path}`) of a project, a funding or education entry, a side project or any folder; opened from a project, from an entry page, from Show in Files and from the Files view's folder menu (Open in New Files), and switched to when it is already open; its left pane holds Files rooted at the folder, Search, Repositories, LaTeX and Problems limited to it, and the sessions whose working folder is inside it; its right pane is the documents pane, where the item's own page opens first and a picked session's Transcript and Timeline open; named by the item's name, else the folder's; listed under one Workbenches rail button that switches and closes; a closed workbench keeps its layout by its folder and restores it on the next open, with Reset layout in its menu; the Explorer page stays as it is; a unique view (D53) opened while a workbench holds it goes to that workbench, and a workbench layout restored with a unique view another page holds makes no copy of it; the Code theme menu and `code_theme:` also take the 19 VS Code themes of `src/lib/themes/vscode-rules.json` by their class names (`vscode-dark-2026` and so on), listed before Shiki's, so any UI theme can colour code as VS Code does.

Its authority: ruling Additions of 2026-10-09 (item 12, the workbench as proposed), ruling D53 before D56, and ruling 30 (open item 30 (a), the VS Code code themes, carried by D56). The shapes the line leaves open are ruled in Z756 (`plan.md` Rulings, self-rule): (a) the Workbenches button is a fixed button at the rail's foot beside Bookmarks, always drawn, with no `rail:` key; (b) the workbench page is made from a new `arrangements: workbench:` entry of `config/layout.yml`; (c) a closed workbench's layout is kept in the browser's saved layout beside the pages, by its folder. Z757 (`plan.md` Rulings, the orchestrator, automode) replaces Z756 (b) and rules the shapes the brief check found open; its parts (a) to (p) are quoted where they apply below.

## What to build

1. **The workbench page.** A page may belong to one folder: the page carries `folder: { root, path }` (a root key of the served roots and a path inside it, `''` for the root itself) and the item it was opened for, if any, and no `rail` key, so Reset all pages leaves it as it is (`resetPlan`, Z757 (k)). At most one open page belongs to a folder, compared by root key and path: opening a workbench for a folder that has one puts that page on screen and keeps its words, whichever opener (Z757 (n)). The page's words are the item's name when it was opened for an item (the project's title, the entry's title, the side project's title), else the folder's last name, and the root's key for the root itself, as a rooted Files tab is named (Z757 (m)). The page is made from the top-level `workbench:` key of `config/layout.yml` (item 2), with each tab given the folder (item 3). The Explorer page and every other rail page stay as they are. Naming (Z757 (b)): reader-facing text and the docs call the page "a workbench"; in code the page's field is `folder` and new identifiers say `folderPage` (`openFolderPage`, `FolderPage`), never a new identifier `workbench`, which already names a page's tree (`Page.workbench`), the shell (`shell/Workbench.svelte`) and the text group `workbench.*`; DESIGN.md says once, where it names the page, that a workbench is a page bound to a folder (`Page.folder`) and that the word otherwise keeps its two existing uses.
2. **The arrangement.** Add a top-level key `workbench:` to `config/layout.yml`, after `arrangements:`, in the shape of an arrangement and read by `parseArrangement` (Z757 (a)): a row split, the left pane one pane holding Files, Search, Repositories, LaTeX, Problems and the sessions list as tabs in that order, Files active (Z757 (c)), the right pane the documents pane (`view: []`). Its comment says it is the arrangement every workbench page is made from and Reset layout gives back. Because it is not a key of `arrangements:`, a `rail:` entry `page: workbench` stays refused as `page_unknown` and the Settings rail editor does not offer it, both as today. Add its entry to `config/catalogs/options.yml` under `layout.yml` (heading, section and help as the `arrangements` entry has them). G54's test gets a row for it (`tests/checks/config/arrangements.test.ts`: a row reading `workbench` beside the `it.each` over `arrangements`), which fails on the unchanged tree because the key is absent.
3. **Each tab limited to the folder.** When a workbench is made, each tab of the arrangement is given the folder in its own state: Files rooted at it (`top`); Search under it (`under`); Problems scoped to the root (`scope`) and to the path under it, through a new `under` field in its state that `problem-rows.ts` filters on (a row kept when its root is `scope` and its path is under `under`) (Z757 (d)); LaTeX in the existing folder-only shape `{ root, path, label }`, which names the folder's first main file and shows the view's no-root state when the folder holds none (Z757 (f)); Repositories listing the roots of the `git` channel that lie inside the folder and the one that holds it, so a hub project folder lists the hub's repository (Z757 (e)); the sessions list listing `sessionsForProject` of the folder's absolute path, the sessions working in it or filed into it by their area (Z757 (g)). Problems, Repositories and the sessions list draw the line Search draws, "In {0}/{1}" (`search.in_folder`), with its clear control, worded for each view in its own catalogue ("Show every root" and so on, with a tip), which takes the folder away in that tab only (Z757 (t)); a shared component may be lifted out of `Query.svelte` for it. For a workbench of a root itself (`path: ''`) Search, Problems and Repositories are limited to the root and draw no line, as Search does today; the sessions list draws the line with the root's key. A tab of these views opened anywhere else is unchanged.
4. **The documents pane.** When the workbench opens for an item, the item's own page opens first in the documents pane: the project view for a project, the entry view for a collection entry (a funding or education entry included), and for a side project its `project.yml` in a source tab, as its card's title opens it (`openManifest`, Z757 (p)). A workbench opened for a folder alone opens nothing there. A session picked in the workbench's sessions list opens its Transcript and Timeline in the documents pane of that workbench. New in that sessions list shows the composer in a Terminal tab opened in the documents pane, its working folder the workbench's folder, since the workbench has no Terminal tab of its own (Z757 (o)).
5. **The openers.** A workbench is opened, or switched to when open, from: the project card (`ProjectCard.svelte`, an action beside Show in Files, so the project view and the Projects board both offer it, Z757 (h)); the entry page (a toolbar action, when the entry has a folder); the collection card (`EntryCard.svelte`) and the Personal board's side project card (an action beside Show in Files); the folder block (`FolderFiles.svelte`); and the Files view's row menu on a folder, as the item "Open in New Files" placed beside Reveal. The venue card's Show in Files (a link that may name a file) and the Show in Files a worktree's opening makes are not given the action (Z757 (h)). Each action's words are in the text catalogue of its view, with a tip; `docs/files-and-search.md:43` lists the new row-menu item.
6. **The Workbenches button.** A fixed button in `RailFoot.svelte` beside Bookmarks (Z756 (a)), always drawn, with its glyph from `config/catalogs/glyphs.yml` and its words in the catalogue; the head comments of `RailFoot.svelte` and `ActivityRail.svelte:2-4` name it. It opens a menu (the `ui/` Menu primitive) listing the open workbenches by their words, the one on screen marked; a row shows that workbench's page; each row has a close control that closes that workbench through `closeAsk` (`navigation/pages.ts:143`), asking first about unsaved text and running terminals as closing a page asks (G28); the menu says so when no workbench is open. Workbench pages are not drawn among the rail's page buttons. The Pages view lists them as it lists every page; a workbench renamed there keeps the new words while it is open and is named afresh from its item or folder on the next open (Z757 (n)).
7. **A closed workbench keeps its layout.** Closing a workbench page keeps its arrangement in the saved layout by its folder (Z756 (c)): the envelope gains the kept workbench layouts beside `pages`, keyed by `root` and `path`. Opening a workbench for that folder again makes the page from the kept layout, the tabs and their states as they were, instead of from the arrangement; a Terminal tab comes back without the terminals its close ended, as a saved Terminal tab comes back after a reload. At most 20 kept layouts are held; closing a 21st drops the one closed longest ago (Z757 (l)); the report gives the envelope's size with 20 kept layouts, measured by a scratch run. A kept entry that does not read (a malformed tree) is dropped and the rest of the envelope is read, as a float that does not add up is dropped (Z757 (r)). The workbench page's menu (its row in the Workbenches menu and wherever Reset is offered for a rail page today) offers Reset layout (the plan line's words), which asks first as Reset of a rail page does (`workbench.reset_page_confirm` with the page's name, `navigation/pages.ts:285`) and then remakes the page from `workbench:` with the folder given to each tab and drops the kept layout (Z757 (j)). Reset all pages leaves workbench pages and the kept layouts as they are (Z757 (k)). `LAYOUT_VERSION` goes up by one; an envelope of version 6 or older is read in with every page and tab kept and no kept workbench, and G29's test (`layout-saved.test.ts:27-38`, one `it` over a version 3 envelope today) becomes a table under its existing title with a row for a version 6 envelope. G31's rule holds for the new part of the envelope: an envelope that does not read is never overwritten.
8. **Unique views.** A unique view (D53) opened while a workbench page holds it goes to that workbench, as for any page, through `showHeld`. A workbench made from `workbench:`, and one remade by Reset layout, takes each unique view it names in from its holder through `withPage` and `createClaims`, as every build from the config does (DESIGN.md:481) (Z757 (i)). A workbench restored from a kept layout leaves out each unique view another page or float holds and makes no copy of it, in the way `withoutHeld` leaves them out of a page made from the default. A kept layout is not a holder: a unique view in a closed workbench's kept layout is not held, and opening it opens it as any view opens.
9. **The VS Code themes as code themes.** `code_theme:` and the Settings view's Code theme menu (`code-theme-menu.ts`) also take the 19 VS Code themes of `src/lib/themes/vscode-rules.json` by their class names (`vscode-dark-2026` and so on), listed before Shiki's in the menu, in the dark and light groups the menu already has for Shiki's (Z757 (q)), each labelled as the UI theme menu labels that class from `appearance.yml` `themes:`, and by the class name when `themes:` no longer lists it. `codeThemeIds` itself returns the 19 classes before Shiki's ids, so `isCodeTheme`, the config write check (`config-sources.ts:49-50`) and the YAML schema (`engine.ts:63-64`) all accept them. A VS Code theme chosen as the code theme colours code in every editor that follows the code theme (the source tab, the diff and the merge editor) with that theme's rules, whatever the UI theme: `load.ts`'s `paintNow` takes a VS Code class as the code theme and paints with `ownRules` of that class instead of the body's classes. A name that is neither `tokens`, a VS Code class nor a Shiki id is still a finding, worded "neither tokens, a VS Code theme nor the id of a Shiki theme" in `findings.yml:33`, and G13's row at `config.test.ts:609` is made true with it. The comment of `code_theme:` (`config/appearance.yml:85`) and the `code_theme` help (`options.yml:146`) say so. Shiki's `dark-plus` and the other Shiki themes named after VS Code's stay listed beside the VS Code classes: they are Shiki's copies and differ from the shipped rules.
10. **The docs.** `docs/window.md` gains a section on workbenches (what one is, how it is opened, the Workbenches button, the kept layout and Reset layout, a unique view in a workbench); `docs/views.md` says what Files, Search, Problems, LaTeX, Repositories and the sessions list show when limited to a folder; `DESIGN.md` names the workbench page and the kept layouts in the layout model, with the naming sentence of item 1; `HELP.md` gets the workbench in its short list where pages are listed; `docs/files-and-search.md:43` gets Open in New Files. Every sentence the step makes false, found by grepping each changed name across `docs/`, `DESIGN.md`, `HELP.md`, `README.md`, the hub's `docs/DATA-MAP.md` and the head comments, is made true.
