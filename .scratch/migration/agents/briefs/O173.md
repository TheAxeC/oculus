## What to build

1. **A row of `audit.required_files` takes `tiers`.** `FILE_FIELDS` takes `tiers`, read as `wordBlock` without `flags` and `not_flags`, since a block drawn from a list whose words carry no flags takes none (`schemas/options.ts:174`), and `RequiredFile` gains `tiers?: WordBlock`. A `tiers` value not of that shape, a block naming flags included, is the problem `audit.required_files.<n>.tiers`, the row off and the other rows running, as for `stages`.
2. **The block is held against the project's tier as `stages` is against its stage.** `AuditRules` carries the merged config's `tiers:` map, set beside `stages`. In `projects.ts`, a function beside `stageMeets` answers whether a project's tier meets a block, no block placing no condition, using `blockHolds(block, wordList(project.tier), input.rules.tiers)`. `requiredFiles` skips a row whose `tiers` the project does not meet. A project of a tier `research_audit.skip_tiers` names stays held to no row, whatever the row names.
3. **The field and its help.** `config/options/behavior.yml`: the row's `help` names `tiers` among the keys a row may name, and the row gains the field `tiers`, `control: words`, `from: tiers`, with a `help` in the shape of `stages`' help saying what it is held against and what a project with no tier meets.
4. **The rows' description.** `docs/templates.md:291-294` names `tiers` and its condition, in the commented block's own style, with one example row among the rows at :306-307.
