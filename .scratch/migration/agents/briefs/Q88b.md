## What to build

1. **The rules of a file operation, once.** A new module `src/lib/data/file-ops.ts`, imported by the server and the page:
   - The name rule, VS Code's `validateFileName` (`fileActions.ts:714-770`) on macOS: a name that is empty or only whitespace is refused; trailing `/` and `\` are stripped; `/` and `\` both separate segments and empty segments are dropped (`a//b` is `a/b`); a leading `/` or `\` is refused; each segment that is `.` or `..`, holds `\0`, or is longer than 255 bytes is refused; leading or trailing whitespace in a segment is a warning, never a refusal. A refused name is `invalid_name`.
   - `freeName(name, taken)`, VS Code's simple increment (`incrementFileName`): `report.md` to `report copy.md`, then `report copy 2.md`; `notes` to `notes copy`; `.env` to `.env copy`.
   - The refusal words, a closed union: `outside`, `missing`, `root`, `protected`, `invalid_name`, `exists`, `into_itself`, `not_a_folder`, `denied`, `trash_failed`, `too_large`, `not_base64`, and the existing `token`, `not-an-action`.
   - `TEXT_LIMIT` (moved here from `state/sources/fs.ts:81`, re-exported there so its readers keep their import) and `MAX_UPLOAD_BYTES` (one constant: `server/content/memories.ts` and `state/life/memories.ts` import it instead of defining it, and `memories-message.test.ts:74` keeps passing).
   - `data/file-ops` joins the state row of `tests/checks/tree/boundaries.test.ts` and `DESIGN.md:171`.
2. **The file operations on the server.** A new module `src/lib/server/files/fs/ops.ts`, its route `src/routes/api/(files)/ops/+server.ts`: `POST /api/ops`, token-checked through `tokenedBody` as `/api/fs` is, the body read through a module-level zod shape (`DESIGN.md:148`, which then names the route), each operation run behind a write chain of its own (`opsWrites` on the `ServerContext`, beside `fsWrites`), so a long copy does not hold the workspace, bookmark and note writes. Every path is a root key and a path under it. A path that is a symbolic link is acted on as the link: its parent folder is resolved and its own name kept, never its target. After the name is applied, the final parent folder is resolved by real path and must lie inside the root (`outside` otherwise), so no segment walks out.
   - `create`: `{ op, root, path, name, folder }`: a new empty file or folder `name` in the folder `path`; a name with several segments creates the folders between. Answers `{ ok: true, path }`.
   - `rename`: `{ op, root, path, name }`: the item renamed in its folder (a several-segment name moves it into the folders it names, created as needed; into its own subtree is `into_itself`). A name differing from the old only in letter case renames on a case-insensitive volume.
   - `trash`: `{ op, root, paths }`: duplicates and paths inside another listed path dropped, then each item moved to the Trash by its own call to `trash(path, { glob: false })`, in order. A call that fails stops there: the answer is `{ ok: false, error: 'trash_failed', done, failed }`, the items before it trashed. As VS Code does, any trash failure asks to delete permanently.
   - `delete`: `{ op, root, paths }`: each item removed for good (`rm` recursive); the page sends it only after `trash_failed` and the reader's yes.
   - `paste`: `{ op, mode: 'copy' | 'move', items: [{ root, path }], root, path, replace }`: each item copied or moved into the folder `path`, across roots allowed. A copy onto a taken name takes `freeName`. A move onto a taken name is refused `exists` unless `replace`, when the taken item goes to the Trash first (its failure is `trash_failed`). A move into the folder it is in does nothing. A folder pasted, by copy or move, into itself or a folder under it is refused `into_itself` (`fileActions.ts:1191-1193`). A move across volumes is a copy then a removal. A copy keeps a symbolic link a link with its target string as written (`verbatimSymlinks`), so a relative link copied into another folder points where that string leads from there. Items run in order; one that fails stops there, answered `{ ok: false, error, done, failed }`. A source that is gone is `missing`.
   - `upload`: `{ op, root, path, name, data, replace }`: one file's bytes (`data`, base64; not base64 is `not_base64`) written into the folder `path` as `name`, a single segment (a `/` or `\` is `invalid_name`), an empty file accepted. A taken name is `exists` unless `replace`; with `replace` a taken file goes to the Trash first and a fresh file is written (never written through a link), and a taken folder is `not_a_folder`. A body over the cap is refused by the parser; the page checks `MAX_UPLOAD_BYTES` first and says `too_large`.
   - The order of the refusals: `token`, `not-an-action`, `outside` (a root key not served, or a path out of it), `missing` (a root whose folder is gone, or a source not there), `root` (the root's own folder as the item of a rename, move, trash or delete), `protected`, `invalid_name`, `exists`, `into_itself`, `not_a_folder` (a target folder that is a file, `create` with `a.md/b.md` where `a.md` is a file), then what the system answers: `EACCES`, `EPERM`, `EROFS` are `denied`, `ENAMETOOLONG` is `invalid_name`.
   - `protected`: any operation that would rename, move, trash, delete, overwrite or copy the engine's `config/local.yml`, or a folder holding it (`engine:''` after `root`, `hub:tools/oculus`, `hub:tools/oculus/config`), compared by real path so every route to it is refused. A symbolic link that points at it is a link and acted on as one. The compare reads it like the source tab does and is not refused (Decision 9).
   - The trash call is a parameter of the entry point (`trash?: typeof trash`, the library when absent), called with `{ glob: false }`, so a route test hands in a spy and moves nothing to the real Trash.
   - Not recorded in the change log (Decision 1).
