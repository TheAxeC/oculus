# Brief: O14d, rail groups and the generic collection view

Read `../spec.md` first; it governs this package unchanged. `DESIGN.md` sections that bind this package: "Layer 3, view" (the shell knows no view; views register themselves), "Configuration", "The wire model" under Decisions (collections carry their entries inline), and the 2026-09-10 decision "the rail draws a large `nav_groups` group as one button with a flyout, so it does not grow one icon per view". Read those sections only.

## What to build

- The rail (`src/lib/shell/ActivityRail.svelte`): `arrange()` keeps its grouping; the drawing changes: a section whose group holds more than four registered views is drawn as one button with the group's label as its tooltip and a `Menu` flyout (O8's `Menu`, `compact`, opening beside the rail as the theme menu does) listing the views with their glyphs and labels; a smaller section stays as buttons under its heading. A flyout pick does what a button click does (`openView`, shift for the panel). The groups are `nav_groups` from the merged config (`config/layout.yml` lines 12 to 19: `collections` with Portfolio, Academic life, Reference; `more` with Personal, System), whose keys must be view ids: the config's keys are renamed to the ids this package registers (`statements`, `events`, `education`, `applications`, `collaborations`, `tasks`, `code` for the collections; `funding`, `venues`, `data`, `programs`, `domains`, `map` stay as they are for the views O24 and O25 add; the `more` groups stay for O28's views). A "Sessions" group with the six session views of O14 is added under a new top-level key of `nav_groups`, `sessions`.
- `src/lib/views/Collection.svelte` (registered once per entry of `sources.yml` `collections:` whose key is not a registry the snapshot carries, so `funding` is left to O24; the registration id is the collection key, the label its `title`, the glyph a name in `glyphs.yml` chosen per key and listed in the report): a `Pane` with the collection's `title` and `intro` from `entities.collections[key]` (O4's `Collection`: `meta` and `entries` inline), a `Search` over every string field, a status facet `Menu` when the schema has a `status` field, and the entries as `Card`s: the title, `sub` under it, a status `Chip` in `statusTone(status)`, the `date`, `deadline` and `kind` fields as text, `tags` and `related` as outline chips, `meta` (the `metalist` type: a list of `{ label, value }` pairs, read from the file's own entries) as label-value chips, `note`, `statement`, `link` and `url` as the body, in the order the file's `schema:` lists its fields; a field the schema names and the entry lacks is skipped. The fields are read through the schema, not hard-coded, so a new field in a file shows without a code change; the seven files' schemas use the types `text`, `select`, `tags`, `textarea`, `date`, `metalist` and nothing else (counted 2026-09-10).
- `src/routes/views.ts` registers the collections from the config at startup: the page has the merged config as data (`+page.server.ts` ships `vocab`; it ships `collections` from the config as well), and `views.ts` registers one `Collection` per entry with `state: { key }` bound at registration (the registry gains an optional `props` on a registration, passed to the component beside `instance`).
- `config/text.yml`: `views.collection_glyph_<key>` for the seven, `collection.search`, `collection.status`, `collection.empty`.
