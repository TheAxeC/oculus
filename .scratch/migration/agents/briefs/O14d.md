# Brief: O14d, rail groups and the generic collection view

Read `../spec.md` first; it governs this package unchanged. `DESIGN.md` sections that bind this package: "Layer 3, view" (the shell knows no view; views register themselves), "Configuration", "The wire model" under Decisions (collections carry their entries inline), and the 2026-09-10 decision "the rail draws a large `nav_groups` group as one button with a flyout, so it does not grow one icon per view". Read those sections only.

## What to build

- The rail (`src/lib/shell/ActivityRail.svelte`): `arrange()` keeps its grouping and its order (a group's views in the group's own key order, done 2026-09-11); the drawing changes: a section whose group holds more than four registered views is drawn as one button carrying the group's glyph (`nav_groups` entries gain an optional `glyph`, a name in `glyphs.yml`; without one the first view's glyph is drawn) with the group's label as its tooltip and a `Menu` flyout (O8's `Menu`, `compact`, opening beside the rail exactly as the theme menu at the foot does, so the same fixed placement holds) listing the views with their glyphs and labels; a smaller section stays as buttons under its heading, as today. A flyout pick does what a button click does (`openView`, shift for the panel). The groups today (`config/layout.yml` lines 12 to 27): `boards` (Boards), `sessions` (Sessions, six views, the first flyout), `collections` (Academic life, Reference; no view yet before this package), `more` (Personal, System). The keys already name view ids; this package renames nothing in `nav_groups` and adds nothing to it: the seven collection ids it registers (`statements`, `events`, `education`, `applications`, `collaborations`, `tasks`, `code`) are already in the Academic life and Reference groups.
- `src/lib/data/model.ts` and `src/lib/data/normalise.ts`: the wire `Collection` gains `schema?: SchemaField[]` with `SchemaField = { field: string; type: string; label?: string; options?: string[]; required?: boolean; help?: string }`, copied from the file's `meta.schema` where the normaliser builds a `Collection` (search `entries` in `normalise.ts`); a `schema` that is not a list of such maps is left off and reported as a finding through the normaliser's existing finding path. The snapshot is what the page reads, so no new fetch.
- `src/lib/views/Collection.svelte`: one component registered seven times, once per entry of `sources.yml` `collections:` whose key is not a registry the snapshot carries (`funding` is left to O24); the component reads which collection it is from `instance.view`, exactly as `Projects.svelte` reads its board from the view id. Registration: `src/routes/views.ts` exports `registerCollections(keys: string[])`, called by `src/routes/+page.svelte` in its script body (before the first render; the registry is a module map and a repeated registration keeps the id's position) with the keys the page data carries: `+page.server.ts` ships `collections` (the keys of the config's `collections:` list, in order, minus those naming a registry) beside `vocab`, and `+page.ts` passes it on. Each registration is `{ id: key, label: 'views.<key>', glyph: 'views.<key>_glyph' }`, so `tests/views/registry.test.ts`'s rule that every label and glyph resolves holds. The view: a `Pane` with the collection's `title` and `intro` from `entities.collections[key]`, a `Search` over every string field, a status facet `Menu` when the schema has a `status` field (values from the entries, offered only when at least two occur, the board's rule), and the entries as `Card`s: the title, `sub` under it, a status `Chip` in `statusTone(status)`, the `date`, `deadline` and `kind` fields as text, `tags` and `related` as outline chips, `meta` (type `metalist`: a list of `{ label, value }` pairs) as label-value chips, `note`, `statement`, `link` and `url` as the body (`link` and `url` as anchors opening in a new tab), in the order the file's `schema:` lists its fields; a field the schema names and the entry lacks is skipped; a field the entry has and the schema does not name is drawn last as text. The seven files' schemas use the types `text`, `select`, `tags`, `textarea`, `date`, `metalist` and nothing else (counted 2026-09-10); an unknown type is drawn as text.
- `config/text.yml`: `views.<key>` and `views.<key>_glyph` for the seven (the label is the collection's own title from `sources.yml`, the glyph a name in `glyphs.yml` chosen per key and listed in the report), `collection.search`, `collection.status`, `collection.empty`, `collection.toolbar`.
