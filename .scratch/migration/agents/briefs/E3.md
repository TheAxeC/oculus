## What to build

1. **The store leaves the row (Z106 (1)).** In line 264, the row loses `store` and gains `storeBytes` and `storeVersion` beside `storeFile`: `storeBytes` is the size of the store file in bytes, 0 when it is absent; `storeVersion` is the first 16 hex characters of the SHA-256 of the file's bytes, and the empty string when the file is absent. A store path that is a folder or cannot be read counts as absent (0 and the empty string). A file over `apps.store_max_kb` is not hashed whole: its version is the first 16 hex characters of the SHA-256 of the text `<size>:<modification time in ms>`, so a hand-placed large file costs the watcher one stat. An empty file (0 bytes) is present: `storeBytes: 0`, version `e3b0c44298fc1c14`, value `null` since it does not parse. The sentence defining `store` is replaced by one defining these two. Say why in one clause: a channel publish sends the whole payload to every subscriber (`src/lib/server/core/channels.ts:103-110`), so a store value in the row would be sent to every page on every store write of any app. The same line's reread list ("the manifest, the walk ..., the content hash, whether the approvals file holds it ..., and the store") ends with "the store file's size and version (read, not parsed)". A KB in this section is 1024 bytes; say so once, where `apps.store_max_kb` is defined (line 311).
2. **The store route (Z106 (1)).** Add to "What an app keeps" (line 311): the page reads one app's store with `GET /api/app-store?view=<view id>`, which answers `{ version, value }`, `value` being the parsed store, `null` when the file is absent, does not parse or is over `apps.store_max_kb`, and `version` the file's `storeVersion` at the read. The route answers any row the watcher holds, approved or not, since only the page calls it. An id no held row names, a built-in view's id among them, answers 404. A `view` absent, empty or given twice answers 400. The page sends the view id through `encodeURIComponent`, and the route compares the decoded value with the held rows' view ids. The route answers GET only (any other method 405) and writes nothing: the section always writes it in full as `GET /api/app-store`, never as bare `app-store`, and says in one clause that it is not one of the write routes, so the count of thirteen at line 313 is unchanged. The route is under `/api/`, so the origin rule and `refused()` apply and the frame cannot call it (its opaque origin fails `sameOrigin`, as line 282 says); only the page calls it. The page's rules, each stated: `getStore()` answers from the value the page holds, and when the page holds none for that app it fetches once, two tabs asking at once sharing that one fetch. A push of `apps` whose `storeVersion` for an app differs from the version the page holds makes the page fetch once per loaded oculus page, whatever the number of tabs; a floating pane and a popped-out window drawn by the same page share that fetch. An app with no mounted frame in the page is not fetched until a frame mounts. At most one fetch per app is in flight per page; when it settles and the latest pushed version differs from the answered one, the page fetches once more; an answer from a superseded request is dropped, and versions are never ordered by comparing them. The page holds the version the GET answered, not the pushed one, and a later push carrying that version fetches nothing. After a fetch the page calls `onStore(value)` in every tab of the app; a tab closed or a frame destroyed while the fetch is in flight gets no call, the answer is kept, and a frame mounted later gets it through `getStore()`. A 404 (the app removed or refused since the push) leaves the page holding nothing for the app and calls nothing, and a `getStore()` waiting on it rejects `missing` (line 307's word). The store write compares the value sent with the parsed value the file holds; when they are equal it writes nothing, records nothing in History and answers success, so the bytes and the version stay as they are, whatever the file's formatting, and the section's "changes nothing and calls nothing" holds. The paragraph's other sentences that read the store from the row are corrected to this.
3. **The first frame (Z106 (1)).** Line 266 keeps `apps: { rows, findings, folders, version }`; with item 1 the rows carry no store values, so the first frame carries none; say so in one clause. A tab reads its store when it mounts, through `getStore()`.
4. **`engine`, the engine's config folder and `closed_paths` (Z103 (b), Z107 (b2)).** In line 315, a machine app may name any root shown in the file browser except `engine` in `file`, and `engine` rejects `closed` for every app. A file whose real path lies inside the real path of the engine's config folder rejects `closed` for every app, whichever root names it, so `hub` + `tools/oculus/config/local.yml` rejects `closed` as `engine` + `local.yml` does, and so does a root that `sources.yml` or a saved workspace gives another key for that folder. A file whose path under its root, given or real, starts with a folder the list `closed_paths` names rejects `closed` for every app; `closed_paths` is a new key of the `apps:` block in `config/behavior.yml`, a list of folder paths each relative to a root and applied to every root, compared segment by segment, default `[secrets]`. Add it to line 327's list of the block's keys, with its default, in the section's form. The section says why in one clause each: `local.yml` holds the machine's private settings, and a root can hold a tracked credential folder that no dot marks. A root the file browser does not show still rejects `missing` for a machine app. Keys compare exactly: `Engine` is not `engine`, and `game-engine` is an ordinary root.
5. **Path segments (Z106 (2)).** In line 315, a `file` whose `path` breaks the whole segment rule of line 284 rejects `closed` for every app, machine app and root app alike: a segment that is empty, `.`, `..` or dot-led, or a backslash or NUL anywhere. So `.env`, `.ssh/id_ed25519`, `.oculus/approvals.json`, `a/.git/config`, `a//b`, `/etc/hosts` (its leading empty segment), `a/./b` and an empty path each reject `closed`. The rule is checked on the exact string the app passed; `open` takes a string over the bridge and decodes nothing, so `%2Eenv` is a literal name that does not start with a dot, and the page passes the path URL-encoded to the source route, which decodes it back to the checked string. The rule is also applied to the part of the file's real path under the root's real path, so a link inside a root that points at a dot folder (`creds -> .secrets`, opened as `creds/key`) rejects `closed`, and a link whose target lies outside the root rejects `closed`, whether or not the target exists. The order of the checks is stated: the segment rule and `closed_paths` on the given path, then `engine`, then whether the root is shown (`missing`), then the real-path checks (outside the root, inside the engine's config folder, the segment rule and `closed_paths` on the part under the root), each `closed`, then existence (`missing`), so the answer to a hidden path never depends on the disk or the roots. A dot inside a segment (`notes.v2.md`) is not dot-led.
6. **`wss:` (Z106 (3)).** In line 260, `wss:` stays refused in `connects`, and the reason "since `connect-src https://host` does not admit it" is removed: the sentence says only that a `wss:` origin is refused. In line 325, the measurements the build step makes in Chrome are three: WebRTC, DNS prefetch, and whether `connect-src https://host` admits `wss://host`; this section then states them. Line 262's `connect_shape` text is kept as it is.
7. **Everything the above makes false in the section.** Read lines 236 to 327 whole and correct every other sentence that states the store rides in the row or in the push, that a machine app may name `engine`, or that `connect-src https://host` does not admit `wss:`. Nothing outside lines 236 to 327 of DESIGN.md changes.

The report gives, under "E2's rows as they now read", the new text of rows 18, 23, 32, 36 and 42 in the table's form (`| <n> | <shape as written (line)> | <alternative considered> |`), with the line numbers of the section after this step; the orchestrator carries them into `E2-report.md` at landing. Row 18: the row carries `storeBytes` and `storeVersion`, the store read by `GET /api/app-store`; alternative: the store value in every row. Row 23: `open` of a path that breaks the segment rule rejects `closed` before anything is looked for, `engine` rejects `closed`, a root the file browser does not show and a file that does not exist reject `missing`, in that order; alternative: `missing` for every file not found, hidden ones included.
