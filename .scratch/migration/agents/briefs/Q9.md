# Brief: Q9, the source editor, the edit-source bars, the lead dismiss

Read `../spec.md` first; it governs this package unchanged. Axel ruled on 2026-09-12 at 20:15 that items 9 and 17 of the parity audit are ported as the cockpit has them. Read against the cockpit's source on 2026-09-12 at 23:40, item 9 is not a lead "mute" (that is the Audit tab's, O28): the cockpit's lead control is a per-browser "Not interested" hide with a show-or-hide-dismissed toggle. Item 17 (editing a LinkedIn idea in place) is the cockpit's in-page raw editor, which it also offers on other tabs as an "edit source" bar. This package ports the editor, the bars the cockpit draws on tabs oculus has, and the lead dismiss.

## How each item lives in oculus (the three layers, the data live)

1. **The source editor.** Data: the file's text arrives through the existing file route (`api/file/<root>/<path>`, `server/files.ts` `serveFile`, the same-origin and inside-root checks). Server: a new `POST /api/source` `{ root, path, content }` (`server/source.ts`, `src/routes/api/source/+server.ts`): the write token as `server/writes.ts` checks it, the same-origin check, the path resolved under the named root the way `serveFile` resolves it (403 outside), the extension in an editable list (403 otherwise), the file written whole with the atomic write `sessions/json.ts` uses, `{ ok: true }` or `{ ok: false, error }` as the write route answers. The cockpit's editable set is a literal in `serve.py` line 39 (`.md .yml .yaml .tex .bib .txt`) and its viewable set adds `.py .sh .slurm .json .csv .r .m .cpp .h` and more (line 41); in oculus both become config, `editable_extensions` and `viewable_extensions` in `config/behavior.yml`, named here. Live: a saved file that the watcher covers (a feed, a collection, a manifest, a config file, the LinkedIn folder after F1) republishes on its channel as any edit on disk does; the editor holds the page's own text while it is open and shows the catalog's saved and failed words. View: a `source` view (`listed: false`, one instance per root and path through `stateId` as `document` is, the tab labelled with the file's name): the cockpit's editor (`assets/js/cockpit/03-filters.js` `openEditor`, lines 176 to 198): a textarea over a highlight mirror that scrolls with it, the language by extension (`yml`, `md`, else plain; the cockpit's small highlighter at lines 199 to 241, ported as a pure `state/highlight.ts` with tests, its token classes coloured from the `--code-*` tokens O27a adds, or from the theme's existing tokens until then; O27a's highlight.js is for read-only code windows and is not used here), Save and Cancel (`js.filters.edit`, `filters.saving`, `filters.saved`, `filters.save_failed`, `filters.failed`, `filters.cannot_open`, `common.x_prefix`), a read-only mode for a viewable but not editable extension (the cockpit's `ro`, no Save). Every control a `ui/` primitive; the textarea is `ui/TextArea.svelte`.
2. **The edit-source bars.** The cockpit draws `editbar(rels)` (`render/helpers.py` lines 143 to 147: `helpers.edit_source` with one link per file) on the Lit Watch tab over `feeds/radar.yml` (`surfaces.py` line 385), on the document tabs and Help (O28's, not here) and on the Config tab (O28's). Here: the Lit Watch view draws the bar over its feed file opening the source view; the LinkedIn view's edit action (`sf.linkedin_edit`, today opening the read-only document tab, O25e) opens the source view on the post's file with the LinkedIn root (`config/sources.yml` `linkedin_dir` served as a root the way the hub is; say how the root is named in `roots()`); the Inbox and Position Leads views draw the same bar over their files (the cockpit's `_radar_acts` tabs share the pattern; if the cockpit draws no bar on those two, the report says so and they draw none).
3. **The lead dismiss.** The cockpit (`05-leads.js` lines 168 to 190, `surfaces.py` line 264 and the `leadhide` button of `02-focus.css` line 59): an x on each lead card marks it "not interested"; dismissed ids live in the browser's storage under one key; dismissed cards are hidden unless the toggle `js.leads.show_dismissed` (with the count) is on, which then reads `js.leads.hide_dismissed`; the x on a shown dismissed card restores it. In oculus: the dismissed ids in the ui store (`state/ui.svelte.ts`, per browser as the cockpit's storage is; a `leadsDismissed: string[]` beside the appearance fields, or in the Leads instance state if Axel prefers per-tab, the brief takes the store), the card's hide control (`ui/ToolButton`, the cockpit's x with `sf.leads_hide_tip` if the catalog has it, else `js.leads.hide` or the nearest existing key, named in the report), the toggle in the view's toolbar, the split in `state/leads.ts` (pure: `visibleLeads(entries, dismissed, showing)`).

## Decisions taken in this brief (each reversible, none silent)

1. `POST /api/source` and the two config lists are the user-visible shapes; both are named above.
2. The editor is a tab, not a modal: oculus has no modal layer and DESIGN.md's one definition per screen puts it in a pane like every view.
3. A file the watcher does not cover (a project README) still saves; nothing republishes, and the document tab showing it reloads only when reopened, which the report says.
4. Dismissed leads are per browser, as the cockpit's.
