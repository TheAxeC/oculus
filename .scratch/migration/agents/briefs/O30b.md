## What to build

1. **The app's build writes into folders of its own.** `buildServer` runs `vite build --mode app`. `vite.config.ts` becomes a function of the mode (`defineConfig(({ mode }) => ...)`). Under the mode `app`, SvelteKit's output folder is `.svelte-kit-app` and the adapter writes to `build-app`. Under every other mode the folders are `.svelte-kit` and `build`. The adapter's `out` is given to the adapter where it is made: `oculusViteServer` takes it as an option and passes it to `adapter({ out })`. The SvelteKit output folder is set through the option the installed `@sveltejs/kit` version's `sveltekit()` takes for it. The builder reads that version's types in `node_modules/@sveltejs/kit` and the report names the option and the file it was read from. No environment variable carries either name, under the spec's rule against them. The content of the `test` block (:30-71) is left as it is, and the report says whether its lines are byte for byte those of the base (see "Shared paths").
2. **The app's build reads nothing under `.svelte-kit/`.** Under the mode `app` the build reads no file under `.svelte-kit/` and prints no tsconfig warning, so it never reads a file `npm run check` or `npm run build` writes. The mechanism is read from the installed kit (`write_tsconfig.js`, the `sveltekit()` options) and Vite (how it resolves the tsconfig a build reads), and the report names it with the file and lines it was read from. `tsconfig.json` is written only if the mechanism needs it, and `npm run check` keeps working with the tsconfig the step leaves.
3. **The server is told where its handler is.** `parseEngineArgs` reads a third flag, `--handler <file>`, also written `--handler=<file>`, resolved against the working directory as `--engine` is; given twice, the last is taken, as for the other two flags. Each wrong form is refused before the build is loaded, with a literal sentence in the existing style: an empty value, a value starting with `--`, and a value that names no file (a missing path, or a directory), the last naming the resolved path. `ArgsReader` gains what the parse needs to tell a file from a directory or a missing path, and both callers (`src/server.ts:26-30` and `src/desktop/app.ts:80-84`) supply it. `src/server.ts` loads the handler from the flag's file when it is given, and from `../build/handler.js` when it is not, so `node src/server.ts` over `npm run build` serves that build. A handler file that fails to import (from the flag or from `../build/`) prints the catalog line `server.start.handler_failed` with the file's path and the error's message, and the process exits 1. `forkServer` passes `--handler <checkout>/build-app/handler.js`.
4. **The app refuses `--handler`.** The app chooses its handler, so `parseAppArgs` refuses `--handler` as it refuses `--default-port`: `--handler` joins `OWN_FLAGS`, so its value is not read as a positional argument, and the parse answers with the same form of sentence as `:36`, naming `--handler`. The head comment (:1-5) names `--handler` among the server's flags the app refuses.
5. **The start checks the app's own folder.** `app.ts` checks `build-app/handler.js` where it checked `build/handler.js`, in a packaged app as in a start from the checkout, since a packaged app runs the handler the checkout's last `npm run app` built. `desktop.dialog.not_built` says: "The oculus server is not built. Run npm run app from the checkout once, then start the app again."
