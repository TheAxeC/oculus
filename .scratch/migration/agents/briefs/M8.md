## What to build

1. **The schema formats, one vocabulary.**
   - Every hub `schema:` block, `manifest-schema.yml`, `options.yml` and the new schemas use `from:` for a reference, `options:` for allowed values, `help:` for the help line and `when:` for a condition. `options_from`, `values_from`, `values` and `description` are renamed in the files and in every reader listed under "What is on the tree", the apps API's `optionsFrom` included (`model-collections.ts:37`, `fs.svelte.ts:209`, `collection.ts`, `docs/apps.md:247`), the cockpit's `page.py:706-709`, the migration template `migrate-joint-work.mjs:273` and `demo/network/joint-work.yml:11`.
   - `from:` takes a registry name (`venues`, `datasets`, `pillars`, `domains`, `funding`, `people`, `organisations`, `resources`), `projects`, or `vocab.<key>`; for `options.yml` the existing `SOURCES` names of `catalog/options.ts:76-95` stay valid. A `from:` naming none of these, or a `when:` naming an undeclared field, is a finding on the schema's own file.
   - `when:` is a map of field to a value or a list of values, all of which must hold for the field to be allowed; `required: { when: ... }` makes a field required under a condition; `when: { path: <glob> }` is a tier or folder condition matched with `node:path`'s `matchesGlob`.
   - A help line on every field of every schema: the 87 hub fields that lack one get one, written as the field's meaning in one plain sentence, and the three false help lines (`venues.yml:27`, `data.yml:28`, `data.yml:32`) are corrected.
2. **New schemas.**
   - `registries/career.yml` and `feeds/literature-radar.yml` get their own `schema:` block, career's sections as a nested field form (a field of type `metalist` with its own `fields:`).
   - A new folder `config/schemas/` holds `manifest-schema.yml` (moved from `config/catalogs/`, with every reader of its path: the catalog merge `merge.ts:18`, `config-folder.test.ts:176`, `docs/configuration.md:19`), `side-project-schema.yml` (the side projects' `project.yml`, hub and `.oculus/`), `deck-schema.yml` (the deck `present.yml` files) and `cpp-schema.yml` (`.oculus/cpp.yml`) and `commands-schema.yml` (`.oculus/commands.yml`), each written from its reader in the tree so the schema accepts exactly what the reader accepts.
   - oculus's own catalogs (`config/catalogs/*.yml`) and text files (`config/text/**`) get JSON Schemas generated from their zod readers with zod 4's `toJSONSchema`, matched by path.
3. **The generator** (new modules under `src/lib/data/snapshot/` or a new folder beside it, under the folder limit). It turns each schema into a JSON Schema: the fields, their types (`date` as a `pattern` from `ISO_DATE` of `writes/entries.ts`), the allowed values, each `from:` as an `enum` of the referenced file's keys as they are on disk (the registries' identity fields of `SHAPES`, `keptResources`, the manifest ids, the vocab lists), each `when:` as `if`/`then`, `additionalProperties: false` with the fields oculus itself writes into collection entries (`snooze`, `subtasks`) added to every collection's entry schema with a catalog help line, and the help line as `description`. It maps each schema to its files by path globs (the 16 hub files, `projects/**/project.yml`, `side-projects/*/project.yml` and `.oculus/project.yml` in every root, every deck `present.yml` outside `tools/` and outside `config/text/`, `tools/oculus/config/*.yml` other than `local.yml` to `options.yml`'s sections, the catalogs and text files to their zod schemas). A file matched by no schema gets none.
4. **yaml-language-server in the editor** (Z682 (8): one entry, one facts entry, one adapter).
   - `package.json` adds `yaml-language-server` 1.24.0 and `ajv` 8.20.0 exactly in `dependencies`.
   - `lsp-servers.ts` gains the `yaml` entry (language `yaml`, words `statusbar.server_yaml`, `source.cmd_yaml_restart`, `source.cmd_yaml_output`, no choices, no extras, `approvedBy: null`, `formatOnType: false`).

   - The server starts for every `.yml` and `.yaml` tab of a served root (Z701 (2)), never for `config/local.yml` (G3).
   - Its `yaml` configuration answer: `schemas` (each generated schema's URI to its globs, for that root), `validate: true`, `hover: true`, `completion: true`, `schemaStore: { enable: false }`, `kubernetesCRDStore: { enable: false }`, `hoverSchemaSource: false`, `format: { enable: false }`. After `initialized` the client sends `yaml/registerContentRequest`, and a `vscode/content` request is refused, so no schema is fetched from the network; a `file:` modeline's schema is read by the server from disk, which the report states.
   - The schemas are served from memory under a custom scheme: `ServerEntry` gains an optional member that answers a server's own requests by method (`custom/schema/content`), read in `held.ts`'s `answer()` before the relay's default, so no language branch is added anywhere.
   - When a referenced file or a schema file changes, the relay sends `workspace/didChangeConfiguration` through the reconfigure path of `choices.ts`, so the enums follow the disk without a restart.
   - `server/machine/lsp/` holds 10 items: the adapters are regrouped into `server/machine/lsp/adapters/` (`pyright/`, `clangd/`, `web/`, `yaml/`), and `servers.ts:8`'s "a folder of its own beside this file" is reworded.

## Decisions taken in this brief (each reversible, none silent)

1. The schema URIs are `oculus-schema:/<name>.json`, answered from memory through the new entry member; nothing is written to disk for them.
2. The ajv validators are compiled once per snapshot build, keyed by the generated schema's text.
3. Dates are a `pattern` from `ISO_DATE`; ajv-formats is not added.
4. Globs use `node:path`'s `matchesGlob`; picomatch is not added.
5. JSON Schema types come from ajv's exported `SchemaObject`; `@types/json-schema` is not added.
6. yaml-language-server's diagnostic and hover texts reach the editor as the server writes them, as pyright's and clangd's do; the Findings rows use catalog sentences.

Five real cases of the vocabulary change, each input and its output under the decision:
1. `registries/venues.yml:18` `- { field: category, type: select, options_from: venue_categories, help: "..." }` becomes `- { field: category, type: select, from: vocab.venue_categories, help: "The kind of venue: a journal, a conference, a thesis or a meeting." }`.
2. `network/joint-work.yml:11` `- { field: person, type: select, options_from: people, required: true, help: "a registries/people.yml key" }` becomes `- { field: person, type: select, from: people, required: true, help: "The person's key in registries/people.yml." }`.
3. `network/events.yml:8` `- { field: role, type: select, options: [present, attend], ... }` becomes `- { field: role, type: select, options: [present, co-present, attend], required: true, help: "..." }` with `- { field: link, ..., required: { when: { role: present } } }`.
4. `config/catalogs/manifest-schema.yml:41` `venue_id: { label: "Venue", type: select, from: venues, section: Core }` keeps its `from: venues` and gains `help:`, in `config/schemas/manifest-schema.yml`.
