## The acceptance list

1. **The three document tabs.** `config/layout.yml` gains a `docs:` list, each `{ label, path, group }` with the path relative to the hub (`RESEARCH-APPROACH.md` and `AGENT-APPROACH.md` under `personal`, `HPC-UTwente-howto.md` under `system`), and the rail draws each inside its group, after the group's views, as a button opening a `doc` view (registered `listed: false`, one instance per path) that draws the markdown through `api/docs` as the project view draws a README (headings, lists, tables, images through the file route), with the document's title as the tab label. A `docs:` entry whose file is missing draws the view's own missing line. These replace what the cockpit drew as `approach`, `agents` and its HPC document; they are configured, not user bookmarks.
2. **The Help view** (`views/Help.svelte`, `help`, in the System group after usage): draws `tools/oculus/HELP.md`, a new file this package writes for oculus (not the cockpit's): the rail and its groups, the pages and the pane tree (split, fold, embed a page, drag), the keys (from `ui/key-rows.ts`, one table), every listed view in one line each, the config files and what each holds (one line each, the same lines the Config view shows), the local file (`local.yml`), the checks (`npm test`, `npm run check`, `npm run test:browser`), and where the hub's data is read from; plain prose, ASCII, no history. Drawn through `api/docs` with the engine directory allowed for this one path.
3. **The Config view** (`views/Config.svelte`, `config`, System group after help): one card per file of the engine's `config/` folder (`*.yml`, sorted) plus `local.yml` when present: the name, the line count, the one-line description from `config/text/views/config.yml` (`config.desc_<name>`, one key per file, the test failing on a file with no description or a description with no file), a collapsible read-only preview of the raw text (a `Disclosure`), and an edit control that opens the file in the Editor view. For that, the engine's `config/` folder becomes a fixed root `engine` served by the file route, the source route and the file browser (`src/lib/server/files.ts` `withHub`'s pattern: the key reserved beside `hub`, the directory `<engine>/config`), so the editor's inside-root rule holds and a config edit reaches the watcher's config push as any edit of that folder does. This root is a user-visible shape the orchestrator books for Axel; build it, and say in the report what changes if he refuses it (the edit control opens the file through `api/open` instead).
4. **Words** in `config/text/views/help.yml`, `config/text/views/config.yml`, `config/text/views/doc.yml`; DESIGN.md's views list and one dated decision line; the registry test's group and order rows.
5. **Tests**: `tests/config.test.ts` (the `docs:` shape, the description keys against the files), `tests/shell/rail.test.ts` (a doc entry drawn in its group after the views, the two groups), `tests/views/doc.test.ts`, `tests/views/help.test.ts` (the file rendered; a source test that every listed view's id appears in HELP.md and every key row's key does), `tests/views/config.test.ts` (one card per file, the preview, the edit control's target), `tests/server/files.test.ts` and `tests/routes/file.test.ts` (the `engine` root: served, inside-root, reserved), `tests/views/registry.test.ts`, a browser case (`tests/browser/system.spec.ts`: open Help from the rail, open Config, expand a preview, open the HPC document from its group).

## Decisions taken in this brief (each reversible, none silent)

1. A hub document tab is a `doc` view over `api/docs`, one instance per path, rather than the `document` view (which frames an HTML file) or the `file` view (which draws source): a markdown document is read as prose.
2. The `docs:` list is oculus's own layout key; the cockpit's `docs:` carried `key`, `title` and `paths`; oculus takes `label`, `path`, `group`.
3. `HELP.md` lives at `tools/oculus/HELP.md`, beside `DESIGN.md` and `README.md`, and is oculus's own text.
4. The `engine` root (item 3), booked for Axel.
