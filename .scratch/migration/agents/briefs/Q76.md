## What to build

Each item is an acceptance item.

1. **A re-read keeps what is shown.** A document that is held keeps being returned while its new answer is in flight; nothing a re-read does sends a view back to its loading state. The loading state is drawn only before a document's first answer. Remove the mistaken invalidation of item 4 of the tree: a moved `files` version re-asks for the documents that are read, and the empty id never wipes the hub documents or the manual.
2. **An unchanged answer repaints nothing.** When the new answer's HTML and frontmatter equal the held ones, the held object stays as it is, so no `{@html}` block is rebuilt and no image reloads. Better still, the server answers a re-read of an unchanged file without rendering it again: `api/docs` sends an `ETag` built from the file's size and modification time, the store sends `If-None-Match` on a re-read, and an unchanged file is a `304` the store treats as "keep what is held". The manual and project documents take the same path.
3. **Only a write that can concern the document re-asks for it.** A `files` event names its root. A hub document and the manual are re-read only for an event on the root that holds them (the hub root; the manual's file lies under the engine directory, so the root that holds that directory), and a project's document only for an event on the root holding that project's folder; an event on another root leaves them alone. Where the payload's root cannot be matched (the empty root of a bookmarks event), nothing is re-read.
4. **A tab of a moved entry follows it.** A `doc` tab whose `path` is not in the current `docs:` list, while an entry with the tab's `label` is, shows that entry's document and writes the entry's path and id into its instance state, so the saved layout holds the new path from then on. A tab whose path and label match no entry says so in the catalog's words and names the path it asked for: "docs/X.md is not in the documents list of config/layout.yml" or the like, never a bare "document does not exist". A path that is in the list but whose file is missing names the path as well. The `doc` view reaches the `docs:` list through state, never through the shell (the layer rules of the spec: `views/` imports no shell).
5. **Tests.** A unit test file for the store over a stubbed `fetch` and a stubbed channel version: a re-read keeps the held answer in flight (asserted between the version move and the answer), a `304` keeps the held object identical (`toBe`), an equal body keeps it identical, an event on another root asks nothing, the empty root asks nothing, and the manual survives an event that re-reads a hub document. A server test of the `ETag` and the `304`. A browser case that opens a hub document, moves the `files` version several times with a write under the served hub, and asserts that the loading words never appear and that the rendered heading element is the same node before and after (`elementHandle` equality, or a data attribute set on the node once). A browser case that seeds a saved layout with a `doc` tab at a stale path whose label matches an entry, and asserts the document renders and the stored tab state now holds the entry's path; and one with a label matching nothing, asserting the path is named in the message. Every new or changed case names the revert that turns it red.

## Decisions taken in this brief (each reversible, none silent)

1. A moved entry is matched by its label. Labels are the words the reader sees in the catalogue, and a move changes the path and keeps the label, which is what happened here.
2. The `ETag` is the file's size and modification time, not a hash of its text: it costs one `stat`, and the render is skipped only when both match.
3. The watcher's filter is left as it is. A write under `.agents/worktrees/` is news to the file listings of the hub root, whose ignored-files toggle can show that folder; this step makes the document readers indifferent to it instead.
