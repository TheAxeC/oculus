## What to build

When the step is done, a reader debugs a `.rite` program from oculus as from VS Code's Run and Debug with cathedra's extension: breakpoints in the gutter of a `.rite` source tab, a launch from the open file or from a configuration of the repository's `.oculus/launch.yml` (with its `before` command run first), stepping, the call stack, the variables of each frame, watch expressions, a hover that evaluates, and a Debug Console with the program's output and an input that evaluates in the selected frame. Every user-visible behaviour below is the fixed choice it states, written into HELP.md.

### 1. The launch file, `.oculus/launch.yml` (server)

`src/lib/server/machine/debug/launch.ts` (new, at most 300 lines) reads `<repo>/.oculus/launch.yml`, a map whose `configurations:` is a list of entries `{ name, program, cwd?, before? }`:

- `name` follows the rule of a command's name, by the same function (`nameProblem` of `runs/commands/files.ts`, exported): not empty, at most `NAME_MAX` characters, no control character. A repeated name keeps the first entry, with the same finding as `collect` gives.
- `program` is the `.rite` file to run, and a named configuration must have one, as cathedra's extension requires (`utils/vscode-rite/extension.js:61-63`): an entry without it is left out with the finding "is required: name the .rite file to run, or ${file} for the file on screen". Only the default configuration, the launch with no `.oculus/launch.yml` (section 4), runs the open `.rite` file. `program` is either a path relative to the repository or a text holding placeholders. A path is checked here, each failure a finding and the entry left out: an absolute path, "must be a path relative to the repository"; a `..` that leaves the repository, "leads above the repository; name a .rite file inside it"; a link that leads out, "is a link that leads out of the repository" (the sentence `folderOf` gives a `cwd`); a missing file or one that is no regular file, "must name a file of the repository that exists"; a name not ending `.rite`, "must name a .rite file". A placeholder's name may be `file`, `fileDirname`, `fileBasename`, `fileBasenameNoExtension` or `workspaceFolder`; `lineNumber` and `selectedText` in a program are the finding "may hold only the placeholders file, fileDirname, fileBasename, fileBasenameNoExtension and workspaceFolder". A text with a placeholder is checked when a launch fills it (section 4), since its value is the open file's.
- `cwd` follows a command's `cwd` rule, by the same function (`folderOf` of `runs/commands/files.ts`, exported): a folder inside the repository by real path, the repository when absent. It takes no placeholder, as a command's `cwd` takes none, so cathedra's `cwd: ${workspaceFolder}` copied from its `launch.json` is the finding "must be a folder of the repository that exists" and is written `.` or left out.
- `before` is a command name, checked by `nameProblem` as `name` is ("must not be empty", the length, "must not hold a tab, a line break or any control character"), the finding at `configurations[<n>].before`; whether a command of that name exists is checked at the launch (section 6), since the commands are read then.
- A field of the wrong type (`name: 7`, `program: 5`, `cwd: [a]`, `before: 3`) is one finding per field, "must be text", and an entry that is not a map is the finding "must be a map of the fields", found as `typeProblems` of `runs/commands/files.ts` finds them; `typeProblems` takes its table of sentences as an argument, so the two readers share it.
- A key outside these four is a finding naming it ("is not a key of a launch configuration: name, program, cwd and before are"), and the entry is left out; this catches `programm` and keys copied from VS Code's `launch.json` (`type`, `request`).
- The file-level rules and findings are those of `readCommandsFile`: no file is no configurations and no finding; a file that is not YAML is one finding ("is not YAML, at line N"); a top that is not a map, or a `configurations` that is not a list, is one finding; an empty file or an empty list is no configurations and no finding. The shared part of reading a YAML file down to its list (existence, read, `parseDocument` with a `LineCounter`, the map, the list and each item's line) moves out of `readCommandsFile` into one exported function of `runs/commands/files.ts` that both readers call, so the rule is written once (G21). Each finding is `{ file, field, message }` (`CommandFinding`), the field `configurations[<n>].<key>`.
- Each configuration read carries its line in the file, for Open File at its entry.

### 3. The session (server)

`src/lib/server/machine/debug/` holds the client side of the protocol, one session at a time, owned by the server context:

- `wire.ts` (new, at most 250 lines): the DAP messages over a child's stdio, framed by `vscode-jsonrpc`'s `StreamMessageReader` and `StreamMessageWriter` (Z704 (C4), the framing the language servers use in `server/machine/lsp/held/process.ts:17,125-128`), so the tree has one Content-Length framing (G21). - One session at a time: a launch while a session is `starting`, `running` or `paused` is refused with "A debug session is running: stop it first", whichever surface asked (F5 while running, the picker, the toolbar, the status bar).
- Stop. `rite_dap` cannot be stopped by the protocol (see "What is on the tree"), so Stop sends SIGTERM to the adapter process this session spawned, and SIGKILL 2,000 ms later if it has not exited. Per `DESIGN.md:165` it runs only behind a confirmation naming the process: an unconfirmed stop answers `{ confirm: "rite_dap <program> (pid <pid>)" }`, and the page asks; a confirmed stop signals. A stop with no session is refused. Restart is Stop with its confirmation, then the same configuration launched again from the start, its `before` included.

### 5. The console

- The console is the program's `output` events in order, each line kept with its category, and the console's own lines: the launch line (`rite_dap <program>` in `<cwd>`), each expression typed and its result or error, the end's sentence. Each line has an absolute number, counted from 0 at the session's first line and never reused within the session. The server holds at most 10,000 lines; past that the oldest go, and the console says how many earlier lines were dropped (the number of its first held line) in a line drawn above the held ones. A new session starts it empty, from number 0.
- It is published on its own channel, `debug-console`, as appends `{ session, start, lines }`, `start` the absolute number of the first line sent. The channel registers a merge in the hub (`hub.merge('debug-console', ...)`) that concatenates a held append and the next of the same session, so a page that falls behind gets every line late. A page holds its console as `{ session, first, lines }`, `first` the absolute number of its first held line; an append continues it when the session is the same and `start` equals `first + lines.length`, and then the page adds the lines and, past 10,000, drops its oldest and raises `first` by as many, so a page subscribed across the cap holds the same last 10,000 lines and says the same dropped count as the server. A page whose next append does not continue what it holds (another session, or a `start` past its end, which is what the replay of the last append gives a new page) reads the whole console with GET `/api/debug?console=1`, which answers `{ session, first, lines }`; an append whose lines the page already holds (a `start` before its end) adds only the lines past its end. Appends are coalesced to at most one per 100 ms. The `debug` channel carries no console, so a state publish never carries 10,000 lines.
