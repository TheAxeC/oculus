## What to build

When the step is done, a reader debugs a `.rite` program from oculus as from VS Code's Run and Debug with cathedra's extension: breakpoints in the gutter of a `.rite` source tab, a launch from the open file or from a configuration of the repository's `.oculus/launch.yml` (with its `before` command run first), stepping, the call stack, the variables of each frame, watch expressions, a hover that evaluates, and a Debug Console with the program's output and an input that evaluates in the selected frame. Every user-visible behaviour below is the fixed choice it states, written into HELP.md.

### 1. The launch file, `.oculus/launch.yml` (server)

`src/lib/server/machine/debug/launch.ts` (new, at most 300 lines) reads `<repo>/.oculus/launch.yml`, a map whose `configurations:` is a list of entries `{ name, program, cwd?, before? }`:

- `name` follows the rule of a command's name, by the same function (`nameProblem` of `commands/files.ts`, exported): not empty, at most `NAME_MAX` characters, no control character. A repeated name keeps the first entry, with the same finding as `collect` gives.
- `program` is the `.rite` file to run, and a named configuration must have one, as cathedra's extension requires (`utils/vscode-rite/extension.js:61-63`): an entry without it is left out with the finding "is required: name the .rite file to run, or ${file} for the file on screen". Only the default configuration, the launch with no `.oculus/launch.yml` (section 4), runs the open `.rite` file. `program` is either a path relative to the repository or a text holding placeholders. A path is checked here, each failure a finding and the entry left out: an absolute path, "must be a path relative to the repository"; a `..` that leaves the repository, "leads above the repository; name a .rite file inside it"; a link that leads out, "is a link that leads out of the repository" (the sentence `folderOf` gives a `cwd`); a missing file or one that is no regular file, "must name a file of the repository that exists"; a name not ending `.rite`, "must name a .rite file". A placeholder's name may be `file`, `fileDirname`, `fileBasename`, `fileBasenameNoExtension` or `workspaceFolder`; `lineNumber` and `selectedText` in a program are the finding "may hold only the placeholders file, fileDirname, fileBasename, fileBasenameNoExtension and workspaceFolder". A text with a placeholder is checked when a launch fills it (section 4), since its value is the open file's.
- `cwd` follows a command's `cwd` rule, by the same function (`folderOf` of `commands/files.ts`, exported): a folder inside the repository by real path, the repository when absent. It takes no placeholder, as a command's `cwd` takes none, so cathedra's `cwd: ${workspaceFolder}` copied from its `launch.json` is the finding "must be a folder of the repository that exists" and is written `.` or left out.
- `before` is a command name, checked by `nameProblem` as `name` is ("must not be empty", the length, "must not hold a tab, a line break or any control character"), the finding at `configurations[<n>].before`; whether a command of that name exists is checked at the launch (section 6), since the commands are read then.
- A field of the wrong type (`name: 7`, `program: 5`, `cwd: [a]`, `before: 3`) is one finding per field, "must be text", and an entry that is not a map is the finding "must be a map of the fields", found as `typeProblems` of `commands/files.ts` finds them; `typeProblems` takes its table of sentences as an argument, so the two readers share it.
- A key outside these four is a finding naming it ("is not a key of a launch configuration: name, program, cwd and before are"), and the entry is left out; this catches `programm` and keys copied from VS Code's `launch.json` (`type`, `request`).
- The file-level rules and findings are those of `readCommandsFile`: no file is no configurations and no finding; a file that is not YAML is one finding ("is not YAML, at line N"); a top that is not a map, or a `configurations` that is not a list, is one finding; an empty file or an empty list is no configurations and no finding. The shared part of reading a YAML file down to its list (existence, read, `parseDocument` with a `LineCounter`, the map, the list and each item's line) moves out of `readCommandsFile` into one exported function of `commands/files.ts` that both readers call, so the rule is written once (G21). Each finding is `{ file, field, message }` (`CommandFinding`), the field `configurations[<n>].<key>`.
- Each configuration read carries its line in the file, for Open File at its entry.

### 3. The session (server)

`src/lib/server/machine/debug/` holds the client side of the protocol, one session at a time, owned by the server context:

- `wire.ts` (new, at most 250 lines), hand-written as Z448 rules: the DAP framing over a child's stdio. It writes `Content-Length: <bytes>\r\n\r\n<json>`; it reads headers up to `\r\n\r\n`, takes `Content-Length` as a decimal integer and refuses any other header value, reads exactly that many bytes, parses the body with `JSON.parse` inside a try, and reads it through a zod shape (a response `{ type: 'response', request_seq, success, command, message?, body? }` or an event `{ type: 'event', event, body? }`). A header with no length, a length that is not a number, a body that is not JSON or that matches neither shape ends the session with the sentence naming what was wrong ("rite_dap sent a message that is not JSON", worded in the catalog), kills the adapter and rejects every pending request; it never throws out of the data handler. Each request has a sequence number and a pending entry; a response settles its entry; the adapter's exit or the session's end rejects every pending entry with the sentence of the end. Requests carry the `@vscode/debugprotocol` types (LA17 (a)).
- `session.ts` (new, at most 700 lines): a launch spawns `[riteDapBin, programAbsolute]` with `cwd`, `stdio: ['pipe', 'pipe', 'pipe']`, no `shell`, and the server's environment, through a `spawn` function the session holder is given (node's `child_process.spawn` in the server context, a recording fake in the G7 test); then `initialize` (`clientID: 'oculus'`, `adapterID: 'rite'`, `linesStartAt1`, `columnsStartAt1`, `pathFormat: 'path'`), `launch` with an empty body, and on `initialized`: `setBreakpoints` for every file the page sent, `setFunctionBreakpoints`, `setExceptionBreakpoints` with no filters, then `configurationDone`. On `stopped`: `stackTrace` (thread 1), then `scopes` and `variables` of the top frame and each watch expression evaluated in it (`context: 'watch'`), all before one publish. On `continued`: publish running. On `output`: console lines (section 5). On `terminated`: `disconnect`, then the adapter's exit ends the session. A spawn that fails (`ENOENT`, `EACCES`) ends the session at once with the sentence "rite_dap could not be started: <error>. Set rite_dap_bin in config/local.yml to the adapter's path." The adapter's stderr text is console lines of category `stderr`. An exit by a signal is said as "rite_dap ended with signal <name>".
- The paths. The page sends absolute paths as its tabs name them (served root folder joined with the path). The session keeps a map from each path's real path to the path as sent (breakpoints, the program), and reports a frame's `source.path` as the path the page sent when the map holds its real path, else as the adapter gave it. A frame whose path is not absolute is reported as given.
- The state the session publishes on the `debug` channel (a state channel, replayed on subscribe): `status` (`idle`, `starting`, `running`, `paused`, `ended`); the session's descriptor (`repo`, configuration `name`, the program as run, `cwd`, `pid`, a session number that grows by one per launch); on a pause the reason, the description and the hit ids; the frames (`id`, `name`, `path`, `line`, `column`); the selected frame; its scopes with their variables (`name`, `value`); the watch results (`expression`, `value` or `error`); the breakpoints as the adapter last answered them per path and line (`id`, `verified`, `message`), a breakpoint whose id is in a stop's `hitBreakpointIds` being verified from then on; the function breakpoints likewise; the end's sentence when the session ended; and the descriptor of the last session since the server started, which the status bar item reads.
- One session at a time: a launch while a session is `starting`, `running` or `paused` is refused with "A debug session is running: stop it first", whichever surface asked (F5 while running, the picker, the toolbar, the status bar).
- Stop. `rite_dap` cannot be stopped by the protocol (see "What is on the tree"), so Stop sends SIGTERM to the adapter process this session spawned, and SIGKILL 2,000 ms later if it has not exited. Per DESIGN.md:153 it runs only behind a confirmation naming the process: an unconfirmed stop answers `{ confirm: "rite_dap <program> (pid <pid>)" }`, and the page asks; a confirmed stop signals. A stop with no session is refused. Restart is Stop with its confirmation, then the same configuration launched again from the start, its `before` included.
- The server context gains `debug`, the session holder, created with the hub and closed by `close()`, which kills a running adapter so no child is left.

### 4. The launch route and its approval

`src/lib/server/machine/debug/routes.ts` (new, at most 450 lines) and `src/routes/api/(machine)/debug/+server.ts` (new, the lines that join them, as `routes/api/commands/+server.ts` does):

- GET `/api/debug?repo=<absolute>` (same origin, `no-store`) answers the repository's configurations (`name`, `program` as written, `cwd` relative as written, `before`, the entry's line) and the findings, and whether the file exists. GET `/api/debug?console=1` answers the console of the current session whole (section 5).
- POST `/api/debug` carries the write token (`tokenedBody`) and one action, read through a zod discriminated union: `launch` (`repo`, `name` or null for the open file, `context` `{ file }`, `breakpoints` `[{ path, lines }]`, `functions` `[name]`, `watch` `[expression]`), `approve` (`repo`, `cwd`, `program`), `continue`, `next`, `stepIn`, `stepOut`, `finishFrame`, `frame` (`id`), `evaluate` (`expression`, `context` `repl` or `hover`, `frame`), `breakpoints` (`path`, `lines`), `functions` (`names`), `watch` (`expressions`), `stop` (`confirmed?`). `repo` is a repository as `repositoryOf` of `commands/repo.ts` decides (a served root, or a folder under one that holds `.git`), or the request is refused with 400 and `repositoryOf`'s sentence before any file under it is read. Every refusal is `{ error }` with status 400, as `refuse` of `commands/routes.ts:57-58` answers, its sentence in `server.debug.*`, apart from the placeholder refusal of the next item, which is a word with its names. ### 5. The console

- The console is the program's `output` events in order, each line kept with its category, and the console's own lines: the launch line (`rite_dap <program>` in `<cwd>`), each expression typed and its result or error, the end's sentence. Each line has an absolute number, counted from 0 at the session's first line and never reused within the session. The server holds at most 10,000 lines; past that the oldest go, and the console says how many earlier lines were dropped (the number of its first held line) in a line drawn above the held ones. A new session starts it empty, from number 0.
- It is published on its own channel, `debug-console`, as appends `{ session, start, lines }`, `start` the absolute number of the first line sent. The channel registers a merge in the hub (`hub.merge('debug-console', ...)`) that concatenates a held append and the next of the same session, so a page that falls behind gets every line late. A page holds its console as `{ session, first, lines }`, `first` the absolute number of its first held line; an append continues it when the session is the same and `start` equals `first + lines.length`, and then the page adds the lines and, past 10,000, drops its oldest and raises `first` by as many, so a page subscribed across the cap holds the same last 10,000 lines and says the same dropped count as the server. A page whose next append does not continue what it holds (another session, or a `start` past its end, which is what the replay of the last append gives a new page) reads the whole console with GET `/api/debug?console=1`, which answers `{ session, first, lines }`; an append whose lines the page already holds (a `start` before its end) adds only the lines past its end. Appends are coalesced to at most one per 100 ms. The `debug` channel carries no console, so a state publish never carries 10,000 lines.
