# Brief: R12e, the files channel

Read `../spec.md` first, its section "The principles every package is judged on" above all. Axel ruled on 2026-09-14 at 16:13 (option (a) on R12b's stop): the file listing keys on a `files` channel of its own rather than on the portfolio's version. This package runs alone.

## What is on the tree (read 2026-09-14 at 17:14 on main at acdc200f)

- `src/lib/state/files.svelte.ts` lines 10 to 12 and 46 to 59: a project's file listing is fetched from `api/project-files` and re-fetched when the portfolio version moves, on the premise that the server republishes the snapshot when a file under a project folder changes. That premise no longer holds: `src/lib/server/watch/portfolio.ts` `namedByConfig` (line 71) rebuilds the portfolio only for a file the config names (a registry, a collection, a feed, a manifest), so a new or changed file under a project folder moves no version and an open listing never refreshes. This is the defect the package fixes.
- `src/lib/server/watch/git.ts`: the git watcher watches the hub root recursively whether or not a session names it (`always`, line 40 on) and every session workspace, ignores `IGNORED` segments (line 34), and on a write schedules a re-read of that root on a two-second throttle (`touch`, line 150 on; `reread`, line 132) which publishes `git`. Every write under a project folder of the hub already reaches it.
- The channels on the wire: config, feeds, git, hpc, portfolio, sessions, starting, usage. `src/lib/server/channels.ts` `Hub.publish` (line 101) versions any channel name; the client subscribes by name through `connect([...])` in `src/routes/+page.svelte` (find with `grep -n "connect(\[" src/routes/+page.svelte`) and reads a channel's latest message with `message(name)` from `state/entities.svelte.ts`.
- No test covers the listing's staleness: `tests/state/` has no files test; `tests/server/watch/git.test.ts` covers the git channel.

## What to build

1. **The `files` channel.** The git watcher publishes `files` beside `git`: each time it re-reads a root, one message whose payload is `{ root: string }` (the root re-read, an absolute path), versioned by the hub like every channel. A `FilesPayload` type in `src/lib/data/model-sessions.ts` beside `GitPayload`, with its comment saying what a message means (a write landed under that root and the listings under it are stale). One channel, one new wire shape, the one Axel allowed.
2. **The listing keys on it.** `state/files.svelte.ts` re-fetches a project's listing when the `files` channel's version moved since the fetch, not the portfolio's; the page subscribes to `files` with the other channels. A project whose folder is under no re-read root (none today, since the hub root is always watched) keeps its listing until the id is forgotten.
3. **The cost, measured.** One write of one file under a project folder of the served hub: how many git commands the watcher runs for the hub root (the test's `reads()` counter over `tests/server/watch/git.test.ts`'s fixture), quoted in the report, since the hub root is watched recursively (R12a's review named this as unmeasured).
4. **Tests.** `tests/server/watch/git.test.ts`: a write under a root publishes one `files` message naming that root, and the manual clock's `fire()` is what makes it happen. `tests/state/files.test.ts` (new): a listing is fetched once, not again on a portfolio version move, and again on a `files` version move (the fetch stubbed as `tests/state/docs.test.ts` stubs its endpoint). `tests/routes/page.test.ts`: the subscription carries `files`.

## Decisions taken in this brief (each reversible, none silent)

1. The `files` payload names the root re-read; the client re-fetches every held listing on any `files` message, as it did on any portfolio version before.
2. The channel is the git watcher's, since it already watches every root and throttles every write; no second watcher.
