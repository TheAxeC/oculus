# Brief: R8, the landing script and the rebase step

Read `../spec.md` first. Axel decided this on 2026-09-13 at 22:45 (the orchestrator is the bottleneck; "Script the landing => yes"; "Rebase before landing => yes"; the second review only after a repair round; the page check as a screenshot pass plus the package's browser spec). The script does by one command what the orchestrator does by hand at every landing, so a landing takes minutes of the orchestrator's attention instead of an hour, and R9 (two workers at a time) becomes possible.

## What the orchestrator does today, by hand, at every landing

1. In the worktree `.agents/worktrees/<pkg>` (a branch `<pkg>` cut at the recorded base): `git add -A tools/oculus && git commit -q -m wip` (a repair round adds a second wip).
2. Bring the branch onto main's head inside the worktree: `git checkout -b <pkg>-land main` there, then `git cherry-pick <base>..<pkg>`; a conflict is resolved in the worktree, never on main.
3. On main: `git cherry-pick -n main..<pkg>-land` (staged, uncommitted).
4. The seven checks on main from `tools/oculus`: `npm test -- --reporter=dot`, `npm run check`, `npm run build`, `npm run format:check`, `npm run lint`, `LC_ALL=C grep -rna '[^ -~]' src tests bin`, `find src tests config bin -type f | xargs wc -l | sort -rn | head -3`; then `npm run test:browser` (27 specs; port 8792 must be free).
5. The booking's numbers: the diff's files, insertions and deletions against the base; the worker's usage summed from the `turn.completed` events of the run's `events.jsonl` and `repair-events.jsonl` (`input_tokens`, `cached_input_tokens`, `output_tokens`, `reasoning_output_tokens`), the `item.completed` count, the seconds between the pid file's and the exit file's mtimes; the same for `review-events.jsonl` and `review-events-2.jsonl`.
6. The commit by literal paths, the worktree removed, the branch and `<pkg>-land` deleted.

The run folder is `<scratch>/runs/<pkg>/` with `prompt.md`, `events.jsonl`, `report.md`, `exit.txt`, `pid.txt` and the `repair-*` and `review-*` twins; `<scratch>` is a session folder outside the repository, given to the script as an argument.

## What to build (a script under the ledger and its test; no oculus source change)

1. `tools/oculus/.scratch/migration/land.sh <pkg> <base> <runs dir> [--no-browser]`, POSIX sh, run from the repository root by the orchestrator: steps 1 to 5 above in order, stopping at the first failure with the step's name and the command's output, and printing at the end one block the orchestrator pastes into the booking: the diff stat, the usage rows in the state file's row format (`<pkg>, worker codex:gpt-5.6-sol at high, first run: N in / N cached / N out (N reasoning), N items, N s (hh:mm:ss to hh:mm:ss); repair round on the same thread: ...; +A -D over F files`, and the reviewer row), and the list of paths for the commit (`git diff --cached --name-only`). It never commits, never pushes, never removes the worktree, and never resolves a conflict: on a conflict in step 2 it prints the conflicting paths and exits 2, leaving the worktree on `<pkg>-land` for the orchestrator.
2. Every git command on the worktree runs from inside it (`cd` in a subshell), never `git -C`. `merge`, `rebase`, `reset --hard`, `restore` and `push` are never used (the hub's rules put them on the ask list); the branch is brought forward by `cherry-pick`, as today.
3. The index lock: before every git command that writes, wait for `.git/index.lock` to go (an IDE holds it briefly), and remove a lock older than a minute when no git process is alive.
4. `tools/oculus/.scratch/migration/land.test.sh`: builds a scratch repository under `mktemp -d` with a `tools/oculus` folder whose `package.json` scripts are stubs (`echo`), a worktree with one wip commit on a branch, fake run files with two `turn.completed` events, and runs `land.sh` against it with `--no-browser`, asserting the staged paths, the printed rows and the exit codes for the clean case and for a conflict. Git is allowed in this scratch repository only; nothing under `/Users/axelfaes/workspace/research-hub` is touched by git during the test.
5. The `plan-orchestration` skill's landing steps (`.claude/skills/plan-orchestration/SKILL.md`, steps 11 and 12) and this ledger's state file "Verification" section name the script as the way a landing is run when the ledger holds one; the by-hand steps stay in the skill as what the script does.
