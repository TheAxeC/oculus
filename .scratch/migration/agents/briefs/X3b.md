## What to build

VS Code's Source Control, row by row from P1's inventory (`agents/reviews/vscode-parity.md`, section "Source Control"), on oculus's structure: one reader (`server/core/git.ts`) and one writer (`server/git/git-write.ts`), each with one call site, list arguments only; every write from an explicit press carrying the write token; nothing ever forced. Each item below is an acceptance item.

1. **Repositories as a list.** The view opens with a Source Control Repositories section listing every repository of the git channel, each row its name, branch, the sync counts (ahead, behind) and the change count, the chosen one marked; pressing a row chooses it (instance state as today). The section folds, as VS Code's does when there is more than one repository. The picker's shape badges stay on the rows.
2. **The commit box in the Repositories view**, as VS Code draws it above the changes: the message field (Ctrl or Cmd+Enter commits), the generated-message button (the existing `suggest`), and the Commit button with a dropdown holding Commit, Commit (Amend), Commit and Push, Commit and Sync. One component serves both this view and the sessions Changes panel (`ChangesRepo.svelte`); the two copies of the commit logic become one.
   - Amend runs `commit --amend -F <file>`; it is refused when HEAD is already contained in the upstream (it would need a forced push), with a sentence saying so. Amend with an empty message field keeps the last message (`--no-edit`).
   - Commit and Push commits, then pushes under the push rules; Commit and Sync commits, then syncs (item 4).
3. **Stage and unstage per hunk and per line.** In the diff (item 5) each hunk carries Stage, Unstage (in a staged diff) and Revert (discard, behind a confirm); a selection of lines stages, unstages or reverts just those lines. Built by generating the patch for the chosen hunks or lines and running `apply --cached` (stage), `apply --cached --reverse` (unstage) or `apply --reverse` (revert), the patch passed on standard input, with `--recount` so line numbers hold; a patch git refuses is reported with git's own line. Section headers carry Stage All Changes, Unstage All and Discard All Changes (behind a confirm naming the count).
4. **Pull, fetch, sync.** Pull runs `pull` with the repository's own configuration (no `--rebase` override); Fetch runs `fetch --prune`; Sync is pull then push, as VS Code's Sync Changes, shown with the ahead and behind counts; Publish Branch for a branch without an upstream (`push --set-upstream origin <branch>`, behind a confirm naming the remote). Pull, fetch, sync and publish are in the view's `...` menu and, for sync and publish, on the status bar's sync item (`RepoItems.svelte`), which today pushes only. A pull that stops on conflicts leaves the merge in progress (item 6).
5. **The diff, side by side and inline.** The diff pane draws both modes with a toggle in its bar (the choice kept as instance state): side by side, the two versions in aligned columns, removed lines on the left and added on the right, changed words marked within the line; inline, one column. Both modes draw line numbers of both sides, fold unchanged regions longer than 6 lines behind an expander (3 lines of context each side, VS Code's default), and carry Previous Change and Next Change (Alt+F5 and Shift+Alt+F5 while the pane has focus), Open File (the file in a source tab) and the hunk actions of item 3. A row of the sessions Changes panel opens the same diff.
6. **Merge conflicts and the three-way editor.** An unmerged path (status `U`, and `AA`, `DD` and the other unmerged pairs) is its own Merge Changes section, worded and coloured as a conflict. A merge (the existing merge back, and pull) that stops on conflicts no longer aborts: it leaves the merge in progress, and the view shows Merge Changes with Abort Merge (`merge --abort`, behind a confirm) and, once nothing is unmerged, Commit with the merge message git prepared. Opening a conflicted file opens the merge editor: Incoming (theirs) and Current (ours) side by side above the Result, each conflict with Accept Incoming, Accept Current, Accept Both (current first), Accept Both (incoming first) and Ignore, the Result editable, a count of conflicts left, and Complete Merge, which writes the Result and runs `add -- <path>`. The three versions come from `show :1:<path>`, `:2:` and `:3:`.
7. **Stash.** Stash (tracked changes), Stash (Include Untracked), Stash Staged, each asking for an optional message; a Stashes section listing each stash with Apply, Pop and Drop (Drop behind a confirm), and View, which opens the stash's diff (`stash show -p`). Pop and apply that conflict leave the conflicts in Merge Changes.
8. **Tags.** Create Tag at HEAD (name checked with `check-ref-format`, an optional message making it annotated), Delete Tag (behind a confirm), a Tags section listing tags with the commit each points at, and Push Tags (`push --tags`, behind a confirm).
9. **The graph, incoming and outgoing.** The log becomes VS Code's Source Control Graph: one row per commit, with a lane graph drawn from each commit's parents (`log --topo-order --format=` with `%P`), the branch and tag names on their commits, the current branch's head marked, and above them the Incoming commits (`HEAD..@{upstream}`) and Outgoing (`@{upstream}..HEAD`) when there is an upstream; 50 commits first and a Load More row that adds 50. Pressing a commit shows its changed files, each opening that commit's diff of the file; a commit row's menu has Copy Commit ID and Copy Message.
10. **Blame.** In the source tab, a Blame toggle in its bar: on, each line's gutter shows the author and the relative date of the commit that last changed it (`blame --porcelain -- <path>`), the hover naming the commit's short id, subject and date, and a press opening that commit in the graph; the status bar shows the caret line's blame while the toggle is on. Uncommitted lines read "Not Committed Yet". The blame is read once per open and again when the file's git state changes.
11. **Gutter marks.** In the source tab, the line gutter marks lines added (a bar in the added colour), changed (the modified colour) and deleted (a small wedge between lines) against the index, as VS Code's quick diff does, refreshed when the file is saved or its git state changes; a press on a mark opens the diff pane at that change.

Every new read form joins `server/core/git.ts`'s list and every new write form `git-write.ts`'s, each at its one call site; the tests that pin the exact lists (`git.test.ts`, `git-write.test.ts:50-63, 562, 570-581`) are extended to the new exact lists, and `--force` stays absent. DESIGN.md's **Git.** paragraph (`:128`), `:247`, `:258`, `:289`, `:311` and `:312` are rewritten to the new lists and behaviours (the reader's forms are no longer ten; a merge that conflicts is left in progress). HELP.md gets the Source Control sections a reader needs.

## Decisions taken in this brief (each reversible, none silent)

1. X3 is split by surface into X3a (Explorer), X3b (Source Control) and X3c (editor tabs); this step carries every Source Control row of P1's inventory whole. Worktrees stays with A2, as the inventory says.
2. Pull uses the repository's own `pull.rebase` setting; no pull strategy is imposed.
3. A conflicting merge or pull is left in progress for the merge editor rather than aborted, with Abort Merge one press away; this reverses the abort at `git-write.ts:437-443` and DESIGN.md `:289`, since VS Code resolves conflicts in place.
4. Amend is refused on a commit the upstream already holds, since the only way on from there is a forced push, which nothing here runs.
5. The graph loads 50 commits at a time.
