# Brief: D2, the map's filters

Read `../spec.md` first, its section "The principles every package is judged on" above all. The plan's D2 line (Axel, 2026-09-12 23:45): the map's controls: filters by project type and by pillar as toggle chips in one toolbar row, a keep-connected-only toggle dropping projects with no edge to a remaining pillar, pure state over the graph.

## What is on the tree (written 2026-09-15 at 19:20 against d4cf3eab; re-read at dispatch)

- The Map view is `src/lib/views/Map.svelte` with two partials, `views/map/Controls.svelte` (the legend chips for active, manuscript and idea; the link and re-tune controls; the collaborators checkbox; one checkbox per archived status) and `views/map/Graph.svelte` (the drawing), and `views/map/edge-write.ts`. Its state is `MapState { collaborators, enabled, linkMode }` (`src/lib/state/graph.ts` line 479, `parseMapState` line 489), kept in the instance state through `write()` (`Map.svelte` lines 41 to 43), so a tab reopened is the tab as it was.
- The graph is `buildGraph(snapshot, { archived, collaborators, labelMode })` (`graph.ts` line 73, `GraphOptions` line 33): nodes of kind `project`, `line` (a pillar, from `programIds`) and `collaborator`; edges of kind `membership` (project to line), `collaborator` and `related`. The layout is `placeInit`, `physics`, `optimize` and `bestLayout` over the nodes, keyed by `layoutKey(nodes)` in localStorage.
- The project types are `config/vocab.yml` `type_order` (line 72); the pillars are the programs registry (`Project.programIds`, the `programs` collection). The map's words are `config/text/views/map.yml`.
- The cockpit's map has no such filters; this is a post-port feature Axel agreed to.

## The acceptance list

1. **The state.** `MapState` gains `types: string[]` (the project types shown; empty means all), `lines: string[]` (the pillar ids shown; empty means all) and `connected: boolean` (drop every project with no membership edge to a pillar that is still shown), parsed by `parseMapState` with the same defaults rule, and kept in the instance state like the rest.
2. **The graph.** `buildGraph` takes the three as options and applies them as a pure filter before the layout: a project whose type is not in `types` (when `types` is not empty) is out; a line not in `lines` (when not empty) is out with its membership edges; with `connected` true, a project with no membership edge to a remaining line is out, and a collaborator node with no remaining project edge is out. The filter is one exported pure function `filterGraph(graph, state)` in `graph.ts` so a case is a plain call, and the layout key includes the filtered node set so a filtered layout is its own.
3. **The controls.** One toolbar row in `Controls.svelte` above the legend: a chip per type present in the portfolio (`ui/Chip.svelte` as a pressed toggle, in `type_order`'s order, drawn in the type's tone through `typeTone`), a chip per pillar present (in the programs' order, the line glyph), and a "connected only" chip; all pressed when nothing is filtered (the empty list), one press narrows to that one, a second press adds or removes, and an "all" control on each group clears it. The row wraps on a narrow pane. Every chip carries its count of projects in the graph now.
4. **The words** in `config/text/views/map.yml` (the row's labels, the "all" control, the connected toggle and its tip); no new view, so no `HELP.md` row, but the `map` row's sentence names the filters; DESIGN.md's decision line.
5. **Tests**: `tests/state/graph.test.ts` (or the file the tree holds for `graph.ts`): `filterGraph` for each of the three, the empty-list rule, the connected rule dropping a project and a collaborator, the layout key differing between two filters; `tests/views/map.test.ts`: the row drawn with the types and pillars of a synthetic snapshot, a pressed chip, the counts; and a browser case: press a type chip and see the node count fall, press "connected only" and see an unconnected project leave.

## Decisions taken in this brief (each reversible, none silent)

1. The empty list means "all", so a saved state from before this package (no `types`, no `lines`) draws the whole graph.
2. The filters live in the instance state with the other toggles rather than in a store, since they are one pane's view of the graph.
