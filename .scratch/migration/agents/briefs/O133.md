## What to build

1. One pattern. A new module `src/lib/data/prose/markdown/front-matter.ts` exports `FRONT_MATTER`: an opening `---` at the very start of the text, trailing spaces or tabs allowed; a block as group 1, empty or ending in a line end, the empty block tried first so an empty header is its two lines alone; a closing `---` or `...` at the start of its line, trailing spaces or tabs allowed, then a line end or the end of the text. CRLF and LF both read. No `m` flag. Its head comment says what the pattern reads, why the empty block is tried first, and that it is the one every reader of a leading header uses. It holds no reader and no I/O.
2. Every reader uses it, and no other copy stays:
   - `docs.ts`: `splitFrontmatter` matches with the imported pattern; its local `FRONTMATTER` and the comment over it go, the comment's content kept on the new module where it still holds. What `splitFrontmatter` returns is unchanged for every input but an empty header followed by a later closing line (case C11).
   - `note-links.ts`: imports the pattern; its own `FRONT_MATTER` export and the comment over it go. `scanNote` matches with it after it strips a BOM and turns line ends into `\n`, as now. `frontTags` reads the block from group 1 and places each tag on the line it stands on in the file, whatever the opening line's trailing spaces.
   - `html.ts:46,628` and `requests.ts` import the pattern from the new module; the hidden token covers every line of the header, the closing line included, in each closing form.
   - `RenderedMarkdown.svelte`: its local copy goes; it imports the pattern, and its comment says the document route splits the same block off, which is then true.
   - `outline.ts`: `frontMatterEnd` goes; `markdownOutline` skips the lines of the header the pattern matches, matched on the text with one leading BOM removed, so a header after a BOM is still skipped as it is now.
   - `tests/checks/tree/layer-rows.ts`: the views row gains `'data/prose/markdown/front-matter'` alone, and the comment block above the table gains its reason: the preview strips the header by the pattern the note scan, the Outline and the docs split read, and the module holds no reader and no I/O.
3. The documents and comments that describe what a header is say the one form:
   - `docs/HELP.md`'s notes section gets one sentence, next to line 405, saying which lines open and close a note's front matter.
   - `config/text/server.yml:385`: the LinkedIn sentence names the one form, a first line `---` and a closing line `---` or `...`, and keeps its key.
   - `src/lib/data/sources/deck/split.ts:7`: the comment names the pattern's place, `data/prose/markdown/front-matter.ts`, through `splitFrontmatter`.
   - Each head comment of a changed file that names a header's form or the pattern's place is rewritten where the change makes it false (grep `FRONT_MATTER`, `FRONTMATTER`, `frontMatterEnd` and `front matter` across `src`, `tests`, `docs` and `config` with `--exclude=local.yml`); the report marks each hit of the grep 'still true' or 'rewritten'.
4. The test of a new guarded entry (ruling 652 (1)). The orchestrator adds the entry to `agents/guarded.md` at landing, as `- G150. Every reader of a Markdown file reads the same leading header: the note scan's tags and headings, the Outline, the preview, an embed, the Markdown server's token and the docs split each take the same lines as the header, or none.`, its Code line naming `src/lib/data/prose/markdown/front-matter.ts` and the six readers, its Test line naming the new describe. The test: a new describe 'the leading header every reader reads' in a new file `tests/data/prose/markdown/front-matter.test.ts`, one table with a row per text of "Cases" C1 to C13, each row giving the text and checking, through the readers themselves:
   - the tags `scanNote` gives, with their lines;
   - the headings `scanNote` gives, with their lines;
   - the titles `markdownOutline` gives;
   - the block `splitFrontmatter` gives, or null;
   - the preview: `render(RenderedMarkdown, { props: { path: 'note.md', text } })` from `svelte/server`, after `installRealText()`, holds the body's headings and none of the header's text;
   - an embed: `blockMarkdownParts('![[other]]\n', ...)` with a note drawing whose `text` gives the row's text holds the body and none of the header's text;
   - the server's token: `markdownRequests(() => ['.md'])['markdown/parse']({ text }, {} as never)` gives a first token `front_matter`, `hidden: true`, whose `map` covers the header's lines, or no such token.
   The test imports no pattern. It reaches the header only through the readers, so it runs unchanged on the unchanged tree.

## Decisions taken in this brief (each reversible, none silent)

1. The wider form, the docs reader's, is the one pattern, as ruled (open item 648 (a)), with the empty block tried first (open item 652 (3) (a)).
2. The pattern lives in a new module under `data/prose/markdown/`, since the docs reader is server-only and the preview, `html.ts` and the Outline run on the page; the views row gets that one module, as ruled (open item 652 (2) (a)).
3. The BOM: the note scan and the Outline keep reading a header after one, as now; the preview, the embed, the Markdown server and `splitFrontmatter` keep reading none, as now. No Markdown file of the hub starts with one, and the docs reader's writers (`feeds.ts`) rebuild a file from the split, so the step changes no byte a write produces.
4. A lone CR line end is left as it is: the note scan and the server turn it into `\n` and read a header, the Outline, the preview, the embed and the docs split do not, before and after. No file of the hub is known to use it; the report names it under the judgment calls.
5. A closing line followed by Unicode white space (a no-break space) is no closing after the step, where the Outline's `\s*` reads one today.
