6. **No status read fails on the count of untracked files (Behaviour 2; part 10 item 3).** With `--untracked-files=all`, the output of a status read grows with every untracked file, and the readers buffer it under a cap (`git-write.ts:107` and `deposit-git.ts:62` at 8 MiB, `core/git/run.ts:99` at 32 MiB), so a repository with an un-ignored folder of enough files fails every write that reads the status (switch, merge, Stage All, stash, discard, worktree removal, the deposit's plan) and the view's state read. End it as VS Code's git extension reads the status, by streaming:
   - The status reads of `git-write.ts` (`porcelain`), `deposit-git.ts` (`porcelain`) and `core/git/state.ts` read git's output as a stream, record by record, with no output cap, and keep in memory only what their caller uses. A caller that asks whether there is a tracked change, or whether there is any change, stops reading at its answer. `untrackedAmong`, `pairOf` and Stage All keep only the records they need; Stage All passes the untracked paths to `git add --pathspec-from-file=- --pathspec-file-nul` as they are read. The view's state read keeps the lists it draws, cut at `MAX_ENTRIES` as now, and the counts of what it cut.
   - A read that is cancelled or out of time still answers with its failure as the readers do now.
   - Measure it on a scratch repository under `$TMPDIR`: one commit, then an un-ignored folder of untracked files with names long enough that the `-uall` output passes 40 MiB (for instance 200,000 empty files under a path of about 200 characters). Quote the output size (`git status --porcelain=v1 -z --untracked-files=all | wc -c`), then the state read, a switch refusal over a tracked change, Stage All and a stash on that repository, each with its time, run on the round-0 tree first (where they fail) and after.
