## What to build

1. **The rule is Q85a1's.** A schema goes where a value of type `unknown` that came from outside the process is narrowed. The schema is a `const` beside the function that narrows, in that function's file, named in lower camel case ending in `Shape`. A schema whose answer has a declared type is held to it with `satisfies z.ZodType<...>`. The function answers, for every input, exactly what it answers on main: the same value, the same null, the same thrown sentence, the same keys, absent keys absent. zod's own error text is never shown or logged. A reader that builds its answer from named fields reads them from `safeParse(...).data`. A reader that hands on an object or an array it was given (to a writer, to a file, or to the page) uses the schema only to accept or refuse and answers the input value itself, so its identity, the order of its keys, an own `__proto__` key and keys the schema does not name all stay. A bare "is this a map" test stays `isMap` from `data/helpers/guards.ts`, as `gatedBody` keeps it; a field read as a string, a whole number or a list through a fallback inside a reader that is converted is read through the reader's schema. Five rules keep the answers the same, each found by a probe of zod 4.6.5 on the tree: a whole number is tested as the hand code tests it, `z.number().refine(Number.isInteger)`, never `z.int()`, which refuses `2 ** 60`; a number the hand code accepts with `typeof === 'number'` stays accepted when it is `NaN` or infinite; an optional field is `.optional()`, never `.nullish()` or `.catch`, where the hand code refuses `null`; a field read as `first ?? second` reads the second only when the first is `null` or absent, whatever type the first has; keys read from a map (the statuses of `careerRules`, the entries of `overrides` and `loadCache`) are read from the input's own keys in their order, never from `z.record`'s `data`, which drops an own `__proto__` key. The body readers of item 2 are promised the same answer for every JSON value, since the write route hands them `JSON.parse`'s result; `asFieldValue` and the file readers keep their answers for every value, a `Date` and a `Map` included. The one answer that changes is item 8's malformed cache entry.
2. **The request bodies** (`edit/writes/bodies.ts`). One schema per body kind, beside its reader, each reader keeping its name, its signature and its answer:
   - the `fields` map of `manifestWrite`, `entryWrite`, `subtaskAdd`, `newEntry`, `leadAddWrite` and `newIdea`, and the `order` array of `reorderWrite` and the two arrays of `deckWrite`, are answered as the input values themselves;
   - `targetOf` becomes one `targetShape` that `subtaskWrite` and `subtaskAdd` share, answering `{ id }` with no `collection` key when the body's target has none;
   - `keyList` becomes one `keysShape` (a list of non-empty strings) shared by the two halves of `deckWrite`;
   - `sessionWrite` refuses a body that names none of `hidden`, `top`, `area` and `title`, and answers only the keys the body names;
   - `linkedinIdeaWrite` answers `category: ''` for a body with no `category`;
   - `configKeyWrite` refuses a body with no own `value` key and answers `value` as the body holds it;
   - `railWrite` answers each row as `{ label, glyph, page }` with no other key;
   - `kind` is a literal on each schema, and a body whose `kind` is read only through its prototype (an own `__proto__` key holding it) is refused, as today;
   - `feedFieldWrite`'s `value` accepts `null`, a string, a boolean and every number, `NaN`, `Infinity` and `-Infinity` included, as `typeof` does today;
   - `sessionWrite`'s `hidden: null`, `subtaskWrite`'s `value: null` and a target's `collection: null` answer null, as today.
   The file's head comment keeps saying what it says; the sentence on the wrong shape refused whole stays true.
