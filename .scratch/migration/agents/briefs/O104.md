## What to build

The look of the project page and the project editor does not change. Every other record comes to look and behave as they do. Axel's ruling 593: "it MUST be exactly how projects page currently looks and feels."

1. **The sections in the schema.** `SchemaField` gains `section?: string`, read by `schema/field.ts` as a text, absent for any other value, absent also for the empty text. `SCHEMA_FIELD` in `record.ts` takes the key, its `$ref` taking it on a nested row too, where nothing reads it. `formFieldOf` copies it at the top level only. `docs/data-map.md`'s attribute table and the key list of `docs/templates.md` gain `section`.

2. **The section names and their order.** `manifest_schema.sections` becomes the one ordered list of editor sections, in this order: Core, Indexing, Content, Connections, Dates, Recovery, "Deposit & compute", Outcome, "Overrides (rare)", Website, Strategy, Positions, Degrees, Awards, References, Profiles. The comment at `manifest-schema.yml:7` is corrected. A manifest draws only the sections that hold a field, as it does now, so its form does not change. `hub-layer.ts` holds a hub's `manifest_fields` rows to this list, so such a row may name the new sections too. This order gives every file the order of the table Axel approved.

3. **Rows with no section.** A section name the list does not hold is drawn after the listed ones, in the order of its first row. Rows with no `section:` are drawn last, under a group named by the catalog word `editor.other` ("Other"). A section the file names `Other` joins that group, with one fold key. No field of a schema is left undrawn.

4. **The one page frame.** `src/lib/views/shared/card/record/RecordPage.svelte` is the frame cut out of `Project.svelte`: the `Pane` (no tint), the column with its gap, the `Surface` outcome line, the terminal-shape font rule, the keep of a preview tab on typing (`oninput`), and the snippets `toolbar`, `card` and the sections as `children`, with the data attributes each view hands it. `Project.svelte` is rebuilt on it. A section of any page is a `GroupHead` folded through `usePaneFold`.

5. **The one editor.** `Editor.svelte` edits every record. Its instance state names the record: `recordField(id)` for a project; `entryPageState(collection, id, label)` for a collection entry, a person (the people collection's key) or a feed entry; `{ id: 'career', label }` for the career file. What differs by kind goes in a helper `src/lib/views/boards/editor/editor-target.ts` beside `Editor.svelte`: the fields, the sections, the values, what is writable, and the save. `EntryEditor.svelte` is deleted, and for every kind but the project everything it holds comes across: the block on Save with its words (a `fault` among them), the refusal under a field, the required reminder, a feed entry's partial save, Add person into the record's own hub. The project keeps what its editor does now, its refusal as a line and no reminder among them. `editor.none` and `editor.unknown` are worded for any record. An entry deleted while its editor tab is open shows that line, and the close asks while the draft holds words. The editor of an entry whose save changes its title moves its tab's label, as `Entry.svelte`'s `$effect` does for the page, which stays. Drafts keep the kinds `project` and `page`, so G28 holds for an editor tab of a page entry: the tab asks before closing over an edit. The sections are drawn for every kind as `Editor.svelte` draws them.

6. **Opening the editor.** Every card that has a record to edit has an Edit row that opens the editor beside the page, as the project card's does: `EntryCard`, the four registry cards, `LeadCard`, `RadarCard`, and the Career cards. The row has its own action id, placed by `RUNS` in `record-menu.ts` where the project card's Edit row stands. Edit in File stays. A file with no schema has no Edit row. On a page, Edit is also in the card's strip. The project card is unchanged. Edit pressed twice shows one tab, by `stateId`.

7. **The entry page.** `Entry.svelte` is rebuilt on the frame: the card at the top, no form, then Referrers and the folder's blocks. Its toolbar stays. A venue, a dataset, a domain and a pillar line draw the card their view draws, opened out: `VenueCard`, `DatasetCard`, `DomainCard` and `LineCard` move to `views/shared/card/record/registry/`, gain the prop `page` (title as words, no Page action, long text whole) and are drawn by their views as before. Every other collection draws `EntryCard` with `more`.

8. **The person page.** `Person.svelte` is rebuilt on the frame: `EntryCard` with `more` and no strip of role rows at the top; the sections Projects and Waiting on, each a `CardGrid` of `ProjectCard`s, closed as a board draws them, the ELI5 clamped with `more` and `onmore` held in the tab's state, a press opening the project page; then the folder. The fact strip and the form go. The "this is me" button, with its tip and its hub chip, moves to the Pane's toolbar beside Delete. A person of a people file with no schema has the card and the sections and no Edit.

9. **The Career page.** `Career.svelte` is rebuilt on the frame: the strategy card at the top, a `RecordCard` titled by the file's `title`, with the goal, the milestone and its day, the order note and the order of work; then the groups Positions, Degrees, Awards, References and Profiles, each a `CardGrid` of `RecordCard`s, one per row (a position's and a degree's title `title`; an award's `award`; a reference's the person's name; a profile's its name in the map), the row's other filled text fields as the card's lines. A row with `hide: true` carries a Tag. No form on the page. Every card's Edit, and the toolbar, open the editor on the career file. Write the website and its said line stay. The states `none` and `no_schema` stay, and in `no_schema` no Edit shows.

10. **The project sets.** `ArchivalCard`, `OrphansCard` and `NoFundingCard` move to `views/shared/card/record/sets/`, each gaining `ontitle`, which opens a new unlisted view `views/boards/listing/Listing.svelte` (id `listing`, state `{ id: 'listing:<set>', set, label }`, `set` one of `archival`, `orphans`, `no_funding`). The page is the frame with the set's card at the top, with no strip, and its projects as `ProjectCard`s in a `CardGrid`, clamped as on the person page; a set with no project draws `Empty`, and the Orphans card with no orphans keeps its title opener; Archival has one folded group per stage in the order of its `dead` numbers. There is no editor and no Edit. The projects come from the state functions the cards read now; No funding shows every unfunded project, whatever the bar's picks. The strip on the Pillars and Funding views stays.

11. **The LinkedIn post.** `PostCard.svelte` and `post-card.ts` move to `views/shared/card/feed/`, and the card's title opens a new unlisted view `views/feeds/post/Post.svelte` (id `post`, state with `hub`, `key` the post's file, and `label`). The page is the frame with the card at the top, `page` set, then the post's body drawn by `views/shared/prose/RenderedMarkdown.svelte`. Edit stays what it is: it opens the text file. Mark posted from the page moves the tab to the numbered file, as `Entry.svelte`'s `$effect` moves a page. A post gone from the feed says so with `Empty`.

12. **The rest.** Inbox threads and search results keep no page. The Add box still opens the new entry's page.

It is made against copies of the hub's files as they stand on disk, and checked with `patch --dry-run -p1 -d ~/workspace/research-hub`. The orchestrator applies it at landing. The same mapping goes on the fixture hub's 15 schemas and on `docs/templates.md`, where `followup` goes to Dates, as the manifest's does, and the fixture's `used_by` of `data.yml` to Connections.

The builder's first task, before any change, is the first run of every case above on the unchanged tree, with each case's result noted.

- A case of a code step (a script, or a product's code) becomes a test of the step only when the rules file's test rule calls for a test of it.
- A case kept as a test is run on the unchanged tree first.
- No prototype script stands in for such a test.
- Every other case of a code step is checked by a run the report quotes, and no test is kept for it.

No new guarded entry is made in this step. Where an entry's Code line already names `schema/field.ts` or `record-fields.ts`, a row is added to its table test for `section:`; otherwise the report says none does. These cases are views, and there is no browser suite, so each is read from the code in the first run and listed for the look with the state to put it in.

When the first run finds a case the brief's own rules get wrong, the builder stops there, before changing any code, and hands back the first run and that case, with the rule and the result it gives. The orchestrator rules on the case and resumes the builder with the ruling, and the final report carries it.
