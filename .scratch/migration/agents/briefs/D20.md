## What to build

### 1. A task's agent, through the composer (the plan line, ruling 662, Z195)

1. **The control** (choice C1). In `views/boards/focus/rows.ts`, `actionsFor` adds an action `agent` (label `project.action.agent`, title `project.action.agent_tip`) to a line that is a task: an entry of the `tasks` collection, and every subtask line (manifest, funding scheme, collection entry). A snoozed line, a follow-up, a lead, a venue and a project's own deadline line get none. `act` takes one more argument, the function that starts a task's agent, and calls it for `agent` instead of writing; `Tasks.svelte` and `CommandCenter.svelte` pass `client.terminals.composeAt`. A helper in `rows.ts` turns a line's target into the task's reference: `{ id, subtask? }` for a manifest, `{ id, collection, subtask? }` for an entry, `{ id, collection: 'funding', subtask }` for a scheme.
2. **The Tasks collection card.** `EntryCard.svelte` takes one optional prop, `extra: CardAction[]`, appended to its controls (502 lines; stay at or under 520). `Collection.svelte` passes, for the `tasks` collection only and for an entry whose status is not terminal by the same `terminal(config, status)` rule the ticker uses, one action "Start Agent" (`collection.start_agent`, title `collection.start_agent_tip`, glyph `terminal_claude`) that calls `composeAt` with `{ id, collection: 'tasks' }`. No other collection's card changes.
3. **The seed, built on the server only.** A new module `src/lib/server/machine/seeds/task-seed.ts` (`server/machine` holds 7 items) resolves a task reference against the hub's files and answers the seed, the folder and the terminal's name, or `task-unknown`:
   - Entry: the entry by its identity (`identityOf`, `entryOf`); manifest: `readManifests`; a subtask: `subtaskValue` of its host, and the host's title.
   - Folder: a manifest's subtask, the project's folder; an entry whose `related` names exactly one project of the snapshot, that project's folder; anything else, the hub root.
   - Seed: these lines, joined by one line feed, each only when it has a value: `server.task.seed_title` with the task's text (the entry's title, or the subtask's `do`), `server.task.seed_part_of` with the host's title (a subtask only), `server.task.seed_deadline`, `server.task.seed_note` (an entry's `note`), `server.task.seed_subtasks` with the entry's open subtasks' `do` joined by `; `, and `server.task.seed_file` with the file's path relative to the hub. Every control character other than the line feed between lines is replaced by a space. A seed longer than `PROMPT_MAX` answers `task-too-long`.
   - Name (choice C3): `server.task.name` with the task's text, every control character replaced by a space, cut so the whole name is at most `NAME_MAX` (80).
   - A task whose text is empty or only spaces: its id (the entry's id, or the subtask's key) stands for the text in the name and in the seed's first line.
4. **The wire** (choice C2). `POST /api/terminal`, behind the token as every action there:
   - `{ action: 'seed', task }` answers `{ ok: true, seed, cwd, name }` or the refusal word.
   - `compose` gains three fields in `composeRequestShape` and `ComposeStart`: `task` (the reference), `seed` (the text the page showed) and `confirm` (true only from the confirmation of item 5). With a `task`, the server builds the seed again; one that differs from `seed` answers `task-changed`; one whose approval text is not approved answers `{ approve: { seed, cwd, agent } }` and starts nothing; an approved one starts with the prompt `seed`, or `seed`, a blank line and the reader's own words when the box holds any, and with the task's name.
   - `{ action: 'approve-seed', task, cwd, agent, seed }` builds the seed again, answers `task-changed` when it differs, and otherwise calls `approveTexts(approvalsFor(), [text])`, answering `{ ok: true }` or `{ error }` with the file's reason.
   - The approval text is `JSON.stringify({ agent, cwd, seed }, null, 1)` with `cwd` the real path of the folder, under the `command:` key `approvals.ts` already writes. The reader's own words are not in it.
   - New refusal words in `TERMINAL_REFUSALS` (`data/model/model-sessions.ts:288`): `task-unknown`, `task-changed`, `task-too-long`, `needs-confirm`, each with its sentence in `state/shared/answers/terminal-words.ts` and the `sessions` catalog.
5. **Permission modes** (ruling 662, choice C8). A value of `config/catalogs/agents.yml` may carry `confirm: true`; `agents.ts` reads it (`VALUE_KEYS` gains `confirm`; a value that is not `true` or `false` is a finding naming the key, G13), and the value's `AgentChoices` entry carries it to the page. The shipped file sets it on Claude's `acceptEdits`, `auto` and `bypassPermissions` and Codex's `danger-full-access` and `never`. `compose` refuses a request whose picks include such a value without `confirm: true` with `needs-confirm` naming the value's label, before any tmux call. The composer's Start, for every start it makes, asks first through `ui/controls/Confirm.svelte` when a picked value carries `confirm`: message `composer.confirm_skip` with the agent and the value's label, detail `composer.confirm_skip_detail`, controls `composer.confirm_skip_yes` and `composer.confirm_skip_no`; No starts nothing.
6. **Opening the composer** (`composeAt`). The terminals store gains `composeAt(cwd, agent, task?)`, which opens the composer in the current page's Terminal tab (or a new one), as `composeIn` does, with the workspace set to `cwd` (as `splitState` sets a tab's folder), the agent given, the account kept, and every list of that agent at its catalog default, so Permissions shows "Manual permissions" whatever the tab's last start used. With a task, it first posts `seed`; a refusal is answered to the caller as its sentence, which the Focus board and the collection view say on their outcome line, and opens nothing. The answered seed and name are kept in the composer's record (`ComposerRecord.task`, read through a shape that drops a malformed one).
7. **The composer with a task** (choice C10). Above the prompt box the composer draws the seed read-only under `composer.task_label`, with a control `composer.task_remove` (title `composer.task_remove_title`) that drops the task, after which the start is a plain start; the box's placeholder becomes `composer.prompt_more`. When `compose` answers `approve`, the composer draws the approval panel in its place: `composer.approve_title`, `composer.approve_detail`, the seed, `composer.approve_folder`, `composer.approve_agent`, and the controls `composer.approve_yes` (posts `approve-seed`, then the same start again) and `composer.approve_no`. `task-changed` replaces the shown seed by the server's current one and says `sessions.refused_task_changed`. Each new block is a component of its own in `views/sessions/terminal/start/` (below), with its head comment; `Composer.svelte` stays at or under 520.
8. **Sizes and folders.** `views/sessions/terminal/` holds 10 items: `Composer.svelte` and `AttachPicker.svelte` move into a new `views/sessions/terminal/start/`, with a new `TerminalStart.svelte` (item 9) and the new blocks of item 7, so the folder holds 9. `terminals.svelte.ts` stays at or under 880; if it would pass, the functions that open a composer (`composeIn`, `composeInTab`, `showComposer`, `freshComposerOf`, `composeAt`) move into a module named for them, and `state/sessions/terminal/` (10 items) keeps its count by moving `composer.ts` beside that module into `state/sessions/terminal/composer/`. `ShellStarter` (`state/shared/stores/shell.ts`) or a type beside it names `composeAt`, so the repositories store reaches it without importing the terminals store.
