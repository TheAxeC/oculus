## What to build

1. **One id shape (ruling 236).** Every record of every hub, the primary's included, has the internal id `<hub>:<key>` and carries `root`, whatever the other hubs hold: projects, registry entries, collection entries and feed entries (leads, Lit Watch, LinkedIn). A project of a workspace folder that is no hub, in a workspace with no primary, has the folder's name as its hub: `<folder>:<key>` (Decision 1). The merge is the one place that gives a record its id, and `hubs/feeds.ts` gives a feed entry its id by the same function. `hub-names.ts` loses every branch on the primary (`root === primary`), its functions take no `primary` argument where the id alone now tells the hub, and its head comment states the rule.
2. **Own hub first (ruling 203 (b)).** Each hub's build keeps every reference value it cannot resolve in its own hub, so the merge sees it (`normalise.ts`). The merge resolves a reference in its own hub, then in the other hubs: one other hub holding the key gives that record; two or more other hubs holding it, with the own hub holding none, give one finding under `findings.hubs` naming the key and each hub that holds it, in the workspace's folder order, and resolve to none. A key two hubs hold is no finding by itself. A folder project's reference has no own hub and resolves in the hubs by the same rule. Every relation table (`projectVenue`, `projectPerson` and the rest) is built from the resolved references, and the `no_key` finding is given only for a value no hub resolves.
3. **No joined id written or shown (ruling No hub prefix shown).** No file, form, finding, label or address writes or shows `<hub>:<key>`. A page shows the key or the label, with the hub chip where the record is of a hub other than the one in view. Every file oculus writes that names a record (the tab and view states in `~/.oculus`, the change log, the recover places, any other) holds the hub and the key as two fields (Decision 2). The builder greps every writer under `src/lib/server/files/workspace/`, `src/lib/server/sessions/` and `src/lib/server/edit/` for a record id written to a file and lists each in the report with what it now writes.
4. **Every reader of an id's hub goes through the helpers.** The places listed under "What is on the tree" that read a hub from an id with `indexOf(':')` or build one with a template string use the helpers. Each of the 44 files is changed where its own id-shape code or a sentence of its is made false by item 1, whether or not it calls a helper.
5. **Writes route by the record's hub.** A write names its record by the internal id; `writes/hubs.ts` routes by its hub part, with no bare-id case and no primary case. The deposit route reaches the manifest of a project of any hub. `hubOwnValues` and `hubOwnFields` write the bare key, and a write from a form that picks another hub's record (item 7) writes the bare key, which resolves to that record by item 2's rule since the own hub does not hold it.
6. **The YAML editor (ruling 231).** A field that names a record allows the keys of every hub of the workspace, so the editor marks no value the Findings view resolves (`schema/record.ts`, `schema/set.ts`, `schema/lists.ts` and their caller in `schema/run.ts`).
7. **Forms (ruling 232).** A form's dropdown for a field that names a record lists the own hub's records, then the other hubs' records each with its hub chip; it writes the bare key, and a key the own hub holds is offered once, the own hub's.
8. **Rename (ruling 233).** The reference index resolves across the hubs by item 2's rule, so a rename rewrites the references in every hub that resolve to the renamed record and no reference that resolves to another record of the same key.
9. **The Audit (ruling 234).** Each hub's records are judged with their references resolved across the hubs, as the portfolio resolves them. The Audit view shows a finding's scope as the key with the hub chip; the scope field holds no prefix. The signature's input stays as today (the primary's scope bare, another hub's `<hub>:<scope>`), so a stored mute keeps matching (Decision 3).
10. **Add (ruling 203).** Add asks which hub's file takes a new entry, as it does today, and the page it opens names the record by its hub and key.
11. **Text.** `findings.hubs.id_prefix` and `ambiguousIds` are removed, since no id can be read two ways; the refusal of `docs/apps.md:749` is kept or removed by whether its code still runs, and the report says which. Every head comment and document sentence the change makes false is rewritten, each rewrapped as a whole paragraph at 100 columns: those listed under "What is on the tree", and any other the grep of item 4 finds. The new head comments say: every record's id is its hub and its key; a reference resolves in its own hub, then in the others; a key two other hubs hold is a finding for a reference that could mean either; no joined id is written or shown.
12. **Tests (ruling 235, `spec.md`'s test rule).** The cases below are rows of `tests/data/hubs/hub-portfolio.test.ts` (G32) and of `tests/routes/hubs/hub-routing.test.ts` or `hub-undo.test.ts` (G8), in tables where a unit has several outcomes. Each row has a part that fails on the unchanged tree, quoted from its first run; a case that holds on both trees is folded into a row with a failing part or checked by reading. The rows plant their keys; `tests/fixtures/hubs/hubs-fixture.ts` gains what a third hub needs. The files are slow-tagged, so each is run alone and the run quoted. Rows of the tests of G8, G28, G32 and G92 that the change makes false are changed, each named in the report.
