## What to build

1. **The converter.** `utils/migrations/convert-vscode-themes.ts`, run from `tools/oculus` as `node utils/migrations/convert-vscode-themes.ts [--from <extensions folder>] [--check]`, its head comment saying so, as `migrate-joint-work.mjs` and `rename-program-to-pillar.ts` do. It reads each of VS Code's 19 colour themes from `--from` (default the installed app's `extensions` folder on macOS; a missing folder or theme file stops it at the start with the path and the flag that sets it), with the theme's `uiTheme` from its extension's `package.json` and its shown label from `package.nls.json`. Each file is parsed as JSON (`JSON.parse`; a file that is not valid JSON stops the run naming it), `include` is followed to its end with the includer's keys winning and the included files' `tokenColors` first, and `semanticTokenColors` is ignored, the head comment saying the editor colours semantic tokens from the TextMate rules (`kit/theme/semantic.ts`). It writes two generated files, each with a head comment naming the source, the VS Code version it was read from (`Info.plist`), VS Code's MIT licence and the command that writes it: `src/lib/themes/vscode.css`, one `body.vscode-<slug>` block per theme, and `src/lib/themes/vscode-rules.json`, each theme's editor rules (item 6). Both are written in the form `npm run format` leaves unchanged (the converter formats them through `prettier`'s API with the project's configuration), and their comments pass the comment checks of `tests/checks`. `--check` writes nothing and exits non-zero, naming each block or theme that differs, when a file is not what a run would write, and names any `vscode-*` row of `config/appearance.yml` without a block and any block without a row. A second run changes nothing. The mapping is pure (a function from a resolved theme and its `uiTheme` to its block and rules), so the cases run it without the file system.

2. **The mapping.** Each token is the first key of its list that the resolved theme holds (decision 2); when the theme holds none of them, the first key of the list whose registered default (item 3) is a colour. `--bg` sideBar.background, activityBar.background, editorGroupHeader.tabsBackground, editor.background; `--panel` editor.background, else the scopeless tokenColors rule's background; `--card` editorWidget.background, input.background, dropdown.background, sideBarSectionHeader.background; `--chip` the value of `--card`; `--ink` foreground, editor.foreground, sideBar.foreground, else the scopeless rule's foreground; `--muted` tab.inactiveForeground, descriptionForeground, editorLineNumber.foreground, a candidate whose contrast on `--panel` is at or above `--ink`'s being skipped (secondary text never reads stronger than body text); `--line` sideBar.border, panel.border, editorGroup.border, contrastBorder, tab.border; `--accent` focusBorder, button.background, activityBarBadge.background; for a high-contrast theme, `--line` takes contrastBorder and `--accent` contrastActiveBorder first; `--tab-active-txt` tab.activeForeground, `--tab-inactive-txt` tab.inactiveForeground, `--tab-active-border` tab.activeBorder, each only when the theme holds the key; the Source Control tokens `--c-scm-added`, `--c-scm-modified`, `--c-scm-deleted`, `--c-scm-conflict` from `gitDecoration.addedResourceForeground`, `modifiedResourceForeground`, `deletedResourceForeground`, `conflictingResourceForeground`, `--c-gutter-modified` from `editorGutter.modifiedBackground`, `--c-scm-added-bg` and `--c-scm-deleted-bg` from `diffEditor.insertedLineBackground` and `diffEditor.removedLineBackground`; `--c-scm-conflict-bg` has no VS Code key of its meaning (`merge.incomingContentBackground` is the incoming change, which oculus paints from `--c-blue`, `colours.ts:460`) and keeps the base's value (item 3). The six code tokens (for highlight.js through `code.css`, and the tokens' editor rules when no theme rules apply): for each token its scopes in list order, the first scope some rule holds exactly, and of the rules holding it the last: comment `comment`; keyword `keyword`, `storage`, `keyword.control`; string `string`; number `constant.numeric`; name `entity.name.function`, `entity.name`, `support.function`; meta `meta.tag`, `entity.name.tag`, `meta.preprocessor`, `punctuation.definition.tag`. A scope string is split on commas and trimmed; a rule with no foreground or an empty one never counts. A colour of three or four digits is expanded first; a colour whose alpha is `00` counts as no value, and the list goes on; any other alpha is composited over the theme's `--panel` to six digits, an alpha of `ff` dropped. A dark or high-contrast-dark theme also sets `color-scheme: dark`, `--shadow: none` and the red and amber tints of `body.dark`, as the Modern dark block does. A class is `vscode-` and a slug of `[a-z0-9-]` only, as `parse.ts:17` reads them.

3. **The fallbacks.** A key the theme does not set takes VS Code's registered default for the theme's type: the git extension's `contributes.colors`, read from `extensions/git/package.json` at run time, for `gitDecoration.*`; for the workbench's keys, a table in the converter holding exactly the keys the mapping names, by type (dark, light, hcDark, hcLight), each written as VS Code 1.137.0 registers it in `workbench.desktop.main.js` (a hex, `null`, another key, or another key with an alpha), with a comment naming that source and the MIT licence; a reference reads the theme's own value of the key it names, else that key's default, and an alpha is composited over `--panel` (decision 3). A token whose keys all come out `null` or transparent, and `--c-scm-conflict-bg`, take the same token of oculus's own base of the theme's type: `body.dark` over `:root` for `vs-dark` and `hc-black` (so `--accent` is `:root`'s, which `body.dark` does not set), `:root` for `vs` and `hc-light`. A tab token with no key in the theme is left out, so the strip keeps the surfaces' colours. The block's comment names each token that came from a registered default and each that came from oculus's base.
