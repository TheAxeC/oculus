## What to build

### 1. The Live HPC view on a hub that names no cluster

When the hub's settings name no `slurm.resource` and the machine names no `hpc_host`, there is no cluster to ask, and that is a plain state:
- The server publishes it as a fifth `HpcStatus`, `none` (Z862), with the no-cluster sentence as `hint`, no `retryMin`, and empty rows. It runs no poll and schedules no retry while the state holds; a config push or a workspace move that names a cluster starts the poll at once, and one that takes the cluster away publishes `none` and stops the poll.
- The Live HPC float and the status bar's HPC item draw `none` as the sentence alone: no `unreachable`, no retry countdown, no error box, no error or warning colour, and no stale mark.
- A hub that names a resource the server cannot use (`notRead`, `unknown`, `notCluster`, `noHost`, `badHost`) and a cluster that does not answer keep `unreachable` with their reason, as now.
- `docs/apps.md:365` lists `none` among the `status` values; `HELP.md:254` says a hub that names no cluster shows that sentence and polls nothing.

### 2. The source tab focused last, kept while it is hidden

The store's focused tab is the source tab whose editor the reader focused last, with what it last said, until that tab is closed (it leaves every page and float of the layout), as VS Code keeps the active editor while a view has the focus:
- Hiding the tab behind another tab of its pane, moving it to another pane, and its `status()` turning null for a moment (a re-read, a configuration push) never clear the focused tab or its last status.
- The tab's entry in `entries` (what the status bar draws for the tab on screen) behaves as now.
- The focused tab is cleared only when the tab is closed, read from the layout's open instances, and when another source tab's editor is focused.
- The readers keep their order: the tab on screen first, then the focused tab (`debug.svelte.ts:340`, `:412`, `commands.svelte.ts:469`).
- `editor-status.svelte.ts`'s head comment says the rule as built.

### 3. A write shows in an open History

The cause was found by `/diagnose oculus/migration D74 premise`; the record is `agents/reviews/D74-diagnosis.md`, and plan.md's Step 0 under D74 states it. Read the record whole before this part.

- The cause: the change log's append, `logChanges` (`src/lib/server/core/changes.ts:382-392`, with `append` at `:345-376`), writes the line and tells no holder of the log; the store that holds the log for History, `createChanges` (`src/lib/state/sessions/changes.svelte.ts:156-207`), holds the first page under `staleTime: Infinity` and reads again only when its own reader calls `reload`, `latest` or `older`. A write made by a server route, an app's host or another page never reaches an open History.
- The rule the fix makes hold: a held copy of the change log is read again whenever the log is appended to, by whichever writer (a page, an app's host, the server), and the read keeps the rows the reader loaded.
- The fix, every place the record names:
  - `ChangeLog` gains `hub?: Pick<Hub, 'publish'>`; `append` answers the moment of its newest record from both its branches; `logChanges` publishes `changes` with `{ at }` after the lines are on disk (`publish`, which keeps the newest message, so a page that subscribes again hears it); a write that changed nothing publishes nothing.

  - `ChangesPayload = { at: string }` in `src/lib/data/model/index.ts`, typed in `Payloads` (`src/lib/state/shared/stores/shapes.ts`) and checked in `payloadShapes` (`src/lib/state/client/shapes/payloads.ts`).   - `createChanges(queries, entities)` hears `changes` through `entities.afterReceive` and `entities.payloadOf`; it asks nothing when it holds no log yet, when it already holds a row that new, or outside a browser; otherwise `queries.refetch(KEY, newer, 'again')`, which follows a request already out. `newer` is a fetcher of its own that puts the fresh first page in front of the held rows when the page reaches the newest held row, so the older pages the reader loaded stay; `first`, used by the first read, `reload` and `latest`, is unchanged. `src/lib/state/client/context.ts:207` passes `entities`.
  - `src/routes/+page.svelte`'s `connect([...])` (`:276-294`) gains `'changes'`.
  - The record's diff is a lead, not a dictation: the builder may write it otherwise as long as each place above is fixed and the cases below hold.
