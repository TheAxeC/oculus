# oculus, design

The successor to the research cockpit (`tools/cockpit`). Same job: a private, local dashboard over the research portfolio, its projects, venues, funding, data, and the Claude Code sessions working on it. Different construction: one language, three layers, one definition per screen, live data pushed by the server rather than polled by the page, and an arrangement you edit in the app.

This is the artefact every change is measured against. When the code and this file disagree, one of them is wrong and the disagreement is a finding, never something to paper over.

The name: the eye, alongside `iris`, `scotoma` and `umbra`; and the opening at the top of a dome that lets the light in, alongside `cathedra`.

## Why a new tool

The cockpit is a Python static-site generator that emits one 8.8 MB HTML file with all CSS and JS inlined, plus a Python dev server that patches the page in place when files change. That shape was chosen so the output would be a single portable file with no build step. The file is never opened; only the served app is used. Every awkward thing in the cockpit follows from a constraint that no longer applies:

- 3668 lines of Python build HTML through f-strings, and 3477 lines of client JS render the live half of the same screens. The Sessions tab is defined in both.
- A live-reload "morph" patches the generated document in place, with `data-skipmorph` escape hatches so it does not wipe what the client rendered, and MutationObservers to re-apply client decoration after it does.
- A hand-rolled module system (`window.CK`, load-order rules, a custom test) stands in for a bundler.
- Config is read into module-level singletons at import, so a config edit re-execs the whole process.

None of these are bugs. They are the cost of the constraint. oculus drops the constraint and therefore the cost. Nothing in the cockpit is thrown away carelessly: the data files are kept as they are, the configuration files are copied over and keep their roles, the palette and themes port unchanged, and the gates port as tests.

## Non-goals

- Not multi-user, not remote, not peered. Clodex-style fleet features are out.
- Not an IDE. It is a development platform for the hub's own files: a file browser, an editor for every text file, search, a language server client (pyright for Python, clangd for C and C++, the TypeScript server for TypeScript and JavaScript, the Svelte server for Svelte), LaTeX builds, PDF reading, project commands and the rite debugger. It has no lint panel and no other debugger.
- Not a rewrite of the data. The YAML in the hub is the source of truth and its shape does not change for oculus.

## The three layers

**Data.** Reads files, produces a typed, validated model. Knows nothing about screens. Runs on the server.

**Code.** Everything between the model and the pixels. Split by where it can run: the server-pinned half touches the filesystem, git, processes and the socket; the client half holds state and computes joins and filters. Neither half renders anything.

**View.** Components. Split into primitives that know no domain, a shell that knows no view, and views that know no layout.

The rules that keep this honest are the import-graph tests (`tests/checks/tree/boundaries.test.ts` for the layers, `tests/checks/imports/` for the order of the folders inside a layer and for cycles) plus one boundary SvelteKit enforces itself. See Boundaries below.

## Configuration

The tracked files under `config/` and `config/catalogs/` are the interface described as data, one concern to a file, and they are treated alike: what the portfolio reads, words and colours, arrangement, thresholds, themes, the glyph vocabulary, the edit form, the agent composer and the options catalog each have a file of their own, which the Configuration guide (`docs/configuration.md`) lists with what each holds. `config/local.yml` sits with them and is the machine's own, read by `loadLocal` and never merged; `loadConfig` merges every other file's top-level keys into one map and reports a key two files define, so a key can move between files and no key sits in two. Every user-facing string lives in the catalog fragments under `config/text/`, read through `t("group.key")` on the client and `findingText` on the server, and every option of every config file is described once in `catalogs/options.yml`, so no component holds a literal user-facing string, a raw colour or a literal glyph; `tests/checks/source/keys.test.ts` and `tests/checks/config/config-folder.test.ts` fail on a key or a glyph name that does not hold.

Paths resolve without environment variables: the command-line argument `--engine <dir>`, then `local.yml`, then a default derived from the file's own location. The hub path is the one value every machine must set and it lives in `config/local.yml`, gitignored and left out of the merge, so the tree carries no machine path. The boundary of what is served is the roots: the roots the file browser may serve are set in the app and stored in config, nothing outside a root is ever served, and `POST /api/open` works on the same roots, so a dotfile the tree leaves out of its listing and a Customizations item named by its real path are resolved like any other path under a root.

## Layer 1, data

**Sources.** One module per kind of file. Each exposes one function that takes a root and returns raw records, and each is unit-tested against synthetic fixtures in a temporary directory. No source knows another exists.

**Model.** `model/index.ts` and the concern modules beside it hold the types and nothing else. The core entities are `Project`, `Venue`, `Dataset`, `Pillar`, `Domain`, `Funding`, `Collection`, `Entry`, `Doc`, `SideProject`. A project carries the ids of its relations (`venueId`, `fundingIds`, `datasetIds`), never resolved objects: a project points at its funding and the funding points back at its projects, and that loop cannot be turned into JSON.

**Validate.** Every id referenced resolves to an entity; every status is in the vocabulary; every manifest field is one the schema names. Failures are reported with file and key, and a run against the real hub must report zero. It runs on every rebuild, so a bad manifest edit shows in the app within a second, as a finding, never a crash.

**Normalise.** What goes over the wire:

```ts
type Snapshot = {
  version: number                         // increments on every rebuild
  entities: { projects: Record<Id, Project>; venues: Record<Id, Venue>; personal: Record<Id, SideProject>; ... }
  relations: { projectFunding: [Id, Id][]; projectDataset: [Id, Id][]; ... }
  findings: Finding[]                     // from validate
}
```

Nothing is copied into a database: the server reads the files, builds one snapshot of entities and relations, pushes it over a WebSocket, and watches the hub and the config folder, so a file edited anywhere reaches the page in the same second.

Flat, JSON-safe, small: the whole hub is a few hundred kilobytes, which is why this page is not the cockpit's 8.8 MB. Documents are not in it; `api/docs` serves one when a view opens it, and an unchanged file is answered `304` by its `ETag` (`src/lib/server/content/docs.ts`). A deck's slides are not in it either: `api/deck` serves one deck whole when the Present view opens it, and the snapshot carries only where each project's deck is (`Project.deck`).

## Layer 2, code

### Server

**The socket.** One WebSocket per open page. Messages are `{channel, version, payload}`. Channels: `portfolio`, `config`, `sessions`, `git`, `files`, `hpc`, `calendar`, `inbox`, `usage`, `feeds`, `audit`, `processes`, `schedule`, `apps`, `jump`, `debug`, `debug-console`, later `pty:<id>`, `lsp:<language>` and `source:<root>/<path>`. A page subscribes to the channels it needs; the server sends the current payload on subscribe and pushes on change. If a page falls behind, the server keeps only the latest payload per channel: the newest state is the only one that matters. The socket accepts nothing from the page except subscriptions, an `unsubscribe` message (`{type: 'unsubscribe', channels}`) that any socket may send and that acts only on that socket's own subscription to the `source:` channels it names (`parseUnsubscription` in `server/root/socket.ts`; any other name in it is ignored), and, from a socket whose subscription carried the write token (a subscribe of no channels carrying the renewed token joins it), terminal input, the frames of an `lsp:<language>` channel and a `jump` message, which a PDF in a window of its own sends to have the main page that opened the window (its `owner`) open a source line: the Hub sends the place once to the pages subscribed to `jump` and keeps none, and a page whose id is not the owner ignores it; `server/root/socket.ts` holds that one set of sockets and hands the terminals and the relay its `canWrite(sink)`, which each asks at every message.

**Language server channels.** An `lsp:<language>` channel carries one language's language server messages both ways with none dropped or merged, so it is the relay's (`server/machine/lsp/relay.ts`) and not the Hub's, and it has no latest payload to send on subscribe. Beside the protocol's JSON-RPC messages it carries the relay's own, told apart by an `oculus` field: from the page `restart`, `output`, `output_off`, `choices`, `choose`, `approve`, which carries an interpreter the relay listed and the reader approved or the Svelte configuration, `revoke`, which takes the configuration's approval back, and `read`, which carries a library address and the root key of the document whose request got it named; from the relay `state`, `output`, `choices`, `refused`, `file`, which answers a `read` with the file's text or with the code that says why it was not read, and `legend`, which carries the token types and modifiers of the server's semantic tokens, because the relay answers the page's `initialize` itself and that answer cannot. The channel `lsp:workspace` names no language and no server: the page sends `held`, the whole set of files its tabs hold open, and `held_ask`, which of some files another page holds open, and the relay answers `held_answer`; a request for the workspace's symbols names the root and goes to that root's server, and a follow-up of a call or type hierarchy item goes to the server of the item's file.

**Watchers.** Each channel has one watcher module that owns its `fs.watch` handles, rebuilds only what changed, and pushes. The usage, bookmarks, portfolio, local and sessions watchers debounce with a `maxWait` of twice the quiet, so a file written without a pause, as a transcript is while a session works, is rebuilt at least every `maxWait` and not only once the writes stop. Git does not debounce: it throttles per root, so it re-reads on change no more often than every two seconds, with at most one read of a root running and one waiting, and its reads run git as child processes so the event loop keeps serving requests while they work. The same recursive watch publishes the `files` channel at the end of each throttle window: `{ root, folders }` names the folders the window's events landed in (`{ root }` for the whole root when more than 64 came), so the Files tree and every other follower of the channel read again only what moved, without waiting for a git read. A configured root's repositories are watched down to `repository_scan_depth` of `sources.yml` levels (1 by default), found at start, on a configuration push and when a `rename` event names a path within that depth. A git write is answered after the state it made is on the `git` channel. The files open in source tabs are the one set polled and not watched: for each `source:<root>/<path>` channel some socket holds, the server stats the file twice a second and publishes the SHA-256 of its bytes (`stat:` and a hash of the stat for a file over the read limit, null when nothing readable is there) when it moves, because a darwin `fs.watch` can miss a write that lands while it registers and a tab has to learn within a second that another program wrote its file; the name is resolved again at every tick, so a link that now points out of every root publishes null and reads nothing, the poll closes when the last socket drops the name, and the number of polls is bounded at 200 names per socket and 1000 over the server (`src/lib/server/files/fs/open-files.ts`, `src/lib/server/core/file-poll.ts`). What each watcher watches and how it rebuilds is in the head comment of its module under `src/lib/server/root/watch/` and `src/lib/server/machine/usage/watch.ts`, and the apps watcher is described with the apps below.

![The channels, from the modules that publish them to the stores and views that read them](docs/diagrams/channels.svg)

**Sessions.** Facts that cost real time to establish and must not be rediscovered:

- Transcripts: `<dir>/projects/<slug>/<id>.jsonl` of each Claude account, 490 files and 1.2 GB on this machine, and a 48 MB transcript folds in 0.2 s. A transcript is read in pieces and each complete line decoded alone, so the size of a file bounds nothing, and a byte-offset cache means a later read takes only what was appended (`src/lib/server/sessions/stores/transcripts.ts`, `src/lib/server/sessions/cache.ts`).
- Subagents are `tool_use` blocks named `Agent`, paired to their `tool_result` by id. `isSidechain` is false on every record everywhere and carries no information.
- The live registry: `<dir>/sessions/<pid>.json` of each Claude account, with `sessionId`, `status` (`busy` or `idle`), `name`, `cwd`. Liveness is `kill(pid, 0)` plus a `procStart` match, one `ps` per scan; the registry stamps in UTC and `ps` under the C locale reports local time, so the match parses both and allows two seconds (`src/lib/server/sessions/registry.ts`).
- Grouping: workspace by walking up to `.git`; area scored from touched files with the cwd counting double, directories clamped to two segments below the workspace root, known project folders exempt from the clamp.
- Context occupancy is the last assistant turn's `input + cache_creation + cache_read`, never the lifetime sums.

**Git.** The read-only modules of `server/core/git/` run exactly the forms listed in the head comments of `run.ts` (`src/lib/server/core/git/run.ts`) and `compare.ts` (`src/lib/server/core/git/compare.ts`) and no others, through one subprocess call site, `run.ts`'s asynchronous `execFile` runner, which never holds the event loop, with a five-second timeout and list arguments only, so the set of git commands the application can run is one list a reviewer reads; no test pins it. Every write is `server/git/git-write.ts`'s, one call site per subcommand, listed in its head comment (`src/lib/server/git/git-write.ts`), and no form carries `--force`; `branch -D`, run only after Delete Branch's second question, is the one form that discards commits no other branch holds. A write runs only from POST /api/git carrying the write token from this application's own page, and one that loses work or reaches a remote also carries the confirm the page sets from a dialog, so no write is reached by a watcher, a timer or the socket, with one exception: `server/root/watch/autofetch.ts` fetches unattended while `git.autofetch_minutes` of `behavior.yml` is above 0 (its default is 0), because a fetch changes no branch, file or commit the reader holds (`src/lib/server/root/watch/autofetch.ts`).

**Fixed git choices.** Oculus makes these choices once, with no setting, and `docs/source-control.md` ("What oculus fixes") lists each of them for a reader. Where git has a setting of its own for a choice, oculus leaves the choice to it, so the repository's own configuration decides, with one setting added: a commit sets `user.useConfigOnly` through the environment, so a repository with no configured name and email is refused with git's own message and git never commits under an identity guessed from the machine (`src/lib/server/git/git-write.ts`). Untracked files get a group apart so that one press of Stage All Changes cannot stage a file nobody looked at, and every configured root is listed because oculus shows every repository it knows at once. Forcing is confined to the deposit snapshot push (`forcePushSnapshot` of `deposit-git.ts`), kept because the snapshot is an orphan commit that has to replace the remote's `main`.

**Search.** One pattern over one served root or all of them, answered by `GET /api/search`, since a search is a request with an answer and holds no state on the server, so it travels over no channel. It sits behind the origin check and the write token, since a search reads every file of every root and that is more than any other read here gives away (`src/lib/server/files/search-routes.ts`). ripgrep is the `@vscode/ripgrep` dependency, so the search works where no `rg` is installed and the version that answers is the lockfile's. The page and the server run one query rule, `data/helpers/search/query.ts`, so the two cannot disagree about what a query is. Replace is the `replace` operation of `POST /api/ops`, with no route of its own, and it shares the search's one subprocess call site, so the page never decides what is written. Find All References over a Python, C or C++ file a language server serves is the References view's; the word toggle over an identifier in a code root finds every file's spelling of it, with no index of oculus's own. What a reader does is in `docs/files-and-search.md` ("Searching the files").

**Literature search.** One query is answered by `GET /api/literature` behind the origin check and the write token, since a search puts the reader's query in a request to a third party and spends the keys of `local.yml`. The page sends one request per source that is on and merges the answers as they arrive, so a slow source never holds a fast one, and the state of one source is that source's answer and never an error of the route. Every request goes through one `LiteratureDesk` that holds a lane per source and the cache of `ok` answers, so no module keeps either as state of its own. A failure names the source, the status and the source's own plain code, never the address or the body, since a key travels in the request and must be in no failure. What a reader sees is in the Views guide (Literature search), and the keys are in the Configuration guide ("The Literature search's keys").

**Live HPC.** One poller publishes one complete state of the cluster on the `hpc` channel. The connection is the poll's own and never the user's shared ssh master, so a master whose route died cannot make a poll wait past its connect timeout. The cluster receives two writes from oculus, both through POST /api/hpc: the cancel of a job and **Submit Job**. The only processes started are `rsync`, with no shell, and the ssh command, both injected so a test starts neither. The host, the cadence and the plan are in the head comments of `src/lib/server/machine/hpc/`, and how a failing poll looks, what Submit Job runs and each refusal word are in the Views guide (Live HPC).

**Schedules.** One rule reads a schedule entry, `readEntry` of `data/helpers/run/schedules.ts` with `cronRuns` of `data/helpers/run/cron.ts`, and both the dialog and the server apply it, so they cannot disagree on what runs. A prompt starts as a Claude terminal whose only argument after `--` is the prompt, so no scheduled text reaches a shell. `POST /api/schedules` carries the write token and edits the entry's node in the file's own document. How a due time is decided, caught up and skipped is in the head comments of `src/lib/server/machine/runs/schedules/`, and the entry's fields and the dialog are in the Window guide (The update tray and schedules).

**Calendar.** One poller publishes the calendars the reader owns at Google and Microsoft, and any calendar shared as a link, on the `calendar` channel, read-only and never writing to a provider. The credentials are kept in the account files under `calendar_dir` of `local.yml` (`~/.oculus/calendar` by default) and the client half, the reader's own OAuth client id and secret or Entra application id and tenant, under `~/.oculus/connect`, so no secret is in the tracked tree, and no token, secret, published link or event body is ever logged, published or answered. The connect flow is the authorization code with PKCE and the read-only scope alone, with the server's own loopback callback as its redirect. The callback route is the one route the write token does not gate, because the provider's redirect carries no token, so it is guarded by the `state` the process minted and takes once. The accounts and their files are in the Configuration guide (Calendar accounts), the poll, the error state and the `ics` provider in the head comments of `src/lib/server/accounts/calendar/`, and the view's forms in the Views guide (Calendar).

**Mail.** One poller reads the reader's own Gmail and Outlook mailboxes over the `inbox` channel and publishes one complete state, in the calendar poller's shape (`src/lib/server/accounts/mail/poll.ts`). What the two connectors share is `server/accounts/connect/`, parameterised by a kind that selects the scopes and the folder, so a calendar consent never carries mail rights and a mail consent never carries calendar rights. `POST /api/mail` never takes a provider's id or an address from the page: triage, reply and archive name a configured account or a thread of the state last published, so a page that invented an id reaches no mailbox. The accounts, the confirmations and the triage notes are in the Configuration guide (Mail accounts and the Inbox), and the plate is in the head comments of `src/lib/server/accounts/mail/`.

**PTY.** Sessions run inside tmux, one session `oculus-<id>` each, so they outlive the server. The server holds one tmux control-mode client per attached terminal and bridges it over the `pty:<id>` channel, and the page renders it with xterm.js. A session started elsewhere is observed (transcript only) until the reader explicitly resumes it into tmux with `claude --resume <id>`, and the server sends no signal to any registry pid other than the liveness probe.

**The change log.** Every write that changed something is recorded: what file, what field, the value the file held and the value written, and when. The record is made by the writer, at the one point it holds both values, so it holds the value the writer saw, and it is appended as one JSON line to `~/.oculus/changes.jsonl`. It is a machine-local file and not a file of the hub, since git already holds the hub's history and what this answers is what oculus did here. `POST /api/write` takes one back with the kind `undo`: the file is checked to still hold what the write left, an address that has moved is refused with `moved` and never written over, and the earlier value is written by the same writer the change came from, so an undo is an ordinary write, is recorded like one and can itself be undone. A `config-value` record carries the replaced text so the undo returns the file byte for byte (`src/lib/server/edit/writes/config/config-value.ts`), and a write with no inverse writer is recorded with `undo: none` and offers no control. What an undo of a removed field or a rewritten note puts back is in the Configuration guide (The change log), and what a record holds is in the head comments of `src/lib/server/core/changes.ts` and `src/lib/server/files/fs/replace.ts`.

A module the trace from the write route reaches is drawn, grouped by folder, when a path from it leads to the disk or to a call the trace cannot follow, or when a refusal calls it. A refusal is a dashed arrow, a function or value referred to without a call is a dotted arrow, and an arrow into the disk is labelled with the `node:fs` call.

![The write chain, from the route through the refusals and the change log to the file on disk](docs/diagrams/writes.svg)

**Auth.** The server binds 127.0.0.1, and any page open in the browser can address localhost, so every request under `/api/` passes one origin rule, `sameOrigin`, before a route sees it, and a request carrying neither Fetch Metadata nor an `Origin` header is refused because a browser without Fetch Metadata sends neither on a cross-site request (`src/lib/server/core/auth.ts`). The Claude Code hooks are `curl` posts to `/api/hook` with neither header nor a write token, so that path is let through when a request names neither header (`HEADERLESS` of `src/hooks.server.ts`), and the hook's own refusals are the rate limit and the size (`src/lib/server/root/hooks.ts`). The guard judges the route Kit matched rather than the raw path, so an encoded address reaches no route unguarded. Writes additionally carry a token minted at server start and delivered to the page once, which holds back another page in the same browser. Nothing outside the hub, the engine config folder, the machine-local files under `~/.oculus` and the configured roots is ever written. The socket checks `allowedOrigin` on its upgrade, which does not pass through `handle`; what it accepts from the page is under "The socket". The files of an app are served outside `/api/` by `src/routes/apps/[...path]/+server.ts`, because a sandboxed frame sends `Origin: null`, which `sameOrigin` refuses ("Apps added while oculus runs").

**Untyped input.** In `server/core`, `server/root`, `server/machine`, `server/accounts`, `server/files`, `server/content`, `server/git`, `server/edit`, `server/sessions`, `server/transcripts`, `src/lib/data`, `state/`, `src/lib/views`, `src/lib/shell` and `src/routes`, a value that comes from outside the process or from outside the page's own code is checked with a zod schema that sits beside the reader, in the same file (`src/lib/data/helpers/guards.ts`). That covers the socket's frames and the payloads of each channel, request bodies, the output of the programs oculus runs, the files it parses, the records of a transcript, the answers of the providers and the configuration, and in the page the answers of the server's endpoints, the browser's storage and the state a tab keeps in the saved arrangement. What a field of the wrong type does is written on its schema: it takes its default, it is read as absent, or it refuses the whole value. The text of a schema's error is never shown or logged.

**Processes.** A process oculus starts from text the reader did not write into oculus's own configuration (a command in a repository's `.oculus/commands.yml`, a debug launch, an agent seeded with a task) runs only after the reader has approved that exact text on this machine, the approval kept under `~/.oculus/` and keyed by the text, so a changed text asks again; it runs in a pane the reader can see, never in the background; and oculus stops only processes it started itself, behind a confirmation naming the process. A process oculus did not start is shown, never signalled. A command the reader saved through the form is text the reader wrote into oculus, so it runs without the question, and a changed text, folder or `depends_on`, or the same text in another repository, asks again; the placeholder values never enter the approved line, so the approved text is the text that runs. A debug launch asks for every launch, the default configuration that runs the open `.rite` file included, and its approved text is the repository, the folder it runs in and its program as written (no name, no adapter), so the default configuration has the text of a configured `program: ${file}` entry in the same folder and one approval covers both. Stop on a debug session is SIGTERM to the adapter oculus started and SIGKILL two seconds later, behind the confirmation naming it, since the protocol's disconnect lets the program run to its end. A language server (pyright, clangd, `typescript-language-server` or `svelte-language-server`, `server/machine/lsp/`) is oculus's own command with oculus's own arguments, so it runs in the background with its state on the status bar and ends with its tabs without a confirmation. What a repository's own configuration would run through a server is a process of the repository's text and takes the approval: the Svelte server starts untrusted for every repository, loading no repository config or package and saying so on the status bar as reduced mode, until the reader approves the text of the repository's `svelte.config.*` and `vite.config.*` files on this machine, an entry `svelte-config:<sha256 hex>` in the same file over the paths of those files with the hash of each one's bytes, so a changed file asks again; the TypeScript server loads `typescript-svelte-plugin` only under that same approval; an approval made or taken back starts both servers again. A Python interpreter a repository holds (`.venv`, `venv`), which oculus runs once to read its version and pyright runs to read its search paths, runs only after the reader approved its path on this machine, an entry `interpreter:<sha256 hex>` in the same file over the JSON `[repository real path, interpreter path]`, so a changed path or another repository asks again.

### Client state

Svelte 5 state modules (`.svelte.ts`). `entities` holds the latest payload per channel, `selectors` computes the joins (a project with its venue, funding and datasets; sessions by project; workspaces), and views read selectors and write `ui`, never `entities` directly. `layout` holds the tree below and is the one place an arrangement is reactive and the one place it is saved, and `ui` holds theme and per-view-instance state such as selection and filters, and a record under a fixed id that no instance has (`pdf-place`, the last places of the last 50 PDFs read). Both persist to `localStorage`, each under its own versioned key. Two tabs that change the same record, or the pages, at the same moment still end with the last write.

## Layer 3, view

**Primitives** (`ui/`): `Card`, `Chip`, `Meter`, `Table`, `Pane`, `Tabs`, `Sash`, `Empty`, `Toolbar`. Nothing here imports state or knows what a project is, and props are values and callbacks. A `Pane` is a header holding the view's title and its icon actions only, and a `bar` under the header for the view's other controls, so a view's controls sit in one place whatever the view.

**Shell** (`shell/`): the workbench. An activity rail on the left, drawn as VS Code's activity bar, whose icons switch pages and carry one badge each, a status bar along the foot under both, and one tree of panes with tabs, split any way and any depth, with sashes between the children of every split and one control on each child that collapses it to the split's edge. The shell renders the layout tree and does not import any view by name: views register themselves in a registry keyed by `ViewId`.

**Views** (`views/`): one folder per view, `views/<group>/<name>/`, holding its component and its partials; a group's folder that is full holds a subfolder of views, as `views/system/workbench/` and `views/system/machine/` do. A view reads selectors, composes primitives and writes its own instance state; it does not know where in the tree it sits and has no internal multi-pane layout, so Sessions is six views arranged by a saved default layout and not one view with three panes inside.

**Boundaries**, enforced by `tests/checks/tree/boundaries.test.ts` over the import graph:

| From | May import | May not import |
|---|---|---|
| `ui/` | `ui/`, `themes/`, `state/shared/words/text`, `data/prose/markdown` (the one Markdown document rule the server shares) | `state/*` otherwise, `views/`, `shell/`, `server/` |
| `shell/` | `ui/`, the state modules the rows of `tests/checks/tree/boundaries.test.ts` name (the client context, the layout, drag, palette, selection and navigation modules, the words, the terminals, and the language server state), `data/shapes/shapes` | any view by name, `server/` |

| `state/` | `data/model`, `data/shapes/shapes`, `data/file-ops` and the pure helpers with no reader and no I/O that `tests/checks/tree/boundaries.test.ts` lists with the reason each is shared with the server | `server/`, anything of layer 3 |
| `data/`, `server/` | `data/` | anything client-side |

Inside a layer the folders have an order from the top down, declared in `tests/checks/imports/order.ts`: a module imports its own folder or one below it, never one above, so no two folders of a layer import each other, type-only imports included, since a type a folder takes from a folder above it ties the two as an import does. `tests/checks/imports/cycles.test.ts` refuses any chain of runtime imports that leads a module back to itself, since the load order would then depend on which module is asked for first (`tests/checks/imports/cycles.test.ts`), and `tests/checks/imports/augments.test.ts` refuses a `declare module` block or a `/// <reference path>` naming a module of the tree, since an augmentation ties two modules in either direction and no order could hold it (`tests/checks/imports/augments.test.ts`). Process-wide state under `src` is refused, so every store is reached through the client context (`tests/checks/tree/boundaries.test.ts`). A view computes nothing a store's payload could be asked for: the filters, sorts, groupings, counts and joins over a payload are functions of the state folder that owns it, each with its own unit test.

## Layout as data

```ts
type ViewId   = 'focus' | 'projects' | 'archive' | 'venues' | ... | 'session-list' | 'terminal' | 'timeline' | 'changes' | 'agents' | 'customization'
type Instance = { id: string; view: ViewId; state: unknown; preview?: true }
type Layout =
  | { kind: 'split'; dir: 'row' | 'col'; sizes: number[]; children: Layout[]; folded?: number[] }
  | { kind: 'pane';  tabs: Instance[]; active: string }
  | { kind: 'page';  page: string }
type Workbench = { root: Layout; focus?: { path: number[] } }
```

A page is one tree. The shell renders it, a drop moves an `Instance` between panes, and opening a view appends an `Instance` to the pane `open/opening.ts` picks, which for a view opened for something is the pane `open/landing.ts` picks (head comment of `src/lib/state/workbench/layout/open/opening.ts`). `folded` holds the indexes of a split's children collapsed to its edge: a folded child keeps its share in `sizes`, so expanding gives back the width it had, and one child of a split is always left open. The saved arrangement is the serialised tree, and what a view keeps lives in each tab's own state, so two instances of the same view have separate state by construction.

Beside the pages the layout holds floats. A float is a workbench of one pane, addressed by its id wherever a page id is taken, so opening, closing, moving and activating a tab in it go through the operations a page's pane uses; it is never a page, so the rail, the Pages view and the page lists of the pane menu never list it, and a split inside it is refused. Its place is one of three shapes (`FloatPlace` of `src/lib/state/workbench/layout/model.ts`): free, docked to an edge, or a window of its own, which is a window of the desktop app or, in a browser, a browser tab at `/?float=<id>` that the press opening it makes. One float is docked to an edge, and docking a second merges its tabs into the first. `shell/panes/floats/FloatLayer.svelte` draws every float once, outside the block keyed by the page, so a switch of page never mounts a float's views again and a maximised pane of the page leaves the floats drawn.

The rule that keeps an emptied pane, which `docs/window.md` ("Where an opened tab lands") states, reaches the tree functions as a `KeepRule` the store hands over (`src/lib/state/workbench/layout/tree.ts`), so it holds whatever takes the last tab out: a close, a drag out, a move to another page, an edge drop, a record deleted, a view leaving the registry.

A page leaf shows another page at that spot, by id, and it is a leaf as a pane is: it folds, it takes a neighbour when a tab is dropped on its edge, and it holds no tab of its own. A page is drawn once on a screen so that no view is mounted twice, which is why a leaf or a drop that would break that is never offered (`docs/window.md`, "Inside a page").

## Theming

`tokens.css` and `themes.css` hold the colours ported from the cockpit, a type scale and radii set on VS Code's measures, and the theme blocks, which override tokens and nothing else, so no component knows a theme exists. The colours a component paints text with are computed, not authored: `src/lib/themes/derive.ts` mints the `--on-*` and `-txt` tokens, the selected-row surface, the scrollbar's colours, the Focus lanes' surfaces and text, the fill under a hovered or open item of the orange status bar while debugging (`--c-orange-hover`), and the Seti icon colours for every theme, and `tokens.css` gives them the default theme's values on `:root` so the first paint draws them before a theme is applied (`src/routes/+layout.svelte`). VS Code Dark Modern and Light Modern are blocks authored for oculus rather than ported, which is why a contrast failure in one of them is fixed in the block and a failure in a ported one is a finding about the port. The contrast test walks every text-on-background pair the primitives declare, under every theme, and fails below 4.5:1; it never repairs a colour or loosens the threshold (`tests/checks/look/contrast.test.ts`). Primitives use tokens only; a raw hex in a component is a test failure.

The wallpaper is one image behind everything, served by `api/wallpaper` from a directory `appearance.yml` names under the hub and nothing outside it, and it is on where a theme's class carries `rice` or under every theme where the config says `all`. The surfaces over it follow one rule: one translucent layer over the picture and never two, since two such layers read as one nearly solid one, so each component that paints a surface declares under `body.wall` what its surface does, and a floating surface is more solid than a panel because it is read through a pane as well as through the picture (`src/lib/themes/tokens.css`, `src/lib/state/shared/words/appearance.ts`). A blurred surface is the containing block and the stacking context of every fixed thing inside it, which is why a tooltip, a menu, the notification centre, toasts and confirm are drawn on the document body through bits-ui's `Portal`.

The icon set is Lucide at one stroke weight, shipped as the `lucide-static` package, and `icons.yml` maps every name of the glyph vocabulary to one of its icons; the server reads each mapped drawing once per config load and pushes it with the rest of the configuration, and `ui/display/Glyph.svelte` draws it inline in the colour of the text beside it. The capsule belongs to a status word, the project type, a filter toggle and the badge of a view in the Views catalogue, and everything else a surface lists, a dataset, a person, a pillar, a deadline, a count, is `ui/controls/Tag.svelte`, the same glyph and words with no capsule, so the capsule keeps its one meaning (`ui/controls/Chip.svelte` and `Tag.svelte`). A tag that stands for a state keeps that state's hue as the colour of its words and of its mark, and a tag that stands for a name or a count carries none and is muted.

The glyph vocabulary is `glyphs.yml`'s one `glyphs:` map, each name with the ASCII stand-in a terminal theme draws in place of its icon, one to three printable ASCII characters (`iconFindings` reports a value that is not). A terminal theme draws the stand-ins unless the viewer turns Icons on, and the swap is a lookup where a glyph renders, in `ui/display/Glyph.svelte` and in `ui/controls/Chip.svelte`'s bracket rule, and never a pass over the document. No string under `config/` carries a glyph: a text that shows one draws a `Glyph` beside its words, with any separator drawn by the markup and hidden from a screen reader, a mark badge's hover says what the mark means in the words its registration's `badgeMark` names, and the check or cross that opens a venue's `wos:` or `scopus:` is read as a yes or a no by `data/snapshot/indexing.ts` and drawn as the `check` or `cross` glyph. A theme row whose `glyph:` is missing, empty or not a glyph name, and a row repeating a theme's name, are findings of `data/sources/config/themes.ts`, and the picker draws such a row with its words alone. Glyph and icon names are read as own keys, so an inherited name such as `constructor` is no name. KaTeX, the terminal and Markdown drawn from hub files carry their own content.

## Hot reload

Three kinds of change, three mechanisms, no restart in any of them.

| Change | Mechanism |
|---|---|
| a component, a selector, a primitive | Vite swaps the module in the open page; state survives |
| a server module or an endpoint | Kit's dev server reloads it; the socket reconnects, and after a reconnect the page takes the first message of every channel whatever its version, since a restarted server numbers its channels from the start again |
| a YAML file in the hub or in `config/` | the watcher rebuilds and pushes; identical in production |

A route reads the configuration through `locals.config()`, which takes the parse of `config/` the server context holds (`configCache`, `src/lib/server/root/process/config-cache.ts`), parsed again only when a file of the folder was added, removed or written since the last parse, which a stat of each entry tells, and never cached when that stat fails, keeps the one read it took for the rest of the request, and a server module takes it from its route as an argument rather than reading it itself, so an edit to `config/` reaches every route on the next request, in production too.

The pollers are built from the configuration read when the server starts, and every config push hands them the settings read again through `server/root/live-settings.ts`, each group by its own reader. A value that its catalog entry refuses hands the poller that setting's `default` and is a finding naming the key, so a bad value costs one setting and never the poller; a push whose merge dropped `behavior.yml` keeps the settings in force.

`local.yml` is read again whenever it changes, by the one watch on it, `server/root/watch/local.ts`, and every key holds at once: the context's `local` takes the new values in place, so a route that reads `locals.server.local` follows with its next request, and each object built from a changed key, an account's poller among them, is closed and built again. A changed `port` moves the server of the same context to the new port, so the hub, the terminals and the token stay: the server lets a request in flight finish for up to five seconds before it ends what remains, so a request that itself changed the port is answered, and only once the server listens on the new port is the new address published (`src/lib/server/root/mover.ts`). The page that was open follows when its own port is the port of the address it holds and the new address answers it (`src/lib/state/client/socket.svelte.ts`), and because the browser keeps `localStorage` per origin it carries the arrangement and the settings in `window.name` to the page at the new address (`src/lib/state/workbench/layout/saved/carry.ts`). A value that a watcher cannot be built from is logged with its key and stays at the value in force, and the user's side of this is `docs/configuration.md`, "`local.yml`".

## Apps added while oculus runs

An app is a folder of web files (a page and its scripts) that the reader puts in one of two places: a folder of this machine, or the `.oculus/apps/` folder of a root shown in the file browser. An app of the machine's folder is a machine app and an app of a root's folder is a root app. Views found at build time stay as they are; an app is a second kind of view, which oculus finds while it runs, lists in the view catalogue, and draws in a tab inside a sandboxed frame once the reader has approved it. It needs no build and no restart. A root app is written by whoever writes to its root, a `git pull` included, so it reaches less than a machine app, cannot be kept approved while it changes, and names only its own root; each paragraph below says what differs for the two kinds, and a rule that names neither kind holds for both.

**Where an app lives.** A machine app is a direct subfolder `<apps_dir>/<name>/` that holds a file `app.yml`. `apps_dir` in `config/local.yml` names the folder, `~/.oculus/apps` when absent, resolved at the call as `calendar_dir` and `mail_dir` are and read through `loadLocal` as `appsDir`. A root app is a direct subfolder `<root>/.oculus/apps/<name>/` that holds a file `app.yml`, for each root shown in the file browser, whether or not the root is a git repository. The roots shown in the file browser are the hub, the engine, the configured roots and the current workspace's saved roots, in that order, with `~/workspace` under the key `workspace` when no root beside the hub exists (`browserRoots`, `src/lib/server/files/roots.ts`, `workspaceRoots`, `src/lib/server/files/fs.ts`). The folder that holds apps, the machine's or a root's, is an apps folder, and the folder of one app is its app folder. The hub is a root like any other, so `<hub>/.oculus/apps/board/` is the root app `board` of the root `hub`. The root `engine` is oculus's own `config/` folder, which holds `local.yml`: it holds no apps and its `.oculus/apps/` is never read. Not an app: a file directly in an apps folder, a folder whose name starts with a dot, and a folder with no `app.yml`, which is ignored without a finding since nothing in it claims to be an app.

An `app.yml` that does not parse or is not a map of keys is a finding (`findings.file.does_not_parse`, `findings.file.not_a_map`, keyed as the findings below are, with the folder's name in place of the app's) and the folder is not an app. In this section a real path is the path as the disk stores it, letter case included, as Node's `fs.realpathSync.native` gives it (`realpathSync` keeps the case the caller typed, `src/lib/server/core/paths.ts`), and every real-path check of the section compares that path; the real path of a file that does not exist is the real path of its deepest existing folder followed by the remaining segments, and a link that points at nothing is read by its target text. A folder that is itself a link is followed once and listed by its real path. A root's `.oculus/apps` that is itself a link is followed once in the same way and must resolve inside the root's real path: one resolving outside the root is `findings.apps.folder_outside` and none of its apps is offered. The apps folders are taken in one order, the machine's first and then each root's in the order the file browser shows the roots, and an apps folder or an app folder whose real path a folder taken before it already holds is `findings.apps.repeated`: one real folder reached through two roots (a link, or two root keys naming one folder) belongs to the root that comes first, and a folder that is both `apps_dir` and a root's `.oculus/apps/` holds machine apps and gives that root the finding.

Inside an app's folder a symbolic link is not part of the app: it is neither hashed nor served, and a dot-named file or folder is not part of it either.

**How an app is named.** A machine app's view id is `app:<name>` and a root app's is `app:<root key>/<name>`, where `<root key>` is the key the file browser gives the root. `name` matches `^[a-z][a-z0-9-]{0,39}$`, which holds neither `/` nor `@`, so the text after the last `/` of a view id is always the name, and a root key that holds `/` or a space parses. Two roots can each hold an app of one name, and a machine app can share its name with a root app: a folder `notes` in the machine's folder, in `cathedra` and in `ordo` gives `app:notes`, `app:cathedra/notes` and `app:ordo/notes`, three finding keys (`apps[notes]`, `apps[cathedra/notes]`, `apps[ordo/notes]`) and three approvals. The view id names an app wherever a bare name would: the header `x-oculus-app`, the change record, the store the server finds for a write, the approval, and the finding key `apps[<view id without app:>]`, made with the folder's name when the manifest's name is not valid. A finding about a root's whole apps folder is keyed `apps[<root key>/]`. The address of a machine app is `/apps/<name>/<key>/<path>` and of a root app `/apps/@<root key>/<name>/<key>/<path>`, where `<key>` is the app's address key (the field `key` of its row). `@` starts the second segment of a root app's address and no name starts with it, and the shared files' segment `-` (below) equals neither an `@` segment nor a name, so the three forms never meet.

A root key that holds a character an address cannot carry, such as a space or `/`, is percent-encoded in the address (`my repo` as `my%20repo`, so `app:my repo/todo` is `/apps/@my%20repo/todo/<key>/index.html`) and compared decoded; the view id carries the key as it is, and the header `x-oculus-app` carries the view id with the root key percent-encoded as the address does, since a header value cannot carry every character a root key can. Where an app's title is drawn (the view catalogue, a tab, the approval panel), a root app's title is followed by its root's key in parentheses, so three apps titled Notes read "Notes", "Notes (cathedra)" and "Notes (ordo)", and the approval panel gives the app's folder path.

**The manifest.** `app.yml` is one map of keys:

```yaml
name: notes
title: Reading notes
description: It lists the venues and files a note under an entry.
glyph: page
bridge: 1
entry: index.html
reads: [portfolio, files]
writes: [entry, new-idea]
connects: [https://api.example.org]
```

`name`, `title` and `bridge` are required. `name` matches the pattern above and equals the folder's name. `title` is 1 to 40 characters, trimmed, with no control character. `bridge` is `1`, the version of the bridge below. `description` is optional, up to 200 characters, and is shown at approval. `glyph` is optional, a name in `config/catalogs/glyphs.yml` other than `app`, the group heading's glyph, which no view of a group carries (`config/layout.yml`); an absent, unknown or reserved name draws the catalog's `apps.glyph`, whose value is the glyph `app_view`, and an unknown or reserved one also gets `findings.apps.glyph_unknown` while the app is offered. `entry` is optional, `index.html` when absent: a `/`-separated relative path whose segments are non-empty and do not start with a dot, ending in `.html`, and naming a file of the app. `reads` and `writes` are optional lists, empty when absent, of names from the open sets below, each name once; the channels open to a root app are fewer than those open to a machine app, and `app-store` is not a name `writes` can hold. `connects` is an optional list, empty when absent, of the outside origins the app may fetch from, for a machine app and a root app alike: `https://host` or `https://host:port`, with no user name, path, query or wildcard, each origin once, compared after a trailing slash is dropped.

`http:` is accepted only for `localhost` and `127.0.0.1` on a port other than oculus's own, and a trailing slash alone (`https://api.example.org/`) is accepted and stored without it. A `wss:` origin is refused. A key this list does not name refuses the app (`findings.apps.key_unknown`), since a key of a later version that was silently ignored would leave the reader approving something other than what runs.

**What refuses an app.** Each of these is a sentence in `config/text/findings.yml` under `findings.apps`, shown in the Findings view keyed `apps[<view id without app:>]`, and each leaves the app not offered, not registered and not served: `name_empty` (absent or empty), `name_shape` (outside the pattern, which also covers every reserved form, since the shared address segment `-` below cannot match it and no name starts with `@`), `name_not_folder`, `key_missing`, `key_unknown`, `title_shape`, `description_shape`, `bridge_unknown`, `entry_shape`, `entry_missing`, `list_repeated` (a name twice in `reads` or `writes`, or an origin twice in `connects`).

Further findings of the same kind are `channel_unknown` and `write_unknown` (a name in neither the open nor the closed set), `channel_closed` (a channel closed to every app, or, for a root app, `inbox`, `calendar`, `sessions` or `usage`; its sentence names the channel, says whether it is closed to every app or to a root app, and gives the reason, which is `findings.apps.carries.<channel>`, what the channel carries), `write_closed` (a name in the closed set, and `app-store`, which every app is granted for its own store and cannot ask for), `list_shape` (`reads`, `writes` or `connects` that is not a list of names), `file_unreadable` (the manifest or a file of the folder cannot be read when the hash is made) and `connect_shape` (an entry of `connects` that is not an origin of the form above: one with a user name, a path, a query or a wildcard, a scheme other than `https:` unless it is `http:` to `localhost` or `127.0.0.1`, `wss:` included, or an `http:` origin on oculus's own port) and `too_large` (more than `apps.max_files` files or `apps.max_mb` megabytes, 500 and 20). Two findings are about a whole apps folder, keyed `apps[<root key>/]`: `folder_outside` and `repeated` for a whole folder. A third, `apps_dir_not_folder`, is about the machine's folder: `apps_dir` names a file, there are no machine apps, and the finding is keyed `apps_dir` and names `local.yml`.

Two folders of one apps folder whose manifests claim one name resolve by `name_not_folder`: the folder that carries the name is the app, the other is refused, and neither wins by order. A manifest that asks for a channel or a write oculus does not have, or for one of the closed sets below, is refused when the folder is read, before there is anything to approve.

**How oculus finds it while running.** One watcher module, `server/root/watch/apps.ts`, owns the `fs.watch` handles of the real path of `apps_dir` (recursive), of the real path of `.oculus/apps` in each root shown in the file browser except `engine` (recursive), of the real path of each app folder that is itself a link (recursive, so an edit in a linked folder is seen), of the folders that hold the stores of the apps it lists (`~/.oculus/app-data` and `<root>/.oculus/app-data`, each not recursive), and of `approvals.json` itself by its path, opened again after every event since a write by rename replaces the file; it never watches `~/.oculus` as a whole, whose other files change on every write. It follows the roots as the file browser gains and loses them: it reads `browserRoots` again on a `config` push and when the saved workspaces file changes, which it polls with `pollFile` as the git watcher does (`server/root/watch/git.ts`), so a root added in the page is read at the next tick and a root that leaves the file browser loses its handles. It debounces with lodash's `debounce` and a maximum wait as every watcher does, and rereads every app on a change: the manifest, the walk of the app's regular files (path, size, modification time and change time of each, recorded), the content hash, whether the approvals file holds it or the app is kept approved, and the store file's size and version (computed without parsing the file).

It reads `local.yml` again when that changes, as accounts are, and follows a new `apps_dir`. When `apps_dir`, a root's `.oculus/apps` or the store folder of a listed app does not exist, one timer looks again at every such folder every two seconds and starts watching each when it appears; a missing folder is no finding, and a root with no `.oculus/apps` is looked at again as the machine's missing folder is. An absent `approvals.json`, which is the case until the first approval, is looked for the same way and means no app is approved; the approve route also tells the watcher after its own write, and the write route does the same after a store write. The server context holds the result as `rows`, `findings` and `folders`, and the watcher publishes `{ rows, findings, folders }` on the channel `apps` when the result differs from the held one. A row is `{ name, root, title, description, glyph, folder, entry, reads, writes, connects, files, bytes, hash, approved, kept, key, storeBytes, storeVersion, storeFile }`: `root` is the root key, empty for a machine app; `folder` is the app's real folder path; `key` is the address key, empty unless the app is approved; `kept` says whether the app is kept approved; `storeBytes` is the size of the app's store file in bytes, 0 when the file is absent; `storeVersion` is the first 16 hex characters of the SHA-256 of the file's bytes, and the empty string when the file is absent; `storeFile` is the path the store is written to.

A store path that is a folder or cannot be read counts as absent, with 0 and the empty string. A file over `apps.store_max_kb` is not hashed whole: its `storeVersion` is the first 16 hex characters of the SHA-256 of the text `<size>:<modification time in ms>`, so a hand-placed file over that limit costs the watcher one stat. An empty file is present, with `storeBytes` 0 and `storeVersion` `e3b0c44298fc1c14`, and its value is `null` since it does not parse. The row holds no store value, because a channel publish sends the whole payload to every subscriber (`src/lib/server/core/channels.ts`), so a value in the row would reach every page at each store write of any app; the page makes a fetch of the value (below). `folders` is the real path of every apps folder the watcher holds. The page always subscribes to `apps`, and the Findings view lists the channel's findings beside the others.

**The first frame.** The list rides with the page data as the collection keys do: `+page.server.ts` returns `apps: { rows, findings, folders, version }` read off `locals.server`, and `+page.svelte` calls `registerApps(client.registry, data.apps.rows)` in the same untracked block that calls `registerCollections`, with the `apps` entity seeded at that version so an older push replayed from before does not replace it. The rows carry no store value, so the first frame carries none, and a tab reads its store when it mounts, through `getStore()`. A saved layout that names `app:notes` or `app:cathedra/notes` on a machine that has the app therefore draws its tab on the first frame, never as an unknown view and never closed for a frame. Afterwards one effect calls `registerApps` for every push of the `apps` channel, and a second effect of `+page.svelte` reads `data.apps`, as the token's effect beside it reads `data.token`, seeds again, untracked, whenever a load hands new page data, and registers the rows the page holds after the seed, so a seed older than the rows held registers nothing older; the load runs again only through `invalidateAll` after a write met a 403 (the load's comment in `+page.server.ts`, `renewToken` in `writes.svelte.ts`). After a server restart the socket reconnects and takes every push (`open` in `socket.svelte.ts`), so the `apps` push carries the keys of the new process.

**The view and the catalogue.** An app's view id is the one above. Built-in view ids and collection keys are bare words, so an app named `focus` or `funding` is `app:focus` and `app:funding` and meets neither. `registerApps` sits beside `registerCollections` in `routes/views.ts`, finds the module that exports `appRegistration` (`views/apps/frame/AppFrame.svelte`, the one component every app is drawn by) and registers one registration per row. `appRegistration` is a name no collection factory uses: `registerCollections` calls only a module whose export named `registration` is a function (`routes/views.ts`), and `AppFrame.svelte` exports no `registration`, so a config push runs `registerCollections` alone and neither calls the app factory nor unregisters an app, and the tabs of every real app are left as they are. The registration is:

```ts
{ id: row.root === '' ? `app:${row.name}` : `app:${row.root}/${row.name}`, label: 'apps.label', glyph: 'apps.glyph',
  words: row.root === '' ? row.title : `${row.title} (${row.root})`, glyphName: row.glyph,
  group: 'apps', order: index,
  badgeGlyph: () => (!row.approved ? 'lock' : row.kept ? 'edit' : ''),
  badgeMark: row.kept ? 'apps.editing_mark' : 'apps.unapproved_mark' }
```

`Registration` has two optional fields, `words` and `glyphName`, holding the title as drawn (the manifest's literal title, and for a root app the root's key after it) and the manifest's glyph name; `registrationLabel` and `registrationGlyph` return them when present and look the catalog key up when absent. A catalog key taking the title as its argument is not used, because those two functions look a key up with no arguments at every place a tab or the catalogue draws one, and each place would have to learn arguments. `badgeMark` (`state/workbench/navigation/registry.ts`) stays a catalog key; `registerApps` runs again on every push of the `apps` channel and passes the key that fits the row, so the hover words follow the mark: the lock mark says the app is not approved, and the mark drawn while an app is kept approved says it is kept. `apps` is an id in `nav_groups` of `config/layout.yml`, with the label Apps, the glyph `app` and no chord, so its views are reached by the direct-chord prefix and a digit. Every group is one rail page keyed by the page's arrangement key (`config/layout.yml`), so the group is also a `rail:` button `{ label: "Apps", glyph: app, page: apps }` and an arrangement `apps` of one empty pane (`view: []`), where a tab opened for an app lands. The rail button is always drawn; the catalogue draws the group only while it holds a view.

`order` is the app's place in one list: the machine apps by name, then the apps of each root by name in the order the file browser shows the roots.

**When an app is added, changed or removed.** An added app is registered and appears in the catalogue. A changed app keeps its id and its tab; its hash differs, so its approval does not hold, a root app changed by a `git pull` included, the frame is taken out of the tab and the approval panel (below) is drawn in its place with the sentence `apps.changed`, and the tab's state is kept; a machine app kept approved (below) is the exception. A removed app is dropped from the registry with `dropView(id)`, which removes the registration and closes no tab, where `unregisterView` closes the tabs of a removed collection; the tab then draws as an unknown view (`ui.unknown_view`, "Unknown view: app:notes"), as a saved tab of a renamed view does, and draws the app again when the folder comes back. Tabs stay because a removed folder is as often an editor saving by replacing, a sync in progress or a rename as a decision, and closing would lose the tab's place and its state. The registry is a `SvelteMap` that `registerView` and `dropView` write and that `views` and `viewFor` read, so the catalogue, the palette and the tab bodies redraw for a registration made while the page runs. A saved layout naming an app's view on a machine without the app draws the same unknown view and loses nothing.

The same holds for a root app whose root leaves the file browser: its tabs stay, draw the unknown view ("Unknown view: app:cathedra/notes") and keep their state, and the root added again draws the app again at once when its files are unchanged and asks when they changed. A root app's tab keeps in its saved state the real folder of the app it shows, beside its value (`{ value, folder }`), and draws the app only while the registered app of its view id has that folder. Root keys are per workspace, so after a workspace switch a key can name another folder; a tab whose key names another folder draws the unknown view, keeps its state, and never draws the other folder's app with the first app's value.

**How it is served.** The address is the one above, a route outside `/api/`, so `refused()` in `src/hooks.server.ts` does not judge it and it is not added to `UNGUARDED`: a frame with an opaque origin sends `Sec-Fetch-Site: cross-site` and an `Origin` of `null`, which `sameOrigin` refuses, so an address under `/api/` would refuse the frame its own files. Because the route is not guarded, any page in the browser can request it, and the answers carry `Access-Control-Allow-Origin: *` (the frame's module scripts and fetches are CORS requests from an opaque origin and need it), so what keeps another page from reading an app's files is `<key>`: the first 32 hex characters of HMAC-SHA256, keyed by a second secret minted at server start beside the write token and never sent to a page, over `<view id>:<hash>`, which names the root as well as the app. The address key is in a row only while the app is approved, changes with the app's files and with each server process, and gives access to that app's files alone. The shared files are at `/apps/-/penpal.js` (the installed `penpal` package's `dist/penpal.mjs`, the file the page imports) and `/apps/-/oculus.js` (the client half of the bridge, a file of the tree).

These two are public and have a rule of their own: the method is GET or HEAD, the origin of the request's URL names this machine, and the path after `/apps/-/` is exactly `penpal.js` or `oculus.js`; they need no app, no key and no approval, and they are sent with the content type, `nosniff`, `no-cache` and `Access-Control-Allow-Origin` headers of an app file and without the policy below, which is a document's.

A request for an app's file is answered only when every one of these holds, and refused with an empty 404 that says nothing about the disk otherwise: the method is GET or HEAD; the origin of the request's URL, which Kit builds from the `Host` header, names this machine (`allowedOrigin` on that origin, `auth.ts`); the `Origin` header is not the input, since a module script or fetch from the opaque frame sends `Origin: null`, which `allowedOrigin` refuses, and a navigation sends none; the check on the `Host`-built origin is also what stops a rebound host name.

Further, a request is answered only when a root part of the address, when there is one, decodes to the key of a root shown in the file browser other than `engine`; `<name>` matches the pattern and names an app of that root, or of the machine when there is no root part, in the held state that is approved or kept approved; `<key>` equals the app's current address key; the path has no segment that is empty, `.`, `..` or dot-led and holds no backslash or NUL after decoding; the path is a file of the app's recorded list; the file's size, modification time and change time (`ctime`, which `cp -p` and `rsync -t` cannot set) equal the record's, and when any of them differs the app is hashed again and the file is served only if the hash still equals the approved one (or, for an app kept approved, the manifest still equals the kept one), so a file edited after the last rebuild is refused until the watcher republishes; and the file's real path lies inside the app folder's real path, compared with a separator so a sibling folder with a longer name does not pass (`inside`, `server/core/paths.ts`). A request for `../../.ssh/id_ed25519` fails the segment rule, then the recorded list, then the real-path check. A link inside an app's folder is not in the list.

The content type comes from a fixed table by extension (html, js, mjs, css, json, svg, png, jpg, gif, webp, woff2, txt, wasm) and is `application/octet-stream` otherwise, with `X-Content-Type-Options: nosniff` and `Cache-Control: no-cache`.

Every app file is sent with this policy, where `<host>` is the host and port of the request's URL from its `Host` header, checked as above, written with no scheme because behind adapter-node the request's protocol defaults to `https` (`node_modules/@sveltejs/adapter-node/files/handler.js`), so an origin built from the request could name the wrong scheme, while a host source matches the scheme the document was loaded over, `<base>` is `<host>` followed by the app's address up to and including its address key (`<host>/apps/<name>/<key>/` for a machine app, `<host>/apps/@<root key>/<name>/<key>/` for a root app, the root key percent-encoded), `<shared>` is `<host>/apps/-/`, and `<connects>` is the manifest's `connects` origins, separated by spaces, and nothing when there are none:

```
Content-Security-Policy: sandbox allow-scripts allow-downloads; default-src 'none'; script-src <base> <shared>; style-src <base> 'unsafe-inline'; img-src <base> data:; font-src <base>; media-src <base>; connect-src <base> <connects>; base-uri 'none'; form-action 'none'; frame-ancestors <host>
```

The `sandbox` directive makes the document opaque wherever it is opened: in the frame, by a direct visit to its address, or in a popup. The sources are named by address and never `'self'`, because whether `'self'` matches in an opaque document is not settled. There is no inline script, so an app loads its code with `<script type="module" src>`. `allow-downloads` lets an app save a file it built from what it read, an export. `allow-popups`, `allow-popups-to-escape-sandbox`, `allow-same-origin`, `allow-top-navigation`, `allow-forms`, `allow-modals` and `allow-pointer-lock` are never in the directive.

**The frame.** The iframe of an app is drawn by the frame layer, outside the pane tree, and the view draws only the place for it. `AppFrame.svelte` draws a slot (`ui/tabs/FrameSlot.svelte`) and describes its frame to the workbench's tab frames (`ui/tabs/tab-frames.svelte.ts`): the kind `app`, the address, the title, a key, the `color-scheme` and what to do with the element once it exists. `shell/frames/FrameLayer.svelte` draws one `<iframe sandbox="allow-scripts allow-downloads" allow="" referrerpolicy="no-referrer">` for each tab id that has a description, with `src` set to the app's address for `entry`, lays it over its slot's rectangle on every animation frame, and hides it while its slot is not on screen. The layer exists because moving an iframe element or drawing it again loads its document again, and a change of layout (a pane added, a tab moved, a page switched) draws the panes again: a frame inside a pane would lose the app's in-memory document at each. A frame is removed only when its tab closes, when the tab no longer shows the app's view, when the row of the app is gone or no longer approved, or when the app did not answer in time (`apps.load_failed` is drawn in its place), or on purpose when the app is loaded again (the control of `apps.load_failed`, or a changed address key); a view drawn again, a pane drawn at a new place and a tab moved into a floating pane remove none.

The sandbox is fixed by the kind, so a view cannot ask for another; `allow-same-origin` is left out on purpose: with it the frame would carry oculus's origin, would read `window.parent` and the write token, and would be admitted by `sameOrigin`. The layer has no box and no stacking context of its own, so a frame is ordered with the floats and the menus by its own depth: one above its floating pane when the tab is in a floating pane, and 0 for a tab in a page, which is under every floating pane and every menu. The page itself sends `Content-Security-Policy: frame-src 'self'`, added by `handle` to the page's answer, because a script inside a sandboxed frame can otherwise navigate its own frame to any address with the reader's data in the query; with the policy such a navigation is refused, and the two other frames the views draw (`Document.svelte`, `File.svelte`, both through the same layer) load from this origin. The policy also governs the Document view's frame, where a link inside a manual that leaves for an outside site would stop loading in the frame.

The Document view therefore opens such a link itself: it listens for a click in its frame's document, which is same-origin and which it already reaches for the right-click (`Document.svelte`), finds the link from the event target by its shape (`target.closest` is a function), since an element of the frame's own document is not an `Element` of the page's realm and `instanceof Element` is false for it, and opens an address of another origin in a browser tab with `window.open(address, '_blank', 'noopener')` (`Document.svelte`), as its own control for the page does. While a sash or tab drag is in progress, and while a layer over the pane is up, the frame takes no pointer (`pointer-events: none`), so the drag keeps its pointer moves. The frame element takes `color-scheme` from the body's computed value, read again one frame after the theme, the wallpaper, the overlay or the text size changes: `dark` under a dark theme and `light` under a light one, which the base `body` rule of `tokens.css` declares so the system's mode never reaches the app. `oculus.js` puts `color-scheme: light dark` on the app's root through a style sheet placed before the app's own, so an app with no scheme of its own follows the frame and draws its controls in the theme's scheme, and an app that declares a scheme keeps it.

The pane the keyboard addresses while a frame holds the focus is the pane of the frame's slot (`focusedPaneElement` in `src/lib/shell/keys/workbench-keys.svelte.ts`), and a key the bridge forwards from the frame and the right-click of the Document view are sent from the slot, so the workbench's keys and menus find the pane. The Electron window keeps Node integration off, subframes included.

**What an app may read.** The bridge is `penpal` 8.0.1. It is owned by one frame instance: made in an effect when the frame element mounts and destroyed by that effect's cleanup, never held at module level, so every remount makes a new one. The page's side is `new WindowMessenger({ remoteWindow: frame.contentWindow, allowedOrigins: ['*'] })` with `connect({ messenger, methods, timeout })`; `'*'` is required because the frame's origin is `null`, and the guard is penpal's check that a message's `source` is the frame's window, together with the manifest lists below. The app's side is loaded from `/apps/-/oculus.js`, which imports `/apps/-/penpal.js` and builds its messenger with `remoteWindow: window.parent` and `allowedOrigins: [new URL(import.meta.url).origin]`, the page's origin, because penpal's default is the frame's own origin, which is `null`. An app calls:

```js
import { connect } from '/apps/-/oculus.js';
const oculus = await connect({ onChannel: (name, version, payload) => draw(name, payload), onTheme: (theme) => paint(theme), onStore: (value) => redraw(value) });
const { payload } = await oculus.read('portfolio');
await oculus.write('entry', body);
await oculus.setStore({ seen: ['a', 'b'] });
await oculus.open({ view: 'venues' });
```

The page exposes `read(channel)`, `getTheme()`, `getState()`, `setState(value)`, `getStore()`, `setStore(value)`, `write(kind, body)`, `open(target)` and `key(init)`; the app exposes `onChannel(channel, version, payload)`, `onTheme(theme)` and `onStore(value)`. `read` answers `{ version, payload }`, the newest the page holds, for a channel in the manifest's `reads`; after that the page calls `onChannel` on every change of a declared channel, at most one call in flight per channel with a newer payload replacing a queued one, the payload being `$state.snapshot` of the entity, or for a root app of its root's part of it. A refusal rejects with one fixed word as a plain string, never an `Error` object: penpal sends a rejected `Error` with its name, message, stack and `penpalCode` (`dist/penpal.mjs`) and any other rejected value as it is (`dist/penpal.mjs`), so a string carries no stack or code of the page to the app. The words: `not_declared` (a channel not in `reads`, or a write of a kind the manifest does not declare), `closed`, `too_large`, `not_json` (a value of `setState` or `setStore` that is not JSON), `rate`, `declined` (the reader refused a confirmation), `missing` (an `open` target that is not there, or the store of an app the server holds no row of, which is a 404 of the store route on every try while the page holds a row, and no row at all otherwise), `refused:<reason>` and `failed:<status>`.

`refused:<reason>` follows from an answer of the write route that is a refusal: the `reason` of the first entry of the `refused` list of a 200 answer (`methods.ts`), or the `kind` or other word of `error` in a 4xx answer of any app write, the 403 `{ error: 'kind' }` of the gate included. `failed:<status>` is any other failed call: a write route answer of another status, with the status after the colon, and a read of the store that got an answer other than 200 or 404 (the status after the colon), got no answer, or saw the store change under all five tries (`failed:0`). The reader also sees `apps.refused_read`, `apps.refused_write` or `apps.refused_open` once per name and mount as a notice in the notice centre, naming the app.

Open to every app: `portfolio`, `feeds`, `hpc`, `audit` and `config`, each whole; they carry the hub's data, the job queue, the findings and the configuration, which includes this machine's host name and address (`ConfigPayload.host`, `data/model/index.ts`). Also open to every app, and whole for a machine app: `git`, which carries the state of the repositories (branches, status, commit subjects), and `files`, a notice that a served root or the bookmarks file changed and no file content. A root app gets the part of these two that belongs to its root, which the page builds from the payload it holds. `git` is `Record<string, GitState>` (`model-sessions.ts`), keyed by the folders that `repositoryRoots` gives, which are the roots' folders (`src/lib/server/files/roots.ts`): a root app gets a record holding the one entry keyed by its root's folder, `onChannel('git')` is called for it only when that entry changed, and a repository below the root's folder has no entry, unless its folder is itself a root shown in the file browser, whose entry belongs to that root. `files` is the notice `{ root, folders?, bookmarks?, workspaces? }` (`model-sessions.ts`, `watch/git.ts`, `watch/bookmarks.ts`) whose `root` is a root's folder and whose `folders` names the folders of it that changed: a root app is called only for a notice whose `root` is its root's folder and whose `folders` is not an empty list, `read('files')` answers the newest such notice or null, and the bookmarks and workspaces notices (`root: ''`) reach machine apps only.

`apps.read.files` and `apps.read.git` say what a machine app gets, and `apps.read_root.files` and `apps.read_root.git` say what a root app gets. Open to a machine app and refused for a root app (`findings.apps.channel_closed`): `inbox` and `calendar` (other people's mail subjects, senders and message previews, and calendar titles, times, places and links), `sessions` (transcript-derived titles, prompts, paths and events) and `usage` (account labels and limits); `apps.read.<channel>` says plainly what each carries, and the approval panel of a machine app that declares one shows it. Closed to every app: `apps`, which carries every approved app's address key, `processes`, which carries the machine's process table (program names, arguments and folders), and every `pty:<id>` (whatever a terminal printed, secrets included). A channel added to oculus is closed to apps until this section names it. The theme: `getTheme()` and `onTheme` carry `{ name, tokens, wall }`, where `name` is the theme's class on the body, `tokens` is every custom property `tokens.css` declares as the body's computed value, and `wall` is whether the body carries `wall`. The page reads them again one frame after the theme or the wallpaper setting changes, once the body carries the new class, as the editor and the terminal do, and calls `onTheme`; `oculus.js` writes the tokens on the frame document's root element and toggles a `wall` class there, so an app keys its surfaces on it as the built-in ones key on the body.

With the wallpaper on the frame element paints nothing and a document the app leaves transparent shows the picture; the app's own surfaces are the app's to paint.

**What an app keeps.** Two JSON values. The tab's instance state, saved with the layout: `getState()` and `setState(value)` read and write one value, in the instance's state as `{ value }` (a root app's tab also keeps its folder, as above). `setState` rejects `too_large` above `apps.state_max_kb` (64) and rejects a value that is not JSON. Two tabs of one app keep separate values by construction, and a moved tab keeps its value. The app's store: one value for the app, shared by every tab of it in every window. `getStore()` answers the value, and `null` when the store file is absent, does not parse or is over `apps.store_max_kb` (256; a KB in this section is 1024 bytes); `setStore(value)` replaces it. A machine app's store is the file `~/.oculus/app-data/<name>.json` and a root app's is `<root>/.oculus/app-data/<name>.json`, created with its folder by the first write. It lies outside the app's folder, so writing it never changes the app's content hash or its approval. For a root app the store is a file of the root, tracked by git unless the root ignores `.oculus/app-data/`. `setStore` is a write of the kind `app-store` (below): it rejects `too_large` above `apps.store_max_kb`, rejects a value that is not JSON, counts toward `apps.writes_per_min`, and rejects `refused:<reason>` when the file cannot be written, which is what a root that cannot be written gives.

The server watches the store files, and a change to one, whoever made it (another tab, History's undo, a pull, a hand edit), reaches the page as a new `storeVersion` in the app's row on the `apps` channel (the page compares that alone), and the page then makes a fetch (below) and calls `onStore(value)` in every tab of the app in every window, the tab that wrote included. A write of a value equal to the one the file holds, as JSON values with object keys in any order, writes nothing, records nothing in History and answers success, so the file's bytes and `storeVersion` stay as they are whatever its formatting, and nothing reaches the page; a file that is absent, does not parse or is over `apps.store_max_kb` holds no value, so a write to it always goes ahead. A tab that mounts reads the value with `getStore()`. A fetch is `GET /api/app-store?view=<view id>`, the page's read of one app's store, and it answers `{ version, value }`: `value` is the parsed store, `null` when the file is absent, does not parse or is over `apps.store_max_kb`, and `version` is the file's `storeVersion` at the read. The route answers GET only (SvelteKit answers 405 to any other method, since the route module exports no other verb) and writes nothing, so it is not one of the write routes counted below.

It answers for any row the watcher holds, approved or not, since only the page calls it; a `view` that is absent, empty or given twice answers 400, and an id no held row names, a built-in view's id included, answers 404. The page sends the view id through `encodeURIComponent`, and the route compares the decoded value with the view ids of the held rows. The route is under `/api/`, so the origin rule and `refused()` apply to it, and the frame cannot call it, since its opaque origin fails `sameOrigin` as above; only the page calls it. The page holds, for each app it has fetched, the version and value of the last answer not dropped, and nothing for an app it has not fetched. `getStore()` answers from the held value; when the page holds none for that app it fetches once, two tabs asking at once sharing that one fetch. When a push of `apps` arrives, and when a frame of the app mounts, the page compares the row's `storeVersion` with the held version (nothing held differs); when they differ and a frame of the app is mounted, it fetches once per loaded oculus page, whatever the number of tabs, and a floating pane and a popped-out window drawn by the same page share that fetch. An app with no mounted frame is not fetched until a frame mounts. At most one fetch per app is in flight per page. When a fetch settles, the page compares the version the answer carries with the row's version as the page holds it then.

If a push moved the row's version while the fetch ran, the answer is dropped and the page fetches once more at once. If the row's version is the one the fetch was made for and the answer carries another, the store was written after the last push and the push that carries the new version has not arrived: the page waits for the next push of `apps`, at most 5 seconds, and fetches again. A 404 answers no version: it is dropped and the page fetches again while the page holds a row of the app, and it is the app's absence below when the page holds none. Versions are compared for equality and never ordered, and a read gives up after five dropped answers: with `missing` when every answer was a 404, and with `failed:0` otherwise, since the store is not gone. A dropped answer is not held and calls no `onStore`, and a `getStore()` waiting on the dropped fetch settles with the answer of the fetch that replaces it. The page holds the version a fetch answered, so a later push carrying that version fetches nothing. After a fetch whose answer is held the page calls `onStore(value)` in every tab of the app; a tab closed, a frame destroyed or a bridge not yet connected while the fetch is in flight gets no call, the answer is kept, and a frame mounted later gets it through `getStore()`. A 404 (the app removed or refused since the last push of `apps`) leaves the page holding nothing for the app and calls nothing, and a `getStore()` waiting on it rejects `missing`.

Nothing else persists: an opaque origin has no cookies, `localStorage` or IndexedDB. An app can name no store but its own, because the page sends the app's view id in a header and the body carries only the value.

**How it writes.** Every write goes through the page. `write(kind, body)` is checked against the manifest's `writes`, and the page sends `POST /api/write` with the write token and the headers `x-oculus-app: <view id>` and `x-oculus-write-kind: <kind>`; the handler, having matched the body to one of its parsers, refuses with 403 `{ error: 'kind' }` and writes nothing when the branch it matched is not named by the header or is a closed kind, because the page cannot tell which parser will match and a body would otherwise satisfy a parser of a closed kind while declaring an open one. The change record carries the app's view id beside its kind, so the reader sees and undoes an app's writes in the change log like any other. Open kinds: `manifest`, `entry`, `subtask`, `subtask-add`, `host`, `new-entry`, `reorder`, `delete-entry`, `feed-field`, `feed-delete`, `lead-add`, `radar-add`, `linkedin-idea`, `linkedin-post` and `new-idea`, which edit the hub's data. The kind `app-store` is in neither set: every app is granted it for its own store. The four entry kinds (`entry`, `new-entry`, `reorder`, `delete-entry`) resolve the collection key `bookmarks` to the reader's bookmarks file under `~/.oculus`, outside the hub (`server/files/fs/collections.ts`, `server/edit/writes.ts`), and a bookmark naming an `.html` file opens it in the Document view, whose frame carries oculus's origin (`views/shared/explorer/opening.ts`).

The handler therefore refuses the collection key `bookmarks` with 403 `{ error: 'kind' }` for a write that carries `x-oculus-app`, so no app edits the reader's bookmarks. Closed: `undo`, which takes back any writer's change, `rail`, which rewrites `config/layout.yml`, `roots`, which adds or removes a folder of the default workspace in `config/sources.yml`, `audit-mute`, which edits `config/behavior.yml`, `config-key`, which sets one option of a tracked config file in place, `config-value`, which sets one list or family of a tracked config file in place, keeping the file's other bytes (`server/edit/block-edit.ts`), `session`, which edits the machine's session overrides, `deck-slides`, which writes the `slides:` lists of several groups and the `order:` list of a deck's `present.yml` under a served root in one edit (`server/edit/writes/config/deck/deck.ts`), and `deck-edit`, which writes and trashes slide files and makes decks under a served root (`server/edit/writes/config/deck/deck-acts.ts`). The other thirteen write routes (`calendar`, `connect`, `mail`, `memories`, `fs`, `open`, `source`, `deposit`, `git`, `hpc`, `usage/refresh`, `hook` and `terminal`) are closed to apps without exception: they run processes, write arbitrary files, reach a remote or act on an account, and the page never sends an app's request to any of them. `delete-entry`, `feed-delete`, `new-idea`, `linkedin-idea` and `linkedin-post` ask the reader first in a `Confirm` naming the app, the kind in words and the target as text, every time, opened with the keyboard on Cancel so a key meant for the app never confirms it.

Three of them are recorded with `undo: 'none'` and cannot be taken back, since `undoChange` answers `nothing` for such a record (`writes/undo.ts`): `new-idea` (`writes/manifest.ts`), `linkedin-idea` (`edit/feeds.ts`) and `linkedin-post` (`edit/feeds.ts`, which moves files). The other open kinds are recorded and undoable and send without asking. At most `apps.writes_per_min` (30) writes pass per frame per minute, `setStore` included, and the rest reject `rate`. The kind `app-store` is refused for a request that does not carry `x-oculus-app`, and a manifest that lists it in `writes` is refused `write_closed`, since the kind cannot be asked for. The body is `{ store: <value> }`, and the handler finds the store from the header's view id alone, writes nothing when the file already holds an equal value (above), and otherwise writes the file by rename, reads it back and refuses unless the read back equals the value sent. Its change record holds the file, the app's view id as `key`, the field `store`, and the sizes in bytes before and after as `before` and `after`. A store write's record is the one change record that holds sizes where every other holds the two values, and History draws the two sizes for it.

The values before and after are kept beside the log in `~/.oculus/app-data/.undo/<time>.json`, named by the record's `at` and deleted when the record leaves the `changes.keep` window, so a 256 KB store does not put 512 KB in a line of `changes.jsonl`; the undo of a store write checks that the store file still holds the value after and puts the value before back through the store's writer, and a record whose file is gone answers `nothing`.

**Opening things in oculus.** `open(target)` asks the page to open a tab and resolves once it has; it needs no manifest entry. The target is one of `{ view: <view id> }`, `{ project: <key> }`, `{ file: { root, path } }` and `{ url: <address> }`. `{ view }` opens a registered view with no state, and only a view that the view catalogue lists (`listed` is not `false`, `state/workbench/navigation/registry.ts`), so `terminal`, which is listed, opens a Terminal tab; `document`, `file`, `source`, `project` and every view that is not listed, which is every view that needs an argument, reject `closed`, and an id no registration holds rejects `missing`. `{ project }` opens the project's tab and rejects `missing` when the portfolio holds no project with that key. `{ url }` is for a link out of the app. The value is an `http:` or `https:` address of at most 2048 characters with no user name or password in it, as the browser reads it; any other value rejects `closed`, the word every target the page refuses carries.

The page then asks the reader in a `Confirm` (`apps.confirm_open_url`) that names the app by its title and shows the whole address on its own line, wrapped where it is longer than the box, with the keyboard on Cancel, because an address can carry what the app read and the policy does not see it, and a key the reader meant for the app must not confirm it; a no rejects `declined`, and a yes opens the address as a browser tab with `window.open(address, '_blank', 'noopener,noreferrer')`, so the tab has no link back to oculus. The question waits its turn in the tab's queue like a write's, the page that holds the tab is shown and the tab selected in its pane when a question is shown, so the reader sees it, and the call counts toward `apps.opens_per_min` before it is judged. `oculus.js` makes the call itself when a press lands on a link outside the app's own address (below, under "What an app does not get"). `{ file }` opens the file as source text in the source tab and never in the Document view. A root app may name only its own root in `file`, and any other root rejects `closed` for it, whether or not the file browser shows that root; a machine app may name any root shown in the file browser except `engine`, and a root the file browser does not show rejects `missing` for it. The key `engine` rejects `closed` for every app, since the root holds `local.yml`, the machine's private settings; keys compare exactly, so `Engine` is not `engine` and a configured root `game-engine` is an ordinary root.

A file whose real path lies inside the real path of oculus's own `config/` folder rejects `closed` for every app, whichever root names it, so `hub` with `tools/oculus/config/local.yml` rejects `closed` as `engine` with `local.yml` does, and so does a root that `sources.yml` or a saved workspace gives another key for that folder. A file whose path under its root, given or real, starts with a folder that the list `closed_paths` names rejects `closed` for every app, since a root can hold a tracked credential folder that no dot marks; `closed_paths` is a key of the `apps:` block in `config/behavior.yml` (below), a list of folder paths each relative to a root and applied to every root, compared segment by segment and without regard to letter case, so `secrets/a.txt` and `SECRETS/a.txt` are closed alike, whether or not the root holds the folder, while `secrets-notes.md` and `a/secrets/b` are not. Its default, `closed_paths: [secrets]`, is written in `config/behavior.yml`.

A `closed_paths` that is absent, or a value that is not a list of strings, gives the finding `findings.apps.closed_paths_shape`, which names the file `config/behavior.yml` and the key `apps.closed_paths`, as `behaviorFindings` reports the other errors of that file (`src/lib/data/sources/config/catalogs.ts`), and while it stands every `file` target rejects `closed` for every app, so an error in the key closes files and never opens one; an entry that is empty, starts or ends with `/`, or holds an empty, `.`, `..` or dot-led segment gives the same finding and is left out, the other entries applying; a duplicate entry applies once and gives no finding. `config/behavior.yml` holds the `apps:` block with every key of the block and its value. A `file` whose `path` breaks the segment rule of the app file server above rejects `closed` for every app, a machine app and a root app alike: a segment that is empty, `.`, `..` or dot-led, or a backslash or NUL anywhere. So `.env`, `.ssh/id_ed25519`, `.oculus/approvals.json`, `a/.git/config`, `a//b`, `/etc/hosts` (its leading segment is empty), `a/./b` and an empty path each reject `closed`, and a dot inside a segment (`notes.v2.md`) is not dot-led. The rule is checked on the exact string the app passed: `open` takes a string over the bridge and decodes nothing, so `%2Eenv` is a literal name that does not start with a dot, and the page passes the path URL-encoded to the source route, which decodes it back to the checked string.

The rule and `closed_paths` are applied again to the part of the file's real path under the root's real path, so a link inside a root that points at a dot folder (`creds` pointing at `.secrets`, opened as `creds/key`) rejects `closed`, and so does a link whose target lies outside the root, whether or not the target exists. The real-path checks compare the real path defined under "Where an app lives", so `hub` with `TOOLS/OCULUS/CONFIG/local.yml` rejects `closed` and, on a root holding `secrets/`, `SECRETS/a.txt` rejects `closed` under the default `closed_paths`. The checks run in this order, so that the answer for a hidden path never depends on the disk or on which roots are shown: the segment rule and `closed_paths` on the given path; the key `engine`; for a root app, a root other than its own (`closed`); whether the root is shown (`missing`); the checks on the real path, each `closed` (outside the root, inside oculus's own `config/` folder, the segment rule and `closed_paths` on the part under the root); then whether the file exists, and a file that does not exist rejects `missing`. A binary file, and a file that `open.program_ext` maps to a program such as a `.docx`, open in the source tab as source text, as every file `open` names does, and no program is started.

Every check of `{ file }` after the view and project forms runs on the server, since the page cannot see a real path: before it opens the tab the page calls `GET /api/app-open?app=<view id>&root=<root key>&path=<path>`, each parameter sent through `encodeURIComponent`, which runs the checks above in their order for that app and answers `{ result: "ok" | "closed" | "missing" }`; the page opens the source tab only on `ok` and otherwise rejects the word the route answered. The route sits beside `GET /api/app-store` under the same rules: GET only (SvelteKit answers 405 to any other method, since the route module exports no other verb), it writes nothing, a parameter that is absent, empty or given twice answers 400, an `app` no held row names answers 404, and only the page calls it. The bridge's `open` reaches the page's own tab opener and never `POST /api/open`, the route that starts a program (the open action of the Configuration section), which stays closed to apps beside the other closed write routes above. A target that is none of the four forms rejects `closed`. At most `apps.opens_per_min` (30) calls of `open` pass per frame per minute, and the rest reject `rate`. `open` resolves once the tab is open. The frame layer keeps the frame of the app that asked through the change of layout, so a call that adds a pane to the page still resolves, the app keeps its in-memory document and its bridge, and a later `open` that adds a tab to an existing pane resolves in the same way.

**Approval.** An app runs only after the reader approved it on this machine, by the processes rule: the approval is kept in `~/.oculus/approvals.json`, named by the `approvals` key of `local.yml`, and keyed by the app's content, so a changed app asks again, and so does a root app that arrives or changes by `git pull`. The file is one shape for every user of the rule: `{ "version": 1, "approved": { "<kind>:<sha256 hex>": { "label": "<text>", "at": "<time>", "folder": "<real folder path>" } } }`, where `folder` is present on an `app` entry only, mode 0600, in a folder that each write of the default file under `~/.oculus` makes 0700 when it is looser and owned by the user (a folder owned by another user, and the folder of a file the `approvals` key puts elsewhere, are left as they stand), written by rename and read back to check the write.

`<kind>` is `app` for an app and `command` for a repository command, debug launch or seeded agent of the processes rule, whose hash is over the exact text, which for a seeded agent is `JSON.stringify({ agent, cwd, seed }, null, 1)`, the agent, the real path of the folder it starts in and the seed text the server built for the task (the reader's own words added to it are outside the text), and for a repository command is `JSON.stringify({ repo, chain: [[folder, run], ...] }, null, 1)`, the repository's real path and, for each command of the chain in run order, its folder relative to the repository (`.` for the repository itself) and its line before any placeholder is replaced, so the hash can be recomputed from those fields with that indent (JSON, so a tab or a line break inside a folder or a line cannot read as the boundary of two), and for a debug launch is `JSON.stringify({ repo, debug: [cwd, program] }, null, 1)`, the repository's real path, the folder the launch runs in relative to it (`.` for the repository) and its program as written before any placeholder is replaced; an app's hash is over its real folder path, its name, its manifest bytes and, for each recorded file in sorted path order, the path, the length and the bytes. The folder is in the hash, so two byte-identical apps in two roots (one repository cloned twice, two worktrees) are two entries, and approving or revoking one never touches the other. An entry is found by the app's real folder path, whatever its name: approving an app removes the `app` entries whose `folder` is that folder, and only those, so one approval per folder is live, and `revoke` finds the entries by the same field.

`POST /api/approve` carries `{ action: 'approve', view, hash, keep? }`, with the app's view id in `view`, which the server refuses with 409 `changed` when the hash is not the app's current one, so the reader approves exactly what they were shown, and `{ action: 'revoke', view }`; it sits under `/api/`, so the origin rule and the write token apply. The server enforces approval: it serves an app's files only while the app's hash is in the file under the app's folder, or the app is kept approved, and the approve route updates the held state before it answers, so a revoke stops serving at once.

Before approving, the tab shows the approval panel in place of the frame: the title (followed by the root's key for a root app) and description; the name and the app's folder path; the file count and size; the channels the app reads and the writes it may ask for, each in plain words (`apps.read.<channel>` and `apps.write.<kind>`, with `apps.read_root.git` and `apps.read_root.files` for a root app); the outside origins it declares in `connects`, each as an address under `apps.connects`, or `apps.connects_none`; where its store is written, and for a root app that the file is in the root and tracked by git unless the root ignores `.oculus/app-data/` (`apps.store_machine`, `apps.store_root`); and a control that opens the app's folder in the file browser so the reader can read the files. Every word that comes from the manifest, the title, description, name and entry included, is drawn as text by Svelte's interpolation and never as HTML, in the catalogue, the tab, the notices and the approval question alike, so a title holding markup shows the markup.

**Keeping a machine app approved while it is written.** The approval panel of a machine app offers a second control beside Approve, `apps.keep_approved` ("Keep approved while I edit"), which approves the content shown as Approve does and also keeps the app approved. Until the server process ends, a change to any file of the app except `app.yml` leaves the app approved and served: the address key changes with the files, so the frame reloads, and no question is asked. A change to `app.yml` ends the keeping and the panel asks again, showing the new manifest's channels, writes and origins, since the manifest is what names what the reader approved. The keeping is held in the server's memory as the hash of the manifest bytes approved with it, never in `approvals.json`; it is ended by Revoke, by a change to `app.yml` and by the end of the server process. After a restart the app is approved only by the entry the control wrote to `approvals.json`, so it runs while its files are as they were at that press and asks at the first change. `POST /api/approve` carries `keep: true` for it, which the server refuses for a root app: the control is never offered for one, since a pull writes a root app's files. While the keeping holds, the tab's strip shows the glyph `edit` with the words `apps.editing_mark` where an unapproved app shows the lock.

**Reading an app's files.** A file whose real path lies inside any apps folder, the machine's or a root's `.oculus/apps/`, never opens in the Document view, from the file browser, a bookmark, a link or `open`, and its `.html` and `.htm` files open as source text, since the Document view's frame carries oculus's origin (`sandbox="allow-same-origin allow-scripts"` at `FrameLayer.svelte`) and an app's page drawn there would run before approval with the write token in reach. Two things hold it. The page joins a file's root folder to its path and tests the result against the `folders` of the `apps` channel (`holds` of the apps store), and `tabForKind` opens the source tab for a match. Every opener goes through it: `openRow`, `openRowBeside`, `openBookmark` and `openPage` (`views/shared/explorer/opening.ts`), which a project card's documents, a card's readable file, an entry's document link and a ghost project's README call, the explorer's row menu, the rail's bookmark rows and a source tab read again (`views/sources/source/actions/read-again.ts`). The file route tests the real path, which the page cannot see through a link, and answers a file of an apps folder as `text/plain; charset=utf-8` with `X-Content-Type-Options: nosniff`, so such a file cannot run as a document wherever its address is opened, a link inside a manual included.

**What an app does not get.** No process and no server code: the server runs nothing an app holds, and `open` starts no program. No file outside its folder but its own store: the frame reaches only the recorded files by address, the store only through `getStore` and `setStore`, and the file browser is not offered to it. Requests: the policy above names the sources the browser is told to allow, which are the app's own files, the shared files, `data:` images and the origins the app declared in `connects`. No cookies or storage, no popup, form, modal or navigation of the page. A press on a link outside the app's own address does not navigate the frame: `oculus.js` listens for a press on an `a[href]` whose address lies outside the app's own address, which is `/apps/<name>/<key>/` or `/apps/@<root>/<name>/<key>/` on the page's origin (so a link to another page or an anchor of the app is the app's own, while a link to another site or to another path of oculus is outside; a `javascript:` address is the app's own script and is left alone), stops the navigation and sends the address through `open({ url })` (above), so a `mailto:` or `ftp:` link is refused `closed` and an `http:` or `https:` one asks the reader, and the frame keeps its document either way. Any other navigation of the frame to an address outside the page's origin is refused by `frame-src 'self'`, the frame ends and the tab shows `apps.load_failed` with Reload.

No other app: an opaque origin, an address key nobody else holds and a store that only the app's own view id names. Not the write token, `/__data.json`, the socket or any `/api/` route: the policy's `connect-src` stops the request; a request that reached the server anyway is cross-site with `Origin: null`, which `sameOrigin` and `allowedOrigin` refuse, a write would lack the token, and no route other than the app files sends `Access-Control-Allow-Origin`, so an opaque document cannot read the page's data. Not the page's DOM, which is another document. The page's chords and its right-click handler do not see events inside the frame: `oculus.js` forwards a `keydown` that holds Control, Meta or Alt, or is Escape, to the page as `key({ key, code, altKey, ctrlKey, metaKey, shiftKey })`, and the page dispatches it as a `keydown` on `window`, where the shell's key handler listens (`<svelte:window onkeydown>`, `Workbench.svelte`). The page accepts `key` only while `document.activeElement` is that app's iframe and at most `apps.keys_per_s` (20) calls a second; any other call is dropped, an Escape without focus included; a right-click inside the frame opens the app's own menu or the browser's, and the page's context menus never open over it.

The boundary against an app sending what it read to another machine is the reader's approval of its files and of the origins it declares: the policy stops the requests a document makes through scripts, styles, images, fonts, media, fetches, forms and frames to any address but the app's own files, the shared files and the origins in its `connects`, and the approval panel lists those origins. Three things the policy does not stop were measured in Chrome (each probe loaded top-level from a static server with no policy as the control, then in the frame `AppFrame.svelte` draws, with a listener on `127.0.0.1`). WebRTC: an `RTCPeerConnection` with `stun:127.0.0.1:3478` sends STUN datagrams to the listener from the frame, so an app can reach a STUN server by address. DNS prefetch: a `<link rel="dns-prefetch" href="//e4-probe.test">` in an app's page makes the browser resolve the name (one host resolution in the net log, in the control and in the frame), so an app can leak a name it chooses. `wss:` under `connect-src https://localhost:9443`: the policy does not admit it, a `securitypolicyviolation` fires and the listener on 9443 logs no connection, so an origin in `connects` admits requests of its own scheme only, and a `wss:` origin stays refused as the manifest paragraph says.

A download link to an outside address from an app with no `connects`: the control sends an HTTP request to the listener on 9444 and the frame sends none, only a preconnect (the net log shows a connection job marked `is_preconnect` that connects and closes with no bytes sent); a sandboxed frame with no policy sends the request with `allow-downloads` and without it, so the policy is what stops the request and taking the flag out would not, and `allow-downloads` stays in the sandbox. WebRTC, DNS prefetch and that preconnect let an app put what it read into an address, a host name or a port, so the boundary against an app sending what it read to another machine stays the reader's approval of its files and of the origins it declares; the policy does not close these three. The address an app passes to `open({ url })` is a fourth way to put what it read into an address, and the page closes it by asking: the `Confirm` shows the whole address, since the app can build it from what it read, and nothing opens without a yes.

**Words.** The words the reader sees come from `config/text/` through `t("group.key")`, in one file, `config/text/views/apps/apps.yml`, holding the group `apps`: `label`, `glyph`, `unapproved_mark`, `editing_mark`, `approve_title`, `approve_question`, `approve`, `keep_approved`, `revoke`, `open_folder`, `reads_none`, `writes_none`, `connects`, `connects_none`, `store_machine`, `store_root`, `read.<channel>` for each channel a machine app may declare (`portfolio`, `feeds`, `git`, `hpc`, `audit`, `config`, `files`, `inbox`, `calendar`, `sessions` and `usage`), `read_root.git`, `read_root.files`, `write.<kind>` for each kind a manifest may declare, `ask.<kind>` for each kind that asks first (the verb phrase `confirm_write` puts after "asks to"), `changed`, `load_failed`, `refused_read`, `refused_write`, `refused_open`, `confirm_write`, `confirm_open_url` and `rate`. The finding sentences are in `config/text/findings.yml` under `findings.apps` with the keys named above, and `findings.apps.carries.<channel>` for `apps`, `pty`, `processes`, `inbox`, `calendar`, `sessions` and `usage`. An app whose bridge handshake does not complete within `apps.connect_timeout_s` (10), the timeout given to `connect`, draws `apps.load_failed` over the frame with a control that reloads it; an app that reads and writes nothing still calls `connect`.

The keys of an `apps:` block in `config/behavior.yml` are the limits `connect_timeout_s`, `state_max_kb`, `store_max_kb`, `writes_per_min`, `opens_per_min`, `keys_per_s`, `max_files` and `max_mb`, and the list `closed_paths` (`[secrets]` in the file), read by `appsSettings`, which sits beside `mailSettings` in `src/lib/data/sources/config/settings.ts` and requires the limits as `mailSettings` requires its keys; `closed_paths` alone is reported as a finding, with files closed, as above.

## Relationship to the cockpit

- The cockpit is frozen: bug fixes only, nothing new is built there.
- No code is shared. oculus holds its own copies of the configuration and of the memory-wall images.
- Both read the hub's data from its one documented data path, which oculus reads from `local.yml`.
- The cockpit retires when the last view it has and oculus does not has moved. The `.app` launcher then points at oculus.

## Conventions

- Every source file under 1000 lines, checked at 900 for a file and 540 for a component by `utils/size-check.sh`. A file approaching it is split by concern, never by line count.
- At most ten items in a folder under `src`, `tests`, `utils` or `config`, checked by `utils/folder-check.sh`; a folder that would pass that is split into folders named for what it holds.
- Four-space indentation in every source file. Prettier is the formatter, pinned in `.prettierrc` (`tabWidth: 4`, `useTabs: false`), with the format command and its check among the verification commands `README.md` lists. A hand-formatted file is never the answer to a failing check.
- ASCII only in every authored file. Glyphs come from `catalogs/glyphs.yml`, strings from the catalogs under `config/text/`, colours from `tokens.css`.
- One continuous line per paragraph and per bullet in Markdown and YAML; no hard wrapping.
- Plain prose in docs and comments; a comment says why, not what.
- An agent working on the application runs no git command that writes, and a commit is the reader's. The git commands the application itself runs, the one timer included, are in "Git" of Layer 2.
- Work proceeds from the ledger in `.scratch/migration/`: `plan.md` is the step list, `orchestrator-state.md` is read first, and `agents/spec.md` is the standard every step is built and reviewed under.

## Decisions taken

- Name: `oculus`, at `research-hub/tools/oculus`.
- Stack: SvelteKit with the Node adapter, Svelte 5, Vite, Vitest, TypeScript. The one enforced boundary (`$lib/server`) is the reason for Kit over bare Vite.

- Live data: one WebSocket with channels, the server watches and pushes, and the page polls nothing: no repeating timer of the page asks the server for anything, and the repeating ones move a clock (`src/lib/state/client/clock.svelte.ts`, `src/lib/views/sessions/agents/Agents.svelte`, the presenter's clock) or sweep the language client's own pending requests (`src/lib/ui/controls/editor/kit/lsp/client.ts`). The page's timers that run once are waits of many kinds (the socket's reconnect, the give-up of a write, a toast's fade, a tooltip's delay among them), and some save what the reader typed, late, among them the scratch notes' save, a wait after the last keystroke (`src/lib/state/life/notes.ts`), and, for a source tab under `editor.autosave` `after_delay`, the autosave timer, which each edit of the tab restarts and which saves the tab `editor.autosave_delay_ms` after its last edit (`src/lib/state/sessions/source/autosave.svelte.ts`), a `POST /api/source` like Cmd+S that asks the server for nothing else. A source the server cannot watch is polled by the server, as the Watchers paragraph says, and so is each file an open source tab holds, twice a second (`src/lib/server/files/fs/open-files.ts`). Writes are `fetch` POSTs, each given up with the form told so once `writes.timeout_seconds` of `behavior.yml` passes with no answer.

- Wire model: entities and relations, joins in client selectors, documents on demand.
- Layout: a serialisable tree.
- Configuration: one concern per file, the research domains' colours keyed `domains` and the UI theme list in `appearance.yml` as data rather than catalog strings, so a theme is added without touching a component.

- Git writes and the deposit: a project's `code/` is ordinary tracked content of the hub and never carries a `.git` of its own. The deposit is a repository with history that lives outside the hub tree, a mirror clone per deposit repo under the machine-local state folder into which each deposit syncs `code/` and commits with a message, so the hub's own history is never split in two, and every write is behind the token and a confirm. A project that is also a public repository (engram) folds into the hub as tracked files, its GitHub history kept in the mirror. The sessions' Changes panel and the Repositories view run the same writes through the one commit box `src/lib/views/shared/changes/CommitBox.svelte`, so the two cannot differ. A git command that runs the repository's hooks has no time limit, because a hook may take as long as it needs and Cancel ends the run; how Cancel ends it is in the head comment of `src/lib/server/core/git/running.ts` and how a failed command is worded in the doc comment of `classifyFailure` in `src/lib/server/core/git/parse.ts`, and what the reader sees is in `docs/source-control.md` ("Committing").

Terminal input and resizes are accepted only on a socket whose subscription carried the write token. The `sessions` payload carries no terminal list until tmux has answered once, and "no server running" is taken as the empty list only when repeated reads all say it, so a restart or a slow tmux never reads as every terminal having ended. Every refusal of `POST /api/terminal` is a word of `TERMINAL_REFUSALS`, so no text of tmux or of a validator reaches the page. The bridge's input, attach, capture and task-terminal behaviour is in the head comments of `src/lib/server/machine/pty/` (`tmux.ts`, `channel.ts`, `capture.ts`, `refusal.ts`) and in `docs/terminals.md`.

Only a slide that a file entry of `order:` placed is the deck's own to copy, delete or give an image, so a member deck's slide is edited in its own deck, and deleting a file that holds only its slide moves it to the Trash and drops its `order:` entry in the same act, since a dangling entry would be a finding. A slide is drawn from what its editor holds unsaved: the page posts the unsaved text of its source tabs to `POST /api/deck`, which reads the deck as if the files held that text and writes nothing, so the view and the file cannot disagree about a draft. Export to PDF is the only export: the print route `/present/print` draws every slide at 1280 by 720 px through the same slide components, the desktop host prints it with `printToPDF`, and the PDF is written through the Files view's upload, so it is one recorded, undoable file; a browser tab leaves the saving to its print dialog. The presenter screen and the audience window are two pages of one presentation. The presenter screen is the pane's own (`views/academic/present/presenter/`) and the audience window is the route `/present/show?root=<root>&path=<path>` (`routes/present/show/`), opened by `window.open` in a browser tab and in the app alike. The messages are a zod discriminated union (`parseMessage` of `state/life/present.ts`): `slide`, `changed`, `end` and `left` from the presenter screen, `opened`, `move` and `closed` from the audience window (the presenter screen waits 3 s after `closed` for an `opened`, so a reload of the audience window keeps the presentation and a closed window ends it), and anything else, a known kind with a field of the wrong type included, is dropped. Presenting is held in the page store `createPresenting` (`state/life/present.svelte.ts`) keyed by the pane's instance id and never in the saved layout, so a tab switch, a page switch or a redraw of the panes keeps it; the presenter takes the lock with `steal: true`, which is how a second pane over the same deck takes the audience window over before the first lets go, and the audience page asks for the same lock and is granted it only when the presenter's page is gone. Both windows draw `filesDeck`, the deck as the files hold it, and `createLive` is handed no drafts while a pane presents, so the audience sees the slide the presenter sees. The audience route reads the deck through `readDeck` and reads it again on `changed`; a read that fails reloads the page once and then shows the end sentence. What a reader sees is in `docs/views.md` ("Present").

- Saving a source file is the save of VS Code's text editor. The page keeps, per tab, `base`, the SHA-256 of the bytes the tab last read or wrote (`src/lib/state/sessions/source/draft.ts`), and sends it as `base` in the `POST /api/source` body; the server compares it with the file's hash and a second stat taken right before the write, and answers 409 with `code: 'changed'` and `refused: [{field: 'base', reason: 'changed'}]` when they differ (`src/lib/server/files/source.ts`), and `ok` with the new `hash` otherwise. The file's channel `source:<root>/<path>` carries `{hash}` (the hash of the bytes, `stat:` and the hash of the stat for a file over the read limit, null when gone); `server/files/fs/open-files.ts` polls each subscribed file every 500 ms, bounded by 200 per socket and 1000 per server, and a page drops a file with the `unsubscribe` message (`src/lib/state/sessions/source/disk.svelte.ts`). Autosave (`src/lib/state/sessions/source/autosave.svelte.ts`) is the same save sent by a timer or a blur, and every close path (`closeQuestion`, the Pages reset, Close Editors) saves first what the mode saves on a close.

- The status bar is drawn as VS Code's: `shell/status/StatusBar.svelte` runs the window's whole width under the rail at `--status-height` with items at `--status-text`, both fixed at every text scale, and every item is a status `ToolButton` or `Menu`; the groups and their order are `shell/status/status-items.ts`, the debug item following the findings in the left group (the last configuration's name once a session has run, the whole bar painted in the theme's orange while one runs or is paused) and the build state of the LaTeX root in front being the last item of the left group (`shell/status/LatexItem.svelte`). Between the line ending and the language, a file a language server serves shows the server's state and the Python interpreter or the compile database. The source view publishes its caret, indent, ending and language to `state/workbench/navigation/editor-status.svelte.ts`, keyed by instance, and performs what the bar asks. Notifications are `state/workbench/navigation/notices.svelte.ts`, which each source posts to once per event (`src/lib/state/workbench/navigation/notice-sources.ts`). The items, the bell and the notification centre as a reader meets them are in `docs/window.md` ("The status bar and notifications").
- A workspaces, bookmarks or notes read that ends in an error is held as the answer in `state/sources/fs.svelte.ts`, so the view asks once rather than once per render, and the control on `views/shared/explorer/tree/Failed.svelte` marks that answer stale to read again. `~/.oculus/bookmarks.yml` is watched on the `files` channel (`src/lib/server/root/watch/bookmarks.ts`), and a pending bookmark marker is merged with the newest root so neither fact is lost while a page is behind (`src/lib/server/files/files-channel.ts`).
- The native window: the app is Electron (`src/desktop/`), started and packaged as `README.md` says. The server is a utility process with its own listening port, because the page, the sockets and the terminals all stay as they are in a browser and a crash of either side leaves the other running; it is the TypeScript tree itself, unbuilt, so there is one copy of the code. The main takes the single-instance lock before it builds, so a second start under the same HOME never rewrites `build-app/` under a running app, and the app's build writes `build-app/` and `.svelte-kit-app/` alone, so an `npm run build` in the same checkout never meets it. A page that goes full screen puts the window in full screen too, so the window file keeps the state taken when the page entered full screen until both have left it (`recordWindow` in `decide/window-file.ts`). A held port is told from an oculus by `GET /api/health`. A window is made with Node integration off, context isolation and the sandbox on (`src/desktop/decide/window-options.ts`), and its only way into the main is the preload's one bridge object, whose handlers answer the top frame of the server's page alone (`src/desktop/windows/bridge.ts`); links, navigations and `window.open` go through one pure decision, so an address of another origin opens in the default browser and a `file:` or `javascript:` address is refused (`src/desktop/decide/links.ts`).
- The language servers. A Python, C, C++, TypeScript, JavaScript or Svelte file in a source tab is served by pyright, clangd, the TypeScript server or the Svelte server, which the oculus server starts as a child process (`server/machine/lsp/`); the page talks to it over its one socket on the channel `lsp:<language>`, through Monaco's own language client (`ui/controls/editor/kit/lsp/`) over a transport of oculus's own. A server is the processes rule's exception because it is oculus's own command with oculus's own arguments: an argument array and never a shell, `process.execPath` with the `pyright`, `typescript-language-server` or `svelte-language-server` package under oculus's own `node_modules`, and `clangd` from oculus's PATH. The TypeScript server runs oculus's own `typescript` (`tsserver.path`), never a repository's, with automatic type acquisition and tsserver's log off, so no `npm` runs and nothing is written into a repository. One entry per server holds what is known before a message is sent (`src/lib/data/prose/lsp-servers.ts`: languages, label keys, semantic tokens, format on type, Organize Imports, choice kinds, approval) and one holds how it is started (`server/machine/lsp/servers.ts`); nothing else names a server or a language. One server runs per page, root and registry entry, shared by that page's tabs of the languages the entry serves, so one clangd serves the C and C++ tabs of a root and two tabs never start two. A page names a document `oculus-file:///<root key>/<path>`, the root key percent-encoded twice so a `/` in it stays one segment, and the relay resolves it by the file's real path against the served roots, refusing a part that is empty, `.`, `..` or holds a slash once decoded, an absolute path and a link out of the root; each address is turned into the server's `file://` form and back, so a server never sees a root key and the page never sees a path of the machine. A file a server names outside every served root reaches the page as a library address, `oculus-lib:///<token>/<file name>`, the file name percent-encoded twice as the root key is. Only an answer to a request of the page mints a token: the relay makes it for that page, the file's real path, the root key of the document the request was made for and the language of the channel, and the server that named the file, so one file named by two servers is two tokens and the same file named again by the same server is one. A notification or a request of a server passes a library file only when the page already holds its token and drops the location otherwise, and no field of any message, a command's `arguments` and the keys of a workspace edit's `changes` included, carries a `file://` path of the machine. No token is minted for a path with a segment that starts with a dot, for a path under a folder `closed_paths` names, or for a path under oculus's own `config/` folder, `~/.oculus` or the hub's `secrets` folder. The one exception to the dot rule is a file under the `sys.prefix` or `sys.base_prefix` that the pyright interpreter probe reports, minted for the pyright server alone, since a Python library lies under a version manager's or a virtual environment's dot folder; a prefix that is the home folder, the filesystem root or a folder that holds the home folder gives no exception. The page reads a library file only over the `lsp` channel with `read`, and the relay answers only for a token of that page: with the file's text, or with a code when the root is no longer served, the root or channel language is not the token's, the real path is no longer the stored regular file, the file is not text, or the file is over the limit of a source read. A token lives as long as the page's connection, and another page holds none of it.
- What a language server may change. An edit a server asks for (a rename, a code action, `workspace/applyEdit`) goes through one page-side function (`state/system/machine/lsp/edits.ts`): a file open in any tab of the page is edited in that tab, unsaved and as one undo step, and every other file is written by the server operation `lsp-edit` of `POST /api/ops` in one request, behind the write chain, with a history copy of each file, an atomic write, a read back and one `files` record that History undoes as one step. The request names each file with the SHA-256 of the bytes the page read just before the post and the server refuses the whole edit when a file's bytes are not those, a file lies outside the served roots, under `node_modules` or under a folder whose name starts with a dot, or is `local.yml`; the page posts first and edits its tabs only after the post succeeded. The page refuses the whole edit, naming the file, when a file is open in a tab of another page (the relay tells it, from the open tabs every page publishes on the channel `lsp:workspace`), is a library file, holds a create, rename or delete of a file, names a version that is not the tab's, or belongs to a document that is gone. A library file's tab is read-only, so no edit reaches it. The interpreter pyright runs and the compile database clangd uses are choices kept per repository in `<lsp folder>/choices.json` (the `lsp` key of `local.yml`, default `~/.oculus/lsp`), and a choices file that does not read is left as it is. The chosen database is linked into the lsp folder, so clangd's index is never written into a repository. A repository's `.oculus/cpp.yml` names configurations that the compile database list offers, and a value that does not read is a finding, listed at the head of that list. A server ended because its root is no longer served says `root_gone` to its page, and a tab still open under the root is served again, without being closed and reopened, when the root is served again. When each server ends, and what the reader sees, is in `docs/files-and-search.md` ("Language servers").

- Windows and the shell around them: a float can become a window of its own (the `window` place), with the same client state and a page of its own (`?float=<id>`, with `&owner=<id>` naming the main page that opened it, which is the page its `jump` messages are for), because a tab's state is held under its instance id; the windows share one saved arrangement, so a write is a turn taken through the main (`src/desktop/decide/save-turn.ts`, `src/lib/shell/desktop-windows.svelte.ts`). In a browser the window is a browser tab that the press opens (`src/lib/state/workbench/layout/open/float/browser.ts`), since a browser opens a window only inside a user's gesture; the tab holds a Web Lock named for its float while it lives, and a main page that can take that lock takes back the tabs of the float, which is how a browser tab closed by hand returns its tab, and a tab hidden or throttled by the browser keeps its lock and is not taken back (`src/lib/shell/browser-windows.svelte.ts`); a main page holds a lock of its own id as well, so the copy a browser makes of a duplicated tab, which starts with the original's id, finds it taken, forgets the id and reloads under another, and `owner` names one page only. The window state, the application menu, the keys the page asks for, the folder sheet and the find bar are the app's, and the text menu and the tab menus stay oculus's own. The find bar is a view of its own because Chromium's find counts the text of a box in the page it searches (`src/desktop/windows/find-bar.ts`). The PDF of a deck is printed by a hidden window of the host (`src/desktop/windows/print.ts`) that loads only the print route of its own server, is answered no bridge channel and is no entry of the windows list, so the window file cannot record it; the page asks for it on `oculus:print-pdf`, which the host refuses for any other address. The audience window of a presentation is the second window of that kind (`src/desktop/windows/show.ts`): `linkDecision` names the server's `/present/show` address with exactly `root` and `path` as its own kind, `route` of `windows.ts` hands it to the audience module instead of the default browser, `senderOf` gives its page the `audience` sender and `mayCall` answers it no channel, and it is no entry of the windows list and no record of the window file, so it is not restored at the next start. One window is open per deck, and asking again loads its address again and brings it forward, so a presenter screen that started after a reload meets a live page. It opens on a display other than the asking window's in simple full screen, or beside the asking window when there is one display (`audiencePlace` of `decide/place.ts`), is granted full screen by the permission handlers, sends a slide's link to the default browser, closes with the window that asked for it, and closes by Close Window while it has the focus. What the app adds for a reader is in `docs/window.md` ("The window and the app").
- The debug client. The server is the client of the debug adapter (`server/machine/debug/`): it holds the one session, publishes its state on the `debug` channel and its console on `debug-console`, and the page sends commands by POST `/api/debug`. A channel that relayed the adapter's messages would lose them, since a page that falls behind keeps only the newest payload of a channel, and the socket takes no requests from the page. The console is on a channel of its own that carries appends, which the hub merges, so a state publish never carries the 10,000 lines the console holds. The adapter cannot be stopped by the protocol, so Stop is a signal behind a confirmation, and a launch is asked once for each text, as a command is. What a reader meets is in `docs/debugging.md`.
