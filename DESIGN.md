# oculus, design

The successor to the research cockpit (`tools/cockpit`). Same job: a private, local dashboard over the research portfolio, its projects, venues, funding, data, and the Claude Code sessions working on it. Different construction: one language, three layers, one definition per screen, live data pushed by the server rather than polled by the page, and an arrangement you edit in the app.

Written 2026-09-10. This is the artefact every later step is measured against. When the code and this file disagree, one of them is wrong and the disagreement is a finding, never something to paper over.

The name: the eye, alongside `iris`, `scotoma` and `umbra`; and the opening at the top of a dome that lets the light in, alongside `cathedra`.

## Why a new tool

The cockpit is a Python static-site generator that emits one 8.8 MB HTML file with all CSS and JS inlined, plus a Python dev server that patches the page in place when files change. That shape was chosen so the output would be a single portable file with no build step. The file is never opened; only the served app is used. Every awkward thing in the cockpit follows from a constraint that no longer applies:

- 3668 lines of Python build HTML through f-strings, and 3477 lines of client JS render the live half of the same screens. The Sessions tab is defined in both.
- A live-reload "morph" patches the generated document in place, with `data-skipmorph` escape hatches so it does not wipe what the client rendered, and MutationObservers to re-apply client decoration after it does.
- A hand-rolled module system (`window.CK`, load-order rules, a custom test) stands in for a bundler.
- Config is read into module-level singletons at import, so a config edit re-execs the whole process.

None of these are bugs. They are the cost of the constraint. oculus drops the constraint and therefore the cost. Nothing in the cockpit is thrown away carelessly: the data files are kept as they are, the configuration files are copied over and keep their roles, the palette and themes port unchanged, the gates port as tests, and the Sessions work (cockpit roadmap B, complete) ports rather than being rebuilt.

## Non-goals

- Not multi-user, not remote, not peered. Clodex-style fleet features are out.
- Not an IDE. It is a development platform for the hub's own files: a file browser, an editor for every text file, search, LaTeX builds, PDF reading, project commands and the rite debugger, and nothing that needs a language server: no go-to-definition beyond search, no lint panel, no other debugger.
- Not a rewrite of the data. The YAML in the hub is the source of truth and its shape does not change for oculus.

## The three layers

**Data.** Reads files, produces a typed, validated model. Knows nothing about screens. Runs on the server.

**Code.** Everything between the model and the pixels. Split by where it can run: the server-pinned half touches the filesystem, git, processes and the socket; the client half holds state and computes joins and filters. Neither half renders anything.

**View.** Components. Split into primitives that know no domain, a shell that knows no view, and views that know no layout.

The rule that keeps this honest is an import-graph test (`tests/boundaries.test.ts`) plus one boundary SvelteKit enforces itself. See Boundaries below.

## Configuration

The ten tracked files under `config/` are the interface described as data, one concern to a file, and they are treated alike; `config/local.yml` sits with them and is the machine's own, read by `loadLocal` and never merged. What the portfolio reads in `sources.yml` (the tier scan paths, the registry and collection files, the document and feed paths); words and their colours in `vocab.yml` (the palette, the research `domains`, the status legend and palette, the focus lanes, the venue tiers, the radar buckets); how things are arranged in `layout.yml` (the rail's groups, the board chrome, the tab rollups, the live badges, which title a surface draws); thresholds and horizons in `behavior.yml`; the UI theme list, the wallpaper and the CRT default in `appearance.yml`; the glyph vocabulary in `glyphs.yml` and the icon each of its names is drawn as in `icons.yml`; every user-facing string in `text.yml` read through `t("group.key")`; the edit form in `manifest-schema.yml`; the tool's own identity in `meta.yml`. `loadConfig` merges every file's top-level keys into one map and reports a key two files define, so a key moves between files without a reader noticing and no key sits in two. No component contains a literal user-facing string, a raw colour, or a literal glyph. `tests/keys.test.ts` fails on a `t()` key that does not exist, so a typo is caught before it renders blank, which is the same gate the cockpit has.

Paths resolve without environment variables: the command-line argument `--engine <dir>`, then `local.yml`, then a default derived from the file's own location. The hub path is the one value every machine must set and it lives in `config/local.yml`, gitignored and left out of the merge, so the tree carries no machine path. Roots the file browser may serve (step 7) are set in the app and stored in config; nothing outside a root is ever served.

## Layer 1, data

**Sources.** One module per kind of file. Each exposes one function that takes a root and returns raw records, and each is unit-tested against synthetic fixtures in a temporary directory. No source knows another exists.

**Model.** `model.ts` holds the types and nothing else. The core entities are `Project`, `Venue`, `Dataset`, `Program`, `Domain`, `Funding`, `Collection`, `Entry`, `Doc`. A project carries the ids of its relations (`venueId`, `fundingIds`, `datasetIds`), never resolved objects: a project points at its funding and the funding points back at its projects, and that loop cannot be turned into JSON.

**Validate.** Every id referenced resolves to an entity; every status is in the vocabulary; every manifest field is one the schema names. Failures are reported with file and key, and a run against the real hub must report zero. This is the cockpit's `selftest.py` referential check, ported. It runs on every rebuild, so a bad manifest edit shows in the app within a second, as a finding, never a crash.

**Normalise.** What goes over the wire:

```ts
type Snapshot = {
  version: number                         // increments on every rebuild
  entities: { projects: Record<Id, Project>; venues: Record<Id, Venue>; ... }
  relations: { projectFunding: [Id, Id][]; projectDataset: [Id, Id][]; ... }
  findings: Finding[]                     // from validate
}
```

Flat, JSON-safe, small: the whole hub is a few hundred kilobytes. Documents are not in it; `api/docs` serves one when a view opens it. That is the reason the cockpit's page is 8.8 MB and this one is not. The one exception is a project's `PRESENT.md` front matter, and for a file that has none its narrative: the Present view draws a slide on a key press, so its slides ride in the snapshot rather than being fetched one at a time.

## Layer 2, code

### Server

**The socket.** One WebSocket per open page. Messages are `{channel, version, payload}`. Channels: `portfolio`, `sessions`, `git`, `hpc`, later `pty:<id>`. A page subscribes to the channels it needs; the server sends the current payload on subscribe and pushes on change. If a page falls behind, the server keeps only the latest payload per channel: the newest state is the only one that matters.

**Watchers.** Each channel has one watcher module that owns its `fs.watch` handles, debounces, rebuilds only what changed, and pushes. Portfolio watches the hub's YAML directories. Sessions watches `~/.claude/projects` (transcripts) and `~/.claude/sessions` (the registry). Git watches each workspace's `.git/index` and worktree and re-reads on change, no more often than every two seconds.

**Sessions.** Ports the cockpit's B1, B2 and B5 with their tests. Facts that cost real time to establish and must not be rediscovered:

- Transcripts: `~/.claude/projects/<slug>/<id>.jsonl`, 490 files and 1.2 GB on this machine. A 48 MB transcript folds in 0.2 s, so there is no size bound on a first read; a byte-offset cache means a later read takes only what was appended. Any change to the accumulator's shape bumps the cache version.
- Subagents are `tool_use` blocks named `Agent`, paired to their `tool_result` by id. `isSidechain` is false on every record everywhere and carries no information.
- The live registry: `~/.claude/sessions/<pid>.json`, with `sessionId`, `status` (`busy` or `idle`), `name`, `cwd`. Liveness is `kill(pid, 0)` plus a `procStart` match; the registry writes that stamp in UTC and `ps` reports local time, so the match parses both and allows two seconds.
- Grouping: workspace by walking up to `.git`; area scored from touched files with the cwd counting double, directories clamped to two segments below the workspace root, known project folders exempt from the clamp.
- Context occupancy is the last assistant turn's `input + cache_creation + cache_read`, never the lifetime sums.

**Git.** Exactly seven read-only commands (`rev-parse --abbrev-ref HEAD`, `rev-list --left-right --count`, `status --porcelain=v1 -z`, `diff --numstat -z`, `log -<n> --format=`, `branch --format=`, `worktree list --porcelain`), one subprocess call site, a five-second timeout, list arguments only. No writing subcommand appears in the module, `worktree` is pinned to its listing, and a test asserts both. Git writes are Axel's alone; the commit action (step 6) runs `git commit` only from an explicit click carrying the write token, and nothing else in the application can reach that endpoint.

**Live HPC.** One poller runs `squeue`, `sacct` and `sinfo` in a single ssh call every `slurm.poll_min` minutes, with disk quota on its own slower cadence, and publishes one complete state on the `hpc` channel. The connection is the poll's own and never the user's shared ssh master, so a master whose route died cannot make a poll wait past its connect timeout. While the cluster is not answering the next attempt comes after two minutes instead of the full period, and an answer restores the regular cadence. The head marks its "as of" time stale when the answer on screen is older than the period plus two minutes. A failed poll keeps the last good queue, recent and partition rows under the state word with the time the cluster was last reached, and their controls are shown unpressable until it answers again. When `slurm.prewarm` is on, the log paths of the finished jobs are resolved in the background after each good poll, one at a time and joined by nothing a press waits on, so the first press on a log is as fast as the second and no press waits on the prewarm's walk.

**PTY** (step 6). Sessions run inside tmux (`tmux new-session -d -s ock-<id> claude`), so they outlive the server. oculus attaches a pty to the tmux session and bridges it over the `pty:<id>` channel; the page renders it with xterm.js. A session started elsewhere is observed (transcript only) until Axel explicitly resumes it into tmux with `claude --resume <id>`; nothing migrates on its own. The server sends no signal to any registry pid other than the liveness probe.

**The change log.** Every write that changed something is recorded: what file, what field, the value the file held and the value written, and when. The record is made by the writer, at the one point it holds both values, and is appended as one JSON line to `~/.oculus/changes.jsonl` behind the process's write chain; `changes.keep` in `behavior.yml` is how many lines are kept. It is a machine-local file and not a file of the hub, since git already holds the hub's history and what this answers is what oculus did here. `GET /api/changes` reads it newest first, and `POST /api/write` takes one back with the kind `undo`, addressed by the change's own time: the file is checked to still hold what the write left, and the earlier value goes back through the writer the change came from, so an undo is an ordinary write and is recorded like one.

**Auth.** The server binds 127.0.0.1. Every request is checked against `Origin` and `Sec-Fetch-Site`; a request from another origin is refused, since any page open in the browser can address localhost. Writes additionally carry a token minted at server start and delivered to the page once. The socket accepts nothing from the page except subscriptions and, later, terminal input.

### Client state

Svelte 5 state modules (`.svelte.ts`). `entities` holds the latest payload per channel. `selectors` computes the joins (`projects` with venue, funding, datasets; `sessionsByProject`; `workspaces`). `layout` holds the tree below. `ui` holds theme and per-view-instance state such as selection and filters. `layout` and `ui` persist to `localStorage` under one versioned key. Views read selectors and write `ui`; they never touch `entities` directly.

## Layer 3, view

**Primitives** (`ui/`): `Card`, `Chip`, `Meter`, `Table`, `Pane`, `Tabs`, `Sash`, `Empty`, `Toolbar`. Props are values and callbacks; a `Chip` takes a label and a tone. Nothing here imports state or knows what a project is.

**Shell** (`shell/`): the workbench. An activity rail on the left selecting what the rail lists; one tree of panes with tabs, split any way and any depth; sashes between the children of every split, and one control on each child that collapses it to the split's edge and shows it again. The shell renders the layout tree and mounts whatever view instance a pane names. It does not import any view by name; views register themselves in a registry keyed by `ViewId`.

**Views** (`views/`): one file per surface. A view reads selectors, composes primitives, writes its own instance state. It does not know where in the tree it sits, and it has no internal multi-pane layout. Sessions is therefore six views, arranged by a saved default layout, not one view with three panes inside.

**Boundaries**, enforced by `tests/boundaries.test.ts` over the import graph:

| From | May import | May not import |
|---|---|---|
| `ui/` | `ui/`, `themes/`, `state/text` | `state/*` otherwise, `views/`, `shell/`, `server/` |
| `shell/` | `ui/`, `state/context`, `state/use`, `state/layout`, `state/drag`, `state/ui`, `state/text`, `state/appearance`, `state/palette`, `state/palette-source`, `state/selection`, `state/terminals`, the view registry | any view by name, `server/` |
| `views/` | `ui/`, `state/`, `views/shared/`, its own partials under `views/<name>/` | `shell/`, `server/`, other views and their partials |
| `state/` | `data/model`, `data/guards`, `data/dates`, `data/deck`, `data/leads`, `data/worktrees`, `data/text-kind`, `views/registry`, `ui/tip-ids` | `server/`, anything else in layer 3 |
| `data/`, `server/` | `data/` | anything client-side |

SvelteKit enforces the last row's server half by refusing client imports of `$lib/server`.

The client's stores are one object, built once by the page root (`createClientState` in `state/context.ts`) and read from Svelte's context by everything below it (`useState` in `state/use.ts`), so no store is a module anything imports and two pages share nothing. `state/context.ts` is the one module of the state layer that names layer 3: the view registry and the primitives' tooltip counter are instances like the rest, and this is where every store is wired to the stores it reads. The shell's row still names the stores the workbench is made of, and `tests/boundaries.test.ts` holds a shell file to that list by the stores it takes out of the object rather than by the module it imports. Three modules stay module-level and are named in that test: the catalogs `state/text.ts`, `state/tones.ts` and `state/appearance.ts`, which hold what the server last sent, are never written after a push installs them, and are read by `t()`, `toneOf()` and `themes()` from every layer including `ui/`; with them the two runes that make those reads redraw, `state/generation.svelte.ts` and `state/glyphmode.svelte.ts`, since a generation held per client would say a push had landed for one client and not for another over the one set of maps they both read.

A partial under `views/shared/` may import `ui/`, `state/` and `views/shared/`, and nothing under any other `views/<name>/`; nothing outside `views/` imports it. It is where a block two views draw the same way lives, the project card and the subtasks block being the two, so the alternative to a view importing another view's partial is one shared partial rather than a copy that falls behind. The card's cross-link tags are one labelled line per kind (funding, research line, datasets, collaborations), each line drawing three entries and a control that draws the rest of that kind in place.

## Layout as data

```ts
type ViewId   = 'focus' | 'projects' | 'archive' | 'venues' | ... | 'session-list' | 'terminal' | 'timeline' | 'changes' | 'agents'
type Instance = { id: string; view: ViewId; state: unknown; preview?: true }
type Layout =
  | { kind: 'split'; dir: 'row' | 'col'; sizes: number[]; children: Layout[]; folded?: number[] }
  | { kind: 'pane';  tabs: Instance[]; active: string }
  | { kind: 'page';  page: string }
type Workbench = { root: Layout; focus?: { path: number[] } }
```

A page is one tree. The shell renders it; a sash drag edits `sizes`; opening a view appends an `Instance`; a drop moves an `Instance` between panes; `preview` marks the one tab of a pane that the next preview open is pointed at instead of a second tab being appended, and it goes when the reader keeps the tab; `focus` is the one pane shown alone while the rest is put away. `folded` holds the indexes of a split's children collapsed to its edge: a folded child keeps its share in `sizes`, so expanding gives back the width it had, and one child of a split is always left open. The saved arrangement is the serialised tree. Two instances of the same view have separate state by construction.

A page leaf shows another page at that spot, by id, and it is a leaf as a pane is: it folds, it takes a neighbour when a tab is dropped on its edge, and it holds no tab of its own. Three rules govern it. It is the same page and never a copy, so a tab opened in it is open everywhere that page shows and the page is reached by the leaf's own panes rather than by a second tree. A page never shows itself, directly or through another page, so a leaf that would close a loop is refused and never offered. A page is drawn at most once on a screen, directly or through a page the screen already draws, so nothing is drawn twice and no view is mounted twice.

## Theming

`tokens.css` and `themes.css` port from the cockpit unchanged: colours, type scale, radii, fifteen theme blocks that override tokens and nothing else. VS Code Dark Modern and Light Modern are two more blocks, authored for oculus rather than ported, which is why a contrast failure in one of them is fixed in the block and a failure in a ported one is a finding about the port. The contrast test walks every text-on-background pair the primitives declare, under every theme, and fails below 4.5:1. Primitives use tokens only; a raw hex in a component is a test failure.

The wallpaper is one image behind everything, served by `api/wallpaper` from a directory `appearance.yml` names under the hub and nothing outside it. It is on where a theme's class carries `rice`, or under every theme where the config says `all`; the body then carries `wall`, and each component that paints a surface declares under that class what its surface does. The shell's pane box and the box a view fills both paint nothing (the shell's keeps its border), and a view that draws its text straight into its box asks the box for the translucent surface instead, so no text is read off the picture with nothing between. Everything the box holds that paints a surface of its own keeps `panel_opacity` of its colour with `panel_blur` of backdrop blur behind it, and so does the rail and the tab strip: one translucent layer over the picture and never two, since two such layers read as one nearly solid one. A surface inside one of those paints nothing in turn, the current tab inside the strip included. A floating surface keeps `popover_opacity`, which is higher because it is read through a pane as well as through the picture: the menus, the palette, the update tray, the key sheet, the confirm box and the tooltip. The small controls stay solid, being what text is read off: the buttons, the chips, the inputs, the meter, the disclosure, the ticker, a menu's items, a table's rows and every hover response. The colour is still the token the contrast test measured. The toggle in the rail starts on whatever the theme answers and holds a value of its own only once pressed, so saving any other appearance value leaves it alone. A blurred surface is the containing block and the stacking context of every fixed thing inside it, so the rail carries a z-index of its own under the class, over the panes beside it and under the drag layer, and a tooltip's bubble is drawn on the document body rather than inside the surface its control sits on.

The icon set is Lucide at one stroke weight, shipped as the `lucide-static` package, and `icons.yml` maps every name of the glyph vocabulary to one of its icons; the server reads the drawing of each mapped icon once per config load and pushes it with the rest of the configuration, `ui/Glyph.svelte` draws it inline through the icon filter of `ui/html.ts`, and a drawing takes the colour of the text beside it. The capsule belongs to a status word and the project type alone: `ui/Chip.svelte` draws those two in the tone of their status or type, and everything else a surface lists, a dataset, a person, a programme, a deadline, a count, is `ui/Tag.svelte`, the same glyph and words with no capsule. A tag that stands for a state keeps that state's hue as the colour of its words and of its mark, which a line icon takes through `currentColor`; a tag that stands for a name or a count carries none and is muted. `tests/views/chips.test.ts` reads every `<Chip` and `<Tag` site in the tree and fails on a chip toned by anything but a status or a type, and on a tag toned by a token no palette declares.

The glyph vocabulary has an ASCII half, `glyphs.yml`'s `ascii:` map, keyed by the character. A terminal theme draws it unless the viewer asks for the real glyphs, and there no icon is drawn at all. The swap is a lookup where a glyph renders, in `ui/Glyph.svelte` and in `ui/Chip.svelte`'s bracket rule, and never a pass over the document.

## Hot reload

Three kinds of change, three mechanisms, no restart in any of them.

| Change | Mechanism |
|---|---|
| a component, a selector, a primitive | Vite swaps the module in the open page; state survives |
| a server module or an endpoint | Kit's dev server reloads it; the socket reconnects |
| a YAML file in the hub or in `config/` | the watcher rebuilds and pushes; identical in production |

## Relationship to the cockpit

- The cockpit is frozen at what it does on 2026-09-10, plus bug fixes. Nothing new is built there.
- No code is shared. oculus copies the config YAML into `config/` and the memory-tab images into its own assets; the copies are then oculus's.
- Both read the hub's data. After cockpit roadmap H (the private feeds move out of `tools/cockpit/data/` into the hub proper), the hub has one documented data path and oculus reads it from `local.yml`.
- The cockpit retires when the last view it still has and oculus does not has moved. The `.app` launcher then points at oculus.

## Conventions

- Every source file under 1000 lines. A file approaching it is split by concern, never by line count.
- Four-space indentation in every source file, by Axel's instruction of 2026-09-10. Prettier is the formatter, pinned in `.prettierrc` (`tabWidth: 4`, `useTabs: false`), with `npm run format` to apply it and `npm run format:check` as the fourth verification command beside `npm test`, `npm run check` and `npm run build`. A hand-formatted file is never the answer to a failing check.
- ASCII only in every authored file. Glyphs come from `glyphs.yml`, strings from `text.yml`, colours from `tokens.css`.
- One continuous line per paragraph and per bullet in Markdown and YAML; no hard wrapping.
- Plain prose in docs and comments; a comment says why, not what.
- No git command that writes is run by the application or by an agent working on it. Commits are Axel's, one request per commit.
- Work proceeds from the ledger in `.scratch/migration/` (the `.scratch/<feature>/` convention shared with cathedra): `plan.md` is the package list in execution order, `orchestrator-state.md` is read first after any compaction, and every package has a brief under `agents/briefs/` written from `agents/spec.md` and checked against the tree before dispatch. One agent at a time, Opus 5 or lower, never Fable, working in a git worktree at main's head; the result lands on main only by the orchestrator's `git cherry-pick` after the whole diff was read and the verification commands ran, and one package is one commit. Agents never run git and never edit the plan files.

## Migration order

Each step names what "done" means. Nothing visual before step 3.

1. **Cockpit H.** Private feeds moved to the hub proper; path resolution without environment variables. Done when the cockpit runs from the new paths and `tools/cockpit/data/` holds only config.
2. **Scaffold.** SvelteKit with the Node adapter, Svelte 5, Vitest. `lib/data` complete with per-source tests; `validate` reports zero findings on the real hub; `normalise` produces a snapshot; `server/socket` pushes it; the boundaries, contrast and keys tests pass on the ported tokens and catalog. Done when a bare page shows the snapshot's version number updating as a manifest is edited.
3. **The shell** (cockpit roadmap A). Workbench, activity rail, tabs, panel with right/bottom/hidden, sashes, the layout tree persisted, theme switching. Done when an empty view can be opened, arranged, and the arrangement survives a reload.
4. **Projects.** The first real view: cards, filters, the manifest edit form writing back through `api/write`. Proves the design system and the data layer on a static, simple case. Done at parity with the cockpit's Projects tab.
5. **Sessions** (cockpit roadmap B, D's read side, and E). The six session views and their default arrangement; the `sessions` and `git` channels; dismissal and pinning through `api/write`; the `Notification` and `Stop` hooks posting to the server (permission granted 2026-09-09) and the server firing a macOS notification through `osascript` the moment a session wants you. Done at parity with the cockpit's Sessions tab plus the notifications.
6. **Terminal** (cockpit roadmap C, then D's write side and G). tmux, the `pty` channel, xterm.js, the composer, explicit migration of an existing session. Then the git panel with staging and the token-guarded commit, then the deposit action with its dry run and the Data view's per-dataset recovery command.
7. **The remaining views** (cockpit roadmap F among them), in the order they are used: Focus, Archive, Coauthor, Venues, Funding, Data (with the per-dataset recovery command), Lit Watch, Leads, Inbox, LinkedIn, Live HPC, the file browser with bookmarks and notes, Memories, Help, Audit, Config.
8. **Retire the cockpit.** Launcher repointed; `tools/cockpit` archived; hub docs updated.

- 2026-09-16, Tab moves the focus and Ctrl with a bracket cycles a pane's tabs. A bare Tab or Shift+Tab reaches no binding of the shell: `resolveKey` in `shell/keys.ts` answers nothing for it and nothing prevents its default, so the browser carries the focus from one control to the next as it does on any page, which is what a reader pressing Tab in a search box, a form or a toolbar is asking for. Ctrl+] and Ctrl+[ take what Tab did and narrow it to the pane under the keyboard: the key resolves to `{ kind: 'cycle-tab', by }` and the workbench moves the focused pane's `active` one place along the `tabs` list of "Layout as data", wrapping at either end, so a pane of two tabs swaps between them on one key. Ctrl and Tab is not the pair: a browser keeps that chord for its own tabs and never dispatches it to a page, so a binding on it would be dead, and the brackets are bound to nothing. The cycling Tab had was over the rail's whole display order, which the chords of the 2026-09-11 line above and the palette already reach, so it is not rebound; `currentView` leaves `KeyContext` and `all` leaves `RailOrder` with it. Ctrl and a digit still answers while a field, the palette, the update tray or a confirmation holds the keyboard, since a digit is not what any of them wants from that chord; Ctrl and a bracket is silent there, because a bracket is a character a field takes. Cmd with a bracket is a browser's own navigation and is bound on no platform. Tab reaching the controls again makes the focus order itself a design surface. The rail is one stop of it and each strip of tabs is one stop, its pane menu the stop after it, since the menu is a control of the pane rather than of the strip; everything else in a strip, the close control and the two scroll controls, carries -1, the scroll controls because the arrows reach every tab whether it is on screen or not and bring the one they land on into view. `tabindex` 0 sits on the control at the stop and -1 on the rest, and the stop moves: in a strip it is the tab the arrows last left the focus on, back to the showing tab when that changes; in the rail it follows the focus, and when the control at the stop leaves the ring, which is what the reader's own press does to the text reset, it passes to the control that took its place and takes the keyboard back, since the browser drops the focus to the document when it disables a control under it. Both rules live once in `ui/roving.ts`, `nextStop` and `heldStop`. The rail's controls sit in a `role="toolbar"` inside the `<nav>`, so the landmark stays a landmark and a reader is told the arrows move along it, and each control answers the arrows itself, so no container takes a tabindex or a focus of its own. Delete closes the tab the focus is on, through the same call the close control makes. The key sheet's rows and HELP.md carry the pair beside Ctrl and a digit, the arrow row, the Delete row, and in words that Tab is the browser's. Package Q27.

- 2026-09-16, the LaTeX panel on a project. A project tab lists the main files of its `manuscript/` folder and builds each one. A main file is content rather than configuration: every `.tex` directly under `manuscript/` whose text carries `\documentclass` outside a comment, `main.tex` first and the rest by name, so a manuscript that gains a supplement or a highlights file is listed the moment it is written and no manifest key has to be kept in step with the folder (Axel's ruling, against a `manuscript: { mains: [...] }` key every manuscript would have had to gain). The build and the clean are task terminals, the shape `recover` and `task` already have in `server/pty/routes.ts`: the page sends the project id, the file and the step, and the server builds `latexmk -pdf -interaction=nonstopmode -file-line-error <main>` or `latexmk -c <main>` and runs it as a shell terminal in the manuscript folder, the file checked against that folder's own main files before a command is built from it. `-file-line-error` is what puts a file and a line in front of every error, which is the form `server/latex.ts` reads the log back in; only what a row of the log itself names is attributed, since a file and a line inferred from the file the log happened to have open read worse than none. `GET /api/latex?id=` answers the rows, and the end of a build is the terminal leaving the terminals list of the `sessions` payload rather than a channel of its own, since that list already says which sessions are running. A rebuilt PDF is redrawn through a version on its address: `fs.bump(root, path)` moves a per-file counter that `fileBytesUrl` carries as `?v=`, so an open PDF tab fetches the new build instead of the bytes the browser cached under the old address.
