# oculus, design

The successor to the research cockpit (`tools/cockpit`). Same job: a private, local dashboard over the research portfolio, its projects, venues, funding, data, and the Claude Code sessions working on it. Different construction: one language, three layers, one definition per screen, live data pushed by the server rather than polled by the page, and an arrangement you edit in the app.

This is the artefact every change is measured against. When the code and this file disagree, one of them is wrong and the disagreement is a finding, never something to paper over.

The name: the eye, alongside `iris`, `scotoma` and `umbra`; and the opening at the top of a dome that lets the light in, alongside `cathedra`.

## Why a new tool

The cockpit is a Python static-site generator that emits one 8.8 MB HTML file with all CSS and JS inlined, plus a Python dev server that patches the page in place when files change. That shape was chosen so the output would be a single portable file with no build step. The file is never opened; only the served app is used. Every awkward thing in the cockpit follows from a constraint that no longer applies:

- 3668 lines of Python build HTML through f-strings, and 3477 lines of client JS render the live half of the same screens. The Sessions tab is defined in both.
- A live-reload "morph" patches the generated document in place, with `data-skipmorph` escape hatches so it does not wipe what the client rendered, and MutationObservers to re-apply client decoration after it does.
- A hand-rolled module system (`window.CK`, load-order rules, a custom test) stands in for a bundler.
- Config is read into module-level singletons at import, so a config edit re-execs the whole process.

None of these are bugs. They are the cost of the constraint. oculus drops the constraint and therefore the cost. Nothing in the cockpit is thrown away carelessly: the data files are kept as they are, the configuration files are copied over and keep their roles, the palette and themes port unchanged, and the gates port as tests.

## Non-goals

- Not multi-user, not remote, not peered. Clodex-style fleet features are out.
- Not an IDE. It is a development platform for the hub's own files: a file browser, an editor for every text file, search, a language server client, LaTeX builds, PDF reading, project commands and the rite debugger; no lint panel and no other debugger.
- Not a rewrite of the data. The YAML in the hub is the source of truth and its shape does not change for oculus.

## The three layers

**Data.** Reads files, produces a typed, validated model. Knows nothing about screens. Runs on the server.

**Code.** Everything between the model and the pixels. Split by where it can run: the server-pinned half touches the filesystem, git, processes and the socket; the client half holds state and computes joins and filters. Neither half renders anything.

**View.** Components. Split into primitives that know no domain, a shell that knows no view, and views that know no layout.

The rules that keep this honest are the import-graph tests (`tests/checks/tree/boundaries.test.ts` for the layers, `tests/checks/imports/` for the order of the folders inside a layer and for cycles) plus one boundary SvelteKit enforces itself. See Boundaries below.

The Help page's group, `help` (Help, chord `h`), holds the manual, the Memories wall and the hub's documents, which the Help page's arrangement draws; every group has a chord, so every entry of every group has a key.

## Configuration

The tracked files under `config/` and `config/catalogs/` are the interface described as data, one concern to a file, and they are treated alike; `config/local.yml` sits with them and is the machine's own, read by `loadLocal` and never merged. What the portfolio reads in `sources.yml` (the tier scan paths, the registry and collection files, the document and feed paths) and the map from a file name to its language (`languages:`, a language's name against the file name endings it claims); words and their colours in `catalogs/vocab.yml` (the palette, the research `domains`, the status legend and palette, the focus lanes, the venue tiers, the venue and dataset theme words with their labels, the radar buckets); how things are arranged in `layout.yml` (the rail's pages and their arrangements, the view catalogue's groups, the board chrome, the tab rollups, the live badges, which title a surface draws); thresholds and horizons in `behavior.yml`, which also holds the source editor's `editor:` block (`tab_size`, `insert_spaces`, `word_wrap`, `minimap`, `render_whitespace`, `sticky_scroll`, the per-language `languages:` records of `tab_size`, `insert_spaces`, `word_wrap` and `rulers`, and `paint_limit_kb`), the Literature search's `literature:` block (`timeout_s`, `per_source`, `cache_min`), which a repository's `.oculus/settings.yml` `languages:` map overrides per language for the files of that root, through `resolveEditor` of `data/helpers/editor.ts` and `parseRepoSettings` of `data/sources/config/editor-options.ts`; the UI theme list with each theme's glyph, the wallpaper, the CRT default and the code theme (`code_theme:`, `tokens` or the id of a Shiki theme, which the Code theme row under This browser in the Settings view overrides per browser, just as its CRT row overrides `crt.default`; only the editors' syntax colours follow it, and Markdown code and the read-only code windows stay on highlight.js and the tokens) in `appearance.yml`; the glyph vocabulary in `catalogs/glyphs.yml` and the icon each of its names is drawn as in `catalogs/icons.yml`; every user-facing string in the catalog fragments under `config/text/`, read through `t("group.key")` on the client and, for the data layer's findings and the audit's, through `findingText` of `data/helpers/finding-text.ts` on the server; the edit form in `catalogs/manifest-schema.yml`; the tool's own identity in `catalogs/meta.yml`; the agent composer's models, efforts and permission modes in `catalogs/agents.yml`; every option of every config file in `catalogs/options.yml`, read through `catalogOf` of `data/sources/config/catalog/options.ts`, with its description, its default, the `heading` the Settings view lists it under (one of ten subject words, `unheaded` when it names none or an unknown one) and its `section`. The `control` is one of `toggle`, `number` (bounded by `min` and `max`, and held to a whole number by `whole: true`), `text` (held by `form` to one of `program`, `extension` and `bundle_id`), `long`, `choice`, `multi`, `list`, `glyph`, `hue`, `colour`, `folder`, `file`, `path`, `parked` or `records`; a family carries `fields` instead, each field being an entry of the same form, so a field has a control of its own. A `list` of numbers takes `min`, `max` and `whole` for each item, and a `list` takes `form` for each item. A choice or multi takes its words from a fixed `values` list or from `values_from`, the sources it names (`SOURCES` of the same module: the domains, clusters, models, views, usage tiers, theme classes, wallpapers and the rest, derived from the merged configuration by `configItems` or from what the page holds); in a family `values_by` names the field of the record that decides which source another field draws from. `suggest_from` gives a text box suggestions; `empty` lets a choice or path hold `''` and may carry the words of the empty item; `slots` names the fixed items of a list; `items: number` makes a list's items numbers; `joined` writes a multi as one string; `allow_missing` lets a folder or file be absent, always or while a named toggle of the record is true. `loadConfig` merges every file's top-level keys into one map and reports a key two files define, so a key moves between files without a reader noticing and no key sits in two. No component contains a literal user-facing string, a raw colour, or a literal glyph. `tests/checks/source/keys.test.ts` fails on a `t()` key that does not exist, so a typo is caught before it renders blank, and `tests/checks/config/config-folder.test.ts` fails on a glyph name nothing reads, on a glyph name whose stand-in is not one to three printable ASCII characters, and on a glyph name with no icon. A request reads the configuration at most once and only if it asks: the page's title and its load share one read, and an API route reads none. The page starts from its own read and takes only a `config` push newer than the hub version that read is at least as new as, so the push the hub replays from before a config change does not replace it; the read rides in the page data only when the hub holds an older configuration, and a reconnect lifts the bound.

Paths resolve without environment variables: the command-line argument `--engine <dir>`, then `local.yml`, then a default derived from the file's own location. The hub path is the one value every machine must set and it lives in `config/local.yml`, gitignored and left out of the merge, so the tree carries no machine path. Roots the file browser may serve are set in the app and stored in config; nothing outside a root is ever served. The open action, `POST /api/open`, works on those same roots, `browserRoots` with the saved workspace's own: a folder under them is revealed in Finder and a file is opened in the one application `open.program_ext` of `behavior.yml` names for its extension. The boundary is the roots, so a dotfile the tree leaves out of its listing is resolved like any other path under a root. A Customizations item names its file by real path (a link followed to its target), so the roots decide where it opens: a file a root holds opens a source tab, and any other opens the Customization viewer.

## Layer 1, data

**Sources.** One module per kind of file. Each exposes one function that takes a root and returns raw records, and each is unit-tested against synthetic fixtures in a temporary directory. No source knows another exists.

**Model.** `model/index.ts` and the concern modules beside it hold the types and nothing else. The core entities are `Project`, `Venue`, `Dataset`, `Pillar`, `Domain`, `Funding`, `Collection`, `Entry`, `Doc`, `SideProject`. A project carries the ids of its relations (`venueId`, `fundingIds`, `datasetIds`), never resolved objects: a project points at its funding and the funding points back at its projects, and that loop cannot be turned into JSON.

**Validate.** Every id referenced resolves to an entity; every status is in the vocabulary; every manifest field is one the schema names; every theme word of a venue or a dataset is on its list in `vocab.yml` (`venue_themes`, `data_themes`). Failures are reported with file and key, and a run against the real hub must report zero. It runs on every rebuild, so a bad manifest edit shows in the app within a second, as a finding, never a crash. A finding's sentence is a key of `config/text/findings.yml`, worded on the server before the snapshot carries it as a plain `message`, so a sentence is reworded in that file alone.

**Normalise.** What goes over the wire:

```ts
type Snapshot = {
  version: number                         // increments on every rebuild
  entities: { projects: Record<Id, Project>; venues: Record<Id, Venue>; personal: Record<Id, SideProject>; ... }
  relations: { projectFunding: [Id, Id][]; projectDataset: [Id, Id][]; ... }
  findings: Finding[]                     // from validate
}
```

Flat, JSON-safe, small: the whole hub is a few hundred kilobytes. Documents are not in it; `api/docs` serves one when a view opens it. That is the reason the cockpit's page is 8.8 MB and this one is not. The one exception is a project's `PRESENT.md` front matter, and for a file that has none its narrative: the Present view draws a slide on a key press, so its slides ride in the snapshot rather than being fetched one at a time. A document answer carries an `ETag` of the server process, the file's size and its modification time, and the absolute path of the file read; the page sends the tag back in `If-None-Match` when it asks again, and an unchanged file under the same process is a `304` that keeps what the page holds, so a re-read renders nothing and a restarted server renders once.

## Layer 2, code

### Server

**The socket.** One WebSocket per open page. Messages are `{channel, version, payload}`. Channels: `portfolio`, `config`, `sessions`, `git`, `files`, `hpc`, `calendar`, `inbox`, `usage`, `feeds`, `audit`, `processes`, later `pty:<id>`. A page subscribes to the channels it needs; the server sends the current payload on subscribe and pushes on change. If a page falls behind, the server keeps only the latest payload per channel: the newest state is the only one that matters.

**Watchers.** Each channel has one watcher module that owns its `fs.watch` handles, rebuilds only what changed, and pushes. The usage, bookmarks, portfolio, local and sessions watchers debounce with lodash's `debounce` and a `maxWait` of twice the quiet, so a file written without a pause, as a transcript is while a session works, is rebuilt at least every `maxWait` and not only once the writes stop; the debounced function starts the rebuild and returns, and lodash does not wait on a rebuild still running. The usage watcher runs one rebuild at a time and keeps at most one waiting behind it, which every refresh in the meantime joins, so a fold slower than its `maxWait` under steady writes leaves one rebuild queued and not one per `maxWait`; a rebuild that fails is logged, and the one waiting behind it still runs. Portfolio watches the hub's YAML directories. Sessions watches, for every account in `local.yml`'s `accounts`, each Claude account's `<dir>/projects` (transcripts) and `<dir>/sessions` (the registry) and each Codex account's `<dir>/sessions` (rollouts), every folder once by its real path, plus the overrides file. Git does not debounce: it watches each workspace's `.git/index` and worktree and throttles per root, reading at once on the first event after a quiet period and once more at the end of the next two seconds when events came in them (`touch` of `server/root/watch/git.ts`), so it re-reads on change no more often than every two seconds. It also polls the saved workspaces file every 500 ms on its own clock, so a root added in the page is read at the next tick even when a folder watch would have lost the write. It drops an event whose path (the path itself, not a link's target), or the nearest folder above it that is still there, last changed before the newest read of that root that answered began, since fseventsd can deliver the writes that made a root after its watch opened; a read that failed hides nothing. Bookmarks watches `~/.oculus/bookmarks.yml` and publishes on the `files` channel, so a bookmark written outside oculus reaches an open page. `server/root/watch/autofetch.ts` owns no channel and no handle: it looks at the `config` and `git` channels once a minute and fetches as the Git paragraph says.

**Sessions.** Facts that cost real time to establish and must not be rediscovered:

- Transcripts: `<dir>/projects/<slug>/<id>.jsonl` of each Claude account, 490 files and 1.2 GB on this machine. A 48 MB transcript folds in 0.2 s. The turns of a transcript are read in pieces of 8 MB (`PIECE_BYTES` of `foldFrom` in `server/sessions/stores/transcripts.ts`), each complete line decoded alone, so the size of the file bounds nothing: a line longer than Node's longest string (`buffer.constants.MAX_STRING_LENGTH`) is skipped and counted as read, and a read that fails after some lines answers the bytes it consumed, so the page asks on from there and not from 0. A first read answers the last 200 turns and `readTurns` holds every turn of the file while it reads, which costs about 460 MiB more for a 629 MB transcript; a later read asks from the offset it was given, and the Markdown export is streamed a turn at a time (`markdownStream` of `server/sessions/transcript-routes.ts`), so a transcript whose text passes the longest string is one download. The session record's own fold is bounded: a first read of a file above `MAX_FIRST_READ_BYTES` (256 MB, `server/sessions/cache.ts`) is not folded and the record says so. A byte-offset cache means a later read takes only what was appended. Any change to the accumulator's shape bumps the cache version. A subagent started in the background is not ended by its launch answer: its row runs until a completion notice names its tool-use id or agent id (`completed` done, `killed` stopped, anything else error), or until `subagents/agent-<id>.jsonl` has been still for the idle time; a subagent whose own transcript is written after the notice that ended it has been resumed and runs again.
- Subagents are `tool_use` blocks named `Agent`, paired to their `tool_result` by id. `isSidechain` is false on every record everywhere and carries no information.
- The live registry: `<dir>/sessions/<pid>.json` of each Claude account, with `sessionId`, `status` (`busy` or `idle`), `name`, `cwd`. Liveness is `kill(pid, 0)` plus a `procStart` match; the registry writes that stamp in UTC and `ps`, run under the C locale so its stamp is readable, reports local time, so the match parses both and allows two seconds. One `ps` per scan answers the start times of the registry's pids.
- Grouping: workspace by walking up to `.git`; area scored from touched files with the cwd counting double, directories clamped to two segments below the workspace root, known project folders exempt from the clamp.
- Context occupancy is the last assistant turn's `input + cache_creation + cache_read`, never the lifetime sums.

**Git.** The read-only modules of `server/core/git/` run exactly these forms over seventeen subcommands, through one subprocess call site (`run.ts`) with a five-second timeout and list arguments only: `state.ts` reads the `git` channel, `reads.ts` and `files.ts` the on-demand reads below, `compare.ts` the reads of the compare items, and `parse.ts` parses what they print. For the `git` channel: `rev-parse --git-dir`, `rev-parse --abbrev-ref HEAD`, `symbolic-ref --short HEAD`, `rev-list --left-right --count @{upstream}...HEAD`, `status --porcelain=v1 -z --untracked-files=normal --renames`, `diff --numstat -z`, `log -<n> --format=`, one `for-each-ref --format= refs/heads refs/tags refs/stash` for the branches, the tags and whether a stash is kept, `log --walk-reflogs --format= refs/stash` only where one is, `remote` only where the branch has no upstream and HEAD is not detached, and `worktree list --porcelain`, with the merge, rebase or cherry pick in progress and git's prepared merge message read from the repository's git folder (the cherry pick by the existence of `CHERRY_PICK_HEAD`). A list of changes is cut at 200 entries, and the channel carries how many each group held before the cut (`GitState.held`), which the views say and the rail badge sums. On demand, for GET /api/git: a page of the graph (`log --topo-order --skip=<n> -<n> HEAD`), the commits either side of the upstream (`log --topo-order HEAD..@{upstream}` and `@{upstream}..HEAD`), `blame --porcelain -- <path>`, the blame of a file at HEAD (`blame --porcelain HEAD -- <path>`) and in the index (`blame --porcelain --contents - -- <path>`, the staged text on its input, `blameAt` of `server/core/git/compare.ts`), the gutter marks (`diff -U0 -- <path>`), a stash's diff against its first parent, the three index stages of a conflicted path (`show :<1|2|3>:<path>`), a commit's files (`show --name-status -z --diff-merges=first-parent`) and one file's change in a commit, the commits that touched one file across its renames (`log --follow --relative -z --name-status --diff-merges=first-parent --format=<fields> [-51] -- <path>` under `GIT_LITERAL_PATHSPECS=1`, which the Files view's Timeline asks for through `GET /api/git?log=<repository>&path=<file>[&before=<hash>]`: the first page asks for 51 rows and the 51st only sets `more`; the page after a commit reads the log from HEAD with no count, finds the row of `before` and answers the 50 rows after it, with `more` set when a row past them exists, so a merge's second parent and a side-branch commit at a page boundary are listed once; `--relative` makes every row's path relative to the served root, which may be a sub-folder of its repository), where a worktree's diff starts (`merge-base <branch> HEAD`), whether git converts a file's text (`check-attr` and `config --get --default= core.autocrlf`), and the ssh command a repository names (`config --get --default= core.sshCommand`), which the automatic fetch extends. The compare reads of `compare.ts` are: a file as HEAD or the index holds it (`cat-file -t HEAD:<path>` to tell a path HEAD lacks, `show --no-textconv HEAD:<path>` or `:0:<path>`, and `ls-files --stage -z -- <path>` for the index), a ref against a commit (each ref resolved first by `rev-parse --verify --quiet <ref>^{commit}`, one starting with a dash refused; then `diff --name-status -z -M --end-of-options <ref> <hash>` for the files and `diff --no-color --no-ext-diff -U0 -M --end-of-options <ref> <hash> -- <path>` with `show --no-textconv <hash>:<path>` for a file's two sides), the refs a picker lists (`for-each-ref` over `refs/heads`, `refs/remotes` and `refs/tags`), and the base Compare with Merge Base names, read as VS Code reads it (`config --get-regexp` of `branch.<name>.vscode-merge-base` when it names a remote branch, else the branch the checked-out one was created from by `log --walk-reflogs --format=%gs`, else the default branch of its remote from the `for-each-ref` table, with `symbolic-ref --short HEAD` naming the branch). Compare with Workspace reads a linked worktree's file and the main worktree's from disk, each kept inside its own worktree and the main worktree refused unless its real path lies under one of the published roots, and runs only `worktree list --porcelain`. The file browser's listing asks the same call site which of a folder's entries the repository ignores (`check-ignore --stdin -z`, `ignoredIn`), and a failure leaves out nothing. For the Status view's line counts, GET /api/lines asks it for the paths tracked under the engine folder (`ls-files -z`, `trackedFiles`), which `server/machine/lines.ts` hands to cloc. Submit asks it for the files a project's code folder keeps (`ls-files -z --cached --others --exclude-standard`, `keptFiles`), tracked files and untracked files that are not ignored, which `server/machine/hpc/submit.ts` filters and sends. No writing subcommand appears in the module; `symbolic-ref`, `worktree`, `remote` and `config`, which have writing forms, and `rev-parse`, `check-ignore`, `ls-files`, `for-each-ref` and `check-attr` are held to the exact vectors listed in the head comment of `run.ts` and in this paragraph; no test pins them, so a form added to the module without being added to both lists is found only when the list is read at review. Every write is `server/git/git-write.ts`'s, one call site per subcommand (`add`, `apply`, `restore`, `commit`, `merge-base`, `push`, `pull`, `fetch`, `remote`, `branch`, `switch`, `check-ref-format`, `status`, `diff`, `rev-parse`, `worktree`, `merge`, `rebase`, `rm`, `stash`, `tag`, `cherry-pick`), among them `switch --detach` for Checkout (Detached), `branch -d` for Delete Branch (a branch git calls not fully merged is refused with the code `not-merged` and kept, and the page then asks VS Code's second question, "The branch '{0}' is not fully merged. Delete anyway?", whose yes runs `branch -D` through the same call site as the `deleteBranchAnyway` action) and a start point on `branch` and `tag`, and `git-remote.ts`, `git-index.ts` and `git-refs.ts` beside it reach git only through those call sites; no form carries `--force`, `branch -D` after Delete Anyway's question is the one form that discards commits no other branch holds, and the list and the absence of `--force` are held by the forms listed in the head comment of `server/git/git-write.ts` and by this paragraph, read at review, with no test pinning them. Two writes touch files and not git: `trashUntracked` (`server/git/git-index.ts`) moves untracked paths to the operating system's Trash (the `trash` library, as the Files view's Trash does), refusing a path the server guards, a tracked path, a path outside the repository, a real path that leaves it and a symbolic link whose target leaves it; a link whose target is missing goes as the link, and a collapsed folder goes as one folder; `ignore` (`git-index.ts`'s `addToGitignore`) appends the paths to the root's `.gitignore`, which the view then opens in a source tab. The commit passes `user.useConfigOnly` through git's environment (`GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_0`, `GIT_CONFIG_VALUE_0`), so a repository with no configured name or email is refused with git's own message and the argument vector stays as the gate reads it. A write runs only from POST /api/git carrying the write token from this application's own page, and one that loses work or reaches a remote also carries the confirm the page sets from a dialog. One exception: while `git.autofetch_minutes` of `behavior.yml` is above 0 (the default is 0), `server/root/watch/autofetch.ts` runs `remote` and then `fetch --prune` through their call sites, unattended (git is told never to ask for a password or a passphrase; when only the older `GIT_SSH` variable names the ssh program, nothing is added for ssh, so ssh may still ask), once per repository on the `git` channel that has a remote, one at a time, once each period, with no token and no confirm. No other write is reached by a watcher, a timer or the socket.
**Fixed git choices.** Oculus makes these choices once, with no setting. Untracked files are a group of their own (VS Code's `git.untrackedChanges: separate`), so Stage All Changes never stages a new file, and Discard on an untracked file moves it to the Trash after VS Code's question. Every root the `git` channel carries is listed in the Repositories view (a repository per configured root, as VS Code's multi-root Source Control lists), because oculus shows every configured repository at once. Fetch prunes (`fetch --prune`, Z83), so a branch deleted on the remote leaves the pickers. Signing is left to git's own `commit.gpgsign`, so oculus adds no flag to a commit. Pull is a plain `git pull`, so the repository's own `pull.rebase` decides between merging and rebasing. A commit never takes an identity git guessed from the machine, because `user.useConfigOnly` is set for it. No Source Control action pushes with `--force`; the deposit snapshot push (`deposit-git.ts`'s `forcePushSnapshot`) is the one forced push in oculus.

**Search.** One pattern over the files of one served root or of all of them, answered by `GET /api/search` behind the origin check and the write token, since a search reads every file of every root and that is more than any other read here gives away. ripgrep comes from the `@vscode/ripgrep` dependency rather than from the machine's PATH, so the search works where no `rg` is installed and the version that answers is the lockfile's. One subprocess call site, list arguments only, the pattern one argument through `--regexp`, a ten-second timeout per root, `--max-count` one past the cap so a file cut short is visible, `--max-filesize 2M`, the root's directory as the working directory and named to the process as `.` rather than left out, since ripgrep given no path reads its own standard input and a server's child has a pipe there that nobody writes to, `.gitignore` honoured as ripgrep honours it and `node_modules`, `.git` and `.svelte-kit` skipped besides. The arguments and every refusal come from `data/helpers/search/query.ts`, which the page runs before it sends and the server runs when it receives, so the two cannot disagree about what a query is; a root that is not one of the served list is refused before any process starts, and a pattern ripgrep will not read answers 400 with `error: 'pattern'` and ripgrep's own one-line reason, which the page shows as it is, as VS Code's Search view shows the regular-expression parse error; it is the one refusal of the Search view whose text is shown, every other refusal being said in the catalog's sentence for its word. The cap bounds the work and not only the answer: the child's output is read line by line as it arrives and folded as it is read, and the child is killed the moment a match arrives with no room left, so a one-letter pattern over a large root buffers what the cap needs rather than the whole stream. The answer is the hits grouped by file, one hit per match, each line cut to a window round its match and each hit carrying `at`, the place of its match in the line in UTF-16 units (a match longer than the window travels whole as group `0`), capped at `search.max_hits` with the cap said when it was reached, and every root whose search failed or ran out of time named in `failed` with `why` (`timed-out` or `failed`) so a missing directory is never silence: the page says each root on its own line, "{root} ran out of time." or "No answer from {root}: ripgrep could not search it.", and never ripgrep's own text. `truncated` means the cap was reached, and a root that ran out of time never sets it. Replace in the Search view is `POST /api/ops` with `op: 'replace'` (`server/files/fs/replace.ts`) and shares the one call site: the request names each match by file, line, `at` and the text it covered, the server runs ripgrep over the file as it is now through `runRipgrep` with a template that reports every group, takes each named match from that run, and refuses the file `changed` before anything is written when a named match is not there with the text it was named with. The text written is computed by `replacementOf` of `data/helpers/search/replace.ts`, which applies VS Code's replace rules (`$N`, `$&`, `\n`, `\U`, Preserve Case) over the groups of the run and is never taken from the page; the page runs the same function to draw each replacement after its struck-through match, so the preview is what is written. Each file is written once, after the local history keeps a copy of it, with the matches spliced in from the end of the file back at their byte offsets and the result checked against the file; a file a source tab holds unsaved is left out on the page and named. Once a file is written, ripgrep reads it again and the answer carries its hits as they are now (`rereads`, one entry per written file, also on a refused answer for the files done before the refusal): the same hit a search answers, with `was` (the line and place it had before the write) on a hit whose match sits on text the write left alone, found by moving the match's byte offset back over the splices, with `edited` when the write also changed other text on that line, and `failed` for a file whose read failed or that holds more than 2000 hits. The page puts those hits in place of the file's hits (`applyRereads` in `state/sources/search/hits.ts`), so the next Replace names the lines and places the file has now; a hit the reader dismissed (kept in the tab's state as a place) stays out when a re-read hit's `was` is its place and the write left its line alone, and comes back when the write changed its line (`edited`), a file whose read failed keeps its row and asks for a new search, and the focus goes to the row it was heading for, found at its new place. The Replace Preview opens beside the Search tab: `openDiff` passes the asking instance, and the landing of a view opened for something treats that instance's pane as locked (`away` in `landingFor`) and splits a new pane to its right when no other pane takes the preview. `POST /api/ops` with `op: 'preview'` and the write token, outside the write chain since it writes nothing, answers a file and the file with the named matches replaced as the two sides of the diff pane the Replace Preview opens, and leaves a named match that is no longer there unreplaced; its body carries the query, the replace text, Preserve Case, the file and its hits as `line` and `at`, so a file with any number of hits can be previewed, which an address could not carry (Node refuses a request head over 16384 bytes). The pane reads it through `diffRequest` of `state/sources/repositories/answers.ts`, and a pane draws the answer of its newest read only and none once it is closed. Turning the regex, case or whole-word toggle over while results are shown, or while a run is in flight (which is aborted), runs the search again, so the preview and Replace read the answer under the toggles on screen; what a Replace All over the whole answer said takes the place of the count line until the results next change (a Replace, a Dismiss, a new run or an edit of the query), and a replace that fails says why whatever it replaced.

**Literature search.** One query over eight scholarly sources, answered by `GET /api/literature` behind the origin check and the write token, since a search puts the reader's query in a request to a third party and spends the keys of `local.yml`. The route has three forms, `?sources` (the eight sources, whether each needs a key and has it, and the name of the key, never a value), `?source=<id>&q=...` (one source's search, its answer `ok` with the hits or a state: `limited`, `timeout`, `refused`, `failed`, `no-key` or `skipped`) and `?bibtex&doi=...` (one entry as a source serves it). The page sends one request per source that is on and merges the answers as they arrive, so a slow source never holds a fast one, and a state of one source is that source's answer, never an error of the route. The adapters are in `server/content/literature/sources/`, one per source, each reading its answer through a zod schema beside it, with `fast-xml-parser` reading PubMed's `efetch` and arXiv's Atom. Every request goes through `ServerContext.literature`, a `LiteratureDesk` that holds one lane per source (one request in flight, and a minimum gap between two starts: 3000 ms for arXiv, 1000 ms for Crossref and Semantic Scholar, 340 ms for PubMed without a key and 100 ms with one) and the cache of `ok` answers (at most 200, kept `literature.cache_min` minutes under a key of the source and every parameter, no key among them), so no module keeps either as state of its own. Each request is given `literature.timeout_s` seconds, an answer is read to 5 MB and no further, and a 429 is never retried. A key is a header or a query parameter of the request to its source, read from `locals.server.local` at each request, and it is in no answer, no refusal word, no log line and no thrown message: a failure names the source, the status and the source's own plain code, never the address or the body. The merge, the filters applied again after the fetch, and the sort are pure functions in `state/feeds/literature/`, so a change of sort asks nothing.

**Live HPC.** One poller runs `squeue`, `sacct` and `sinfo` in a single ssh call every `slurm.poll_min` minutes, with disk quota on its own slower cadence, and publishes one complete state on the `hpc` channel. The connection is the poll's own and never the user's shared ssh master, so a master whose route died cannot make a poll wait past its connect timeout. While the cluster is not answering the next attempt comes after two minutes instead of the full period, and an answer restores the regular cadence. The head marks its "as of" time stale when the answer on screen is older than the period plus two minutes. A failed poll keeps the last good queue, recent and partition rows under the state word with the time the cluster was last reached, and their controls are shown unpressable until it answers again. When `slurm.prewarm` is on, the log paths of the finished jobs are resolved in the background after each good poll, one at a time and joined by nothing a press waits on, so the first press on a log is as fast as the second and no press waits on the prewarm's walk. The host it connects to is the machine's `hpc_host` of `local.yml` when that names one, else the `host` of the cluster entry of `registries/resources.yml` that `slurm.resource` of `behavior.yml` names (`server/machine/hpc/host.ts`). When the entry is missing, is not a cluster, has no host, or has a host that is not a plain ssh alias, the poller has no host: it runs no ssh, publishes `unreachable` with the sentence for why, and the view shows that sentence in place of the ssh error. The registry is portfolio data a user may edit while the server runs, so the host is resolved again after each portfolio rebuild. The cluster receives two writes from oculus, both through POST /api/hpc: Live HPC's cancel runs `scancel <id>` (`server/machine/hpc/actions.ts`), and **Submit Job** (`server/machine/hpc/submit.ts`) copies a project's code and queues a job. Submit Job sends `action: 'plan'` (a served root and path), which answers the `SubmitPlan` of a `.slurm` file under a project's `code/` folder, and `action: 'submit'` with the plan and `confirm: true`, which runs it. The plan names the code folder, the cluster folder (`paths.cluster` of the manifest, else `~/projects/<id>`, held to `clusterFolder` of `data/shapes/shapes.ts`), the files git keeps minus `__pycache__`, `.npy`, `results/` and `logs/`, the rsync arguments, the one remote command `cd <folder> && sbatch --parsable <script>`, and whether the script or a file it sources names `/local/$SLURM_JOB_ID` (`scratch.ts`, reading each file through the shell parser `sh-syntax` so comments never count). The run computes the plan again at the press and refuses with `changed` unless it equals the confirmed plan; it then runs `rsync` (`transfer.ts`, an argument vector with the file list on standard input and no shell, never `--delete`) and the ssh command of `ssh.ts`, with a refusal word for each step that fails (`copy-failed` carries one line of rsync's stderr, `submit-failed` sbatch's). One run per `<host>:<folder>` at a time; closing the server aborts the runs and their children, and a run that is computing its plan at the close, or that arrives after it, is refused as `closed` and starts nothing. A failed copy carries one line of rsync's stderr: the first line that begins `ssh:` when there is one, else the last. The copy passes no `--mkpath` and runs no remote `mkdir`, so a cluster folder that rsync cannot create ends in `copy-failed` with the line rsync wrote.

**Processes view.** The Processes view lists what oculus started itself in tmux and the local processes whose program the `processes.patterns` list of `behavior.yml` names. Oculus's own are the process trees under the pane of every `oculus-<id>` terminal session (one `tmux list-panes -a` read, then a walk down by parent pid); the hidden usage sessions and a session named `oculus-` by hand are not oculus's own. A pattern matches a process when it equals the file name of the first or of the second word of the command line, so `node /usr/local/bin/codex` matches `codex` and `/bin/zsh -c source ~/.claude/s.sh` does not. The watcher reads the process table from one `ps -axww` run that oculus starts itself, with an argument list, no shell and `LC_ALL=C`, under a ten-second limit at which the child is killed (a close of the watcher kills it too), and the working folder of each listed process through one `lsof -a -d cwd -Fn -p` call with a five-second timeout, and publishes one payload on the `processes` channel every ten seconds while the hub has a subscriber on it and reads nothing while it has none; every page subscribes with its other channels, so the reads run while a page is open, the first page after none starts a read at once, and a later page gets the newest read through the hub's replay. A read that fails keeps the last good rows under the failure's sentence from the text catalog (`processes.failed_*`); a read fails when `ps` cannot start, ends with a status, prints no line that reads, does not answer within ten seconds, prints more than 32 MB, fails while its output is read, or gives an empty table. The head line counts the projects in flight, the projects whose folder holds an oculus terminal's process or an agent, and the agents running: the `claude` and `codex` programs of the whole table by the same matching rule, one per tree of the same program. Only an oculus terminal has Stop; it ends the terminal's tmux session after a question naming the terminal and its pane process, and every process in the terminal ends with it.

**Calendar.** One poller reads the reader's own Google and Microsoft calendars and any calendar published as a link over the `calendar` channel, read-only and never writing to a provider. An account is a row of `calendars:` in `config/local.yml`, one `provider` and one `label`, added from the Calendar's Add account and taken away by its row's Remove, both read again at once by the routes and the poller; its `refresh_token` is one file per account under `calendar_dir` (`~/.oculus/calendar` by default), mode 0600, which the connector writes, and the client half is the provider's own file under `~/.oculus/connect/`, saved once from the Account setup view for every account of that provider (an account file that names a `client_id` of its own still wins). The connect flow is the authorization code with PKCE and the server's own loopback callback as its redirect: the Connect control asks the server to open the provider's consent page, the provider sends the browser to `/api/calendar/callback`, and that route, the one route the write token does not gate, is guarded by the `state` the process minted ten minutes earlier and takes once. The poll exchanges the refresh token for an access token it holds in memory for the length of that account's read, reads the calendars and the events of the window `calendar.days_back` to `calendar.days_ahead` in `behavior.yml`, and publishes one complete state; a provider that refuses puts its own account in the error state with the status and the provider's error code, keeps that account's last good events under the state word, and shortens the next attempt to two minutes. A published link is a third provider, `ics`, for calendars alone: its row is `- { provider: ics, label: <label> }`, the link is the one field `url` of its own file `<calendar_dir>/ics-<label>.json` (mode 0600, written by the Add, deleted by the Remove), it signs in nowhere, and each poll reads the link from that file, fetches it (`webcal://` as `https://`) and parses it with `ical.js`, the file's own `VTIMEZONE` blocks naming its zones and repeating events expanded over the window, `EXDATE` honoured; a failed read is the account's error with a fixed hint naming its label. Every request of a round, a token refresh, a provider's read and a published link's fetch, is given `READ_TIMEOUT_MS` (30 s) by `timedFetcher` in `server/accounts/connect/oauth.ts`, its body included; one cut off is that account's error in the catalog's `accounts.timed_out` sentence, and the round goes on to the next account. The view draws the payload with `@event-calendar/core` as a day, a week, a month or a list, the chosen view kept in the instance's state and paging held inside the window. The options it hands the library are `calendarOptions` in `state/life/calendar.ts`, the view adding only its callbacks; the library's box fills the pane and its time grid scrolls inside itself, its cell and grid backgrounds are transparent so the pane's surface or the wallpaper shows, and each event's tooltip is its title, its time range or all day, its calendar, its location and its tentative mark, joined by ` | `. No token, secret, published link or event body is ever logged, published or answered.

**Mail.** One poller reads the reader's own Gmail and Outlook mailboxes over the `inbox` channel and publishes one complete state: the plate, the account rows and the triage notes. An account is a row of `mail:` in `config/local.yml`, one `provider` and one `label`, added and removed from the Inbox as a calendar account is from the Calendar, with its own token file under `mail_dir` (`~/.oculus/mail` by default), the provider's client half shared with the calendar accounts through `~/.oculus/connect/`, and its own consent asking for the mail scopes alone (`gmail.modify gmail.send`; `Mail.ReadWrite Mail.Send offline_access`), so a calendar token never gains the right to send and a mail token never gains the calendar. The connect flow, the credential file and the one authenticated call are the calendar's, shared under `server/accounts/connect/` and selected by the kind. So is the read timeout: a provider that does not answer within `READ_TIMEOUT_MS` is that account's error in the `accounts.timed_out` sentence, and the round goes on. The plate is three signals, unread, the `todo` label and unlabeled, each capped at `mail.per_signal`, unioned and deduplicated by thread; the unlabeled signal drops a thread of more than one message and one whose subject says it is a reply or a forward, and every signal drops a thread whose newest message is the reader's own or is in the trash. What the payload carries of a message is the provider's own snippet, never a body, and the address a reply would reach: the newest message's `Reply-To` where it has one and its sender otherwise, which the confirmation names and the send uses. Graph is never asked who the reader is, since the user resource sits behind a permission the mail consent does not ask for: the sent-items and deleted-items well-known folders decide the two whole-plate drops. Every Graph listing is asked newest first, and a listing that carries a `$filter` names `receivedDateTime` first in it over the whole of time, since Graph refuses a sort whose property is not first in the filter; the unlabeled signal has no filter and follows its pages until it holds `per_signal` uncategorised messages or four pages have been read. What each thread wants, the line about it and the drafted answer are the triage notes, one object per thread id in `<mail_dir>/triage.json`, written by the page and by the `/research-cockpit inbox` skill and polled every 500 ms so a write from outside republishes; a note whose thread has left the plate is kept thirty days. `POST /api/mail` is refresh, connect, add, remove, triage, reply and archive: a reply is sent on the thread through the provider and an archive takes the thread off the inbox, each only after a confirmation on the page naming the recipient and the account, and neither ever creates a draft at the provider. The page never sends a provider's id: every action names a configured account or a thread of the state last published.

**PTY.** Sessions run inside tmux, one session `oculus-<id>` each, so they outlive the server. The server holds one tmux control-mode client per attached terminal and bridges it over the `pty:<id>` channel; the page renders it with xterm.js. A session started elsewhere is observed (transcript only) until the reader explicitly resumes it into tmux with `claude --resume <id>`; nothing migrates on its own. The server sends no signal to any registry pid other than the liveness probe.

**The change log.** Every write that changed something is recorded: what file, what field, the value the file held and the value written, and when. The record is made by the writer, at the one point it holds both values, and is appended as one JSON line to `~/.oculus/changes.jsonl` behind the process's write chain; `changes.keep` in `behavior.yml` is how many lines are kept. It is a machine-local file and not a file of the hub, since git already holds the hub's history and what this answers is what oculus did here. `GET /api/changes` reads it newest first, and `POST /api/write` takes one back with the kind `undo`, addressed by the change's own time: the file is checked to still hold what the write left, and the earlier value goes back through the writer the change came from, so an undo is an ordinary write and is recorded like one. A `config-value` write also records the text it replaced and the text it put in its place, with the offset where it starts (`replaced` on the record, from the common prefix and suffix of the file's text and the edited text); its undo puts that text back when the file still holds it at that offset and the key still holds the record's value, so the file returns byte for byte with its comments and column alignment, and a record without `replaced`, with a malformed one, or whose text no longer sits there goes back through the value write. A Search replace is one `files` record with the field `replace`, holding a stamp per file before and after, each stamp before naming the copy the history kept; its undo writes each file back from its copy only while every file is as the replace left it (`moved` otherwise), keeps a copy of each file as it is, and is recorded as a `replace` itself, so the redo is the same path. A write that removes a field keeps the removed text, where it stood and the text that followed it, so its undo puts the text back before that following text, as it was, whatever else changed in the file; when the following text is gone, whole lines go back at the nearest line start that gives the right values, and only when none does does the value come back as a new line, as for a change that carries no such text; text removed from inside a line (a flow map's key) goes back only at the place of its following text, and otherwise comes back through the value write. A write that rewrote a bare follow-up note or a list of one note as a map keeps the text it replaced, comments included, and its undo writes that text back over the lines the write left while the file still holds them, so the note returns in its own shape; any other undo of that field comes back through the value write.

A module the trace from the write route reaches is drawn, grouped by folder, when a path from it leads to the disk or to a call the trace cannot follow, or when a refusal calls it; a module that is none of these is left out with its arrows. A refusal is a dashed arrow labelled with its check, a function or value referred to without a call is a dotted arrow, an arrow into the disk is labelled with the node:fs call, and every other arrow's `<title>` names the functions it calls.

**Auth.** The server binds 127.0.0.1, and any page open in the browser can address localhost, so every request under `/api/` passes one origin rule before a route sees it: `sameOrigin(headers, host)` in `server/core/auth.ts`, applied by `handle` in `src/hooks.server.ts`, which refuses a failing request with 403 `{ error: 'forbidden' }`. `Sec-Fetch-Site` of `same-origin` or `none` is admitted; an `Origin` header is admitted when it names this machine or the request's own host and refused otherwise; no `Origin` with any other `Sec-Fetch-Site` is refused; a request carrying neither header is refused, since a browser without Fetch Metadata sends neither on a cross-site request. A second list beside the guard names the five paths that admit a request carrying neither header: `/api/hook`, which Claude Code's hook posts with `curl`, the picture routes `/api/memories`, `/api/wallpaper` and `/api/diagrams/[name]`, which the command line fetches as well as the page, and `/api/health`, which answers `{"app":"oculus"}` to the app's main process when a port is held, so it can tell an oculus from another program. A request to one of them that carries either header is judged by the rule like any other. The guard judges the route Kit matched rather than the raw path, so an encoded address reaches no route unguarded. The two OAuth callbacks, `/api/calendar/callback` and `/api/mail/callback`, are passed unchecked, named in one list beside the guard, because the provider's redirect brings the browser there from another site; the `state` this process minted for the consent guards them. Writes additionally carry a token minted at server start and delivered to the page once, which is what holds back another page in the same browser and a client that sends a header it chose. The socket checks `allowedOrigin` on its upgrade, which does not pass through `handle`, and accepts nothing from the page except subscriptions and, later, terminal input.

**Untyped input.** In `server/core`, `server/root`, `server/machine`, `server/accounts`, `server/files`, `server/content`, `server/git`, `server/edit`, `server/sessions`, `server/transcripts`, `src/lib/data`, `state/`, `src/lib/views`, `src/lib/shell` and `src/routes`, a value that comes from outside the process or from outside the page's own code is checked with a zod schema that sits beside the reader, in the same file. What is read that way on the server: the socket's subscribe message and the terminal socket's frames, the hook's request body, the request bodies of the write endpoint and of the terminal, git, deposit, file-browser write, file operations (`/api/ops`, through a module-level shape of `server/files/fs/ops.ts` that is held to `OpsRequest` with `satisfies`), source, open, account add, mail triage and memories upload routes, a line of the changes log and the values it records for an undo, the output of cloc, ripgrep and `gh`, the YAML and JSON files the writers parse, the records of a Claude transcript and of a Codex rollout, which the fold, the turns reader and the usage table read, the files of Claude, Codex and oculus (the fold cache, the overrides file, a Claude session registry file and the hooks of a settings file among them), the answers of the mail and calendar providers, the answers of the literature sources, and the configuration. A schema whose answer has a declared type is held to that type with `satisfies`. What a field of the wrong type does is written on its schema: it takes its default, it is read as absent, or it refuses the whole value; a cache entry with a field of the wrong type is dropped, and its transcript is folded from the start. A reader that hands its input on, to a file, to a writer or to the page, uses the schema only to accept or refuse and answers the input object itself, so the order of its keys and the keys the schema does not name stay as they are. A record that is read once per line of a transcript is first read through its schema without the repairs of its fields, and a record that fails that is read through the full schema, which gives the same answer; `quickly` of `data/shapes/shapes.ts` builds the pair; `data/shapes/shapes.ts` holds the shared schema helpers the server, the state layer, the views and the shell read through (`unchanged`, `unchangedAs`, `mapShape`, `mapOfShape`, `keysOfShape`, `valuesOfShape`, `anyNumberShape`, `wholeShape`, `stringItemsShape`, `optionalItemsShape`, `textOrNumberOnlyShape`, `survivorsShape`, `rowsShape`, `searchRevealShape`, `quickly`, `readAs`, `readOr`, `filledText`, `optionalText`, `textOrNumber`, `readJson` and `text`). In `src/lib/data` what is read that way: the hub's YAML files (a registry, a collection, a `project.yml`, a document's front matter, the career file, a feed file and the deck file) and the config's, the file whose top must be a map by the one reader `sources/yaml-file.ts`, the merged configuration by key, `local.yml` through `checkLocal` and `loadLocal`, an agents cache file, and the raw portfolio's entries that `snapshot/normalise.ts` and `snapshot/validate.ts` read; the modules of `data/helpers` read through zod directly, because `data/shapes` sits above them. In `state/` what is read that way: the socket's frames (`frameShape`) and the top-level fields of each channel's payload (`state/client/payloads.ts`, a payload that fails is dropped as a malformed frame is), the answers of the server's endpoints (a body that is JSON null or is not JSON is a failed read, never a map of the wrong shape, and an `error` that is not text is the status text; the page says a failed read in a catalog sentence, never in a status number alone: `failedAnswer` of `state/shared/answers/answers.ts` gives the sentence of the refusal word the server answered, and otherwise `ui.answer_refused` or `ui.answer_unreadable` with the status in parentheses; a refusal of the terminal route, a project command's actions included, is a word of `TERMINAL_REFUSALS` with the names its sentence is about (the command, the placeholder or the cycle that stops the run), said by `terminalSentence` of `state/shared/answers/terminal-words.ts`), the browser's storage (the appearance envelope, the saved arrangement and the form drafts), the state a tab keeps in the saved arrangement, the merged configuration by key, and the fields of an entry. In `src/lib/views`, `src/lib/shell` and `src/routes` what is read that way: a tab's instance state through the readers of `state/workbench/layout/instance.ts` (a view that writes its tab's state back with a key added spreads `instanceMap` of it, which answers the state itself, so the other keys stay), the bodies of the answers a view fetches through `state/sources/repositories/answers.ts`, the merged configuration by key, and an entry's fields. A list a store hands on to a view is read item by item, answered as the input itself when every item passes and as a new list of the items that pass otherwise. A map built from an outside map's keys skips an own `__proto__` key. The text of a schema's error is never shown or logged. A request body read through `gatedBody` of `core/auth.ts` is narrowed to a map by `isMap`; a route that builds a typed value from its fields reads them through a schema, and a field compared with a word, or handed to a check that answers its own refusal, is read as it came.

**Processes.** A process oculus starts from text the reader did not write into oculus's own configuration (a command in a repository's `.oculus/commands.yml`, a debug launch, an agent seeded with a task) runs only after the reader has approved that exact text on this machine, the approval kept under `~/.oculus/` and keyed by the text, so a changed text asks again; it runs in a pane the reader can see, never in the background; and oculus stops only processes it started itself, behind a confirmation naming the process. A process oculus did not start is shown, never signalled. A project command is such a process when it comes from a file of the repository (`.oculus/commands.yml`) or is found in one (CMake presets, the scripts of `package.json`, the targets of the top Makefile); the commands saved through the form are kept in `~/.oculus/commands.json`, keyed by the repository's absolute path, and are text the reader wrote into oculus, so they run without the question. The approval of a command is an entry `command:<sha256 hex>` in the approvals file (the `approvals` key of `local.yml`, default `~/.oculus/approvals.json`, the file the Approval paragraph below describes), over the whole chain of the command as it is written, before any placeholder is replaced, together with the repository's real path: a JSON text holding the path and, for each command the chain runs in run order, the pair `[cwd relative to the repository, run]` (`chainText` of `server/machine/approvals/approvals.ts`; JSON, so a tab or a line break inside a line cannot read as the boundary between two). The chain is one entry, so a changed line, a changed folder, a changed `depends_on` or the same text in another repository asks again, and the question lists every line of the chain. A command runs as a task terminal, which stays listed after its line ends so that its result shows and Rerun can run the same line again; Restart stops a running line behind a confirmation naming its process (`server/machine/commands/` and `server/machine/approvals/`). A placeholder's value (`${file}`, `${selectedText}` and the others) is never written into the line: the placeholder becomes `${OCULUS_ARG_<n>+"$OCULUS_ARG_<n>"}`, a form quoted both outside and inside the line's own double quotes, and the value is set in the task terminal's environment with tmux's `new-session -e`, so the shell reads it as data, whole, in every context the line writes it in except a line that evaluates text itself (`eval`, `sh -c`, `$((...))` in bash), and the approved text is the text that runs (`fillPlaceholders` of `server/machine/commands/placeholders.ts`).

### Client state

Svelte 5 state modules (`.svelte.ts`). `entities` holds the latest payload per channel. `selectors` computes the joins (`projects` with venue, funding, datasets; `sessionsByProject`; `workspaces`). `layout` holds the tree below. `ui` holds theme and per-view-instance state such as selection and filters. `layout` and `ui` persist to `localStorage`, each under its own versioned key. The browser tabs of one server share what the arrangement is made of: the saved pages and each view instance's own state. A tab that saves fires the `storage` event in the others (`followKey` of `state/shared/stores/storage-events.ts`), and each takes the saved pages at once (`takeSaved` of `state/workbench/layout.svelte.ts`) while it keeps showing the page it was showing, and takes the saved instance records (`takeSavedInstances` of `state/workbench/ui.svelte.ts`) while the appearance stays its own; neither writes back. The ui store's `save` reads the saved records first and writes them with the records this tab changed laid over them and the ones it removed taken out (`mergedInstances`), so a save never drops a record another tab saved. Two tabs that change the same record, or the pages, at the same moment still end with the last write. Views read selectors and write `ui`; they never touch `entities` directly.

## Layer 3, view

**Primitives** (`ui/`): `Card`, `Chip`, `Meter`, `Table`, `Pane`, `Tabs`, `Sash`, `Empty`, `Toolbar`. A `Pane` is a 22 px header holding the view's title and its icon actions only, and a `bar` under the header for the view's other controls: a search box, a select, a segment, a toggle or chip, a text button, a status line. The header's `Toolbar` asks for `overflow`: its controls stay on one line, each an icon action in a 20 px box (`--header-action`) with a 16 px icon, and the controls the line has no room for are out of the tab order and held in a popover that the `more` button at the line's end opens, which moves the focus to the first control in it and gives it back to the button on Escape. `ui/frame/toolbar/` holds the `Toolbar` and the pure `fit.ts` that counts how many controls fit. The bar wraps and does not scroll with the body. `Empty` is the centred empty state, and with `error` a boxed message drawn as text, the view's retry as its `action`. Props are values and callbacks; a `Chip` takes a label and a tone. Nothing here imports state or knows what a project is.

**Shell** (`shell/`): the workbench. An activity rail on the left, drawn as VS Code's activity bar, whose icons switch pages and carry one badge each, the first count their page holds, and a status bar along the foot under both, drawn as VS Code's (see the status bar decision below); one tree of panes with tabs, split any way and any depth; sashes between the children of every split, and one control on each child that collapses it to the split's edge and shows it again. The shell renders the layout tree and mounts the view of every tab a pane has shown, the active one drawn and the rest hidden (`shell/panes/TabView.svelte`), until the tab closes or leaves the pane; a tab never shown mounts nothing, and there is no cap. A view kept hidden draws at no size; `onShown` in `ui/shown.ts` tells a view when it comes back to a size, and then the Map measures its labels again and a confirm takes the keyboard again. It does not import any view by name; views register themselves in a registry keyed by `ViewId`.

**Views** (`views/`): one folder per view, `views/<group>/<name>/`, holding its component and its partials; a group's folder that is full holds a subfolder of views, as `views/system/workbench/` and `views/system/machine/` do. A view reads selectors, composes primitives, writes its own instance state. It does not know where in the tree it sits, and it has no internal multi-pane layout. Sessions is therefore six views, arranged by a saved default layout, not one view with three panes inside.

## Layout as data

```ts
type ViewId   = 'focus' | 'projects' | 'archive' | 'venues' | ... | 'session-list' | 'terminal' | 'timeline' | 'changes' | 'agents' | 'customization'
type Instance = { id: string; view: ViewId; state: unknown; preview?: true }
type Layout =
  | { kind: 'split'; dir: 'row' | 'col'; sizes: number[]; children: Layout[]; folded?: number[] }
  | { kind: 'pane';  tabs: Instance[]; active: string }
  | { kind: 'page';  page: string }
type Workbench = { root: Layout; focus?: { path: number[] } }
```

A page is one tree. The shell renders it; a sash drag edits `sizes`; opening a view appends an `Instance` to the pane `open/opening.ts` picks, which for a view opened for something is the pane `open/landing.ts` picks; a drop moves an `Instance` between panes; `preview` marks the one tab of a pane that the next preview open is pointed at instead of a second tab being appended, and it goes when the reader keeps the tab; `focus` is the one pane shown alone while the rest is put away. `folded` holds the indexes of a split's children collapsed to its edge: a folded child keeps its share in `sizes`, so expanding gives back the width it had, and one child of a split is always left open. The saved arrangement is the serialised tree, and what a view keeps lives in each tab's own state; a field a saved page carries beyond its id, name, tree and rail key is dropped when it is read. Two instances of the same view have separate state by construction.

Beside the pages the layout holds floats. A float is a workbench of one pane, addressed by its id wherever a page id is taken, so opening, closing, moving and activating a tab in it go through the operations a page's pane uses; it is never a page, so the rail, the Pages view and the page lists of the pane menu never list it. It is free, `{ x, y, w, h }` in fractions of the window, or docked, `{ dock: left | right | bottom, size }` with `size` the fraction of the window's width (its height for `bottom`) from 0.1 to 0.6, or a window of the app, `{ kind: 'window', x, y, w, h }` in screen points of the window's content area, at least 200 by 200, which the main window does not draw and the app opens as a window of its own; one float is docked to an edge, and docking a second merges its tabs into the first. `shell/panes/floats/FloatLayer.svelte` draws every float once, outside the block keyed by the page, so a switch of page never mounts a float's views again and a maximised pane of the page leaves the floats drawn. A docked float is a strip in the grid of the workbench body with a sash on its inner edge; a free float is placed by its fractions of the window (`position: fixed` in viewport units), so it scales with the window, never leaves it and may lie over the rail and the status bar, and it is drawn above the panes with the border `--float-border`, moves by the empty part of its tab strip and resizes by its edges and corners on `interactjs`, and docks when it is released within 24 px of the area's left, right or bottom edge. A float is removed when its last tab goes, and a split inside it is refused. The pure operations are `layout/open/float/pages.ts`: `floatPane`, `floatTab`, `dockFloat`, `freeFloat`, `returnFloat` (its tabs go back into the page on screen as a new pane split off the right of the page's largest pane), `placeFloat` and `adoptFloats`; the store's operations over them are `layout/open/float/store.ts`, which adds `windowPane`, `windowTab`, `windowFloat` and `copyTabToWindow` for the window place.

A pane keeps itself when its last tab goes and that tab was a view opened for something or a Terminal tab: it stays, empty, and an empty terminals pane carries `keeps: 'terminals'` in the saved tree while an empty documents pane carries nothing. A page holds never more than one empty unlocked pane, whatever its kind, so a pane emptied while another empty pane is on the page closes as a pane always did, and `closePane` removes a kept one. The store hands the rule to the tree functions as a `KeepRule` (`layout/tree.ts`), so it holds whatever takes the last tab out: a close, a drag out, a move to another page, an edge drop, a record deleted, a view leaving the registry. A float is never kept empty.

A page leaf shows another page at that spot, by id, and it is a leaf as a pane is: it folds, it takes a neighbour when a tab is dropped on its edge, and it holds no tab of its own. Three rules govern it. It is the same page and never a copy, so a tab opened in it is open everywhere that page shows and the page is reached by the leaf's own panes rather than by a second tree. A page never shows itself, directly or through another page, so a leaf that would close a loop is refused and never offered. A page is drawn at most once on a screen, directly or through a page the screen already draws, so nothing is drawn twice and no view is mounted twice.

## Theming

`tokens.css` and `themes.css` hold the colours ported from the cockpit, a type scale and radii set on VS Code's measures, and fifteen theme blocks that override tokens and nothing else. The type scale is seven steps, `--fs-xs` 11 px, `--fs-sm` 12, `--fs-md` 13, `--fs-lg` 14, `--fs-xl` 16, `--fs-2xl` 20 and `--fs-3xl` 26, each times `--text-scale`, and a terminal palette sets them one step down (10, 11, 12, 13, 14, 16 and 20 px). A text takes its step by its role: the main words of a row, a paragraph or a card `--fs-md`, secondary words (a detail, a date, a caption, a control's words) `--fs-sm`, a label, a badge or an uppercase heading `--fs-xs`, a page or document title `--fs-xl` and above. Every focus ring is `1px solid var(--accent)` at an offset of -1 px, or 1 px for plain words with no box, and a link has no underline at rest. VS Code Dark Modern and Light Modern are two more blocks, authored for oculus rather than ported, which is why a contrast failure in one of them is fixed in the block and a failure in a ported one is a finding about the port. The contrast test walks every text-on-background pair the primitives declare, under every theme, and fails below 4.5:1. `derive.ts` also derives, for every theme, `--accent-bg`, a fifth of the accent in the page's colour, which a selected tree row fills with; `--scroll-track`, the panel; and `--scroll-thumb`, halfway between `--muted` and `--line` and moved in lightness until it clears 3:1 on the track, which the contrast test also measures. For every hue it also derives `--c-<hue>-lane`, half the hue and half the panel, which the header of a Focus lane and of the Funding, Jobs and Teaching columns fills with (`views/boards/focus/lanes/LaneHead.svelte`), and `--c-<hue>-lane-txt`, the hue's text colour made readable on that surface first, which the header's name and count are drawn in, so no other hue text changes. The contrast test measures `--c-<hue>-lane-txt` on its own `--c-<hue>-lane` and on nothing else. The contrast test also reads src/ for a lane text token used outside the header's shape. `tokens.css` gives those four the default theme's derived values on `:root`, so the first paint draws them ahead of any theme being applied, and one rule in the page root draws every scrolling box's thin bar in the two scrollbar tokens. Primitives use tokens only; a raw hex in a component is a test failure.

The wallpaper is one image behind everything, served by `api/wallpaper` from a directory `appearance.yml` names under the hub and nothing outside it. It is on where a theme's class carries `rice`, or under every theme where the config says `all`; the body then carries `wall`, and each component that paints a surface declares under that class what its surface does. The shell's pane box and the box a view fills both paint nothing (the shell's keeps its border), and a view that draws its text straight into its box asks the box for the translucent surface instead, so no text is read off the picture with nothing between. Everything the box holds that paints a surface of its own keeps `panel_opacity` of its colour with `panel_blur` of backdrop blur behind it, and so does the rail and the tab strip: one translucent layer over the picture and never two, since two such layers read as one nearly solid one. A strip that stays in place over rows scrolling in the same box keeps a mix of its own over the box's tint: the Calendar's header row, which holds the weekday headings and the all-day row, and the list view's date headings keep `popover_opacity` of the panel's colour, since at `panel_opacity` the rows passing under them still show, and a table's sticky header row in `ui/display/Table.svelte` keeps `panel_opacity`. A surface inside one of those paints nothing in turn, the current tab inside the strip included, and so do the code spans and code blocks of prose drawn on one, since a blur behind a span that wraps covers the prose between its halves. A floating surface keeps `popover_opacity`, which is higher because it is read through a pane as well as through the picture: the menus, the palette, the update tray, the key sheet, the confirm box and the tooltip. The small controls stay solid, being what text is read off: the buttons, the chips, the inputs, the meter, the disclosure, the ticker, a menu's items, a table's rows and every hover response. The colour is still the token the contrast test measured. The wallpaper toggle in the Settings view starts on whatever the theme answers and holds a value of its own only once pressed, so saving any other appearance value leaves it alone. A blurred surface is the containing block and the stacking context of every fixed thing inside it, so a pane's tab strip carries depth 1 over its pane body and stays under the drag layer at 10. A tooltip's bubble, a menu's list, the status bar's notification centre, toasts and confirm are drawn on the document body through bits-ui's `Portal` rather than inside the surface their control sits on. The modal boxes, the confirm, the prompt, the key sheet, the palette and the update tray, stand on `ui/frame/Modal.svelte`, on bits-ui's Dialog: the focus moves into the box, Tab stays inside it, Escape and a press on the ground close it, and once the dialog is gone the focus goes back to the control that held it, where nothing holds it (`giveBackQuietly` in `ui/frame/quiet-focus.ts`), except that a tab chosen in the palette, by a result or by the `:tab` and `:goto` commands, takes the keyboard on its tab head, while an editor action leaves the keyboard in its editor. A dialog raised in a tab is drawn in place, so it stays in that tab, and holds nothing of the page while its tab is hidden.

The icon set is Lucide at one stroke weight, shipped as the `lucide-static` package, and `icons.yml` maps every name of the glyph vocabulary to one of its icons; the server reads the drawing of each mapped icon once per config load and pushes it with the rest of the configuration, `ui/display/Glyph.svelte` draws it inline through the icon filter of `ui/html.ts`, and a drawing takes the colour of the text beside it. It is drawn at 16 px times the text scale whatever the text beside it is (`--icon-box`; the activity rail's 24 px and the status bar's 14 px are set as `--glyph-size` on those two surfaces). The capsule belongs to a status word, the project type, a filter toggle and the badge of a view in the Views catalogue: `ui/controls/Chip.svelte` is VS Code's count badge (18 px minimum, 11 px words, an 11 px radius), draws a status word and the project type in the tone of their status or type and the catalogue badge in the hue its view registration names, and given an `onclick` is a toggle with `aria-pressed`, toned or untoned (the Joint-work and disclosure pills are untoned), drawn filled in its tone while pressed. Everything else a surface lists, a dataset, a person, a pillar, a deadline, a count, is `ui/controls/Tag.svelte`, the same glyph and words with no capsule. A tag that stands for a state keeps that state's hue as the colour of its words and of its mark, which a line icon takes through `currentColor`; a tag that stands for a name or a count carries none and is muted.

The glyph vocabulary is `glyphs.yml`'s one `glyphs:` map, each name with the ASCII stand-in a terminal theme draws in place of its icon: one to three printable ASCII characters, which `iconFindings` reports a value for not being and the three-character box of `ui/display/Glyph.svelte` fits. A terminal theme draws the stand-ins unless the viewer turns Icons on (the ui store's `icons`; a browser that saved the older `unicode` field has it read once and written back as `icons`), and there no icon is drawn at all. The swap is a lookup where a glyph renders, in `ui/display/Glyph.svelte` and in `ui/controls/Chip.svelte`'s bracket rule, and never a pass over the document. No string under `config/` carries a glyph: a text that shows one draws a `Glyph` beside its words, with any separator drawn by the markup and hidden from a screen reader; a mark badge's hover says what the mark means in the words its registration's `badgeMark` names, or the view's name where it names none; the Venues deadline line is SVG bars in the text colour; a check or cross that opens a venue's `wos:` or `scopus:` in `registries/venues.yml` is read as a yes or a no by `data/snapshot/indexing.ts` and drawn as the `check` or `cross` glyph. A theme row's `glyph:` that is missing, empty or not a glyph name, and a row repeating a theme's name, are findings of `data/sources/config/themes.ts`; the picker draws such a row with its words alone and offers a repeated name once. Glyph and icon names are read as own keys, so an inherited name such as `constructor` is no name. In the icon mode a name with no drawing is an empty 16 px box, never text. KaTeX, the terminal and Markdown drawn from hub files carry their own content.

## Hot reload

Three kinds of change, three mechanisms, no restart in any of them.

| Change | Mechanism |
|---|---|
| a component, a selector, a primitive | Vite swaps the module in the open page; state survives |
| a server module or an endpoint | Kit's dev server reloads it; the socket reconnects, and after a reconnect the page takes the first message of every channel whatever its version, since a restarted server numbers its channels from the start again |
| a YAML file in the hub or in `config/` | the watcher rebuilds and pushes; identical in production |

A route reads the configuration through `locals.config()`, which reads `config/` from disk at most once a request and only when asked, and a server module takes it from its route as an argument rather than reading it itself, so an edit to `config/` reaches every route on the next request, in production too. The one server module that takes the configuration from the `config` channel instead is `server/root/live-settings.ts`, which has no route.

The pollers are built from the configuration read when the server starts, and every config push hands them the settings read again through `server/root/live-settings.ts`, each group by its own reader: the Live HPC settings, the calendar settings, the mail settings, the usage refresh and the usage tiers, with the three sentences the pollers write on a row. A value that its catalog entry refuses (its `control`, `min`, `max` or values in `config/catalogs/options.yml`) hands the poller that setting's `default` and is a finding naming the key, at start and on every push; a push whose merge dropped `behavior.yml`, and a group whose key the catalog holds no entry for, keep the settings in force and are logged once. A portfolio rebuild also hands the Live HPC poller its host, because the cluster entry `slurm.resource` names can change while the server runs; the portfolio watcher calls the `built` option of its `WatchOptions` once per rebuild, after the portfolio, the audit and the feeds are published.

`local.yml` is read again whenever it changes, by the one watch on it (`server/root/watch/local.ts`), and every key holds at once: the context's `local` takes the new values in place, so a route that reads `locals.server.local` follows with its next request, and each object built from a changed key is closed and built again (a changed `hub` the portfolio, git and auto fetch watchers and the usage refresh; `accounts`, `sessions_cache` and `sessions_overrides` the sessions watcher and the usage refresh and watcher; `workspaces` the git watcher and the auto fetch; `bookmarks` the bookmarks watcher; `claude_bin` the usage refresh and the usage watcher; `open_bin` the opener; `hpc_host` the Live HPC poller; the calendar and mail keys their pollers). A changed `port` moves the server of the same context to the new port, so the hub, the terminals and the token stay. The server stops listening, ends idle connections at once, lets a request in flight finish for up to five seconds and then ends what remains, so a request that itself changed the port is answered; the WebSocket connections stay open, and only once the server listens on the new port is the new address published, in the `host` the `config` payload already carries. The page that was open follows when its own port is the port of the address it holds and the new address answers it: it goes to its own address on the new port, with its path, query, hash and host name. A page reached through a forwarded port of another number, and one forwarded under the same number, whose machine serves nothing at the new port, stays where it is. The browser keeps `localStorage` per origin, so the page writes the arrangement and the settings of this browser into `window.name` just before it goes, marked with the origin it goes to and the time, and the page at the new address writes them back and clears the name when both match, within a minute (`state/workbench/layout/saved/carry.ts`), so the workbench comes back as it was; a port in use, 8787 or a number outside 1 to 65535 keeps the server where it is and is logged, and a listen that fails on the new port and on the old one logs both reasons and ends the process with status 1. A value that a watcher cannot be built from is logged with its key, stays at the value in force and leaves the other keys applied. A key whose value is wrong takes its default and is a finding naming `local.yml` and the key, a wrong row of `accounts`, `calendars` or `mail` is left out with its finding, and the other keys and rows are applied; a file that does not read keeps every value in force and says why once.

## Apps added while oculus runs

This section is a ruled and unbuilt proposal: nothing in it exists in the code, and once it is built the agreement rule at the head of this file applies to it like every other section.

An app is a folder of web files (a page and its scripts) that the reader puts in one of two places: a folder of this machine, or the `.oculus/apps/` folder of a root shown in the file browser. An app of the machine's folder is a machine app and an app of a root's folder is a root app. Views found at build time stay as they are; an app is a second kind of view, which oculus finds while it runs, lists in the view catalogue, and draws in a tab inside a sandboxed frame once the reader has approved it. It needs no build and no restart. A root app is written by whoever writes to its root, a `git pull` included, so it reaches less than a machine app, cannot be kept approved while it changes, and names only its own root; each paragraph below says what differs for the two kinds, and a rule that names neither kind holds for both.

**Where an app lives.** A machine app is a direct subfolder `<apps_dir>/<name>/` that holds a file `app.yml`. `apps_dir` in `config/local.yml` names the folder, `~/.oculus/apps` when absent, resolved at the call as `calendar_dir` and `mail_dir` are and read through `loadLocal` as `appsDir`. A root app is a direct subfolder `<root>/.oculus/apps/<name>/` that holds a file `app.yml`, for each root shown in the file browser, whether or not the root is a git repository. The roots shown in the file browser are the hub, the engine, the configured roots and the current workspace's saved roots, in that order, with `~/workspace` under the key `workspace` when no root beside the hub exists (`browserRoots`, `src/lib/server/files/roots.ts:25-36`, `workspaceRoots`, `src/lib/server/files/fs.ts:222-233`). The folder that holds apps, the machine's or a root's, is an apps folder, and the folder of one app is its app folder. The hub is a root like any other, so `<hub>/.oculus/apps/board/` is the root app `board` of the root `hub`. The root `engine` is oculus's own `config/` folder, which holds `local.yml`: it holds no apps and its `.oculus/apps/` is never read. Not an app: a file directly in an apps folder, a folder whose name starts with a dot, and a folder with no `app.yml`, which is ignored without a finding since nothing in it claims to be an app. An `app.yml` that does not parse or is not a map of keys is a finding (`findings.file.does_not_parse`, `findings.file.not_a_map`, keyed as the findings below are, with the folder's name in place of the app's) and the folder is not an app. In this section a real path is the path as the disk stores it, letter case included, as Node's `fs.realpathSync.native` gives it (`realpathSync` keeps the case the caller typed, `src/lib/server/core/paths.ts:31`), and every real-path check of the section compares that path; the real path of a file that does not exist is the real path of its deepest existing folder followed by the remaining segments, and a link that points at nothing is read by its target text. A folder that is itself a link is followed once and listed by its real path. A root's `.oculus/apps` that is itself a link is followed once in the same way and must resolve inside the root's real path: one resolving outside the root is `findings.apps.folder_outside` and none of its apps is offered. The apps folders are taken in one order, the machine's first and then each root's in the order the file browser shows the roots, and an apps folder or an app folder whose real path a folder taken before it already holds is `findings.apps.repeated`: one real folder reached through two roots (a link, or two root keys naming one folder) belongs to the root that comes first, and a folder that is both `apps_dir` and a root's `.oculus/apps/` holds machine apps and gives that root the finding. Inside an app's folder a symbolic link is not part of the app: it is neither hashed nor served, and a dot-named file or folder is not part of it either.

**How an app is named.** A machine app's view id is `app:<name>` and a root app's is `app:<root key>/<name>`, where `<root key>` is the key the file browser gives the root. `name` matches `^[a-z][a-z0-9-]{0,39}$`, which holds neither `/` nor `@`, so the text after the last `/` of a view id is always the name, and a root key that holds `/` or a space still parses. Two roots can each hold an app of one name, and a machine app can share its name with a root app: a folder `notes` in the machine's folder, in `cathedra` and in `ordo` gives `app:notes`, `app:cathedra/notes` and `app:ordo/notes`, three finding keys (`apps[notes]`, `apps[cathedra/notes]`, `apps[ordo/notes]`) and three approvals. The view id names an app wherever a bare name would: the header `x-oculus-app`, the change record, the store the server finds for a write, the approval, and the finding key `apps[<view id without app:>]`, made with the folder's name when the manifest's name is not valid. A finding about a root's whole apps folder is keyed `apps[<root key>/]`. The address of a machine app is `/apps/<name>/<key>/<path>` and of a root app `/apps/@<root key>/<name>/<key>/<path>`, where `<key>` is the app's address key (the field `key` of its row). `@` starts the second segment of a root app's address and no name starts with it, and the shared files' segment `-` (below) equals neither an `@` segment nor a name, so the three forms never meet. A root key that holds a character an address cannot carry, such as a space or `/`, is percent-encoded in the address (`my repo` as `my%20repo`, so `app:my repo/todo` is `/apps/@my%20repo/todo/<key>/index.html`) and compared decoded; the view id carries the key as it is, and the header `x-oculus-app` carries the view id with the root key percent-encoded as the address does, since a header value cannot carry every character a root key can. Where an app's title is drawn (the view catalogue, a tab, the approval panel), a root app's title is followed by its root's key in parentheses, so three apps titled Notes read "Notes", "Notes (cathedra)" and "Notes (ordo)", and the approval panel gives the app's folder path.

**The manifest.** `app.yml` is one map of keys:

```yaml
name: notes
title: Reading notes
description: It lists the venues and files a note under an entry.
glyph: page
bridge: 1
entry: index.html
reads: [portfolio, files]
writes: [entry, new-idea]
connects: [https://api.example.org]
```

`name`, `title` and `bridge` are required. `name` matches the pattern above and equals the folder's name. `title` is 1 to 40 characters, trimmed, with no control character. `bridge` is `1`, the version of the bridge below. `description` is optional, up to 200 characters, and is shown at approval. `glyph` is optional, a name in `config/catalogs/glyphs.yml` other than `app`, the group heading's glyph, which no view of a group carries (`config/layout.yml:24`); an absent, unknown or reserved name draws the catalog's `apps.glyph`, whose value is the new glyph `app-view`, and an unknown or reserved one also gets `findings.apps.glyph_unknown` while the app is still offered. `entry` is optional, `index.html` when absent: a `/`-separated relative path whose segments are non-empty and do not start with a dot, ending in `.html`, and naming a file of the app. `reads` and `writes` are optional lists, empty when absent, of names from the open sets below, each name once; the channels open to a root app are fewer than those open to a machine app, and `app-store` is not a name `writes` can hold. `connects` is an optional list, empty when absent, of the outside origins the app may fetch from, for a machine app and a root app alike: `https://host` or `https://host:port`, with no user name, path, query or wildcard, each origin once, compared after a trailing slash is dropped. `http:` is accepted only for `localhost` and `127.0.0.1` on a port other than oculus's own, and a trailing slash alone (`https://api.example.org/`) is accepted and stored without it. A `wss:` origin is refused. A key this list does not name refuses the app (`findings.apps.key_unknown`), since a key of a later version that was silently ignored would leave the reader approving something other than what runs.

**What refuses an app.** Each of these is a sentence in `config/text/findings.yml` under `findings.apps`, shown in the Findings view keyed `apps[<view id without app:>]`, and each leaves the app not offered, not registered and not served: `name_empty` (absent or empty), `name_shape` (outside the pattern, which also covers every reserved form, since the shared address segment `-` below cannot match it and no name starts with `@`), `name_not_folder`, `key_missing`, `key_unknown`, `title_shape`, `description_shape`, `bridge_unknown`, `entry_shape`, `entry_missing`, `list_repeated` (a name twice in `reads` or `writes`, or an origin twice in `connects`), `channel_unknown` and `write_unknown` (a name in neither the open nor the closed set), `channel_closed` (a channel closed to every app, or, for a root app, `inbox`, `calendar`, `sessions` or `usage`; its sentence names the channel, says whether it is closed to every app or to a root app, and gives the reason, which is `findings.apps.carries.<channel>`, what the channel carries), `write_closed` (a name in the closed set, and `app-store`, which every app is granted for its own store and cannot ask for), `connect_shape` (an entry of `connects` that is not an origin of the form above: one with a user name, a path, a query or a wildcard, a scheme other than `https:` unless it is `http:` to `localhost` or `127.0.0.1`, `wss:` included, or an `http:` origin on oculus's own port) and `too_large` (more than `apps.max_files` files or `apps.max_mb` megabytes, 500 and 20). Two findings are about a whole apps folder, keyed `apps[<root key>/]`: `folder_outside` and `repeated` for a whole folder. Two folders of one apps folder whose manifests claim one name resolve by `name_not_folder`: the folder that carries the name is the app, the other is refused, and neither wins by order. A manifest that asks for a channel or a write oculus does not have, or for one of the closed sets below, is refused when the folder is read, before there is anything to approve.

**How oculus finds it while running.** One watcher module, `server/root/watch/apps.ts`, owns the `fs.watch` handles of the real path of `apps_dir` (recursive), of the real path of `.oculus/apps` in each root shown in the file browser except `engine` (recursive), of the real path of each app folder that is itself a link (recursive, so an edit in a linked folder is seen), of the folders that hold the stores of the apps it lists (`~/.oculus/app-data` and `<root>/.oculus/app-data`, each not recursive), and of `approvals.json` itself by its path, opened again after every event since a write by rename replaces the file; it never watches `~/.oculus` as a whole, whose other files change on every write. It follows the roots as the file browser gains and loses them: it reads `browserRoots` again on a `config` push and when the saved workspaces file changes, which it polls with `pollFile` as the git watcher does (`server/root/watch/git.ts:427`), so a root added in the page is read at the next tick and a root that leaves the file browser loses its handles. It debounces with lodash's `debounce` and a maximum wait as every watcher does, and rereads every app on a change: the manifest, the walk of the app's regular files (path, size, modification time and change time of each, recorded), the content hash, whether the approvals file holds it or the app is kept approved, and the store file's size and version (computed without parsing the file). It reads `local.yml` again when that changes, as accounts are, and follows a new `apps_dir`. When `apps_dir`, a root's `.oculus/apps` or the store folder of a listed app does not exist, one timer looks again at every such folder every two seconds and starts watching each when it appears; a missing folder is no finding, and a root with no `.oculus/apps` is looked at again as the machine's missing folder is. An absent `approvals.json`, which is the case until the first approval, is looked for the same way and means no app is approved; the approve route also tells the watcher after its own write, and the write route does the same after a store write. The server context holds the result as `rows`, `findings` and `folders`, and the watcher publishes `{ rows, findings, folders }` on a new channel `apps` when the result differs from the held one. A row is `{ name, root, title, description, glyph, folder, entry, reads, writes, connects, files, bytes, hash, approved, kept, key, storeBytes, storeVersion, storeFile }`: `root` is the root key, empty for a machine app; `folder` is the app's real folder path; `key` is the address key, empty unless the app is approved; `kept` says whether the app is kept approved; `storeBytes` is the size of the app's store file in bytes, 0 when the file is absent; `storeVersion` is the first 16 hex characters of the SHA-256 of the file's bytes, and the empty string when the file is absent; `storeFile` is the path the store is written to. A store path that is a folder or cannot be read counts as absent, with 0 and the empty string. A file over `apps.store_max_kb` is not hashed whole: its `storeVersion` is the first 16 hex characters of the SHA-256 of the text `<size>:<modification time in ms>`, so a hand-placed file over that limit costs the watcher one stat. An empty file is present, with `storeBytes` 0 and `storeVersion` `e3b0c44298fc1c14`, and its value is `null` since it does not parse. The row holds no store value, because a channel publish sends the whole payload to every subscriber (`src/lib/server/core/channels.ts:103-110`), so a value in the row would reach every page at each store write of any app; the page makes a fetch of the value (below). `folders` is the real path of every apps folder the watcher holds. The page always subscribes to `apps`, and the Findings view lists the channel's findings beside the others.

**The first frame.** The list rides with the page data as the collection keys do: `+page.server.ts` returns `apps: { rows, findings, folders, version }` read off `locals.server`, and `+page.svelte` calls `registerApps(client.registry, data.apps.rows)` in the same untracked block that calls `registerCollections`, with the `apps` entity seeded at that version so an older push replayed from before does not replace it. The rows carry no store value, so the first frame carries none, and a tab reads its store when it mounts, through `getStore()`. A saved layout that names `app:notes` or `app:cathedra/notes` on a machine that has the app therefore draws its tab on the first frame, never as an unknown view and never closed for a frame. Afterwards one effect calls `registerApps` for every push of the `apps` channel, and a second effect reads `data.apps`, as the token's effect reads `data.token` (`+page.svelte:72-74`), and registers and seeds again whenever a load hands new page data; the load runs again only through `invalidateAll` after a write met a 403 (`+page.server.ts:26-27`, `writes.svelte.ts:430-431`). After a server restart the socket reconnects and takes every push (`socket.svelte.ts:155-160`), so the `apps` push carries the keys of the new process.

**The view and the catalogue.** An app's view id is the one above. Built-in view ids and collection keys are bare words, so an app named `focus` or `funding` is `app:focus` and `app:funding` and meets neither. `registerApps` sits beside `registerCollections` in `routes/views.ts`, finds the module that exports `appRegistration` (`views/apps/frame/AppFrame.svelte`, the one component every app is drawn by) and registers one registration per row. `appRegistration` is a name no collection factory uses: `registerCollections` calls only a module whose export named `registration` is a function (`routes/views.ts:68-80`), and `AppFrame.svelte` exports no `registration`, so a config push runs `registerCollections` alone and neither calls the app factory nor unregisters an app, and the tabs of every real app are left as they are. The registration is:

```ts
{ id: row.root === '' ? `app:${row.name}` : `app:${row.root}/${row.name}`, label: 'apps.label', glyph: 'apps.glyph',
  words: row.root === '' ? row.title : `${row.title} (${row.root})`, glyphName: row.glyph,
  group: 'apps', order: index,
  badgeGlyph: () => (!row.approved ? 'lock' : row.kept ? 'edit' : ''),
  badgeMark: () => (row.kept ? 'apps.editing_mark' : 'apps.unapproved_mark') }
```

`Registration` gains two optional fields, `words` and `glyphName`, holding the title as drawn (the manifest's literal title, and for a root app the root's key after it) and the manifest's glyph name; `registrationLabel` and `registrationGlyph` return them when present and look the catalog key up when absent. A catalog key taking the title as its argument is not used, because those two functions look a key up with no arguments at every place a tab or the catalogue draws one, and each place would have to learn arguments. `badgeMark` (`state/workbench/navigation/registry.ts:102`), a catalog key in the tree, becomes a catalog key or a function of the badge client, as `badgeGlyph` is, so the hover words follow the mark: the lock mark says the app is not approved, and the mark drawn while an app is kept approved says it is kept. `apps` is a new id in `nav_groups` of `config/layout.yml`, with the label Apps, the new glyph `app` and no chord, so its views are reached by the direct-chord prefix and a digit. Every group is one rail page keyed by the page's arrangement key (`config/layout.yml:24`), so the group is also a `rail:` button `{ label: "Apps", glyph: app, page: apps }` and an arrangement `apps` of one empty pane (`view: []`), where a tab opened for an app lands. The rail button is always drawn; the catalogue draws the group only while it holds a view. `order` is the app's place in one list: the machine apps by name, then the apps of each root by name in the order the file browser shows the roots.

**When an app is added, changed or removed.** An added app is registered and appears in the catalogue. A changed app keeps its id and its tab; its hash differs, so its approval no longer holds, a root app changed by a `git pull` included, the frame is taken out of the tab and the approval panel (below) is drawn in its place with the sentence `apps.changed`, and the tab's state is kept; a machine app kept approved (below) is the exception. A removed app is dropped from the registry with a new `dropView(id)` that removes the registration and closes no tab, where `unregisterView` closes the tabs of a removed collection; the tab then draws as an unknown view (`ui.unknown_view`, "Unknown view: app:notes"), as a saved tab of a renamed view does, and draws the app again when the folder comes back. Tabs stay because a removed folder is as often an editor saving by replacing, a sync in progress or a rename as a decision, and closing would lose the tab's place and its state. The registry keeps a revision in `$state` that `registerView` and `dropView` advance and that `views` and `viewFor` read, so the catalogue, the palette and the tab bodies redraw for a registration made while the page runs. A saved layout naming an app's view on a machine without the app draws the same unknown view and loses nothing. The same holds for a root app whose root leaves the file browser: its tabs stay, draw the unknown view ("Unknown view: app:cathedra/notes") and keep their state, and the root added again draws the app again at once when its files are unchanged and asks when they changed. A root app's tab keeps in its saved state the real folder of the app it shows, beside its value (`{ value, folder }`), and draws the app only while the registered app of its view id has that folder. Root keys are per workspace, so after a workspace switch a key can name another folder; a tab whose key names another folder draws the unknown view, keeps its state, and never draws the other folder's app with the first app's value.

**How it is served.** The address is the one above, a route outside `/api/`, so `refused()` in `src/hooks.server.ts` does not judge it and it is not added to `UNGUARDED`: a frame with an opaque origin sends `Sec-Fetch-Site: cross-site` and an `Origin` of `null`, which `sameOrigin` refuses, so an address under `/api/` would refuse the frame its own files. Because the route is not guarded, any page in the browser can request it, and the answers carry `Access-Control-Allow-Origin: *` (the frame's module scripts and fetches are CORS requests from an opaque origin and need it), so what keeps another page from reading an app's files is `<key>`: the first 32 hex characters of HMAC-SHA256, keyed by a second secret minted at server start beside the write token and never sent to a page, over `<view id>:<hash>`, which names the root as well as the app. The address key is in a row only while the app is approved, changes with the app's files and with each server process, and gives access to that app's files alone. The shared files are at `/apps/-/penpal.js` (the installed `penpal` package's `dist/penpal.mjs`, the file the page imports) and `/apps/-/oculus.js` (the client half of the bridge, a file of the tree). These two are public and have a rule of their own: the method is GET or HEAD, the origin of the request's URL names this machine, and the path after `/apps/-/` is exactly `penpal.js` or `oculus.js`; they need no app, no key and no approval, and they are sent with the content type, `nosniff`, `no-cache` and `Access-Control-Allow-Origin` headers of an app file and without the policy below, which is a document's.

A request for an app's file is answered only when every one of these holds, and refused with an empty 404 that says nothing about the disk otherwise: the method is GET or HEAD; the origin of the request's URL, which Kit builds from the `Host` header, names this machine (`allowedOrigin` on that origin, `auth.ts:29-38`); the `Origin` header is not the input, since a module script or fetch from the opaque frame sends `Origin: null`, which `allowedOrigin` refuses, and a navigation sends none; the check on the `Host`-built origin is also what stops a rebound host name; a root part of the address, when there is one, decodes to the key of a root shown in the file browser other than `engine`; `<name>` matches the pattern and names an app of that root, or of the machine when there is no root part, in the held state that is approved or kept approved; `<key>` equals the app's current address key; the path has no segment that is empty, `.`, `..` or dot-led and holds no backslash or NUL after decoding; the path is a file of the app's recorded list; the file's size, modification time and change time (`ctime`, which `cp -p` and `rsync -t` cannot set) equal the record's, and when any of them differs the app is hashed again and the file is served only if the hash still equals the approved one (or, for an app kept approved, the manifest still equals the kept one), so a file edited after the last rebuild is refused until the watcher republishes; and the file's real path lies inside the app folder's real path, compared with a separator so a sibling folder with a longer name does not pass (`inside`, `server/core/paths.ts:15-19`). A request for `../../.ssh/id_ed25519` fails the segment rule, then the recorded list, then the real-path check. A link inside an app's folder is not in the list. The content type comes from a fixed table by extension (html, js, mjs, css, json, svg, png, jpg, gif, webp, woff2, txt, wasm) and is `application/octet-stream` otherwise, with `X-Content-Type-Options: nosniff` and `Cache-Control: no-cache`.

Every app file is sent with this policy, where `<origin>` is the origin of the request's URL from its `Host` header, checked as above, `<base>` is `<origin>` followed by the app's address up to and including its address key (`<origin>/apps/<name>/<key>/` for a machine app, `<origin>/apps/@<root key>/<name>/<key>/` for a root app, the root key percent-encoded), `<shared>` is `<origin>/apps/-/`, and `<connects>` is the manifest's `connects` origins, separated by spaces, and nothing when there are none:

```
Content-Security-Policy: sandbox allow-scripts allow-downloads; default-src 'none'; script-src <base> <shared>; style-src <base> 'unsafe-inline'; img-src <base> data:; font-src <base>; media-src <base>; connect-src <base> <connects>; base-uri 'none'; form-action 'none'; frame-ancestors <origin>
```

The `sandbox` directive makes the document opaque wherever it is opened: in the frame, by a direct visit to its address, or in a popup. The sources are named by address and never `'self'`, because whether `'self'` matches in an opaque document is not settled. There is no inline script, so an app loads its code with `<script type="module" src>`. `allow-downloads` lets an app save a file it built from what it read, an export. `allow-popups`, `allow-popups-to-escape-sandbox`, `allow-same-origin`, `allow-top-navigation`, `allow-forms`, `allow-modals` and `allow-pointer-lock` are never in the directive.

**The frame.** `AppFrame.svelte` draws `<iframe sandbox="allow-scripts allow-downloads" allow="" referrerpolicy="no-referrer">` with `src` set to the app's address for `entry`. `allow-same-origin` is left out on purpose: with it the frame would carry oculus's origin, would read `window.parent` and the write token, and would be admitted by `sameOrigin`. The page itself sends `Content-Security-Policy: frame-src 'self'`, added by `handle` to the page's answer, because a script inside a sandboxed frame can otherwise navigate its own frame to any address with the reader's data in the query; with the policy such a navigation is refused, and the two frames views already draw (`Document.svelte`, `File.svelte`) load from this origin. The policy also governs the Document view's frame (`Document.svelte:153-160`), where a link inside a manual that leaves for an outside site would stop loading in the frame. The Document view therefore opens such a link itself: it listens for a click on a link in its frame's document, which is same-origin and which it already reaches for the right-click (`Document.svelte:113`), and opens an address of another origin in a browser tab with `window.open(address, '_blank', 'noopener')`, as its own control for the page does (`Document.svelte:125`). While a sash or tab drag is in progress the frame draws with `pointer-events: none`, so the drag keeps its pointer moves. The frame element paints nothing and takes `color-scheme` from the body's computed value. A frame stays mounted while its tab is hidden, as every mounted view does. A tab moved into a floating pane, a popped-out window or the Electron window mounts a new frame element in the document that draws it, and the bridge below is made again for that element; the address, the sandbox and the policy do not depend on the window. The Electron window keeps Node integration off, subframes included.

**What an app may read.** The bridge is `penpal` 8.0.1. It is owned by one frame instance: made in an effect when the frame element mounts and destroyed by that effect's cleanup, never held at module level, so every remount makes a new one. The page's side is `new WindowMessenger({ remoteWindow: frame.contentWindow, allowedOrigins: ['*'] })` with `connect({ messenger, methods, timeout })`; `'*'` is required because the frame's origin is `null`, and the guard is penpal's check that a message's `source` is the frame's window, together with the manifest lists below. The app's side is loaded from `/apps/-/oculus.js`, which imports `/apps/-/penpal.js` and builds its messenger with `remoteWindow: window.parent` and `allowedOrigins: [new URL(import.meta.url).origin]`, the page's origin, because penpal's default is the frame's own origin, which is `null`. An app calls:

```js
import { connect } from '/apps/-/oculus.js';
const oculus = await connect({ onChannel: (name, version, payload) => draw(name, payload), onTheme: (theme) => paint(theme), onStore: (value) => redraw(value) });
const { payload } = await oculus.read('portfolio');
await oculus.write('entry', body);
await oculus.setStore({ seen: ['a', 'b'] });
await oculus.open({ view: 'venues' });
```

The page exposes `read(channel)`, `getTheme()`, `getState()`, `setState(value)`, `getStore()`, `setStore(value)`, `write(kind, body)`, `open(target)` and `key(init)`; the app exposes `onChannel(channel, version, payload)`, `onTheme(theme)` and `onStore(value)`. `read` answers `{ version, payload }`, the newest the page holds, for a channel in the manifest's `reads`; after that the page calls `onChannel` on every change of a declared channel, at most one call in flight per channel with a newer payload replacing a queued one, the payload being `$state.snapshot` of the entity, or for a root app of its root's part of it. A refusal rejects with one fixed word as a plain string, never an `Error` object: penpal sends a rejected `Error` with its name, message, stack and `penpalCode` (`dist/penpal.mjs:15-20`) and any other rejected value as it is (`dist/penpal.mjs:88-97`), so a string carries no stack or code of the page to the app. The words: `not_declared` (a channel not in `reads`), `closed`, `too_large`, `rate`, `declined` (the reader refused a confirmation), `missing` (an `open` target that is not there, or the store of an app removed or refused since the last push of `apps`), `refused:<reason>` (the server refused a store write, and the word the write route answers in `error` follows the colon) and `failed:<status>` (the write route answered an error, and the status follows the colon). The reader also sees `apps.refused_read`, `apps.refused_write` or `apps.refused_open` once per name and mount as a notice in the notice centre, naming the app.

Open to every app: `portfolio`, `feeds`, `hpc`, `audit` and `config`, each whole; they carry the hub's data, the job queue, the findings and the configuration, which includes this machine's host name and address (`ConfigPayload.host`, `data/model/index.ts:228`). Also open to every app, and whole for a machine app: `git`, which carries the state of the repositories (branches, status, commit subjects), and `files`, a notice that a served root or the bookmarks file changed and no file content. A root app gets the part of these two that belongs to its root, which the page builds from the payload it holds. `git` is `Record<string, GitState>` (`model-sessions.ts:544`), keyed by the folders that `repositoryRoots` gives, which are the roots' folders (`src/lib/server/files/roots.ts:45-49`): a root app gets a record holding the one entry keyed by its root's folder, `onChannel('git')` is called for it only when that entry changed, and a repository below the root's folder has no entry, unless its folder is itself a root shown in the file browser, whose entry belongs to that root. `files` is the notice `{ root, bookmarks? }` (`model-sessions.ts:555`, `watch/git.ts:207`, `watch/bookmarks.ts:66`) whose `root` is a root's folder: a root app is called only for a notice whose `root` is its root's folder, `read('files')` answers the newest such notice or null, and the bookmarks notice (`root: ''`) reaches machine apps only. `apps.read.files` and `apps.read.git` say what a machine app gets, and `apps.read_root.files` and `apps.read_root.git` say what a root app gets. Open to a machine app and refused for a root app (`findings.apps.channel_closed`): `inbox` and `calendar` (other people's mail subjects, senders and attendees), `sessions` (transcript-derived titles, prompts and paths) and `usage` (account labels and limits); `apps.read.<channel>` says plainly what each carries, and the approval panel of a machine app that declares one shows it. Closed to every app: `apps`, which carries every approved app's address key, and every `pty:<id>` (whatever a terminal printed, secrets included). A channel added to oculus is closed to apps until this section names it. The theme: `getTheme()` and `onTheme` carry `{ name, tokens, wall }`, where `name` is the theme's class on the body, `tokens` is every custom property `tokens.css` declares as the body's computed value, and `wall` is whether the body carries `wall`. The page reads them again one frame after the theme or the wallpaper setting changes, once the body carries the new class, as the editor and the terminal do, and calls `onTheme`; `oculus.js` writes the tokens on the frame document's root element and toggles a `wall` class there, so an app keys its surfaces on it as the built-in ones key on the body. With the wallpaper on the frame element paints nothing and a document the app leaves transparent shows the picture; the app's own surfaces are the app's to paint.

**What an app keeps.** Two JSON values. The tab's instance state, saved with the layout: `getState()` and `setState(value)` read and write one value, in the instance's state as `{ value }` (a root app's tab also keeps its folder, as above). `setState` rejects `too_large` above `apps.state_max_kb` (64) and rejects a value that is not JSON. Two tabs of one app keep separate values by construction, and a moved tab keeps its value. The app's store: one value for the app, shared by every tab of it in every window. `getStore()` answers the value, and `null` when the store file is absent, does not parse or is over `apps.store_max_kb` (256; a KB in this section is 1024 bytes); `setStore(value)` replaces it. A machine app's store is the file `~/.oculus/app-data/<name>.json` and a root app's is `<root>/.oculus/app-data/<name>.json`, created with its folder by the first write. It lies outside the app's folder, so writing it never changes the app's content hash or its approval. For a root app the store is a file of the root, tracked by git unless the root ignores `.oculus/app-data/`. `setStore` is a write of the new kind `app-store` (below): it rejects `too_large` above `apps.store_max_kb`, rejects a value that is not JSON, counts toward `apps.writes_per_min`, and rejects `refused:<reason>` when the file cannot be written, which is what a root that cannot be written gives. The server watches the store files, and a change to one, whoever made it (another tab, History's undo, a pull, a hand edit), reaches the page as a new `storeVersion` in the app's row on the `apps` channel (the page compares that alone), and the page then makes a fetch (below) and calls `onStore(value)` in every tab of the app in every window, the tab that wrote included. A write of a value equal to the one the file holds, as JSON values with object keys in any order, writes nothing, records nothing in History and answers success, so the file's bytes and `storeVersion` stay as they are whatever its formatting, and nothing reaches the page; a file that is absent, does not parse or is over `apps.store_max_kb` holds no value, so a write to it always goes ahead. A tab that mounts reads the value with `getStore()`. A fetch is `GET /api/app-store?view=<view id>`, the page's read of one app's store, and it answers `{ version, value }`: `value` is the parsed store, `null` when the file is absent, does not parse or is over `apps.store_max_kb`, and `version` is the file's `storeVersion` at the read. The route answers GET only (any other method answers 405) and writes nothing, so it is not one of the write routes counted below. It answers for any row the watcher holds, approved or not, since only the page calls it; a `view` that is absent, empty or given twice answers 400, and an id no held row names, a built-in view's id included, answers 404. The page sends the view id through `encodeURIComponent`, and the route compares the decoded value with the view ids of the held rows. The route is under `/api/`, so the origin rule and `refused()` apply to it, and the frame cannot call it, since its opaque origin fails `sameOrigin` as above; only the page calls it. The page holds, for each app it has fetched, the version and value of the last answer not dropped, and nothing for an app it has not fetched. `getStore()` answers from the held value; when the page holds none for that app it fetches once, two tabs asking at once sharing that one fetch. When a push of `apps` arrives, and when a frame of the app mounts, the page compares the row's `storeVersion` with the held version (nothing held differs); when they differ and a frame of the app is mounted, it fetches once per loaded oculus page, whatever the number of tabs, and a floating pane and a popped-out window drawn by the same page share that fetch. An app with no mounted frame is not fetched until a frame mounts. At most one fetch per app is in flight per page. When a fetch settles and the latest push that arrived after it began carries a version other than the one answered, the answer is dropped and the page fetches once more, at once while a frame of the app is mounted and otherwise when one mounts; a 404 answers no version, so it is dropped in the same way when that push holds a row of the app, and it is the app's absence below only when no push arrived after the fetch began or the latest one holds no row of the app; a push that arrived before the fetch began is not compared, and versions are compared for equality and never ordered. A dropped answer is not held and calls no `onStore`, and a `getStore()` waiting on the dropped fetch settles with the answer of the fetch that replaces it. The page holds the version a fetch answered, which can be newer than the pushed one, so a later push carrying that version fetches nothing. After a fetch whose answer is held the page calls `onStore(value)` in every tab of the app; a tab closed, a frame destroyed or a bridge not yet connected while the fetch is in flight gets no call, the answer is kept, and a frame mounted later gets it through `getStore()`. A 404 (the app removed or refused since the last push of `apps`) leaves the page holding nothing for the app and calls nothing, and a `getStore()` waiting on it rejects `missing`. Nothing else persists: an opaque origin has no cookies, `localStorage` or IndexedDB. An app can name no store but its own, because the page sends the app's view id in a header and the body carries only the value.

**How it writes.** Every write goes through the page. `write(kind, body)` is checked against the manifest's `writes`, and the page sends `POST /api/write` with the write token and the headers `x-oculus-app: <view id>` and `x-oculus-write-kind: <kind>`; the handler, having matched the body to one of its parsers, refuses with 403 `{ error: 'kind' }` and writes nothing when the branch it matched is not named by the header or is a closed kind, because the page cannot tell which parser will match and a body would otherwise satisfy a parser of a closed kind while declaring an open one. The change record carries the app's view id beside its kind, so the reader sees and undoes an app's writes in the change log like any other. Open kinds: `manifest`, `entry`, `subtask`, `subtask-add`, `host`, `new-entry`, `reorder`, `delete-entry`, `feed-field`, `feed-delete`, `lead-add`, `radar-add`, `linkedin-idea`, `linkedin-post` and `new-idea`, which edit the hub's data. The kind `app-store` is in neither set: every app is granted it for its own store. The four entry kinds (`entry`, `new-entry`, `reorder`, `delete-entry`) resolve the collection key `bookmarks` to the reader's bookmarks file under `~/.oculus`, outside the hub (`server/edit/writes/entries.ts:68`, `server/edit/writes.ts:89-90`), and a bookmark naming an `.html` file opens it in the Document view, whose frame carries oculus's origin (`views/shared/explorer/opening.ts:98-110`). The handler therefore refuses the collection key `bookmarks` with 403 `{ error: 'kind' }` for a write that carries `x-oculus-app`, so no app edits the reader's bookmarks. Closed: `undo`, which takes back any writer's change, `rail`, which rewrites `config/layout.yml`, `audit-mute`, which edits `config/behavior.yml`, `config-key`, which sets one option of a tracked config file in place, `config-value`, which sets one list or family of a tracked config file in place, keeping the file's other bytes (`server/edit/block-edit.ts`), `session`, which edits the machine's session overrides, and `deck`, which writes `config/present.yml`, an engine file (`server/edit/writes/config/deck.ts:1-4`). The other thirteen write routes (`calendar`, `connect`, `mail`, `memories`, `fs`, `open`, `source`, `deposit`, `git`, `hpc`, `usage/refresh`, `hook` and `terminal`) are closed to apps without exception: they run processes, write arbitrary files, reach a remote or act on an account, and the page never sends an app's request to any of them. `delete-entry`, `feed-delete`, `new-idea`, `linkedin-idea` and `linkedin-post` ask the reader first in a `Confirm` naming the app, the kind in words and the target as text, every time. Three of them are recorded with `undo: 'none'` and cannot be taken back, since `undoChange` answers `nothing` for such a record (`writes/undo.ts:188`): `new-idea` (`writes/manifest.ts:415`), `linkedin-idea` (`edit/feeds.ts:253`) and `linkedin-post` (`edit/feeds.ts:306`, which moves files). The other open kinds are recorded and undoable and send without asking. At most `apps.writes_per_min` (30) writes pass per frame per minute, `setStore` included, and the rest reject `rate`. The kind `app-store` is refused for a request that does not carry `x-oculus-app`, and a manifest that lists it in `writes` is refused `write_closed`, since the kind cannot be asked for. The body is `{ store: <value> }`, and the handler finds the store from the header's view id alone, writes nothing when the file already holds an equal value (above), and otherwise writes the file by rename, reads it back and refuses unless the read back equals the value sent. Its change record holds the file, the app's view id as `key`, the field `store`, and the sizes in bytes before and after as `before` and `after`. A store write's record is the one change record that holds sizes where every other holds the two values, and History draws the two sizes for it. The values before and after are kept beside the log in `~/.oculus/app-data/.undo/<time>.json`, named by the record's `at` and deleted when the record leaves the `changes.keep` window, so a 256 KB store does not put 512 KB in a line of `changes.jsonl`; the undo of a store write checks that the store file still holds the value after and puts the value before back through the store's writer, and a record whose file is gone answers `nothing`.

**Opening things in oculus.** `open(target)` asks the page to open a tab and resolves once it has; it needs no manifest entry. The target is one of `{ view: <view id> }`, `{ project: <key> }` and `{ file: { root, path } }`. `{ view }` opens a registered view with no state, and only a view that the view catalogue lists (`listed` is not `false`, `state/workbench/navigation/registry.ts:86-91`); `terminal`, `document`, `file`, `source`, `project` and every view that is not listed, which is every view that needs an argument, reject `closed`, and an id no registration holds rejects `missing`. `{ project }` opens the project's tab and rejects `missing` when the portfolio holds no project with that key. `{ file }` opens the file as source text in the source tab and never in the Document view. A root app may name only its own root in `file`, and any other root rejects `closed` for it, whether or not the file browser shows that root; a machine app may name any root shown in the file browser except `engine`, and a root the file browser does not show rejects `missing` for it. The key `engine` rejects `closed` for every app, since the root holds `local.yml`, the machine's private settings; keys compare exactly, so `Engine` is not `engine` and a configured root `game-engine` is an ordinary root. A file whose real path lies inside the real path of oculus's own `config/` folder rejects `closed` for every app, whichever root names it, so `hub` with `tools/oculus/config/local.yml` rejects `closed` as `engine` with `local.yml` does, and so does a root that `sources.yml` or a saved workspace gives another key for that folder. A file whose path under its root, given or real, starts with a folder that the list `closed_paths` names rejects `closed` for every app, since a root can hold a tracked credential folder that no dot marks; `closed_paths` is a key of the `apps:` block in `config/behavior.yml` (below), a list of folder paths each relative to a root and applied to every root, compared segment by segment and without regard to letter case, so `secrets/a.txt` and `SECRETS/a.txt` are closed alike, whether or not the root holds the folder, while `secrets-notes.md` and `a/secrets/b` are not. Its default, `closed_paths: [secrets]`, is written in `config/behavior.yml`. A `closed_paths` that is absent, or a value that is not a list of strings, gives the finding `findings.apps.closed_paths_shape`, which names the file `config/behavior.yml` and the key `apps.closed_paths`, as `behaviorFindings` reports the other errors of that file (`src/lib/data/sources/config/catalogs.ts:152`), and while it stands every `file` target rejects `closed` for every app, so an error in the key closes files and never opens one; an entry that is empty, starts or ends with `/`, or holds an empty, `.`, `..` or dot-led segment gives the same finding and is left out, the other entries applying; a duplicate entry applies once and gives no finding. `config/behavior.yml` has no `apps:` block until the build step adds it with every key of the block and its value. A `file` whose `path` breaks the segment rule of the app file server above rejects `closed` for every app, a machine app and a root app alike: a segment that is empty, `.`, `..` or dot-led, or a backslash or NUL anywhere. So `.env`, `.ssh/id_ed25519`, `.oculus/approvals.json`, `a/.git/config`, `a//b`, `/etc/hosts` (its leading segment is empty), `a/./b` and an empty path each reject `closed`, and a dot inside a segment (`notes.v2.md`) is not dot-led. The rule is checked on the exact string the app passed: `open` takes a string over the bridge and decodes nothing, so `%2Eenv` is a literal name that does not start with a dot, and the page passes the path URL-encoded to the source route, which decodes it back to the checked string. The rule and `closed_paths` are applied again to the part of the file's real path under the root's real path, so a link inside a root that points at a dot folder (`creds` pointing at `.secrets`, opened as `creds/key`) rejects `closed`, and so does a link whose target lies outside the root, whether or not the target exists. The real-path checks compare the real path defined under "Where an app lives", so `hub` with `TOOLS/OCULUS/CONFIG/local.yml` rejects `closed` and, on a root holding `secrets/`, `SECRETS/a.txt` rejects `closed` under the default `closed_paths`. The checks run in this order, so that the answer for a hidden path never depends on the disk or on which roots are shown: the segment rule and `closed_paths` on the given path; the key `engine`; for a root app, a root other than its own (`closed`); whether the root is shown (`missing`); the checks on the real path, each `closed` (outside the root, inside oculus's own `config/` folder, the segment rule and `closed_paths` on the part under the root); then whether the file exists, and a file that does not exist rejects `missing`. A binary file, and a file that `open.program_ext` maps to a program such as a `.docx`, open in the source tab as source text, as every file `open` names does, and no program is started. Every check of `{ file }` after the view and project forms runs on the server, since the page cannot see a real path: before it opens the tab the page calls `GET /api/app-open?app=<view id>&root=<root key>&path=<path>`, each parameter sent through `encodeURIComponent`, which runs the checks above in their order for that app and answers `{ result: "ok" | "closed" | "missing" }`; the page opens the source tab only on `ok` and otherwise rejects the word the route answered. The route sits beside `GET /api/app-store` under the same rules: GET only (any other method answers 405), it writes nothing, a parameter that is absent, empty or given twice answers 400, an `app` no held row names answers 404, and only the page calls it. The bridge's `open` reaches the page's own tab opener and never `POST /api/open`, the route that starts a program (the open action of the Configuration section), which stays closed to apps beside the other closed write routes above. A target that is none of the three forms rejects `closed`. At most `apps.opens_per_min` (30) calls of `open` pass per frame per minute, and the rest reject `rate`.

**Approval.** An app runs only after the reader approved it on this machine, by the processes rule: the approval is kept in `~/.oculus/approvals.json`, named by the `approvals` key of `local.yml`, and keyed by the app's content, so a changed app asks again, and so does a root app that arrives or changes by `git pull`. The file is one shape for every user of the rule: `{ "version": 1, "approved": { "<kind>:<sha256 hex>": { "label": "<text>", "at": "<time>", "folder": "<real folder path>" } } }`, where `folder` is present on an `app` entry only, mode 0600, in a folder that each write of the default file under `~/.oculus` makes 0700 when it is looser and owned by the user (a folder owned by another user, and the folder of a file the `approvals` key puts elsewhere, are left as they stand), written by rename and read back to check the write. `<kind>` is `app` for an app and `command` for a repository command, debug launch or seeded agent of the processes rule, whose hash is over the exact text, which for a seeded agent is `JSON.stringify({ agent, cwd, seed }, null, 1)`, the agent, the real path of the folder it starts in and the seed text the server built for the task (the reader's own words added to it are outside the text), and for a repository command is `JSON.stringify({ repo, chain: [[folder, run], ...] }, null, 1)`, the repository's real path and, for each command of the chain in run order, its folder relative to the repository (`.` for the repository itself) and its line before any placeholder is replaced, so the hash can be recomputed from those fields with that indent (JSON, so a tab or a line break inside a folder or a line cannot read as the boundary of two); an app's hash is over its real folder path, its name, its manifest bytes and, for each recorded file in sorted path order, the path, the length and the bytes. The folder is in the hash, so two byte-identical apps in two roots (one repository cloned twice, two worktrees) are two entries, and approving or revoking one never touches the other. An entry is found by the app's real folder path, whatever its name: approving an app removes the `app` entries whose `folder` is that folder, and only those, so one approval per folder is live, and `revoke` finds the entries by the same field. `POST /api/approve` carries `{ action: 'approve', view, hash, keep? }`, with the app's view id in `view`, which the server refuses with 409 `changed` when the hash is not the app's current one, so the reader approves exactly what they were shown, and `{ action: 'revoke', view }`; it sits under `/api/`, so the origin rule and the write token apply. The server enforces approval: it serves an app's files only while the app's hash is in the file under the app's folder, or the app is kept approved, and the approve route updates the held state before it answers, so a revoke stops serving at once.

Before approving, the tab shows the approval panel in place of the frame: the title (followed by the root's key for a root app) and description; the name and the app's folder path; the file count and size; the channels the app reads and the writes it may ask for, each in plain words (`apps.read.<channel>` and `apps.write.<kind>`, with `apps.read_root.git` and `apps.read_root.files` for a root app); the outside origins it declares in `connects`, each as an address under `apps.connects`, or `apps.connects_none`; where its store is written, and for a root app that the file is in the root and tracked by git unless the root ignores `.oculus/app-data/` (`apps.store_machine`, `apps.store_root`); and a control that opens the app's folder in the file browser so the reader can read the files. Every word that comes from the manifest, the title, description, name and entry included, is drawn as text by Svelte's interpolation and never as HTML, in the catalogue, the tab, the notices and the approval question alike, so a title holding markup shows the markup.

**Keeping a machine app approved while it is written.** The approval panel of a machine app offers a second control beside Approve, `apps.keep_approved` ("Keep approved while I edit"), which approves the content shown as Approve does and also keeps the app approved. Until the server process ends, a change to any file of the app except `app.yml` leaves the app approved and served: the address key changes with the files, so the frame reloads, and no question is asked. A change to `app.yml` ends the keeping and the panel asks again, showing the new manifest's channels, writes and origins, since the manifest is what names what the reader approved. The keeping is held in the server's memory as the hash of the manifest bytes approved with it, never in `approvals.json`; it is ended by Revoke, by a change to `app.yml` and by the end of the server process. After a restart the app is approved only by the entry the control wrote to `approvals.json`, so it runs while its files are as they were at that press and asks at the first change. `POST /api/approve` carries `keep: true` for it, which the server refuses for a root app: the control is never offered for one, since a pull writes a root app's files. While the keeping holds, the tab's strip shows the glyph `edit` with the words `apps.editing_mark` where an unapproved app shows the lock.

**Reading an app's files.** A file whose real path lies inside any apps folder, the machine's or a root's `.oculus/apps/`, never opens in the Document view, from the file browser, a bookmark, a link or `open`, and its `.html` and `.htm` files open as source text, since the Document view's frame carries oculus's origin (`Document.svelte:157`) and an app's page drawn there would run before approval with the write token in reach. Two things hold it. The page joins a file's root folder to its path and tests the result against the `folders` of the `apps` channel, and opens the source tab for a match, in `openRow`, `openRowBeside` and `openBookmark` (`views/shared/explorer/opening.ts:68-104`). The file route tests the real path, which the page cannot see through a link, and answers a file of an apps folder as `text/plain; charset=utf-8` with `X-Content-Type-Options: nosniff`, so such a file cannot run as a document wherever its address is opened, a link inside a manual included.

**What an app does not get.** No process and no server code: the server runs nothing an app holds, and `open` starts no program. No file outside its folder but its own store: the frame reaches only the recorded files by address, the store only through `getStore` and `setStore`, and the file browser is not offered to it. Requests: the policy above names the sources the browser is told to allow, which are the app's own files, the shared files, `data:` images and the origins the app declared in `connects`. No cookies or storage, no popup, form, modal or navigation of the page. No other app: an opaque origin, an address key nobody else holds and a store that only the app's own view id names. Not the write token, `/__data.json`, the socket or any `/api/` route: the policy's `connect-src` stops the request; a request that reached the server anyway is cross-site with `Origin: null`, which `sameOrigin` and `allowedOrigin` refuse, a write would still lack the token, and no route other than the app files sends `Access-Control-Allow-Origin`, so an opaque document cannot read the page's data. Not the page's DOM, which is another document. The page's chords and its right-click handler do not see events inside the frame: `oculus.js` forwards a `keydown` that holds Control, Meta or Alt, or is Escape, to the page as `key({ key, code, altKey, ctrlKey, metaKey, shiftKey })`, and the page dispatches it as a `keydown` on `window`, where the shell's key handler listens (`Workbench.svelte:250-251`, `svelte:window`). The page accepts `key` only while `document.activeElement` is that app's iframe and at most `apps.keys_per_s` (20) calls a second; any other call is dropped, an Escape without focus included; a right-click inside the frame opens the app's own menu or the browser's, and the page's context menus never open over it. The boundary against an app sending what it read to another machine is the reader's approval of its files and of the origins it declares: the policy stops the requests a document makes through scripts, styles, images, fonts, media, fetches, forms and frames to any address but the app's own files, the shared files and the origins in its `connects`, and the approval panel lists those origins. Whether the policy also stops WebRTC and DNS prefetch, and whether `connect-src https://host` also admits `wss://host`, is not claimed here: the build step measures all three in Chrome, and this section then states the results. Whether a download link to an outside address sends a request from an app with no `connects` is not claimed either: the build step measures it in Chrome and closes it if it does.

**Words.** The words the reader sees come from `config/text/` through `t("group.key")`, in one new file, `config/text/views/apps/apps.yml`, holding the group `apps`: `label`, `glyph`, `unapproved_mark`, `editing_mark`, `approve_title`, `approve_question`, `approve`, `keep_approved`, `revoke`, `open_folder`, `reads_none`, `writes_none`, `connects`, `connects_none`, `store_machine`, `store_root`, `read.<channel>` for each channel a machine app may declare (`portfolio`, `feeds`, `git`, `hpc`, `audit`, `config`, `files`, `inbox`, `calendar`, `sessions` and `usage`), `read_root.git`, `read_root.files`, `write.<kind>` for each kind a manifest may declare, `changed`, `load_failed`, `refused_read`, `refused_write`, `refused_open`, `confirm_write` and `rate`. The finding sentences are in `config/text/findings.yml` under `findings.apps` with the keys named above, and `findings.apps.carries.<channel>` for `apps`, `pty`, `inbox`, `calendar`, `sessions` and `usage`. An app whose bridge handshake does not complete within `apps.connect_timeout_s` (10), the timeout given to `connect`, draws `apps.load_failed` over the frame with a control that reloads it; an app that reads and writes nothing still calls `connect`. The keys of an `apps:` block in `config/behavior.yml` are the limits `connect_timeout_s`, `state_max_kb`, `store_max_kb`, `writes_per_min`, `opens_per_min`, `keys_per_s`, `max_files` and `max_mb`, and the list `closed_paths` (`[secrets]` in the file), read by `appsSettings`, which sits beside `mailSettings` in `src/lib/data/sources/config/settings.ts` and requires the limits as `mailSettings` requires its keys; `closed_paths` alone is reported as a finding, with files closed, as above.

## Relationship to the cockpit

- The cockpit is frozen: bug fixes only, nothing new is built there.
- No code is shared. oculus holds its own copies of the configuration and of the memory-wall images.
- Both read the hub's data from its one documented data path, which oculus reads from `local.yml`.
- The cockpit retires when the last view it has and oculus does not has moved. The `.app` launcher then points at oculus.

## Conventions

- Every source file under 1000 lines, checked at 900 for a file and 540 for a component by `utils/size-check.sh`. A file approaching it is split by concern, never by line count.
- At most ten items in a folder under `src`, `tests`, `utils` or `config`, checked by `utils/folder-check.sh`.
- Four-space indentation in every source file. Prettier is the formatter, pinned in `.prettierrc` (`tabWidth: 4`, `useTabs: false`), with `npm run format` to apply it and `npm run format:check` as a verification command beside `npm test`, `npm run test:checks`, `npm run check` and `npm run build`. A hand-formatted file is never the answer to a failing check.
- ASCII only in every authored file. Glyphs come from `catalogs/glyphs.yml`, strings from the catalogs under `config/text/`, colours from `tokens.css`.
- One continuous line per paragraph and per bullet in Markdown and YAML; no hard wrapping.
- Plain prose in docs and comments; a comment says why, not what.
- The application runs a git command that writes only when the reader presses the control for it, behind the write token and, for a write that loses work or reaches a remote, a confirm; the one exception is the timer of `git.autofetch_minutes`, which while the key is above 0 runs `git remote` and then `git fetch --prune` in each repository with a remote, with no token and no confirm; no other watcher, timer, socket or agent working on the application runs one, and a commit is the reader's. The other git behaviours oculus has are fixed with no key, and nothing pushes after a commit except where the reader pressed Commit and Push or Commit and Sync.
- Work proceeds from the ledger in `.scratch/migration/`: `plan.md` is the step list, `orchestrator-state.md` is read first, and `agents/spec.md` is the standard every step is built and reviewed under.

## Decisions taken

- Name: `oculus`, at `research-hub/tools/oculus`.
- Stack: SvelteKit with the Node adapter, Svelte 5, Vite, Vitest, TypeScript. The one enforced boundary (`$lib/server`) is the reason for Kit over bare Vite.
- Live data: one WebSocket with channels, the server watches and pushes; no polling. Writes are `fetch` POSTs, each given up with the form told so once `writes.timeout_seconds` of `behavior.yml` passes with no answer.
- Wire model: entities and relations, joins in client selectors, documents on demand.
- Layout: a serialisable tree.
- Configuration: one concern per file (`sources`, `vocab`, `layout`, `behavior`, `appearance`, `meta`, `glyphs`, `text`, `manifest-schema`), the research domains' colours keyed `domains`, the UI theme list in `appearance.yml` as data rather than catalog strings. Appearance: VS Code Dark Modern and Light Modern as two more themes, the wallpaper behind the panels, the icon or ASCII toggle.
- Git writes and the deposit: a project's `code/` is ordinary tracked content of the hub and never carries a `.git` of its own. The deposit grows from a force-pushed snapshot into a repository with history that lives outside the hub tree: a mirror clone per deposit repo under the machine-local state folder, into which each deposit syncs `code/` (minus the deposit-exclude rules) and commits with a message, and from which the tool pushes, lists, creates and switches branches; every write behind the token and a confirm. A git command that runs the repository's hooks (a commit, a merge, a cherry-pick, a rebase continued, a push, a pull, a switch, the making of a worktree and the deposit's commit, switch and push) runs with no time limit, and every other command keeps its limit (`TIMEOUT_MS` for the local ones, `PUSH_TIMEOUT_MS` for a fetch, `NETWORK_TIMEOUT_MS` for the deposit's clone and `gh` calls). `server/core/git/running.ts` keeps one `AbortController` per root and per deposit, and the `cancel` action of `/api/git` and `/api/deposit` (behind the token, with no confirm) aborts the one in flight. A command ended that way, by its time limit or by its output limit ends the processes it started below git (a hook, the ssh of a fetch), passing over the git processes between them (the merge a pull runs), and leaves git to end on its own (`endWith`), so a hook does not outlive it and a merge cancelled during its pre-merge-commit hook is left in progress with its `MERGE_HEAD`; a process still running two seconds later is sent SIGKILL, and git is signalled itself only when nothing is left below it. Cancel is listened for by `endWith` rather than handed to `execFile`, which on an abort closes the command's pipes and answers before git has exited; the page's git writes wait for the server's answer with no limit of their own, and `cancel` keeps `writes.timeout_seconds`. One classifier, `classifyFailure` of `server/core/git/parse.ts`, reads a failed command in this order: Cancel (`cancelled`), the time limit (`timed-out`), the output limit (`too-much-output`), a signal (`signal`), then git's own text, then an exit status with nothing written (`exit-status`); the five codes are worded by the `server.git` group of the catalog, with the program's word first. The reason of git's own text is the last line of stderr that begins `fatal: `, with the prefix dropped, since a command that prints progress before it fails ends on its fatal line; a stderr with no such line gives its first line; and an empty stderr gives the last non-empty line of stdout, so a commit on a clean tree answers `nothing to commit, working tree clean`. When Cancel, a signal, the time limit or the output limit ends a merge, a cherry-pick or a rebase continued, `leftInProgress` of `server/git/git-index.ts` reads the repository as for any other failure and the answer adds that the operation is left in progress (`Git was stopped by Cancel; the merge is left in progress`), so the view draws its in-progress state and Abort Merge. `endWith` reads the process table (`ps -A -o pid= -o ppid= -o comm=`) at the kill and again every two seconds until nothing is left below git, and a process that detached itself with `setsid` has left the parent chain the read follows, so it is not reached. `--abort` and `worktree remove` keep the ten-second limit. A project that is also a public repository (engram) folds into the hub as tracked files, its GitHub history kept in the mirror. The sessions' Changes panel and the Repositories view stage, commit, push, pull, sync and manage branches, stashes and tags on the repositories oculus knows the same way, and the Repositories view also cherry-picks a commit, checks a commit or a remote branch out detached, creates a branch or a tag from a commit, deletes a merged branch, moves untracked files to the Trash and adds paths to `.gitignore`, and reads a file as HEAD or the index holds it, a ref against a commit and a linked worktree's file against the main worktree's, through the one commit box `views/shared/changes/CommitBox.svelte` both draw.
- Sessions cover two agents and a shell: Claude Code transcripts (`<dir>/projects` of every Claude account, with the pid registry) and Codex CLI rollouts (`<dir>/sessions/YYYY/MM/DD/rollout-*.jsonl` of every Codex account, no registry, liveness from a running `codex` process) fold into one record shape with a `tool` field; a terminal pane runs `claude`, `codex` or a plain shell inside tmux.
- A project opens as its own tab (`project` view, one instance per project, documents on demand through `api/docs`); a local HTML file under a configured root opens as a tab (`document` view over `api/file`, the roots in `sources.yml`, bookmarks in the reader's own `~/.oculus/bookmarks.yml`); the rail draws one button per page of `rail:`, and every view is listed in the Views catalogue; every control has an immediate tooltip.
- Docking: tabs drag between panes and across pages, a drop on a pane's edge splits it, a tab dragged with Alt held floats at the pointer, a pane can be closed whole, maximised and floated, all with keyboard equivalents.
- Sessions are six views, not one.
- Tmux is the session backend (installed, 3.7c); migration of a running session is explicit and per session.
- The pty bridge is tmux control mode and no native pty module: a terminal is a tmux session `oculus-<id>`, and the server holds one `tmux -C attach-session` client per attached terminal, since tmux streams `%output` only for the panes of the session a control client is attached to. Terminal input and resizes are accepted only on a socket whose subscription carried the write token. What the page types reaches the pane as the bytes it is, through `send-keys -H`, in pieces of at most 996 bytes (tmux's command-line client refuses a command of more than 1000 words) cut only between characters and between escape sequences (`inputChunks` of `server/machine/pty/tmux.ts`), so a mouse report or a focus report reaches the program in one write and never as a lone Escape, and a paste longer than 996 bytes arrives in several writes, in order, its opening and closing markers each whole. A steer is typed the same way (`inputArgs` of `server/machine/pty/sessions.ts`), then Enter. A page that attaches is given the pane's whole capture followed by a move to tmux's own cursor (`screenAt` of `server/machine/pty/sessions.ts`) and by the modes the pane's program set that a capture does not hold, read from tmux's flags in the same `display-message` (bracketed paste, the cursor and keypad keys, the mouse reports, insert, wrap and a hidden cursor; `modesAt` of the same file), since the page resets its grid before it writes the capture, on a new grid and on a reconnect alike; the cursor move lands right once the page's grid and the pane are the same height, as they are once the page's resize has answered; after `RESIZE_WAIT` (2 s) with no answer the channel is asked for anyway, and the first lines can land at the old height (`subscribePty` of `state/sessions/terminals.svelte.ts`). The `sessions` payload carries no terminal list until tmux has answered once, and a failed `list-sessions` keeps the last list, except that "no server running" or a missing tmux socket is taken as the empty list only when the read and the `NO_SERVER_CONFIRMS` reads after it, `NO_SERVER_CONFIRM_MS` apart, all say it, no control client runs then and no kept server pid is a running tmux (a control client's process ends with the tmux server, and the list read also names the pid of the server that answered, which `kill -0` and `ps` know while its socket cannot be reached, so with either the answer is given up and the last list stands), and reads that answer out of order never put an older list back (`refresh` of `server/machine/pty/channel.ts`), so a restart or a slow tmux never reads as every terminal having ended. Every terminal `startTerminal` starts carries `CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN=1` (the `GRID_ENV` pair of `server/machine/pty/sessions.ts`, placed by `startArgs` after the account pairs), so Claude Code draws in its scrolling renderer and the grid keeps its scrollback; the usage refresh's own Claude, started by `refresh.ts` without it, keeps the renderer it has. A terminal that ends leaves the list, except a task terminal, which tmux keeps with `remain-on-exit` and the option `@oculus_task` (the repository, the command's name, its source, the token its line prints before each command's name, and the chain with each command's folder) until it is closed and which the channel polls at `POLL_MS` while its line runs; the diagnostics of a task terminal that ended with no grid showing it are read from one `capture` action of the terminal route, the whole text of its pane (`capture-pane -p -J -S -`, `captureTask` of `server/machine/commands/run.ts`), refused for a name oculus does not list; the page takes an ended terminal out of the Terminal tab that owned it, on any page, closes a tab left owning no terminal unless the reader is composing in it, and clears a selection that was that terminal; a tab that never held a terminal, or one showing the composer when its last terminal ends, shows the composer and stays (`endedTerminals` of `state/sessions/terminal/terminal-lists.ts` and `createTerminals` of `state/sessions/terminals.svelte.ts`, wired in `state/client/context.ts`). Attach to Session, a submenu of a Terminal tab's New Terminal menu and of the empty area of its list, names the terminals no Terminal tab owns (`unownedTerminals` and `terminalLabel` of `state/sessions/terminal/terminal-lists.ts`; built by `kindsMenu` and `emptyListMenu` of `views/sessions/terminal/terminal-list.ts`) and a pick puts the one chosen at the end of that tab's order, shown alone, and shows the tab (`attachTerminal` of `createTerminals`). `POST /api/terminal` answers every refusal as a word of `TERMINAL_REFUSALS` with the names its sentence needs (`server/machine/pty/refusal.ts`), and a failed tmux call as `terminal-ended` when the list no longer holds the terminal and `terminal-failed` when it does (a start whose session is not listed afterwards is `terminal-not-started`), so no text of tmux or of a validator reaches the page, which says the catalog sentence of the word (`state/shared/answers/terminal-words.ts`); a refused resize is said on the bar of the tab that owns the terminal. A start sets the session's name, its resume mark and a task's mark in the `new-session` invocation itself, joined by tmux's `;`, so a command that ends at once still leaves a named, marked session. The list the `sessions` payload carries is republished when a terminal's name, title, icon, colour, task mark, exit status or pane process changes (`#took` in `server/machine/pty/channel.ts`), so a task terminal run again that ends with the status it ended with before is a change the pages are told of.
- `local.yml` carries `hub` (the research hub's absolute path, default two directories above `tools/oculus`) and `port` (default 8790; 8787 is the cockpit's and is never used). The text catalog reaches the browser as the page's data at first load and afterwards by push over the socket like every other YAML (the portfolio watcher covers `config/` as well as the hub); the browser never fetches the YAML as a file.
- One tree per page, every split child foldable to its edge through one control and expandable again, the folded state saved with the layout. There is no panel beside the tree: what a side panel would hold (shift-click in the Views catalogue, a session detail opened from a card, a project's editor and deposit opened from its card) opens in a new pane to the right of the active one, and the next one joins that pane as a tab while it is still open, so opening the editor from five cards is one pane of five tabs rather than five panes. A saved layout of two trees is read as one: a page keeps its main area as the root when the panel holds nothing, and otherwise is a split of the two at the shares the panel had, with the panel child folded when the panel was hidden.
- A page shows other pages. A leaf of a page's tree is another page, drawn where it sits with a header naming it and the one control that stops showing it there; it is the same page and never a copy, so a tab opened in it is open wherever that page shows and switching to it shows the same arrangement. A page never contains itself, directly or through another page, and is drawn at most once on a screen; a drop or a menu item that would break either rule is not offered, and a page taken out, or closed from the Pages view, gives its space back to the neighbour it was split from. Two page leaves side by side show two pages next to each other. A nested page is reached by focus and not by a digit: a bare digit is the rail page of its place. Every store operation that names a path names the page it addresses, the page on screen when it names none, so a pane carries the page it belongs to beside its path and a view opened while reading inside a shown page lands in that page. The pane menu is the keyboard path to showing a page and a page's row dragged from the Pages view onto a pane's edge is the pointer path.
- Pages: the workbench is one of several pages, each a whole arrangement with a name, and the saved layout is the list of pages plus which one is current plus the floats, so the layout tree of "Layout as data" is unchanged and gains a level above it. The rail's buttons are the pages of `rail:`, each tied to its arrangement by key; a browser with no saved layout draws no page until the configuration names the first, and starts on it; the Pages view makes, renames and closes pages, one explorer row per page (`ui/tree/TreeItem.svelte` in a `TreeView`), whose press shows the page; a row dragged past the drag threshold and released over itself shows nothing, by the rule the Views catalogue keeps for its cards (`views/system/workbench/row-press.ts`). The Views catalogue on the System page opens a view on the page shown before that page, which the layout store tracks and does not save; a catalogue moved onto another page opens on that page. An entry is also opened on the catalogue's own page: dragged onto a pane there (a `view` drag of `state/workbench/drag.svelte.ts`), or through its right-click menu's Open on this page and Open beside on this page. None of them covers the catalogue. A view asked for in the catalogue's own pane opens in another pane of the page, or beside the catalogue when its pane is the page's only one, and a view already open in another pane of the page is activated where it is (`openAway` and `openNextTo` of `state/workbench/layout/open/away.ts`). Switching pages unmounts the hidden page's views, which rebuild from the stores when it returns (a terminal repaints its scrollback), so nothing is drawn twice and no hidden terminal holds a client. The digits 1 to 9 show the rail page of their place, Ctrl with a digit switches the tab in the focused pane, and a group's `chord` letter before a digit opens the entry of that place in the group (`f`, `m`, `p`, `e`, `s`, `c`, `l`, `r`, `t`, `h` and `y`, one per rail page); `direct_chord` counts the entries of a group with no `chord`, and every shipped group has one. A rail button's menu, and a rail page's row of the Pages view, reset that page to its arrangement, and Settings resets every rail page, removes the pages of buttons the rail no longer has and puts the floats of `config/layout.yml` back in place of the floats held (`resetPlan`, `resetAsk` and `resetAfterAsking` of `state/workbench/navigation/pages.ts`, `resetPage` and `resetPages` of the layout store); each asks first through a confirmation naming the pages, then asks each tab of those pages holding unsaved text the question closing that tab asks, one at a time, and a no to any ends the reset with nothing changed; a page the reader made is never touched. Every write of the saved layout is also recorded: the page gives each browser tab an id for its life under `oculus.layout.tab` in `sessionStorage`, and each write appends one entry to a list of the last 500 under `oculus.layout.writes.v1` in `localStorage` (`WRITES_KEY` and `WRITES_KEPT` of `state/workbench/layout/saved/storage.ts`, newest last). An entry is `{ at, tab, call, page, tabs }`: `at` the time in milliseconds, `tab` the id of the browser tab or the app window whose page wrote, `call` the name of the layout store operation the caller invoked (`openPage`, `closeInstance`), `page` the id of the page on screen, and `tabs` every tab of every page and float written as `<tab id>:<view id>`, so a tab that is missing from one entry and present in the one before shows which browser tab wrote the entry it went missing in. A write equal to the newest entry in all but its time, such as each move of a sash drag, is counted on that entry as `n` (the writes it stands for) and `last` (the time of the latest), so a drag keeps the older entries. The record reads and writes only those two keys, and a full, refused or unparsable storage loses the record and never the layout write.
- Floats are saved beside the pages: the envelope is `{ version: 6, pages, current, floats }`, each float `{ id, pane, place }`; a version 4 or 3 envelope is read with no floats, and a browser holding one takes the floats of `config/layout.yml` once (the shipped floats reach the page with the configuration, after the saved layout is read, so a layout read from a version 4 envelope is written back at version 4 by `serialiseFloatless` until the shipped floats have been taken in, `needsFloats` and the store's `pendingFloats` marking it, and at version 6 from then on; a float-less layout written at version 5 or 6 would read as a reader who has no floats and the shipped ones would never arrive), each tab of a view a shipped float holds moving out of its page into that float with its instance id and state kept (`adoptFloats`); a float that does not add up (no tab, a place past the window, an id a page or another float already uses, a tab id held twice, a second float docked on one edge, a window place with a size that is not finite or is under 200) is dropped on reading and the rest kept. `config/layout.yml` carries the top-level `floats:` list, each entry `{ view, dock, size }` or `{ view, x, y, w, h }` with `view` as an arrangement pane's `view`, read by `parseFloats` of `state/workbench/navigation/arrangement.ts`; a browser with no saved layout starts with them and Reset all pages gives them back. The first entry docks Live HPC and Usage at the right edge, so the Focus page is the Focus board alone. The border is the token `--float-border`, `--c-orange` by default and so each theme's own orange, declared on `body` in `themes/tokens.css`. A float's menus offer Dock Left, Dock Right, Dock Bottom (each left out for the edge the float is on), Float on a docked float and Return to Page, and no split, fold or maximise; a tab's state is held under its instance id, so a float can later move to a window of its own. A pane has an optional `locked` flag (Lock Group in the strip menu, `setLocked` of `layout/tree.ts`): a locked pane is skipped when a document opens (`landingFor`), still takes a tab dragged onto it, keeps its lock through activate, open, move, split and close, is saved as `locked: true` inside the envelope (a pane without the field is read as unlocked), and keeps its place when its last tab closes, so only Close pane removes it. A tab is pinned with `pinned: true` (`pinTab` and `unpinTab` of `layout/open/pinned.ts`): a pane keeps its pinned tabs first, in their order, then the rest, and a saved pane whose pinned tabs are not first is put in that order on reading; a pinned tab is never a preview (the two flags together read as pinned), keeps its pin through a float, a move to another page and a split, and lands in the pinned run of the pane it goes to, a drag into the run pins it and a drag out of it unpins it. A pane holds `recent`, the ids of the other tabs it showed, the one shown last first, and closing the active tab shows the first of them still open, else the tab that took its place; `recent` is saved with the pane, so a version 5 envelope, which holds none, reads with the active tab as the only one used. A new tab opens after the active tab (`openedAt` of `layout/tree.ts`), after the pinned run when the active tab is pinned, which is VS Code's `openPositioning: right`; the preview tab's replacement, that position and the unlimited tab count are VS Code's defaults and have no setting. The pane of a float is lockable the same way: its strip menu offers Lock Group and Unlock Group, and the lock stays through a dock, a move, a return to a page and a save and read back. A saved page tied to the rail key `info` is folded into the page tied to `views` when a layout is read (a views page holding no system view gets the info page's system views in a new pane below the pane holding Pages, split in halves, and one still labelled Views and Settings takes the label System; the info page's own splits, sizes and label are not carried), and a saved `config` tab becomes a `settings` tab with its state dropped (`state/workbench/layout/saved/migrate.ts` and `fold.ts`), so a browser that saved the two old system pages opens the one System page with its tabs.
- Opened views land beside the tools. - The native window. oculus runs in a browser tab or in its own app: `npm run app` starts Electron (`src/desktop/`, run unbuilt as the server is), whose main process builds the checkout's server, runs it as a utility process and draws its page in Chromium, and `npm run app:package` makes an `oculus.app` whose bundle is a stub importing the checkout's main. The reasons, one clause each. The server is a utility process with its own listening port, because the page, the sockets and the terminals all stay as they are in a browser and a crash of either side leaves the other running; it is the TypeScript tree itself, unbuilt, so there is one copy of the code. The main takes the single-instance lock before it builds, so a second start never rewrites `build/` under a running app. A held port is told from an oculus by `GET /api/health`, so a start onto a running server offers a window onto it instead of a second server. A window is made with Node integration off, context isolation and the sandbox on, and its only way into the main is the preload's one bridge object, whose handlers answer the top frame of the server's page alone; links, navigations and `window.open` go through one pure decision, so an address of another origin opens in the default browser and a `file:` or `javascript:` address is refused. A float can become a window of its own (the `window` place), with the same client state and a page of its own (`?float=<id>`), because a tab's state is held under its instance id; the windows share one saved arrangement, so a write is a turn taken through the main (the save turn): a write made from an arrangement that is not the one the main holds is refused and answered with the held one, and the page takes it and makes its change again. The window state (`~/.oculus/window.json`), the application menu, the keys the page asks for (Cmd+W, Ctrl+Tab, Cmd+N, Cmd+F), the folder sheet and the find bar are the app's, and the text menu and the tab menus stay oculus's own, so the spelling suggestions are drawn by oculus at the top of the text menu from the checker's answers, and no native menu is drawn in a page.
