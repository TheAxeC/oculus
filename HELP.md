# Oculus

Oculus is the private working surface for the research hub: one page in a browser on this machine, reading the hub's own YAML and Markdown from disk and showing it as boards, lists and documents. It writes only where a control says it writes, and only back into the same files. This page is the manual; the Config view beside it shows the files every one of these surfaces is configured by.

## The window

Down the left is the rail, and along the bottom is the status bar. Everything else is the pane tree: one tree per page, made of splits and panes, each pane a stack of tabs, each tab one view.

A control's tooltip opens when the pointer rests on it and when the keyboard brings the focus to it. A click puts it away, and it comes back once the pointer has left the control and rested on it again. Every scrolling box draws a thin scrollbar in the theme's colours, its thumb at 3:1 or more on its track, except the rail's list and the tab strips, which draw none and scroll by wheel, trackpad and their own controls.

### The rail

The rail draws one button per entry of the `rail:` list of `config/layout.yml`, each `{label, glyph, page}`, where `page` names an arrangement under `arrangements:`. As shipped there are twelve, top to bottom: Focus, Sessions, Projects, Incoming (the Inbox, Lit Watch, Position Leads and LinkedIn feeds beside the Calendar), Explorer (Files, Repositories and Search, with an empty pane beside them), Academic Life, Pillars, References, Present, System (Status, Findings, Audit, History, the configuration and the gallery), Help (this manual and the HPC how-to beside Research approach, Agent approach and the Memories wall) and Views and Settings (the Views catalogue, Settings, Account setup and Pages). Every listed view sits on exactly one of these pages, in the pane its arrangement gives it. The Views catalogue lists each page's views under the page's name, the Help page's under Help, reached by `h`. A button shows its page: made from its arrangement the first time and shown as it was left after that. A browser with no saved layout starts on the first of them, and draws no page until the configuration has named it. A button is an icon; hovering it shows its page's name and the digit that reaches it. It carries one badge, in the accent: the count of the first view of its page that counts anything, in the order of the page's tabs, the arrangement's views before the page is first made. Drag a button up or down the rail to move it; right-click it (or press Shift+F10) to hide it, to reset its page to its arrangement, or to open the rail list in Settings. Hiding and moving rewrite `rail:`, and History undoes either. Reset is offered once the button's page has been made, and asks first: the question names the page, and then each of its tabs holding text no save has taken is asked about as closing it would be, one at a time; a no to any leaves the page as it was. It rebuilds the page from its arrangement, under the button's name, closing every tab the page held. Hiding the page on screen leaves it on screen. Every view, and every hub document of the `docs` key, is listed in the Views catalogue on the Views and Settings page, under its `nav_groups` group; the groups, their order and their letters are those two keys. A document tab saved at a path the `docs` list no longer holds follows the entry carrying its name, or closes into the tab already showing that entry; one that matches no entry names the path it asked for.

In the catalogue on the Views and Settings page a click shows the page the reader was on before that page and opens the view there, where views land, which is the pane whose tab was activated last; after a load straight onto the Views and Settings page it opens on the first rail page. A catalogue the reader has moved onto a page of their own opens the view on that page. A view already open is activated where it is rather than opened twice. A shift-click opens it in a new pane to the right, on that same page, and the next shift-click joins that pane as a tab while it is still open. Dragging an entry onto a pane of the page the catalogue is on opens it there. An entry's right-click menu, or Shift+F10, offers Open on this page, which opens it in another pane of that page (beside the catalogue when the catalogue's pane is the only one), and Open beside on this page, which opens it in a new pane beside the catalogue. A view that was a tab of the catalogue's own pane moves out of it, and that pane goes on showing the catalogue. A view already open in another pane of that page is activated where it is. A drop on the catalogue's own pane goes to another pane, so the catalogue is never covered.

At the foot of the rail are Bookmarks, a menu rising from the star that lists the reader's own bookmarks from `~/.oculus/bookmarks.yml` by name, which the Files view adds and takes away, each opened as a tab of its own; Search, which opens the palette; and Update, which opens the update tray. Each is an icon with its name as the tooltip. The button of the page on screen draws its icon in the text colour with an accent bar on its left edge. The list above the foot scrolls on its own, and a fade at its top or bottom edge says more entries are past it. The appearance controls (Theme, the Text row of smaller, reset and larger, CRT, Wallpaper where the theme has one, and Icons) are in the Settings view.

Update, at the foot of the rail, opens the update tray: the four update tasks (Lit Watch, Scout, LinkedIn and Inbox), each with the date of its last run, and a Chat control that starts a portfolio-wide Claude session. A task runs the `/research-cockpit` skill as an ordinary Claude session in a terminal, so its permission prompts are answered by you in the terminal pane, which is where the tray puts you when the task starts. Setting `skip_permissions: true` under `tasks:` in `config/behavior.yml` starts them with `--dangerously-skip-permissions` instead, which lets a task run unattended and answer its own prompts; while it is on, a press asks for a confirmation first. The key under its old name, `chat.skip_permissions`, is not read, and a file still carrying it gets a finding on the Findings view naming the key that replaced it.

### Pages and the pane tree

A page is a whole working surface with a name: its own tree, its own tabs, its own arrangement. The rail's buttons switch to their pages. The Pages view on the Views and Settings page lists every page as one row of the explorer's size: press a row to show its page, and hover or focus it for Rename and Close, Close asking first when the page holds more than one tab. The page on screen is the bold row with a check, a page of a rail button names its key after its name, and a page holding unsaved text carries the unsaved dot at the row's end. A page of a rail button also carries Reset to its arrangement, the same reset as the rail button's menu. Settings holds Reset all pages, which rebuilds every page of a rail button from its arrangement and removes the pages of buttons the rail no longer has, leaving the pages you made yourself alone; it asks first, naming each page it rebuilds and each it removes, then asks about each tab of those pages holding unsaved text as closing that tab would, one at a time, and a no to any of them ends the reset with nothing changed; it says so when there is nothing to reset. The digits 1 to 9 show the rail page of that place.

Switching tabs keeps each tab's view as it was left: a pane keeps the view of every tab it has shown until that tab closes.

Where an opened tab lands. A view opened for something (a project, a person, a deposit, a manifest edit, a hub document, a file, a source file, a diff, a merge, a note, a customization file) never covers the tool views of the page it is opened on. It lands, in this order: in the pane that received the last such tab on this page, while that tab is still there; in the pane you are in, when that pane already holds such tabs; in an empty pane; in a pane holding such tabs and nothing else; and otherwise in a new pane split off to the right of the pane you are in, which the next one then joins. A pane holding a tool view takes one only when you are in it and it already holds opened tabs. A tab of that document already open anywhere on the page is activated where it is, and a maximised pane of tools is restored first so the landing pane shows. The rule does not move tool views. An empty pane says Files and documents you open on this page appear here; the Explorer page carries one beside Files, Repositories and Search. Closing the last tab of a pane removes the pane, the empty pane of an arrangement included once something landed in it, and the next view opened for something then splits a new pane off to the right.

Inside a page:

- **Split.** Drag a tab onto the edge of a pane to split that pane and drop the tab into the new half. The pane menu splits without a drag.
- **Fold.** Every child of a split has one control that folds it to the split's edge and shows it again. A folded child is saved folded.
- **Maximise.** A pane can be drawn alone, the rest of the tree left where it is, and shown again from the same control.
- **Drag.** A tab moves inside its pane and to another pane, and a page's row dragged from the Pages view onto a pane's edge shows that page there. A row dragged and let go over itself shows nothing.
- **Show a page.** A leaf of a page's tree can be another page, drawn where it sits with a header naming it. It is the same page, never a copy: a tab opened in it is open wherever that page shows. A page never contains itself and is drawn at most once on a screen.
- **The pane menu.** Close, maximise or restore, fold where the pane sits in a split, split right and split down, and two choices that open a list of pages in place of the menu, Move tab to page... and Show a page here..., each offered only when there is a page to offer. Back, first in the list, returns to the menu; Escape closes the whole menu.
- **Tabs past the strip's width.** The strip scrolls rather than shrinking its tabs, and tab names are drawn whole. Its two controls move the left edge to the next tab's start, or to the strip's end past the last one; a tab being shown or pressed is brought in whole, and so is the shown tab when a narrower window crosses it or takes it out of sight. A wheel or trackpad scrolls the strip freely and leaves it where it stops, so a tab may show in part at either edge.
- **How a strip is drawn.** Tabs stand edge to edge at one height, the shown tab on the pane's surface. The shown tab of the one pane a view opens into carries an accent line along its top and every other pane strip carries a plain one. A page drawn inside another page carries the pane accent only while the reader's active instance is inside that page, and a folded pane a view opens into carries the accent along its folded strip. A tab's close control shows on the shown tab and under the pointer. A tab holding text no save has taken shows a dot in the close control's place until the pointer is over it, and a screen reader hears its name followed by ", unsaved"; the Pages view marks a page holding such a tab as unsaved. The right end of a pane's strip holds the pane menu's ... opener, and, while the pane shows a tab, a split-right button; they and a strip's scroll controls are one bare icon each. A handle between panes, and between the Source view's editor and preview, shows nothing until the pointer rests on it, draws its line at once while dragged or when the keyboard reaches it, and is caught on the borders beside it as well as in its gap.

The layout is saved as it is changed, so the window comes back as it was left.

Tab and Shift-Tab are the browser's: they move the focus between the controls on the page and reach no binding of this table, except in the source tab's editor, where Tab inserts one step of indentation and Escape then Tab moves on. The rail is one stop of that order, and each strip of tabs is one stop with its pane menu the stop after it, so Tab steps past a whole strip in one press and the arrow keys move inside it; the stop stays on the tab the arrows left the focus on, and Delete closes the tab the focus is on. A tab holding text no save has taken is closed only after a confirmation, whether the close came from Delete or from the tab's own control. That text is a source tab's unsaved edit, a field of the manifest editor not yet saved, a value typed into an entry form that differs from the entry as the file holds it now, or a folder or workspace name typed into the Files view's root or workspace form and not yet added. The editor's fields, and in the Tasks, collection, Pillars, Domains, Venues and Data views the open add and edit forms with what was typed into them, and in the Files view the open bookmark form with what was typed into it and the root or workspace form with its line, are there again after the tab is switched away from and after a reload. Cancel, the view's Add or Edit control closing the form, a delete, a save and Revert let them go; a value typed into either form while its save is on its way is kept, in the form left open, and so is the text of an add form closed and opened again while its save was out; an add form closes once its entry is added only while nothing touched it since the save went, and one left open goes on writing the entry it added until its identity field is typed away from it, when it adds another; a bookmark form whose save renames its bookmark stays open over the bookmark under its new name; a save that would give an entry the name another entry of the same file already carries is refused, so no file ends up holding two entries a write cannot tell apart; and the Save control is not pressable while its own save is out. Closing a pane or a page, whether or not it asked first, lets go of what its own tabs held, as closing each tab would; a page shown inside the closed page is not closed with it and keeps what its tabs hold. In the Files view, + bookmark or a bookmark's edit control closing or moving the bookmark form lets what was typed go, and so do opening the root or workspace form over it and the bookmark it edits being taken away. A root, workspace or bookmark save answered after the reader opened another form or switched the tab away closes only the form it was sent from, and a root or workspace form closed and opened again while its add is out stays open with its line. Ctrl and Tab is not the pair that cycles a pane's tabs, because a browser keeps it for its own tabs and never hands it to a page.

Cmd-K opens the palette. With nothing typed it lists the views; a word typed searches the projects, the collection entries and the feed entries as well. Each result names what it is, View, Project, Collection or Feed, before its title. A colon starts a command: `:` and a line number moves the source tab on screen to that line, and `:language` lists every language the highlighter knows, narrowed by what follows, to repaint the tab.

The sheet itself opens with `?` and closes with `?` or Escape. The letters before a digit are the `direct_chord` of `config/layout.yml` and the `chord` of each group in `nav_groups`. A group's documents follow its views in its chord, in the catalogue's order, so the digit after the group's last view opens its first document; the directly drawn groups' documents follow the direct views under the direct chord the same way. Every view now sits in a group with a letter of its own, so the direct chord reaches nothing and the key table has no row for it; a group that names no `chord` gives it entries again.

The status bar runs along the bottom under the rail. On the left: the machine oculus runs on (opens Status), the branch of the repository holding the active tab's file (a list of its branches to switch to, after a confirmation), how far it is behind and ahead of its upstream (after a confirmation, pushes when the branch is only ahead and otherwise pulls and then pushes; a branch with no upstream shows Publish Branch in its place), the findings the Findings view lists (opens it), the Live HPC poll, the usage refreshers and the server connection. On the right, for a source tab: the caret line's blame while Blame is on (opens its commit in the Repositories graph), the line and column (opens the palette on `:`), the indentation (switch spaces or tabs and width, or convert the text), UTF-8, the line ending (convert it), and the language (a searchable list). Then the live sessions, the unsaved tabs (shows the first; not pressable at 0) and the bell. A right-click on the bar hides or shows any item. The bell counts unread notifications and opens the notification centre, with Clear, Clear All and Do Not Disturb, which stays on after a reload; a new notification shows as a toast for eight seconds. Notifications come from a refused rail change, a session waiting on a permission prompt or waiting for input after its turn, an update task that ran, a Live HPC job that ended, and a write that was refused or got no answer.

## Searching the files

The Search view runs one pattern over the files of one root or of every root, and the roots are the file browser's own: the hub, the engine's config folder, the roots `sources.yml` names, and whatever the workspace in force added. Nothing outside those is reachable, and the query never leaves the machine: the search is a local process reading local files, with no index and no service of any kind.

ripgrep does the reading, the copy that comes with oculus rather than one the account happens to have installed, so the version that answers is the one the lockfile pins. What a repository ignores is skipped as ripgrep skips it, and `node_modules`, `.git` and `.svelte-kit` are skipped in every root whether or not a `.gitignore` says so. A hidden file and a hidden directory are skipped the same way, so a `.env`, a `.gitignore` and everything under a `.hidden/` folder are never opened. A file over two megabytes is not opened.

Three toggles decide what the pattern means: `word` matches whole words only, `case` matches the pattern's own upper and lower case, and `regex` reads the pattern as a regular expression rather than as text to find. Finding every reference to a name is `word` over the root that holds the code, which is what a C++ codebase needs and gets without a language server.

Typing runs nothing. Enter in the box and the Search control are the two ways a run starts, and `/` puts the cursor back in the box from anywhere in the results. A result heading opens its file at its first hit and a result row opens it at its own line, both in the source tab. The answer stops at the configured number of hits (`search.max_hits` in `behavior.yml`) and says so when it did; the reading stops there too, so a one-letter pattern over a large root costs what the cap needs and not what the root holds. Each root's search is given `search.timeout_s` seconds, and a root that fails or runs out of time is named under the count rather than passed over in silence. What a tab last found is kept with the tab, so a saved page draws its results again without running the search a second time.

## Source Control

The Repositories view and a session's Changes panel are Source Control as VS Code draws it, over the repositories oculus knows. Every write runs only from a press on the page, and one that throws work away or reaches a remote asks first.

### Committing

The commit box sits above a repository's changes, in the Repositories view and in a session's Changes panel alike, and both hold one message per repository, so a message typed in one is there in the other. The Commit button commits what is staged; its list beside it adds Commit (Amend), Commit and Push, and Commit and Sync, the last two only while the branch has an upstream. An amend needs nothing staged, and with the field empty it keeps the last commit's message. The button beside the field writes a message from the staged diff. Ctrl+Enter or Cmd+Enter in the field commits as the button does. Every commit asks first.

### Diffs, and staging part of a file

Pressing a changed row opens its diff in a pane of its own: side by side, the old version on the left and the new on the right, or inline, one column with the removed line above the added one; the pane remembers which. Within a changed line the words that changed are marked. An unchanged run longer than six lines is folded behind an expander, three lines kept beside each change, and pressing the expander shows it. Alt+F5 and Shift+Alt+F5, or Next Change and Previous Change on the bar, move from change to change, and Open File opens the file at the change the pane is at.

Each change of a file's own diff starts with a bar: Stage Block and Revert Block in a diff of the worktree, Unstage Block in a staged one. Pressing a changed line's number chooses that line, and a block holding chosen lines offers the same actions for just those lines, so one line can be staged or unstaged and the rest left as it was. Revert asks first, since it throws the change away. The group heads carry Stage All Changes, Unstage All Changes, Discard All Changes and Stage All Untracked; Discard asks first.

### Pull, push, fetch, sync and publish

The `...` menu of the Repositories view holds Pull, Push, Fetch, Sync and Publish Branch. Pull runs git's own `pull` with the repository's own configuration, so whether it merges or rebases is the repository's choice; Sync pulls and then pushes; Fetch reads the remote's branches and forgets the ones the remote deleted. A branch with no upstream offers Publish Branch to each of the repository's remotes, which pushes it and makes that its upstream. Everything except Fetch asks first, and none of them ever forces. The status bar's sync item does the same for the repository of the tab on screen.

### Merges and conflicts

A merge, a pull or a stash applied or popped that stops on conflicts is left in progress, as VS Code leaves it: the view says a merge is in progress and how many files are in conflict, and lists them under Merge Changes. Open in Merge Editor opens the three-way merge editor: Incoming, the version being merged in, and Current, the checked-out branch's, side by side above the Result. Each conflict offers Accept Incoming, Accept Current, Accept Both in either order, and Ignore, which keeps what the two had in common; the Result can also be typed into, which settles a conflict by hand, and the bar counts the conflicts still open. Complete Merge writes the Result over the file and stages it, asking first while any conflict is still open. Where one side deleted the file, or both did, the editor says which and offers Accept Deletion, which after a confirm takes the file out of the index and the folder; Complete Merge with an empty Result does the same. Mark Resolved stages a file resolved some other way, or records its deletion where the folder no longer holds it. The commit box starts with the message git prepared for the merge, and the commit finishes it; Abort, after a confirmation, takes the merge back. A rebase stopped on conflicts offers Continue once they are resolved.

### Stashes and tags

Stash, Stash (Include Untracked) and Stash Staged in the `...` menu set work aside, each after asking for an optional message; Stash Staged needs git 2.35 or later, and an older git refuses it with a sentence saying so. The Stashes section lists them newest first; pressing one opens its whole diff, and Apply Stash, Pop Stash and Drop Stash sit on its row, Drop asking first. Create Tag asks for a name, which must be a name git accepts for a tag, and an optional message, which makes it an annotated tag; the tag is made at the checked-out commit. The Tags section lists the tags, an annotated one with its message; pressing one opens its commit in the Graph, Delete Tag asks first, and Push Tags in the menu pushes every tag after a confirmation.

### The graph

The Graph section draws the checked-out branch's history fifty commits at a time, Load More reading the next fifty, each commit with its lanes, the branch and tag names on it, and the checked-out commit marked. While the branch has an upstream, Incoming (what the upstream holds that the branch does not) and Outgoing (the other way round) come first. Pressing a commit lists its changed files under it, each opening that commit's diff of the file, and its `...` holds Copy Commit ID and Copy Commit Message.

### Blame and the gutter

A source tab over a file of a repository marks its changes against the index in the line-number gutter: a bar beside added and modified lines and a wedge where lines were deleted. Pressing a mark opens the file's diff at that change. Blame on the tab's bar adds, beside each line, who last changed it and how long ago, with the commit and its subject on hover; a line no commit holds yet says Not Committed Yet. Blame reads the file as it is saved. Pressing a blamed line, or the blame item on the status bar, opens its commit in the Repositories view's Graph.

## Worktrees and the merge back

The Repositories view is over every root the file browser serves, the hub and the configured roots and whatever the current workspace added, plus the workspace of every session, one repository at a time, chosen in the Repositories list at its top, whose rows say which of them is gone in red, is no repository in blue or could not be read in amber. A repository with no commit yet is listed like any other, with its branch and its files, and its Branches section says the branch has no commit yet. A repository git could not read this time, or whose check timed out, stays in the list and the view stays on it: its path, and its branch line while git named the branch, stay above git's reason, one line in the error colour in place of the sections. What it shows is the pushed state of that repository: nothing is polled, and a commit made in a terminal moves it within two seconds. A diff, the graph, a commit's files, the blame and the gutter marks are not pushed; each is read when a pane or a section asks for it, so a repository with two hundred changed files costs the socket nothing.

A worktree is a second checkout of the same repository on a branch of its own, which is how one repository carries two pieces of work at once. The control at the bottom of a root's worktree list takes a name, says the path before anything is made, and on confirm makes `<root>/.agents/worktrees/<name>` on a new branch of that name from the repository's HEAD, then opens a shell there. A repository whose `.gitignore` does not carry `/.agents/worktrees/` is warned about in the view rather than edited: what a repository ignores is its owner's to decide, and without the rule a worktree made there becomes content of the repository.

Each worktree row opens its diff when pressed and carries four controls, shown on hover or when the row has the focus: its diff against the repository's checked-out branch, a shell started in it, the merge back, and the removal. The merge back is git's own `merge` onto the checked-out branch, a fast-forward where it can be one and a merge commit otherwise. It is refused when the repository has staged or changed paths of its own, when the repository has no branch checked out, when the name is not one of the repository's own branches, and when the branch asked for is the one checked out; a merge that stops on conflicts is left in progress and reported by the paths that conflicted, which the view lists under Merge Changes for the merge editor, with Abort one press away. An untracked file does not refuse a merge, because git carries one across untouched.

Removing the worktree is a second control and never part of the merge. It refuses a worktree holding uncommitted changes or untracked files, which is the difference from the merge: the removal takes the folder away and everything in it with it, so a file git never saw would be a file nobody can get back. The branch goes with the worktree only when no work is left only there, and the answer says when the branch was kept.

## Where the data comes from

Everything on the boards is read from the research hub, whose absolute path is the `hub` key of `local.yml`. The scan rules of `sources.yml` name the folders projects sit in, and a project is any folder holding a `project.yml`. The registries, the collections and the feeds are single YAML files named in the same place; the manuscripts, READMEs and decks are Markdown in each project's own folder.

People and organisations are two of those registries. `registries/people.yml` holds one entry per human, keyed by a short slug, with a name, an `affiliations:` list whose values are keys of `registries/organisations.yml` and whose first is the primary one, a role, and optionally an ORCID, an email, links and a supervision folder; exactly one entry carries `self: true` and that is the hub's owner. A manifest's `collaborators:` and `waiting-on:` name people by those keys, and an entry of `network/joint-work.yml` names its person by `person:`. A value in any of the four that the registry does not hold is a finding on the Findings view, as is an `affiliations:` key or a funding scheme's `funder:` that names no organisation, and an organisation `kind:` outside `university`, `hospital`, `funder`, `company` and `other`. An entry still written with the one key `affiliation:` is read as a list of that one and gets a finding asking for the new name.

Nothing is copied into a database. The server reads the files, builds one snapshot of entities and relations, and pushes it over a WebSocket; it watches the hub and the config folder, so a file edited anywhere reaches the page in the same second. The long documents stay out of that snapshot and are fetched one at a time when a tab shows one.

Three things outside the hub are read as well, all of them this machine's own. The agent sessions are read from every account `accounts` in `local.yml` names: `<dir>/projects` for the transcripts and `<dir>/sessions` for which session is alive for each Claude account, and `<dir>/sessions` for the rollouts of each Codex account; two accounts whose folder is one real folder through a symlink are read once. The session cache, the per-session overrides, the saved workspaces, the reader's own bookmarks and the scratch notes are read and written under `~/.oculus`, or wherever `local.yml` puts each of them, and the providers' client halves are read and written in `~/.oculus/connect`. The engine's own `config/` folder is read on every load and written when a file of it is saved from a source tab.

Writes into the hub go back to the files they came from: a manifest field from the editor, a collection entry from a card, a text file from a source tab. Every write is a POST carrying the page's own token, and nothing outside the hub, the engine config folder, the machine-local files under `~/.oculus` and the configured roots is ever written; what is read beyond those is the agent account folders above, and the workspace a session names when its git state or its terminal is opened.

The Inbox is read live from the reader's own mailboxes, and is the one view that writes to something outside the hub. A mail account is a row of `mail:` in `local.yml`, one `provider` (`google` or `microsoft`) and one `label`; it is added from the Inbox's Add account, which writes the row and the account's file and opens the consent at once, and taken away by its row's Remove; its refresh token is one file per account under `mail_dir` (`~/.oculus/mail` by default), mode 0600, which the consent brings back, and the provider's client half is the one saved on the Account setup view for every account of that provider. A mail account is its own consent with the mail scopes alone, so a calendar account of the same mailbox never gains the right to send. A thread is on the plate when it is in the inbox and unread, or carries the `todo` label, or is unlabeled and is a single message whose subject is not an answer or a forward; a thread whose newest message is the reader's own, or is in the trash, is off it. What the poller publishes of a message is the provider's own one-line snippet, its HTML entities decoded, and nothing more. A provider that does not answer within 30 seconds puts its account in error with a sentence saying so, and the other accounts are still read.

A calendar account is a row of `calendars:` in `local.yml`, added from the Calendar's Add account and removed by its row's Remove, and read again at once without a restart. The first account of a provider needs that provider's client half: Add opens the Account setup view, whose steps register the reader's own application at Google (a Desktop OAuth client) or at Microsoft (an Entra public client with the two redirect addresses the page lists on this server's port), and whose Save writes the half to `~/.oculus/connect/google.json` or `microsoft.json`, mode 0600; the account is then added and its consent opened. Every later account of the provider, calendar or mail, uses the same half and needs no setup. The Set up control and the hint on such an account name the provider as the setup page does (Google, Microsoft), in the Inbox as in the Calendar, while the row keeps the view's word for the provider (Gmail and Outlook in the Inbox). Remove asks first, takes the row out of `local.yml` and deletes the account's own file; the provider's half stays for the other accounts. An account whose own file names a `client_id` loses that id with the file, and its Remove's question says so. A calendar published as a link, such as an Outlook or Google calendar shared by its address, is added from the same Add account by choosing Published link as the provider and pasting the link, which starts `https://` or `webcal://`; it needs no setup and no consent. Its row in `local.yml` is `- { provider: ics, label: <label> }` and the link itself is kept in the account's own file, `<calendar_dir>/ics-<label>.json` (`~/.oculus/calendar/ics-<label>.json` by default), mode 0600, which Remove deletes. The link is read again from that file at every poll and is never logged, published, sent back to the page or written into an error.

What each thread wants, the line about it and the answer drafted for it are the triage notes, one JSON object per thread id in `<mail_dir>/triage.json`. The card writes them, and so does `/research-cockpit inbox`, which reads the mailbox through the runner's own Gmail connector and classifies what it finds; the server polls the file every half second, so a note written from outside is on the page without waiting for the next poll. A note whose thread has left the plate is kept for thirty days and then dropped. Send puts the answer on the thread at the provider and Archive takes the thread off the inbox, each behind a confirmation naming the address the answer would reach and the account it goes from; no draft is ever created at the provider, and those two are the only writes to a mailbox oculus makes. Which address that is follows the thread's newest message: its `Reply-To` where it carries one, and its sender otherwise, which is the rule the send itself uses.

Every write through the write endpoint that changed something is recorded in the change log, `~/.oculus/changes.jsonl`: when it was made, which file it wrote, what it addressed, and the value that file held before it against the value it holds after. That is the manifest fields, the collection entries, the subtasks, the feeds, the deck and the per-session overrides, and a scaffolded idea and the two LinkedIn writes, which are recorded and cannot be taken back; a text file saved from a source tab and a scratch note go through their own endpoints and are not recorded. The History view draws the log newest first, and the control on a row puts the earlier value back through the writer the change came from, refusing when the file has changed since. `changes.keep` in `behavior.yml` is how many changes the file holds.

## How the code fits together

The diagrams are drawn from the source by `npm run diagrams`, which writes each to `docs/diagrams/` as a Graphviz `.dot` file and the `.svg` drawn from it. `npm test` fails while a committed diagram differs from what the source gives now and names every such file, so a change that moves an import, a channel or a write is committed with the diagrams it redraws. A module no layer row places is drawn in a dashed group named "not placed". In the layers overview, an import whose target is not written out is a dashed box naming its file and line, with a dashed arrow from the box of the module that makes it; in the channel and write diagrams, the dashed "not placed" group names with its file and line a publish, a channel read or comparison, a re-export of a whole module, or a call through a computed member or a method of an imported value, whose target is not written out. A call through a local alias, and a function passed by name to a function that calls it, in the same module or another, are followed; a name that holds a function only by a branch, a second assignment or the answer of a call is not.

The diagrams count the imports that run: an `import type` leaves nothing behind in the built code. No module imports itself through a chain of runtime imports (`tests/checks/imports/cycles.test.ts` fails on one and names its modules in order), and inside each layer the folders have an order from the top down, declared in `tests/checks/imports/order.ts`: a module imports its own folder or one below it and never one above, a type as much as a value, and `tests/checks/imports/order.test.ts` fails on an import that climbs. No module augments another module of the tree, with a `declare module` block or a `/// <reference path>` directive, in any direction; `tests/checks/imports/augments.test.ts` fails on one, while a block that adds to a package stays. The checks and the diagrams read a module's imports by parsing it, a component's scripts and markup included, so an import named in a comment is none. The channel and write diagrams read a module's calls in its text with every comment blanked by the same parses, so a call named in a comment is none, while a string or a regular expression holding `/*` or `//` is kept whole, and so is a component's markup, where a channel may be read. The composition roots head their layers (`server/root`, which builds the server's objects and starts the watchers; `state/client`, which builds the page's stores; the shell's own `Workbench.svelte`), and what a whole layer shares sits at its foot (`server/core`, `state/shared` with its `words/` holding the catalogs above its `stores/` holding the shapes of the stores other stores are handed, types only, so a store that is handed one does not depend on the module that builds it, `data/model` with the facade of every type, the files of `ui` itself).

The layers: one box per layer that an import joins, `src/routes` as one box, the Node entry and the hooks under `src` as one box named entry, and one arrow per pair that imports, labelled with how many runtime imports it carries. The entry's arrow to routes is its load of the built app, which is the routes compiled. A file outside every layer that is no module, the favicon, is a box named by its folder, `assets`, with the arrow from the routes that link it; the dashed "not placed" group holds only a module no layer places that an import joins. An import the reader cannot follow is a dashed box with its file and line and a dashed arrow from the box that makes it; the source holds none today. In every diagram an arrow's count or list of calls stands on the arrow as a small box of words, and every other arrow is routed around it.

## Running it and checking it

The server runs on this machine only, bound to the loopback address, on the port `local.yml` names. `npm run dev` runs it in development, where a component's stylesheet is always served compiled, whichever the page asks for first; `npm run build` builds it and `npm run preview` serves that build. The built server is `node src/server.ts`, and its one argument is `--engine <dir>`, the directory holding the `config/` folder it reads and writes and the `HELP.md` this page is drawn from; without it that directory is `tools/oculus` itself. The server reads no environment variable of its own; the one it does read is the operating system's `SHELL`, which is the command a plain terminal starts, `/bin/zsh` when the environment names none.

The checks, from `tools/oculus`:

- `npm test` runs the unit suite over the data layer, the server, the stores, the shell and the views.
- `npm run check` runs the TypeScript and Svelte check over every file.
- `npm run lint` and `npm run format:check` hold the source to its conventions.
