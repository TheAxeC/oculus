# Oculus

Oculus is the private working surface for the research hub: one page in a browser on this machine, reading the hub's own YAML and Markdown from disk and showing it as boards, lists and documents. It writes only where a control says it writes, and only back into the same files. This page is the manual; the Config view beside it shows the files every one of these surfaces is configured by.

## The window

Down the left is the rail, and along the bottom is the status bar. Everything else is the pane tree: one tree per page, made of splits and panes, each pane a stack of tabs, each tab one view.

A control's tooltip opens when the pointer rests on it and when the keyboard brings the focus to it. A click puts it away, and it comes back once the pointer has left the control and rested on it again. Every scrolling box draws a thin scrollbar in the theme's colours, its thumb at 3:1 or more on its track, except the rail's list and the tab strips, which draw none and scroll by wheel, trackpad and their own controls.

### The rail

The rail draws one button per entry of the `rail:` list of `config/layout.yml`, each `{label, glyph, page}`, where `page` names an arrangement under `arrangements:`. A button shows its page: made from its arrangement the first time and shown as it was left after that. A browser with no saved layout starts on the first of them, and draws no page until the configuration has named it. A button is an icon; hovering it shows its page's name and the digit that reaches it. It carries one badge, in the accent: the count of the first view of its page that counts anything, in the order of the page's tabs, the arrangement's views before the page is first made. Drag a button up or down the rail to move it; right-click it (or press Shift+F10) to hide it or to open the rail list in Settings. Both rewrite `rail:`, and History undoes either. Hiding the page on screen leaves it on screen. Every view, and every hub document of the `docs` key, is listed in the Views catalogue on the Views and Settings page, under its `nav_groups` group; the groups, their order and their letters are those two keys.

In the catalogue on the Views and Settings page a click shows the page the reader was on before that page and opens the view there, where views land, which is the pane whose tab was activated last; after a load straight onto the Views and Settings page it opens on the first rail page. A catalogue the reader has moved onto a page of their own opens the view on that page. A view already open is activated where it is rather than opened twice. A shift-click opens it in a new pane to the right, on that same page, and the next shift-click joins that pane as a tab while it is still open. Dragging an entry onto a pane of the page the catalogue is on opens it there. An entry's right-click menu, or Shift+F10, offers Open on this page, which opens it in another pane of that page (beside the catalogue when the catalogue's pane is the only one), and Open beside on this page, which opens it in a new pane beside the catalogue. A view that was a tab of the catalogue's own pane moves out of it, and that pane goes on showing the catalogue. A view already open in another pane of that page is activated where it is. A drop on the catalogue's own pane goes to another pane, so the catalogue is never covered.

At the foot of the rail are Bookmarks, a menu rising from the star that lists the reader's own bookmarks from `~/.oculus/bookmarks.yml` by name, which the Files view adds and takes away, each opened as a tab of its own; Search, which opens the palette; and Update, which opens the update tray. Each is an icon with its name as the tooltip. The button of the page on screen draws its icon in the text colour with an accent bar on its left edge. The list above the foot scrolls on its own, and a fade at its top or bottom edge says more entries are past it. The appearance controls (Theme, the Text row of smaller, reset and larger, CRT, Wallpaper where the theme has one, and Icons) are in the Settings view.

Update, at the foot of the rail, opens the update tray: the four update tasks (Lit Watch, Scout, LinkedIn and Inbox), each with the date of its last run, and a Chat control that starts a portfolio-wide Claude session. A task runs the `/research-cockpit` skill as an ordinary Claude session in a terminal, so its permission prompts are answered by you in the terminal pane, which is where the tray puts you when the task starts. Setting `skip_permissions: true` under `tasks:` in `config/behavior.yml` starts them with `--dangerously-skip-permissions` instead, which lets a task run unattended and answer its own prompts; while it is on, a press asks for a confirmation first. The key under its old name, `chat.skip_permissions`, is not read, and a file still carrying it gets a finding on the Findings view naming the key that replaced it.

### Pages and the pane tree

A page is a whole working surface with a name: its own tree, its own tabs, its own arrangement. The rail's buttons switch to their pages. The Pages view on the Views and Settings page lists every page and makes, renames, shows and closes one, asking first when the page holds more than one tab, and marks a page holding unsaved text. The digits 1 to 9 show the rail page of that place.

Switching tabs keeps each tab's view as it was left: a pane keeps the view of every tab it has shown until that tab closes.

Inside a page:

- **Split.** Drag a tab onto the edge of a pane to split that pane and drop the tab into the new half. The pane menu splits without a drag.
- **Fold.** Every child of a split has one control that folds it to the split's edge and shows it again. A folded child is saved folded.
- **Maximise.** A pane can be drawn alone, the rest of the tree left where it is, and shown again from the same control.
- **Drag.** A tab moves inside its pane and to another pane, and a page's name dragged from the Pages view onto a pane's edge shows that page there.
- **Show a page.** A leaf of a page's tree can be another page, drawn where it sits with a header naming it. It is the same page, never a copy: a tab opened in it is open wherever that page shows. A page never contains itself and is drawn at most once on a screen.
- **The pane menu.** Close, maximise or restore, fold where the pane sits in a split, split right and split down, and two choices that open a list of pages in place of the menu, Move tab to page... and Show a page here..., each offered only when there is a page to offer. Back, first in the list, returns to the menu; Escape closes the whole menu.
- **Tabs past the strip's width.** The strip scrolls rather than shrinking its tabs, and tab names are drawn whole. Its two controls move the left edge to the next tab's start, or to the strip's end past the last one; a tab being shown or pressed is brought in whole, and so is the shown tab when a narrower window crosses it or takes it out of sight. A wheel or trackpad scrolls the strip freely and leaves it where it stops, so a tab may show in part at either edge.
- **How a strip is drawn.** Tabs stand edge to edge at one height, the shown tab on the pane's surface. The shown tab of the one pane a view opens into carries an accent line along its top and every other pane strip carries a plain one. A page drawn inside another page carries the pane accent only while the reader's active instance is inside that page, and a folded pane a view opens into carries the accent along its folded strip. A tab's close control shows on the shown tab and under the pointer. A tab holding text no save has taken shows a dot in the close control's place until the pointer is over it, and a screen reader hears its name followed by ", unsaved"; the Pages view marks a page holding such a tab as unsaved. The right end of a pane's strip holds the pane menu's ... opener, and, while the pane shows a tab, a split-right button; they and a strip's scroll controls are one bare icon each. A handle between panes, and between the Source view's editor and preview, shows nothing until the pointer rests on it, draws its line at once while dragged or when the keyboard reaches it, and is caught on the borders beside it as well as in its gap.

The layout is saved as it is changed, so the window comes back as it was left.

Tab and Shift-Tab are the browser's: they move the focus between the controls on the page and reach no binding of this table, except in the source tab's editor, where Tab inserts one step of indentation and Escape then Tab moves on. The rail is one stop of that order, and each strip of tabs is one stop with its pane menu the stop after it, so Tab steps past a whole strip in one press and the arrow keys move inside it; the stop stays on the tab the arrows left the focus on, and Delete closes the tab the focus is on. A tab holding text no save has taken is closed only after a confirmation, whether the close came from Delete or from the tab's own control. That text is a source tab's unsaved edit, a field of the manifest editor not yet saved, a value typed into an entry form that differs from the entry as the file holds it now, or a folder or workspace name typed into the Files view's root or workspace form and not yet added. The editor's fields, and in the Tasks, collection, Pillars, Domains, Venues and Data views the open add and edit forms with what was typed into them, and in the Files view the open bookmark form with what was typed into it and the root or workspace form with its line, are there again after the tab is switched away from and after a reload. Cancel, the view's Add or Edit control closing the form, a delete, a save and Revert let them go; a value typed into either form while its save is on its way is kept, in the form left open, and so is the text of an add form closed and opened again while its save was out; an add form closes once its entry is added only while nothing touched it since the save went, and one left open goes on writing the entry it added until its identity field is typed away from it, when it adds another; a bookmark form whose save renames its bookmark stays open over the bookmark under its new name; a save that would give an entry the name another entry of the same file already carries is refused, so no file ends up holding two entries a write cannot tell apart; and the Save control is not pressable while its own save is out. Closing a pane or a page, whether or not it asked first, lets go of what its own tabs held, as closing each tab would; a page shown inside the closed page is not closed with it and keeps what its tabs hold. In the Files view, + bookmark or a bookmark's edit control closing or moving the bookmark form lets what was typed go, and so do opening the root or workspace form over it and the bookmark it edits being taken away. A root, workspace or bookmark save answered after the reader opened another form or switched the tab away closes only the form it was sent from, and a root or workspace form closed and opened again while its add is out stays open with its line. Ctrl and Tab is not the pair that cycles a pane's tabs, because a browser keeps it for its own tabs and never hands it to a page.

Cmd-K opens the palette. With nothing typed it lists the views; a word typed searches the projects, the collection entries and the feed entries as well. Each result names what it is, View, Project, Collection or Feed, before its title. A colon starts a command: `:` and a line number moves the source tab on screen to that line, and `:language` lists every language the highlighter knows, narrowed by what follows, to repaint the tab.

The sheet itself opens with `?` and closes with `?` or Escape. The letters before a digit are the `direct_chord` of `config/layout.yml` and the `chord` of each group in `nav_groups`. A group's documents follow its views in its chord, in the catalogue's order, so the digit after the group's last view opens its first document; the directly drawn groups' documents follow the direct views under the direct chord the same way.

The status bar runs along the bottom under the rail. On the left: the machine oculus runs on (opens Status), the branch of the repository holding the active tab's file (a list of its branches to switch to, after a confirmation), how far it is behind and ahead of its upstream (pushes after a confirmation when only ahead, otherwise opens Repositories), the findings the Findings view lists (opens it), the Live HPC poll, the usage refreshers and the server connection. On the right, for a source tab: the line and column (opens the palette on `:`), the indentation (switch spaces or tabs and width, or convert the text), UTF-8, the line ending (convert it), and the language (a searchable list). Then the live sessions, the unsaved tabs (shows the first; not pressable at 0) and the bell. A right-click on the bar hides or shows any item. The bell counts unread notifications and opens the notification centre, with Clear, Clear All and Do Not Disturb, which stays on after a reload; a new notification shows as a toast for eight seconds. Notifications come from a refused rail change, a session waiting on a permission prompt or waiting for input after its turn, an update task that ran, a Live HPC job that ended, and a write that was refused or got no answer.

Every text file of the file browser opens in `source`. What counts as text is the file's own first bytes: no extension list decides it, so a script nobody gave an extension opens for editing and an archive somebody called a `.txt` is a download. Whether it can be saved is the file's mode on this machine: a file this machine locks, and one too long to have been read whole, are drawn as a read-only window under a line saying why, and neither takes a keystroke.

A single click in the tree opens a preview tab, drawn in italics: the next single click in that pane is pointed at the file it names instead of opening a second tab, so a walk through a folder leaves one tab and not twenty. Clicking the same file a second time keeps its tab; so do a double click on the tab itself, typing into it, dragging it and splitting the pane around it. A double click on the row keeps it where the tree stays on screen beside the file, in a split pane; in one pane the first click has already put the file where the tree was, so the second click lands on the tab and keeps it the same way.

## Searching the files

The Search view runs one pattern over the files of one root or of every root, and the roots are the file browser's own: the hub, the engine's config folder, the roots `sources.yml` names, and whatever the workspace in force added. Nothing outside those is reachable, and the query never leaves the machine: the search is a local process reading local files, with no index and no service of any kind.

ripgrep does the reading, the copy that comes with oculus rather than one the account happens to have installed, so the version that answers is the one the lockfile pins. What a repository ignores is skipped as ripgrep skips it, and `node_modules`, `.git` and `.svelte-kit` are skipped in every root whether or not a `.gitignore` says so. A hidden file and a hidden directory are skipped the same way, so a `.env`, a `.gitignore` and everything under a `.hidden/` folder are never opened. A file over two megabytes is not opened.

Three toggles decide what the pattern means: `word` matches whole words only, `case` matches the pattern's own upper and lower case, and `regex` reads the pattern as a regular expression rather than as text to find. Finding every reference to a name is `word` over the root that holds the code, which is what a C++ codebase needs and gets without a language server.

Typing runs nothing. Enter in the box and the Search control are the two ways a run starts, and `/` puts the cursor back in the box from anywhere in the results. A result heading opens its file at its first hit and a result row opens it at its own line, both in the source tab. The answer stops at the configured number of hits (`search.max_hits` in `behavior.yml`) and says so when it did; the reading stops there too, so a one-letter pattern over a large root costs what the cap needs and not what the root holds. Each root's search is given `search.timeout_s` seconds, and a root that fails or runs out of time is named under the count rather than passed over in silence. What a tab last found is kept with the tab, so a saved page draws its results again without running the search a second time.

## Worktrees and the merge back

The Repositories view is over every root the file browser serves, the hub and the configured roots and whatever the current workspace added, plus the workspace of every session, one repository at a time through the picker at its top, whose rows say which of them is gone in red, is no repository in blue or could not be read in amber. A repository with no commit yet is listed like any other, with its branch and its files, and its Branches section says the branch has no commit yet. A repository git could not read this time, or whose check timed out, stays in the picker and the view stays on it: its path, and its branch line while git named the branch, stay above git's reason, one line in the error colour in place of the sections. What it shows is the pushed state of that repository: nothing is polled, and a commit made in a terminal moves it within two seconds. A diff is the one thing not pushed; it is read when a pane opens it, so a repository with two hundred changed files costs the socket nothing.

A worktree is a second checkout of the same repository on a branch of its own, which is how one repository carries two pieces of work at once. The control at the bottom of a root's worktree list takes a name, says the path before anything is made, and on confirm makes `<root>/.agents/worktrees/<name>` on a new branch of that name from the repository's HEAD, then opens a shell there. A repository whose `.gitignore` does not carry `/.agents/worktrees/` is warned about in the view rather than edited: what a repository ignores is its owner's to decide, and without the rule a worktree made there becomes content of the repository.

Each worktree row opens its diff when pressed and carries four controls, shown on hover or when the row has the focus: its diff against the repository's checked-out branch, a shell started in it, the merge back, and the removal. The merge back is git's own `merge` onto the checked-out branch, a fast-forward where it can be one and a merge commit otherwise. It is refused when the repository has staged or changed paths of its own, when the repository has no branch checked out, when the name is not one of the repository's own branches, and when the branch asked for is the one checked out; a conflict is taken back with `merge --abort` and reported by the paths that conflicted, so a press on the page never leaves a repository half merged and a real conflict is taken to a terminal knowingly. An untracked file does not refuse a merge, because git carries one across untouched.

Removing the worktree is a second control and never part of the merge. It refuses a worktree holding uncommitted changes or untracked files, which is the difference from the merge: the removal takes the folder away and everything in it with it, so a file git never saw would be a file nobody can get back. The branch goes with the worktree only when no work is left only there, and the answer says when the branch was kept.

## The configuration

The files below sit in the `config/` folder of the engine, `tools/oculus/config/`, the vocabularies in its `catalogs/` folder. Every one but `local.yml`, which is this machine's own, is read on every load and merged into one map by its top-level keys, so a key moves between files without a reader noticing. The Config view shows the same list, each file with its text and a control that opens it for editing; an edit saved there is picked up and pushed to the page without a reload.

| File | What it holds |
|---|---|
| `appearance.yml` | The UI theme list with the glyph each theme is offered under, the wallpaper behind the panels, the Memories wall's folder, the CRT default and the terminal text size. |
| `behavior.yml` | Thresholds, horizons and cadences: read limits, stale days, the context window, the Live HPC settings, the audit's waiting statuses and mute list, the source editor's `editor.paint_limit_kb`, the update tasks' `tasks.skip_permissions`, the application `open.program_ext` names for each extension that may open, git and chat. |
| `catalogs/glyphs.yml` | The glyph vocabulary: each name with the ASCII stand-in, one to three characters, that a terminal theme draws in place of its icon. |
| `catalogs/icons.yml` | The line icon each glyph name is drawn as, one row per name in the glyph vocabulary. |
| `layout.yml` | How things are arranged: the rail's pages and the arrangements each starts as, the view catalogue's groups, the hub documents, the board chrome, the tab rollups and the live badges. |
| `catalogs/manifest-schema.yml` | The project.yml edit form as data: its sections, its fields, the widget each field is edited by, and where a widget takes its choices from. |
| `catalogs/meta.yml` | The tool identity: the title and the subtitle the window carries. |
| `present.yml` | The public deck the Present view draws: the deck slides, the domain themes, the tag tones and the order. |
| `sources.yml` | What the portfolio reads: the scan paths, the registry and collection files, the feeds, and the roots a local file is served from. |
| `catalogs/vocab.yml` | Words and their colours: the palette, the research domains, the status legend, the focus lanes, the venue tiers, the venue and dataset theme words and the radar buckets. |
| `local.yml` | This machine's own values, read on their own and never merged into the configuration: the hub path, the port, the ssh alias of the cluster, the Claude command, the account folders, the calendar accounts, the mail accounts and where the machine-local state is kept. |

Every user-facing word lives under `config/text/`, one file per surface, a view's file in the folder of its view group under `config/text/views/`, and is read by its dotted key. Those files merge with the rest, so a word is changed there and nowhere else. The sentences of the Findings view are `config/text/findings.yml`, one per problem the readers and the checks report, with `{0}` and `{1}` standing for the values the finding names. A sentence the file does not hold, which is every sentence while the file does not parse, is shown as its key followed by those values. A missing `config/` folder is always shown that way, as `findings.config.directory_missing`, since there is then no file to read the sentence from.

`local.yml` sits in the same `config/` folder, last in the list, and is this machine's own. Its keys are `hub`, the absolute path of the research hub; `port`, the port the server listens on; `hpc_host`, the ssh alias the Live HPC view uses; `claude_bin`, the Claude command the update tasks and the chat terminal run; `accounts`, the agent account folders the Usage view reads; `calendars`, the calendar accounts the Calendar view reads, one `provider` (`google` or `microsoft`) and one `label` each; `mail`, the mail accounts the Inbox view reads, written the same way; and `calendar_dir`, `mail_dir`, `sessions_cache`, `sessions_overrides`, `workspaces`, `bookmarks`, `notes` and `changes`, the places the calendar credential files, the mail credential files and triage notes, the session cache, the per-session overrides, the saved workspaces, the reader's own bookmarks, the scratch notes and the change log are kept in. Every key has a default, so a machine that sets only `hub` works. The whole file is read once when the server starts, and `hub`, `sessions_overrides`, `bookmarks` and `changes` are read again on every write, every wallpaper request and every file opened outside the browser, so an edit to one of those four holds from the next such call and an edit to `port`, `hpc_host`, `sessions_cache`, `workspaces`, `notes`, `claude_bin`, `accounts`, `calendars`, `calendar_dir`, `mail` or `mail_dir` holds from the next start. The file is not tracked, so no machine path is ever in the repository, and it is served and edited like the files above it: the Config view cards it with a tag saying it is this machine's own. It is the one file of the folder whose keys are checked before a save: a body the server could not read back is refused with the reason, and the file is left as it was.

## Where the data comes from

Everything on the boards is read from the research hub, whose absolute path is the `hub` key of `local.yml`. The scan rules of `sources.yml` name the folders projects sit in, and a project is any folder holding a `project.yml`. The registries, the collections and the feeds are single YAML files named in the same place; the manuscripts, READMEs and decks are Markdown in each project's own folder.

People and organisations are two of those registries. `registries/people.yml` holds one entry per human, keyed by a short slug, with a name, an `affiliations:` list whose values are keys of `registries/organisations.yml` and whose first is the primary one, a role, and optionally an ORCID, an email, links and a supervision folder; exactly one entry carries `self: true` and that is the hub's owner. A manifest's `collaborators:` and `waiting-on:` name people by those keys, and an entry of `network/joint-work.yml` names its person by `person:`. A value in any of the four that the registry does not hold is a finding on the Findings view, as is an `affiliations:` key or a funding scheme's `funder:` that names no organisation, and an organisation `kind:` outside `university`, `hospital`, `funder`, `company` and `other`. An entry still written with the one key `affiliation:` is read as a list of that one and gets a finding asking for the new name.

Nothing is copied into a database. The server reads the files, builds one snapshot of entities and relations, and pushes it over a WebSocket; it watches the hub and the config folder, so a file edited anywhere reaches the page in the same second. The long documents stay out of that snapshot and are fetched one at a time when a tab shows one.

Three things outside the hub are read as well, all of them this machine's own. The agent sessions are read from every account `accounts` in `local.yml` names: `<dir>/projects` for the transcripts and `<dir>/sessions` for which session is alive for each Claude account, and `<dir>/sessions` for the rollouts of each Codex account; two accounts whose folder is one real folder through a symlink are read once. The session cache, the per-session overrides, the saved workspaces, the reader's own bookmarks and the scratch notes are read and written under `~/.oculus`, or wherever `local.yml` puts each of them, and the launch note `~/.oculus/dispatches.json` is read there as well. The engine's own `config/` folder is read on every load and written when a file of it is saved from a source tab.

A launcher that starts an agent as a process of its own (a Codex worker, or `claude -p`) records it with `node bin/dispatch-note.mjs start --launcher <what> --label <work> --harness claude|codex --parent <session id> --cwd <dir> [--model <m>] [--transcript <path>] [--pid <n>]`, which prints an id; `transcript <id> <path>` adds the transcript once known and `end <id>` stamps the end. `--pid` names the builder's own running process, started in the background of the `sh -c` wrapper that records it, and a pid no process has is refused. The Agents view draws each record under the session named as its parent. A launched row reads done once its end is stamped. Before that, a row with a pid reads running while that process runs and done within about 15 seconds of it exiting or its pid being taken by a later process, except that a pid whose start time `ps` could not give at the start reads running for as long as that pid runs; once a scan sees the pid running another process, the launch is stamped ended in the note, so the row reads done for good; a row without one reads running while its launcher's session is live, and once the launcher's session is not live, it follows its builder's own session when the scan holds it. A launched row counts from its start to its stamped end, and to now while it runs; a row read done because its process exited shows no count until its end is stamped.

Writes into the hub go back to the files they came from: a manifest field from the editor, a collection entry from a card, a text file from a source tab. Every write is a POST carrying the page's own token, and nothing outside the hub, the engine config folder, the machine-local files under `~/.oculus` and the configured roots is ever written; what is read beyond those is the agent account folders above, and the workspace a session names when its git state or its terminal is opened.

The Inbox is read live from the reader's own mailboxes, and is the one view that writes to something outside the hub. A mail account is a row of `mail:` in `local.yml`, one `provider` (`google` or `microsoft`) and one `label`; its credentials are one file per account under `mail_dir` (`~/.oculus/mail` by default), mode 0600, whose client half the reader writes and whose refresh token the Connect control's consent brings back. A mail account is its own consent with the mail scopes alone, so a calendar account of the same mailbox never gains the right to send. A thread is on the plate when it is in the inbox and unread, or carries the `todo` label, or is unlabeled and is a single message whose subject is not an answer or a forward; a thread whose newest message is the reader's own, or is in the trash, is off it. What the poller publishes of a message is the provider's own one-line snippet and nothing more.

What each thread wants, the line about it and the answer drafted for it are the triage notes, one JSON object per thread id in `<mail_dir>/triage.json`. The card writes them, and so does `/research-cockpit inbox`, which reads the mailbox through the runner's own Gmail connector and classifies what it finds; the server polls the file every half second, so a note written from outside is on the page without waiting for the next poll. A note whose thread has left the plate is kept for thirty days and then dropped. Send puts the answer on the thread at the provider and Archive takes the thread off the inbox, each behind a confirmation naming the address the answer would reach and the account it goes from; no draft is ever created at the provider, and those two are the only writes to a mailbox oculus makes. Which address that is follows the thread's newest message: its `Reply-To` where it carries one, and its sender otherwise, which is the rule the send itself uses.

Every write through the write endpoint that changed something is recorded in the change log, `~/.oculus/changes.jsonl`: when it was made, which file it wrote, what it addressed, and the value that file held before it against the value it holds after. That is the manifest fields, the collection entries, the subtasks, the feeds, the deck and the per-session overrides, and a scaffolded idea and the two LinkedIn writes, which are recorded and cannot be taken back; a text file saved from a source tab and a scratch note go through their own endpoints and are not recorded. The History view draws the log newest first, and the control on a row puts the earlier value back through the writer the change came from, refusing when the file has changed since. `changes.keep` in `behavior.yml` is how many changes the file holds.

## Running it and checking it

The server runs on this machine only, bound to the loopback address, on the port `local.yml` names. `npm run dev` runs it in development, where a component's stylesheet is always served compiled, whichever the page asks for first; `npm run build` builds it and `npm run preview` serves that build. The built server is `node src/server.ts`, and its one argument is `--engine <dir>`, the directory holding the `config/` folder it reads and writes and the `HELP.md` this page is drawn from; without it that directory is `tools/oculus` itself. The server reads no environment variable of its own; the one it does read is the operating system's `SHELL`, which is the command a plain terminal starts, `/bin/zsh` when the environment names none.

The checks, from `tools/oculus`:

- `npm test` runs the unit suite over the data layer, the server, the stores, the shell and the views.
- `npm run check` runs the TypeScript and Svelte check over every file.
- `npm run test:browser` drives the built page in a real browser, which is where the layout, the drag, the keyboard and the sanitiser are exercised.
- `npm run lint` and `npm run format:check` hold the source to its conventions.
