# Oculus

Oculus is the private working surface for the research hub: one page in a browser on this machine, reading the hub's own YAML and Markdown from disk and showing it as boards, lists and documents. It writes only where a control says it writes: back into the same files, and, from the Files view's right-click menu, files and folders under the roots the view serves. This page is the manual; the Settings view on the System page lists the files every one of these surfaces is configured by, with the options in them.

## The window

Down the left is the rail, and along the bottom is the status bar. Everything else is the pane tree: one tree per page, made of splits and panes, each pane a stack of tabs, each tab one view.

A control's tooltip opens when the pointer rests on it and when the keyboard brings the focus to it. A click puts it away, and it comes back once the pointer has left the control and rested on it again. Every scrolling box draws a thin scrollbar in the theme's colours, its thumb at 3:1 or more on its track, except the rail's list and the tab strips, which draw none and scroll by wheel, trackpad and their own controls.

### The rail

The rail draws one button per entry of the `rail:` list of `config/layout.yml`, each `{label, glyph, page}`, where `page` names an arrangement under `arrangements:`. As shipped there are eleven, top to bottom: Focus, Sessions, Projects, Incoming (the Inbox, Lit Watch, Position Leads, LinkedIn and Literature search views beside the Calendar), Explorer (Files, Repositories and Search, with an empty pane beside them), Academic Life, Pillars, References, Present, Help (this manual and the HPC how-to beside Research approach, Agent approach, Data map and the Memories wall) and System (Settings, Account setup, the Views catalogue, Pages, Status, Findings, Audit, History, the gallery and Processes). Every listed view sits on exactly one of these pages, in the pane its arrangement gives it, except Live HPC and Usage, which sit in the float docked at the right edge of the window and are on every page. The Views catalogue lists each page's views under the page's name, the Help page's under Help, reached by `h`. A button shows its page: made from its arrangement the first time and shown as it was left after that. A browser with no saved layout starts on the first of them, and draws no page until the configuration has named it. A button is an icon; hovering it shows its page's name and the digit that reaches it. It carries one badge, in the accent: the count of the first view of its page that counts anything, in the order of the page's tabs, the arrangement's views before the page is first made. Drag a button up or down the rail to move it; right-click it (or press Shift+F10) to hide it, to reset its page to its arrangement, or to open the rail list in Settings. Hiding and moving rewrite `rail:`, and History undoes either. Reset is offered once the button's page has been made, and asks first: the question names the page, and then each of its tabs holding text no save has taken is asked about as closing it would be, one at a time; a no to any leaves the page as it was. It rebuilds the page from its arrangement, under the button's name, closing every tab the page held. Hiding the page on screen leaves it on screen. Every view, and every hub document of the `docs` key, is listed in the Views catalogue on the System page, under its `nav_groups` group; the groups, their order and their letters are those two keys. A document tab saved at a path the `docs` list no longer holds follows the entry carrying its name, or closes into the tab already showing that entry; one that matches no entry names the path it asked for.

In the catalogue on the System page a click shows the page the reader was on before that page and opens the view there, where views land, which is the pane whose tab was activated last; after a load straight onto the System page it opens on the first rail page. A catalogue the reader has moved onto a page of their own opens the view on that page. A view already open is activated where it is rather than opened twice. A shift-click opens it in a new pane to the right, on that same page, and the next shift-click joins that pane as a tab while it is still open. Dragging an entry onto a pane of the page the catalogue is on opens it there. An entry's right-click menu, or Shift+F10, offers Open on this page, which opens it in another pane of that page (beside the catalogue when the catalogue's pane is the only one), and Open beside on this page, which opens it in a new pane beside the catalogue. A view that was a tab of the catalogue's own pane moves out of it, and that pane goes on showing the catalogue. A view already open in another pane of that page is activated where it is. A drop on the catalogue's own pane goes to another pane, so the catalogue is never covered.

At the foot of the rail are Bookmarks, a menu rising from the star that lists the reader's own bookmarks from `~/.oculus/bookmarks.yml` by name, which the Files view adds and takes away, each opened as a tab of its own; Search, which opens the palette; and Update, which opens the update tray. Each is an icon with its name as the tooltip. The button of the page on screen draws its icon in the text colour with an accent bar on its left edge. The list above the foot scrolls on its own, and a fade at its top or bottom edge says more entries are past it. The appearance controls (Theme, Code theme, the Text row of smaller, reset and larger, CRT, Wallpaper where the theme has one, and Icons) are in the Settings view.

Update, at the foot of the rail, opens the update tray: the four update tasks (Lit Watch, Scout, LinkedIn and Inbox), each with the date of its last run, and a Chat control that starts a portfolio-wide Claude session. A task runs the `/research-cockpit` skill as an ordinary Claude session in a terminal, so its permission prompts are answered by you in the terminal pane, which is where the tray puts you when the task starts. Setting `skip_permissions: true` under `tasks:` in `config/behavior.yml` starts them with `--dangerously-skip-permissions` instead, which lets a task run unattended and answer its own prompts; while it is on, a press asks for a confirmation first. The key under its old name, `chat.skip_permissions`, is not read, and a file still carrying it gets a finding on the Findings view naming the key that replaced it.

### Pages and the pane tree

A page is a whole working surface with a name: its own tree, its own tabs, its own arrangement. The rail's buttons switch to their pages. The Pages view on the System page lists every page as one row of the explorer's size: press a row to show its page, and hover or focus it for Rename and Close, Close asking first when the page holds more than one tab. The page on screen is the bold row with a check, a page of a rail button names its key after its name, and a page holding unsaved text carries the unsaved dot at the row's end. A page of a rail button also carries Reset to its arrangement, the same reset as the rail button's menu. Settings holds Reset all pages, which rebuilds every page of a rail button from its arrangement, removes the pages of buttons the rail no longer has and puts the floats of `config/layout.yml` back in place of the floats you have, leaving the pages you made yourself alone; it asks first, naming each page it rebuilds, each it removes and each float it replaces, then asks about each tab of those pages holding unsaved text as closing that tab would, one at a time, and a no to any of them ends the reset with nothing changed; it says so when there is nothing to reset. The digits 1 to 9 show the rail page of that place.

Switching tabs keeps each tab's view as it was left: a pane keeps the view of every tab it has shown until that tab closes.

Where an opened tab lands. A view opened for something (a project, a person, a deposit, a manifest edit, a hub document, a file, a source file, a diff, a merge, a note, a customization file) never covers the tool views of the page it is opened on. It lands, in this order: in the pane that received the last such tab on this page, while that tab is still there; in the pane you are in, when that pane already holds such tabs; in an empty documents pane, then an empty terminals pane; in a pane holding such tabs and nothing else; and otherwise in a new pane split off to the right of the pane you are in, which the next one then joins. A pane holding a tool view takes one only when you are in it and it already holds opened tabs. A tool view that asks for a tab (the Search view's Replace Preview) is never landed in: its pane is taken out of every step above, and when no other pane takes the tab a new pane is split off to the right of it. A tab of that document already open anywhere on the page is activated where it is, and a maximised pane of tools is restored first so the landing pane shows. The rule does not move tool views. An empty pane says Files and documents you open on this page appear here; the Explorer page carries one beside Files, Repositories and Search. Closing or dragging out the last tab of a pane that held a view opened for something leaves the pane empty, a documents pane, and the last tab of a pane that was a Terminal tab leaves an empty terminals pane saying Terminals you start from this pane's menu appear here. A page keeps never more than one empty pane, a documents pane or a terminals pane, so a pane emptied while another empty pane is on the page closes, and Close pane removes a kept one. A pane whose last tab was a tool view closes, and the next view opened for something lands in an empty pane if there is one, else splits a new pane off to the right. Inside the pane it lands in, a new tab opens to the right of the active tab, after the pinned tabs when the active tab is pinned. Closing the shown tab shows the tab that was shown before it and is still open, and the order the tabs were shown in is kept with the layout. How a single click opens a preview tab, where a new tab opens and how many tabs a pane holds (no limit) are VS Code's defaults and have no setting.

Inside a page:

- **Split.** Drag a tab onto the edge of a pane to split that pane and drop the tab into the new half. The pane menu splits without a drag.
- **Fold.** Every child of a split has one control that folds it to the split's edge and shows it again. A folded child is saved folded.
- **Maximise.** A pane can be drawn alone, the rest of the tree left where it is, and shown again from the same control.
- **Float.** A pane can float over every page: Float in the pane menu or in the right-click menu of the pane's strip floats the pane, and a tab dragged with Alt held (Option on a Mac) floats at the pointer wherever it is let go, an outline showing where. A floating pane has an orange border, stays on screen when the rail switches pages and while a pane of the page is maximised, and holds one pane of tabs, so it has no split, fold or maximise. Drag the empty part of its tab strip to move it and its edges or corners to resize it; let go within 24 pixels of the area's left, right or bottom edge to dock it there. A docked float is a strip along that edge with a handle on its inner edge that sets its size, by drag or by the arrow keys. Its menus offer Dock Left, Dock Right and Dock Bottom (not for the edge it is on), Float on a docked float, which floats it again, Return to Page, which puts its tabs back into the page on screen as a new pane split off the right of the largest pane, and Close, which closes the float and asks as the pane close does. One float is docked to an edge, so docking a second there joins its tabs to the first. A float disappears when its last tab goes, is placed by fractions of the window, so it scales with the window and may lie over the rail and the status bar, and answers the keyboard as a pane does. Live HPC and Usage start as a float docked at the right edge, and Reset all pages puts the floats of `config/layout.yml` back.
- **Drag.** A tab moves inside its pane and to another pane, and a page's row dragged from the Pages view onto a pane's edge shows that page there. A row dragged and let go over itself shows nothing.
- **Show a page.** A leaf of a page's tree can be another page, drawn where it sits with a header naming it. It is the same page, never a copy: a tab opened in it is open wherever that page shows. A page never contains itself and is drawn at most once on a screen.
- **The pane menu.** Close, maximise or restore, fold where the pane sits in a split, split right and split down, Float while the pane shows a tab, and two choices that open a list of pages to the side, Move tab to page... and Show a page here..., each offered only when there is a page to offer. ArrowRight or Enter on one of them opens its list, and ArrowLeft or Escape in that list goes back to the choice; Escape in the menu closes it. In any menu the arrow keys, Home and End move through the choices, and typing the start of a choice's name goes to it.
- **Right-click menus.** A right-click on the empty part of a pane's tab strip, or anywhere in an empty pane, offers Open File... (the palette, as Cmd-K opens it), New Text File (an untitled text opened in a source tab of that pane; its first Save asks for a folder, chosen among the workspace's served folders with the first selected, and for a name, which may hold folders that are made, and makes the file there; a name that leaves the folder is refused), Split Up, Split Down, Split Left, Split Right and Float while the pane shows a tab, Lock Group or Unlock Group (a locked pane takes no tab opened from elsewhere, though a tab can still be dragged onto it, and a lock mark at the right end of its strip unlocks it when pressed; a float's pane is locked and unlocked the same way), Tab Bar (Multiple Tabs, Single Tab or Hidden) and Editor Actions Position (Tab Bar, named Title Bar while the tab bar is hidden, or Hidden; the choice in force carries a check mark in both submenus), which write `show_tabs` and `editor_actions` of `appearance.yml` and can be set in Settings, with Hidden also taking the `...` off the pane of a float, Close while the page has more than one pane (asking first as the pane menu's Close does), and New Terminal. A right-click on a tab opens the tab's menu, VS Code's in its groups and words: Close, Close Others, Close to the Right, Close Saved and Close All (each asks first when a tab it closes holds unsaved text or a running program; a pinned tab is closed by Close alone); for a tab showing a file, Copy Path, Copy Relative Path, Reveal in Finder, Show in Files, Open Timeline, Select for Compare and Compare with Selected; Keep Open (enabled on a preview tab) and Pin or Unpin; and Split Right with a Split & Move submenu. A right-click on any other part of the page that has no menu of its own, a blank area included, shows no menu at all; the browser's own menu stays inside a text box, the code editor and the terminal. Every text box offers Undo, Redo, Cut and Copy over a selection, Paste and Select All, a read-only one only Copy and Select All; rendered Markdown and a document framed in the Document view offer Copy over a selection, Copy Image over an image and Open Image over an image of the hub, and nothing where there is neither. Shift-F10 or the context menu key opens the menu of the row or control that has the focus, and a line between items separates their groups. A right-click on a row of the Files view offers the file operations listed under the `files` view in the table below.
- **Tabs past the strip's width.** The strip scrolls rather than shrinking its tabs, and tab names are drawn whole. Its two controls move the left edge to the next tab's start, or to the strip's end past the last one; a tab being shown or pressed is brought in whole, and so is the shown tab when a narrower window crosses it or takes it out of sight. A wheel or trackpad scrolls the strip freely and leaves it where it stops, so a tab may show in part at either edge.
- **Wrapped tabs.** With `wrap_tabs: true` in `appearance.yml` (a toggle under Appearance in Settings, off by default) a strip of `show_tabs: multiple` puts the tabs it cannot fit on more rows instead of scrolling one row, and the pane's actions stay at the end of the last row; a tab dropped on a wrapped strip lands by the row under the pointer as well as by its place along the row. The key is ignored under `single` and `none`.
- **Pinned tabs.** Pin in a tab's right-click menu, Pin Editor in the palette (listed with Cmd-K Shift+Enter, for the active tab of the pane that last held the focus), or a drag into the pinned tabs, moves a tab to the start of its pane's strip, where it shows a pin in place of its close control (a press on the pin unpins; a pinned tab holding unsaved text shows its dot). Unpin, Unpin Editor or a drag out of the pinned tabs puts it back. A pinned tab keeps its pin when its pane floats, when it moves to another page and when its pane splits, and stays open through Close Others, Close to the Right, Close Saved, Close All and the Close All of Open Editors. Delete on a focused pinned tab closes nothing and shows the first tab that is not pinned.
- **The path over a file tab.** A tab showing a file (a source tab, a document, a PDF or another file view) has the file's path drawn under the strip as a breadcrumb in place of a file-name row: the root, each folder, the file. A press on the root or a folder shows the Files view at that folder, and a press on the file shows it in the Files view. With `show_tabs: single` the breadcrumb sits in the strip's row beside the tab, and with `none` it has a row of its own. When the bar is narrower than the path and the file's actions together, the path is cut from the left and the actions stay whole. The tab's tooltip holds the file's whole path with the home folder written `~`. A file tab draws its file's icon before its name, the one the Files tree draws for that file, in the strip and in Open Editors; a tab showing no file, a Terminal tab, a Files tab opened on a folder and a LaTeX tab among them, draws its view's icon, and a Markdown preview tab draws the preview's icon, as VS Code's does.
- **A file tab's actions.** The right end of the tab's breadcrumb bar carries the tab's own actions as icon buttons, each where it applies: Save (a source tab that may be written; disabled while nothing is unsaved) and Revert File (shown while the tab holds unsaved text), then Add Bookmark or Remove Bookmark (the star, filled when the file is bookmarked; a file under a served root), Open in Program (a file whose extension `open.program_ext` names an application for; none of `.md`, `.png`, `.pdf` or `.html` has one as shipped), Open Preview (a Markdown source tab not read at a commit; it opens the file's preview tab, kept, in the same pane), Open Preview to the Side (the same tab, which opens the file's preview tab in a new pane to the right, or shows the one already open), Submit Job (a `.slurm` file on disk under a served root; it saves unsaved text, then asks one question that names the project's code folder and the cluster folder it is copied to, how many files and how large, the rsync arguments and the `sbatch` command run over ssh, and on Submit sends the code and queues the job, then opens Live HPC; a script that never names `/local/$SLURM_JOB_ID` gets a warning first and its button reads Submit Anyway) and Toggle Blame (a source tab over a file of a repository, and the tab of a file at HEAD or in the index). A picture, a PDF, a download, an HTML document and a Doc carry the star and Open in Program where they apply, and a Markdown preview carries them with Open Source, which opens the file's source tab, kept, in the same pane. A refused bookmark write is said beside the star. The tab row's right end carries only Split Right and the `...` opener. The rendered half of a Markdown source tab and word wrap are palette actions, listed while the tab is on screen and each applies: File: Save and File: Revert File (a tab that may be written), Git: Toggle Git Blame Editor Decoration (a file in a repository, a version at HEAD or in the index included), Markdown: Toggle Rendered Half (a Markdown tab that may be written, off until turned on and kept per tab), Markdown: Open Preview to the Side, Slurm: Submit Job (a `.slurm` file on disk), and View: Toggle Word Wrap (Alt+Z). Cmd+S (Ctrl+S off macOS) saves the source tab on screen wherever the focus is and never opens the browser's own save dialog. The tab's right-click menu offers Add Bookmark or Remove Bookmark for a served file that is not read at a commit, Open in Browser Tab for a picture, a PDF, a download or an HTML document, and Open in Program where `open.program_ext` names an application for the file. The line saying what a save did stays in the source tab, under the editor.
- **How a strip is drawn.** Tabs stand edge to edge at one height, the shown tab on the pane's surface. The shown tab of the one pane a view opens into carries an accent line along its top and every other pane strip carries a plain one. A page drawn inside another page carries the pane accent only while the reader's active instance is inside that page, and a folded pane a view opens into carries the accent along its folded strip. A tab's close control shows on the shown tab and under the pointer. A tab's label is 13 px, its close control and pin 16 px, and a pane strip that does not hold the focus is drawn dimmer than the one that does. A tab holding text no save has taken shows a dot in the close control's place until the pointer is over it, and a screen reader hears its name followed by ", unsaved"; the Pages view marks a page holding such a tab as unsaved. The right end of a pane's strip holds, while the pane shows a tab, a split-right button, and the pane menu's ... opener; they and a strip's scroll controls are one bare icon each. At a large text size or in a narrow pane the shown tab keeps its title and its close control: a strip too narrow for its scroll arrows beside the tabs draws none, and its actions move to a line under the tabs, before a title is cut, so a pane about 100 px wide still shows the shown tab and its close control. A handle between panes, and between the Source view's editor and preview, shows nothing until the pointer rests on it, draws its line at once while dragged or when the keyboard reaches it, and is caught on the borders beside it as well as in its gap.

The layout is saved as it is changed, so the window comes back as it was left.

Tab and Shift-Tab are the browser's: they move the focus between the controls on the page and reach no binding of this table, except in the source tab's editor, where Tab inserts one step of indentation; an Escape that closes nothing of the editor's, such as the find box or a suggestion, lets the next Tab or Shift-Tab move on. The rail is one stop of that order, and each strip of tabs is one stop with its pane menu the stop after it, so Tab steps past a whole strip in one press and the arrow keys move inside it; the stop stays on the tab the arrows left the focus on, and Delete closes the tab the focus is on. A tab holding text no save has taken is closed only after a confirmation, whether the close came from Delete or from the tab's own control. That text is a source tab's unsaved edit, a field of the manifest editor not yet saved, a value typed into an entry form that differs from the entry as the file holds it now, or a folder or workspace name typed into the Files view's root or workspace form and not yet added. The editor's fields, and in the Tasks, collection, Pillars, Domains, Venues and Data views the open add and edit forms with what was typed into them, and in the Files view the open bookmark form with what was typed into it and the root or workspace form with its line, are there again after the tab is switched away from and after a reload. Cancel, the view's Add or Edit control closing the form, a delete, a save and Revert let them go; a value typed into either form while its save is on its way is kept, in the form left open, and so is the text of an add form closed and opened again while its save was out; an add form closes once its entry is added only while nothing touched it since the save went, and one left open goes on writing the entry it added until its identity field is typed away from it, when it adds another; a bookmark form whose save renames its bookmark stays open over the bookmark under its new name; a save that would give an entry the name another entry of the same file already carries is refused, so no file ends up holding two entries a write cannot tell apart; and the Save control is not pressable while its own save is out. Closing a pane or a page, whether or not it asked first, lets go of what its own tabs held, as closing each tab would; a page shown inside the closed page is not closed with it and keeps what its tabs hold. In the Files view, + bookmark or a bookmark's edit control closing or moving the bookmark form lets what was typed go, and so do opening the root or workspace form over it and the bookmark it edits being taken away. A root, workspace or bookmark save answered after the reader opened another form or switched the tab away closes only the form it was sent from, and a root or workspace form closed and opened again while its add is out stays open with its line. Ctrl and Tab is not the pair that cycles a pane's tabs, because a browser keeps it for its own tabs and never hands it to a page.

Cmd-K opens the palette. With nothing typed it lists the views; a word typed searches the projects, the collection entries and the feed entries as well. A word matches fuzzily, its letters in order but not necessarily together, so `rpls` finds RAW-PLS, and the letters it matched are marked in each result's title; a result whose title matched comes before one that matched only elsewhere. The arrow keys, Home and End move through the results and Enter opens the one selected; the keyboard goes to the tab it opens, which becomes the page's active tab. Each result names what it is, View, Project, Collection, Feed or Editor, before its title. Cmd-K and Ctrl-K open the palette from inside the source tab's editor too, and while a source tab is on screen the palette also lists the editor's own Cmd-K commands, such as Add Line Comment or Fold All, each named Editor with its old keys beside it; choosing one runs it in the tab. Pin Editor and Unpin Editor are among them, with Cmd-K Shift+Enter beside them, and act on the active tab of the pane that last held the focus. A result whose title is longer than the row is cut with an ellipsis on one line, and its tooltip holds the whole title. A colon starts a command: `:` and a line number moves the source tab on screen to that line, and `:language` lists Auto Detect (the language the file name gives), Configure File Association for the file's ending (a second list whose choice is written into the `languages:` map of `sources.yml`, undoable in History), Configure the language's settings (opens Settings on `editor.languages`) and then every language the highlighter knows, each with its name in brackets and the one in force marked Configured Language, narrowed fuzzily by what follows with the matched letters marked, to repaint the tab.

The sheet itself opens with `?` and closes with `?` or Escape. The letters before a digit are the `direct_chord` of `config/layout.yml` and the `chord` of each group in `nav_groups`. A group's documents follow its views in its chord, in the catalogue's order, so the digit after the group's last view opens its first document; the directly drawn groups' documents follow the direct views under the direct chord the same way. Every view now sits in a group with a letter of its own, so the direct chord reaches nothing and the key table has no row for it; a group that names no `chord` gives it entries again.

The status bar runs along the bottom under the rail. On the left: the machine oculus runs on (opens Status), the branch of the repository holding the active tab's file (a list of its branches to switch to, after a confirmation), how far it is behind and ahead of its upstream (after a confirmation, pushes when the branch is only ahead and otherwise pulls and then pushes; a branch with no upstream shows Publish Branch in its place), the findings the Findings view lists (opens it), the Live HPC poll, the usage refreshers and the server connection. On the right, for a source tab over a file of a repository: the caret line's blame, whether or not Git: Toggle Git Blame Editor Decoration is on (opens its commit in the Repositories graph; a tab over a file at HEAD or in the index shows its blame in the gutter only, since VS Code shows the status bar's blame for a working file alone), the line and column (opens the palette on `:`), the indentation (switch spaces or tabs and width, or convert the text), UTF-8, the line ending (convert it), and the language (a searchable list that starts with Auto Detect, Configure File Association and Configure the language's settings, then the languages). Then the live sessions, the unsaved tabs (shows the first; not pressable at 0) and the bell. A right-click on the bar hides or shows any item. The bell counts unread notifications and opens the notification centre, with Clear, Clear All and Do Not Disturb, which stays on after a reload; a new notification shows as a toast for eight seconds. Notifications come from a refused rail change, a session waiting on a permission prompt or waiting for input after its turn, an update task that ran, a Live HPC job that ended, and a write that was refused or got no answer.

## Searching the files

The Search view runs one pattern over the files of one root or of every root, and the roots are the file browser's own: the hub, the engine's config folder, the roots `sources.yml` names, and whatever the workspace in force added. Nothing outside those is reachable, and the query never leaves the machine: the search is a local process reading local files, with no index and no service of any kind.

ripgrep does the reading, the copy that comes with oculus rather than one the account happens to have installed, so the version that answers is the one the lockfile pins. What a repository ignores is skipped as ripgrep skips it, and `node_modules`, `.git` and `.svelte-kit` are skipped in every root whether or not a `.gitignore` says so. A hidden file and a hidden directory are skipped the same way, so a `.env`, a `.gitignore` and everything under a `.hidden/` folder are never opened. A folder chosen with Find in Folder... in the Files view is the exception: it is searched even when it is hidden or ignored itself, as ripgrep searches a path it is given, while the files and folders inside it follow the rule above, so a hidden file in it and an entry an ignore file names are still skipped, and the Search view says "In <root>/<folder>" above the box with a control that clears the scope. A file over two megabytes is not opened.

Three toggles decide what the pattern means: `word` matches whole words only, `case` matches the pattern's own upper and lower case, and `regex` reads the pattern as a regular expression rather than as text to find. Turning one over while results are shown, or while a search is running, runs the search again under the new toggles, so the preview and Replace use the toggles on screen. Finding every reference to a name is `word` over the root that holds the code, which is what a C++ codebase needs and gets without a language server. `case` is the only control over case: there is no smart case (an editor's `search.smartCase`, which matches case only when the pattern holds a capital), so a pattern is matched without regard to case until `case` is on. The files and the hits come in the order ripgrep answers them, which is not sorted, and the view lists them as they came.

Typing runs nothing. Enter in the box and the Search control are the two ways a run starts, and `/` puts the cursor back in the box from anywhere in the results. A result heading opens its file at its first hit and a result row opens it at its own line, both in the source tab. The answer stops at the configured number of hits (`search.max_hits` in `behavior.yml`) and says so when it did; the reading stops there too, so a one-letter pattern over a large root costs what the cap needs and not what the root holds. Each root's search is given `search.timeout_s` seconds, and a root that fails or runs out of time is named under the count rather than passed over in silence. What a tab last found is kept with the tab, so a saved page draws its results again without running the search a second time. A hit is one match, so a line holding two matches is two rows, each with its own Replace and Dismiss.

Replace works as the editor's Search view does. The chevron at the start of the query row shows or hides the replace row: the replace box, the `AB` toggle (Preserve Case) and Replace All. Whether the row is shown, the replace text and Preserve Case are kept with the tab, and so are the last twenty texts each box ran, which Up and Down in the box walk, newest first. Enter in the replace box runs the search as Enter in the query box does, and Cmd+Alt+Enter in either box is Replace All. Cmd+Shift+F opens the Search view with the cursor in its query box and Cmd+Shift+H opens it with the replace row shown and the cursor in the replace box. While the row is shown each hit row draws the matched text struck through and the text that would replace it, which follows the replace text and Preserve Case as they are typed without a new run, and the count line says how many hits would be replaced in how many files. A hit offers Replace and a file heading Replace All in that file, under the pointer and on the focused row; Cmd+Shift+1 runs the one the focused row offers. Every hit and every file offers Dismiss, with Delete (Cmd+Backspace on macOS) on the focused row, which takes it out of the results without writing, and Replace All then leaves it out. After a Replace or a Dismiss the focus moves to the next row. After a Replace the hits left in a written file are read from the file as it is now, so each keeps the line and place the file has for the next Replace; a hit you dismissed stays out while its line is as it was, and comes back when the replace changed its line; a file whose hits could not be read keeps its row with "Search again to see this file's hits." A root that ran out of time or could not be searched is named on a line of its own under the count ("claude ran out of time.", "No answer from claude: ripgrep could not search it."), and the count says "cut at 500" only when the number of hits was reached. Replace All asks first, "Replace 12 occurrences across 3 files with 'bar'?", and when the search stopped at the configured number of hits it says that only the hits listed are replaced. One replace runs at a time. What a Replace All over the whole answer came to ("Replaced 12 occurrences across 3 files with 'bar'.") takes the place of the count line until the results next change (a Replace, a Dismiss, a new run or an edit of the query); a Replace of a hit or of a file leaves the count line, and a replace that fails says why. Pressing a hit while the replace row is shown opens its Replace Preview, a diff pane with the file as it is on the left and the file with this tab's replacements on the right, one pane per file, opened beside the Search view (in the pane of the other opened tabs, or in a new pane to the right of the Search view's, which the next previews land in) and never over it; a dismissed hit stays unreplaced in it, and after a Replace the next hit opens in the same preview.

The replace text is read as the editor reads it. In regular-expression mode `$0` is always the whole match and `$1` to `$99` are always the groups of the pattern, and `\n` is a newline, `\t` a tab and `\\` a backslash. `$<name>` (a named group), `$&` (the whole match) and `$$` (a dollar sign) take effect only when the replace text also holds a numbered reference, as in VS Code: `[$<name>]$1` writes the named group and the first group, and `$<name>` alone is written as typed. A group number the pattern lacks is written as typed. `\u`, `\U`, `\l` and `\L` placed directly before a group reference upper-case or lower-case the first character or the whole of that group's text. Without `regex` the replace text is written exactly as typed. Preserve Case gives the replacement the capitals of the match it replaces. In a file with Windows line ends a newline the replace text writes is written as `\r\n`. A file that a source tab holds with unsaved text is left out of a replace and named in the line that says what was done, since the search reads the disk and not the tab; a clean source tab on a replaced file reads the file again. The server decides what is written: it runs the search again over each file, refuses a file in which a named match is no longer where the search found it (`changed`), a file its mode locks (`denied`), a file that is not text (`binary`), a file over the save limit, `config/local.yml` and a file or a replace text holding one of the four private-use characters U+E000 to U+E003 that the search uses to read its groups (`marker`). A replace stops at the first refused file, names it and the files before it that were written (their hits are read again as well), and keeps a copy of every file it writes. The whole replace is one record of the History view, "Replaced in 3 files", with an Undo that writes each file back from its copy while every file still holds what the replace left, and, after that undo, a redo; the Timeline of the Files view lists those copies as File Replaced.

## Project commands

A repository has project commands: named lines that run in its folder, drawn as a row of buttons and run as terminals. They come from three places, listed in this order. The first is the repository's own file, `.oculus/commands.yml`, a list `commands:` of entries with `name`, `run`, an optional `cwd` (a folder inside the repository, the repository by default), an optional `depends_on` (a list of command names that run first) and an optional `default` (`build` or `test`). The second is the commands saved through the form, kept in `~/.oculus/commands.json` under the repository's absolute path. The third is what oculus finds in the repository: the presets of `CMakePresets.json` and `CMakeUserPresets.json`, hidden ones left out (a configure preset is named `cmake: <preset>`, a build preset `cmake build: <preset>` and a test preset `ctest: <preset>`), the scripts of `package.json` (named `npm: <script>`, and run with `pnpm` when `pnpm-lock.yaml` is there and `yarn` when `yarn.lock` is), and the targets of the top `Makefile` (named `make: <target>`, without pattern rules, special targets and variable assignments). A name can be held by two sources of one repository, the file and the saved commands: both are listed, each button and each menu item names its source beside the name (`build (file)`, `build (saved)`), and a press runs the command of the source it names. The default keys run the default build or test of the repository and name no source. The form refuses to save a name that `.oculus/commands.yml` or a found command already holds. A field of the wrong type, an empty or repeated name, a folder outside the repository and a second `default` of one kind are findings: the entry or the default is left out, and the bar marks the findings with a warning whose tooltip names each file and field.

Where they are drawn. The Repositories view draws a repository's commands above its commit box; a project card draws the same bar below its chips when the project's folder is a repository; and the Files view's right-click menu on a root or a folder that is a repository has a Run Command submenu, whose commands are read when the menu opens. A bar shows five buttons and puts the rest in an overflow menu, whose Manage submenu holds the same menus as the buttons. A button's tooltip is the command's line and where it was read from. A right-click on a button opens Edit and Delete for a saved command, and Open File at its entry (`.oculus/commands.yml`, `package.json`, the presets file or the Makefile) for a command from a file or one that was found. Add Command... opens the form: the name, the line, an optional folder, an optional list of the commands it depends on and an optional default; it saves for that repository.

The run. A press starts one terminal named after the command. When the command has `depends_on`, the terminal runs each command of the chain once, in the order listed, each after the one before it, and stops at the first that fails; a cycle, a command that depends on itself and a name no command has are refused with the names. The terminal is shown and selected. These placeholders take their values from the source tab on screen, or, when the command is started from a button in another view, from the source tab whose editor had the focus last: `${file}`, `${fileDirname}`, `${fileBasename}`, `${fileBasenameNoExtension}`, `${lineNumber}` and `${selectedText}` (its file, the line of its caret and its selected text), and `${workspaceFolder}` from the repository. A value reaches the command as an environment variable and is never read as shell text: each placeholder in the line becomes `${OCULUS_ARG_1+"$OCULUS_ARG_1"}`, `${OCULUS_ARG_2+"$OCULUS_ARG_2"}` and so on, one number per placeholder name, and the terminal starts with each variable set to its value, so a selection holding blanks, quotes, `;` or `$(...)` arrives whole as those characters wherever the line writes the placeholder: bare, inside double quotes, in a here-document or inside `$(...)`. Inside single quotes that text is printed as written, as any `$NAME` is there, and a line that evaluates text itself (`eval`, `sh -c`, and `$((...))` arithmetic in bash) runs the value as code, which the approved line shows. A placeholder the page has no value for refuses the run and names it; any other `${...}` is left as written. Before each command the terminal prints a line of a token minted for that run and the command's name, by which its output is read.

Approval. A command from a file of the repository or a found one runs only after you approved its exact text on this machine. The first press asks, listing every line of the command's chain in run order, each with its folder when it is not the repository's, with Approve and Run and Cancel. The chain is approved as one text together with the repository's real path, kept in the file the `approvals` key of `local.yml` names, so a changed line, folder or dependency asks again, a command that gains a dependency asks again for the whole chain, and the same text in another repository asks again. When the file is the default one, `~/.oculus/approvals.json`, its folder is made private to you (mode 0700) when it is looser; a file the `approvals` key puts elsewhere leaves its folder as it is. Approvals given before the text took this form (the repository's path and the whole chain, in place of each command alone) ask again. A command saved through the form is text you wrote into oculus and runs without the question.

The result. A command's terminal stays in its tab after the line ends, with a green check for exit code 0 and a red cross otherwise; the server looks at a running command's terminal every five seconds, so the result shows at the next look. Rerun, on an ended terminal's menu and bar, runs the same line again in the same terminal and is refused while the line runs. Restart, on the same menu and bar, stops a running line and runs it again after a confirmation that names the process, and on an ended terminal does what Rerun does. A line in the output of the form `file:line:column: error: message` or `file:line: warning: message` has its `file:line:column` underlined under the pointer when the file exists under the repository (relative names are read from the command's folder), and a click opens it in a source tab at that line. The errors of a command's output are kept as the command's diagnostics and replaced when it runs again; a terminal no pane shows when its line ends is read once from the text of its tmux pane, and in a chain a relative file name is read from the folder of the command that printed it.

Cmd+Shift+B (Ctrl+Shift+B off macOS) runs the default build and Cmd+Alt+T (Ctrl+Alt+T) the default test of the repository holding the file of the source tab on screen. With no such tab, no repository around the file or no command marked `default` for the key, the status bar says which is missing and nothing runs.

## Source Control

The Repositories view and a session's Changes panel are Source Control as VS Code draws it, over the repositories oculus knows. Every write runs from a press on the page, except the automatic fetch described under Pull, push, fetch, sync and publish, and every one that throws work away or reaches a remote asks first, except Fetch.

### Committing

The commit box sits above a repository's changes, in the Repositories view and in a session's Changes panel alike, and both hold one message per repository, so a message typed in one is there in the other. The field opens one line high and grows with what is typed up to ten lines; the button under it is Commit while anything is staged, changed, untracked or unmerged, with the list at its right end adding Commit (Amend), Commit and Push, and Commit and Sync, the last two only while the branch has an upstream. With nothing to commit it is Sync Changes, with the behind and ahead counts, while the branch is ahead of or behind its upstream, and Publish Branch for a branch with no upstream; both ask first. Where Commit cannot be pressed, its hover words say why. A repository with no configured name or email refuses the commit with git's own message, since a commit never takes an identity git guessed from the machine. An amend needs nothing staged, and with the field empty it keeps the last commit's message. The button inside the field writes a message from the staged diff. Ctrl+Enter or Cmd+Enter in the field commits as the button does. Every commit asks first. A commit, a merge, a cherry-pick, a rebase continued, a push, a pull, a switch and the making of a worktree run the repository's own hooks, so they have no time limit, and a Sync is a pull and then a push, each with none; while a git write runs, the repository says Working with a Cancel button beside it, which stops the hooks and other processes that command started and lets git end on its own, and the write answers "Git was stopped by Cancel"; a merge, a cherry-pick or a rebase stopped midway is named as left in progress, and the repository offers its Abort. The deposit's panel has the same Cancel. Every other command keeps its limit, 10 seconds for those that stay on the machine and 60 for Fetch, and a command that fails without a message of git's own says why: that it did not finish within its limit, that it wrote more than 8 MB of output, that a signal ended it, or the exit status it stopped with.

### Diffs, and staging part of a file

Pressing a changed row opens its diff in a pane of its own, drawn by the editor's diff view over the two whole versions of the file: side by side, the old version on the left and the new on the right, or inline, one column with the removed lines above the added ones; the pane remembers which, and Inline View in the bar's `...` menu switches it, Refresh in the same menu reads the diff again. Within a changed line the words that changed are marked. An unchanged run is hidden with three lines kept beside each change, and the bar drawn in its place shows it again; Collapse Unchanged Regions in the bar turns the hiding off and on; the pane keeps what was shown and where it was scrolled across a re-read and a reopen. A diff of several files, a stash's, a worktree's or a group's (Open Changes on the Staged Changes or Changes head, which offers no hunk action), gives each file a header row with its file icon, its name, its folder and Open File (a deleted file has none, and a renamed file's header shows R and the path it had), and a chevron that folds the file; the header stays at the top while its file scrolls, and a file's diff is drawn when it comes near the view; a commit's diff opens one file per pane. A file whose line endings alone changed says so above it and shows all its lines. Alt+F5 and Shift+Alt+F5, or Next Change and Previous Change on the bar, move from change to change through every file, opening a folded file they step onto and passing over a binary file and a file whose text did not change, and Open File opens the file at the change the pane is at.

Each block of a file's own diff, the changes git groups into one hunk as `git add -p` offers them, starts with a bar holding git's head for it (`@@ -a,b +c,d @@`) and Stage Block and Revert Block in a diff of the worktree, Unstage Block in a staged one. In a pane too narrow for the buttons' words they are drawn as icons with their words as the tooltip, and the words return when the pane is wide enough; the head, or the sentence of a file with no block actions, is cut with an ellipsis inside the bar. Selecting lines on either side, by dragging or by pressing a line's number, narrows the block's actions to them (Stage 2 Selected Lines), so one line can be staged or unstaged and the rest left as it was. A new or deleted file is staged or reverted whole from its bar. A file has no block or line actions, and its bar says to stage or revert it from Changes, when it holds a carriage return, when its text is not UTF-8, or when git converts it: a `filter`, `working-tree-encoding` or `ident` attribute, or, where the `text` attribute is not unset, `eol=crlf` or `core.autocrlf` set to `true` or `input`. A path in conflict has no block or line actions either, and its bar says to resolve it in the merge editor from Merge Changes. Revert asks first, since it throws the change away. The group heads carry Stage All Changes, Unstage All Changes, Discard All Changes and Stage All Untracked; Discard asks first.

### Pull, push, fetch, sync and publish

The `...` menu of the Repositories view holds Pull, Push, Fetch, Sync and Publish Branch. Pull runs git's own `pull` with the repository's own configuration, so whether it merges or rebases is the repository's choice; Sync pulls and then pushes; Fetch reads the remote's branches and forgets the ones the remote deleted. A branch with no upstream offers Publish Branch to each of the repository's remotes, which pushes it and makes that its upstream. Everything except Fetch asks first, and none of them ever forces. The status bar's sync item does the same for the repository of the tab on screen. With `git.autofetch_minutes` in `behavior.yml` above 0, oculus fetches every repository with a remote at that period, as Fetch does, without asking for a password or a passphrase, and the behind count of each branch moves with what the remote holds; when only the older `GIT_SSH` variable names the ssh program, nothing is added for ssh, which may then still ask. 0, the default, fetches only when Fetch is pressed. Nothing else reaches a remote unasked, and nothing pushes after a commit except where the reader pressed Commit and Push or Commit and Sync. The other git behaviours oculus has are fixed and have no key; "What oculus fixes" below lists them.

### Merges and conflicts

A merge, a pull or a stash applied or popped that stops on conflicts is left in progress, as VS Code leaves it: the view says a merge is in progress and how many files are in conflict, and lists them under Merge Changes. Open in Merge Editor opens the three-way merge editor: Incoming, the version being merged in, and Current, the checked-out branch's, side by side above the Result, each an editor like a file's with each conflict's lines tinted and its choices on a bar above it. Each conflict offers Accept Incoming, Accept Current, Accept Both in either order, and Ignore, which keeps what the two had in common; the Result can also be typed into, which settles a conflict by hand, and the bar counts the conflicts still open. A choice rewrites the Result as one edit, so Undo takes it back and the conflict is open again. Complete Merge writes the Result over the file and stages it, asking first while any conflict is still open. Where one side deleted the file, or both did, the editor says which and offers Accept Deletion, which after a confirm takes the file out of the index and the folder; Complete Merge with an empty Result does the same. Mark Resolved stages a file resolved some other way, or records its deletion where the folder no longer holds it. The commit box starts with the message git prepared for the merge, and the commit finishes it; Abort, after a confirmation, takes the merge back. A rebase stopped on conflicts offers Continue once they are resolved. A cherry pick stopped on conflicts is left in progress the same way, with Abort and no Continue, since committing finishes it.

### Stashes and tags

Stash, Stash (Include Untracked) and Stash Staged in the `...` menu set work aside, each after asking for an optional message; Stash Staged needs git 2.35 or later, and an older git refuses it with a sentence saying so. The Stashes section lists them newest first; pressing one opens its whole diff, and Apply Stash, Pop Stash and Drop Stash sit on its row, Drop asking first. Create Tag asks for a name, which must be a name git accepts for a tag, and an optional message, which makes it an annotated tag; the tag is made at the checked-out commit. The Tags section lists the tags, an annotated one with its message; pressing one opens its commit in the Graph, Delete Tag asks first, and Push Tags in the menu pushes every tag after a confirmation.

### The graph

The Graph section draws the checked-out branch's history fifty commits at a time, Load More reading the next fifty, each commit with its lanes, a circle that is larger for a merge and larger still with a ring for the checked-out commit, the branch and tag names on it as pills, and the checked-out commit's subject in bold. The checked-out branch's pill has a right-click menu of its own, with Checkout and Delete Branch both unavailable and their hover words saying why: "This branch is checked out already" and "The checked-out branch cannot be deleted; switch to another branch first". While the branch has an upstream, Incoming (what the upstream holds that the branch does not) and Outgoing (the other way round) come first, drawn with dashed circles. While the section is open, its head offers on hover Go to Current (the checked-out commit scrolled into view), Fetch, Pull, and Push or Publish Branch, each asking first except Fetch. Pressing a commit lists its changed files under it, each opening that commit's diff of the file, and its `...` holds the same items as its right-click menu: Open Changes, Copy Commit ID, Copy Commit Message, Checkout and Delete Tag lists, Checkout (Detached), Create Branch..., Create Tag..., Cherry Pick and the three compares. The commits under Incoming and Outgoing are drawn like the others, each list with its own lanes.

### From a commit of the graph

Checkout (Detached) runs `git switch --detach` on the commit, or on a remote branch named on it, and is refused when the working tree is dirty. Create Branch... and Create Tag... ask for a name (and a message for a tag), and the new branch or tag starts at the commit. Cherry Pick applies the commit to the checked-out branch after asking. A pick that stops on conflicts is left in progress as a merge is: the view says Cherry-picking with the number of files in conflict, lists them under Merge Changes, starts the commit box from git's message, and Abort runs `cherry-pick --abort`; a pick that would change nothing is aborted and answered with 'The changes are already present in the current branch.'. Compare with Remote compares the commit with the checked-out branch's upstream, and is not offered while the branch has none; Compare with Merge Base compares it with the base git names for the branch, as VS Code reads it, and is not offered while there is none; Compare with... asks which reference in a list of the branches, remote branches and tags. Each opens a diff pane over the files that reference and the commit differ in. Delete Branch, on a local branch name that is not checked out and on each branch row of the Branches section, asks first and runs `git branch -d`; when git keeps the branch because it is not fully merged, a second question, "The branch '{0}' is not fully merged. Delete anyway?", follows, and its yes runs `git branch -D`. Any other refusal is git's reason, and the branch is kept. The commit's Checkout list leaves out the checked-out branch, whose pill has a menu of its own with Checkout and Delete Branch unavailable.

### Untracked files, ignoring and earlier versions

Untracked files are a group of their own, so Stage All Changes never stages a new file. Discard Changes on an untracked file, a folder of them, or Discard All Untracked Changes on the group's head moves them to the Trash after asking, and a file can be got back from there; a folder git lists as a whole goes as one folder, and a path outside the repository, one the server keeps for itself, and a tracked one are refused before the Trash. Add to .gitignore appends the path to the repository's `.gitignore`, one line each, and opens that file. When git lists more than 200 changes, the view shows the first 200 of a group and says under it 'Too many changes were detected. Only the first 200 changes will be shown below.', and the rail badge counts what git reported.

### Repositories, closing and opening worktrees

Close Repository takes a repository out of the list of that Repositories tab only; another tab, a session's Changes panel and the rail count still have it. Reopen Closed Repositories lists the closed ones in a box with the title 'Reopen Closed Repositories' and the placeholder 'Pick a repository to reopen', and All Repositories after a rule while more than one is closed; with every repository closed the view says so and offers the same control. Open Worktree adds the worktree's folder as a root of the workspace and shows it in Files; Open Worktree in New Window opens this page's address in a new window as well.

### What oculus fixes

These git choices have no setting. Untracked files are their own group, as VS Code's `git.untrackedChanges: separate`, so one press of Stage All Changes cannot stage a file nobody looked at. Every configured root is listed, because oculus shows every repository it knows at once. Fetch prunes, so a branch deleted on the remote leaves the lists. Signing is left to git's own `commit.gpgsign`, so oculus adds no flag. Pull is a plain `git pull`, so the repository's own `pull.rebase` decides between merging and rebasing. A commit sets `user.useConfigOnly`, so it never takes an identity git guessed from the machine. No Source Control action carries `--force`; the push of a deposit snapshot is the one forced push in oculus.

### Blame and the gutter

A source tab over a file of a repository marks its changes against the index in the gutter beside the line numbers: a bar beside added and modified lines and a wedge where lines were deleted. Pressing a mark opens the file's diff at that change. From the keyboard, Go to Next Change (Alt+F5) and Go to Previous Change (Shift+Alt+F5) put the caret on the first line of the next or previous mark, going round at the ends, and Open Change opens the change on the caret's line as pressing its mark does; the palette lists all three while the tab is on screen and its file has a change. Blame, from the Toggle Blame button of the breadcrumb bar or the palette's Git: Toggle Git Blame Editor Decoration, writes beside the line numbers who last changed the lines and how long ago, on the first line of each run from one commit, with the commit and its subject on hover over a line's number; a line no commit holds yet says Not Committed Yet. Blame reads the file as it is saved. A tab over the file at HEAD or in the index (Open File (HEAD), Open File (Index)) offers the same toggle and blames that version: the last commit's, or the staged text, where a staged change to a line shows as not committed yet; such a tab has no change marks. Pressing a blamed line's number, or the blame item on the status bar, opens its commit in the Repositories view's Graph.

## Worktrees and the merge back

The Repositories view is over every root the file browser serves, the hub and the configured roots and whatever the current workspace added, plus the workspace of every session, one repository at a time, chosen in the Repositories list at its top, whose rows say which of them is gone in red, is no repository in blue or could not be read in amber. A repository with no commit yet is listed like any other, with its branch and its files, and its Branches section says the branch has no commit yet. A repository git could not read this time, or whose check timed out, stays in the list and the view stays on it: its path, and its branch line while git named the branch, stay above git's reason, one line in the error colour in place of the sections. What it shows is the pushed state of that repository: nothing is polled, and a commit made in a terminal moves it within two seconds. A diff, the graph, a commit's files, the blame and the gutter marks are not pushed; each is read when a pane or a section asks for it, so a repository with two hundred changed files costs the socket nothing.

A worktree is a second checkout of the same repository on a branch of its own, which is how one repository carries two pieces of work at once. The control at the bottom of a root's worktree list takes a name, says the path before anything is made, and on confirm makes `<root>/.agents/worktrees/<name>` on a new branch of that name from the repository's HEAD, then opens a shell there. Create with Claude and Create with Codex, beside Create, ask the same question and make the same worktree, then open the composer there for that agent in place of the shell; a worktree that cannot be made opens nothing. A repository whose `.gitignore` does not carry `/.agents/worktrees/` is warned about in the view rather than edited: what a repository ignores is its owner's to decide, and without the rule a worktree made there becomes content of the repository.

Each worktree row's menu also holds Start Claude Here and Start Codex Here, which open the composer in that worktree's folder for that agent. Each worktree row opens its diff when pressed and carries four controls, shown on hover or when the row has the focus: its diff against the repository's checked-out branch, a shell started in it, the merge back, and the removal. The merge back is git's own `merge` onto the checked-out branch, a fast-forward where it can be one and a merge commit otherwise. It is refused when the repository has staged or changed paths of its own, when the repository has no branch checked out, when the name is not one of the repository's own branches, and when the branch asked for is the one checked out; a merge that stops on conflicts is left in progress and reported by the paths that conflicted, which the view lists under Merge Changes for the merge editor, with Abort one press away. An untracked file does not refuse a merge, because git carries one across untouched.

Removing the worktree is a second control and never part of the merge. It refuses a worktree holding uncommitted changes or untracked files, which is the difference from the merge: the removal takes the folder away and everything in it with it, so a file git never saw would be a file nobody can get back. The branch goes with the worktree only when no work is left only there, and the answer says when the branch was kept.

## The configuration

A change to a cadence, a window, a count or the usage tiers takes effect at once. | `catalogs/vocab.yml` | Words and their colours: the palette, the research domains, the status legend, the focus lanes, the venue tiers, the venue and dataset theme words, the radar buckets and the side-project statuses. |
| `local.yml` | This machine's own values, read on their own and never merged into the configuration: the hub path, the port, the ssh alias of the cluster, the Claude command, the program an address is opened with, the account folders, the calendar accounts, the mail accounts, the Literature search's keys and where the machine-local state is kept. |

Every user-facing word lives under `config/text/`, one file per surface, a view's file under `config/text/views/` in the folder named as the view's own folder under `src/lib/views/`, and is read by its dotted key. Those files merge with the rest, so a word is changed there and nowhere else. The sentences of the Findings view are `config/text/findings.yml`, one per problem the readers and the checks report, with `{0}` and `{1}` standing for the values the finding names. A sentence the file does not hold, which is every sentence while the file does not parse, is shown as its key followed by those values. A missing `config/` folder is always shown that way, as `findings.config.directory_missing`, since there is then no file to read the sentence from.

`local.yml` sits in the same `config/` folder, last in the list, and is this machine's own. Its keys are `hub`, the absolute path of the research hub; `port`, the port the server listens on; `hpc_host`, the ssh alias the Live HPC view uses, which takes precedence over the host of the cluster that `slurm.resource` of `behavior.yml` names; `claude_bin`, the Claude command the update tasks and the chat terminal run; `open_bin`, the program a provider's consent page and an event's link are handed to, macOS `open` when absent; `accounts`, the agent account folders the Usage view reads; `calendars`, the calendar accounts the Calendar view reads, one `provider` (`google` or `microsoft`) and one `label` each, written by the view's Add account and Remove with the file's comments kept; `mail`, the mail accounts the Inbox view reads, written the same way; `literature`, a map of the Literature search's keys, `wos_key` (Web of Science), `scopus_key` and `scopus_insttoken` (Scopus), `openalex_key`, `semantic_scholar_key`, `ncbi_key` (PubMed) and `mailto` (the contact address Crossref, OpenAlex and PubMed ask for), each a non-empty text and each optional; and `calendar_dir`, `mail_dir`, `sessions_cache`, `sessions_overrides`, `workspaces`, `bookmarks`, `notes`, `changes`, `history` and `approvals`, the places the calendar credential files, the mail credential files and triage notes, the session cache, the per-session overrides, the saved workspaces, the reader's own bookmarks, the scratch notes, the change log and the local history of files and the approved texts of project commands are kept in; a value of these that is `~` or starts with `~/` is under the home folder, as an account's `dir` is, and any other relative value is resolved against the engine folder. Every key has a default, so a machine that sets only `hub` works. The file is read again whenever it changes, from the page or by hand, and every key holds at once; a key whose value is wrong is listed in the Findings view with `local.yml` and the key, never the value, and takes its default, and a wrong row of `accounts`, `calendars` or `mail` is left out with its finding. A `literature` that is not a map, or a key under it that is not a non-empty text, is such a key as well, and a key under it that is not one of these seven is warned of and ignored. A `port` that is not a whole number is such a key: its default is 8790, so a server on 8791 moves to 8790 as a written 8790 would move it, and the page follows; a port in use or reserved keeps the server where it is. A changed `port` moves the server and the open page follows it, once the new port answers, with its tabs, layout and settings as they were; a file that does not read keeps the values in force and says why once. The file is not tracked, so no machine path is ever in the repository, and it is served and edited like the files above it: the Settings view lists it as a group tagged as this machine's own, with its description and the control that opens it, and never its values. It is the one file of the folder whose keys are checked before a save: a body with a key the server would read as its default is refused with the sentence naming that key, and the file is left as it was.

## Where the data comes from

Everything on the boards is read from the research hub, whose absolute path is the `hub` key of `local.yml`. The scan rules of `sources.yml` name the folders projects sit in, and a project is any folder holding a `project.yml`. The `side-projects/` folder and the `.oculus/project.yml` of each Files root are the exception: they feed the Personal board only and are never read as research projects. The registries, the collections and the feeds are single YAML files named in the same place; the manuscripts, READMEs and decks are Markdown in each project's own folder.

People and organisations are two of those registries. `registries/people.yml` holds one entry per human, keyed by a short slug, with a name, an `affiliations:` list whose values are keys of `registries/organisations.yml` and whose first is the primary one, a role, and optionally an ORCID, an email, links and a supervision folder; exactly one entry carries `self: true` and that is the hub's owner. A manifest's `collaborators:` and `waiting-on:` name people by those keys, and an entry of `network/joint-work.yml` names its person by `person:`. A value in any of the four that the registry does not hold is a finding on the Findings view, as is an `affiliations:` key or a funding scheme's `funder:` that names no organisation, and an organisation `kind:` outside `university`, `hospital`, `funder`, `company` and `other`. An entry still written with the one key `affiliation:` is read as a list of that one and gets a finding asking for the new name. `registries/resources.yml` is another: the clusters, machines and storage a project runs on, each with a `kind:` of `cluster`, `machine` or `storage`. A manifest's `compute:` lists their keys, and `slurm.resource` of `behavior.yml` names the cluster whose `host:` the Live HPC view connects to. A `compute:` key the registry does not hold, and an entry whose `kind:` is none of the three, is a finding on the Findings view.

Nothing is copied into a database. The server reads the files, builds one snapshot of entities and relations, and pushes it over a WebSocket; it watches the hub and the config folder, so a file edited anywhere reaches the page in the same second. The long documents stay out of that snapshot and are fetched one at a time when a tab shows one.

Three things outside the hub are read as well, all of them this machine's own. The agent sessions are read from every account `accounts` in `local.yml` names: `<dir>/projects` for the transcripts and `<dir>/sessions` for which session is alive for each Claude account, and `<dir>/sessions` for the rollouts of each Codex account; two accounts whose folder is one real folder through a symlink are read once. The session cache, the per-session overrides, the saved workspaces, the reader's own bookmarks and the scratch notes are read and written under `~/.oculus`, or wherever `local.yml` puts each of them, and the providers' client halves are read and written in `~/.oculus/connect`. The engine's own `config/` folder is read on every load and written when a file of it is saved from a source tab.

Writes into the hub go back to the files they came from: a manifest field from the editor, a collection entry from a card, a text file from a source tab. Every write is a POST carrying the page's own token, and nothing outside the hub, the engine config folder, the machine-local files under `~/.oculus` and the configured roots is ever written; what is read beyond those is the agent account folders above, and the workspace a session names when its git state or its terminal is opened.

The Literature search sends the query and its filters from the server to the sources toggled on, with the keys of `local.yml` in a header or a parameter of the request, and a key is never in an answer, a message or a log line. It reads the sources' answers and writes nothing but the Lit Watch entry the reader adds.

The Inbox is read live from the reader's own mailboxes, and is the one view that writes to something outside the hub. A mail account is a row of `mail:` in `local.yml`, one `provider` (`google` or `microsoft`) and one `label`; it is added from the Inbox's Add account, which writes the row and the account's file and opens the consent at once, and taken away by its row's Remove; its refresh token is one file per account under `mail_dir` (`~/.oculus/mail` by default), mode 0600, which the consent brings back, and the provider's client half is the one saved on the Account setup view for every account of that provider. A mail account is its own consent with the mail scopes alone, so a calendar account of the same mailbox never gains the right to send. A thread is on the plate when it is in the inbox and unread, or carries the `todo` label, or is unlabeled and is a single message whose subject is not an answer or a forward; a thread whose newest message is the reader's own, or is in the trash, is off it. What the poller publishes of a message is the provider's own one-line snippet, its HTML entities decoded, and nothing more. A provider that does not answer within 30 seconds puts its account in error with a sentence saying so, and the other accounts are still read.

A calendar account is a row of `calendars:` in `local.yml`, added from the Calendar's Add account and removed by its row's Remove, and read again at once without a restart. The first account of a provider needs that provider's client half: Add opens the Account setup view, whose steps register the reader's own application at Google (a Desktop OAuth client) or at Microsoft (an Entra public client with the two redirect addresses the page lists on this server's port), and whose Save writes the half to `~/.oculus/connect/google.json` or `microsoft.json`, mode 0600; the account is then added and its consent opened. Every later account of the provider, calendar or mail, uses the same half and needs no setup. The Set up control and the hint on such an account name the provider as the setup page does (Google, Microsoft), in the Inbox as in the Calendar, while the row keeps the view's word for the provider (Gmail and Outlook in the Inbox). Remove asks first, takes the row out of `local.yml` and deletes the account's own file; the provider's half stays for the other accounts. An account whose own file names a `client_id` loses that id with the file, and its Remove's question says so. A calendar published as a link, such as an Outlook or Google calendar shared by its address, is added from the same Add account by choosing Published link as the provider and pasting the link, which starts `https://` or `webcal://`; it needs no setup and no consent. Its row in `local.yml` is `- { provider: ics, label: <label> }` and the link itself is kept in the account's own file, `<calendar_dir>/ics-<label>.json` (`~/.oculus/calendar/ics-<label>.json` by default), mode 0600, which Remove deletes. The link is read again from that file at every poll and is never logged, published, sent back to the page or written into an error.

What each thread wants, the line about it and the answer drafted for it are the triage notes, one JSON object per thread id in `<mail_dir>/triage.json`. The card writes them, and so does `/research-cockpit inbox`, which reads the mailbox through the runner's own Gmail connector and classifies what it finds; the server polls the file every half second, so a note written from outside is on the page without waiting for the next poll. A note whose thread has left the plate is kept for thirty days and then dropped. Send puts the answer on the thread at the provider and Archive takes the thread off the inbox, each behind a confirmation naming the address the answer would reach and the account it goes from; no draft is ever created at the provider, and those two are the only writes to a mailbox oculus makes. Which address that is follows the thread's newest message: its `Reply-To` where it carries one, and its sender otherwise, which is the rule the send itself uses.

Every write through the write endpoint that changed something is recorded in the change log, `~/.oculus/changes.jsonl`: when it was made, which file it wrote, what it addressed, and the value that file held before it against the value it holds after. That is the manifest fields, the collection entries, the subtasks, the feeds, the deck, the rail list, a setting written from the Settings view and the per-session overrides, and a scaffolded idea and the two LinkedIn writes, which are recorded and cannot be taken back; a text file saved from a source tab and a scratch note go through their own endpoints and are not recorded, and muting an audit finding goes through the write endpoint and is not recorded. The History view draws the log newest first, and the control on a row puts the earlier value back through the writer the change came from, refusing when the file has changed since. A write that removes a field keeps the removed text, where it stood and the text that followed it, so the control puts the text back before that following text, as it was, whatever else changed in the file; when the following text is gone, whole lines go back at the nearest line start that gives the right values, and only when none does does the value come back as a new line, as for a change that carries no such text; text removed from inside a line (a flow map's key) goes back only at the place of its following text, and otherwise comes back through the value write. A write that rewrote a bare follow-up note or a list of one note as a map keeps the text it replaced, and the control puts that text back over the lines the write left while the file still holds them, so the note returns in its own shape. `changes.keep` in `behavior.yml` is how many changes the file holds.

## How the code fits together

The diagrams are drawn from the source by `npm run diagrams`, which writes each to `docs/diagrams/` as a Graphviz `.dot` file and the `.svg` drawn from it. `npm test` fails while a committed diagram differs from what the source gives now and names every such file, so a change that moves an import, a channel or a write is committed with the diagrams it redraws. A module no layer row places is drawn in a dashed group named "not placed". In the layers overview, an import whose target is not written out is a dashed box naming its file and line, with a dashed arrow from the box of the module that makes it; in the channel and write diagrams, the dashed "not placed" group names with its file and line a publish, a channel read or comparison, a re-export of a whole module, or a call through a computed member or a method of an imported value, whose target is not written out. A call through a local alias, and a function passed by name to a function that calls it, in the same module or another, are followed; a name that holds a function only by a branch, a second assignment or the answer of a call is not.

The diagrams count the imports that run: an `import type` leaves nothing behind in the built code. No module imports itself through a chain of runtime imports (`tests/checks/imports/cycles.test.ts` fails on one and names its modules in order), and inside each layer the folders have an order from the top down, declared in `tests/checks/imports/order.ts`: a module imports its own folder or one below it and never one above, a type as much as a value, and `tests/checks/imports/order.test.ts` fails on an import that climbs. No module augments another module of the tree, with a `declare module` block or a `/// <reference path>` directive, in any direction; `tests/checks/imports/augments.test.ts` fails on one, while a block that adds to a package stays. The checks and the diagrams read a module's imports by parsing it, a component's scripts and markup included, so an import named in a comment is none. The channel and write diagrams read a module's calls in its text with every comment blanked by the same parses, so a call named in a comment is none, while a string or a regular expression holding `/*` or `//` is kept whole, and so is a component's markup, where a channel may be read. The composition roots head their layers (`server/root`, which builds the server's objects and starts the watchers; `state/client`, which builds the page's stores; the shell's own `Workbench.svelte`), and what a whole layer shares sits at its foot (`server/core`, `state/shared` with its `words/` holding the catalogs above its `stores/` holding the shapes of the stores other stores are handed (so a store that is handed one does not depend on the module that builds it), the shell action and the test of whether a fetch is the page's own, `data/model` with the facade of every type, the files of `ui` itself).

The layers: one box per layer that an import joins, `src/routes` as one box, the Node entry and the hooks under `src` as one box named entry, and one arrow per pair that imports, labelled with how many runtime imports it carries. The entry's arrow to routes is its load of the built app, which is the routes compiled. A file outside every layer that is no module, the favicon, is a box named by its folder, `assets`, with the arrow from the routes that link it; the dashed "not placed" group holds only a module no layer places that an import joins. An import the reader cannot follow is a dashed box with its file and line and a dashed arrow from the box that makes it; the source holds none today. In every diagram an arrow's count or list of calls stands on the arrow as a small box of words, and every other arrow is routed around it.

## Running it and checking it

The server runs on this machine only, bound to the loopback address, on the port `local.yml` names. `npm run dev` runs it in development, where a component's stylesheet is always served compiled, whichever the page asks for first; `npm run build` builds it and `npm run preview` serves that build. The built server is `node src/server.ts`, and its one argument is `--engine <dir>`, the directory holding the `config/` folder it reads and writes and the `HELP.md` this page is drawn from; without it that directory is `tools/oculus` itself. The server reads no environment variable of its own; the one it does read is the operating system's `SHELL`, which is the command a plain terminal starts, `/bin/zsh` when the environment names none.

The checks, from `tools/oculus`:

- `npm test` runs the unit suite over the data layer, the server, the stores, the shell and the views, leaving out the tree checks and the tests tagged slow. A file named `*.client.test.ts` runs in Svelte's client runtime with no DOM, which is where an effect's teardown runs; every other file runs against Svelte's server build.
- `npm run test:checks` runs the tree checks under `tests/checks` (comment width, file size, duplication, import order and the rest) with no time limit.
- `npm run test:slow` runs the tests tagged slow (`// @module-tag slow` in a test file's head comment tags the file, `{ tags: ['slow'] }` a test or a describe), which start a process, wait on a real timer, open a socket or take 100 ms or more in a run of their own.
- `npm run check` runs the TypeScript and Svelte check over every file.
- `npm run lint` and `npm run format:check` hold the source to its conventions.
