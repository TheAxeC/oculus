# oculus

The private dashboard over the research portfolio. `DESIGN.md` is what it is measured against; this file is how to run it.

Install once, with Node 24 and npm 11 (`nvm install 24` gives both): `npm ci` from the committed lockfile, or `npm install` to regenerate it. The Status view's line counts also need Perl on the PATH to run cloc; macOS and most Linux systems carry it.

Develop with `npm run dev`, which hot-reloads and serves on 127.0.0.1 at the port from `local.yml` (8790 by default), the same address as the built server, so the Claude Code hooks that post to it reach whichever is running; the two cannot run at once. For the built server, `npm run build` then `node src/server.ts`. Port 8787 belongs to the cockpit and is never used.

The native app: `npm run app` starts oculus in its own window (Electron, with the server as a utility process; the first run fetches Electron's binary), and `npm run app:package` writes `oculus.app` to `~/Applications`, or to the folder `--out <dir>` names. The app builds the checkout's server into `build-app/` and `.svelte-kit-app/` before it starts (the packaged app runs no build and reads `build-app/`, so it needs one `npm run app` from the checkout first), takes the same `--engine <dir>`, and keeps its window state in `~/.oculus/window.json`. HELP.md describes what the app adds to the page.

The built server takes three arguments. `--engine <dir>` (`--engine=<dir>` too) names the directory that holds the `config/` folder it reads and writes and the `HELP.md` the help view draws; a relative path is resolved against the directory the command was typed in. Without it the engine is `tools/oculus` itself, which is what a plain `node src/server.ts` over the checkout means. `--default-port <n>` (`--default-port=<n>` too) is a whole port number from 1 to 65535: the port the server takes while `local.yml` is missing, which the app passes so that the port it expects is the port the server takes. `--handler <file>` (`--handler=<file>` too) names the built handler the server loads, resolved against the directory the command was typed in like `--engine`; the app passes `build-app/handler.js`, and without it the server loads `build/handler.js`, the build of `npm run build`. A directory holding no `config/` and a `--handler` that names no file are refused at start, and any other argument is refused naming it. The development server runs over the checkout and takes no argument.

Machine-local values live in `config/local.yml` of the engine directory the server was given, which for the checkout is `tools/oculus/config/local.yml`; it is gitignored and optional: `hub` is the absolute path of the research hub, defaulting to two directories above the engine; `port` is an integer, defaulting to 8790; and `claude_bin` names the Claude CLI used by update tasks and by the prompts of schedules, defaulting to `claude` on PATH. That file is read by itself and is never merged with the rest of the folder, so a key it carries is the machine's own and no other reader sees it. The server reads no environment variable of its own: a run that must not touch the checkout's configuration is started over a copy with `--engine`.

## Two Claude accounts

Claude Code keeps its login, settings and session history in one folder, `~/.claude` by default; the environment variable `CLAUDE_CONFIG_DIR` points it at another folder, and the login stored for that folder is its own Keychain entry. Axel's second account (the university address, Max 5x) lives in `~/.claude-work`, whose `CLAUDE.md`, `rules`, `settings.json` and `projects` are symlinks to `~/.claude`'s, so both accounts share the rules, the settings, the transcripts and the memory, and only the login and the app state differ.

The Status view prints the Claude Code hooks block that posts to oculus, which goes in `~/.claude/settings.json`, the settings file both accounts read through that symlink, so a session started in any folder tells oculus when it wants you. A block in the hub's own `.claude/settings.local.json` is not needed once it is there.

Start Claude Code on the second account from the hub root:

```sh
cd ~/workspace/research-hub
CLAUDE_CONFIG_DIR=~/.claude-work claude
```

Resume a session there, whichever account it started on, since the transcripts are shared:

```sh
CLAUDE_CONFIG_DIR=~/.claude-work claude --resume <session-id>
```

`~/.zshrc` on Axel's machine defines `claude-work` as a shortcut for `CLAUDE_CONFIG_DIR=~/.claude-work claude`, with arguments passed through, so `claude-work` and `claude-work --resume <session-id>` do the same as the two commands above. A terminal without the variable runs on the first account. Never resume one session in two terminals at once: both write the same transcript. To branch instead, add `--fork-session`. Codex has the same in `CODEX_HOME`. The Usage view reads both folders through the `accounts:` list in `local.yml`.
