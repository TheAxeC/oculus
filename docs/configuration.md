# Configuration guide

Every setting of oculus lives in a file: the files of the engine's `config/` folder and the machine's own `config/local.yml`. This guide lists each file with what it holds, the keys of `local.yml`, and the hub files and accounts the settings point at.

## The files of `config/`

The files below sit in the `config/` folder of the engine, `tools/oculus/config/`, the vocabularies and the options catalog in its `catalogs/` folder. Every one but `local.yml`, which is this machine's own, is read on every load and merged into one map by its top-level keys, so a key moves between files without a reader noticing. Every option of these files is described once in `catalogs/options.yml` and set in the Settings view, with its default and the file and line of its key; the keys of `local.yml` are listed there without their values. The Settings view lists the same files, each subject group with a line per file it draws from, holding the file's description and a control that opens the file in a source tab for editing, and below them the files of `catalogs/` and of `text/` with the same control; an edit saved in a source tab is picked up and pushed to the page without a reload. A change to a cadence, a window, a count or the usage tiers takes effect at once. A value written by hand that the option's control, range or list refuses is listed in the Findings view with the file and the key, and that setting takes its default until the value is mended; the server starts and every other setting is read as written.

| File | What it holds |
|---|---|
| `catalogs/agents.yml` | The composer of a new agent session: per agent, the models, efforts and permission modes it offers, each with the words it shows and the flag it passes, and each list with its default; a value with `confirm: true` makes every start with it ask first, and a `confirm` that is neither true nor false is reported and reads as true. |
| `appearance.yml` | The UI theme list with the glyph each theme is offered under, the wallpaper behind the panels, the Memories wall's folder, the CRT default, the code theme of the editors, the terminal text size and the terminal's cursor style, cursor blinking, Option key and copy on selection. The four under `terminal:` are `mac_option_is_meta` (Option sends Meta on macOS), `copy_on_selection` (a selection is copied as it is made), `cursor_style` (`block`, `line` or `underline`) and `cursor_blinking`; all four start false or block and follow a change of the file without a reload. The `code_theme` key is `tokens`, or the id of a Shiki theme such as `dark-plus`, and is what a browser that has not picked in the Code theme menu starts on. `show_tabs` (`multiple`, `single` or `none`) says whether a pane's strip draws every tab, the active tab alone, or no tab, and `editor_actions` (`strip` or `hidden`) whether the strip carries the pane's actions; both are set in Settings or by the strip's right-click menu. |
| `behavior.yml` | Thresholds, horizons and cadences: read limits, the `refresh_stale_days` thresholds of the refresh strip, the context window, the Live HPC settings, the audit's waiting statuses and mute list, the source editor's `editor.paint_limit_kb`, `editor.tab_size`, `editor.insert_spaces`, `editor.word_wrap`, `editor.minimap`, `editor.render_whitespace`, `editor.sticky_scroll` and the per-language `editor.languages` records, the Files view's `files.confirm_delete` (true asks before a delete to the Trash), the Literature search's `literature.timeout_s`, `literature.per_source` and `literature.cache_min`, the apps' `apps` block (the frame's start timeout, the state, store, write, open, key, file and size limits, and `closed_paths`), the application `open.program_ext` names for each extension that may open, git (the commit-message model and the auto fetch period `git.autofetch_minutes`) and chat. |
| `catalogs/file-nesting.yml` | The files the Files view draws under another file when File Nesting is on: per parent name, the names nested under it, as VS Code lists them by default. |
| `catalogs/glyphs.yml` | The glyph vocabulary: each name with the ASCII stand-in, one to three characters, that a terminal theme draws in place of its icon. |
| `catalogs/icons.yml` | The line icon each glyph name is drawn as, one row per name in the glyph vocabulary. |
| `layout.yml` | How things are arranged: the rail's pages and the arrangements each starts as, the view catalogue's groups, the hub documents, the board chrome, the tab rollups and the live badges. |
| `catalogs/manifest-schema.yml` | The project.yml edit form as data: its sections, its fields, the widget each field is edited by, and where a widget takes its choices from. |
| `catalogs/meta.yml` | The tool identity: the title and the subtitle the window carries. |
| `catalogs/options.yml` | Every option of every config file: what it does, its default, the control it is set with, and the subject heading the Settings view lists it under. |
| `present.yml` | What every deck inherits: `defaults.tag_tones`, the hue each tag class of a project slide wears. A deck's own `present.yml` can change it. Which folder is the portfolio deck is `portfolio_deck:` in `sources.yml`. |
| `sources.yml` | What the portfolio reads: the scan paths, the registry and collection files, the feeds, and the hub folder of the portfolio deck (`portfolio_deck:`) and the roots a local file is served from (the folders of the default workspace, which the Files view's Add Folder to Workspace and Remove Folder from Workspace write, keeping the file's comments), and the language each file name opens in. The language map is `languages:`, a language's name against its extensions with their dot and its whole file names; it colours the file in the editor and names it in the status bar, and a file no entry matches opens as plain text. |
| `catalogs/vocab.yml` | Words and their colours: the palette, the research domains, the status legend, the focus lanes, the venue tiers, the venue and dataset theme words, the radar buckets and the side-project statuses. |
| `local.yml` | This machine's own values, read on their own and never merged into the configuration: the hub path, the port, the ssh alias of the cluster, the Claude command, the program an address is opened with, the account folders, the calendar accounts, the mail accounts, the Literature search's keys and where the machine-local state is kept. |

## The text of the interface

Every user-facing word lives under `config/text/`, one file per surface, a view's file under `config/text/views/` in the folder named as the view's own folder under `src/lib/views/`, and is read by its dotted key. Those files merge with the rest, so a word is changed there and nowhere else. The sentences of the Findings view are `config/text/findings.yml`, one per problem the readers and the checks report, with `{0}` and `{1}` standing for the values the finding names. A sentence the file does not hold, which is every sentence while the file does not parse, is shown as its key followed by those values. A missing `config/` folder is always shown that way, as `findings.config.directory_missing`, since there is then no file to read the sentence from.

## `local.yml`

`local.yml` sits in the same `config/` folder, last in the list, and is this machine's own. Its keys are `hub`, the absolute path of the research hub; `port`, the port the server listens on; `hpc_host`, the ssh alias the Live HPC view uses, which takes precedence over the host of the cluster that `slurm.resource` of `behavior.yml` names; `claude_bin`, the Claude command the update tasks, the prompts of schedules and the chat terminal run; `open_bin`, the program a provider's consent page and an event's link are handed to, macOS `open` when absent; `accounts`, the agent account folders the Usage view reads; `calendars`, the calendar accounts the Calendar view reads, one `provider` (`google` or `microsoft`) and one `label` each, written by the view's Add account and Remove with the file's comments kept; `mail`, the mail accounts the Inbox view reads, written the same way; `literature`, a map of the Literature search's keys, `wos_key` (Web of Science), `scopus_key` and `scopus_insttoken` (Scopus), `openalex_key`, `semantic_scholar_key`, `ncbi_key` (PubMed) and `mailto` (the contact address Crossref, OpenAlex and PubMed ask for), each a non-empty text and each optional; and `apps_dir`, `calendar_dir`, `mail_dir`, `sessions_cache`, `sessions_overrides`, `workspaces`, `bookmarks`, `notes`, `changes`, `history`, `approvals`, `schedules` and `schedule_record`, the places the machine's apps, the calendar credential files, the mail credential files and triage notes, the session cache, the per-session overrides, the saved workspaces, the reader's own bookmarks, the scratch notes, the change log and the local history of files, the approved texts of project commands and the schedules and their run record are kept in; a value of these that is `~` or starts with `~/` is under the home folder, as an account's `dir` is, and any other relative value is resolved against the engine folder. Every key has a default, so a machine that sets only `hub` works. The file is read again whenever it changes, from the page or by hand, and every key holds at once; a key whose value is wrong is listed in the Findings view with `local.yml` and the key, never the value, and takes its default, and a wrong row of `accounts`, `calendars` or `mail` is left out with its finding. A `literature` that is not a map, or a key under it that is not a non-empty text, is such a key as well, and a key under it that is not one of these seven is warned of and ignored. A `port` that is not a whole number is such a key: its default is 8790, so a server on 8791 moves to 8790 as a written 8790 would move it, and the page follows; a port in use or reserved keeps the server where it is. A changed `port` moves the server and the open page follows it, once the new port answers, with its tabs, layout and settings as they were; a file that does not read keeps the values in force and says why once. The file is not tracked, so no machine path is ever in the repository, and it is served and edited like the files above it: the Settings view lists it as a group tagged as this machine's own, with its description and the control that opens it, and never its values. It is the one file of the folder whose keys are checked before a save: a body with a key the server would read as its default is refused with the sentence naming that key, and the file is left as it was.

## The hub's files

Everything on the boards is read from the research hub, whose absolute path is the `hub` key of `local.yml`. The scan rules of `sources.yml` name the folders projects sit in, and a project is any folder holding a `project.yml`. The `side-projects/` folder and the `.oculus/project.yml` of each Files root are the exception: they feed the Personal board only and are never read as research projects. The registries, the collections and the feeds are single YAML files named in the same place; the manuscripts, READMEs and decks are Markdown in each project's own folder.

People and organisations are two of those registries. `registries/people.yml` holds one entry per human, keyed by a short slug, with a name, an `affiliations:` list whose values are keys of `registries/organisations.yml` and whose first is the primary one, a role, and optionally an ORCID, an email, links and a supervision folder; exactly one entry carries `self: true` and that is the hub's owner. A manifest's `collaborators:` and `waiting-on:` name people by those keys, and an entry of `network/joint-work.yml` names its person by `person:`. A value in any of the four that the registry does not hold is a finding on the Findings view, as is an `affiliations:` key or a funding scheme's `funder:` that names no organisation, and an organisation `kind:` outside `university`, `hospital`, `funder`, `company` and `other`. An entry still written with the one key `affiliation:` is read as a list of that one and gets a finding asking for the new name. `registries/resources.yml` is another: the clusters, machines and storage a project runs on, each with a `kind:` of `cluster`, `machine` or `storage`. A manifest's `compute:` lists their keys, and `slurm.resource` of `behavior.yml` names the cluster whose `host:` the Live HPC view connects to. A `compute:` key the registry does not hold, and an entry whose `kind:` is none of the three, is a finding on the Findings view.

## What is kept outside the hub

Three things outside the hub are read as well, all of them this machine's own. The agent sessions are read from every account `accounts` in `local.yml` names: `<dir>/projects` for the transcripts and `<dir>/sessions` for which session is alive for each Claude account, and `<dir>/sessions` for the rollouts of each Codex account; two accounts whose folder is one real folder through a symlink are read once. The session cache, the per-session overrides, the saved workspaces, the reader's own bookmarks, the scratch notes, the schedules and their run record are read and written under `~/.oculus`, or wherever `local.yml` puts each of them, and the providers' client halves are read and written in `~/.oculus/connect`. The engine's own `config/` folder is read on every load and written when a file of it is saved from a source tab.

## The Literature search's keys

The Literature search sends the query and its filters from the server to the sources toggled on, with the keys of `local.yml` in a header or a parameter of the request, and a key is never in an answer, a message or a log line. It reads the sources' answers and writes nothing but the Lit Watch entry the reader adds.

## Mail accounts and the Inbox

The Inbox is read live from the reader's own mailboxes, and is the one view that writes to something outside the hub. A mail account is a row of `mail:` in `local.yml`, one `provider` (`google` or `microsoft`) and one `label`; it is added from the Inbox's Add account, which writes the row and the account's file and opens the consent at once, and taken away by its row's Remove; its refresh token is one file per account under `mail_dir` (`~/.oculus/mail` by default), mode 0600, which the consent brings back, and the provider's client half is the one saved on the Account setup view for every account of that provider. A mail account is its own consent with the mail scopes alone, so a calendar account of the same mailbox never gains the right to send. A thread is on the plate when it is in the inbox and unread, or carries the `todo` label, or is unlabeled and is a single message whose subject is not an answer or a forward; a thread whose newest message is the reader's own, or is in the trash, is off it. What the poller publishes of a message is the provider's own one-line snippet, its HTML entities decoded, and nothing more. A provider that does not answer within 30 seconds puts its account in error with a sentence saying so, and the other accounts are still read.

What each thread wants, the line about it and the answer drafted for it are the triage notes, one JSON object per thread id in `<mail_dir>/triage.json`. The card writes them, and so does `/research-cockpit inbox`, which reads the mailbox through the runner's own Gmail connector and classifies what it finds; the server polls the file every half second, so a note written from outside is on the page without waiting for the next poll. A note whose thread has left the plate is kept for thirty days and then dropped. Send puts the answer on the thread at the provider and Archive takes the thread off the inbox, each behind a confirmation naming the address the answer would reach and the account it goes from; no draft is ever created at the provider, and those two are the only writes to a mailbox oculus makes. Which address that is follows the thread's newest message: its `Reply-To` where it carries one, and its sender otherwise, which is the rule the send itself uses.

`mail:` in `behavior.yml` sets how often every account is read (`poll_min`, 10 by default, and every 2 minutes while a provider refuses) and how many threads each of the three plate signals reads (`per_signal`, 25). A reply and an archive each ask a confirmation on the card naming the address the answer reaches and the account, Archive on the card's own row and Send in the draft editor beside the answer it sends, and no draft is ever created at the provider.

## Calendar accounts

A calendar account is a row of `calendars:` in `local.yml`, added from the Calendar's Add account and removed by its row's Remove, and read again at once without a restart. The first account of a provider needs that provider's client half: Add opens the Account setup view, whose steps register the reader's own application at Google (a Desktop OAuth client) or at Microsoft (an Entra public client with the two redirect addresses the page lists on this server's port), and whose Save writes the half to `~/.oculus/connect/google.json` or `microsoft.json`, mode 0600; the account is then added and its consent opened. Every later account of the provider, calendar or mail, uses the same half and needs no setup. The Set up control and the hint on such an account name the provider as the setup page does (Google, Microsoft), in the Inbox as in the Calendar, while the row keeps the view's word for the provider (Gmail and Outlook in the Inbox). Remove asks first, takes the row out of `local.yml` and deletes the account's own file; the provider's half stays for the other accounts. An account whose own file names a `client_id` loses that id with the file, and its Remove's question says so. A calendar published as a link, such as an Outlook or Google calendar shared by its address, is added from the same Add account by choosing Published link as the provider and pasting the link, which starts `https://` or `webcal://`; it needs no setup and no consent. Its row in `local.yml` is `- { provider: ics, label: <label> }` and the link itself is kept in the account's own file, `<calendar_dir>/ics-<label>.json` (`~/.oculus/calendar/ics-<label>.json` by default), mode 0600, which Remove deletes. The link is read again from that file at every poll and is never logged, published, sent back to the page or written into an error.

`calendar:` in `behavior.yml` sets how often every account is read (`poll_min`, 15 by default, and every 2 minutes while a provider refuses), how many days of events before today (`days_back`, 31) and after it (`days_ahead`, 62) are read, and the last good events of an account stay on screen while it is refusing.

## The change log

Every write through the write endpoint that changed something is recorded in the change log, `~/.oculus/changes.jsonl`: when it was made, which file it wrote, what it addressed, and the value that file held before it against the value it holds after. That is the manifest fields, the collection entries, the subtasks, the feeds, the slides list of a deck group, the rail list, a setting written from the Settings view and the per-session overrides, and a scaffolded idea and the two LinkedIn writes, which are recorded and cannot be taken back; a text file saved from a source tab and a scratch note go through their own endpoints and are not recorded, and muting an audit finding goes through the write endpoint and is not recorded. The History view draws the log newest first, and the control on a row puts the earlier value back through the writer the change came from, refusing when the file has changed since. A write that removes a field keeps the removed text, where it stood and the text that followed it, so the control puts the text back before that following text, as it was, whatever else changed in the file; when the following text is gone, whole lines go back at the nearest line start that gives the right values, and only when none does does the value come back as a new line, as for a change that carries no such text; text removed from inside a line (a flow map's key) goes back only at the place of its following text, and otherwise comes back through the value write. A write that rewrote a bare follow-up note or a list of one note as a map keeps the text it replaced, and the control puts that text back over the lines the write left while the file still holds them, so the note returns in its own shape. `changes.keep` in `behavior.yml` is how many changes the file holds.
