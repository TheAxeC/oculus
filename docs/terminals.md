# Terminals and commands guide

Terminals, the agent sessions a reader drives from them, and the project commands that run in a repository's folder.

## The Terminal view

A terminal panel of its own: each Terminal tab owns one or more terminals running Claude, Codex or a shell inside tmux, and shows only those; a terminal belongs to one tab.

## Starting a terminal

A new Terminal tab shows the composer, where you pick the workspace, agent, account and options and write the first prompt; while the shell, Claude or Codex that New Terminal asks for is starting, the tab says "Starting Shell..." (or Claude, or Codex) in its place. A start whose options make the agent ask less (Claude's Accept edits, Auto and Bypass permissions, Codex's Full access and a Never approval) asks first, at every start, what the option changes, and No starts nothing; the server refuses such a start that did not come from that question. The header's `new terminal` control starts a shell at once in the folder of the terminal shown here (else the first terminal's, else the hub), and the arrow beside it starts a Shell, Claude or Codex the same way; its items are Shell, Claude and Codex, then With a Prompt, which shows the composer for the first message, then Attach to Session. New Terminal in a pane's tab menu starts a shell in a Terminal tab of that pane. A start that is refused is said on the bar and changes nothing.

A start from a hub task opens the composer seeded with the text the server builds from the task, in the task's folder, and the text runs only after you approve it for that agent and that folder (Approve and Start; a changed text asks again). Such a start is refused with a sentence before anything runs when the agent is a shell, the task is no longer in the hub, the task changed since it was shown, or its text with the words you add is longer than a prompt may be. A value of `config/catalogs/agents.yml` with `confirm: true` asks before every start that resolves to it, and the server refuses such a start that did not come from that question.

## Starting an agent from a task

A task's `agent` button, Start Agent and the worktree controls that start an agent open the composer in the page's Terminal tab (or a new one) in the folder they name, with that agent and every option at its default, so Permissions reads Manual permissions whatever the tab's last start used. With a task, the folder is the project's, the funding scheme's `link:` folder, the one project an entry relates to, or else the hub; the composer shows the task's text read-only under Task, only Claude and Codex are offered, Remove the task makes the start an ordinary one, and what you type is added after the task's text. The first start of a task's text for an agent in a folder shows the text and asks Approve and Start; the approval is kept in `~/.oculus/approvals.json` for that agent, that real folder and that text, so a changed text asks again, and a task whose text changed since it was shown replaces the shown text with the new one and starts nothing. A task the hub does not hold, a text longer than a prompt may be, and an approvals file that cannot be written are said and start nothing.

## The renderer and the steer box

Every terminal oculus starts runs Claude's classic renderer (`CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN=1`), so Claude's output keeps its scrollback in the grid; a Claude already running keeps its renderer until it is started again. Once Claude or Codex runs, the steer box below the grid sends more text, and Stop interrupts; a shell has no steer box and is typed into at the grid.

## Several terminals in one tab

From two terminals on, a list on the right names each terminal of this tab by the title you gave it, else after what runs in it (Claude, Codex, the project command's name for a task terminal, or the shell's running command, the word shell when none is reported) with its session or folder after it, and a Terminal tab's title in the strip follows the same rule; press a row, or move with the arrow keys and press Enter, to show it here, hover a row for Split (a new terminal of its kind starts right of it, in its folder; Shift+Enter on the row, or the header's Split) and Kill (press twice; Delete or Backspace on the row, twice), and double-click a row's name to rename it. A row of terminals holds any number side by side, at least 80 px each, and scrolls sideways when they do not fit; drag the handle between two to resize them and double-click it to even them; pressing a terminal outside the row shows it alone. Drag a row within the list to reorder this tab, or onto another Terminal tab's list (or its body, when it shows a single terminal) to move it there; a tab left with no terminal closes, unless it shows the composer, which stays with what you typed. A tab showing the composer lists a single terminal too, so it can be shown, split or killed from there; a tab showing its only terminal names it on the bar instead. A right-click on that name on the bar opens the menu of a list row (Split Terminal, Kill Terminal, Rename, Change Icon, Change Color, Clear, and Join Terminals while another Terminal tab owns a terminal), which acts on that terminal as the row's menu does. A terminal started elsewhere (an update task, a resume or fork, a dataset recovery, a project chat, a LaTeX build, a Repositories shell) shows in the tab that owns it, or in the page's Terminal tab, or a new one. Floating a pane and returning it to a page keep where each terminal's scrollback was scrolled to, or at the end when it was there. A Terminal tab's tab in the strip is drawn with the icon and colour of the terminal it shows (the view's own glyph and the default colour when that terminal has none).

## Task terminals

A task terminal, which a project command starts (see Project commands), whose line ended is drawn with a green check for exit code 0 and a red cross for any other, on the strip, on its row and on the bar, in place of its icon and colour.

## The grid's menu

A right-click on the grid offers Copy and Copy as HTML over a selection, Paste, Select All, Clear, Rerun and Restart on a task terminal, Split Terminal, Rename, Change Icon, Change Color and Kill Terminal (picked twice, as a row's Kill is pressed twice: the first pick arms the terminal and the item then reads "Press again to kill this terminal", with the row's Kill shown armed, in the accent's colours, when the tab lists its terminals; a pressed toggle button anywhere is drawn the same way; a terminal joining or leaving the tab takes the arm off); on a row of the list Rerun (a task terminal whose line ended) and Restart (a task terminal), Split Terminal, Kill Terminal, Rename, Change Icon, Change Color, Clear, Unsplit Terminal on a terminal of a row of more than one, and Join Terminals, which lists the terminals other Terminal tabs own by name and moves the one you pick into this tab, split beside the row; and on the list below its rows New Terminal, New Terminal With Profile (Shell, Claude or Codex, each started at once) and Attach to Session. Attach to Session, in the arrow's menu and in the menu of the list's empty area, lists by name the terminals no Terminal tab owns (a session started in tmux by hand is not one of them) and moves the one you pick into this tab, at the end of its order and shown alone; it is absent when there is none. Shift-F10 or the context menu key in the grid opens its menu at the cursor rather than reaching the program.

## Find, links, pasting and what reaches the program

Cmd+F (Ctrl+F off macOS) in the grid opens the find bar over its top right, as VS Code's terminal find: the text, Match Case, Match Whole Word and Use Regular Expression, the count of matches ("3 of 12"), Previous, Next and Close; every match is marked in the accent's surface and the one found in the accent, and Escape closes the bar and gives the grid the keys back. A web address in the output is underlined under the pointer and opens in a new browser tab on Cmd+click (Ctrl+click off macOS); a plain click stays the program's. An emoji or a wide character takes two cells, as the shell counts it. A paste that holds a line break, a single line ending in one included, asks before it is sent, since the line would run at once, from the menu as from the keyboard, and a file dropped from Files types its quoted path. What you type, click, scroll or paste reaches the program as the bytes the grid sends, so a click, a scroll or a focus change arrives in one write and never as a lone Escape followed by text, and a long paste arrives in several writes, in order, its opening and closing markers each whole.

## Reopening, ending and closing

A terminal opened again, or shown again after the server restarted, shows its screen with the cursor where the program left it, so a new shell's prompt is at the top, and keeps the modes the program set, so a paste into a waiting shell still reaches it as a paste and the arrow keys and the mouse reach an editor as it asked. An editor open in a terminal is drawn full screen after the page attaches, and leaving it shows the shell's text again with the prompt where the shell left it. When a terminal ends (`exit` in a shell, or it is killed), its row leaves its tab, except a task terminal, which stays after its line ends until it is closed, and a tab whose last terminal ended closes, on every page, unless it shows the composer, which stays with what you typed. Closing a tab, a pane or a page, or resetting a page, ends the terminals it owns, after asking when one of them runs a program other than its shell (the question names each, and unsaved text first); a task terminal whose line ended is not asked about, and one whose line runs is; closing a task terminal ends its session; moving a tab, splitting and reloading end none. A terminal's line height, letter spacing, weight and ligatures are fixed and have no setting.

## Sessions

Every agent session on this machine. The sessions list groups sessions by workspace and orders each group pinned first, then those that need input, then newest first. Archived sessions are hidden until the filter asks for them; Archive is offered on ended sessions only. New shows the composer in the page's Terminal tab, or a new one. Below the sessions every terminal oculus runs is listed, those no Terminal tab owns among them: pressing one shows it in the Terminal tab that owns it, or takes it into the page's Terminal tab, and its menu's Open in its own pane moves it into a new Terminal tab.

## Where project commands come from

A repository has project commands: named lines that run in its folder, drawn as a row of buttons and run as terminals. They come from three places, listed in this order. The first is the repository's own file, `.oculus/commands.yml`, a list `commands:` of entries with `name`, `run`, an optional `cwd` (a folder inside the repository, the repository by default), an optional `depends_on` (a list of command names that run first) and an optional `default` (`build` or `test`). A command may also be named as the `before` of a debug launch configuration, which runs it first and launches only when it ends with exit code 0 (see the [Debugging guide](debugging.md#a-command-before-the-launch)). The second is the commands saved through the form, kept in `~/.oculus/commands.json` under the repository's absolute path. The third is what oculus finds in the repository: the presets of `CMakePresets.json` and `CMakeUserPresets.json`, hidden ones left out (a configure preset is named `cmake: <preset>`, a build preset `cmake build: <preset>` and a test preset `ctest: <preset>`), the scripts of `package.json` (named `npm: <script>`, and run with `pnpm` when `pnpm-lock.yaml` is there and `yarn` when `yarn.lock` is), and the targets of the top `Makefile` (named `make: <target>`, without pattern rules, special targets and variable assignments). A name can be held by two sources of one repository, the file and the saved commands: both are listed, each button and each menu item names its source beside the name (`build (file)`, `build (saved)`), and a press runs the command of the source it names. The default keys run the default build or test of the repository and name no source. The form refuses to save a name that `.oculus/commands.yml` or a found command already holds. A field of the wrong type, an empty or repeated name, a folder outside the repository and a second `default` of one kind are findings: the entry or the default is left out, and the bar marks the findings with a warning whose tooltip names each file and field.

## Where project commands are drawn

The Repositories view draws a repository's commands above its commit box; a project card draws the same bar below its chips when the project's folder is a repository; and the Files view's right-click menu on a root or a folder that is a repository has a Run Command submenu, whose commands are read when the menu opens. A bar shows five buttons and puts the rest in an overflow menu, whose Manage submenu holds the same menus as the buttons. A button's tooltip is the command's line and where it was read from. A right-click on a button opens Edit, Schedule... and Delete for a saved command (Schedule... opens the update tray's schedule dialog with that command filled in), and Open File at its entry (`.oculus/commands.yml`, `package.json`, the presets file or the Makefile) for a command from a file or one that was found. Add Command... opens the form: the name, the line, an optional folder, an optional list of the commands it depends on and an optional default; it saves for that repository.

## The run

A press starts one terminal named after the command. When the command has `depends_on`, the terminal runs each command of the chain once, in the order listed, each after the one before it, and stops at the first that fails; a cycle, a command that depends on itself and a name no command has are refused with the names. The terminal is shown and selected. These placeholders take their values from the source tab on screen, or, when the command is started from a button in another view, from the source tab whose editor had the focus last: `${file}`, `${fileDirname}`, `${fileBasename}`, `${fileBasenameNoExtension}`, `${lineNumber}` and `${selectedText}` (its file, the line of its caret and its selected text), and `${workspaceFolder}` from the repository. A value reaches the command as an environment variable and is never read as shell text: each placeholder in the line becomes `${OCULUS_ARG_1+"$OCULUS_ARG_1"}`, `${OCULUS_ARG_2+"$OCULUS_ARG_2"}` and so on, one number per placeholder name, and the terminal starts with each variable set to its value, so a selection holding blanks, quotes, `;` or `$(...)` arrives whole as those characters wherever the line writes the placeholder: bare, inside double quotes, in a here-document or inside `$(...)`. Inside single quotes that text is printed as written, as any `$NAME` is there, and a line that evaluates text itself (`eval`, `sh -c`, and `$((...))` arithmetic in bash) runs the value as code, which the approved line shows. A placeholder the page has no value for refuses the run and names it; any other `${...}` is left as written. Before each command the terminal prints a line of a token minted for that run and the command's name, by which its output is read.

## Approval

A command from a file of the repository or a found one runs only after you approved its exact text on this machine. The first press asks, listing every line of the command's chain in run order, each with its folder when it is not the repository's, with Approve and Run and Cancel. The chain is approved as one text together with the repository's real path, kept in the file the `approvals` key of `local.yml` names, so a changed line, folder or dependency asks again, a command that gains a dependency asks again for the whole chain, and the same text in another repository asks again. When the file is the default one, `~/.oculus/approvals.json`, its folder is made private to you (mode 0700) when it is looser; a file the `approvals` key puts elsewhere leaves its folder as it is. Approvals given before the text took this form (the repository's path and the whole chain, in place of each command alone) ask again. A command saved through the form is text you wrote into oculus and runs without the question.

## The result

A command's terminal stays in its tab after the line ends, with a green check for exit code 0 and a red cross otherwise; the server looks at a running command's terminal every five seconds, so the result shows at the next look. Rerun, on an ended terminal's menu and bar, runs the same line again in the same terminal and is refused while the line runs. Restart, on the same menu and bar, stops a running line and runs it again after a confirmation that names the process, and on an ended terminal does what Rerun does. A line in the output of the form `file:line:column: error: message` or `file:line: warning: message` has its `file:line:column` underlined under the pointer when the file exists under the repository (relative names are read from the command's folder), and a click opens it in a source tab at that line. The errors of a command's output are kept as the command's diagnostics and replaced when it runs again; a terminal no pane shows when its line ends is read once from the text of its tmux pane, and in a chain a relative file name is read from the folder of the command that printed it.

## The default build and test keys

Cmd+Shift+B (Ctrl+Shift+B off macOS) runs the default build and Cmd+Alt+T (Ctrl+Alt+T) the default test of the repository holding the file of the source tab on screen. With no such tab, no repository around the file or no command marked `default` for the key, the status bar says which is missing and nothing runs.
